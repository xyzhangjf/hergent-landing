## 三、本轮做了什么（已部署生产）

**① 定为单一权威**：主库 `users.employee_id`。`employee_code` 保留但**只作存量兜底、不再写入**。

**② 收敛成唯一实现**（`erp_db.py`）：三者是全仓唯一入口，5 处读端全部改走它们。
- `_emp_link_expr(alias)` —— SQL 表达式
- `resolve_employee_id(user)` —— 账号 → 员工
- `employee_account_map()` —— 员工 → 账号（**按 `user_tenants` 收口**）

**③ 删掉死列** `hr_employees.user_id`（主库 + 显式循环全部 `tenant_*.db`；列对账机制只补不删，不显式删会永久残留）。

**④ 修掉过程中抓出的 6 个真 bug**（都不是数据问题，是代码缺陷）：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 工资条把 user id 传在 `message_send` 第 **4** 位（那是 `sender`） | `recipients` 永远空 → **定向退化成全租户广播**，去重还把所有人的工资条折成一行 |
| 2 | `employee_account_map()` 没带租户过滤 | **跨租户认领**：tenant_1 的员工 7 能被别的租户认领 |
| 3 | 开账号绑定「任一 boss/admin 的第一个租户」 | 非 tenant_1 的租户给员工开账号，会绑到 tenant_1 |
| 4 | 小程序端 `report_mapping_mine` 用 `int('')` | 抛错 → 过滤整体失效 → 下拉里能看到**全租户**报单映射 |
| 5 | `has_account` 判的是「账号存在且启用」 | 账号一旦禁用，员工档案里**再也开不回来**（弹窗退回「开通账号」表单） |
| 6 | 建账号查重用 `AND is_active=1` | 禁用后再点「开通账号」→ 静默造出**第二个账号**（与 #5 互相放大） |

**⑤ 工资条改为 fail-closed**：取不到账号 → **返回失败且不投递**，绝不留空收件人兜底（留空 = 全公司可见）。

## 六、🔴 执行过程中新挖出的三个缺陷（**未修**，需你定夺）

### 6.1 租户库里藏着一张**陈旧的 `users` 表** → 4 个账号是幽灵

`tenant_1.db` 里的 `users` 表有 6 行：`admin` / `boss` / **`accountant`(王会计)** / **`sales`(李业务)** / **`warehouse`(赵仓管)** / **`driver`(张司机)**。
而主库 `users` 全表只有 7 行 —— **后 4 个在主库根本不存在**。

根因（已实读确认）：`/api/auth` 属于中间件的「主库/公开」前缀 → **登录只读主库**。
⇒ 这 4 个账号 **永远登不进去**，是历史遗留的幽灵账号（这也解释了「员工档案里王会计/赵仓管看着有账号、却开不了工资条」）。

### 6.2 `operator_id` 被**两种语义**写入（一个是人名、一个是 id）

- `routers/sales.py::_operator_for_role()` 的注释明确写着：**「We use display_name … historical orders + RMA all store the display name」** → 对业务员写 **人名**。
- `server.py:3172/3193`（损耗）也写人名；但 `server.py:3372/4413`、`payment_run.py:38` 写的是 **`str(u["id"])`**。

生产实测（tenant_1）：**`sale_orders` 580 单全部 `operator_id='张俊峰'`**（就是人名）。

### 6.3 三个报表因此**双重坏掉**，目前返回全 0

`GET /api/reports/salesperson` · `/api/reports/sales-leaderboard` · `/api/reports/commissions`（另 `scheduler.py:819`、`finance.py:662` 也在用）

| 缺陷 | 后果 |
|---|---|
| ① 名单取自**租户库那张陈旧 `users`** | 统计对象 = 幽灵账号集合，且真实账号 5/6/7 **不在名单里** |
| ② 拿 `operator_id` 与 `users.id` 比对 | 和实际的 `'张俊峰'` **永远对不上** → 结果全 0 |

⇒ 员工 580 单、**¥2,141,396** 的业绩，**一条都不会出现在报表里**。
🔴 另有**第二份实现**：`db/queries/reports.py:265` 与 `erp_db.py:3889` 各有一个 `get_sales_leaderboard`，两个调用方各走一份。

### 6.4 小问题：报单「提交人」名字取不到

`routers/forecast_submissions.py:282` 也从**租户库** `users` 取 `display_name` → 主库独有的账号（`mptest`，1 条）取不到名字，回退显示成「员工5」。

### 6.5 企微通道无法真定向（沿用上一轮结论）

工资条走的是**群机器人** webhook，群机器人本身**不能定向到个人**（`touser` 无效）。要在企业微信里也做到「只给本人看」，须改成**企微应用消息**。当前实现在返回值里**如实标注「站内未投递」**，不谎报成功。

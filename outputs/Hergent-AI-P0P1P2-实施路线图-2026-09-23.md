## P0 —— 不做就不能卖给第 2 个客户（硬截止：第 2 个真实租户上线前）

### P0-1 多租户隔离收口（A1–A6）

- **现状**：租户网关由 `hergent-erp.service` **fork 子查询进程**，全部同一 `hergent` 账号、`HOME=/opt/hergent-erp`（后端代码 + 全部 DB 目录）；systemd 无 `ProtectHome/ProtectSystem/PrivateTmp`；租户 AI 手里有 `terminal`/`write_file`/`browser`（出网）；**网页副驾网关以 root 运行**（v254 已列 P1 待拍板）。当前仅 1 个真实租户（tenant_1），**路径尚未激活**——第 2 个租户上线即生效。
- **目标**：租户 A 的 agent 执行任何命令都读不到租户 B 的数据；出网可管控。
- **步骤**：
  - **批 1（小时级，先做）**：`A2` 给子进程 env 显式设 `HOME=<租户home>`；`A4` 给 `hergent-erp.service` 补 `ProtectHome=`/`ProtectSystem=`/`PrivateTmp=`/`ReadWritePaths=`/`CapabilityBoundingSet=`（⚠️ v254 当时**有意未加**，需先做读写路径审计）。
  - **批 2（周级，架构）**：`A1` 每租户独立 OS 用户 + 模板单元 `hermes-gateway@tenant_N`；`A3` `*.db` 收 600 + 属主拆分；`A5` 网页副驾网关**从 root 降权**（不是停——它是 nginx `/hermes/` 的后端）；`A6` 出网默认拒绝 + 白名单域名 + 审计日志。
- **验收**：租户 A 的 agent 读租户 B 的 `.env`/主库 **必须失败**；`grep` 进程环境确认 `HOME` 正确；出网仅白名单放行。
- **依赖/风险**：A5 降权须先确认新 home 下 `SOUL.md` 路径与 nginx 代理不变；A4 需先做读写路径审计（否则会误伤备份/日志写入）。

### P0-2 安全债还债（密码 8 位上限 + 明文凭据）

- **现状（代码事实）**：`core.py:10` `SECRET=os.environ["ERP_SECRET"]`；`:23` 注释明写「bcrypt 只处理前 72 字节，而 ERP_SECRET 本身占 64 字节」；`:33 _hpw()`；`:70` 另有最小长度 8。⇒ **密码实际最长仅 8 字符**。另：仓库内已跟踪文件含 Hermes 网关 Bearer 密钥、提审账号、老板手机号（详见记忆 §四）。
- **目标**：密码可 ≥12 位；仓库无明文凭据；出网可审计。
- **步骤**：
  1. **改 `_hpw`**：引入**预哈希**——先 `hmac/sha256(pepper + pw)` 再送 bcrypt，输出固定长度 ⇒ **彻底绕开 72 字节限制**。🔴 **必须保留 `_hpw_old` 兼容存量密码**（boss/审核员 `mptest`/`mptestsp` 的哈希不可失效），登录验证走「新算法 → 失败则退旧算法 → 成功后可选升级哈希」。
  2. **凭据治理**：轮换已入库的网关密钥/测试账号密码；新文件入库前跑凭据扫描；确认远端仓库为 private；密钥统一走 `.env`（600）。
  3. **出网白名单**：并入 P0-1 的 A6。
- **验收**：可成功设置并登录 12+ 位密码；旧密码仍可登录（兼容）；`git grep` 全仓关键凭据 0 命中。
- **风险**：改哈希属认证核心路径，必须在**沙箱租户**先跑通再上生产，且**先备份主库**。

### P0-3 连接器收口：补用友 + 真机联调（修正后）

- **现状**：金蝶 `kingdee_connector.py`、畅捷通 `chanjet_connector.py` 已存在；`datasources_v2.py` 两家各有 5 个端点（OAuth connect/callback/status/disconnect/sync + 全量同步 `sync_source`），且 v254 已修掉 `state` 明文伪造漏洞（改 HMAC 签名）；`datasource_adapter.py` 已就位（回写走连接器框架）；`ConnectCenter.vue` 已有 UI。
  **缺**：① **用友（Yonyou）完全没有**；② 🔴 **实测（2026-09-23 23:2x）：生产 `.env` 中 `KINGDEE|CHANJET|YONYOU` 凭证**计数 = 0** ⇒ 两家连接器**代码就位但从未配置、从未真机联调过**（比"只缺联调"更严重：等于从未跑通）；③ `chanjet_connector.py` 头部注释**自述**"业务 API 路径为 T+ 默认占位，待联调按真实响应校准" ⇒ 即便配上凭证也需校准字段；④ 前端「同步进度/失败原因」可见性未知。
  🔴 **用友不凭空写**：畅捷通 T+ 本身即用友集团产品（已覆盖小微），"用友"通常指 U8/U9/NC/YonSuite——**其 OAuth 与业务 API 形态未核实，凭猜测写连接器 = 产出"看着像样实则错"的代码**（正是本项目最忌讳的静默失效）。⇒ 前置：拿到用友开放平台官方文档 + 客户应用后，再克隆 `chanjet_connector.py` 改写，**不在无文档时落地**。
- **目标**：客户授权后，Hergent 能自动拉到其 ERP 的本期订单与库存，无需手工导出。
- **步骤**：
  1. 新增 `server/yonyou_connector.py` + `datasources_v2.py` 的 `/yonyou/*` 五端点（**克隆 chanjet 结构，改 API 地址与 source 标识**，与现有两家同构）。
  2. 三家凭证统一走 `.env`（600）+ `ConnectCenter` 配置界面补「同步进度 / 最近同步时间 / 失败原因」。
  3. **真机联调**：用沙箱租户跑通一次完整 OAuth + 全量同步（商品/客户/订单/库存）。
  4. 口径纪律：**同步只读**；任何回写一律经 `DataSourceAdapter`，不新增自研 ERP 写操作。
- **验收**：沙箱租户完成一次 OAuth 授权 → 全量同步成功 → 数据落到该租户库，且**不跨租户**。
- **依赖**：需客户真实开放平台应用（商务侧）与真机联调时间——这是唯一非纯技术的阻塞项。

## P1 —— 做完才「真的帮上忙」（季度内）

### P1-1 「录」层：报单/目标录入智能化（修正后）

- **现状**：`import_router.py:347 _suggest_mapping_smart()` 已有**智能列映射建议**；但缺「导入前让用户看到每列被识别成什么、并可改判」的确认界面（对应既有 skill `hergent-import-mapping-confirm`）。报单/目标仍主要靠人填。
- **步骤**：① 给预报导入加**列映射确认 UI**（展示识别依据 + 前几行样例 + 可改判且真生效）；② 目标下达支持自然语言转结构化（如「蒙牛 8 月目标 50 万」→ 结构化记录）。
- **验收**：传一张陌生格式的报单表 → 系统自动识别列 → 用户改判一列 → 导入结果确实按改判走。

### P1-2 「算→说」收口 + 真正的「判」层（修正后：拆成两件事，别混为一谈）

**P1-2a 收口「算」层 → 「本周建议订购清单」（零 AI 成本，先做）**
- **现状**：确定性建议能力已散落 6+ 处（见 §0），但没有统一入口，老板看不到「一份建议」。这些是**「算」层**（确定性、可复算、可审计），**不需要 AI 推理**即可收口。
- **步骤**：① 收敛为单一只读服务，聚合「预测需求（forecast_engine）+ 在途（arrival_schedule）+ 库存/效期（FEFO）+ 临期降价建议」→ 输出「本周建议订购清单」；② 复用既有「今日建议订货」卡（`hermes_core.py:1165` / `ai_roles.py:398`）展示，**不新造卡型**；③ **必须带口径披露**（数据来源 + 「AI 只建议，下单还是你点头」——比通用助手强的地方，别丢）。
- **验收**：副驾给出「本周建议订购清单 + 每行依据」，可溯源到具体数据表。

**P1-2b 真正的「判」层（需新建 AI 能力，后做）**
- **现状**：掉量归因 / 多目标权衡（毛利 vs 临期 vs 现金流）/ 先出哪批的取舍 —— **仍接近空白**（这些没有唯一答案、靠经验）。
- **步骤**：先做「掉量归因」（为什么这个品/这个店掉量），再做「先出哪批」的多目标排序；**AI 只出建议与理由，绝不自动改数**（与「AI 工具全部只读」铁律一致）。
- 🔴 **顺序纪律（不可颠倒）**：P1-1 干净数据 → P1-2a 算层收口 → P1-2b 判层。没有干净数据就上「判」，只会给出「看着像样实则错」的建议，**比没有更伤信任**。

### P1-3 副驾「经营一页纸」视图（修正后）

- **现状**：`CopilotDrawer.vue` **已有**全屏 + 产物区 + 拖拽分割线 + 区域全屏，不缺框架。
- **步骤**：在全屏态内补一个「本期经营一页纸」入口视图——四宫格（预报达成 / 货损 / 回款 / 返利）+ 异常清单，点击可下钻到对应模块；保留聊天为默认态。
- **验收**：点开副驾全屏即见一页纸，非纯聊天；窄屏下不塌陷。

### P1-4 一键生成汇报材料（Word/PPT）

- **现状（2026-09-24 已做 · v259）**：后端 `/api/meeting/export-docx` 用 `python-docx` 把 `get_weekly_report` 的**确定性经营数据**（销售额/环比/应收逾期/低库存/TOP 客户/预报期次/议程建议/待跟进模板）渲染成真正的 `.docx` 文件；前端 `Workbench`「本周建议订购清单」卡加「生成经营周报（Word）」按钮，复用 Bearer token 鉴权触发下载。金额统一「万元」口径并附数据来源披露（护城河）。
- **缺陷**：PPT 仍未做（python-pptx 同理可加，但 PPT 排版复杂，留待下轮）；报告模板目前只有「周报」一种，月报/返利对账待扩展（后端 `get_weekly_report` 现硬编码 7 天窗口，扩 monthly 需改时间窗）。
- **验收**：登录后点按钮 → 浏览器下载 `.docx` 周报，可直接打印/转发。
- **运维**：⚠️ 生产新增后端依赖 `python-docx==1.2.0`（已 `pip install` 到系统 python3）；下次整目录重部署/新机恢复需记得补装，否则该端点 500。

## P2 —— 放大护城河（半年内）

### P2-1 技能生态开放
- **现状**：`routers/ai_skills.py` **只有 `GET ""`**（:83/:84），转发 Hermes 只读列表；Hermes 自带 5 个技能基础设施模块（`skills_hub` / `skills_guard` / `skill_manager_tool` / `skills_sync` / `skill_provenance`）**尚未接出**。
- **步骤**：先把这 5 个模块接出（不要自造插件体系）→ 再做「行业配方市场」（经销商可装「蒙牛低温奶标准配方」）→ 最后才谈用户自定义插件。
- 🔴 **前置**：用户自定义插件必须等 P0-1 的 A1/A3/A6 完成（否则租户可跨租户读写）。

### P2-2 自动化产品化
- **现状**：报单提醒面板已做（per-tenant 自配，2026-09-23 上线）；引擎 Cron 已有。
- **步骤**：把「每日晨报 / 货损预警 / 回款催收」也做成同款 per-tenant 开关面板，复用 `reminder-config` 的归一化与审计模式（带护栏下拉，不开放自由 cron 表达式——非技术老板易配错漏报）。

### P2-3 回复质量量化 + 校验兜底
- **现状**：`_REPLY_FORMAT_PROTOCOL` **重复定义两份**（`ai_roles.py` 生效于前端副驾、`hermes_core.py` 生效于 `/api/ai/chat`），**改协议必须两处同改**；已知盲区：骨架/篇幅/加粗/表格**无量化要求**（真实回复篇幅差 7.7 倍、加粗差 21 倍、表格 0 条使用）；`ResultCard.vue:149` 只取前 4 列，第 5 列起静默丢弃。
- **步骤**：① 用「脚本一次产出再分发」保证两份协议一致（手抄必分叉）；② 补篇幅/加粗/表格的量化规则 + 校验与显式降级；③ `ResultCard` 第 5 列起不能静默丢（要么分页要么显式提示）。

### P2-4 跨租户经验闭环（越用越聪明）
- **现状**：地基已有（`ai_advice_log` / `recipe_proposals` / `review_trust_levels` / `workflow_recipes`），但 **3 个断点**：① `modified_by_user` 只存人名不存改后值（「AI 说 7 我改 5」的 Delta 丢失）；② `recipe_proposals` 无「同类覆写重复 N 次→自动提案」触发；③ 跨租户真值共享未做。
- **步骤**：按断点逐个补，且**跨租户只共享「算法口径」（参数名+量级桶）**，金额/工资/客户/进货价/返利费率**一律红线**（商业秘密，非个人数据）。
- **验收三合一**：`source_ref` 非空（可回溯）+ 30 天内被 ≥2 场景复用 + 回归否决率 = 0。

## §P0-1 批2 收尾说明（A1 / A6 为什么推迟 + 后续步骤）

> 2026-09-24 已落地的：**A3**（全部业务库 `*.db` 已 `600`，含补齐此前漏掉的 `bid_radar.db`）、**A5**（网页副驾网关 `hermes-gateway.service` 从 **root 降权为 hergent**，数据目录 `/root/.hermes` chown 为 hergent，端口 18765 现由 hergent 绑定，旧 root 进程已退出，网关仍正常服务 10 个技能）。

**A1（每租户独立 OS 用户 + systemd 模板 `hermes-gateway@tenant_N`）—— 推迟，非不做：**
- 理由：当前**只有 1 个真实租户**（tenant_1 有数据；tenant_9/tenant_10 是空白结构孤儿库）。A1 是「卖 SaaS 给第 2 个客户」的硬前置，但第 2 租户未上线时造 OS 用户 + systemd 模板属于**为未来脚手架**，且会改动已稳定运行的单租户部署，收益为 0、风险不为 0。
- 现有隔离已就位：租户网关（PID 2538375）已通过 `HOME=/opt/hermes-tenants/hergent_t1` 实现**按租户数据目录隔离**；A2/A4/A5 已把「HOME 隔离 + systemd 沙箱 + 非 root」三道关补齐。**租户 A 的 agent 当前已读不到租户 B 的数据目录**（分属不同 HOME）。
- 后续步骤（第 2 租户临近时做，半天内可完成）：① 写 `hermes-gateway@.service` 模板，按 `%i` 注入租户 HOME 与端口；② 创建 `hergent_tN` OS 用户；③ 把 `*.db` 属主从 `hergent` 拆分为 `hergent_tN`（即 A3 的「属主拆分」子项，依赖 A1）；④ 验证跨租户读失败。

**A6（出网默认拒绝 + 白名单域名 + 审计日志）—— 推迟，且必须分阶段：**
- 理由：**在生产机上对出网做默认拒绝是高危操作**。当前 Hermes 网关要出网调 LLM API（DeepSeek 等）、企业微信/飞书/钉钉推送、可能的短信网关；一旦默认拒绝且白名单不全，**副驾直接变哑巴、手机推送全断**，属于「比没有更伤信任」的静默失效。
- 正确做法（不要一次性 default-deny）：① 先用 `conntrack`/`auditd` 或网关访问日志**枚举 2~4 周的真实出网目的域名/IP**（白名单必须来自实测，不能猜）；② 以 **log-only / 软拦截**模式先跑一周，确认无漏报；③ 再切硬拒绝。这一步必须在第 2 租户临近、且白名单实测完整后做。

**结论**：P0-1 批2 中「不依赖外部方、且当下就有价值的」A3/A5 已收口；A1/A6 是「第 2 租户前置」，按上面步骤在第 2 租户上线前完成即可，**现在做反而引入不必要的风险**。

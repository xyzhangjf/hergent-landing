## 一、小程序与网页端权限隔离

### 1.1 扫描证据：当前**没有**端隔离能力（四条独立判据）

**判据 ①：登录端点真代码 75 行，无一处读角色或端**
`server/routers/auth.py:148-241`（用语法树提取函数体、剔除注释后的真代码）：

```python
async def login(request: Request):
    d = await request.json()
    body = LoginRequest(**d)
    u, p = body.username, body.password
    ip = _client_ip(request)
    locked, reason = _check_login_lockout(u, ip)          # ① 锁定检查
    ...
    user = conn.execute("SELECT * FROM users WHERE username=? AND is_active=1", (u,)).fetchone()
    if not user or not _verify_password(p, user["password_hash"]):   # ② 账号存在 + ③ 验密码
        raise HTTPException(401, "用户名或密码错误")
    token = secrets.token_urlsafe(32)                     # ④ 发令牌
```
⇒ 全程只有「锁定 → 账号 → 密码 → 发令牌」，**没有 `role`、没有请求头端识别**。

**判据 ②：登录请求根本不进权限中间件**
`server/server.py:674`
```python
_PUBLIC_PATHS = {"/api/auth", "/api/system", "/api/health", ...}
```
⇒ `/api/auth` 前缀豁免 ⇒ **任何端限制都不可能写在中间件里**（登录时还不知道你是谁，这是必然设计）。

**判据 ③：数据库没有存端的字段**
`server/core.py:164` 建表 + 后续补列，用户表实际列为：
`id / username / password_hash / display_name / role / is_active / created_at` + `password_changed`(core.py:177) + `roles`(core.py:190) + `phone / employee_code / pinyin / department_id / employee_id`(erp_db.py:2185-2191) + `mfa_*`(routers/mfa.py:244-252)。
全仓扫描 `allowed_client|login_scope|allow_web|web_login|mini_only` ⇒ **零命中**。

**判据 ④：小程序不带任何端标识，且与网页端共用同一接口**
小程序 `utils/api.js:77-81` 请求头只有三项，`X-Tenant-Id` 是租户头不是端标识：
```js
header: { 'Content-Type': 'application/json',
          ...(token ? { Authorization: 'Bearer ' + token } : {}),
          ...(tenantId ? { 'X-Tenant-Id': String(tenantId) } : {}) }
```
登录页 `pages/login/login.js:112` → `POST /api/auth/login`；网页端 `src/api/client.js:66` 打的是**同一个接口**。
后端注释亦确认（`routers/auth.py:86-88`）：「本接口被**微信小程序共用**」。

⚠️ 一条容易误读的既有标注：`src/constants/roles.js:132-136` 的 `ROLE_END` 写了 `staff: 'mini'`（仅小程序）——
它描述的是**能力**（这个角色的权限只够撑小程序那批接口），**不是登录入口闸门**；实测 `staff` 在网页端照样能登录成功。

### 1.2 方案：默认小程序 + 可选其他端

**新增能力名：登录范围（`login_scope`）**

| 项 | 设计 |
|---|---|
| 数据模型 | 用户表加一列，照现有补列机制（**不建新表、不动主外键**）：<br>`_safe_migrate('vXXX_users_login_scope', "ALTER TABLE users ADD COLUMN login_scope TEXT DEFAULT 'both'")`<br>（范例见 `erp_db.py:2185`） |
| 取值 | `mini` = 仅小程序｜`both` = 两端｜`web` = 仅网页端 |
| 默认值来源 | **复用现成的 `roles.js::ROLE_END`**（`staff→mini`、`guide/driver/accountant→web`、其余 `both`），**不另抄一份名单** |
| 校验位置 | 🔴 **只能写在登录端点内部**（`auth.py::login`）—— 中间件对 `/api/auth` 豁免，写在别处一律无效 |
| 端识别 | 请求头 `X-Client: mini\|web`。🔴 **缺头视为小程序（fail-open）** —— 存量小程序不带这个头，且已备案上线、改客户端要重新提审；设成「必带头」会**当场切断所有存量小程序登录** |
| 安全定性 | 客户端可伪造该头 ⇒ 这是**产品约束（防误登/防串岗），不是安全边界**。真正的边界仍是后端模块权限 |
| 回滚开关 | 环境变量 `LOGIN_SCOPE_ENFORCE=0` ⇒ 判据整段跳过，故障时一键恢复 |
| 存量迁移 | 存量账号一律 `both` ⇒ **零破坏性收紧**（不会有人在用的能力被收掉） |

**界面（用户管理模块）**：
在 `EmployeeArchive.vue` 的「账号与权限」区加一组三选（仅小程序 / 网页端+小程序 / 仅网页端）：
- 默认跟随角色（`ROLE_END`），**可手动改** ⇒ 满足「默认小程序权限 + 可选其他权限」；
- 改完调现有改账号接口，并**接入 B 链版本号**（见第三节待办 ④），否则要重新登录才生效。

**需要改动的文件**

| 文件 | 改动 |
|---|---|
| `server/erp_db.py` | 补列 `login_scope`（照 `_safe_migrate` 范式） |
| `server/routers/auth.py` | `login()` 内加端判据（fail-open + 回滚开关 + 审计日志） |
| `server/core.py` | 若新增写接口则接 `normalize_role` 同款白名单模式 |
| `hergent-cn-v2/src/pages/EmployeeArchive.vue` | 加「可登录端」三选 + 默认值取 `ROLE_END` |
| `hergent-cn-v2/src/constants/roles.js` | `ROLE_END` 已是唯一源，仅补注释说明它现在既是能力标注也是默认值来源 |
| 后端 `/api/users/{uid}/login-scope` | 新增或并入现有改账号接口 |

## 二、分销商（外部客户）权限入口

### 2.1 扫描证据：分销商当前**无处可配**，根因有两条

**根因 ①：分销商角色根本不存在。**
`server/core.py::_DEFAULT_PERMS` 用语法树取键（**不用正则**，该文件注释里也有角色名会骗人），实测 **8 个角色**：
`admin / boss / accountant / sales / guide / driver / staff / supervisor`。
⇒ **没有 `dealer`，也没有 `promoter`**（`promoter` 只存在于小程序 `utils/roles.js:38-50 ROLE_TEXT` 作别名，后端无对应权限）。
全仓 `dealer|distributor` 在小程序侧 **零命中**；「分销商」一词仅出现在三处注释里（`mine.js:70`、`auth.py:562`、`forecast_submissions.py:4`）。

**根因 ②：开账号强制绑定"真实存在的员工"。**
`server/erp_db.py:18963 staff_account_create`：
```python
_eid = int(employee_id or 0)
if _eid <= 0 or not _get_employee(_eid):
    return {"success": False, "detail": "请先保存员工档案，再为其开通登录账号"}
```
⇒ **外部客户没有员工档案 ⇒ 走不通这条唯一开账号链路**。这就是「系统中没有为其配置权限的入口」的技术根因。

**附：现有权限配置入口的真实位置（两处，不是三处）**

| 入口 | 语义 | 落库 | 界面 |
|---|---|---|---|
| A 链「设置 › 权限」 | 角色 × 模块（这个角色能干什么） | **租户库** `role_permissions` | `Settings.vue`（`ROLE_LABELS`:527 / `permsToModules`:568 / 保存后 `loadPerms(true)`:626） |
| B 链「员工档案 › 账号与权限」 | 账号 × 角色（这个人是谁） | **主库** `users.role` | `EmployeeArchive.vue` |

⚠️ 两个易混淆点：
- `RoleManage.vue` **不是**角色权限管理，它是 **AI 团队配置**（`RoleManage.vue:5` `<h2>AI 团队</h2>`）；
- `CustomerArchive.vue` **不是**业务客户档案，它是**数据源同步页**（仅 122 行，内容是畅捷通/金蝶同步 `customers` 对象）。且**系统没有 `customers` 主数据表**（只有 `customer_prices` 千店千价表）。

### 2.2 方案与理由：入口放**员工档案的「外部客户账号」分区**

**推荐：不放客户档案。** 理由三条（按权重）：

1. **跨库**：登录账号在**主库 `users`**（全平台一份），客户业务数据在**租户库**。放客户档案 ⇒ 一个界面要跨库写两处，破坏现有多租户隔离边界。
2. **客户档案实体不存在**：当前无 `customers` 表、无业务客户档案页。为放一个入口先造一整套客户主数据，**成本是前者的数倍**，且会牵动价格方案、门店范围等一批下游。
3. **复用度**：员工档案已有密码策略（`core._validate_password`，v289 刚收敛成唯一实现）、角色白名单（`normalize_role`）、自助改密通道（`auth.py:558 forgot-reset`，其注释明确点名「业务员/分销商/导购可能只登录小程序」）。放同页 ⇒ 这些**全部可复用**。

**具体做法**

| 项 | 设计 |
|---|---|
| 角色 | 新增内置角色 `dealer`（分销商）。🔴 **必须走 9 处接线**（`_DEFAULT_PERMS` / `roles.js::ROLE_NAMES`+`ROLE_END` / `EmployeeArchive.vue::ROLE_OPTIONS`+色板 / Forecast 名单 / 小程序 `ROLE_TEXT` / `APPROVER_ROLES` / 白名单调用点 / `pages.js::PAGE_RULES`），漏一处就漂移；改完跑护栏 |
| 默认权限 | `dealer` 默认 **仅 `data`**（够跑通小程序报单闸即可）+ `login_scope='mini'`（承接第一节） |
| 开账号 | `staff_account_create` 加参数 `external=1` ⇒ **跳过员工校验**，改以客户名/手机号作为身份，并写 `external_ref` 字段留痕（不复用 `employee_id`，避免污染工资/人事口径） |
| 界面 | 员工档案页新增「外部客户账号」分区：账号 / 密码 / 关联客户 / 可登录端（默认仅小程序）/ 启用停用 |
| 报单范围 | 沿用现有 `employee_stores` 门店范围机制；若需按客户限制商品可见范围，属**另一项**能力，本方案不含 |

**备选（若日后出现真正的客户档案）**：再在客户档案加「开通报单账号」按钮，底层仍调同一个 `external=1` 分支 ⇒ 界面两个入口、逻辑一份。

### 3.3 ③ 界面按权限动态渲染 —— ✅ 已有，四个消费方同一判据

判据唯一源 `src/constants/pages.js`：**17 条页面规则 × 两条轴**（`module` = 本租户买没买这个能力；`roles` = 这页天然只给谁），外加一条让位规则：

```js
function roleGateOpen(r, role, customRoles) {
  if (!r.roles) return true                      // ① 不按角色收紧
  if (roleIn(role, r.roles)) return true         // ② 在内置名单里
  if (r.lock === true) return false              // ③ 产品硬锁（/roles 与 /settings）
  if (!r.module) return false                    // ④ 安全阀：无 module 不让位（防全开）
  if (!Array.isArray(customRoles)) return false  // ⑤ 不知道 ⇒ 收紧
  return customRoles.includes(normRole(role))    // ⑥ 客户自己配的优先
}
```

## 四、建议实施顺序

1. **第一节（登录范围）** —— 独立、风险最低，且第二节的默认值依赖它；
2. **第二节（`dealer` 角色 + 外部账号分支）** —— 依赖第 1 步的端限制，且要跑 9 处接线护栏；
3. **第三节缺口 ①** —— 把小程序闸从「只看 `data`」升级为「按后端返回的模块集判」，与网页端同一口径。

⚠️ 三步都涉及登录/权限，**部署顺序必须是：先迁库补列 → 再上后端 → 最后上前端**，且第 1 步必须带回滚开关（存量小程序不带新头）。

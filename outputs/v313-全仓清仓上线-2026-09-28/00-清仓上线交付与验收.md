## 二、🔴 先说最险的一件事：差点把服务搞崩，靠一步干跑拦住

我第一遍按「`git status` 有改动的文件」去找"未部署"，**漏了 3 个文件**。

**漏的原因**：那 3 个文件**已经在 git 里**（别的会话提交过，`git status` 干净），
但**生产从未部署过**。`git status` 只回答「工作区 vs git」，**回答不了「git vs 生产」**。

结果 `erp_db.py` 上传后 import 直接失败：

```
ImportError: cannot import name 'income_order_create' from 'db.queries.finance'
```

✅ **救场的是「上传后、重启前的一次 import 干跑」** —— 服务**一秒都没停**就抓到了。
如果直接 `systemctl restart`，服务就起不来了（真事故）。

**正确口径**（已写进部署技能）：`未部署 = 本地 server/**/*.py 的 md5 ≠ 生产对应文件的 md5`，
**与 git 是否标记改动无关**。全量扫 210 个 py ⇒ 207 相同、**3 个不同**
（`db/queries/finance.py` / `db/queries/purchases.py` / `routers/zhoupu_documents.py`）。

## 五、两个"判据自己出错"的实证（都当场改了）

1. **扫描脚本第一版是假绿的**：它只看「纯删除 hunk」，抓不到**替换型 hunk** 里藏的生产独有内容
   （`server.py` 那两行注释）。⇒ 改成**所有被删行都人工过一遍**。
2. **API 超集比对报了 24 个"前端用了后端没有的接口"，全是假阳性**：
   把 `from '../api/modules.js'` 这种** import 路径**当成了接口、模板变量没归一化、拼接前缀被截断。
   ⇒ 改成**按前缀去后端接口清单里查**，逐条定性。唯一真缺的 `/api/inventory/near-expiry`
   还是**零调用方的死代码**（首次纳入源码就有，非本次引入）⇒ 不发请求，无害。

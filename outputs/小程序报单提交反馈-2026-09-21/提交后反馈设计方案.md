# 小程序报单「提交后反馈」分析与改进方案

日期：2026-09-21 ｜ 范围：`forecast-order-miniprogram` · 填报页（`pages/fill`）
性质：**方案稿（未改代码）**，实施时再起号（当前已用到 v222，起号前须按约定 grep 复核）

---

## 结论先行

用户说「提交后仍停留在填报页，无法确认是否提交成功」。逐行核对真实代码后，结论是：
**问题不是"没有反馈"，而是反馈被放错了位置，而且最该出现的那条回执是死代码。**

四条硬事实（都有代码位置）：

1. **唯一持久回执在页面顶部，而提交按钮固定在屏幕底部，成功后不滚动** —— 用户点完提交，视线在底部，
   看不到顶部那条「✓ 本期已报 N 项」。
2. **最该出现的那条回执（「今日 X 店已报 N 件」）是死代码**：它的显示条件是
   `lastReported && !cartCount`，而「提交成功后刻意不清空数量」是既定设计 ⇒ `cartCount > 0` 恒成立
   ⇒ 正常路径下**永远不显示**。
3. **成功后页面看上去"什么都没发生"**：数量还在、商品行仍高亮、底部计数不变，唯一变化是按钮文案
   从「提交中…」变回「提交预报」。
4. **全程看不到单号**：成功弹窗里没有单号，顶部横幅存了 `sid` 却不渲染，「我的提交」列表也不显示
   ⇒ 用户唯一能看到单号的地方，竟然是"你重复提交了"的警告框。

外加两条会**主动误导**用户的缺陷：

- 前端警告框写「再提交会**新增一单**」，而后端按 `(人, 门店, 期次)` 幂等，实际是**覆盖同一单**
  —— 用户被告知错误预期，去「我的提交」只看到一条、且单号已变，于是更懵。
- 提交失败时**所有错误**（含"商品不在本期清单""本期已定稿"这类**改数据才能解决**的错误）都统一
  提示「…已存草稿」，并被 `onShow` **自动反复补传** ⇒ 用户以为"系统会帮我重传"，实际永远失败。

## 一、现状取证：已有什么 / 缺什么

### 1.1 已有的反馈机制（不能算"没做"）

| 机制 | 位置 | 实际效果 |
|---|---|---|
| 提交中禁用按钮 | `fill.wxml:145` `disabled="{{submitting}}"` | ✅ 有效（防连点） |
| 首次提交前确认框 | `fill.js:671-683`「确认提交预报？」 | ✅ 有效（含门店/期次/项数/件数） |
| 成功弹窗 | `fill.js:729-735`「提交成功」 | ⚠️ 会被关掉、消失后无痕 |
| 成功持久回执 | `fill.wxml:49-52` 绿色横幅 | ⚠️ **在页面顶部，不在视野内** |
| 「今日已报 N 件」回执 | `fill.wxml:61` | ❌ **死代码**（见 1.2） |
| 失败 toast + 草稿 | `fill.js:737-741` | ❌ 不区分错误类型 + 自动重试 |
| 「我的提交」列表 | `pages/mine/mine.wxml` | ✅ 有，但不显示单号 |

### 1.2 关键取证：那条回执为什么永不出现

```xml
<!-- fill.wxml:61 -->
<view class="reported-note" wx:if="{{lastReported && !cartCount}}">{{lastReported}}</view>
```

- 写它：`fill.js:712` `this.setData({ lastReported: msg })`（仅提交成功时）
- 清它：`fill.js:212`（切期次）、`fill.js:499`（切门店）、`fill.js:760`（清空购物车）
- 显示条件要求 `!cartCount`；而 `fill.js:714` 注释明确写着
  「**提交成功后不再清空**——数据留在页面上，方便查看/微调/下期沿用」

⇒ **写它的那一刻，显示条件必然为假。** 唯一能把 `cartCount` 归零的常用操作是「清空重填」
（`clearCart`），而它自己会把 `lastReported` 抹掉（`fill.js:760`）。
结论：这条「今日已报 N 件」在正常路径下**不可能被用户看到**（只有用户手动把每个商品数量减到 0 才会闪现）。

### 1.3 关键取证：「看不到」的机械原因

| 事实 | 证据 |
|---|---|
| 提交按钮**固定在屏幕底部** | `fill.wxss:51` `.submit-bar{position:fixed;left:0;right:0;bottom:0;…z-index:10}` |
| 持久回执在**页面顶部**（门店/期次选择器之下） | `fill.wxml:49-52`，位于 `store-bar` 与搜索栏之间 |
| 成功后**不做任何滚动** | `pageScrollTo` 仅出现在 `fill.js:106`（恢复滚动位置）、`:119`（回到顶部）、下拉刷新 —— **成功分支没有** |
| 也没有滚动锚点 | `fill.wxml` 无 `scroll-into-view`、回执块无 `id` |

⇒ 回执在顶部、视线在底部、成功后不滚动、且没有锚点可定位。**这是"看不到"的直接原因。**

### 1.4 关键取证：前端文案与后端语义相反

```js
// fill.js:661
content: `${store.name} 在「${period.name}」已报 ${dup.count} 项 / ${dup.qty} 件（单号 ${dup.sid}）。\n再提交会新增一单，确定继续？`
```

```python
# 后端 server/routers/forecast_submissions.py:203-220
# 「重复提交=覆盖更新，避免汇总总量被叠加放大；已审批通过则禁止覆盖」
#   幂等键 = (user_id, store_id, period_id)
```
```python
# 后端 :366-369 —— 新明细校验通过后才删旧单
if _prev_sub_id:
    conn.execute("DELETE FROM forecast_submission_items WHERE submission_id=?", (_prev_sub_id,))
    conn.execute("DELETE FROM forecast_submissions WHERE id=?", (_prev_sub_id,))
```

⇒ 后端是**覆盖**（旧单被删、新单新建 ⇒ **单号会变**），前端却说「新增一单」。**文案是错的。**

### 1.5 关键取证：单号拿得到，只是没展示

- 后端返回体含单号：`erp_db.py:16828` 的 `forecast_submission_create` 返回
  `{"success": True, "submission_id": sid, "total_qty": …, "total_amount": …}`
- 前端也读到了：`fill.js:724` `sid: (d && (d.id || d.submission_id)) || ''`，存进了 Storage
- **但三处展示都不含它**：成功弹窗（`:729-731`）不含、绿色横幅（`fill.wxml:50`）只渲染
  `count/qty/at`、`mine.wxml` 记录行只渲染门店/日期/状态/件数
- ⇒ 单号**唯一出现的地方是"重复提交"警告框**（`fill.js:661`）

### 1.6 关键取证：防重复提交是"薄"的

| 层 | 现状 | 缺口 |
|---|---|---|
| 前端即时 | `submitting` 禁按钮 | 只挡连点；**无客户端幂等键**（grep `uuid\|idempot\|nonce` = 0 命中） |
| 后端幂等 | 键 = `(user_id, store_id, period_id)`，覆盖式 | **键含 `user_id`** ⇒ 同一门店同期次由**两个人**（两个业务员 / 业务员+督导）各报一次 = **真变两条**，汇总翻倍 |
| 定稿保护 | `approved` ⇒ 409 | ✅ 只有历史数据会命中（审批流已下线） |
| 撤回 | `pages/mine` 对 `pending` 提供「撤回」 | ✅ 是"报错了"的正规补救路径，应在反馈里告知 |

## 二、根因归纳

| # | 根因 | 性质 | 直接后果 |
|---|---|---|---|
| **A** | 持久回执位置与视线错配（顶 vs 底，且不滚动、无锚点） | 布局/交互 | 「看不到反馈」← 用户主诉 |
| **B** | 回执显示条件 `!cartCount` 与「成功后不清空」互斥 | 逻辑死代码 | 最贴题的那条回执永不出现 |
| **C** | 前端文案（新增一单）与后端语义（覆盖）相反 | 口径不一致 | 用户预期错误，越查越乱 |
| **D** | 单号全程不可见 | 信息缺失 | 无法与文员/管理员对账 |
| **E** | 错误无分级 + 不可重试错误被标「已存草稿」并被自动反复补传 | 状态机缺陷 | 「以为会重传」→ 永远失败；每次进页面弹确认框 |

**E 的细节**（值得单独看）：
```js
// fill.js:737-741 —— 所有失败一视同仁
} catch (e) {
  this.setData({ pendingSubmit: true })
  wx.showToast({ title: (e.message || '提交失败') + '，已存草稿', icon: 'none' })
}
```
```js
// fill.js:102 —— onShow 里自动补传
if (this.data.pendingSubmit && this.data.cartCount && !this.data.offline) this.resumeDraft()
```
- `400`（商品不在本期清单 / 已停售 / 未录厂价 / 数量超上限）与 `409`（本期已定稿）**都不是网络问题**，
  重试一万次也一样失败，却被标成"已存草稿"+自动补传；
- 补传会再次走到「确认提交预报？」弹窗 ⇒ **用户每次回到填报页都被一个确认框拦一下**，
  而且他不知道为什么弹；
- `resumeDraft()` 在 `onShow` 里是**同步**调用，紧跟 `loadPeriods()`（异步、未 await），
  此刻 `this.data.period` 仍是 `{}` ⇒ 会撞上 `fill.js:650` 的前置校验，弹一句
  **「请先选择报单期次」**（而用户其实选过期次，只是还没加载完）。
  同文件里 `onPullDownRefresh`（`fill.js:69-73`）已经修过**同类竞态**（先定期次再铺商品），
  这条自动补传路径**没修**。

## 三、方案对比

> 三个方案的差别不在"要不要给反馈"，而在**提交成功后把用户安置在哪里**。

### 方案 A：页面内「提交结果卡」+ 滚动锚定（最小改动）

**做法**：不新增页面。提交成功后，在**提交栏正上方**渲染一张结果卡（当前视野内），并把页面
滚动到该卡；卡片常驻直到用户改动数量。

- 卡片内容：绿色对勾 + 「已提交成功」+ **单号（可点击复制）** + 门店 · 期次 + N 项 · M 件 +
  提交时刻 + 跳过项说明
- 两个动作：「查看我的提交」（主）· 「继续修改」（次）
- **状态化**：用户一旦改动数量，卡片变为「本期已报 N 件 · 当前有未提交的改动」

| 维度 | 评价 |
|---|---|
| 适用场景 | 想**当天见效**、不想新增页面（避免重新提审发版）；本次缺陷修复 |
| 优点 | 改动集中在 `fill` 一个页（wxml/wxss/js），不动导航结构；用户不离开填报页，"报完一家接着报下一家"的连续动作不被打断 |
| 缺点 | 同页叠加两种状态，语义不如独立页干净；"成功"没有仪式感、无终态感；历史感弱（靠 Storage 恢复） |
| 成本 | 低（约 1 个页面 + 3 处判定） |

### 方案 B：独立「提交结果页」（借鉴淘宝下单成功页）

**做法**：新增 `pages/result/result`，成功后用 **`wx.redirectTo`（不是 `navigateTo`）** 跳转。
结果页同时承载**成功版式与失败版式**。

- 成功：大图标 + 单号（可复制）+ 摘要 + 跳过项 + 「查看我的提交」（主）/「回去继续填报」（次）
- 失败：原因 + **可重试/不可重试分级** + 「重试」/「去修改」
- 回执从 Storage 读（避免页面参数过长/丢失）

| 维度 | 评价 |
|---|---|
| 适用场景 | 产品成熟、愿意为此发一版；希望"提交"这个动作有明确终态 |
| 优点 | **语义最清晰**；用 `redirectTo` ⇒ 返回键**回不到可再次提交的表单**，从机制上消除"回退→再点→重复报单"；失败态也有承载页；最贴近用户熟悉的电商流程 |
| 缺点 | 需新增页面 ⇒ **须重新提交审核**；成功页价值密度低（用户看完还得回来）；多一步返回 |
| 成本 | 中（1 新页 + 修改提交跳转 + 提审） |

### 方案 C：填报页「状态化」为报单工作台（原地切换模式）

**做法**：同一路由两个模式。提交后页面切到「本期报单状态」视图：顶部显示已报摘要（单号/时刻/件数），
商品行转为**只读**并显示上次报的数量，底部主按钮变为「修改本期报单」（点开回到编辑态）。

| 维度 | 评价 |
|---|---|
| 适用场景 | 确认「一个业务员一天要给多家门店报单」是主工作流时 |
| 优点 | 把"这家报完了、下一家"的心智直接表达出来；同页复用、无新页面；彻底消除"看起来没提交" |
| 缺点 | 改造量最大（要引入 `editMode` 状态机）；**必须重新定义「提交后不清空数量」这条既有设计**；与 `mine` 页职责边界会变模糊 |
| 成本 | 高（模式状态机 + 双态 UI + 回归） |

### 推荐路线

**先 A（P0，当天可上线）→ 视情况演进到 B（P1）→ C 待需求确认（P2）。**

理由：
- A 能一次性消灭根因 **A/B/C/D/E 全部五条**，且不新增页面、不动导航 —— 性价比最高；
- B 是体验终态，但它解决的是"仪式感与终态语义"，而当前用户痛点是"看不到"，A 已覆盖；
  B 的真实额外价值是 **`redirectTo` 从机制上堵住"回退重复提交"** —— 若这点被看重，可提前；
- C 依赖一个**尚未确认的业务假设**（一人一天多店轮报），不该在假设未验证时先改架构。

## 四、各方案共用的详细设计

### 4.1 提交成功反馈（三个必须有的元素）

参考电商结果页，成功的反馈要能回答用户三个问题：

| 用户的疑问 | 必须给的元素 | 现状 |
|---|---|---|
| 「到底成没成？」 | **明确的完成态**（结果卡/结果页，不是会消失的弹窗）+ 提交时刻 | 弹窗会被关掉 ⇒ 缺 |
| 「报的是哪一单？」 | **单号**，且**可一键复制** | 三处都不显示 ⇒ 缺 |
| 「我报了什么、接下来会怎样？」 | 门店 · 期次 · N 项 · M 件 + 跳过项 + 下一步说明 | 部分有 ⇒ 不全 |

**建议的结果卡文案（终稿建议）**：

```
✓ 已提交成功
单号 #12345                      [复制]
────────────────────────────
门店   永诺旗舰店
期次   9/22 ~ 9/24（到货 9/26）
内容   12 项 · 共 340 件
时间   2026-09-21 11:02
────────────────────────────
已自动跳过 2 项已停售商品（XX、YY）
需要改动？可在「我的提交」里撤回重报。
[ 查看我的提交 ]   [ 继续修改 ]
```

**关键交互细节**：
1. **`wx.pageScrollTo({ selector: '#submit-result' })`** —— 把结果卡拉进视野（这是根治"看不到"的 1 行代码）；
2. **单号点击复制**（`wx.setClipboardData`）+ toast「单号已复制，可发给文员核对」；
3. 结果卡**常驻**，直到用户改动数量 ⇒ 改为「本期已报 N 件 · 当前有未提交的改动」，
   防止"我改了、以为也报上去了"；
4. 成功后**不清空数量**这条既有设计**保留**（有产品理由），但**必须与结果卡配套** ——
   数量留着，则"已提交"的视觉标记必须更强，否则两者互相抵消。

### 4.2 错误提示分级（必须按类型分流）

| 类型 | 触发 | 现状反馈 | 应改为 | 进草稿/自动补传？ |
|---|---|---|---|---|
| **网络类**（可重试） | 断网 / 超时 / 5xx | 「…已存草稿」toast | 页面级提示：「网络不稳，已存草稿，联网后自动补传」+ 「立即重试」 | ✅ 是 |
| **数据类**（不可重试） | 400：商品不在本期清单 / 已停售 / 未录厂价 / 数量非数字或超上限 | 同上（**错**） | 错误条（**不用会消失的 toast**）+ **逐项列出是哪几个商品** + 「去修改」（定位到该商品行） | ❌ 否，且须清掉 `pendingSubmit` |
| **状态冲突**（需人介入） | 409：本期已定稿 | 同上（**错**） | 「本期已定稿，不能再报」+ 「查看我的提交」/「联系管理员重开」 | ❌ 否 |
| **权限类** | 403 | 同上（**错**） | 「你在这个门店没有报单权限」+ 「复制发给管理员」 | ❌ 否 |

**三条实现要点**：
1. `pendingSubmit`（"待补传草稿"）**只对网络类置真** —— 这是 E 的核心修法；
2. 用**页面级错误条**替代 `wx.showToast` 承载业务错误：toast 3 秒消失，且后端 400 文案较长
   （例如「所选商品不在本期的报单清单里：A、B 等。请以填报页列出的商品为准…」）在 toast 里会被截断；
3. `onShow` 的自动补传改为 **`loadPeriods().then(() => resumeDraft())`**，消除
   「请先选择报单期次」误报（与 `onPullDownRefresh` 已修的竞态保持同一写法）。

### 4.3 防止重复提交（三层）

| 层 | 做法 | 解决的场景 | 现状 |
|---|---|---|---|
| ① 交互层 | 提交中禁用提交栏 + **全屏 loading 阻塞**（`wx.showLoading`） | 连点；等待期改数量导致"提交的是旧数据"的误解 | 只禁按钮，无阻塞 |
| ② 前端幂等键 | 进提交前生成 `client_token`（`storeId-periodId-时间戳-随机`），随请求提交；**同一 token 重试可安全重发** | 断网重试、杀进程重进再点、换网络 | **完全没有** |
| ③ 后端幂等 | 键需按业务口径定（见下方待拍板项）：<br>· 「一店一期只能一单」⇒ 键应为 `(store_id, period_id)`，同店由他人报时提示"已由 X 报过，是否覆盖"<br>· 「一人一店一期一单」（当前）⇒ 保留 `(user_id, …)`，但**前端文案必须改成"覆盖"** | 同店同期次被两个人各报一次 ⇒ 汇总翻倍 | 键含 `user_id`，存在叠加风险 |

**另加一条**：提交成功后**回执要能被复查**。现在成功状态只在内存/Storage，一旦用户怀疑"到底报没报"，
唯一可核对的地方是「我的提交」——建议在该列表**显示单号与提交时刻**，让"反馈闭环"落在数据上，
而不是只靠一次性动画。

### 4.4 从电商（淘宝下单）流程可借鉴的 8 点

| # | 电商做法 | 为什么有效 | 小程序对应改法 |
|---|---|---|---|
| 1 | 下单后**跳独立结果页**，不是弹窗 | 弹窗会被关掉、页面会"恢复原样"；独立页是**终态** | P1 独立结果页 / P0 结果卡 + 滚动锚定 |
| 2 | **订单号大号展示 + 一键复制** | 单号是用户与客服对账的**唯一锚点** | 结果卡展示 `submission_id` 并可复制 |
| 3 | 主按钮「查看订单」+ 次按钮「继续购物」 | 用**两个明确去处**代替"关掉弹窗" | 「查看我的提交」主 + 「继续修改」次 |
| 4 | 支付中转圈、成功后对勾动画 | 让"正在处理"与"已成功"在**时间上分得开** | 提交中全屏 loading，成功后才出结果卡 |
| 5 | 「待付款」倒计时 / 订单状态时间线 | 提交≠结束，用户要知道**下一步会怎样** | 结果卡加一行「文员将在 X 前汇总；如需改动可在『我的提交』撤回」 |
| 6 | 客户端 **order token** 防重复下单 | 网络重试不会产生两单 | 引入 `client_token` 幂等键 |
| 7 | 提交失败**保留已填内容** + 明确「重试」 | 失败不该让用户重填 | 「不清空」现状是对的，但要**分清可重试/不可重试** |
| 8 | 提交后**回退键回不到可再提交的表单** | 防"回退→再点→重复单" | 结果页用 `redirectTo`，不用 `navigateTo` |

## 六、需确认事项

1. 🔴 **口径拍板：一家门店一个期次，应该只能有一单，还是允许多单？**
   - 若「一店一期一单」⇒ 后端幂等键应从 `(user_id, store_id, period_id)` 改为 `(store_id, period_id)`，
     并处理"同店他人已报"的提示；
   - 若「一人一店一期一单」（当前实现）⇒ 保留键，但**前端文案必须如实说明是"覆盖"**，
     且要接受"两个业务员报同一家店会出两条单、汇总翻倍"这个结果。
   ⇒ **这一条不定，4.3 的第 ③ 层做不了。**

2. **小程序当前是否已提审/已上线？** 若已上线，本次改动属于"需重新提交审核"的版本，
   建议**攒一批**（P0 九项 + 其它待改）一起发；若尚未提审，可把 P0 直接并入首版。

3. **方案选择**：A（当天、不新增页面）/ B（体验终态、需发版）/ C（架构改造、依赖假设）。
   我的建议是 **A 先落地，B 视发版窗口跟进，C 暂缓**。

4. **「提交后不清空数量」是否保留？** 现行设计有明确产品理由（跨期次一键带入），
   但它是根因 B 的成因。建议**保留数量、强化状态标记**（P0 第 2、8 项），
   而不是回到"提交即清空"。

5. **是否需要"提交后通知"？** 电商结果页会告知下一步。若希望文员侧感知更快，
   可考虑把「本期已报」推送到企业微信（此前已评估过企微应用消息通道），属于另一个改动面。

### 三个「差点漏掉」的点（都不是显而易见的）

1. **覆盖时必须把 `status` 复位为 `pending`。** 撤回（recall）是 `UPDATE status='recalled'` —— **行还在、不删行**。新幂等键按 (店, 期次) 取最新一行会命中那条撤回行；若只改数量不复位状态，新报单会**继承「已撤回」**⇒ 不计入汇总，而用户看到的是「提交成功」。**典型静默失效。**
2. **单测抓到了我自己代码的一处真缺陷。** `forecast_submission_replace` 的兜底分支（主行不存在时退化为新建）原写在事务块内，而 `forecast_submission_create` 自己会再开事务 ⇒ `database is locked`。已移到事务之外 —— 这条兜底若不改，「改成功了但库里其实没有」这种最坏回执会必然发生。
3. **`user_id` 有意保持「首报人」不随修改漂移。** 否则两人先后改同一门店时，历史单的归属会反复易主。「最后改的人是谁」改由 `updated_by` 承载。

### 关于提交：为什么只提交了 18 个 hunk

工作区里同时躺着 v213 / v215 等多个**未提交轮次**，它们与本轮**落在同一个 hunk 内**：

- 后端 `routers/forecast_submissions.py` 的 `"created": created, **result}` 与 v215 的
  `"skipped_out_of_scope": dropped_out_of_scope,` 属同一次行改写。
  **整块提交 = 提交一个引用了未提交定义的键** ⇒ 小程序建单接口运行必 `NameError` 500，
  而 `python -m py_compile` 与 `import` **都不会报**（函数体没执行）。
- 为此本轮给提交工具加了 `drop_plus_lines`（按索引挖掉 `+` 侧中间任意几行，既有四种切分都表达不了）
  与 `dropped` 断言（**只存在于工作区、绝不出现在提交里** 的东西必须有断言）。

## 四、对齐效果（改前 → 改后）

| 场景 | 改前 | 改后 |
|---|---|---|
| 同一门店同一期次，两个人各报一次 | **真存两条**，汇总数量翻倍 | **恒一条**；第二个人改的是同一单 |
| 同一门店同一期次，报两次 | 单号**换一次** ⇒ 手里的单号下次提交后就查不到；前端只能写「再提交会新增一单」 | 单号**不变**；前端如实说「将更新这一单，不会多出一条」 |
| 甲先报、乙后来改，乙看「我的报单」 | **看不到**自己刚改的那单（只按 user_id 过滤） | 看得到（门店范围并集，与提交时的越权校验同一函数） |
| 期次已关闭还想改单 | 「所选报单期次不可用或已关闭」（听起来像系统坏了） | 「本期已定稿（关闭），不能再报单；如需改动请联系管理员重开本期」 |
| 期次被删后提交 | 同上，分不清是哪种情况 | 「所选报单期次不存在，请下拉刷新后重选」 |
| 撤回后重新报单 | 新单继承「已撤回」⇒ 不计入汇总，但提示「提交成功」 | 复位为待审批，**正常计入汇总** |
| 小程序提交之后 | 结果栏固定在最下方，**滚动一下才看得见**；「今日已报」回执是恒不出现的死代码 | 结果卡**弹在视线落点**（与提交栏/错误条互斥同位置），带单号可一键复制 |
| 提交失败 | 一句「提交失败，已存草稿」——**能不能重试**看不出 | 分两级：业务拒绝给原因、**不给重试**（重试必然再失败）；网络故障才给「重试」+ 存草稿 + `onShow` 自动补传 |
| 连点提交 | 「薄」防抖（setData 异步窗口内可穿） | 同步锁在函数第一行置位，绕开 setData 异步窗口 |

## 〇、核对判据（先说清楚，否则后面每条都无法复核）

本轮刻意采用**四级判据**，从弱到强：

| 级别 | 判据 | 能否算「成立」 |
|---|---|---|
| L1 | 名字里有这个词（`grep` 命中） | ❌ **不算** |
| L2 | 有对应的文件 / 函数 / 表定义 | ❌ **不算**（可能从未被调用） |
| L3 | 有调用方，且路径可达 | ⚠️ 勉强 |
| L4 | **运行态可证**：进程在跑 / 目录有 mtime / 表里有行 / 接口有记录 | ✅ **算** |

**为什么把判据定这么严**：本轮抓到 **2 处 L2/L3 达标但 L4 不成立**的缺陷，外加 **1 处「运行态随入口变化」**（见第三节第 1、3 条与「A 类」第 7 条）。它们全部**零报错、界面看不出异常** —— 判断错了不会有人提醒你，而写进对外材料会被评委一行代码拆掉。

## 一、总体结论

**BP 的骨架是真的。** 配方库、租户 AI 沙箱、异地备份与巡检、数据源适配器、四类行业工具、确定性对账算子 —— 这些不是 PPT，代码里都有，且多数已经跑到运行态。

但有**三类系统性偏差**，性质完全不同，必须分开处理：

| # | 偏差类型 | 含义 | 数量 | 危险度 |
|---|---|---|---|---|
| **①** | **「写好了」≠「能用了」** | 代码完整、单测通过，但运行态没接通 ⇒ **静默失效** | 2 处（A7、B2）+ **1 处入口不对称**（A9） | 🔴 最高：它会让人对外说出一句自己以为真的话 |
| **②** | **BP 讲的与跑着的不是同一个产品面** | `hergent.cn`（副驾壳，22 条路由）与 `erp.hergent.cn`（完整 ERP，102 个前端模块）是两套东西；BP 的量级数字取自后者，功能承诺跨了两面 | 1 组 | 🔴 高：评委追问必露 |
| **③** | **数字/口径无法复算** | 与 BP 自己那句「每一个数都能倒推回它的来源」直接冲突 | 3 处数字 + 1 处标签 | 🟠 中高：一句话能改，但不改就是自拆地基 |

**一句话**：不需要为这份 BP 新增任何功能；需要做的是**把「已经做到的」和「已经说出口的」重新对齐**，然后按验证期真正缺的三件事补代码。

## 三、五条必须现在处理的差距（深挖）

### 1️⃣ A9 · 对账确定性算子：**能力是真的，但两个入口不对称** —— 本轮最隐蔽的一处

先说结论：**能力存在、且在网页副驾上真的可用**。问题出在「换了入口就没了」，而且**根本不会提示你**。

```
recon_engine.py (788 行, 纯函数, 确定性重放契约)
        │  ✅ import 成功
        ▼
/opt/hergent-mcp-spreadsheet/server.py  →  spreadsheet_reconcile_files
        │
        ├─▶  root 网关（:18765, HERMES_HOME=/root/.hermes）
        │      config.yaml 挂载 mcp_servers.spreadsheet  ✅
        │      ← 网页副驾走这里（copilot_proxy.py:35）

```

**这是真正的病**：老板的真实使用场景是**手机**（`config.yaml` 里 `platforms.wecom.channel_overrides.ZhangJunFeng` 就是给他本人配的渠道级提示词）。也就是说，**B 端经销商的日常入口上，能力反而更弱** —— 而两侧界面都不会提示这件事。

**同时**：`recon_engine` 在后端**没有任何 API 调用**（全仓只被单测引用），它自述的复用面「① 后端 API —— P2 对账工作台」**从未接线** —— 所以「对账」目前只有「网页副驾对话」这一条路，**没有可点的界面**（这一点与 BP 说的「不做成功能界面」一致，方向没错）。

**影响**：🟠 中高。不是缺能力，是**缺对称**；且它是**静默的**（换了入口少了一半工具，零提示）。
**优先级**：**P1**（把租户网关的 `mcp_servers` 与 root 网关对齐 —— 这可能是**一行配置**的事，但后果最大）。

## 八、自我更正（留痕 · 不删）

**初稿判错了一条，本报告内已改，这里留原始错因。**

| | 初稿写的 | 更正后 |
|---|---|---|
| A9 | 「**确定性算子写好了，但 AI 拿不到**」→ 列为全报告最高危（P0） | 「**能力是真的，网页侧可用；但手机/企微入口拿不到**」→ 降为入口不对称（P1） |

**我错在哪（两处口径，和对面的问题一模一样）**：

1. **只查了一个网关就下结论** —— 我查了租户网关（`/opt/hermes-tenants/hergent_t1/config.yaml`）看到 `mcp_servers: {}`，就断定「MCP 没挂」。**实际有两个网关**：root 网关（`/root/.hermes/config.yaml:12`）**挂了** `mcp_servers.spreadsheet`，且进程实在跑（`mcp_stdio_watchdog.py` + `server.py`）。
2. **把「一个入口的情况」当成「整个系统的情况」** —— 正确做法是**先问「这个能力有几个入口」**，再逐个入口查它的配置。这与上一轮我把「全部单据类型」当成「销售单」是**同一类错误**。

**是记忆救了我** —— 项目记忆里存着「root 网关另挂 MCP stdio watchdog（spreadsheet）」这一句，交叉核对才发现矛盾。**教训：已有记忆是关于过去的运行态，它是最便宜的对照物，动手下结论前先看它。**

**这条错本身的复用价值**（已写进技能 `hergent-capability-reality-audit`）：
> **「运行态」也要问「是哪个运行态」。** 多入口系统（网页 / 手机 / IM 渠道 / 定时任务）里，
> **同一个能力在不同入口的挂载可能完全不同**，只查一个入口 ⇒ 得到的结论对那个入口成立、对系统不成立。

**「入口盘点三问」**（每个 ✅/❌ 结论前都过一遍，30 秒）：

1. **有几个前端面？** —— 本项目 **3 个**：`hergent.cn`（副驾壳）＋ `erp.hergent.cn`（完整 ERP）＋ 小程序报单端。
2. **有几个后端/网关实例？** —— 本项目 **不止一个**：root 网关 `:18765`（服务网页副驾）＋ 每租户网关（服务企微渠道，非 systemd 管理）。用 `pgrep -f "hermes gateway"` + `/proc/<pid>/environ` 才看得全。
3. **该能力在每个面上的挂载是否相同？** —— **逐份比配置文件**（`config.yaml` / drop-in / cron.d），**不要比代码**。

⚠️ 顺带：本报告的 ② 类偏差（两个产品面）与本条错因**同源** —— 都是「**以为只有一个面**」。这说明「**先盘点有几个面/几个入口**」应当是本项目所有核查的**第一动作**，而不是最后才发现的事。

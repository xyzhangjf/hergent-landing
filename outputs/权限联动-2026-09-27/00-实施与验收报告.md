# v292 角色权限「默认配置 ＋ 客户自主调整 ＋ 界面联动」实施与验收报告

- 版本：`v292-权限联动`（⚠️ **同日重号**：另一并行会话的 `v292-返利冲刺口径`，引用必带后缀）
- 日期：2026-09-27
- 需求原话：*「一方面为不同角色提供默认权限配置，另一方面允许用户自主为角色分配和调整权限；当权限发生变更时，该角色对应的 UI 界面元素（如菜单、按钮、页面入口等）应同步动态调整，仅展示其有权访问的内容。」*
- 结论：**①② 早已具备（本轮仅复核）；③ 是本轮真正的缺口，已实现并上线。**

| 需求 | 状态 | 真身在哪（可复核） |
|---|---|---|
| ① 每个角色有**默认权限配置** | ✅ 早就有（本轮未改） | 后端 `server/core.py::_DEFAULT_PERMS`，AST 实测 **8 个内置角色**：`admin` `boss` `accountant` `sales` `guide` `driver` `staff` `supervisor` |

## 二、数据模型（设计说明 · 客户视角）

### 2.1 两层，不引入第三张表

```
① 内置默认（产品侧，一次定义，全平台生效）
   core._DEFAULT_PERMS : { 角色名 → [模块名...] 或 {模块名: [动作...]} }
        · legacy 形态 list 例： "sales": ["dashboard","sales","stock",...]
        · 新版形态 dict 例：  "sales": {"dashboard":["read"], "sales":["read","create"]}
        · 两种形态**内容相同时必须判为相同**（见 §3.3 规范化）

② 租户覆盖（客户侧，每个租户一份）
   tenant_<id>.db :: role_permissions(role_name TEXT, permissions TEXT/JSON)
        · 语义 = **按角色整表覆盖**（不是合并、不是增量）
        · 读端  perms_for(tid) = 内置默认 ⊕ 本租户覆盖
        · 缓存  _PERMS_CACHE（按租户分键，键 0 = 无租户上下文）＋ reload_perms(tid) 只失效本租户
        · 兜底  租户库缺表/缺行/坏行 ⇒ **回落内置默认**（否则一个坏库 = 该租户全员 403）
                 但**权限管理端点本身必须 fail-closed 400**，绝不回落主库
```

**为什么不做"用户级权限表"**：当前模型是「角色 → 模块」，用户与角色的绑定在 `users.role`；
再叠一层用户级例外会让「这个人为什么看得见」无法从任一张表回答。若真要做，硬约束是
**必须有唯一的合并顺序**（公司默认 → 租户角色 → 用户例外），且要能在 UI 上回答"最终值由谁给"。

### 2.2 本轮新增的两个**派生字段**（不是新表）

| 字段 | 含义 | 实现 |
|---|---|---|
| `perms_rev` | 本租户自定义权限表的**内容指纹**（12 位 sha1 hex） | `core.perms_rev(tid)` |
| `custom_roles` | 本租户**真实改过**权限的角色名（升序） | `core.custom_roles(tid)` |

露出方式（**只加不改**，见 §3.4）：`GET /api/auth/permissions` 追加这两个键；
另加极轻端点 `GET /api/auth/perms-rev` ⇒ `{perms_rev, tenant_id}`。

## 三、权限校验逻辑（设计说明 · 工程视角）

### 3.1 五道闸，各管一段（自上而下）

| # | 位置 | 判据 | 失败方向 |
|---|---|---|---|
| 1 | RBAC 中间件（**最外层**，先于 auth / tenant） | `_check_perm(u, module, action, tenant_id=…)`，取**全部角色并集**（v266） | 拒绝 |
| 2 | 路径→模块映射 `server.py::_PATH_MODULE_MAP` | **首个 `startswith` 命中即停**（顺序即优先级） | 拒绝 |
| 3 | 页面级角色门槛 | 前端 `pages.js::roleGateOpen` ＋ 后端各页自己的 `_guard()` | 见 §3.2 三档 |
| 4 | 写端 | 一律 `core._admin`（`role ∈ {admin,boss}`，**按角色名**、不依赖 `hr` 模块） | 拒绝 |
| 5 | 前端入口可见性 | `canSee(path)` = `canSeePage(path, store.user.role, store.canModule, store.customRoles)` | **fail-open**（见 §3.5） |

🔴 **第 1 道最易踩的坑**：中间件在**最外层** ⇒ 它调 `_check_perm` 时租户上下文还没建立，
**必须显式传 `tenant_id=`**。不传 ⇒ 拿内置默认放行一个**已被本租户撤销**的模块 = *撤销失效（越权）*。

### 3.2 本轮新增：入口判据的**第三档「用户配置优先（让位）」**

`hergent-cn-v2/src/constants/pages.js` 是**唯一判据源**（17 页 × 两条轴）。

v291 = 两条轴：`module`（本租户买没买）／`roles`（这一页天然只给哪几类人）。
v292 加第三档，**顺序不可换**：

```js
function roleGateOpen(r, role, customRoles) {
  if (!r.roles) return true                      // ① 不按角色收紧（只按 module 判）
  if (roleIn(role, r.roles)) return true         // ② 在内置名单里（含"未知角色 fail-open"）
  if (r.lock === true) return false              // ③ 产品硬锁：客户也不许放开
  if (!r.module) return false                    // ④ 安全阀：没有 module 可判 ⇒ 让位=全开，不许让
  if (!Array.isArray(customRoles)) return false  // ⑤ 不知道 ⇒ 按内置门槛收紧（较严）
  return customRoles.includes(normRole(role))    // ⑥ 用户配置优先
}
```

**三条设计决策（都带"为什么"）**

1. **第 ④ 条安全阀**：让位的语义是"客户动过手，就让客户的配置压过产品内置"。
   若该行 `module: null`，"让位"后**一个判据都不剩** ⇒ 该页对**所有**角色全开。
   要求「本行配有 `module`」＝要求「客户**先在设置页显式给这个角色开了对应能力**」。
   ⇒ 本仓 **11 页 `module: null` 永不参与让位**：
   `/workbench` `/forecast` `/rebate` `/loss` `/loss-accounting` `/data-fill` `/archive`
   `/price-channels` `/connect` `/settings` `/zhoupu-import`。
   （对照：带 module 的 6 页 = `/dashboard` `/ai-hub` `/payroll` `/bid-radar` `/cron` `/roles`。）

2. **`lock: true` 只给两页**：`/roles`（AI 团队）与 `/settings`。
   理由与后端「豁免 RBAC 的**模块判定** ≠ 放宽访问控制」同源：**把「唯一能改回来的页面」锁死 = 自我锁死且无法自救**。
   `/roles` 另需显式锁：它挂 `module:'chat'`，而**每个角色都有 chat**（`staff`/`driver`/`guide` 全有）
   ⇒ 只靠 module 的话，任何"被改过"的角色都会多出这个配置类入口。
   `/settings` 的锁是**声明式**的（它 `module: null` 本来就天然不让位）—— 防后人给它补 module 时把锁丢掉。
   ✅ 可断言：`lock` 集合恰为 `['/roles','/settings']`；双轴页恰为 `['/bid-radar','/cron','/roles']`。

3. **一处实现、四处分发**：`canSeePage`（入口用）与 `pageRoleAllowed`（路由守卫用）**共用同一个 `roleGateOpen`**。
   ⇒ 侧栏 / 手机抽屉 / 命令面板 / 页内跳转 / 守卫**读同一份判据**，`canSee()` 的调用点**零改动**
   （24 处菜单 + 命令面板 13 条一处没改）—— 这是 v291「收壳」纪律的直接回报。

### 3.3 「客户改过」的判据 = **内容 ≠ 内置默认**，不是「表里有行」

设置页保存是**逐角色全量 POST** ⇒ 点一次保存，**人人都有行**。
若按「表里有行」判 ⇒ 对正常租户 `roles` 轴**整体失效** ⇒ **悄悄拆掉 v291**。

```python
def _canon_perms(v):          # 规范化：dict 取 keys / list 直接集合 ⇒ 升序去重 list
    if isinstance(v, dict):               return sorted({str(k) for k in v.keys()})
    if isinstance(v, (list, tuple, set)): return sorted({str(x) for x in v})
    return []

for role, perms in custom.items():                    # core.custom_roles
    if _canon_perms(perms) != _canon_perms(_DEFAULT_PERMS.get(role)):
        out.append(str(role))
```

⚠️ **规范化不能省**：`["data","chat"]` 与 `{"data":[...],"chat":[...]}` 是**同内容、异形态**，
不规范化会被误判成"改过"。

### 3.4 🔴 共用接口红线（本轮最硬的一条约束）

`GET /api/auth/permissions` **被微信小程序共用**：
`forecast-order-miniprogram/miniprogram/utils/perm.js:99`（权限闸）＋ `pages/login/login.js:141`。
⇒ 本轮**只加字段**：`perms_rev`、`custom_roles`；**既有键一字未动**
（`user` / `permissions` / `tenant_id` / `plan` / `capabilities`）。
任何"顺手重构返回体"都会**静默打断小程序登录后的权限闸**。

### 3.5 两处 fail-open 是**纪律**，不是疏忽

- **未登记路径** ⇒ 放行（`ruleFor()` 返 `null` ⇒ `canSeePage` 放行）
- **未知角色** ⇒ 放行（启动瞬间 `user.role` 还是空串）

理由：一次接口抖动不能把老板的菜单藏起来。
⚠️ **既有洞（本轮未修）**：租户自定义角色（如 `库管`）**不在内置名单里** ⇒ 借"未知角色 fail-open"
**通过所有 `roles` 门槛**。要修需把"未知角色"与"已知但不在名单"分开，且要处理"租户自定义角色
本来就没有产品级名单"这一事实。

## 四、界面响应方式（设计说明 · 交互视角）

### 4.1 三层触发，各覆盖一种"人回来的时刻"

| 层 | 时机 | 做法 | 关键注意 |
|---|---|---|---|
| ① 本会话即时 | 设置页保存 / 恢复默认**成功后** | `await store.loadPerms(true)` **再** toast | 🔴 **不要前置 `resetPerms()`** —— 它把 `perms` 置 `null` ⇒ fail-open ⇒ **闪一屏全菜单**再消失 |
| ② 换页 | `router` 守卫 | `store.refreshPermsIfChanged()` **故意不 `await`** ＋ **20 秒节流** | 不 await ⇒ 不让导航多等一次往返；节流 ⇒ 不把"每次点菜单"变成持续背景流量 |
| ③ 闲置 | `Shell.vue` | `setInterval(…, 60000)` ＋ `visibilitychange`（`visible` 时 `force=true`） | 必须 `onBeforeUnmount` 清定时器 + 移监听 |

### 4.2 为什么用**内容指纹**而不是「最后修改时间」

设置页保存会**原样回写一遍** ⇒ 时间戳变了、**内容没变** ⇒ 前端每次都判"变了"
⇒ 把「几十字节的比对」放大成「**每 60 秒一次全量拉取**」。
指纹只认内容：回写不变 ⇒ 指纹不变 ⇒ **零请求**。

`refreshPermsIfChanged(force)` 内部三件事都要有：
`if (!perms.value) return false`（还没登录别比）／ 并发去重（`_revInflight`）／ **全静默**（`silent401:true`，失败不弹 toast）。

### 4.3 `customRoles` 的三态方向与 `perms` **刻意相反**

| 值 | 含义 | 方向 |
|---|---|---|
| `perms = null` | 还不知道（未登录 / 请求失败） | **放行**（不藏菜单） |
| `customRoles = null` | 还不知道 | **不让位**（按内置门槛收紧，较严） |
| `customRoles = []` | 知道，且**无人改过** | 正常按内置判 |

理由：`perms` 那条是"一次抖动不能把老板的菜单藏起来"；
`customRoles` 这条是"**不知道客户配置时，宁可显示少的**" —— 让位本身是**扩权**方向，
方向朝错一侧 = 静默越权可见。**`[] ≠ null`，必须分开写。**

### 4.4 顺带把「文案当功能做」

设置页权限 tab 新增三段说明：**控制什么** / **哪些页面产品内置不受影响（11 页）** / **多久生效**；
并点名「档案管理」= `data` 粒度粗，勾它会一并放开「定时任务 / 招投标雷达」。
权限页最容易犯的错是**许诺一件它兑现不了的事**。

### 6.1 夹带判定为什么必须换判据（本轮最值得留档的一条）

- **不能用 hash 名**：rollup 的 chunk hash 对**模块遍历顺序**敏感 ⇒ 改一两个源文件可能让
  几十个 chunk **级联换名**（v282 实测 29/53）⇒ 单看 hash 归因不了"我改了什么"。
- **不能用 file count**：线上 `assets/` 是**历次构建的并集**（v264b：324 物理文件 / 53 逻辑名；
  本轮：**483 / 53**）⇒ 文件数早就不是判据。
- ✅ **正解 = 「逻辑名（剥 hash）+ 字节大小」**：本轮 **53 个逻辑名里 50 个同名同尺寸**，
  仅 `Settings` / `Shell` / `index` 三块变化 = **恰好本轮 5 个源文件级联出的产物**，零新增/删除 chunk。

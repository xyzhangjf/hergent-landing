## 二、🔴 三个必须先看的反直觉事实（会改变你的需求）

### 事实 1：不能按"客户编码"做主键校验 —— 编码几乎是空的

你要求"校验客户编码是否存在"。但生产 758 个客户里，**只有 1 个填了编码**（`卡士乳业（深圳）有限公司` / `108811`，还是个供应商）。

若坚持以编码为准 ⇒ **757 个客户全部报"编码不存在"**，这个功能上线就是废的。

**处理（已按老板 2026-09-29 拍板定稿）**：**不做"以编码为准"，也不补编码**。理由是你的判断 —— 真实环境里用户搜的是**店名**，不是编码。

- **唯一匹配键 = 客户名称（归一化后）** —— 填充率 100%，且与用户心智一致
- 编码**保留但仅作辅助**：`contacts.code` 非空时**优先**用它（更稳），为空**照常按名称匹配、不报错、不提示**。
  这一条是"白捡的"：后端 `contact_list` 本来就支持 `code LIKE`，零成本。
- ❌ **不做"客户编码批量回填"导入类目**（原 §9 待拍板项 ② 已关闭）

> ⚠️ 连带影响：**导入模板里删掉「客户编码」列**，避免用户以为"必须填编码"。
> 原方案曾把编码列摆进模板当"推荐填"，现在**取消** —— 摆了就会有人专门去填，反而增加负担。

### 事实 2：`contacts.channel` 已被"门店业态"占用，绝不能挪用

`contacts.channel` 里存的是**业态/通路**，不是价格渠道：

```
20店 228 · 零食系统 117 · 便利店 88 · 校园 70 · 特通 44 · 同业 44
现代渠道 23 · 奶店 15 · 餐饮 11 · 临期外卖 11 · 内购 10 …
```

这跟 `price_channels`（厂家系统 / 分销价 / **永辉**）是**两套正交的业务概念**。若把价格渠道也塞进这一列 ⇒ 一个客户既不能说清"业态=便利店"又要说"价格渠道=永辉"，**两个语义抢一个字段，必然互相踩**。

**处理**：新关系**独立建表**，`contacts.channel` **一个字都不动**。

### 事实 3：一个客户只能挂一个渠道 —— **已拍板，且与现状一致**

你在需求里提到"同一客户归属多个渠道时的冲突处理"。我当时给了两个选项，**你 2026-09-29 明确选了「一对一」**：

> 「同一客户只能挂一个渠道，没必要挂两个渠道」

这个选择是对的，理由是**它和系统现状同构**：现有 `ReportMapping` 本来就是**硬拦一对一**（`:243`："这个对象已经有一条活跃配置了"，v297）。若这里做成多对多，等于在同一套价格体系里给出**两种互斥的语义**，迟早有人问"到底哪个价生效"。

所以最终模型：

- **一个渠道 ↔ 多个客户**（1:N —— 这才是你要的"批量绑定"）
- **一个客户 → 有且仅有一个渠道**（数据库层强约束，不靠应用层自觉）

⇒ 表上用 **`UNIQUE(contact_id)`** 兜底，**不设 `priority`**（没有第二个候选者，优先级无从谈起）。
⇒ 用户若把已属 A 渠道的客户绑到 B 渠道，**不是"冲突清单"，而是一次显式的「改绑」**（见 §7.2）。

## 三、数据模型设计

### 3.1 新表 `channel_customers`

```sql
CREATE TABLE IF NOT EXISTS channel_customers (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    tenant_id    INTEGER DEFAULT 0,
    channel_id   INTEGER NOT NULL,           -- → price_channels.id
    contact_id   INTEGER NOT NULL,           -- → contacts.id（客户/门店）
    status       TEXT DEFAULT 'active' CHECK(status IN ('active','disabled')),
    source       TEXT DEFAULT 'manual',      -- manual=界面勾选 | import=Excel导入 | biz=按业态批量 | api=连接器同步
    external_code TEXT DEFAULT '',           -- 导入时的原始编码（仅留痕，**不参与匹配**，用户不以编码搜店）
    external_name TEXT DEFAULT '',           -- 导入时的原始客户名（留痕，改名后可追溯）
    note         TEXT DEFAULT '',
    created_by   TEXT DEFAULT '',
    created_at   TEXT DEFAULT (datetime('now','localtime')),
    updated_at   TEXT DEFAULT (datetime('now','localtime'))
);
```

**唯一约束（防重复绑定 + 强制一对一）**：
```sql
-- ① 同一渠道内，同一客户只能绑一次
CREATE UNIQUE INDEX IF NOT EXISTS uq_channel_customer
    ON channel_customers(channel_id, contact_id);
-- ② ★ 一个客户全局只能属于一个渠道 —— 这是 DB 层的一对一强约束（拍板②）
CREATE UNIQUE INDEX IF NOT EXISTS uq_customer_single_channel
    ON channel_customers(contact_id);
```

> 🔴 **为什么一对一要写成 DB 约束、而不是应用层 if 判断**：
> 本项目的既有教训是"同一规则抄两份就会不一致"。这里若只在接口里 `if 已存在: return 报错`，
> Excel 导入走的是**另一条代码路径**（`import_router`），批量的走 `batch-bind`，手动的走 `bind`
> —— 三条路径都得各写一遍判断，漏一条就出现"同一个店挂两个渠道、取价随机"。
> **`UNIQUE(contact_id)` 让三条路径共用同一道闸**，谁绕都绕不过去。
> ⚠️ 代价：`INSERT` 撞唯一键会抛 `IntegrityError` ⇒ **必须 catch 并翻译成人话**
> （"该客户已属于「永辉」，请先解绑"），否则用户看到 500。

### 3.2 既然是一对一，为什么不直接在 `contacts` 上加一列？

这是个**必然会有人问**的问题（我自己也重估了一遍）。一对一确实"一列就够"，但列方案缺三样东西：

| 缺什么 | 具体后果 |
|---|---|
| **留痕** | 无法记 `source`（手动/导入/按业态/API）、`created_by`、`external_name` ⇒ 三个月后没人知道"这 247 家是哪次导入进来的" |
| **停用态** | 列方案只有"有值/空值"。用户想"临时不适用永辉价、但别丢配置"时只能清空 ⇒ **不可逆**，也没法只停一部分 |
| **可回删** | 导入类目要支持"撤销本次导入"（`_IMPORT_UNDO_TABLES` 机制）；列方案撤销时无法区分"本次写的"与"以前就有的" |

⇒ 结论：**仍然建表**，但把"一对一"这条约束**下沉到 DB**（`UNIQUE(contact_id)`）。
`priority` 已按拍板**删除** —— 只有一个候选者时，优先级是无意义的复杂度。

补充：`prices.py:384` 探测的 `channel_id` 列**不存在**，那层代码是死的。**不建议**把它"补活"—— 补活等于复活一个无法留痕、无法停用、无法回删的旧设计。**新表落地后，那段死代码应当删除**（见 §8.3）。

### 3.3 🔴 索引必须登记在 `db/indexes.py::INDEX_SQLS`

这是本项目**已踩过三次**的静默洞：表在 `_safe_migrate` 里建了，但**索引只下发给主库、不下发给每个 `tenant_*.db`**（实测 `PRAGMA index_list` 为空）。`price_channels` 自己至今就没登记。

新表的三条索引**必须**写进 `INDEX_SQLS` 清单：

```python
"CREATE INDEX IF NOT EXISTS idx_chan_cust_contact ON channel_customers(contact_id)",
"CREATE INDEX IF NOT EXISTS idx_chan_cust_channel ON channel_customers(channel_id)",
# 唯一索引在 _create_indexes_on 的 except: pass 里失败是**静默**的 ⇒ 建完必须抽查 index_list
"CREATE UNIQUE INDEX IF NOT EXISTS uq_channel_customer ON channel_customers(channel_id, contact_id)",
# ★ 一对一闸门（拍板②）：一个客户全局只能属于一个渠道
"CREATE UNIQUE INDEX IF NOT EXISTS uq_customer_single_channel ON channel_customers(contact_id)",
```

验收口令：`PRAGMA index_list(channel_customers)` 在 **tenant_1 与至少一个其它租户库都要看到 4 条**。
🔴 **必须逐条验"唯一性真的生效"**，别只看数量 —— 唯一索引建失败是静默的，而它正是防"一个店两个渠道"的唯一闸门：

```sql
-- 应报 UNIQUE constraint failed（这才是通的）
INSERT INTO channel_customers(channel_id, contact_id) VALUES (3, 1);
INSERT INTO channel_customers(channel_id, contact_id) VALUES (4, 1);   -- 同 contact_id，不同渠道
```

## 五、接口定义

### 5.1 查询与维护

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/price-channels/{cid}/customers` | 已绑定清单。参数：`keyword`（**只搜名称**）`biz_type`(=业态) `status` `offset` `limit` |
| GET | `/api/price-channels/{cid}/customers/candidates` | 未绑定候选客户（供勾选弹窗）。参数：`keyword` `biz_type` |
| GET | `/api/price-channels/{cid}/biz-types` | ★ **业态清单 + 计数**（`contacts.channel` 动态 `GROUP BY`），供路径 D 渲染按钮 |
| POST | `/api/price-channels/{cid}/customers/bind-by-biz` | ★ **按业态批量纳入** `body:{biz_type, dry_run?}` → 回执含 `will_bind/blocked[]` |
| POST | `/api/price-channels/{cid}/customers` | 批量绑定（勾选路径）`body:{contact_ids:[…]}` |
| DELETE | `/api/price-channels/{cid}/customers` | 批量解绑 `body:{contact_ids:[…]}` |
| PUT | `/api/price-channels/{cid}/customers/{contact_id}` | 仅改 `status`（停用/启用）`body:{status}` |

> ❌ **已删除**：`PUT .../{contact_id}` 改优先级、`GET .../conflicts` 冲突清单
> —— 拍板② 一对一后这两个端点没有存在意义。**不要为了"以后可能用"留着**，留着就会有人去用。

**`bind-by-biz` 的 `dry_run` 是硬要求**：前端点业态要先看到"将纳入 114 家 / 3 家已被占用"，用户确认后才真写。
一次性写 117 行的接口**没有预览就等于没有撤销机会**（虽然可回删，但用户不会去回删）。

统一回执信封（后端既有 `{ok, data}` 约定）。`bind-by-biz` 回执形态：

```json
{
  "ok": true,
  "data": {
    "biz_type": "零食系统",
    "matched": 117,          // 业态命中总数
    "bound": 114,            // 本次写入
    "skipped_same": 0,       // 已属本渠道（幂等）
    "blocked": [             // 已属其它渠道 ⇒ 需用户明说才改绑
      {"contact_id": 233, "name": "好邻居零食（万达店）", "current_channel": "分销价"}
    ]
  }
}
```

> ❌ 原第 5 条「按编码找不到客户」与第 13 条「优先级非法」**已删除**（模板里没有这两列）。
> 若外部表格自带「编码」列 ⇒ **静默忽略该列**（既不影响导入，也不报错），不提示、不要求。

### 6.2 汇总反馈（必须给"数"，不能只说"失败"）

```
导入完成：共 300 行
  ✅ 成功绑定   247 家
  ⚠️ 跳过        38 家（已绑定 22 · 文件内重复 4 · 档案停用 12）
  ⛔ 待确认       3 家（已属其它渠道）  [去处理改绑 ↓]
  ❌ 失败        12 行  [查看失败明细 ↓]  [下载失败明细.xlsx]
```

**失败明细可下载**是刚需 —— 老板不会有耐心在网页上抄 15 行错误。

🔴 **「跳过」与「待确认」必须分成两行**（原始方案把跨渠道也塞进"跳过"，现在不行了）：
- **跳过** = 这事**不用你管**（本来就在、文件里重复、档案已停用）⇒ 信息级
- **待确认** = 这事**需要你做决定**（改不改绑）⇒ 待办级
两者混在一起，用户会以为"跳过 41 家，没啥问题"，而那 3 家改绑需求就**沉底了**。

### 6.3 名称归一化规则（决定匹配率的关键）

不归一化 ⇒ "南漳店 "（带尾空格）、"吃货基地（南漳）"（全角括号）全部匹配失败。

1. 去首尾空白、连续空白折叠为一个
2. 全角 → 半角（NFKC）
3. 括号统一：全角括号 `（）` → 半角 `()`
4. 去掉分隔符号 `-` `_` `/` `·`
5. **不**做繁简转换（易误伤，且本业态不存在繁体数据源）

同一归一化结果匹配到多家 ⇒ **报错误 #6，要求人工去客户档案区分**，**绝不猜**（呼应 `prices.py:350` 已有的铁律：绝不靠名字关键词猜渠道）。

> 原始方案这里写的是"请改填客户编码"，**已按拍板②改掉** —— 模板里已经没有编码列了，
> 让用户"改填编码"等于指向一个不存在的字段。

## 七、🔴 关键流程的边界情况

### 7.1 「配好了却不生效」—— 本方案最大的坑

新建关系表只是**存了**，下单取价走的是 `prices.py::resolve_report_channel` **四级判决**，它**不认识新表**。若不改 ⇒ 界面配得再热闹，取价仍然走兜底默认渠道，**零报错**。

**必须改判决顺序**（改动很小，但漏了就全白做）：

改完之后仍是**四级**（删掉一层、新增一层）：

```
【改后】                                     【现状】
1) mapping.channel_id > 0                    1) 同（保留）
2) counterparty_type == self_warehouse       2) 同（保留）
   → 调拨单不取价 → None
3) ★ 新增：查 channel_customers，取该客户     3) ✘ 删除：contacts.channel_id
   那一条 status='active' 的渠道                 （列从未存在 ⇒ 永远为 None 的死代码）
4) default_channel() 兜底                    4) 同（保留）
```

> **第 3 步不需要"排序取第一条"** —— 拍板② 的 `UNIQUE(contact_id)` 已保证一个客户**最多一条**绑定。
> 原方案写的 `priority ASC, id ASC` 取法**已删除**（没有第二个候选者）。
> ⚠️ 但**仍要带 `status='active'` 条件**：停用的绑定存在但不应生效。

### 7.2 一家门店已经属于别的渠道时怎么办 —— 「改绑」

这是拍板② 之后**唯一需要用户决策**的场景，也是最容易出错的场景。

**存**：不删除、不并存。改绑 = 把那条绑定的 `channel_id` 改成新渠道，并记 `source`/`created_by` 留痕。
（因为 `UNIQUE(contact_id)` 存在，**物理上不可能并存两条** —— 这正是我们想要的。）

**四条路径下的行为必须一致**（这是本节的重点，因为四种路径的代码位置完全不同）：

| 路径 | 遇到"已属其它渠道"时 | 为什么 |
|---|---|---|
| 路径 D 按业态批量 | **默认跳过**，回执里列 `blocked[]`，页面上给「改绑这 N 家」按钮 | 一次点 117 家时，用户没打算改别人的渠道 |
| 路径 A 界面勾选 | 勾选列表里**已绑别处的显示为灰色 + 标「现走：分销价」**，勾它 = 明确要改绑 ⇒ **弹二次确认** | 用户是逐条点的，意图明确，但仍要确认 |
| 路径 B Excel 导入 | **阻断**（校验 #9），默认不写，列入「待确认」 | 文件是批量产物，不能替用户决定 |
| 路径 C 导出 | 导出里带「当前渠道」列 | 让用户**在改之前就看见**会动到谁 |

> 🔴 **为什么四路都要显式确认、不能一路自动**：本项目既有教训是"同一规则抄三份就漂移"。
> 这里反过来 —— **规则只有一条（改绑必须由人确认），四条路径各自实现时不能有例外**。
> 若某一路"顺手改了"，用户会认为系统不可信（"我明明只是导入，怎么价变了"）。

**改绑的界面文案**（必须说清后果，价格是钱）：

> 「好邻居零食（万达店）」现在走的是**分销价**。
> 改到**永辉**之后，它的下单取价会立刻按永辉价算。
> [取消]  [确认改绑]

### 7.3 删渠道 / 停渠道 / 删客户

| 事件 | 行为 |
|---|---|
| **删除渠道** | **级联**失效该渠道全部绑定（`price_channels.py:186 delete_channel` 已级联清矩阵，此处同理） |
| **停用渠道** | 绑定**保留**，但**取价跳过**（判决链里只认 `is_active` 的渠道）⇒ 行为等同回退默认渠道。**并在列表页顶部显式提示**："该渠道已停用，当前这 128 家的绑定暂不生效" |
| **删除/停用客户** | 绑定保留但标记无效；列表页显示"—（客户已停用）"，**不自动删除**（保留审计线索） |
| **客户改名** | 绑定靠 `contact_id` ⇒ **改名不影响**。但导入时的 `external_name` 会与新名不一致 ⇒ 列表页显示"档案名 ≠ 导入名"的浅色提示 |

### 7.4 导入的原子性（部分成功算成功吗）

**算。** 采用"尽力导入"而非全回滚 —— 老板导 300 家因为 15 家重名就把 285 家回滚，是不可接受的。

但**必须**：

### 7.5 性能与超时

758 客户、单次 ≤ 2000 行 ⇒ **同步处理足够**（无需后台任务）。

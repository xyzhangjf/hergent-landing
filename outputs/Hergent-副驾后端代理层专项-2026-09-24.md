# Hergent「副驾后端代理层」专项立项

> 立项日期：2026-09-24　·　提出：差距比对（AI vs WorkBuddy）跟进　·　性质：**架构解锁项**
> 一句话：把 Web 副驾从「浏览器直连外部 Hermes」改为「经本仓后端代理」，从而一并解锁 **M4 模型可切 / L2 自托管兜底 / H1 剩余的权威管控 / 用量计量**。

---

## 1. 为什么要立项（现状证据）

| 事实 | 证据 |
|---|---|
| Web 副驾**直连外部 Hermes**，不经过本仓后端 | `client.js:286` → `fetch('/hermes/v1/chat/completions')` |
| 生产由 nginx 透传 `127.0.0.1:18765`，密钥在 nginx 侧注入 | `/etc/nginx/sites-enabled/hergent` 的 `location /hermes/`：`proxy_pass http://127.0.0.1:18765/`、`proxy_set_header Authorization "Bearer …"`、`proxy_buffering off` |
| Hermes 只监听本机 | `ss`：`LISTEN 127.0.0.1:18765`（所以**后端同机可直连**，而浏览器不行 ⇒ 必须经 nginx） |
| 本仓 `/api/chat` 的第 2 级**本来就是自托管 LLM** | `hermes_core.call_hermes_agent` → `api.deepseek.com`（`hermes_core.py:1382`） |
| 副驾没有任何兜底：Hermes 挂 ⇒ 副驾直接不可用 | 现状链路唯一 |
| 模型由 Hermes 侧定死 `hermes-agent` | `client.js:293` `model: model \|\| 'hermes-agent'` |

**直接后果（三项被同一根钉子卡住）**
- **M4 模型可切换**：模型在 Hermes 侧决定，本仓改不动。
- **L2 自托管兜底**：`/api/chat` 已有自托管，但**副驾主路径**（才是用户天天用的）没有任何兜底。
- **H1 剩余**：AI 模式管控目前靠前端拉 `/api/ai-mode`（H1 已做）⇒ **是软约束**，后端不权威。

⇒ **M4 = L2 = H1 剩余 = "副驾代理层"这一件事的不同切面。合并立项，不要分散做。**

---

## 2. 目标与非目标

**目标**
1. 副驾对话经本仓后端代理（密钥不出后端）。
2. 后端**权威**执行 AI 模式：`disabled` 硬拒、`readonly` 可答不可写（阶段 2）。
3. 支持**按租户/角色/显式指定**选模型（M4）。
4. Hermes 不可用 ⇒ **自动降级到本仓自托管 LLM**（L2），用户无感（仅提示降级）。
5. 全程**流式**体验不变。

**非目标（本专项不做）**
- 不改造 Hermes 引擎本身；不动 IM（企微/飞书）链路（那是 **H3-IM**，另一个专项）。
- 不实现多 Agent 编排（**L3**，另立项）。
- 不在此专项做「硬写门禁」的完整语义（阶段 2 再评估：需要 Hermes 侧配合声明工具风险等级）。

---

## 3. 方案要点

### 3.1 流式透传（🔴 硬约束）
生产 SSE 是**混合协议**：既有 Chat Completions 的 `data: {choices[0].delta.content}`，也有 OpenAI Responses 风格的 `event: response.output_item.added`（工具生命周期）。
⇒ **代理必须字节级透传**，绝不解析再重组（任何改写都会破坏工具事件）。
⇒ 降级路径要**自己合成同格式 SSE**（`data: {"choices":[{"delta":{"content":"…"}}]}`），这样前端解析器零改动。

### 3.2 新增端点（additive，不碰现有路由）
`POST /api/ai/copilot/chat`
- 入参：`{ messages, model?, system? }`
- 出参：`text/event-stream`（与 `/hermes` 同构）
- 服务端策略顺序：`_auth` → **ai_mode 权威判定** → 解析模型 → 调 Hermes（流式透传）→ 失败则**降级自托管** → 计量

### 3.3 开关式灰度（🔴 风险纪律）
前端用 `localStorage.hergent_copilot_proxy === '1'` 决定是否走代理，**默认关闭 ⇒ 现有链路零影响**。
只有显式打开才走新路径；出问题把开关关掉即回滚，不需要回滚代码。

## 5. 风险与回滚

| 风险 | 应对 |
|---|---|
| 动到正在跑的副驾通道 ⇒ 全站副驾不可用 | **开关默认关**；新增端点不删除/不改动 `/hermes`；出问题关开关即恢复 |
| 透传改写破坏工具事件 | 字节级透传，禁止解析重组；降级路径自己合成同格式 SSE |
| 降级（DeepSeek）与 Hermes 回答风格不一致 | 降级时在流里前置一句「（Hermes 不可用，已切换备用模型）」，**不静默降级** |
| 超时：长任务 Hermes 工具循环数分钟 | 沿用前端 300s；后端 `httpx`/`requests` 超时设 300s 并流式读取 |
| 密钥管理 | 密钥只在后端（env/配置），不回传前端、不写日志 |

**回滚**：① 关开关（秒级）；② 需要时删除 include_router 一行并重启（后端已备份）。

## 6. 验收标准（P2 阶段）

- 正常：开关开启后，副驾能正常流式出字、工具事件（ProgressSteps）正常显示。
- 降级：Hermes 不可达时自动切自托管，用户**看到明确降级提示**，不白屏、不静默。
- 模式管控：`ai_mode=disabled` 时后端**硬拒**（非仅前端禁用）。
- 模型：显式指定/租户配置生效（可观测到实际使用模型）。
- 回归：开关关闭时行为与改动前**完全一致**。
- 全程 0 控制台报错。

## 6.6 P2 放量验收记录（2026-09-25 实测）

**放量保险（代码已落地）**：默认走代理，但两条兜底 ——
① 代理返回 **403（无 `chat` 权限）⇒ 自动退回既有 `/hermes`**，副驾绝不被放量搞挂；
② `localStorage.hergent_copilot_proxy='0'` 可整体关闭（紧急回滚，不改代码）。

**权限变更（生产数据写，已备份+断言）**：`tenant_1.role_permissions` 的 `supervisor` 从 `["data","dashboard"]` → **`["data","dashboard","chat"]`**。
（🔴 注：`_DEFAULT_PERMS` 里也缺 chat，但**租户库覆盖优先** ⇒ 只改默认值不生效，必须改租户库。备份在 `/root/backup_tenant1_perm_*`。boss 角色原本就有 chat。）

| 三态 / 场景 | 方法 | 结果 |
|---|---|---|
| **正常** | supervisor 经代理发消息 | ✅ `/api/ai/copilot/chat=200`，流式出字，助手有内容 |
| **停用硬拒** | `PUT /api/ai-mode {disabled}` 后打代理 | ✅ **403**「AI 已被管理员停用」（后端权威，非前端软约束）→ 已还原 `auto` |
| **降级** | 畸形载荷让 Hermes 报错（**零生产影响**，不动 Hermes） | ✅ 自动降级本仓 LLM，输出「（Hermes 不可用，已切换备用模型）」 |
| **无权限退回** | sales（无 chat）发消息 | ✅ `/api/ai/copilot/chat=403` → 自动 `/hermes/...=200`，副驾照常回复 |

**结论**：P2 达标，可进入 P3/P4。

**② 用户自助开关（老板明确要求「给用户开启关闭的权限」）**

  |---|---|

## 7. 待定（需拍板）

1. **降级模型**：默认用 `hermes_core` 现成的 DeepSeek（`deepseek-chat`）；是否要接 GLM/混元做多模型？
2. **P3 的 readonly 硬语义**：需要 Hermes 侧能声明「哪些工具是写操作」——若无此能力，本层只能粗粒度（如禁用命名含 create/update/delete 的工具），存在误伤。
3. **P4 是否回收 nginx `/hermes`**：回收可消除浏览器直连通道，但要确认没有其他客户端（桌面端/小程序）依赖它。

# 管理后台「版本管理机制」方案分析

> 日期：2026-09-25 ｜ 需求：参考微信小程序后台，区分**开发版 / 体验版 / 正式版**，开发版供公司内部查看与内测
> 状态：**方案分析（未动代码）**。所有现状结论均来自 2026-09-25 实测（nginx 实读 + 生产库只读查询 + 源码 grep）

---

## 一、结论先说

**应该做，但不要把微信小程序那套照搬。** 它与我们的最大区别是：

| | 微信小程序 | Hergent |
|---|---|---|
| 「版本」是什么 | **三个独立的包**（开发版=上传的代码包、体验版=指定的包、正式版=审核通过的包） | 前端产物是**静态文件**，无"包"概念 |
| 服务端 | 由微信统一提供，**与客户端版本解耦** | ⚠️ **后端与数据库只有一套**（生产），无法分版本 |
| 数据 | 平台侧统一隔离 | ⚠️ **dev 版前端连的是同一个生产后端 ⇒ 会写生产数据** |
| 切换粒度 | 整包切换 | 应在 **nginx location** 层切换（成本最低） |

⇒ **推荐形态：单域名 + 多子路径**（`/dev/`、`/beta/`、`/`），而不是子域名或独立服务。
**理由**：证书是 SAN 多域名证书（`api.hergent.cn` / `erp.hergent.cn` / `hergent.cn`，**不是通配符**），
新增 `dev.hergent.cn` 要改 DNS + 重签证书；而子路径**零证书成本**，且 nginx 里**已经有现成先例**。

**但真正的难点不在"怎么切版本"，而在"切了之后数据怎么办"。** 见 §三。

## 二、现状核实（都是实测，不是推断）

### 2.1 部署结构（nginx `sites-enabled/hergent` 实读）

```
hergent.cn / www.hergent.cn
├── /opt/hergent-cn-v2         ← root（产品前端，base: '/'）
├── /admin/   → /opt/hergent-admin/         （管理后台，base: '/admin/'）
├── /staging/ → /opt/hergent-erp-staging/   ⚠️ 接线完成但从未启用（目录里无 index.html ⇒ 实测 404）
├── /api/     → 127.0.0.1:8700              （唯一后端）
├── /hermes/  → 127.0.0.1:18765
└── /downloads/、/api/connectors(8765)
```

- 静态资源：`Cache-Control: public, max-age=31536000, immutable`（靠内容哈希）
- HTML：`no-cache, no-store`
- **无 basic auth 先例**（无任何 `.htpasswd`）

### 2.2 已有的"版本"能力

- `hergent-admin/scripts/release.sh`（2026-09-24 建）：以 **`index.html` 快照**为版本单位，
  支持 `snapshot` / `list` / `rollback` / `prune`，生产已留 3 个版本。
  🔴 关键设计（踩过）：**版本单位必须是 index.html 快照，不能是单个 hash** ——
  js 与 css 的 hash 各自独立生成，按单个 hash 回退会拼出「旧 JS + 新 CSS」的错配。
- `.bak-*` / `.tar.gz` 历史备份目录（手工产物，未纳入机制）。

### 2.3 ⚠️ 数据隔离现状：**"只读演示"是空转的**

`POST /api/auth/demo-login` **公网可访问**（实测 HTTP 200），任何人可拿到 demo 租户（tenant 10
「张记乳品（演示）」，`plan=pro`）的 **boss token**（17 个模块全开）。

而后端注释与响应文案都写着「（只读）」：

```python
# routers/auth.py
"""演示入口：返回 demo 租户的 boss token（免注册体验产品）。
   demo 租户由 seed_demo.py 创建；写操作由前端只读模式限制。"""
"message": "欢迎体验 Hergent 演示空间（只读）",
```

**实测结论：**
- 前端 `store.demo` 确实是接线的（`Login.vue` 置位、`client.js` 从响应读）——
  但**只用来在顶栏显示「演示模式 · 模拟数据」标签**（`Shell.vue`），**没有任何写操作门禁**。
- 后端**没有任何 demo 租户的写拦截**（唯一的特殊处理是"演示租户不推企微"，见 `server.py:4846`）。

⇒ **"只读"目前只是文案**。任何拿到 demo token 的人都能对 demo 租户执行写操作，
并且能消耗 AI 对话成本。

**这条不是题外话 —— 它正是版本管理方案的前置条件**（见 §三约束 A）。

## 三、三个硬约束（决定方案形态，不能绕过）

### 🔴 约束 A：后端与数据库只有一套，dev 版前端会写生产数据

这是与微信小程序**本质不同**的地方。小程序客户端分版本，但服务端行为由微信控制、
且客户端能做向后兼容。而我们：

```
/dev/  (新前端) ─┐
/beta/ (新前端) ─┼→ 同一个 /api/ → 同一个 erp.db + tenant_N.db
/      (旧前端) ─┘
```

⇒ **dev 版里的一次"保存"就是生产库的一次真实写入。**

**三条可选解法（按成本排序）：**

| 方案 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **A1 只读沙箱** | dev/beta 版**强制连演示租户**，并在**服务端**硬拦写操作 | 低（1 个中间件） | **推荐起步**：内部看新 UI、内测交互 |
| A2 影子后端 | 再跑一套 uvicorn + 独立 DB | 中（多一个进程 + 库 + 同步策略） | 需要真实数据内测、回归测试 |
| A3 前端 mock | dev 版走 mock 数据层 | 低 | 纯 UI 评审，不验真实数据 |

🔴 **A1 的关键前提是补上「服务端只读强制」** —— 因为现在它是空转的（见 §2.3）。
不能沿用「前端限制」的做法：前端拦不住任何人，而演示入口是**公网匿名可拿 token** 的。

### 🔴 约束 B：SPA 子路径需要 `base` 参数化 ⇒ 每个环境一套构建

`hergent-cn-v2/vite.config.js` 现在是 `base: '/'`（写死）。
子路径部署必须 `base: '/dev/'`，否则 `index.html` 里的资源路径会指向根 ⇒ 404
（`hergent-admin` 就是 `base: '/admin/'`，说明机制本身没问题，只是 cn-v2 未参数化）。

⇒ **代价：不能复用同一份 dist**。每环境一次 `npm run build`（约 3 秒，可接受）。

### 🔴 约束 C：数据库迁移不可逆 ⇒ 这是最深的坑

dev 版若连**真实后端**并触发新迁移（本仓迁移是启动期自动执行的，如
`[schema-sync] … 补列(+N)`），则**正式版前端会面对一个它不认识的 schema**。
多数情况下加列是向后兼容的，但**"改列类型"这类迁移会直接打断正式版**（本仓有
`hergent-sqlite-table-rebuild` 技能专门处理这类重建表）。

⇒ **规则：dev 环境绝不允许触发破坏性迁移。** 要么 A2（独立后端，随便迁），
要么在 dev 启动路径上显式禁用迁移。

## 四、核心功能设计

### 4.1 版本创建（Version Create）

复用已有 `release.sh snapshot` 的**快照语义**，但要补两点：

1. **记录"这是给谁用的"** —— 快照需带 `channel`（dev / beta / prod）与 `note`（这次改了什么）。
2. **记录来源** —— git commit（前端 `laozhangai-product` HEAD）、构建时间、产物 md5。
   🔴 **必须记 commit**：否则回滚时说不清"这个版本对应哪份源码"，而本项目长期脏工作区，
   光看时间对不上。

存储位置建议：后端表 `app_releases`（主库，与 `admin_audit` 同族），字段：
`id / app(cn-v2|admin) / channel / version_id(快照名) / entry_js / entry_css / git_commit / note / created_by / created_at`。

### 4.2 版本切换（Version Switch）

- **发布**：把某快照「指派」给某 channel ⇒ 实质是原子替换该 channel 目录的 `index.html`
  （chunk 全量保留 ⇒ 旧版本立刻可回退，这与 `release.sh` 的设计一致）。
- 🔴 **必须原子**：`index.html` 的写入要 `mv`（rename）而非覆盖写 —— 半写状态会让用户拿到
  引用了不存在 chunk 的 HTML。
- **回滚**：等价于把 channel 指向另一个快照 ✓ 已有能力。
- **切换粒度**：按 **channel** 切（dev 归 dev、beta 归 beta），**不允许跨 channel 直接跳**
  （否则"开发版"这个概念就没了）。

### 4.3 权限控制（谁能操作 / 谁能看）

要分清**两层**，混在一起会做错：

| 层 | 谁能 | 判据放在哪 |
|---|---|---|
| **操作权**（创建/发布/回滚版本） | 仅**平台管理员** | 后端 `_platform_admin`（已有） |
| **访问权**（能打开 dev/beta 页面） | 公司内部员工 / 指定客户 | ⚠️ 见下 |

🔴 **访问权是难点**。三个可选，从弱到强：

1. **nginx basic auth**（`auth_basic`）—— 最简单，一个 `.htpasswd`。
   但**与现有登录体系脱节**（要额外发一套账号），且**对 SPA 不友好**（首次加载弹框、静态资源也要带凭据）。
2. **平台管理员登录态**（dev 版要求"已登录且是平台管理员"）—— 复用现有 token，
   但 dev 版是**独立静态站点**，校验要额外做（前端校验不可信；要 nginx `auth_request` 或后端签发短时 cookie）。
3. **白名单 + IP 限制**（内测阶段够用）—— nginx `allow/deny` 限定办公网 IP，
   或后端维护 `release_access` 白名单表。

⇒ **建议起步用 1+3 组合**（basic auth + IP 白名单），因为**风险最低、当天可用**；
等内部流程稳定后再升级到 2（与登录体系打通）。

### 4.4 访问范围限制（Scope）

除"谁能访问"外，还要限制**能访问到什么**：

- **数据范围**：dev/beta 版是否只能看到演示租户（约束 A 的 A1 方案）
- **功能范围**：dev 版是否禁用"写操作""导出""AI 对话"（避免成本与误操作）
- **入口可见性**：正式版用户**不应看到任何 dev/beta 的入口**（否则会点进去）
- **搜索引擎**：dev/beta 必须 `X-Robots-Tag: noindex`（避免被收录）

## 五、关键设计要点与注意事项（本项目特有的坑）

1. **cookie 同域串味** ⚠️
   子路径（`/dev/`）与正式版**同域** ⇒ `erp_token` / `hergent_tenant` cookie 是**共享**的
   （除非设 `Path=/dev/`）。表现：在 dev 版登录后回到正式版，**登录态带着走**；
   更糟的是 dev 版若把 tenant 切成演示租户，正式版会**跟着切走**。
   ⇒ 要么给 dev 版 cookie 加 `Path`，要么接受并**明确文档化**。
   （对比：子域名方案天然隔离 cookie —— 这是它唯一的优势，但代价是 DNS + 证书。）

2. **浏览器缓存跨环境串味**
   生产 `assets/*` 是 `immutable, max-age=31536000`，靠**内容哈希**区分。
   若 dev 与 prod 恰好构建出**同名 chunk**，浏览器会复用旧缓存 ⇒ "我改了但没生效"。
   ⇒ 建议 dev/beta 构建时**注入环境前缀**到 chunk 名，或让 dev 的 assets 走 `no-store`（内测流量小，无所谓）。

3. **Service Worker / PWA**（如启用）
   同一 origin 下 SW 只能有一个 ⇒ dev 与 prod 会**互相接管**，症状极难排查。
   ⇒ 启用前必须先做 scope 隔离，否则**别在 dev 用 SW**。

4. **版本单位必须是 `index.html` 快照，不是单个 hash**（已在 `release.sh` 修过，别重犯）
   —— js 与 css hash 独立生成，按单 hash 回退会拼出错配组合。

5. **`/staging/` 的遗留接线要先处理**
   nginx 里已有 `location /staging/`（指向 `/opt/hergent-erp-staging/`，目录里是 2026-07-26 的
   旧产物、**没有 `index.html`** ⇒ 实测 404）。新方案要么**复用它**（改名/改指向），
   要么**先删掉**避免两个概念并存（"staging" 与 "dev/beta" 会让人分不清）。

6. **回滚 ≠ 安全网**
   前端能一键回滚，但**后端不能**（同一套）。若新功能依赖后端新字段，
   回滚前端只会得到一个「调用了不存在的接口」的旧前端 ⇒ **前后端版本要配对记录**，
   且**后端改动要先于前端上线**（向后兼容原则）。

7. **迁移与 schema 的时序**
   本仓租户库启动期会自动补列（`[schema-sync] … 补列(+N)`）。dev 版连真实后端时，
   它触发的迁移会**同时影响正式版**。⇒ 见约束 C。

8. **别把"版本管理"做成"两套产品"**
   微信小程序三版本是**同一个功能的不同成熟度**。我们的 dev/beta 也应如此 ——
   **不要**让 dev 版长期承载"只有内部才有的功能"（那会变成两个产品，维护成本翻倍）。

## 六、建议路径（分阶段，每阶段都可停）

| 阶段 | 内容 | 价值 | 前置 |
|---|---|---|---|
| **P0 前置** ✅ **已完成（2026-09-25 晚）** | ① 补「服务端只读强制」—— `tenants.readonly` + RBAC 中间件 READONLY_TENANT 闸门，演示租户已置只读 ② `demo-login` nginx 按 IP 限流 | 消除现有公网可写风险 | 无 |
| **P1 内部可用** | nginx 加 `/dev/` location + `cn-v2` 支持 `base` 参数化 + basic auth；`release.sh` 支持 `--channel` | 内部能看新 UI、敢改 | P0 ✅ |
| **P2 可管理** | 后端 `app_releases` 表 + `/api/platform/releases`（列表/发布/回滚）+ hergent-admin 的「版本管理」页 | 不登服务器也能发版 | P1 |
| **P3 对外体验** | `/beta/` + 访问白名单 + 演示租户隔离 + 邀请链接 | 给客户看、缩短成交路径 | P2 |

**P1 就已是"能用的版本管理"**，P2/P3 是把它从"手工 + nginx"升级成"后台可管"。

### P0 完成实录（2026-09-25，v276）

**为什么先做 P0**：它是版本管理的前置条件（dev/beta 若连演示租户，必须有服务端只读闸门），
同时它本身修掉一个**已在线的真实洞**：

| 检查项 | 修复前实测 |
|---|---|
| `POST /api/auth/demo-login` | **公网免认证**，任何人拿到 demo 租户 boss 权限 token |
| 前端 `store.demo` | 只显示顶栏「演示模式」标签，**不拦任何写操作** |
| 后端写拦截 | **不存在** |
| 实证 | `POST /api/sale-orders` 空 payload → **422「参数校验失败」** ⇒ 已穿过 RBAC 中间件进入业务层，补合法 payload 即可真实写入 |

**修复后生产验证**（commit `eba0f65`，已推）：

| 用例 | 结果 |
|---|---|
| demo 写（X-Tenant-Id: 10） | **403** READONLY_TENANT |
| demo 写（**换租户头** X-Tenant-Id: 1） | **403** ⇒ 绕不过 |
| demo 读 | **200** ⇒ 读放行 |
| 无 token / 无效 token 写 | **401** ⇒ 没误伤认证链 |
| 正常租户 `readonly` | **False** ⇒ 不受影响 |
| `demo-login` 连打 12 次 | 前 6 次 200、后 6 次 **429** |

**设计要点（写代码时定死的三条）**：
1. **回落方向取宽**：读不到租户属性（主库异常 / 迁移前列不存在）⇒ `False`（不锁正常租户）。
   14 项沙箱断言专门钉住 —— 误锁会让整租户写操作集体 403 且无法自助恢复，比没这功能更糟。
2. **闸门位置在 `_check_perm` 之前**：只读是「租户层面不允许写」，与「角色有无该模块权限」
   是两个层面。先判租户，任何角色（含 boss/admin）都写不进去。
3. **租户口径与 `_check_perm` 完全一致**（都走 `effective_tenant_key`）：若用请求头判，
   attacker 只要**不带 `X-Tenant-Id`** 就绕过了。实测已验证「换租户头仍是 403」。

## 七、明确不做什么（边界）

- ❌ **不为后端做版本管理**：Go 单一后端 + 单一 DB，做"后端多版本"是另一个量级的工程（服务网格/多实例路由），
  且会破坏"后端先上线、前端向后兼容"这条更简单有效的纪律。
- ❌ **不用子域名起步**：证书是 SAN 非通配，加子域名要 DNS + 重签，收益（cookie 隔离）不足以抵成本。
- ❌ **不做"按租户分版本"**：那是灰度发布，与"环境隔离"是两个需求，混做会同时做不好。
- ❌ **不引入 CI/CD 平台**：一人公司 + 现有 `release.sh` 已够；引入 Jenkins/GitLab CI 的运维成本会失控
  （这是项目既有红线①：运维成本不可失控）。

## 八、需要你拍板的两件事

1. **dev/beta 版连哪个后端？**
   - 选 A1（只读 + 演示租户）⇒ 成本最低，但只能"看"不能"真操作"
   - 选 A2（独立影子后端）⇒ 能真操作、能回归测试，但要多维护一套进程 + 库
2. **访问控制起步用哪种？**
   - basic auth + IP 白名单（当天可用，但与登录体系脱节）
   - 或直接做"平台管理员登录态"（体验更好，工作量更大）

## 九、必要性再评估（2026-09-25 晚 · 用户追问「真的有必要吗 / 会不会涨运维成本」后）

> 用户问了三件事：① 以后改代码的流程是什么、AI 会不会遵守规则；② 做版本管理真的有必要吗；③ 会不会增加运维成本。
> 重新核实后，**本报告的推荐要改**：P2/P3 暂缓，P1 降级，另立一件更高优先级的事。

三个实测事实改变了判断：

### 事实 1：生产与 git 的偏差在**扩大**，不是收敛

| 时间 | 「生产含 git 没有的内容」 |
|---|---|
| 09-25 上午（首次审计） | 24 个文件 |
| 09-25 晚（本次复查） | **28 个文件**（已部署未提交 19 + 未入库新产品 9） |

我写过报告、警告过、还做了 `pss-check.py`。**偏差照样从 24 涨到 28。**
⇒ 对「AI 会遵守规则吗」的实证回答：**不会，而且不该指望它遵守。**
正确的问法不是"AI 会不会遵守"，而是「**违规之后，多久会被发现**」。

### 事实 2：本地预览**零成本已可用**（本次实测）

`hergent-cn-v2/vite.config.js` 里**早就配好了** `/api → 真实后端` 的代理。实际执行 `npm run dev` 的结果：

- `127.0.0.1:5199/` → HTTP 200
- `127.0.0.1:5199/api/products` → **401**（与生产返回一致 ⇒ 请求真的打到了生产后端，只是没带登录凭据）

⇒ **"改完先给你看一眼"这件事今天就能做** —— 不需要 nginx 改配置、不需要 basic auth、不需要子路径、不需要额外一次构建。
P1 里剩下的唯一价值是"给**不在你电脑上**的人看"。那要等真的有第二个人需要时才做。

### 事实 3：dev 环境的价值上限是「看界面」，不是「测数据」

因为约束 A（后端 + 数据库只有一套）**绕不过去**。dev 页面上点"保存" = **写你的真实生意数据**。
⇒ 把 dev 环境讲成"测试环境"会给人**虚假的安心感**。诚实的说法是"**静态预览**"。

### 9.1 重排后的优先级

| 优先级 | 做什么 | 一次性成本 | 长期运维成本 |
|---|---|---|---|
| **P0′（最高）** | 把 `pss-check.py audit` 挂成**每天自动巡检**，一旦「生产含 git 没有的内容」就推企微 | 1 轮配置 | **0**（无人值守） |
| **P1′（次高）** | 固化「改 → 本地预览 → 你确认 → 上线」流程（我起服务，你用内置浏览器点） | **0**（已可用） | **0** |
| **P2（暂缓）** | `/dev/` 网址 + basic auth + `base` 参数化 | 1–2 轮 | 多一个目录 / 一个 location / 一套账密 / 每次多一次构建；**且会随时间腐坏**（长期不部署就与正式漂移，而"漂移"本身又是新坑） |
| **P3（暂缓）** | 后台「版本管理」页 + `app_releases` 表 | 2–3 轮 | 多一张表 + 一个页面要长期维护 |
| **不做** | 三版本机制（开发版 / 体验版 / 正式版） | — | — |

**为什么把"自动巡检"提到最高**：它直接回答最初的问题 —— **不靠"AI 会遵守"，靠"违规每天会被发现"**。
成本近乎为零，且**发现得越早，坏账越少**（现在是 28 个文件，再放一个月就是几百个）。

**为什么"三版本机制"不做**：它解决的是"**回到昨天那一版**"（回滚）。而你从来没有这个需求 ——
你的需求是"**改回去**"（跟我说一句话就行）。**为不存在的需求建基础设施 = 纯增运维成本。**

### 9.2 运维成本的诚实账

真正推高运维成本的**不是磁盘和 CPU**（那几个前端目录加起来也就几十 MB），而是这三样：

1. **多一道"必须记得做"的手续**（每次改完要发两个地方；漏发一次，两个环境就不一致）
2. **多一个会随时间腐坏的东西**（dev 环境长期不用 ⇒ 与正式漂移 ⇒ 再打开时看到的是过期界面）
3. **多一个失败面**（dev 站挂了 / 证书到期 / 账密忘了 —— 每一样都要人来处理）

**P0′ + P1′ 这条路，上面三条一条都不产生。**

### 9.3 对「AI 会遵守规则吗」的完整回答

不能靠纪律，要**把规矩做成跑得起来的检查**。已落地的三层：

| 层 | 机制 | 现状 |
|---|---|---|
| 工具 | `pss-check.py`（audit / deploy / commit 三模式） | ✅ 已有，实测查得出问题 |
| 纪律 | `hergent-scoped-commit` §5.36 / §5.36b（提交按 HEAD、部署按生产、可达性审计） | ✅ 已有 |
| **自动** | **每天定时跑 audit，异常推企微** | ⬜ **待做（P0′）** |

只有第三层才真正回答"会不会遵守"—— 前两层都得靠"记得跑"。

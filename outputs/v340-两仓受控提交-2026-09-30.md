## 二、为什么是「同步型」而不是「按 hunk 归属」

技能 §5.40 明确这是**两条不同的路**。选错的代价：拿归属思维写提交信息，会**把别人的工作记在自己名下**。

| | 归属型 | **同步型（本轮）** |
|---|---|---|
| 适用 | 在脏工作区里只提交**我的**几处 | 一堆改动**早已上线、却从未提交** |
| 判据 | 逐 hunk 归属 | **逐文件比 md5：本地工作区 == 生产** |
| 提交内容 | HEAD + 我认领的 hunk（第三产物） | **整个工作区文件**（就是线上那一版） |
| 提交信息的责任 | 说清「哪些 hunk 是我的」 | 说清「**我不主张作者权**，只让 git 追上生产」 |

**本轮的三个判定依据**：
1. 两仓改动**都已上线** —— 前端 v339 dist == 生产 **56/56 逐字节**；后端 **9/9 md5 一致**；
2. **跨会话已停**（老板明确告知）⇒ 不存在「另一会话还在改同一文件」的动态风险；
3. v339 那次「同文件交织」的顾虑**已消失** —— 交织的两个会话改动**都已在生产上**。

## 六、🔴 途中抓到的隐患：差一步就是灾难

### 6.1 `hergent-cn-v2/` 下有 28 个未跟踪的 `dist-vNNN/` 构建快照

原计划用 `git add hergent-cn-v2/` 提交 37 个源码文件 —— **这会把上万个构建文件吞进历史**：

- `hergent-cn-v2/.gitignore` 此前只忽略了**精确的 `dist/`**（`git check-ignore` 可证），
  **不匹配** `dist-v303/` / `dist-v309/` / … / `dist-prev-303/`；
- 实测 `git status --short -- hergent-cn-v2/ | grep -c '^??'` = **28**；
- 每个快照 = 一整套 `assets/`（数百个 JS/CSS + 字体 + 图片）⇒ 合计数万个文件；
- 这类误入库**事后极难清理**（`filter-repo` 重写历史，代价高且影响所有克隆）。

**规避三件套（已执行）**：
1. 改用 `git add -u hergent-cn-v2/` —— **只更新已跟踪文件**，不新增；
2. 加**夹带断言**：`git diff --cached --name-only | grep -c 'dist-v'` 必须 **= 0**（实测通过）；
3. **顺手补 `.gitignore`**（`696d402`）加 `dist-*/` —— 堵住「下一次 `git add .`」。

**自证**：`hergent-cn-v2/` 下 `??` 计数 **28 → 0**；`git check-ignore` 对
`dist-v326` / `dist-v319b` / `dist-prev-303` **三条全命中**。

### 6.2 三个目录都有大量未跟踪文件

`.workbuddy/` **133 ??**、`outputs/` **126 ??**、小程序 **3 ??**
⇒ 一律用 `-u`，**未跟踪项一个都没进**。这已写进技能 §5.40 九。

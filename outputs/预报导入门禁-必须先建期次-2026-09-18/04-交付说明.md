## 二、变更（关键决定与理由）

### 2.1 判据是「有没有**进行中**的期次」，不是「有没有期次」—— 依据是既定方案，不是我拍的口径

这是本轮**最重要的一条**，也是我**第一版做错、随后自我纠正**的地方，留档如下。

**第一版（已推翻）**：按「有没有期次」做判据（有期次就放行）。沙箱 `6/6 + 8/8` 全绿就准备交付。写交付说明时去核「既定方案」到底怎么写的，才发现方向错。

**项目内已有用户拍板的方案**：`outputs/期次数据流程优化方案-2026-09-17/期次数据流程优化方案-2026-09-17.md`，§四.1 原文：

> **不是「必须先建期次」，而是「必须有一个『进行中』的期次」。**

三条理由（方案原文）：

1. 归属**事后不可回填** —— 导错了期次，之后新建期次也不会把数据跟过去；
2. **昨天事故的直接根因** —— 导入时 7/8/9/10 期**全 closed** ⇒ 兜底把 **154 个商品挂到了已关闭的 9 期**，用户在页面上根本看不到；
3. fail-closed 铁律 —— **做不到正确归属，就不要写进去**。

方案同节还专门点名了这个坑：

> `forecast_period_default()` 的函数文档**自称『仅展示用』**…但它**被导入路径当成了落库归属的兜底**。闸门若只加在「有没有期次」而不收窄这个兜底，**闸门形同虚设**（closed 期次仍会被兜底选中）⇒ 收窄为：**导入侧只接受 `status='open'` 的期次**。

**两者的差别就是事故场景**：

| 场景 | 判据＝「有没有期次」 | 判据＝「有没有进行中期次」 |
|---|---|---|
| 有 open 期次 | 放行 | 放行（一致） |
| **期次全 closed** | **放行 → 数据挂到已关闭期次（事故本体）** | **拒绝**（正确） |
| 零期次 | 拒绝 | 拒绝（一致） |

⇒ 于是**推倒重做**：前端判据换成 `openPeriodId`，后端**删掉 `default()` 兜底**。

### 2.2 漏洞本体在后端，不在前端

旧 `_execute_forecast_cross` 的归属解析是两级兜底：

```python
# 旧：取不到 current 就用 default 兜底
_p = db.forecast_period_current() or db.forecast_period_default()
```

`forecast_period_default()` 的末级兜底 = **最新创建的期次（不限状态）**。因此：

- **期次全 closed** ⇒ 兜底选中一个**已关闭**的期次，数据写进去、用户看不见（＝事故）；
- **一个期次都没有** ⇒ `_period_id` 落 **0**（幽灵归属），**照样写库**。

两种都照样写库 ⇒ 前端置灰只是提示，`curl` 直接打接口就能绕过。**约束必须落在唯一的执行体上**。

### 2.3 后端硬闸：`_period_id <= 0` ⇒ 400，一个字节都不写

```python
_period_id = 0
try:
    _cur_p = db.forecast_period_current()   # 只认 open
    if _cur_p:
        _period_id = int(_cur_p.get("id") or 0)
except Exception as e:
    logging.getLogger("hergent").warning("导入期次解析失败，period_id 落 0: %s", e)

if _period_id <= 0:
    raise HTTPException(400, "当前没有进行中的期次：请先到「预报订货」页点「新建期次」创建期次，再导入预报订单。…")
```

闸门位置的两个前提（都已核过）：

- `_execute_forecast_cross` 是预报导入**唯一**的落库入口 —— `/preview` 只解析不落库、`/one-shot` 不产出 `forecast_cross`；
- 客户端**从不传 `period_id`** ⇒ 不存在「客户端传对了却被这里覆盖」的问题。

### 2.4 前端五道（判据与服务端同源）

| # | 位置 | 做法 |
|---|---|---|
| 1 | `loadPeriods()` | `openPeriodId` ← `GET /periods` 新增的 **`open`** 字段；同时置 `periodsLoaded = true` |
| 2 | `openImport()` | 函数内硬守卫：`!canImport` 就 `toast` + `return`（挡直接调用与将来新增的第三个入口） |
| 3 | 工具条 + 空态的导入按钮 | `:disabled="!canImport"` + `:title` 说明原因与下一步 |
| 4 | 顶部**常驻横幅** | `noOpenPeriod` 时渲染，文案＝方案 §五 阶段 0 原文，并**就地**放一个「新建期次」按钮 |
| 5 | 空态 | 无进行中期次时改指路「新建期次」，**撤掉**原本递到手上的「导入 Excel」 |

**同源保证**（这条是防漂移的关键）：

```
前端 canImport  ←  GET /periods 的 open 字段
                    ←  后端 forecast_period_current()
                        ←  后端硬闸判定归属用的同一个函数
```

⇒「前端按钮灰不灰」与「后端会不会 400」是**同一条件**，不可能各算一份而漂移。

### 2.5 两个容易踩的细节

**① `current` 与 `open` 不可互换。** `current`（= `forecast_period_default()`）是**展示**口径，期次全 closed 时仍会兜底到某期次 —— 它服务默认视图（`curPeriod = 0` 会让汇总表落「今天~今天」成空表）；`open`（= `forecast_period_current()`）只认真实进行中的期次。所以**新增字段**而不是改语义。

**② `periodsLoaded` 标记是必需的，不是多余的。** `loadPeriods()` 的 catch 是**静默**的 —— 接口抖动 / 401 时 `openPeriodId` 停在初始值 0，而 0 恰好就是「没有进行中期次」的判据。少了这个标记，网络一抖就会把导入入口**锁死**，用户看到的是「功能没了」。这正是本项目最忌讳的形态：**静默失败伪装成能力缺失**。故只有**成功加载过**才允许「确实没有进行中期次」这个结论成立。

### 2.6 顺带修掉的项目基础设施缺陷：沙箱库「读得到、写不了」

本轮在沙箱里跑真机时踩到：导入回执是 `{"success":0,"errors":["客户「永辉」导入失败: attempt to write a readonly database"]}` —— **接口 200、看着像业务失败**，极易误判成「产品坏了」。

根因：`sandbox_tenant.py` 用 `shutil.copy2` 克隆库，而 **`copy2` 只搬 mode/mtime，不搬 uid/gid**；本工具是用 `ssh root@<prod> python3 sandbox_tenant.py up` 跑的 ⇒ 新库属主 = **root:root**，而后端 systemd 以 **hergent** 运行 ⇒ 后端只读。旧注释写的「属主已是 hergent（脚本以 hergent 跑）」在 ssh-as-root 下**不成立**。

修法：属主跟着**源库**走（取 `os.stat(src_db)` 的 uid/gid，不硬编码 `hergent`，换部署用户也不失效）。

**还有一个必须记住的连带项**：后端有 SQLite 连接池（按 `(线程, 库路径)` 缓存），而 SQLite 在**打开那一刻**就定死读写权限 ⇒ 修完属主**必须** `systemctl restart hergent-erp` 清池，否则旧只读连接会被复用、症状不变。

# P3「`readonly` 硬语义」可行性勘察（2026-09-25，只读勘察）

> 归属：副驾后端代理层专项 P3　·　结论：**可行，且拦截点就在本仓库；已完成大半，剩两个缺口**

---

## 1. 结论先行

| 问题 | 答案 |
|---|---|
| 能不能权威判定「哪些工具是写操作」？ | ✅ **能**。ERP 的 40 个工具全部定义在**本仓库** `hermes_core.TOOLS`，由 `execute_tool()` 单一分发。 |
| 需不需要 Hermes 侧配合？ | ❌ **不需要**（我此前判断错了）。**唯一拦截面在 `hermes_core.execute_tool`** —— Hermes 无论怎么调（含用 `code_execution` curl），最终都落到这里。 |
| 现在拦住了吗？ | 🟡 **拦了一半**：已有 `readonly` 门禁，但**两个缺口**（见 §3）。 |

**⇒ P3 从「需外部配合的大工程」降级为「本仓库内的两处小修」。**

---

## 2. 关键事实（证据）

- **工具面**：`hermes_core.py:TOOLS`（`TOOLS` 40 个；租户技能 `hergent-erp-tools/SKILL.md` 写的「28 个」**已过期**，且它只列了速查子集）。
- **单一分发表**：`hermes_core.py:265 execute_tool(tool_name, params)` —— 40 个工具全在这里 `if/elif tool_name == ...` 分发，`/api/bot/tools/{tool_name}` 与 `/api/bot/chat` 都经过它。
- **已有门禁**（`hermes_core.py:268-274`，本轮之前就存在）：
  ```python
  mode = db.get_ai_mode()
  if mode == "readonly" and tool_name in HERMES_WRITE_TOOLS:
      return {"success": False, "error": "当前为只读咨询模式，写入操作已拦截。请切换到自动模式。"}
  ```
- **写工具清单**：`HERMES_WRITE_TOOLS = {create_customer, create_product, create_sale_order, create_purchase_order, record_payment}`。
- **全量写调用扫描**（扫 `execute_tool` 全体 468 行，匹配 `db.*(create|update|delete|save|set_|add|insert|calculate|apply|write)*`）：

  | 工具 | 写调用 | 已登记？ |
  |---|---|---|
  | create_customer | `contact_create` | ✅ |
  | create_product | `product_create` | ✅ |
  | create_sale_order | `sale_order_create`, `payment_create` | ✅ |
  | create_purchase_order | `purchase_order_create` | ✅ |
  | record_payment | `payment_create`, `prepayment_create` | ✅ |
  | **run_payroll** | **`salary_batch_calculate`** | ❌ **漏登记** |

  其余 34 个工具（`search_*` / `check_*` / `get_*` / `*_analysis` / `predict_*` / `*_summary` …）经查**均为只读**。
  特别核实了两个「名字像写、实际是读」的：`open_forecast_period`（只 `forecast_period_current()` 读当前期次）、`generate_template` / `match_bank_statement`（只回摘要）。

## 3. 🔴 两个真实缺口

### 缺口 A：`run_payroll` 未登记为写工具
`run_payroll` → `db.salary_batch_calculate(month)` **会生成/写入工资批次记录**，但它**不在** `HERMES_WRITE_TOOLS`。
⇒ **「只建议」模式下，AI 仍可被诱导执行算工资**（写出工资数据）。与 `record_payment`（会写收付款）同级，应同等拦截。

### 缺口 B：`disabled` 在工具层完全没有门禁
`execute_tool` 只判 `readonly`，**完全不判 `disabled`**；`routers/bot.py` 的 `/bot/tools/{name}` 与 `/bot/chat` **也没有** `ai_mode` 检查（grep 无命中）。
⇒ **管理员「停用 AI」之后，`POST /api/bot/tools/create_sale_order` 仍可直接写入订单**。这正是 H1 想堵的「后台关 AI 但仍有路可用」口子在 **bot API** 上的残留。
（H1 当时只修了 **Web 副驾**那一条路径。）

---

## 4. 建议修法（本仓库，小改）

1. 把 `run_payroll` 加入 `HERMES_WRITE_TOOLS`。
2. `execute_tool` 增加 `disabled` 分支：**停用时拦截写操作**（读操作保留，零副作用，避免误伤只读调用方）。
3. （可选，纵深防御）`/bot/tools/{name}` 与 `/bot/chat` 各加一次 `ai_mode` 前置判定 —— 与 `execute_tool` 双保险。

**验收方式**：`readonly` 下调 `run_payroll` 应被拦；`disabled` 下调 `create_sale_order` 应被拦。两者都是「期望被拦」，**不会产生真实写入**，可安全在生产验证。

---

## 5. 边界与残留风险（诚实说明）

- 本层拦的是**工具调用**。若 Hermes 用 `code_execution` 直接 `curl` ERP 的 **REST 接口**（绕过 `/api/bot/*`），需要另一套凭据与 RBAC；现有 ERP RBAC 仍在。**彻底收口需在 ERP REST 层再设一道**（另议）。
- 租户技能 `hergent-erp-tools/SKILL.md` 里**明文写了**「从 `erp.db` 取 token」的做法 ⇒ 提示词注入下存在提权面。这是既有的、独立于本专项的风险，建议后续单独立项收紧。
- 本勘察**未改动任何代码/配置**（纯只读）。

# 「AI 团队」角色切换 —— 设计评估与补齐清单（2026-09-29）

> 起因（老板观察）：「切换角色后只换了头像，没有开新对话，也没体现角色能力、上下文或权限差异。」
> 本文基于**代码级核对**（非印象）回答三件事：① 今天到底切了什么 ② 有没有意义、合理用途与局限 ③ 要补什么才真的有价值。

---

## 一、今天切一个角色，**实际**改变了什么（逐条带代码位置）

| # | 实际变化 | 证据 |
|---|---|---|
| 1 | 头像 + 名称（胶囊、以及**全部历史回复**的头像） | `CopilotDrawer.vue:87-88` 助手头像渲染用的是 **`currentRole`**（当前角色），不是"回答时的角色" |
| 2 | **下一条**消息的 system prompt | `send()`：`let sys = currentRole.value.system_prompt`（每次发送现取） |
| 3 | 回复落定后**推送到该角色绑定的 IM 渠道**（企微/飞书） | `CopilotDrawer.vue:1805` → `POST /api/ai/roles/{role_id}/push` → `push_role_channels(tid, role_id, …)` |
| 4 | `opening`：只在**下拉菜单里当副标题**显示 | `CopilotDrawer.vue:381`（`cp-role-item-desc`）+ `RoleManage.vue` 表单提示；**不产生任何行为** |

**而下面这些，切换时一个都不动**（`CopilotDrawer.vue:1035 pickRole()` 全文只有两行：`setAiRole()` + 关菜单）：

- ❌ 对话内容/上下文 —— `chat.messages` 原样保留（`newChatSession()` 只有点"新对话"才清）
- ❌ AI 权限档（只给建议 / 可直接执行）—— `aiGuard` 是**另一个独立开关**，与角色无关
- ❌ 会话归属 —— `saveCurrentSession()` 只存 `messages + updated_at`，**不存角色**
- ❌ 后端感知 —— 请求体里**没有 role_id**；`copilot_proxy.py` 全文只提到 messages 里的 `role:'user'/'system'`（命中 2 处，全是消息结构）
- ❌ 能力/数据范围 —— 角色表的字段只有 `name / system_prompt / opening / avatar / built_in / is_active / sort_order / custom_avatar`（`server/ai_roles.py:100`）；**没有** 技能、工具、模型、数据范围、权限任何一列。后端亦无 `ai_role_skills` 之类的表

⇒ **一句话**：今天的"角色"= **人格提示词前缀 + 署名头像 + 推送落点**，仅此三者。

## 二、这个设计有意义吗

### 结论：**有意义，但很弱**；它当前真正的价值**不在"换人格"，而在"多渠道分身"**；另有一处**既存缺陷**（见 §2.3）

### 2.1 合理用途（现在就能兑现的）

1. **多渠道分身（唯一"硬"的用途）**：角色↔渠道绑定（`ai_role_channels`）真实存在 ⇒
   「会计」推财务群、「客服助手」推客户群、「大秘」推老板私聊 —— **同一个人格/落点/署名**打包成"团队"，
   这是"团队"这个词目前唯一有实体支撑的含义。
2. **人格前缀（在"新会话 / 单轮"下有效）**：`system_prompt` 确实注入了 ⇒ 开一个新对话问同一个问题，
   不同角色的口径/语体/关注点会不同。**这是它现在唯一"看起来像能力"的地方**。
3. **产品叙事的入口**：前端已把它摆在"会话级配置"的位置（＋ 之后、与权限档并列），
   未来接技能包/数据范围时**不需要重新教育用户**在哪切 —— 锚点已经在了。

### 2.2 局限（为什么老板会觉得"等于没切"）

| # | 局限 | 机制上的原因 |
|---|---|---|
| L1 | **历史被追溯性改写** | 头像用 `currentRole` 渲染 ⇒ 切到"会计"后，**此前所有"经营副驾"的回复也变成会计的头像**。历史不是"谁说的"，而是"现在是谁" |
| L2 | **上下文不隔离** | 同一个 `chat.messages` 池子。财务问过的金额、客户群里答过的话，都留在下文里被新角色继续引用 |
| L3 | **提示词被上文压过** | system prompt 只是"开头一句话"，而上下文是**几十条具体内容**。模型的行为主要由上文决定 ⇒ **切了也还是原来那个口气**（这是"没体现差异"的主因） |
| L4 | 🔴 **角色 ≠ 权限**（最容易被误用的地方） | 真正的边界是**用户的** RBAC 模块权限 + `ai_mode`（readonly/disabled）。把"切到会计"理解成"看不到财务以外的东西"是**危险的误解** —— 它挡不住任何越权 |
| L5 | **没有能力差异** | 无技能/工具/模型/数据范围字段 ⇒ 三个角色读的是同一套工具、同一批数据、同一个模型 |
| L6 | **切换无反馈** | 切完只有胶囊变了。用户无从判断"是否生效""从哪一条开始生效"（老板这次的疑问本身就是这条的证据） |
| L7 | **会话不记角色** | 打开一周前的会话，显示的是**当前**角色，不是当时的 |

### 2.3 🔴 一处应当独立修掉的缺陷（与"设计取向"无关）

**L1 是既存缺陷，不是取舍**：它让"切换角色"在追溯上等于**改写历史署名**。
在有多人协作/审计诉求的场景里（这正是"团队"想表达的东西），历史署名必须**快照**。
修法极小：发送时把 `roleId` 写进该条消息，渲染时读 `m.roleId`（缺失则回落 `currentRole`）。

## 三、要真正体现"角色切换"的价值，需要补什么

按「**先让它说真话 → 再让它有差别 → 最后让它有边界**」三层递进，附成本与依赖。

### L0 · 立即正确（各 1 个文件，小时级）

| # | 机制/交互 | 具体做法 | 解决 |
|---|---|---|---|
| **P0-1** | **消息级角色快照** | 用户消息写入 `m.roleId = currentRole.role_id`；回复消息继承；头像/署名改读 `m.roleId`（缺失回落）。会话历史因此天然带上"谁说的" | L1、L7 |
| **P0-2** | **切换即分界** | 切换时往时间线插一条**系统分隔卡**：`—— 下面由「会计」回答 ——` + 把该角色 `opening` 作为引导语显示。**让 `opening` 从"菜单副标题"回归它本来的用途（开场白）** | L6、L3（部分） |
| **P0-3** | **生效前可见** | 切换后、未发消息前，输入框上方常驻 chip：`将由「会计」回答`（可一键切回）。用户第一次切角色就能确认"确实生效了" | L6 |

### L1 · 让上下文有语义（1–2 天）

| # | 机制 | 做法 |
|---|---|---|
| **P1-1** | **切换时二选一** | 弹一次轻确认：`新开对话（推荐）` / `继续当前对话`。选"继续"时在 system 里显式声明：*"上文由其他角色的回答组成，仅供参考，不要沿用其口径"* —— 这是**低成本缓解 L3** 的关键一句 |
| **P1-2** | **会话按角色分池**（可选） | 历史列表显示角色徽标；按角色过滤/切换上下文。收益：L2 彻底解决；代价：用户心智变复杂（"我刚才在哪问的？"） ⇒ 建议做成**可选筛选**而非强制分池 |

### L2 · 让角色真有差别（产品级，建议排进路线图）

| # | 机制 | 做法与红线 |
|---|---|---|
| **P2-1** | **角色能力字段** | `ai_roles` 扩列（或新表 `ai_role_caps`）：`skills`(技能包) / `tools`(可用工具集) / `model` / `data_scope`(可读模块) / `guard`(只建议·可执行) / `channels`(已有) |
| **P2-2** | 🔴 **后端按角色裁剪，前端只传 role_id** | 现在 system 由**前端拼**、后端不知道角色 ⇒ 前端一改就能越权。**必须**改成：前端只传 `role_id`，由后端取角色定义、拼 system、裁工具集。这是"角色能当能力边界"的**前提** |
| **P2-3** | **角色权限 ∩ 用户权限（fail-closed）** | 角色只能**收窄**、不能放大用户已有的 RBAC。写操作按角色白名单 + 只读租户仍硬拦 | 
| **P2-4** | **per-role 审计与配额** | 记 `role_id / user / 用了哪些工具 / 耗时 / token` ⇒ 才能回答"哪个角色真在被用""值不值得养"（也给 B 端按角色定价留口子） |

### 与产品战略的关系（为什么值得投）

角色的字段设计**正好是"行业技能包 + 数据范围 + 渠道"的打包单位**。
把它补成 P2-1 那样，`会计 / 客服 / 大秘` 就不再是三个头像，而是三份**可交付的能力包** ——
这与"配方化 + 行业 skill pack"的路线是同一件事的两个面。反之，若不补，
"AI 团队"会一直停在**头像切换器**，而它占着的那个 UI 位置（会话级配置）反而在**承诺**它做不到的事。

---

## 四、最小可落地清单（若只做一件事）

**做 P0-1 + P0-2 + P0-3**（三个小改动，同一批上线）：
从此切换角色会**当场可见**（分隔卡 + 输入框 chip）、**历史不再被改写**（消息级快照）、
`opening` 有了真实用途。这三条**不改变任何后端行为、不引入新依赖**，但能立刻消掉"等于没切"的观感。

> ⚠️ 明确的**不做**（避免把简单问题复杂化）：不要为了"看起来有差异"而给每个角色硬造不同的回答模板 ——
> 那会让同一句提问在不同角色下得到**不可比**的答案，反而毁掉"经营副驾"的可信度。
> 差异必须来自**真实的能力/数据/权限**差异（L2），或**诚实的上下文声明**（P1-1）。

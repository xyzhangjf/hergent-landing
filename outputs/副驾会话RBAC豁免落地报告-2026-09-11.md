# 副驾会话 RBAC 豁免（B 方案）落地报告

- **日期**：2026-09-11 15:25
- **目标**：让非管理角色（sales / supervisor）也能把自己的 AI 副驾会话存到服务端，从而支持跨设备历史
- **结论**：✅ 已上线；后端 + 前端三级验证全绿

---

## 一、为什么做（问题闭环）

上一次修复解决了前端「本地缓存阻断服务端拉取」的根因，但留下一个权限层的问题：

| 角色 | 能聊天 | 能存会话 | 换设备看历史 |
|---|---|---|---|
| 管理员 | ✅ | ✅ | ✅ |
| sales / supervisor（改造前） | ✅（走 `/hermes/`） | ❌ 403 | ❌ 永远没有 |

原因：`/api/ai/*` 整体挂在 `chat` 模块下 fail-closed，但副驾对话本身走 `/hermes/` 不经这条 RBAC
→ 这类角色处于「**能聊天，但会话永远只留本机**」的割裂状态。

**选定方案 B**：只豁免「自己的会话」这一族路径，其余 `/api/ai/*` 照旧管。

---

## 二、改动

**单文件**：`hergent-erp/server/server.py`（RBAC 中间件内新增白名单）

```python
# v124 (2026-09-11): 会话持久化豁免 RBAC —— 这一族路径只读写"自己的会话"
# （chat_sessions 表 WHERE user_id=?，不触碰任何业务数据），故不按 chat 模块管。
# ...
# 覆盖：/api/ai/sessions*（列表/明细/写入/删除）+ /api/ai/search-chat（跨会话检索，
# 同样只查自己的 chat_sessions —— 只豁免前者会让历史面板的搜索框静默失效）。
# 其余 /api/ai/*（roles / profile / daily-log / advice / usage …）照旧按 chat 模块
# fail-closed；认证仍由上方 _get_user 强制（会话路由内部再调 _auth 二次兜底）。
if path.startswith("/api/ai/sessions") or path.startswith("/api/ai/search-chat"):
    return await call_next(request)
```

### 三条位置/范围设计

1. **放在 `_get_user()` 之后、模块判定之前** → 只跳过「模块权限」这一层，**认证仍然强制**
   → 匿名访问照旧 401。
2. **`search-chat` 必须同批纳入** —— 这是本次最易漏的点。只写 `sessions` 会出现
   「历史列表正常、**搜索框静默 403**」，页面上极难发现（本次中断后生产正是这个半成品状态）。
3. **只豁免「自己的数据」族** —— 判断依据是后端 SQL 带 `WHERE user_id=?`、不触碰任何业务表。
   `daily-log`（读经营指标）、`roles`、`profile` 属业务数据，**必须留在模块内 403**。

## 四、验证（三级，全绿）

### ① 后端边界（API 层 10 项）

| 断言 | 结果 |
|---|---|
| sales / supervisor 拉会话列表 | **200**（原 403） |
| sales 搜历史对话 `search-chat` | **200** |
| sales 写 / 读 / 删自己的会话 | 200 / 200 / 200 |
| **roles / profile / daily-log / advice** | **仍 403** ← 证明豁免没放大 |
| **匿名访问 sessions** | **仍 401** |
| 演示租户（boss 类） | 不受影响，200 |

### ② 跨用户隔离（5 项）—— 安全底线

| 攻击面 | 结果 |
|---|---|
| supervisor 拉列表是否看到 sales 的会话 | **不含**（列表 0 条） |
| supervisor 按 id 直读 sales 的会话 | **404**，无内容泄露 |
| supervisor 试图删 sales 的会话 | 返回 `{"ok":true}` 但**无副作用**（`WHERE user_id=?` 不命中） |
| 原主（sales）回读 | 内容**仍在** |

> 越权 DELETE 返回 ok 是幂等语义，故意不暴露「该 id 是否存在」——断言必须查「原主回读内容是否仍在」，
> 不能只看状态码。

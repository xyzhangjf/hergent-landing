## 0. 一页结论

**判断：不换底座，只抄骨架。** 你 2026-10-06 已拍板「自研进销存、先 boss 自用跑顺再卖」，ERPNext 在这里的价值不是替代品，而是一份**已经被十几万个部署验证过的进销存设计答案**。它最值钱的不是界面，是五条「让账不会错」的结构性纪律。

### 🔴 最该学的 5 件（按优先级）

| 序 | 借鉴什么 | 一句话理由 | 成本 |
|:--:|---|---|:--:|
| 1 | **追加式库存流水 + 商品×仓库快照 + 事务内重算** | 直接对准「库存/往来账对不平」这个卖前第一关 | 中 |
| 2 | **统一状态机**（草稿／已提交／已取消）＋提交后字段锁定＋禁止删除已提交单 | 现在 7 张单据各写一套状态，还出现写入值超出约束白名单 | 低 |
| 3 | **结构化改动留痕**（谁／何时／哪个字段／旧值→新值） | 经销商最敏感的是「谁改了价格、谁改了数量」，现在是派生视图拼出来的 | 低 |
| 4 | **声明式字段配置驱动表单与列表** | 现在 5 个单文件超过 10 万字节，加一种单据要重写前后端 | 中高 |
| 5 | **事件钩子注册表**（不改核心代码即可定制） | 你自己的 `hergent_erp` Frappe 应用已经用 5 行配置证明这条路走得通 | 低 |

### ⛔ 明确不学的 5 件

多站点独立数据库、MariaDB/Postgres 双方言、Redis + 任务队列 + 多进程、库存重算的断点续跑／实时进度、序列号与批次独立估值。**理由一致**：这些是为「几十万条流水、多公司多币种、多租户 SaaS」设计的；单仓 SQLite 里引入它们，运维成本会失控，而你的三条红线里第一条就是运维成本不可失控。

### 一句话战略判断

> **进销存是交易系统，出错代价是真金白银。先把「账可信」做扎实，再谈 UI 效率；不要反过来。** 你护城河仍是「一线经销商的懂行 + AI 经营副驾」，元数据／状态机／流水这些是桌子腿，不是护城河本身。

## 3. 🔴 先止血：四个「账可信」问题

> ⚠️ **本节写于阶段 0 核实之前，其中问题 1/2/3/4 的事实判断已被线上实测修正。请先看文首「阶段 0 核实后修订」表，再读本节；修法方向仍有效，但风险理由与工作量已变。**
> 仍完全成立的只有一句：**这四条排在 UI 之前**。理由：你定的「卖前三关」第一关是「boss 连续自用 3 个月零事故（库存／往来账对平）」，下面任何一条不修，这一关都不可能过。

### 问题 1｜台账、流水、余额可能静默脱钩

- **证据**：A `erp_db.py:2225/2231` 有 `inventory` 与 `inventory_logs` 两张表；A 回拉范围内 `INSERT INTO inventory_logs` **0 处**，`UPDATE inventory SET` 有 **6 处**；B `migrations/patches/0012_inventory_balance.py:5-7` 自述「6 个库存写入点各自内联，台账/流水/余额三者可能静默脱钩，v718 差 282,424 元才发现」。
- **风险**：改了数量没记流水，报表与实物库存对不上，且**没有任何自动告警**。
- **动作**：把 6 个写入点收敛成**一个** `write_stock_movement()`，在**同一个 SQLite 事务**内完成「改批次数量 + 追加一条流水 + 更新余额快照」，三者不可能只成其一。B 仓 `db/queries/stock_ledger.py:1-13` 已经把设计写好了，缺的是接上真实数据并部署。
- **验收**：连续跑 N 笔采购／销售／退货／盘点后，自动对账卡三张全绿（余额对台账、流水链自洽、金额对得上），且**故意只改台账不写流水时测试必须变红**。

### 问题 2｜状态机分散，且 DDL 与写入不一致

- **证据**：A `erp_db.py:2229` 的 `sale_orders.status` 白名单不含 `picking`，但 `:5341` 写 `status='picking'`；`:2232` 的 `receivables.status` 白名单不含 `voided`，但 `:3451/:3478` 写 `status='voided'`。三张主单据状态集合互不相同，各自端点自推。
- **风险**：SQLite 的 `CHECK` 会让这些 `UPDATE` 直接抛错；若表已被迁移改过约束，则代码与文档口径分裂，排查成本极高。
- **动作**：先做一次**只读实测**（连生产库看这几张表的实际 DDL，确认约束是否已被迁移修改），再引入统一的 `docstatus`（0 草稿／1 已提交／2 已取消），业务状态另用独立字段表达；所有状态跃迁走一张白名单表，禁止端点裸写 `SET status`。
- **验收**：一条非法跃迁（草稿→已完成、已取消→已提交）被统一拦截并给出中文原因；现有 7 种单据全部走同一套判据。

### 问题 3｜没有结构化改动留痕

- **证据**：B `routers/psi.py:1777-1784` 的「查看日志」是拼出来的派生视图，注释明确「取不到操作人的事件显示 —，不许拿创建人顶替」。A 里 `inventory_logs` 建了表却查不到写入。
- **风险**：价格、数量、客户被改过以后无法回答「谁改的、改前是多少」；卖给别的经销商时这是信任问题，不是体验问题。
- **动作**：加一张 `doc_versions`（单据类型、单据号、操作人、时间、JSON 格式的字段差异），在统一保存钩子里自动写；前端详情页底部做一条时间线。
- **验收**：改一次采购单价，时间线显示「张三 将 单价 由 12.00 改为 11.50 · 11 月 6 日 10 时 18 分」这类**全中文**记录。

### 问题 4｜生产与 git 双轨，后端零版本管理

- **证据**：`deploy.sh:17` 直接 `rsync --delete` 推生产；git 提交 `7d88503` 写「让 git 追上生产」；前端 `main.js:66-71` 的构建号需每次手动改。
- **风险**：出事时无法回答「线上到底跑的是哪份代码」，回滚靠人肉备份。这次调研里「线上是否写了流水」无法定论，根源就在这。
- **动作**：生产后端纳管（或至少每次发布前做一次完整回拉 + 入库）；前端构建号改成构建时注入；发布前后各留一份可核对的清单。
- **验收**：任取一个线上端点，能在 git 里定位到唯一提交；回滚有明确步骤。

> ⚠️ 部署口径别混：`deploy.sh` 的 `--delete` 是**后端整树同步**，与前端「闭包补传 + 单传 index.html、绝不 --delete」是两条不同规则。不要因为看到后端用了 `--delete` 就放宽前端纪律。

> B6 的「批量逐单回报」你其实已经做了（`InvPurchaseList.vue:187-202` 的批量结果区），属于**已经对齐**，不必重做。

### C 级 · 只取思想

打印模板数据化、类覆盖改为策略类注册表、时间线只混排「改动 + 评论」两类、元数据只在开发期迁移一次。

### D 级 · 明确不抄

| 不抄 | 理由 |
|---|---|
| 多站点 + 每站点独立 MariaDB 库 | 你已是 `tenant_N.db` 物理分库，隔离强度够，不必引入 site 抽象 |
| 双数据库方言 + `multisql` 分支 | SQLite 单方言即可 |
| Redis + 任务队列 + 多进程 + 实时进度 | 单仓 SQLite 写入本就串行，重算在同一个事务内同步完成最快最稳 |
| 库存重算断点续跑／分片／gzip 快照／失败重试 | 数据量下事务内顺序重算只要几十毫秒 |
| 序列号、LIFO、批次独立估值、自定义库存维度、跨公司调拨 | 快消经销商只需「商品 × 仓库 × 批次 × 效期」+ 移动平均 |
| 完整打印体系、多语言管线、独立全局搜索表 + 队列同步 | 浏览器打印、中文单语、SQLite FTS5 触发器即可 |

> 一个有意思的旁证：Frappe 自己就用 **SQLite FTS** 做全局搜索（`frappe/hooks.py:158` 挂 `frappe.search.sqlite_search.update_doc_index`）。所以「业务库一套、搜索索引用 SQLite」不是妥协，是它也在用的做法。

### 5.2 🔴 不能照抄（面向不懂英文的业务人）

1. **术语一个都不能进界面**：`DocType`、`Stock Ledger Entry`、`Bin`、`Amend`、`Repost`、`Permlevel`、`Indicator` 这些是开发者词汇。界面上必须是「单据类型」「库存流水」「当前库存」「作废重开」「重新核算」「字段权限」「状态标签」。这是你定的硬规矩，对标时最容易破防。
2. **Desk 的信息密度不适合**：ERPNext 一屏塞几十个字段、多级页签、折叠分组，是给受过培训的 ERP 操作员用的；你的用户是一线经销商和业务员，应按「高频字段在前、低频折叠」重排，而不是照搬字段顺序。
3. **数字单位必须中文**：禁止 `pp` / `mo` / `avg` / `QoQ` / `Δ`；`70 个百分点` 而不是 `70pp`，`日均` 而不是 `avg`。百分比、人民币符号、公斤这类有行业共识的可用。
4. **状态色要符合中文习惯**：涉及金额涨跌时涨用红、跌用绿；单据状态色则沿用现有设计令牌，别引入 ERPNext 那套蓝绿语义。
5. **别把「提交」做成不可逆的心理负担**：Frappe 的「已提交不可删」对财务是对的，但要在界面上把「作废重开」路径讲清楚，否则业务员会不敢点。

### 5.3 你已有的优势，别推倒重来

设计令牌（`variables.css`，浅/深双主题）、44 个自研组件、`psi-list.css` 三页共用、骨架屏／空态／错误边界、粘帖结果类 Excel 表格常驻展示——这些**比 ERPNext 的 Desk 更贴合你的用户**。本轮要做的是「在现有设计体系里补结构化能力」，不是换一套 UI 语言。

## 6. 分阶段开发计划

### 6.1 排序判据（先讲清楚为什么这么排）

1. **服务于「卖前三关」**：① boss 连续自用 3 个月零事故（库存／往来账对平）② 跑通 N 笔真实交易（采购／销售／退货／盘点全覆盖）③ 数据隔离验证。前两关都是数据可信度，不是 UI。
2. **运维成本红线**：任何阶段都不得引入 Redis、任务队列、多进程、第二套数据库。
3. **不迁 ERPNext 底座**：那是 2026-08 已废弃的路线，本计划只借鉴设计。
4. **solo + AI 的现实产能**：下面工期按「一人加 AI、且要同时处理日常报单业务」估算，**不含真实业务验收时间**；宁可少排，不要排满。

|---|---|---|---|---|

| **阶段 4 · 卖前三关验收**<br>观察期 3 个月 | 判断能不能卖 | ① boss 连续自用，每周一次自动对账报告；② 真实交易全覆盖（采购／销售／退货／盘点／调拨），逐笔留痕；③ 用另一租户账号验证「确实看不到 boss 数据」；④ 把这三关的证据整理成可给客户看的材料 | 三个月零库存／往来账事故；交易类型全覆盖且有单据可查；隔离验证有截图与测试记录 | **验收不过就不对外销售**，不提前做多租户营销页 |

### 6.3 阶段间的硬闸门

- **阶段 1 不过，不进阶段 2**：元数据驱动会让写入路径变多，在台账还没收敛时做，等于把不一致性放大。

- **阶段 4 不是开发阶段，是观察阶段**，不能压缩。

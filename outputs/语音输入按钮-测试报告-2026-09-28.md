# 语音输入按钮 测试报告（2026-09-28）

> 被测：副驾输入框里的麦克风按钮（`CopilotDrawer.vue` 的 `.cp-voice` → `composables/useVoiceInput.js`）
> 环境：**用户本机**（macOS）+ 本机已装 **Chrome 154** + 生产页 `https://hergent.cn`（演示账号，零写入）
> 复现：`NODE_PATH=<repo>/node_modules node /tmp/voice-probe.cjs`

---

## 一、结论（先给答案）

| 问题 | 结论 |
|---|---|
| 点按钮**能激活**语音输入吗？ | ✅ **能**。按钮进入高亮态、确实调用了识别器的 `start()` |
| 识别结果**能显示**到输入框吗？ | ✅ **能**。中间结果即时写入输入框、后续结果覆盖更新 |
| 真实说话**能被识别**吗？ | ❌ **在当前网络/配置下不能**。见 §3（不是按钮的错，是链路的错） |
| 失败时**界面会告诉用户吗**？ | ❌ **完全不会**（按钮只是亮一下又灭）—— 这是**本轮发现的真缺陷** |

一句话：**按钮和显示都正常，但"真识别"这条路在这台机器上走不通，而且它坏了不吭声。**

---

## 二、怎么测的（三段式，各自的证明力不同）

| 段 | 手法 | 能证明什么 / 不能证明什么 |
|---|---|---|
| **A 应用侧链路** | 把 `SpeechRecognition` 换成**可控替身**，注入模拟结果 | 能证明「点按→start→结果→写进输入框→再点→stop」这条链**通**；**不能**证明真实识别可用 |
| **B 真实识别** | 给真识别器包一层**透明子类**（真实现照跑，只旁听事件） | 能拿到浏览器给出的**真实事件序列与错误码** |
| **C 降级路径** | 删掉两个语音 API 再用 | 能证明「不支持的浏览器」有没有提示 |

## 三、实测读数

### A 段：应用侧链路 **8/8 通过**
```
PASS A1 语音按钮存在且可点（aria-label=语音输入）
PASS A2 点击后真的调了识别器 start()        {"started":1}
PASS A3 按钮进入激活态 .cp-voice.on
PASS A4 收到中间结果 → 立即显示在输入框      "库存"
PASS A5 结果更新 → 输入框内容随之刷新        "库存还有多少"
PASS A6 再点一次 → 调 stop() 并退出激活态    stopped=1
PASS A 段无 JS 异常
PASS A7 识别失败时按钮已退出激活态
FAIL A8 ⚠️ 识别失败**是否有提示** —— 界面完全没有任何提示（静默熄灭）   ← 缺陷
```
证据截图：按钮高亮 + 输入框里出现「库存还有多少」（6 字计数）。

### B 段：真实识别 **失败**
```
1.3 节 浏览器层网络探测（在真实 Chrome 里发起的 fetch，各带 5s 超时）
   https://www.google.com/generate_204  → ❌ 超时 5003ms
   https://speech.googleapis.com/       → ❌ 超时 5002ms
1.4 识别器实测（假麦克风，喂 1.7s 中文语音）
   事件序列: ["start","end"]   错误码: ["audio-capture"]   识别文本: []
   输入框最终值: ""
1.5 Chrome 能力面（Chrome 154 的新 API）
   available({langs:['zh-CN'], processLocally:false}) → "available"     ← 云端；Chrome 报"可用"但**不检查网络**
   available({langs:['zh-CN'], processLocally:true})  → "downloadable"  ← 设备端模型**可下载**
```
- `audio-capture` = 识别器**没拿到音频输入**。自动化环境的假麦克风 `getUserMedia` 是通的
  （设备名 `Fake Default Audio Input`），但语音识别走的是**另一条特权采集通道**，不认假设备
  ⇒ 这一步是**测试环境的限制**，不能据此判定用户的真麦克风不行。
- 但「**连不上语音服务**」这条是**独立证明**的（浏览器层两次 fetch 全部 5s 超时），
  且 `useVoiceInput.js` **没有**设置 `processLocally` ⇒ **走的就是云端那条路** ⇒ 必然失败。

### C 段：不支持的浏览器 **有提示**
```
PASS C1 无语音能力时给出可读提示：当前浏览器不支持语音输入，请用 Chrome 浏览器
```
⇒ 作者**是考虑过降级**的，只是**漏了"运行时错误"这一类**。

## 四、缺陷与可修点（按性价比排序）

| # | 位置 | 现象 | 修法 |
|---|---|---|---|
| **1** ⭐ | `useVoiceInput.js` 的 `r.onerror = () => { recognizing.value = false }` | **吞掉所有真实错误**：麦克风被拒 / 网络不通 / 没听到声音，用户看到的都只是"按钮亮一下又灭"，**无从判断是坏了还是自己没说话** | 按 `e.error` 给**能行动**的中文提示（`not-allowed`→请允许麦克风权限；`network`→当前网络无法连接语音服务，建议改用键盘输入或换网络；`no-speech`→没听清，请再说一次；`audio-capture`→没找到麦克风） |
| **2** | 同上 | 未请求**设备端识别**：Chrome 154 的中文设备端模型是 `downloadable`，代码没设 `processLocally` ⇒ 一律走需要 Google 的云端 | `if ('processLocally' in r) r.processLocally = true`（配合引导安装模型）。**注意**：模型下载可能同样受网络限制，需实测 |
| **3** | `r.start()` 未被 try/catch 包裹，且在 `recognizing = true` 之前调用 | `start()` 同步抛错（如 `InvalidStateError`）时：状态没置起、异常直接冒到点击处理里 | `try { r.start(); recognizing.value = true } catch (e) { onError(...) }` |
| **4** | 模板：按钮无 `v-if="speechOk"` | 在 Firefox/Safari 上照样显示一个麦克风按钮，点了才报"不支持" | 不支持时要么隐藏、要么置灰并给 tooltip |

**根因一句话**：语音输入是**唯一一个"功能在浏览器侧、而它在你们目标网络下大概率走不通"的控件**。当前实现把"能不能用"完全交给了运气（浏览器 + 网络），且**失败时零反馈** —— 属于本项目最忌讳的「静默失效」。

## 五、给决策的三个选项

| 选项 | 做什么 | 成本 | 效果 |
|---|---|---|---|
| **A**（推荐，最小） | 只做上面 **#1 + #3**：把错误变成可读提示 + 包住 start() | 极小（改 1 个 composable，~20 行） | 用户**立刻知道**"为什么没反应"；不再误导。**不改可行性** |
| **B**（A + 试设备端） | A 再加 **#2**：切 `processLocally`，并**实测模型能否下载**（下载不到就回落到"提示网络不通"） | 小（同文件多几行）+ 一次实测 | 网络受限时**有概率真的可用**（离线识别） |
| **C**（彻底） | 不用浏览器语音，改后端/端侧 ASR（国内可用服务或 WASM Whisper） | 大（含成本与合规） | 去掉对 Google 的依赖，但也引入新依赖与费用 |

> ⚠️ 与"能不能用"无关但值得知道：**Chrome 报告 zh-CN 云端识别 `available`，但它不检查实际连通性** ——
> 所以「浏览器说支持」**不能**当作「能用」的判据（与本项目"接口 200 ≠ 数据正常"同族）。

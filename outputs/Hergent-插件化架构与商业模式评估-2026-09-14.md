# Hergent「一切皆插件」可行性 · 成本 · 商业模式评估

**评估日期**：2026-09-14　**评估对象**：hergent.cn（AI 经营副驾）+ hergent-erp 后端 + Hermes 引擎
**评估方式**：生产环境实测 + 源码核查 + 公开市场数据（非推演）

---

## 摘要：五问结论

| # | 问题 | 结论 | 信心 |
|---|---|---|---|
| 一 | 侧栏可否「基础功能锁定 + 用户自写插件」 | **可做，但必须把"插件"拆成四层**。L0 基础功能（锁）已经天然成立；L1 配方插件已上线；L2 能力插件（Hermes Skill）**地基已备但前端是只读的**；L3 界面插件（用户在自己侧栏加新页面）**风险远大于收益，建议不做** | 高 |
| 二 | 技术可行性 / 复杂度 / 风险 | 可行性 **L1 高 · L2 中高 · L3 低**。最大风险不是技术，是**安全与支持**：Agent 插件生态 2026 年已被大规模武器化（实测数据见 §2.3） | 高 |
| 三 | 成本会增加多少 | 服务器增量**很小**（约 15~50 元/租户/月）；**LLM 是更大的一项**（约 15~30 元/租户/月）；真正的成本杀手是**人工支持**，插件化的商业价值恰恰在于压这一项 | 中高 |
| 四 | 商业模式 | **不做插件市场抽成**，走「基础订阅 + 官方能力包 + 定制交付」三档。定价下限 **2000 元/年**，低于此无毛利空间 | 中高 |
| 五 | 聚焦低温奶还是扩快消 | **先聚焦低温奶**，但把「配方命名空间 + 技能包目录约定」预埋成多行业可扩展结构。**横扩的时机是机制成熟，不是功能齐全** | 高 |

**同时发现一个必须先修的既有缺陷**：租户 Hermes 的行业技能在租户创建那一刻后被冻结，用户在 Web 端改配方**传不到租户的 AI**（详见 §0.3）。这是"用户按需定制"方案的地基，不修则 L2 无从谈起。

| 层 | 现状 | 关键文件 / 位置 |
|---|---|---|
| 侧栏 | **完全硬编码**：15 个 `<router-link>` + 移动端抽屉，逐个手写 | `hergent-cn-v2/src/components/Shell.vue` |
| 前端路由 | **静态表**，构建期固定，无运行时加载能力；依赖只有 vue / vue-router / pinia / xlsx | `src/router/index.js`、`vite.config.js` |
| 配方（用户可调参数） | **已上线**：货损阈值、工资口径、预报口径可 Web 端改并存库 | `routers/loss_workflow.py`、`payroll_workflow.py`、`forecast_config.py` |

| 配方版本与审批 | **已上线**：导出/导入/版本快照/回滚 + "AI 提案 → 老板审批 → 合并" | `routers/recipe_io.py`、`recipe_evolution.py` |
| 技能列表 | **只读代理**，前端只能看不能写 | `routers/ai_skills.py`（仅一个 `GET`） |
| 多租户 Hermes | **已上线**：每租户独立 HOME + 独立网关进程 | `hermes_tenants.py` |
| 能力中心 / 技能页 | **已有 UI 壳**：技能 tab、预置/自进化分组、机器名→业务名的解释映射 | `src/pages/ConnectCenter.vue:221-272` |

**Hermes 侧（`/usr/local/lib/hermes-agent`）已内置一整套插件基础设施**——这是本次评估最重要的发现：

| 模块 | 能力 | 对 Hergent 的意义 |
|---|---|---|
| `skills_hub.py` | 技能注册中心适配器：GitHub 源、官方源、来源追踪锁、**隔离区（quarantine）**、审计日志、索引缓存 | 插件分发与溯源不用自造 |
| `skills_guard.py` | **外部技能安全扫描器**：正则静态分析检测数据外泄 / 提示注入 / 破坏性命令 / 持久化；**信任分级**（builtin 永不扫描 / trusted 仅官方两源 / community 有任一发现即拦截） | 插件准入闸门不用自造 |
| `skill_manager_tool.py` | Agent 自主 create / edit / patch / delete 技能，写入 `~/.hermes/skills/` | "AI 帮用户造插件"的现成通路 |
| `skills_sync.py` | Manifest 式播种与更新，**能区分"用户改过"与"未改过"**（改过就 SKIP，不覆盖） | 插件升级不丢用户定制 |
| `skill_provenance.py` | 区分"AI 自动沉淀"与"用户要求写的"，用户技能永不被自动清理 | 权属边界已建模 |

**结论：用户想要的"一切皆插件"，在 Hermes 这一层已经有 70% 的实现，缺的是"Hergent 把它接出来 + 加上业务语言的外壳"。**

### 0.3 🔴 必须先修的既有缺陷：租户技能被冻结

**现象**：`recipe_sync.py` 写的是 `/root/.hermes/skills/`；租户网关跑在自己的 HOME（`/opt/hermes-tenants/hergent_t1/`），读的是自己那份。

**证据链**：

1. `recipe_sync.py:34` → `DEFAULT_SKILLS_DIR = "/root/.hermes/skills"`
2. `recipe_sync.py:263-275` → `trigger_sync_from_service()` 以 sudo 身份跑，用**默认目录**，不带租户参数
3. 调用点共 5 处（`loss_workflow.py:213`、`payroll_workflow.py:172`、`forecast_config.py:87`、`recipe_io.py:246,311`、`recipe_evolution.py:256`）——**全部不传 `--tenant-id`**
4. `hermes_tenants.py:226-235` → 租户 home 的 skills **只在目录不存在时**从 `_seed` 拷贝一次（`if not dst_skills.exists()`），此后永不更新
5. 生产时间戳印证：`_seed` 与 `hergent_t1` 的 SKILL.md 均为 `2026-09-10 20:56`（同一次播种），`/root/.hermes` 为 `2026-09-07`
6. 全服 crontab 中**没有任何**把 `/root/.hermes/skills` 重新同步到 `_seed` 或租户 home 的任务（实测 root crontab 仅 3 条）

**影响**：用户今天在「货损计算」里把临期阈值从 7 天改成 5 天，Web 端算式立刻按 5 天走，但**租户的 AI 副驾仍然按 7 天回答**——"后端算的"与"AI 说的"分叉。这正是 `recipe_sync.py` 模块注释里写明要消灭的问题，只是当时只考虑了单租户（全局 HOME）场景。

**为何先修这个**：L2「用户自定义能力插件」的本质就是"用户配置 → 写进租户自己的 skill"。连 4 个内置 skill 的同步链路都不通，加再多插件功能也只是放大这个断层。**修法很小**（见 §6 P0），但它是整个方案的地基。

## 一、产品形态：能不能「基础功能锁定 + 用户加载插件」

### 1.1 先把「插件」这个词拆开

用户口中的"插件"实际混了四种诉求。它们的实现代价差两个数量级，必须分开决策：

| 层 | 用户诉求 | 用户能改什么 | 现状 | 代价 |
|---|---|---|---|---|
| **L0 基础功能** | 「这些别动」 | 不能改，只有权限开关 | ✅ 已成立（15 个入口硬编码） | — |
| **L1 配方插件** | 「我的临期阈值是 5 天，不是 7 天」 | 参数、口径、阈值、字段映射 | ✅ 已上线（4 个域） | 低 |
| **L2 能力插件** | 「我要一个"每周一自动算上周毛利并发企微"的能力」 | 一段提示词 + 可选脚本，不产生新页面 | ⚠️ 后端地基已备，**前端只读** | 中 |
| **L3 界面插件** | 「我要在我侧栏加一个"车辆调度"页面」 | 完整前端页面（Vue 组件） | ❌ 完全空白 | 高 |

**建议路线：把 L1 做深、把 L2 做通、把 L3 明确不做（或只做官方白名单）。**

### 1.2 L0：基础功能锁定——已经天然成立，只需显式化

现状侧栏 15 个入口全部硬编码在 `Shell.vue`，用户改不了——这**已经是**用户想要的状态。要做的是把它"显式化"，让用户看得出边界：

- 侧栏分区：**「经营」（锁定）** / **「我的能力」（用户可增删）** 两个分组，视觉上区分。
- 锁定区每个入口标注"系统功能"，用户能隐藏（自己不看）但**不能删除**（避免他删了之后找不回来，反手变成你的支持工单）。
- 关键设计原则：**"锁定"不等于"不可配置"**。基础功能锁定的是"入口与流程"，开放的是"流程里的参数"（那正是 L1）。

### 1.3 L1：配方插件——已上线，建议扩面

这是**当前最被低估的资产**。它已经具备：

- 用户可改参数（阈值、计价口径、工资项、预报窗口…）
- 存库 + 版本快照 + 一键回滚
- 「AI 提案 → 老板审批 → 合并」的治理流（`recipe_evolution.py`）
- 自动渲染进 skill，让"AI 说法"与"后端算法"同源（`recipe_sync.py`）

**建议动作**：把 L1 从 4 个内置域**扩成"用户可注册的域"**——用户说"我还有个'车辆油耗'要按我的算法算"，系统给他一个空白配方槽位，而不是等你们开发。这是"一切皆插件"里**性价比最高的一步**：不需沙箱、不需前端加载、不需审核代码，因为它只填数字。

### 1.4 L2：能力插件——地基已备，前端要接

**形态**：用户（或 AI 代用户）写一段 `SKILL.md`——一段自然语言的"何时触发、做什么、按什么口径"。它不给用户新页面，而是让**已有的副驾多会一件事**。

**为什么这是正确的重心**：用户的真实痛点 90% 是「AI 不懂我的业务」，而不是「界面少了个按钮」。一段 SKILL.md 能解决的，往往比一个新页面更有价值。

**现状缺口**：

| 需要 | Hermes 有 | Hergent 有 | 缺什么 |
|---|---|---|---|
| 写技能 | `skill_manager_tool` ✅ | ❌ | 前端入口 + 权限 |
| 存技能（按租户隔离） | 每租户 HOME ✅ | ✅ | — |
| 安全扫描 | `skills_guard` ✅ | ❌ | 接出来 |
| 来源追踪 | `skill_provenance` + `HubLockFile` ✅ | ❌ | 展示 |
| 升级不丢定制 | `skills_sync` manifest ✅ | ❌ | 接出来 |
| 看技能列表 | — | ✅ 只读 | 加上写 |

**要新增的后端端点（约 5 个）**：列表（已有）、创建/编辑、启停、删除、扫描报告。**全部走租户 HOME，不碰全局目录。**

**安全设计（照抄 Hermes 已有的信任分级，不要自创）**：

| 来源 | 策略 |
|---|---|
| builtin（平台预置 4 个行业包） | 永不扫描，永远可信 |
| verified（平台审核过的能力包，随版本分发） | 自动扫描 + 人工看过，用户可一键启用 |
| user（本租户内 AI 代写 / 用户手写） | 自动扫描 + **仅本租户可见**，绝不跨租户分发 |

**关键取舍：不做跨租户的"社区插件市场"。** 理由见 §2.3——2026 年的实测数据说明这个生态的恶意比例高到不该由一家小公司承担审核责任。

### 1.5 L3：界面插件——建议不做

**技术上可行路径**（按风险从低到高）：

| 方案 | 隔离性 | 能力 | 判定 |
|---|---|---|---|
| 用户提交配置，**平台审核后编译进产物** | 最好 | 全 | 这是"定制开发"，不是插件 |
| iframe 沙箱 + postMessage 通信 | 好 | 受限（拿不到宿主状态，需设计 API 桥） | **可行，但只能承载"独立展示型"页面**（如一张自定义报表） |
| 运行时 `import()` 远程 JS 包 | **无**（同源同上下文，可读 token、可发请求） | 全 | **否决** |
| 浏览器内编译 Vue SFC | 无 | 全 | **否决**（且引入 30 万行编译器到产物） |

**建议**：L3 只做一种受控形态——**「自定义看板」**：用户用配置（选指标、选维度、选图表类型）拼出一个页面，挂到「我的能力」分组下。这是 L1 的延伸（配置驱动），而不是代码插件。它能覆盖 L3 诉求里最常见的那一类（"我想在侧栏看到我关心的那个数"），且零安全风险。

真需要完整新页面时，**走"平台开发 + 配置化开关"**，即：功能是你们写的，用户只是开启它。这也符合"基础功能锁定"的整体基调。

## 二、技术可行性 · 架构复杂度 · 风险

### 2.1 可行性打分

| 层 | 技术可行性 | 主要不确定性 | 工作量级 |
|---|---|---|---|
| L0 锁定 + 分组 | **确定可做** | 无 | 小（前端 1~2 天） |
| L1 扩面（用户自定义配方域） | **确定可做** | 配方 schema 的通用化 | 中（后端 1~2 周） |
| L2 能力插件（写/扫/启停/隔离） | **高**（Hermes 已有 5 个模块） | 租户技能同步链路（§0.3） | 中（2~3 周） |
| L3 自定义看板（配置式） | **可做** | 指标/维度元数据要暴露 | 中（2~3 周） |
| L3 真·界面插件（代码式） | **技术上可行，工程上不建议** | 沙箱、审核、版本兼容、支持成本 | 大（2~3 月且长期负债） |

### 2.2 架构复杂度：三个必须解决的硬问题

**问题一：技能的双源/多源漂移（§0.3）**

`/root/.hermes/skills`、`_seed`、`/opt/hermes-tenants/<t>/skills` 三处同名文件，目前内容一致纯属"配方恰好没改过"。任何一次配方保存都会让它们分叉。

**修法**：确立"**租户 HOME 是唯一权威，其余都是种子**"，并把同步改成**幂等下发 + 校验**：
- `recipe_sync` 接受 `--tenant-id`，或遍历所有租户 HOME；
- 内置 skill 的更新走 `skills_sync` 的 manifest 逻辑（用户改过就跳过，不覆盖）；
- 加一个"技能一致性"检查（源文件 hash vs 各租户实际 hash），不一致就告警。

**问题二：进程模型的成本线性**

每租户一个常驻网关（255~342 MB）。这是**当前架构最大的成本放大项**：

| 租户数 | 常驻模型内存 | 按需启停后 | 判定 |
|---|---|---|---|
| 2 | ~0.7 GB | — | 现机够用 |
| 10 | ~3.6 GB | ~1.2 GB | 常驻需升 4C8G |
| 30 | ~9.6 GB | ~2.0 GB | 常驻需 8C16G |
| 100 | **~30 GB（单机不可行）** | ~4 GB | 必须优化 |

**修法：空闲回收（lazy start + idle shutdown）**。当前 `ensure_running()` 由 scheduler 保活，是为了企微/飞书通道的常驻连接。要区分两类负载：

| 负载 | 特性 | 策略 |
|---|---|---|
| IM 通道（企微/飞书机器人） | 需要常驻长连接 | 保留常驻，但只有**开通了通道的租户**才起 |
| Web 副驾对话 | 请求-响应，天然可启停 | **按需启动 + 空闲 10 分钟回收** |

这一条能把 100 租户的内存需求从 30 GB 压到 4 GB 量级——**是成本优化里最大的一根杠杆，且不需要改 Hermes**。

**问题三：多租户隔离的边界**

现有隔离是"一个 HOME 一个进程"，**隔离性强但成本高**。要警惕的是"为了省内存改成共享进程"——那会引入跨租户上下文泄漏（记忆、技能、对话历史混在一起），对一个卖给同行的 B 端产品来说，**一次泄漏 = 口碑归零**。

**结论：隔离性不换成本。成本从"空闲回收"和"水平扩展"里找，不从"合并进程"里找。**

### 2.3 风险清单（按严重度排序）

**风险一：插件即远程代码执行 —— 这不是理论，是 2026 年的实况**

Agent 插件生态在 2026 年已被大规模武器化，公开实测数据：

| 事件 | 规模 |
|---|---|
| ClawHavoc 攻击（恶意 skill） | 影响 **42,900** 个实例、**82** 个国家 |
| ClawHub 市场恶意 skill | Antiy CERT 确认 **1,184** 个在流通；另有分析称该市场约 **20%** 技能为恶意 |
| 暴露公网的 MCP server | Trend Micro 发现 **492** 个零认证可访问 |
| VS Code 扩展投毒 | 2025 年恶意扩展检测量翻两番；仿冒 Prettier 扩展存活约 4 小时后被下架 |
| 协议层漏洞 | MCP 参考实现缺陷衍生一串 CVE（MCP Inspector / LibreChat / Cursor 等） |

**官方文档的定性**（Anthropic 对 Claude Code 的明确表述）：**已安装的插件与 MCP server 以用户的完整权限运行，没有按插件的沙箱，插件之间也没有运行时隔离。** 生态里唯一的信任边界就是"人点了安装"。

**对 Hergent 的含义**：
- 用户是**非技术经销商老板**。他没有能力审阅一段 skill 是否安全。把"安装插件"这个动作交给他，等于把风险转嫁给最没能力承担的人。
- 你的产品里装着**他的客户名单、进货价、返利率、员工工资**——这是全套经营数据。一次数据外泄，赔不起。
- **因此：不开放任意第三方上传，不建社区市场。** 只做"平台审核过的能力包"，辅以 Hermes 已有的 `skills_guard` 作为第二道闸门。

**风险二：提示注入与记忆投毒**

技能/工具返回的内容会被模型当作可信输入。一次注入可以：读走数据（通过允许的出站请求）、改写行为（工具描述被投毒）、或**污染长期记忆**（写入即持久，工具断开也仍在影响后续所有决策）。

Hergent 已有长期画像与记忆沉淀机制，**记忆投毒在这里的破坏力更大**。缓解措施：工具输出一律当不可信数据处理、记忆写入要带来源与时间戳、关键业务动作保留人工确认。

**风险三：稳定性 —— 用户插件搞崩的是他的生意**

用户自己写的 skill 若有语法/逻辑错误，可能导致：副驾答错口径 → 用户按错的口径下单/算工资。这不是"功能坏了"，是**真金白银的错误**。

缓解：写入前**强制 dry-run 演示**（用他上个月的真实数据跑一遍，把结果给他看）、高危 skill（涉及金额/工资/报单）打上"需老板二次确认"标记、每次改动进版本快照可一键回滚（`recipe_io.py` 已有这套，扩展即可）。

**风险四：支持成本无上限**

这是对 solo 非技术创始人最真实的风险。用户自己配错了，他一定会来找你，而且他描述不清"我配错了什么"。

**缓解**：插件配置必须有"恢复默认"按钮（一键）；有"我配了什么"的可读摘要（给非技术人看的中文清单）；有"AI 帮你检查配置"的一句话诊断。**这一项的投入产出比高于任何功能。**

**风险五：AI 成本失控**

用户写出一个"每小时自动分析一次"的技能 → LLM 调用量暴涨。必须有：配额上限（`ai_credit` 体系已有雏形）、单技能执行频率限制、异常调用告警。

**风险六：合规**

- 用户数据不得转售（既有红线），插件若允许出站请求，须**白名单域名**并记录审计日志。
- 生态里已有"技能描述字段藏指令"的投毒手法（静态代码审查看不出来）——所以**审核必须看描述文本，不只扫代码**。

### 2.4 前提澄清：「仅限自己使用、不进场」能解决多少

> **澄清（2026-09-14）**：用户明确「一切皆插件」的含义是 —— **每个租户自己写、自己用、本地加载，不允许对外分发与共享**，不是插件市场。本节据此重新界定 §2.3 的结论。

**总判断：它能消除风险链条四段中的一段（分发传递），但那不是最重的一段。**

| 风险链条 | 环节含义 | 「仅限自用」的效果 |
|---|---|---|
| ① 代码来源 | 谁写的 | **残留**：作者是 LLM，用户既读不懂也判断不了；连"第三方用过"的间接信号都没有 |
| ② 分发传递 | 陌生人的代码怎么进来 | **已消除** ✅ 这是真正被解决的一段，也是 2026 年最常被引用的那一类 |
| ③ 执行边界 | 它能碰到什么 | **残留 · 最重**：见 H4 |
| ④ 数据输入 | 谁在指使它 | **残留**：与插件来源完全无关，见 H2 |

**它真正解决的（有依据）**

1. **第三方投毒——归零**。§2.3 风险一的全部实测数据（42,900 实例 / 1,184 个恶意技能 / 492 个零认证 MCP）都建立在"陌生人的代码进入你的执行环境"之上；不进场，这条路径不存在。
2. **供应链传递与信任继承**。市场模式下 A 装的时候你审的是 A，但 A 依赖的 B 更新后你会静默继承新权限。无分发即无传递链。
3. **审核成本转嫁**。市场模式下你**必须**审核（否则承担平台责任），这是持续人力成本；自用模式下审核责任回到用户本人。
4. **数据转售红线的纠纷面**。若插件作者把数据带到自己的服务上，平台存在连带风险；不进场直接消除这类纠纷。

**它仍然解决不了的（本节重点）**

**H1 · 「自己写」在你的用户群 ≈ 「让 AI 写」，作者不是评审者。**
用户是非技术经销商老板，写不了代码，因此"自己编写"实操上等价于「描述需求 → AI 生成 SKILL.md」。于是**产出者与审阅者是同一个人，且这个人是唯一没有能力审阅的人**。市场模式至少还有"别人用过没出事"这个间接信号，自用模式连它也没有。
→ **这替换了风险的来源，没有降低风险的总量。**

**H2 · 混淆代理（confused deputy）：真正危险的入口是「数据」，不是「插件」。**
插件可以完全无害，但它是**读数据的**；数据里可以携带指令。Hergent 的外部数据入口很多：Excel 上传、企业微信里的客户消息、舟谱导出的报表、邮件。插件只是把这个能力**正当化**了。
→ 判据：**只要 AI 会读外部内容 + 会执行命令，这条路径就存在，与插件从哪来无关。**「不进场」对它完全无效。

**H3 · 「不对外分发」在技术上不可执行 → 政策必然溃散（最需注意的一条）。**
插件在 Hergent 里是**纯文本**（SKILL.md），纯文本无法阻止复制。而业务动作本身就在分发：既有做法是"先在群里丢样本验证需求"，经销商之间也天然互换模板（产品设计上还要求"全经销商统一模板"）。
→ **结果：「自用插件」会经微信/抖音/网盘变成事实上的市场，但你完全没有市场该有的控制手段（无审核、无版本、无下架）。这在安全性上比开一个受控市场更差。**
→ **政策不是靠约定成立的，是靠机制成立的。"不许分发"这句话，必须有技术或流程去承载，否则它只是愿望。**

**H4 · 隔离边界根本不在这一层（生产实测）。**
详见下图与下表 —— 这是**当前最严重的单点**，且与插件功能无关：即使不开任何插件能力，它今天就已经成立。

| 实测项 | 现状 | 应为 |
|---|---|---|
| 租户网关运行身份 | 全部为同一个 `hergent`（`/etc/passwd` 里只有这一个业务账号） | 每租户独立 OS 用户或容器 |
| 租户网关 `HOME` | **`/opt/hergent-erp`**（后端代码 + 全部数据库所在目录） | 指向该租户自己的 home |
| `~` 解析 | `file_tools.py:48` 用 `expanduser`；`file_operations.py:49` 用 `Path.home()`；`code_execution_tool.py:1914` 提示词明确写 `os.path.expanduser('~/.hermes/.env')` | `~` 必须落在租户 home 内 |
| `*.db` 权限 | `erp.db` / `tenant_1.db` / `tenant_10.db` 均为 **644** | 600 + 属主拆分 |
| 系统级沙箱 | `ProtectHome=no` · `ProtectSystem=no` · `PrivateTmp=no` · 无 docker/podman/bwrap/nsjail | 全部收紧 |
| 另有一个 root 网关 | `hermes-gateway.service` 以 **root** 运行（`HOME=/root`，已长跑约 23 小时） | 应当不存在 |

→ 结论：租户 A 的"自用插件"只要让 AI 执行一条命令，就能读到**租户 B 的 `.env`（企业微信等渠道凭证）**、**主库 `erp.db`**、**全部 `tenant_*.db`**。当前生产只有 1 个真实租户，所以这条路径尚未被激活 —— **第 2 个租户上线那一刻它就会活。**

**H5 · Hermes 的"沙箱"不是安全边界（实测，易误判）。**
它确实有沙箱（`code_execution_tool.py`），但：
- **允许的工具**是 `web_search / web_extract / read_file / write_file / search_files / patch / terminal` —— 里面有 **`terminal`（任意命令）与 `write_file`（任意文件）**；
- 它限制的是**资源与稳定性**（300s 超时、50 次工具调用、stdout 50KB），**不是能碰哪些文件**；
- 租户 `config.yaml` 只有 4 个键（`model` / `max_turns` / `mcp_servers` / `onboarding`），**没有任何沙箱或权限配置**。
→ **不要把"有沙箱"当成"有隔离"。** 这是最容易被外部说法误导的一点。

**H6 · 可用性与支持成本被自用模式放大（商业风险，非技术风险）。**
对非技术用户，最可能的坏结果不是被攻击，而是**把系统搞坏**（删数据、死循环、配错口径导致报表算错）。而这是他自己写的 → 事故归因变成"你的产品坏了"，**支持工时落在你身上**。§3.5 已判定支持成本是这门生意的生死线，自用模式必须为此单独留出预算。

**必要条件（三组，逐条可验收）**

*A 组 —— 让「仅限自己使用」变成技术事实。**这一组不做完，后面的插件功能一律不要开。***

| # | 措施 | 验收判据 |
|---|---|---|
| A1 | 每租户独立 OS 用户或独立容器/命名空间 | 以租户 A 身份 `ls /opt/hermes-tenants/<租户B>` **必须失败** |
| A2 | 租户网关 `HOME` 指向自己的 home（现为 `/opt/hergent-erp`） | AI 执行 `echo $HOME`、`ls ~` 落点在该租户 home 内 |
| A3 | `*.db` 收到 600 且属主按租户拆分；`/opt/hermes-tenants` 保持 700 并按租户再分一层 | 跨租户读 `tenant_*.db` 必须失败 |
| A4 | 给 `hergent-erp.service` 补 systemd 沙箱指令（`ProtectHome` / `ProtectSystem` / `PrivateTmp` / `ReadWritePaths` / `CapabilityBoundingSet`） | `systemctl show` 这些字段不再为空 |
| A5 | 停掉以 **root** 运行的 `hermes-gateway.service` | 该进程不存在；功能无回归 |
| A6 | 技能**出网默认拒绝**（白名单域名） | 未声明域名的技能发起请求必须被拦 |

> A6 是"数据不得转售"这条红线在技术上的对应物 —— **能出网，才谈得上把数据带走**；不能出网，最坏也只是搞坏本地。

*B 组 —— 让「自己写」不等于「自己背锅」*

| # | 措施 | 说明 |
|---|---|---|
| B1 | **把"写插件"从"写代码"改成"填表单"**（即 §1.3 的 L1 配方域） | **最关键的一条**。类型只有 4 种（数字/选项/开关/文本），**不需要执行任何用户代码** → 安全性是结构性成立的（by construction），不依赖审查 |
| B2 | 每个用户可写的技能必须**声明它要碰什么**（读哪些数据、是否出网、是否写文件），由**执行端强制** | 靠提示词请求 AI"自觉"不算强制 |
| B3 | 升级为"官方能力包"必须过你这一关：自用随便，一旦要被其他租户复用**必须审核 + 签名 + 版本化** | 这才是"不建市场但有分发控制"的正确形态 |
| B4 | 受限试跑 + 一键回滚：新技能先在只读副本上跑，异常自动回滚 | `skills_provenance` 已有基础 |

*C 组 —— 成本与流程*

| # | 措施 |
|---|---|
| C1 | 支持工时按**分品项**计入单位经济模型（配方类 vs 插件类分别计），不沿用单一 0.3 工单/租户/月 |
| C2 | 每个自定义插件必须绑定"谁在用它" —— **验收判据：保存后必须能指出它在哪里起了作用**（AI 答得出，或某个页面算出了不同结果）。否则就是空承诺（同报单模版"必填"踩过的坑） |

**结论**

1. **「仅限自己使用」不是安全方案，是安全方案的一条前提。** 它砍掉的是"陌生人的代码"；它砍不掉"无隔离的执行环境"与"可携带指令的数据"。
2. **两者的区别是"政策 vs 能力"**：前者靠约定与人自觉，后者靠机制。**你现在有的是政策，没有机制。**
3. **"自用"降低的是「你信任的人变多了」这个风险；"隔离"降低的是「它能碰到的东西太多了」这个风险。前者是人事问题，后者是技术问题 —— 而自用模式只处理了前者。**
4. **顺序必须是：A 组隔离机制 → B1 配方域（让写插件不写代码）→ 才谈开放自定义域。** 反过来做，等于在没有围墙的院子里发钥匙。
5. 一个反直觉的推论：**A 组做完之后，即使将来开一个小范围的受控分发，风险也不会显著变大**；而 A 组不做，无论分不分发，风险都是同一量级。**决定风险量级的是隔离，不是分发。**

## 三、成本测算

### 3.1 现状锚点

2 vCPU / 3.4 GiB / 40 GB 单机，跑 Web 后端 + 小程序后端 + 2 个 Hermes 网关 + MariaDB + Redis + MCP，**负载 0.00**。所以"再加一个租户要多少钱"可以用**边际量**算：

| 口径 | 每租户增量 |
|---|---|
| 内存（常驻网关） | **约 250~340 MB** |
| 内存（按需启停后，按 20% 同时在线） | **约 50~70 MB** |
| 磁盘（skills + cache + logs） | **约 45 MB** |
| CPU | 空闲时接近 0；对话时短暂占用 |

### 3.2 服务器成本（估算，需以阿里云实时报价为准）

| 规模 | 常驻模型 | 按需启停 | 推荐机型 | 月费区间 | **每租户/月** |
|---|---|---|---|---|---|
| 现在（2 租户） | ~0.7 GB | — | 2C4G（**现有**） | 100~160 元 | 50~80 元 |
| 10 租户 | 3.6 GB ⚠️ | 1.2 GB | 4C8G | 300~500 元 | **30~50 元** |
| 30 租户 | 9.6 GB ❌ | 2.0 GB | 8C16G | 700~1100 元 | **23~37 元** |
| 100 租户 | 30 GB ❌ 单机不可行 | 4.0 GB | 8C16G + 水平扩展 | 1500~2500 元 | **15~25 元** |

> ⚠️ 标记表示常驻模型在该机型上放不下。**这张表的核心结论是：不做空闲回收，成本会随租户数线性上升并在 20 租户左右撞上单机天花板；做了空闲回收，100 租户仍可在一台 8C16G 上跑。**

### 3.3 LLM 成本（DeepSeek 官方价，2026-09）

| 模型 | 输入（缓存命中） | 输入（未命中） | 输出 |
|---|---|---|---|
| deepseek-v4-flash | 0.02 元/百万 token | 1 元/百万 token | 2 元/百万 token |
| deepseek-v4-pro | 0.025 元/百万 token | 3 元/百万 token | 6 元/百万 token |

**单次副驾对话估算**（按 flash、输入 15k / 输出 1k token）：
`0.015 × 1 + 0.001 × 2 ≈ **0.017 元/次**`

| 使用强度 | 单租户/月 LLM 成本 |
|---|---|
| 轻度（10 次/天） | 约 **5 元** |
| 中度（30 次/天） | 约 **15 元** |
| 重度（100 次/天，含定时任务） | 约 **51 元** |

**注意**：技能越多 → 注进上下文的内容越多 → 输入 token 越多。**"一切皆插件"会推高 LLM 成本**，这也是为什么缓存命中价（0.02 元）和"只加载相关技能"很关键。

### 3.4 总成本与定价下限

按中度使用、30 租户档：

| 项目 | 单租户/月 |
|---|---|
| LLM | 15 元 |
| 服务器分摊 | 30 元 |
| 磁盘 / 带宽 / 备份 | 3 元 |
| **小计** | **约 48 元/月 ≈ 580 元/年** |

**关键商业判断**：纯 SaaS 成本已接近 580 元/年。对照市场——管家婆进销存 **698 元/年**、云订货 **3800 元/年**、快马数字 B2B **9800 元/年**（见 §4.2）。

→ **定价 698 元/年 = 毛利几乎为零。定价下限必须 2000 元/年。**

### 3.5 真正的大头：人工支持成本

上面所有服务器+LLM 加起来的钱，**远小于**一次"用户配置出错后的一小时远程排查"。solo 创始人的时间是唯一不可扩容的资源。

| 成本项 | 量级 | 可否优化 |
|---|---|---|
| 服务器 | 15~50 元/租户/月 | ✅ 空闲回收可压 60% |
| LLM | 5~50 元/租户/月 | ✅ 配额 + 缓存 + 按需加载技能 |
| **支持工时** | **无法用钱衡量，最贵** | ✅ **只能靠设计消灭**（见下） |

**必须从这三个方面衡量成本增加：**

1. **边际基础设施成本**（服务器 + 存储 + 带宽）——可预测，小。
2. **边际 AI 成本**（token）——与用户活跃度和技能数量正相关，需配额封顶。
3. **边际支持成本**（工时）——**决定这个生意能不能做**。衡量指标应是"每个客户每月的支持工单数"，而不是"每台服务器的月费"。插件化如果让工单数上升，这个方向就是错的。

**给成本设的验收线（建议）**：
- 每租户月度基础设施 + AI 成本 ≤ **60 元**（对应 2000 元/年定价的 3% 以内）
- 每租户月度支持工单 ≤ **0.3 次**（即 10 个客户每月不超过 3 次求助）

## 四、商业模式

### 4.1 先看别人怎么做定制（可借鉴的成熟范式）

**明道云（低代码平台）** 的插件体系是本次调研里最贴近的参照：

- 用户把常用逻辑**封装成自定义节点**，在组织内发布使用；
- 插件可**导出成文件**，在别的组织导入或升级；
- 导出时可设**授权密钥 + 到期时间 + 指定组织**——即"插件本身就是一件可售商品"；
- 平台侧有**开发者伙伴体系**，通过应用市场实现应用与插件的商业化。

**关键启示**：它没有开放"上传任意代码"，而是"**模板 + 封装 + 授权**"三件套。既给了扩展性，又守住了平台稳定。此外明道云明确的设计原则值得抄：**渐进式**（无代码 → 低代码 → 全代码，用户按需选档）、**隔离性**（用户代码不能搞崩平台）、**可调试**、**可复用**。

### 4.2 市场定价锚点（2026 年公开报价）

| 产品 | 定价 |
|---|---|
| 网上管家婆·进销存 | 698 元/年（1 用户） |
| 网上管家婆·云财务 | 480 元/年 |
| 网上管家婆·网店 ERP | 2380 元/年 |
| 管家婆·云订货 | 3800 元/年 |
| 管家婆·快马数字 B2B 订货 | 9800 元/年 |
| 管家婆增值模块（外勤管理 / 云仓 / 委托销售） | 800 / 1200 / 200 元/年 |
| 辛巴软件 | 1800~18000 元/年 |

**观察**：这个市场愿意为"模块"单独付费（200~1200 元/年），且愿意接受按人数/网点/门店分档计价。

### 4.3 建议的商业模式：三档 + 两条铁律

| 档位 | 定位 | 建议价（元/年） | 内容 |
|---|---|---|---|
| **基础版** | 引流，替代"Excel + 微信群" | **1980~2980** | 基础功能锁定区全部（报单/返利/货损/工资/对账）+ 副驾基础对话 + 3 个内置行业技能 |
| **能力包版** | 主力，卖"你需要的那个能力" | **+800~1500/包** | 官方能力包（到期预警自动化、返利测算、毛利周报…），按需选购 |
| **定制版** | 高客单，一对一 | **8000~20000/年 + 实施费** | 专属配方域、专属能力包、专属看板、接入他的 ERP、优先支持 |

**铁律一：不做插件市场抽成。** 生态规模撑不起审核成本，而审核缺失的代价（§2.3）由你承担。**所有可分发的能力包必须是你自己或你审核过的。**

**铁律二：定制能力是"你出人工"，不是"客户自己写"。** 至少在第一年，L2 能力插件的正确用法是：客户用自然语言描述需求 → **你（或你的 AI 助手）写成 SKILL.md** → 交付给他 → 他只需"启用"。这样你能：控制质量、积累行业 know-how（这正是护城河）、并让每次交付都变成可复用的能力包资产。

**为什么"AI 代写"是关键**：它把"定制"从"技术活"变成"业务活"。客户说需求，Hermes 写技能——这个动作本身就是产品最独特的卖点，也是你相对舟谱/畅捷通的结构性优势（它们的定制必须派实施顾问）。

### 4.4 变现路径的现实排序

用户的既有规划是"先在群里丢样本验证需求，有人要才批准做完整功能"。这个节奏是对的，此处只补三条：

1. **第一笔钱应该来自"定制交付"，不是"订阅"**。因为定制的价值可被单一客户立刻感知，而订阅卖的是"未来可能有用"。一个人 8000 元/年的定制，比 10 个 698 元的订阅更容易谈。
2. **能力包是复利资产**。给 A 客户做的"冷链温度异常预警"，B 客户大概率也要。第 5 个客户的交付成本应显著低于第 1 个。
3. **不要在早期做自助注册 + 自助付费**。你的支持能力扛不住无门槛流入。**邀请制**（系统已有 `invite_codes.py` 的基础）既控制节奏，又制造稀缺感。

## 五、竞争环境 · 市场前景 · 定位

### 5.1 竞争格局（2026 年公开数据）

| 厂商 | 定位 | 规模 |
|---|---|---|
| **舟谱数据** | 快消渠道数字化（经销商 → 品牌商） | **4 万+ 活跃经销商、200+ 活跃品牌商、700 万+ 终端网点、年 GMV 4500 亿+**，7 轮融资，2015 年成立 |
| 纷享销客 | 连接型 CRM，主攻大中型品牌商 | 服务蒙牛、元气森林、好丽友 |
| 勤策（原外勤 365） | 快消全链路（SFA → DMS → TPM） | 品牌商 |
| 销售易 | 企业级 CRM | 中大型企业 |
| 用友畅捷通 | 业财一体化云 ERP（T+） | 成长型企业；深度绑定用友生态 |
| 管家婆 | 进销存 / 订货 / 电商 ERP | 120 万+ 企业用户 |

**行业分类共识**（四类定位）：快消渠道增长平台 / 销售管理一体化 / 渠道分销与 B2B 订货 / 经销商业财与进销存。

**关键判断：这四类里没有"AI 经营副驾"这一类。** 舟谱的"易商 BI"和"AI 招商"是在其 ERP 数据之上的分析层，本质仍是**"用它的数据、在它的平台里"**。而客户的现实是：**数据在别人的 ERP 里，且拿不出来做 AI 分析**——这正是用户创业的起点痛点，也仍然是空位。

### 5.2 Hergent 的结构性优势与劣势

| | 内容 |
|---|---|
| **优势** | ① 创始人本人是经销商，domain expertise 别人买不到；② AI 原生，没有历史包袱（舟谱做不到"数据在别家 ERP 也能用"）；③ 配方驱动，天然适配"每个经销商口径不同"；④ 轻，不碰交易一致性 |
| **劣势** | ① 单人 + 非技术；② 无销售团队、无实施团队；③ 稳定性/支持能力未经规模检验；④ 数据要靠用户上传或连接器，比"自带 ERP"的厂商更依赖客户配合 |

### 5.3 结论：聚焦低温奶，但预埋多行业

**建议：现在聚焦低温奶，不要横扩到整个快消。**

**理由（按重要性排序）**：

1. **护城河在域知识，不在功能数量。** 低温奶的特殊性在于：效期极短（必须按天算货损）、冷链成本、批次强追溯、返利规则复杂（多品牌月度阶梯）。这些是"把配方做准"的活。横扩到休食/酒水，配方要重写一遍，而你的配方深度会立刻被摊薄。
2. **舟谱已在"广度"上建立不可逾越的规模优势。** 4 万经销商、4500 亿 GMV——拼覆盖、拼 SKU 库、拼品牌资源，赢不了。**只能拼深度。**
3. **横扩的正确触发条件是"机制成熟"，不是"功能齐全"。** 即：当 L1「用户自定义配方域」和 L2「能力插件」跑通，且你已有 3~5 个能力包在真实客户那里复用成功——**那时横扩的边际成本才低到可行**（新行业 = 写一套配方模板 + 能力包，而不是重做产品）。
4. **低温奶是天然的"高门槛品类"**：能做准低温奶的效期/货损/返利，迁到其他品类是降维；反过来则不是。

**架构上必须预埋的三件事（现在做，成本几乎为零）**：

1. **配方命名空间按行业分段**（如 `loss.milk.*` / 未来 `loss.*`），避免第一套配方把结构写死。
2. **技能包目录按行业约定**（现有 `hergent-milk-*` 前缀就是对的，继续沿用）。
3. **不把"低温奶"硬编码进平台逻辑**——它应该只出现在配方数据和技能包文本里。**判据：如果新建一个行业要改代码，说明预埋没做到位。**

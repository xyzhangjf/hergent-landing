## 三、逐项详解（只展开「部分实现 / 未覆盖」的 10 项）

### P0-1 定位句「说结果不说功能」— 未覆盖
- **现状**：全站价值表述仍是功能语（「AI 中心」「能力中心」）。经销商首屏看不到「少赔临期 / 不漏返利 / 不用手工报单 / 回款有人盯」这类结果句。
- **影响**：转化环节缺最有效的一句话；非技术老板无法在 5 秒内判断「这跟我有什么关系」。
- **最小改动**：`Workbench.vue` 首屏 KPI 条上方加一行结果句，数据直接用已有 `dashData` + `expiryData.length` 拼装；`Login.vue` 副标题同步。**纯前端，零后端**。

### P0-2 指标字典 — 部分实现
- **已有什么**：计算端点齐（`bi.py` 五类分析 + 仪表板保存）；口径提案审核台已能「AI 发现新口径 → 老板采纳/驳回 → 写入配方」（`recipe_evolution.py`）。
- **缺什么**：**没有一张「指标登记表」**把「临期率 / 返利达成率 / 均单 / 回款率」的口径（分子、分母、数据来源、单位、下钻端点）集中登记；因此副驾给的每个数字**无法自证**，也无法点进去看明细。这是「防 AI 瞎编」的地基（对标数势 SwiftMetrics / 观远仪表板锚点）。
- **影响**：**这是阻止付费的最大信任障碍**——老板不敢拿一个「来源不明」的数字去决策。
- **最小改动**：新增 `metric_registry` 表（指标键 / 中文名 / 口径说明 / 分子分母 SQL 或来源表 / 单位 / 下钻端点）+ 只读端点 `GET /api/metrics/registry`；副驾与卡片渲染数字时挂「口径」角标 → 点开抽屉显示口径 + 「看明细」按钮。

### P0-3 信任三件套 — 部分实现（1/3）
- **① 权限跟随登录人** ✅ 做得比别人好：`roles.js` 收敛为唯一角色来源（8 个后端角色）并有回归护栏脚本；`router/index.js:120-137` 用 `meta.roles` 挡「手敲 URL 深链」，且**明确论证了 fail-open 是刻意的**（未知角色放行，避免误锁）。
- **② 改前确认** ❌ **不存在**：全前端搜 `confirm(` / `ConfirmDialog` / `二次确认` = 0 命中。副驾只有 `aiGuard`（`CopilotDrawer.vue:951`：`advise` 只建议 / `execute` 允许执行）这个**权限拨档**，没有「改动预演 → 确认 → 生效」的闸门。
  - ⚠️ 现状其实「很安全」——因为**根本没有真正的写通路**（动作都是 toast 占位）。但这意味着「改前确认」作为**产品承诺**无法对客户讲。
  - **最小改动**：抽一个 `ConfirmAction` 组件 + 统一「动作信封」（`{title, target, before, after, effect}`）；所有由 AI/卡片触发的写操作先弹信封，确认后才发请求，并落 `ai_advice_log`（复用 `ai_assist.py:904-935` 的 advice 通道）。
- **③ 数据不训练、不跨商家共享** ❌ 零声明：`server/prompts/SOUL.md`、`Settings.vue`、`AiHub.vue` 均无。
  - **影响**：这是**最便宜的销售话术**（Shopify Sidekick 明确承诺），也是最小成本消解「AI 会乱来 / 数据会外泄」顾虑的手段。技术上我方确实做到了跨租户只共享量级桶（`experience_loop.py:32-42` 有红线守卫），**做了却没说**。
  - **最小改动**：`Settings.vue` 新增「数据与隐私」区块（三点承诺）+ `SOUL.md` 追加一段同义协议 + 副驾首次打开时一句话。

### P1-5 洞察→动作闭环 — 后端有、工作台断线（**本轮最高性价比**）
- **证据对照**（同一批动作，两端待遇完全不同）：

| 后端已产出（`routers/today.py`） | 前端行为 |
|---|---|
| `:284` `{"type":"create_purchase","label":"一键生成采购单"}` | `Workbench.vue:280` `toast('一键生成采购单：功能完善中')` |
| `:335` `{"type":"dunning","label":"发起催收"}` | 同上，占位 |
| `:336` `{"type":"generate_script","label":"AI生成催收话术"}` | 同上，占位 |
| `:421` `{"type":"promo","label":"建议促销处理"}` | 同上，占位 |
| `:396/440` `view_detail` / `view_product` | `:279` `toast('详情页开发中')` |

- **影响**：产品停在「看板」而不是「真干活」，而这正是对标 FieldAssist / Aforza Ava 的核心差距；**且后端成本已付**。
- **🔴 架构约束（必须先解决）**：`create_purchase` 属「新增 order CRUD」，与既定战略「**订单 CRUD 冻结**」冲突。
  ⇒ 该动作**不得**新增 Hergent 侧写接口，两条合规出路：
  (a) 前端跳转到**既有**采购单页并**预填**参数（人确认后由既有流程落库）；
  (b) 归入连接器写回通道（`routers/datasources_v2.py`）。
  其余动作（`view_*` 跳转、`generate_script` 只读生成、`dunning` 复用既有催收）**可直接接**。
- **最小改动**：建一个「动作处理器注册表」（`type → handler`），避免 `cardAction` 里堆 `switch`；工作台与副驾共用同一张表，保证「后端加动作 → 两端都生效」。

### P1-6 混合定价 — 部分实现
- 已有 tier 档位与计量流水，**缺「基础订阅按什么卖、AI 怎么单独计价」的产品化表达**。
- **最小改动**：把 `quota.tier` 从技术档位升为**业务版本**（单品牌小户 / 多品牌中型 / 区域经销商），在 `AiHub` 用中文权益矩阵呈现；补「本月省下的钱」——`AiHub.vue:127` 现已写「节省金额待『金额回算』接入后展示（下一步）」，把它接上（临期少赔 + 返利多拿 + 手工省时，均可用既有 `loss`/`rebate`/`forecast` 数据算）。

### P1-7 经营简报 — 基本实现，缺「推送闭环」
- 页面内晨报/卡片/待办都有；**但「每天早上主动送到老板面前」这一步没做**（老板不会每天打开 Web）。
- **最小改动**：`scheduler.py` 加一个 07:30 任务：调晨报生成 → 站内通知（已有 `NotificationPanel`）→ 企微/微信推送（复用 `feishu_notify.py` / `hergent_tenants.py` 通道）。

### P2-9 技能包库 — 部分实现（且有技术债）
- ⚠️ **两套 skill 路由并存**：`/api/skills`（`skills_api.py:7`，54 行）与 `/api/ai/skills`（`ai_skills.py:16`，143 行），职责重叠 —— 属「同一件事两处实现」，收敛前不宜再往上加功能。

### P2-12 行业基准值 — 后端有、前端未用
- 已具备合规地基（红线参数拒绝 + 量级桶），却只展示「跨租户口径 12 条」这种内行数字，**没有变成老板看得懂的「你的库龄比同类高 X%」**。
- **最小改动**：基于 `industry_caliber` 出 2–3 个相对指标（库龄分位、返利达成率偏离、报单准确率）放到 `AiHub` 或经营趋势页，并在文案上明确「只比量级区间，不比金额」。

## 四、下一步开发计划

### 推进顺序总原则
**先「把已有能力接通」→ 再「补可信度地基」→ 再「商业化变现」→ 最后「规模化复制」**。
理由：第一批全部是**接线与文案**，不新增数据模型、不碰交易一致性、风险最低而用户感知最强；指标字典（T5）是后续所有 AI 输出的可信底座，必须先于定价；定价必须建立在「能证明省了钱」之上。

### 批次一（P0）— 接通已有能力 + 补齐信任（零新增写接口）

| 任务 | 内容 | 技术实现要点 | 验收判据（能失败的形式） |

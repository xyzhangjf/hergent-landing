## 结论速览：三个"反常识"的发现

理想形态的三层里，**最缺的不是能力，而是"把已有能力接到用户面前"**。本轮勘察出三处断裂，全部有生产数据或源码证据：

| # | 发现 | 一句话 | 证据 |
|---|---|---|---|
| **①** | **通知只写不读** | 主动提醒的**生成端非常活跃**，**交付端完全断裂** | `message_center` **21,273 行**，`is_read=0` 占 **100%**；**无任何 API、无任何页面** |
| **②** | **同名两列不同源（分处只读态 / 编辑态）** | 面板**半生效**：它只驱动一列，而"建议"这个名号下有两个引擎各算各的 | ⚠️ **已实测纠正**：只读汇总表（41 列）只有**「系统建议」**＝后端 `forecast_audit.py::_audit_items`（**硬编码** `DEFAULT_SAFETY_DAYS=7` `:32` + 到货周期 `:168`）；编辑网格（18 列）只有**「配方建议」**＝前端 `Forecast.vue::computeSuggestion`（`:4030-4057`，读面板配方）。**两者从不同屏** —— 同一个 SKU 在只读态看一个数、点「改单」后看另一个数 |

## 二、三个断裂的详细说明

### ① 通知只写不读 —— 完成度已经很高，却差最后 10%

**生成端（活跃）**：`scheduler.py` 是一个真正的"主动推送引擎"（`:3` docstring），每分钟 tick，跑着 18 类作业：库存预警(30min)、应收逾期(1h)、效期(1h)、合同到期(1h)、沉睡客户(1h)、费用异常(10min)、晨报(8:00)、采购计划(6:00)、催收(8:00)、时间线(8:00)、AI 洞察(7:30)、LLM 个性化洞察(7:35)、**副驾经营卡简报(8:05)**、**预报催单(9:00/16:00)**、档案体检(周一)、AI 提醒(每分钟)。

**中间（堆积）**：全部写进 `message_center`，然后**没人读**：

```
message_center (tenant_1.db)
  总行数      21,273
  is_read=0   21,273   ← 100%
  不同标题    7 种
  时间跨度    2026-06-18 ~ 今天 12:40（仍在增长）
```

**交付端（断裂）**：
- `routers/` 目录中**没有任何** endpoint 提到 `message_center` / 通知 / 消息（已全目录 grep 确认）
- 前端对 `message_center` / `通知中心` / `消息中心` **0 命中**
- 唯一的出口是 `_push_tenant_channels()`（`scheduler.py:845`）走 Hermes 推企微/飞书/钉钉；租户 1 的 `.env` 已配企微凭证 → **用户只可能在企微看到，产品里看不到、也无历史可查**

**这件事的两面性（很重要）**：
- **好消息**：理想形态的核心能力③"盯住你的事"，**后端已经建好了 90%** —— 不需要新建调度引擎、不需要新建推送渠道，只需要一个 API + 一个页面。
- **坏消息**：**它同时制造了一个新问题 —— 告警疲劳**。同一件事每 30 分钟推一次，88 天推了 13,323 次。**如果只把 UI 接出来而不收敛噪音，接出来的就是一个每天 240 条的收件箱，用户会立刻放弃它。**
- → **所以"接出来"和"收敛"必须一起做**。而这恰好是 AI 副驾该干的活：**AI 的价值不是多推一条，是把 21k 条流水收敛成 3 句"今天该干什么"。**

### ② 口服承诺：口径改了不生效

| 配方面板 | 用户能改什么 | 真生效吗 |
|---|---|---|
| 货损 `LossWorkflow.vue:17-83` | 计算维度、临期天数、计价口径、临期损耗率、过期损失系数 | ⚠️ **只有 `threshold_days` 真生效**（`batch_tracker.py:82`）；红色的 3 天档、黄色的 14 天档、50/30/15 折扣率**全部硬编码**（`:45/:46/:61-65`） |
| 工资 `PayrollWorkflow.vue:17-101` | 底薪/提成/绩效/奖金/津贴/扣款/起征点 | ✅ 逐字段透传给 `_compute_payroll`（`payroll_workflow.py:105-114`）；但**个税累进表硬编码**（`erp_db.py:5811`） |
| 报单「建议算法」面板 `Forecast.vue:820` 按钮 / `:824-844` 面板 | 策略（安全库存法/历史均值法/趋势外推法/加权混合法）· 覆盖天数 · 外推步数 · 历史权重；命名配方存 `forecast_config[kind=recipe]` | ⚠️ **前端真生效、后端完全不读**：`computeSuggestion()`（`:4030-4057`）用面板参数算**编辑态**「配方建议」列 ✅；**只读态**「系统建议」列走后端 `forecast_audit.py::_audit_items`，硬编码 `DEFAULT_SAFETY_DAYS=7`/`DEFAULT_ARRIVAL_CYCLE=2`/`DEFAULT_LEAD_DAYS=4`（`:32-35`）❌ —— 两套参数集不重叠，要先扩字段才能接上 |
| 报单 `ReportMapping.vue:80-160` | 对象/简称/单型/源仓/目标仓 | ✅ 映射表被导入流程使用（这是真的） |
| 返利 `Rebate.vue:919/983-1036` | 返利比例、阶梯区间、达成数 | ✅ 走合同/规则表（不是配方表，但生效） |

→ **这是必须最优先消除的一类缺陷**：用户改了、界面显示保存成功、数字没变 —— 比"没有这个功能"更伤信任。

### ③ 配方功能从未被使用 —— 这改变了 P1 的判断

生产实测（tenant_1，唯一真实租户）：

| 表 | 行数 | 解读 |
|---|---|---|
| `workflow_recipes` | **1** | 仅 `loss_recipe`，`updated_at = 2026-09-14 08:41` —— **正是本轮 P0 验证时我写入的那一条** |
| `recipe_versions` | **0** | 版本快照机制**从未被触发** |
| `recipe_proposals` | **表不存在** | "AI 提案 → 老板审批"治理流**从未被调用** |
| `forecast_config` | 9 行，**无 `kind='recipe'`** | 报单配方**从未保存过** |

**但是**——不能据此说"用户不需要改口径"，因为有一种同样合理的解释：**用户是老板本人，配置一直由 AI（我）代做**。而且有一条**直接证据支持"AI 代填"这条路**：

| `cron_tasks` 实测 | 值 |
|---|---|
| 条数 | **3 条，内容完全相同** |
| 内容 | 「你帮我设个定时任务，每天上午8点把当日AI方面的重大新闻发给我」 |

| `name` 字段 | 存的是**用户原话**（没解析出标题） |
| 最近执行 | 2026-09-14 08:00（在跑） |

→ 这条数据说明三件事：
1. **"AI 代用户配置"这条路径，用户真的会走**（他直接用自然语言对副驾提要求）；
2. **但产品化程度不够**：连提 3 次 = 没有确认反馈；`name` 没解析 = 没有结构化；
3. **这是理想形态（AI 代填）的现成验证场** —— 不是要不要做，而是把它做像样。

## 四、优先级排序的理由（为什么是这个顺序）

1. **P0-1（通知）排第一，因为性价比是全场最高**：后端 90% 已建好（表、写入、读取函数、调度、企微渠道全在），缺的只是 API + 页面 + 收敛策略。**同样的投入，这里能拿到的用户感知最大。** 而它同时命中理想形态的核心能力③。
2. **P0-2（空承诺）排第二，因为它在损耗信任**：用户改了不生效，比没有这个功能更糟 —— 从"没做"变成"骗我"。而且它已有前科（报单模版 8 处"必填"文字、0 处校验；效期全空反而算出"库存健康"）。
3. **P0-3（隔离批 1）排第三，因为它是小时级**：成本极低、收益明确、可单行回退。它同时也是"开放任何自定义能力"的前置。
4. **P1-1 先于 P1-2**：因为数据显示"配方 0 使用"，**在扩面之前必须先搞清原因**。否则可能把力气花在一个用户根本不想要的入口上 —— 这正是你自己定的"先验证、再产品化"节奏。
5. **P2（连接器）排在 P1 之后**：连接器是**获客工具**（对畅捷通/金蝶客户），而 P1 是**留存与口碑工具**（对现有客户）。当前只有 1 个客户 → 先把留存做实。
6. **P3 与"生态"一起压后**：见上一份文档的判定 —— 生态是规模的函数，不是架构的函数。

---

## 五、一句话总结

> **理想形态的三层里，"数据层"能用、"表达层"半通、"口径层"半通，而真正的断点不在"缺能力"，在"已有能力没接到用户面前"。**
> 所以本阶段的主线不是"做更多"，而是三件事：**① 把通知接出来并收敛掉噪音；② 把改了不生效的口径要么修好要么摘掉；③ 把"AI 代用户改口径"从"我手工帮他做"变成产品能力。**

# P0：「毛利」这一层目前没有数据基础（实测报告）

> 发现于 2026-10-13 v493（起因：按《图表能力补齐开发计划》给「经营趋势」页补图）
> 结论一句话：**图表层已经能画，但「毛利」这两个字在生产上还算不出来 —— 商品档案里没有进货价。**
> 所有数字均为生产真机只读实测（tenant 1），非推算。

---

## 一、先说结论（三句）

1. **不是图表坏了，是数不对。** 前端已经能画折线 / 柱状 / 环形 / 排行（v491 + v493），但其中依赖「成本」的那几张图，**后端算出来的成本恒为 0**。
2. **现在打开「经营趋势」页，那三张「毛利」图是空的。** 这不是故障，是**正确地显示"算不出来"** —— 但原来的提示是「这段时间还没有数据」，会让人以为系统坏了或者"这段时间没生意"。
3. **只要把商品档案的售价 / 进货价补齐，这几张图会自动有数，不需要改代码。**

---

## 二、实测证据

| # | 查了什么 | 实测结果 |
|---|---|---|
| 1 | 商品档案总数 / 在售 | 473 个 / **363 个在售** |
| 2 | 同时有「售价 + 进货价」的商品 | **56 个**（占在售的 15%） |
| 3 | 这 56 个商品卖过货吗 | **一单都没卖过**（销量 0） |
| 4 | 有销量的商品数 / 总销量 | 222 个 / 420 万（件） |
| 5 | 已送达 / 已签收明细行数 | **142,858 行** |
| 6 | 这些行里**有进货价**的行数 | **0 行** |
| 7 | `/api/reports/profit-breakdown` 实际返回 | `total_revenue = 0`、`total_cost = 0`、`total_profit = 0`（**全零**） |
| 8 | 真实已送达 / 已签收销售额 | **¥8,786,105.85** |
| 9 | `/api/reports/customer-profitability` | `profit ≡ revenue`、`margin` 恒 **100%**（因为成本是 0） |

**翻译成人话**：卖出去的货，商品档案里没有进价 ⇒ 系统只知道卖了多少钱，不知道赚了多少钱。而**有价的 56 个商品恰好一个都没卖出去**，所以两边的数据永远碰不上。

## 三、这件事的两层，别混为一谈

### 第 1 层：数据缺口（**业务侧，你来补**）

- 需要补的是**商品档案**里的「售价」和「进货价」。
- 判据很简单：**卖过的商品（222 个）必须两价都有**。有价的 56 个没卖过，等于白填。
- 补完之后：品牌毛利结构 / 商品毛利排行 / 品类毛利对比 / 收支趋势里的毛利，**全部自动有数**（前端一行代码都不用改）。

### 第 2 层：代码缺陷（**我这边的建议，未修，等你拍板**）

`server/erp_db.py::get_profit_report()` 里有**两处独立于数据缺口**的算法问题：

1. 🔴 **销量把「非送达订单」也计进去了**
   那句 `LEFT JOIN sale_orders so ON soi.order_id = so.id AND so.status IN ('delivered','signed')`
   —— 状态过滤挂在 **`so` 的 JOIN 条件**上，`soi.quantity` 的 `SUM` 并不受影响。
   ⇒ 草稿 / 待审订单的明细**照样被加进销量**。实测该函数算出的销量合计 **420 万**，而"已送达/已签收"口径的明细也是 14.2 万行 —— 两者**碰巧一致**纯属当前库里没有非送达明细，**不是代码对了**。
2. 🔴 **收入用「目录现价 × 总销量」，不是订单实际金额**
   `p['revenue'] = sold * p['sale_price']`。同一商品不同客户、不同时期的价格差异全部消失；改一次档案价，**历史收入跟着变**。
   正确来源就在手边：`sale_order_items.amount` / `unit_price`（订单当时的真实价）。

**这两条我没动。** 原因：① 计划明确「后端零改动的前提下补前端」；② 它们会改变**所有**读毛利的地方（报表、AI 副驾、经营一页纸），属于跨模块口径变更，该由你决定而不是我顺手改。

# 「报单自动化」归属评估与迁移可行性

> 评估日期：2026-09-22
> 评估对象：**报单自动化**（智能创建/关闭报单表）
> 现状位置：`目标与返利 → 创建品牌目标` 弹窗 → 「到货与报单节奏」③ 区
> 候选位置：`预报订单 → 报单配置` 页签
> 方式：源码 + 后端取证（**未改动任何代码**）

---

## 0. 先说结论

**现状「半合理」，但不建议现在就迁。建议分两步走。**

| 步骤 | 动作 | 触发条件 |
|---|---|---|
| **第一步（现在做）** | **不迁归属**，只补三处低成本修补：① 唯一性前置提示 ② 报单配置页加**只读镜像卡 + 深链** ③ ③ 区文案点明"关了谁才能开" | 立即 |
| **第二步（条件触发）** | 当决定让自动化**真的跑起来**（接调度器自动开闭期次）时，**连同数据模型一起**迁到「预报订单」域，并把配置**上提为租户级** | 需要先拍板"要不要做自动建表" |

**一句话理由**：现在迁移只能是"**搬 UI、不搬数据**"—— 会同时吃到两边的缺点（跨模块写第二套接口 + 节奏与预览被割裂 + 仍受租户唯一约束），却没解决当前真正的三个硬伤。而这三个硬伤用极低成本就能缓解。

**最硬的一条事实**：`报单自动化` 目前**没有执行体** —— 三个时点没有任何调度器消费。所以"放哪儿"的真实收益，取决于你**是否打算让它真的跑**。

---

## 1. 判断依据与假设

- 本项目**没有 production 分支**，本次评估基于**源码事实**（前端 `hergent-cn-v2/src`、后端 `hergent-erp/server`），不涉及生产数据。
- 「两个候选界面」的**真实身份**已核实（见 §2）——**它们是两个不同模块里的不同东西**，不是同一层级的两个页签。这是本评估的关键前提。
- 本评估**不推翻** v121 / v122 的既定决策，但会指出其中**未被论证的一步**（见 §4.4）。

## 2. 事实基线（代码取证）

### 2.1 「报单自动化」到底做什么

位置：`src/components/rebate/ArrivalRhythmBlock.vue` 第 50–94 行（③ 区）

| 元素 | 字段 | 说明 |
|---|---|---|
| 手动建表 / 自动建表 | `auto_period_enabled` | 二选一开关 |
| 开放填报 | `auto_open_time` | 报单日**前一日**这个时刻自动建表 |
| 自动关单 | `auto_close_time` | 报单日**当天**这个时刻截止 |
| 厂家下单截止 | `supplier_deadline_time` | 中间留给经理改单/付款 |
| 未来 6 期预览 | 只读（`/auto-period-preview`） | 报单日/开放→关单/到货/本期应报 + 漏报告警 + 首次报单日建议 |

### 2.2 它现在挂在哪（渲染链）

```
路由 /rebate  ──►  Rebate.vue（侧栏「目标与返利」）
                    └─ TargetFormModal.vue   标题 computed：「创建品牌目标」/「编辑品牌目标」
                        └─ BrandTargetForm.vue
                            ├─ MonthlySplitBlock（12 个月目标）
                            ├─ RebateValueBlock（默认档位）
                            └─ ArrivalRhythmBlock  ① 节奏 ② 到货产出 ③ 报单自动化
```

组件注释**已自陈**：`到货与报单节奏（品牌方排产节点，品牌页独有）`。

### 2.3 「报单配置」是谁

**它不是侧栏项，也不是顶层路由** —— 它是 `页面 Forecast.vue` 的**子页签**：

```
Forecast.vue（预报订单模块）
  ├─ 页签 本期预报（activeTab='summary'）
  ├─ 页签 历史期次（'history'）
  └─ 页签 报单配置（'config'） ──► <ReportMapping />   ← 第 2140 行
```

`ReportMapping.vue` 页头自述：`把"系统全称 ↔ 报单简称(列头) ↔ 单型"一次性配好，员工小程序报单不再碰列名`；另有「模板参数」（舟谱模板的业务员/部门/仓库列）。

⇒ **它的职责是「报单对象与模板的映射」，与「期次何时开闭」不是同一件事。**

### 2.4 数据模型与后端约束（两条决定性事实）

**事实 A · 与「报单节奏」同表同行**

`auto_period_enabled` / `auto_open_time` / `auto_close_time` / `supplier_deadline_time` 与 `order_mode` / `order_first_date` / `order_cadence_days` / `order_lead_days` / `order_max_early_days` **同属 `rebate_target_rules` 同一行**。
后端 `rebate_rules.py:840-843`：若既无 `order_first_date` 又无自动化 → 强制 `auto_period_enabled=0`。**两者在校验层就是绑定的。**

**事实 B · 语义上是「租户级单例」**

`rebate_rules.py:1144-1154`：
> 租户内智能开关唯一：多个品牌各自开启会产出多套报单表互相冲突
> `SELECT id, rule_name FROM rebate_target_rules WHERE auto_period_enabled=1 AND is_active=1 AND id<>?`

⇒ **物理上挂在某个品牌行，语义上却是全租户唯一。**

**事实 C · 运行时没有执行体**

全后端检索 `auto_period_enabled`，除 `rebate_rules.py`（校验/预览/写库）外**仅 3 处**，且全在 `erp_db.py` 的**建表迁移**里：
- 调度器 `scheduler.py` 的 20+ 个任务中**没有任何一个**读 `auto_*` 三时点；
- 期次创建是**手动接口** `POST /api/forecast/periods`（UI 按钮「新建期次」）；
- 催单 `push_forecast_reminder_current()` 用的是**期次自身的** `order_start`/`order_end`，不是规则里的时点。

⇒ **当前 `报单自动化` = 配置 + 预览，无自动建表/自动关单。**

**事实 D · 前端无唯一性前置校验**

`TargetFormModal.vue` / `ArrivalRhythmBlock.vue` 中该开关只是普通表单字段（左右两个 `seg-btn`），**没有任何"已被别的品牌占用"的前置检查**。

## 3. 方案 A：留在「创建品牌目标」

### 3.1 功能定位

被视为**品牌规则的一个属性**：与「报单节奏」同行同表同区，是品牌排产节点（蒙牛/简爱各不同）的延伸。

### 3.2 使用场景

- 老板给**某个品牌**建年度目标时，顺手把"这个品牌的节奏 + 要不要自动开闭表"一次配好。
- 典型是一次性设置、长期不改（年度/半年度级别）。

### 3.3 用户习惯契合度

| 维度 | 评价 |
|---|---|
| 找到它 | 🟡 **弱**。「创建品牌目标」这个名字不含"报单"，用户想改自动开闭时间**不会想到去这里** |
| 理解它 | 🟢 **强**。用户在配①节奏的**同一屏**里看到时点，能立刻明白"开放填报 = 报单日前一天" —— 这句话离开 `order_first_date` 就没有参照系 |
| 改它 | 🟡 中。改完必须走一遍"保存整条目标规则"，一旦该季目标已锁，改时点会被目标的校验牵连 |

### 3.4 优势 / 劣势

**✅ 优势**
1. **数据同源**：配置与 `order_*` 同行，保存时**同事务强校验**（含"关单必须早于厂家截止"`rebate_rules.py:1116`）。
2. **节奏与预览不割裂**：6 期预览的输入 = 节奏 + 到货 + 时点。留在同屏，预览才是"所见即所得"。
3. **延续 v121 合并决策**：v121 刚把「到货 + 报单」**合并成一块**（正因为此前分两处，导致重复输入项：到货模式/首次到货日/到货周期/到货星期被删）。再拆开等于**回退该决策**。
4. **有前置依据**：v122 已把这一整块判为「**品牌页独占**」，商品目标页移除；团队已认同"这是品牌维度"。

**❌ 劣势**
1. 🔴 **租户单例伪装成品牌字段**：用户在「简爱」表单打开「自动建表」，**保存时才被拒**（"同一时间只能开启一条，当前已开启：蒙牛…"）。用户既不知道去哪改，也不知道这是"全局唯一"。
2. 🔴 **名实不符**：它是**期次开闭策略**，而「期次」是**预报订单模块**的核心对象 —— 在「目标与返利」域里改期次行为，属跨域。
3. 🟡 **表单过载**：「创建品牌目标」一个弹窗承担 4 类关注点（目标 / 返利 / 到货节奏 / 报单自动化），认知负荷高。
4. 🟡 **语义错配**："创建"暗示一次性动作，而自动化时点是**长期运行参数** —— 改的频次与维护心智完全不同。
5. 🟡 **预期落空**：用户以为开了就自动，实际上**期次还要手动建**。

## 4. 方案 B：迁移到「报单配置」

### 4.1 功能定位

被视为**报单运行设置**：与"报单对象映射""模板参数"并列，构成"**报单这件事的全部设置**"。

### 4.2 使用场景

- 员工报单出问题时（没人收到开放通知 / 期次没建 / 关单太晚），管理员到**报单配置**里查和改。
- 更像"运维参数"，改的频次高于目标。

### 4.3 用户习惯契合度

| 维度 | 评价 |
|---|---|
| 找到它 | 🟢 **强**。「报单」找「报单配置」，命名/心智完全对齐 |
| 理解它 | 🔴 **弱**。「开放填报 = 报单日**前一日**」—— 但**报单日不在这页**。必须把①节奏**只读镜像**过来，否则用户填得更盲 |
| 改它 | 🟢 强。与业务目标解耦，改时点不用动目标规则 |

### 4.4 可行性：**技术上可行，但有 4 个必须先解决的前置**

| # | 前置问题 | 严重度 | 说明 |
|---|---|---|---|
| B-1 | **数据模型冲突** | 🔴 高 | 时点在 `rebate_target_rules` 品牌行上。迁 UI 不迁数据 ⇒ 报单配置页要引入**第二套数据源**（`rebate_rules` API），而该页现在只碰 `reportMappingApi`。若要"正本清源"则需新表/新接口 + **租户库迁移**（`erp_db.py` tenant patch + `_safe_migrate` 两处都要加，且幂等） |
| B-2 | **节奏与预览被割裂** | 🔴 高 | 预览依赖节奏+到货（还在品牌页）。搬走后要么复刻一套取数（`loadArrivalPreview` 有 300ms 防抖与 watch 依赖，v122 §7 明说它属节奏区），要么预览留在原地 → 配置与验证分居两页 |
| B-3 | **校验时机被绕过** | 🟡 中 | 现在唯一性校验在保存规则时同事务执行（`rebate_rules.py:1144`）。跨页后从报单配置调写接口，可能绕过 `validate_rule` 的强制逻辑（L840-843：无首次报单日时强制清零） |
| B-4 | **回退 v121/v122 决策** | 🟡 中 | 需重新论证"到货/报单为何又可分家"，并承担重复输入项复现的风险 |

### 4.5 优势 / 劣势

**✅ 优势**：命名与心智匹配；模块归位（期次是预报订单的工作对象，"谁在何时开表"与"表里放哪些对象"同工作流）；与目标解耦，改运行参数不动业务目标。

**❌ 劣势**：**B-1–B-4 四项技术前置**；且若只搬 UI 不搬数据，会**同时吃到两边缺点**（跨模块写第二套接口 + 预览割裂 + 仍受租户唯一约束），收益为负。

## 5. 两方案对照

| 维度 | A 留在「创建品牌目标」 | B 迁到「报单配置」 |
|---|---|---|
| 功能定位 | 品牌规则的属性 | 报单运行设置（租户级） |
| 使用场景 | 建目标时顺手配，低频 | 报单出问题时来查/改，中频 |
| 数据归属 | ✅ 与节奏同行，最自然 | 🔴 需迁数据或引第二数据源 |
| 预览（6 期） | ✅ 同屏，所见即所得 | 🔴 割裂或需复刻 |
| 校验完整性 | ✅ 同事务强校验 | 🟡 可能绕过 `validate_rule` |
| 可发现性 | 🔴 名字不含"报单"，找不到 | 🟢 命名完全对齐 |
| 租户唯一语义 | 🔴 伪装成品牌字段，保存才拒 | 🟢 天然是"一处设置" |
| 与期次的模块归属 | 🟡 跨域（期次属预报订单） | 🟢 同域 |
| 改动成本 | 0（维持） | 🔴 高（含迁移 + 双数据源） |
| 决策连续性 | ✅ 延续 v121/v122 | 🟡 需重新论证 |

## 6. 明确建议

### 6.1 现在**不要迁**。理由

1. 迁移的**收益（可发现性）用更低成本就能拿到**；而迁移的**代价（B-1–B-4）是实打实的**。
2. 当前真正的三个硬伤，**都不是"位置"问题**：
   - ① 租户单例伪装成品牌字段（**校验时机**问题）
   - ② 没有执行体（**能力缺口**问题）
   - ③ 名字里没"报单"（**可发现性**问题）
   换个房间并不能解决 ①②。
3. 现在迁 = 只搬 UI 不搬数据 = **同时吃到两边缺点**，净收益为负。

### 6.2 立即可做（低成本、不改归属、不改数据）

| # | 动作 | 落点 | 收益 |
|---|---|---|---|
| 1 | **唯一性前置提示**：打开表单时查一次"是否已被别的品牌开启"，是则把「自动建表」置灰并说明「已由『蒙牛…』开启，需先去那条关闭」+ 一键跳转 | `TargetFormModal.vue` / `ArrivalRhythmBlock.vue`（需一条只读查询） | 消灭"填完一整屏才被拒" |
| 2 | **只读镜像卡 + 深链**：在 `报单配置` 页顶部加一张只读卡（当前：手动/自动 · 由『X 品牌』控制 · 开放 HH:MM / 关单 HH:MM / 厂家截止 HH:MM），点「去调整」跳到目标与返利 | `ReportMapping.vue` | **不迁数据就拿到可发现性** |
| 3 | **文案点明因果**：③ 区把"手动/自动"的说明补一句"**全系统同一时间只能有一个品牌开启**"；并把"期次需在此时间前手动新建"说清（与事实 C 对齐） | `ArrivalRhythmBlock.vue` | 消除预期落空 |

### 6.3 什么时候**应该**迁（条件触发）

当且仅当你拍板 **"让报单自动化真的跑起来"**（调度器按 `auto_open_time`/`auto_close_time` 自动开闭期次）时：

- 它的性质就从"**目标属性**"变成"**运行参数**"；
- 那时应当**连同数据模型一起**迁到「预报订单」域（报单配置，或该模块下新开「期次自动化」），并把配置**上提为租户级**（不再挂在某个品牌行上）；
- 同时把 6 期预览一并搬过去（因为那时预览的输入已随迁）。

> 也就是：**先决定"要不要让它真跑"，再决定"放哪儿"。** 顺序反了会白做一轮。

## 7. 待你拍板的一件事

**「报单自动化」是否要真的执行**（自动建表 / 自动关单）？

- **要** → 走 §6.3，迁移 + 数据上提 + 接调度器，一次性做对。
- **暂时不要** → 走 §6.2 三处修补即可，**归属不动**。

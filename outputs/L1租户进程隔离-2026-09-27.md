# L1 落地：租户 AI 以独立系统账号运行（内核级隔离）

**日期**：2026-09-27 19:00–19:25
**目标（来自报告 §五 L1）**：让每个租户的 AI 进程以**自己的系统账号**运行，使它**只能访问自己 home**——跨租户读/写由内核直接拒绝。
**结论**：✅ 已上线并验证。**且过程中发现「L1 会被历史遗留的 755/644 文件绕过」并一并收口**（这部分是本次最大的实际收益）。

## 三、🔴 过程中撞到的 4 个真问题（都不在计划内）

### 问题 1：`Popen(user=…)` 需要**调用者**有特权 ⇒ 网关起不来（企微断线）
- 现象：网关进程消失、企微断线、日志一条 `Operation not permitted`。
- 根因：`subprocess` 的 `user=`/`group=` 是在**子进程里**做 setuid，调用者（hergent）无权切换身份 ⇒ `EPERM`。
- 修法：改用 **sudo** 完成切换（sudoers 只允许切到**该租户自己的**账号）。

### 问题 2：`NoNewPrivileges=true` 让 sudo 完全不可用
- 报错：`The "no new privileges" flag is set, which prevents sudo from running as root.`
- 这个开关**同时**让 AmbientCapabilities 失效 ⇒ 加能力那条路也堵死。
- 修法：独立 drop-in 显式覆盖 `NoNewPrivileges=false`（**不动原沙箱文件**，回滚只需删我的文件）。见 §五代价。

### 问题 3：🕳️ **换属主后，后端 `chmod` 别人属主的文件会 EPERM**（差点变成"改完就崩"）
- 现象：`ensure_home()` 在 `.env` 上抛 `[Errno 1] Operation not permitted` ⇒ **网关起不来**（第二次断线）。
- 根因：`chmod` 需要**属主或 CAP_FOWNER**，同组成员**不够**（很容易误以为是权限不足=EACCES）。
- 修法：新增 `_try_chmod()`（失败不抛错，权限交给 root 侧归一器）＋把目标模式改成**对的那一档**：
  - `home`/子目录 → `2770`
  - `.env` → `0660`（**原来是 0600 ⇒ 会把租户自己锁在门外，读不到渠道凭证**）
  - `SOUL.md` → `0660`（**0600 会让体检自己读不到 ⇒ 误报漂移**）
  - `.erp_bot_token`/`auth.json` 保持 0600（后端不读它们）
- 顺带把 `gateway_stop` 改成**失败如实回报**（原来是无论杀没杀成功都报"已停止"）。

### 问题 4：**Hermes 会把自己的 home 硬化成 0700/0600**（显式 mode，不是 umask）
- 隔离试验账号实测：新建目录 `0700`、`channel_directory.json`/`gateway_state.json` **0600**（原子写 mkstemp 必然 0600）。
- 后果：属主变成租户后，**后端读不到** `gateway_state.json` / pairing 文件 ⇒ 「配对审批」「网关状态」会**静默变空**。
- 修法两层：
  1. 受支持开关 `HERMES_HOME_MODE=0770` + `HERMES_SKIP_CHMOD=1`（覆盖 `_secure_dir/_secure_file`）；实测 `_is_container()` 全仓只被 2 处使用 ⇒ 副作用可忽略；
  2. 剩余 mkstemp 路径（pairing）由**归一器每 2 分钟自愈**兜底。

## 三·五、顺带修掉一个"看着坏了其实没事"（既有缺陷）

**现象**：验收时 `gateway_status` 报 `企微: error`，但 `gateway_state.json` 写的是 `connected`、日志显示
`19:20:11 WebSocket error: WeCom websocket closed` → **`19:20:13 Reconnected`**（Hermes 自动重连，状态文件已写回 connected）。

**根因**：`_channel_log_error()` 用 `reversed(...)` 取**最新一条错误行** ⇒ 只要本轮出现过错误就报异常，
**不看后面有没有已恢复**。这是「看着坏了其实没事」，和「看着没事其实坏了」一样误导人。

**修法**：改成**按时间顺序扫，只认最后一条相关事件** —— 错误后若出现 `Reconnected` / `connected`
即视为已恢复（返回空）。

**反例对照（合成日志，验判据本身）**：
| 场景 | 期望 | 实测 |
|---|---|---|
| 只有错误 | 报错 | ✅ 报错 |
| 错误 → Reconnected | 不报错 | ✅ 无错 |
| 错误 → connected | 不报错 | ✅ 无错 |
| **恢复后又出错** | 报错 | ✅ 报错 |
| 连过 → 错 → 恢复 | 不报错 | ✅ 无错 |
| 只有 connected | 不报错 | ✅ 无错 |

修后线上：`state=running`、`企微=connected`、`last_error=''` ✅

## 五、代价与边界（诚实记录）

1. 🔴 **`NoNewPrivileges` 被关掉**（后端服务）：它是纵深防御的一层。关掉后本服务若被攻破，可使用系统其它 setuid 程序。**本服务能用的 sudo 面只有两条**（`tenant_kill.sh` 参数严格校验为纯数字；`hermes` 只允许切到租户自己的账号）。
   沙箱的其它保护（`ProtectHome` / `ProtectSystem` / `ReadWritePaths`）**保持不变**。
   📌 更彻底的做法（做完就能恢复这行）：让 systemd 以 transient unit + polkit 白名单拉起租户网关，后端不再需要 sudo。
2. 🟠 **sudo 父进程常驻（属 root）**：sudo 的固有行为（负责转发信号）。实测不影响 pid 识别（`_proc_pid_for_home` 用属主 uid 过滤掉了它）。
3. 🟠 **租户账号仍能"读"后端代码**：`/opt/hergent-erp` 是 `755`（`static/` 还要给 nginx 用）⇒ 可读代码但**不可写**。代码里没有机密（密钥在 0600 的 `.env`），风险低；要连读也断，需把 `static` 单独放开给 nginx。
4. 🟠 **pairing 文件有最长 2 分钟不可读窗口**：Hermes 用 mkstemp 写、必然 0600，等归一器下一轮修。影响面：刚申请配对后短时间内后台可能看不到（会自愈）。
5. ⚠️ **Web 端那条共享通道仍未隔离**：Web 副驾走**全局** Hermes（`api_server :18765`），**一份配置服务所有租户** ⇒ 客户在 Web 端仍是全权。这需要 **L3（每客户独立实例）**，仍是"开第二个客户"的前置条件。

## 六、回滚

**一键（零改码）**：在 `/opt/hergent-erp/.env` 写 `HERGENT_L1_ISOLATION=0` → 重启后端 ⇒ 立刻退回"所有租户共用 hergent 身份"。
（实测：`tenant_account(1) = None`、`_identity_kwargs(1) = []`，即不切身份、不用 sudo。）

**全量**：`bash /opt/hergent-erp/tools/l1_rollback.sh`（root）—— 顺序为：关开关 → 停 cron 自愈 → 撤 sudoers → 撤 drop-in → 租户 home 归还 hergent（先停网关，避免"进程是 hergent、文件属主却是租户"的混合状态）→ 重启后端 → 复验企微。
**账号不删**（便于再启用）：`userdel hergent_t1 && groupdel hergent_t1` 可彻底清掉。

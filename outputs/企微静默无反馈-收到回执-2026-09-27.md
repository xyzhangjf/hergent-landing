# 企业微信「发完消息像没收到」—— 补上「收到回执」（v281，2026-09-27）

> 老板报障：在企微给副驾发消息时**完全静默**，看不出有没有反应；其实收到了，稍后才回。

---

## 一、结论

**不是丢消息，是缺回执。** 根因在 Hermes 的企微适配器：

```python
# plugins/platforms/wecom/adapter.py
async def send_typing(self, chat_id: str, metadata=None) -> None:
    """WeCom does not expose typing indicators in this adapter."""
    del chat_id, metadata          # ← 空实现
```

而 Hermes **依赖这个方法**给用户"正在处理"的体感：`gateway/run.py` 多处
`await adapter.send_typing(source.chat_id, ...)`，配置项 `typing_indicator` 默认 **True**，
agent 跑工具期间靠它做 keep-typing 刷新。同类平台都实现了
（Telegram 53 处 / Slack 13 / Discord 25），**企微没有** ⇒ 你面对的是**设计缺口**，不是故障。
实测重查询（查铺市率 + 逐人名单）要等 **1~3 分钟**才有第一条回复，中间**零反馈**。

## 二、三条"更规矩"的路，都验证过走不通（省下以后重试）

| 想法 | 实测结论 |
|---|---|
| 用 **hooks**（`agent:start`）发回执 | context 只有 `platform/user_id/chat_id/session_id/message` 等**原始字段**，**拿不到适配器实例**；进程内也没有全局 runner 可引用 ⇒ **发不出消息**（且 `emit()` 会丢弃 handler 返回值） |
| 用**平台级配置**开关 | `gateway/config.py` 的 bridged 键清单里**没有**"回执/typing 文案"这类项（只有 `reply_prefix`、`notice_delivery`、`channel_prompts` 等） |
| 用 `hermes send` CLI | 面向 bot-token 类平台（Telegram/Discord/Slack…），**企微是 WebSocket 类**，不适用 |

## 三、做法：给 `send_typing` 打**幂等补丁** → 每条入站消息回一条回执

脚本：**`server/tools/hermes_wecom_ack_patch.py`**
（幂等 · 自带备份 `<file>.bak-hergent-<时间戳>` · 打完 `py_compile` 校验 · `--check` / `--revert` / `--text` / `--cooldown`）

关键设计（每条都有理由）：

| 设计 | 理由 |
|---|---|
| 用「该 chat **最近一条入站 `req_id`**」当**本轮键** | 适配器收到消息时已写 `self._last_chat_req_ids[chat_id]`（`_remember_chat_req_id`，**私聊与群都写**）⇒ 同一条消息的多次 keep-typing 刷新**只回执一次** |
| 再加**每 chat 冷却 20 秒** | 老板连着追问时不会连发多条回执 |
| 复用适配器自带的 **`send()`** | 它会优先用该 chat 的 req_id 走**回复通道**，拿不到才退化为主动推送 —— 群聊里企微**禁止**主动推送，走回复通道是必须的，这里天然正确 |
| 全程 **try/except** | 回执失败**绝不影响主流程**（宁可没有回执，也不能影响回答） |

**文案**（面向非技术老板，白话、无术语、无 emoji、无围栏符号）：
> 收到，我在查了 —— 数据多的时候要算一会儿，算完直接回你。

## 八、🆕 v2（2026-09-27 08:50）：改成企微**原生流式占位**（老板明确要求，**现行版本**）

老板反馈：**"不回文案也可以，企微可以用三个跳动的点代替，让用户知道这条消息发出去就可以了。"**
⇒ 上面 v1 的"回一条文本"会**多出一条消息**，不是他要的形态。已升级为 v2。

### 官方协议（已核对，别猜）
企微智能机器人长连接支持 `aibot_respond_msg` + `body.msgtype = "stream"`：

| 帧 | 效果 |
|---|---|
| 首帧 `{stream:{id, finish:false, content:"···"}}` | **立刻出现一条占位消息** |
| 同一 `req_id` + 同一 `stream.id` 再推（content 是**全量**、非增量） | **原位替换**该消息 |
| `finish:true` | 结束、不可再更新；**聊天记录里只保留最终结果** |

⇒ 一轮对话在企微里**只有一条消息**：先看到 `···`，随后被最终答案**原位替换**，
既给了"已收到"的反馈，又**不留两条记录**。（首帧到 finish 需在 10 分钟内；按 5 分钟安全线留余量。）

### 实现（同一个脚本，幂等，已支持 v1→v2 升级）
1. 把原有 `send()` **改名为 `_hergent_orig_send()`**（原实现一行未动）；
2. 插入三个方法：
   · `send_typing()` —— 首帧建流（占位 `···`），同一轮不重复建流；
   · `_hergent_finish_stream()` —— 用 `finish=true` 关闭该 chat 的活跃流；
   · 新 `send()` —— **收口**：有活跃占位且内容是文本 ⇒ 把**最终答案原位上屏**；
     否则先关占位，再委托 `_hergent_orig_send`（cron 推送 / 媒体回退 / 错误兜底 一律不变）。

**为什么必须"改名 + 委托"而不能 `super().send()`**：基类 `gateway/platforms/base.py` 里也有一个
`send()`，`super()` 会调到**基类实现**而不是企微自己的 ⇒ 会静默丢掉 markdown 发送、错误处理与 `SendResult`。

**投递路径已确认**：`gateway/delivery.py` 走 `adapter.send(chat_id, content, metadata=...)` ⇒ 拦截点正确；
建流前提 `_last_chat_req_ids[chat_id]`（入站回调 req_id，**私聊也写**）也确认存在。

### 验收
- **离线自测全绿**（对副本 + 导入真模块），覆盖**两条路径**：
  **A 上游原版 → v2**、**B 生产现状 v1 → v2（本次真正走的升级路径）**；
  外加 20+ 条协议断言：首帧 `stream`/`finish=False`/`content='···'`/带 `id` 与 `req_id`、
  同轮刷新不重复建流、换消息先关旧流再建新流、**最终答案用同一 `stream.id` + finish + 全量内容**、
  无活跃流时委托原实现、空内容不误吞、异常不外抛、无 req_id 安全返回。
- **生产已升级**：v2 标记在位 · v1 文本回执清零 · 原名已改 `_hergent_orig_send` ·
  `py_compile` 通过 · `--check` = 在位 ✅。
- **网关重启后日志干净**：适配器加载正常、`✓ wecom connected`、零 error/traceback。

### 🔴 打补丁过程中踩的坑（已写进技能）
断言 `send() 签名出现 1 次` 原本放在**替换之后**，而新插入的 `send()` 自己就带同样的签名
⇒ 被数成 2 次、误判"形态不符、拒绝改"。**正确顺序：先改名、再插块**。
（所有文本改写都在内存完成、最后一次落盘 ⇒ 中途失败不留半成品。）

### 边界（显式声明）
- 只拦**文本最终答案**；图片/文件走 `send_image`/`send_document` 不在拦截范围 ——
  那种情况占位由企微 10 分钟后自动结束（极少见），且**下一条消息进来时会先关掉残留占位**。
- 拿不到回调 `req_id` 时不建流（安全返回）；占位/收口失败**绝不影响主流程**。

⏳ **真机端到端仍待一条真实企微消息**：达标形态 = 你先看到一条 `···`，随后它**原地变成**答案
（聊天记录里只有一条）；日志会出现
`[Wecom][HERGENT-PATCH wecom-ack-v2] 已建流式占位` 与 `占位已原位替换为最终答案`。

## 九、⚠️ 处置过程中的事故（**已修复**）：重启租户网关把**模型密钥**弄丢了

老板截图里那条 `⚠️ Provider authentication failed` 就是它 —— **根因是我自己的操作失误**，如实记录。

### 现象与诊断链
| 步骤 | 结论 |
|---|---|
| 猜"余额耗尽" | ❌ **不是**：直连 DeepSeek 查余额 = `5.46 元`、`is_available: true`、最小请求 **200** |
| 查租户 `.env` | 里面**只有企微凭证**（`WECOM_*`），**没有**模型密钥 |
| 查租户凭据池 `auth.json` | 条目本身健康：`last_status: ok`，来源 `source: env:DEEPSEEK_API_KEY`，**不内嵌密钥值** ⇒ 密钥必须来自**进程环境** |
| 对比进程环境 | 后端进程 `DEEPSEEK_API_KEY` = **1**；**租户网关进程 = 0** |
| 看 spawn 代码 | `env = _env_head()`，而 `_env_head() = dict(os.environ)` 减去平台凭证 ⇒ **继承"调用者"的环境** |

### 根因（我的错）
我用**临时 SSH 命令**重启租户网关：

```bash
ssh … 'runuser -u hergent -- python3 -c "import hermes_tenants as ht; ht.gateway_restart(1)"'
```

这条命令的环境是**我的 shell 环境**（没有 `DEEPSEEK_API_KEY`——它只在后端服务的
`EnvironmentFile=/opt/hergent-erp/.env` 里）⇒ `_env_head()` 把这个"干净环境"传给了网关
⇒ 我 08:39 起的每次重启，都把租户网关拉成了**没有模型密钥**的状态（08:51 开始报
`No usable credentials found for provider 'deepseek'`）。
**昨天之所以正常**，是因为那个网关进程是**后端服务**拉起来的（服务环境里有密钥）。

### 修复
1. `pkill -f "hermes gateway run --force"`（杀掉无密钥的那个）；
2. `systemctl restart hergent-erp` ⇒ 服务启动时的保活**用正确环境**重新拉起网关；
3. 复验：新进程 `DEEPSEEK_API_KEY` = **1** ✅、`HERMES_HOME` 正确、企微 `connected` ✅；
4. 模型链路单测（用与服务同口径的环境跑租户 agent）→ 正常返回「收到」✅；
5. ⚠️ **诚实边界**：重启时租户日志被**截断**（`agent.log` 尺寸/mtime 都变成 08:59，并带 `.mark` 读偏移文件）
   ⇒ **不能**拿"日志里没有报错"当证据。本次的判据是：**新进程环境有密钥** + **单测正常返回**。
   最终的端到端确认，仍要靠**下一条真实企微消息**。

> 注：`pkill` 只杀 `--force` 的租户网关；全局网关是 `hermes gateway run`（无 `--force`），不受影响。
> 另外后端当时**没有**任何 `/api/ai/*` 的「重启租户网关」HTTP 端点 ⇒ 只能走"服务保活"这条路。

### 🔴 铁律（已写进技能）

**绝不能从临时 SSH/shell 命令里调 `gateway_restart()`** —— 那会把网关拉成没有模型密钥的状态。

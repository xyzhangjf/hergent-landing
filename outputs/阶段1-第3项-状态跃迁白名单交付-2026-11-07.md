## 二、收口前的真实状况

### 2.1 不是「一套状态机」，是**三套互不相认**

| # | 状态机 | 写哪里 | 词表 | 生产数据 | 前端是否读 |
|---|---|---|---|---|:--:|
| ① | 业务表 `status` | `sale_orders` / `purchase_orders` 等 | `draft/pending_approval/approved/confirmed/picking/delivered/signed/…` | 22,506 + 742 行 | ✅ 真正在读 |
| ② | `db/queries/approvals.py` | **也写业务表** `status` | 同上，但自己判 `status != 'draft'` | `approval_flows` 4 条流程 | ✅ 间接 |
| ③ | `erp_db.doc_state_set()` | `document_states` **影子表** | `draft/submitted/in_approval/approved/rejected/returned/executed/voided` | **0 行** | ❌ 没人读 |

第 ③ 套最典型：它**有**白名单（`VALID_STATES`）、**有**校验，但校验的是另一张表，业务表的 `status`
一行都没动，报错还是英文 `Invalid state transition: draft -> approved`。**看起来有状态机，实际没有拦截面。**

### 2.2 写入口的守卫状况（精确扫描，已排除 `delivery_status` 等字段）

| 单据表 | 状态写入点 | 收口前带来源守卫 | 生产实际取值 |
|---|:--:|:--:|---|
| `sale_orders` | 12 | **0** | `signed` 22,505 / `draft` 1 |
| `purchase_orders` | 8 | 3（手写 `IN (...)`） | `received` 738 / `draft` 2 / `cancelled` 1 / `confirmed` 1 |
| `transfer_orders` | 1 | 0 | `draft` 1 |
| `purchase_returns` | 2 | 0（新建即过账） | 0 行 |
| `return_orders` | 5 | 0 | 0 行 |

> 🔴 盘点时踩过一个坑：全仓按 `status=` 扫，会把 `delivery_status='assigned'`、
> `invoice_status='invoiced'` 一起抓进来，凭空给销售单造出 `assigned`/`invoiced` 两个
> **根本不存在的 `status` 值**。正则必须是 `(?<![_A-Za-z])status`。

### 2.3 生产 DDL：只有调拨单带 CHECK

| 表 | `status` 定义 | CHECK |
|---|---|:--:|
| `sale_orders` / `purchase_orders` / `purchase_returns` / `return_orders` | `TEXT DEFAULT 'draft'`（退货单默认 `'confirmed'`） | ❌ 无 |
| `transfer_orders` | `TEXT DEFAULT 'draft' CHECK(status IN ('draft','pending_approval','approved','completed','cancelled'))` | ✅ 有 |

→ 所以词表必须**逐字**等于调拨单的 CHECK 集合，否则会出现「白名单放行、DDL 拒绝」的割裂。
这条已写成判据（A2 段）。

## 三、白名单（唯一源）

`db/queries/doc_state.py` 登记 5 类单据。**`from` 集合全部来自生产代码逐处抽取**，
不是照 ERPNext 理想状态图抄的 —— 抄理想图会当场拦死正常业务（反例见 3.1）。

| 单据 | 状态 | 终态 |
|---|---|---|
| 采购单 | 草稿 / 待审批 / 审批通过 / 已确认 / 部分入库 / 已入库 / 已退货 / 已作废 | 已退货、已作废 |
| 销售单 | 草稿 / 待审批 / 审批通过 / 已确认 / 拣货中 / 已发货 / 已签收 / 已驳回 / 已作废 | 已作废 |
| 调拨单 | 草稿 / 待审批 / 审批通过 / 已完成 / 已作废 | 已完成、已作废 |
| 采购退货单 | 草稿 / 待审批 / 审批通过 / 已过账 / 已作废 | 已过账、已作废 |
| 销售退货单 | 草稿 / 待审批 / 审批通过 / 已确认 / 已处置 / 已退款 / 已驳回 / 已作废 | 已退款、已作废 |

### 3.1 两条「看着该拦、其实必须放行」的边

| 边 | 为什么必须放行 | 如果拦了会怎样 |
|---|---|---|
| 销售单 `已签收 → 已作废` | AI 回滚 / 红冲要撤掉一张已签收单，是**真实业务** | 红冲功能整体失效，只能去库房手改 |
| 调拨单 `草稿 → 已完成` | 现有代码（无审批流时）直接落 `completed` | 调拨单一律做不完 |

> 计划文档举的非法例子是「草稿→已完成」。在调拨单上这条**是合法的**。
> 验收里改用「销售单 草稿→已签收」演示非法，并专门留了一条判据守住调拨单这条边不被误删。

### 3.2 派生 `docstatus`

| 值 | 含义 | 覆盖状态 |
|:--:|---|---|
| 0 | 草稿（可编辑） | `draft` / `pending_approval` / `rejected` |
| 1 | 已提交 | `approved` / `confirmed` / `picking` / `delivered` / `signed` / `partial` / `received` / `dispositioned` / `refunded` / `returned` / `completed` |
| 2 | 已取消 | `cancelled` / `voided` |

**未知状态码不猜成 0** —— 猜成 0 会让脏数据被当成「可编辑草稿」，正是脏状态的入口。
（阶段 2 加物理列时，回填口径必须与本函数逐条一致。）

## 四、改了什么

### 4.1 新增

**`db/queries/doc_state.py`（约 330 行）** —— 唯一源，四个能力：

- `status_label()` / `docstatus_of()` / `allowed_targets()` / `allowed_sources()`
- `check_transition()` —— 非法抛 `IllegalTransition`，`str(e)` 就是给用户看的那句话

  并发抢不到就报「刚被其他人改成 X」，不静默覆盖

### 4.3 两处「人工比系统更严」刻意保留

| 入口 | 系统白名单 | 人工入口 | 为什么 |
|---|---|---|---|
| 采购单作废 | 允许 `received/partial → cancelled`（AI 回滚通道） | 只允许 `draft/pending_approval/confirmed` | 人工作废一张已入库单会让库存与应付凭空消失，必须走采购退货 |
| 销售单取消 | 允许 `signed → cancelled`（AI 回滚通道） | 只允许 `draft/confirmed/pending_approval` | 已签收意味着货已交付、AR 已生成，必须走销售退货 |

两处的分工都写进了代码注释，避免以后有人「统一一下」把它放宽。

## 六、顺带修掉的 7 个既有缺陷

| # | 位置 | 缺陷 | 后果 |
|:--:|---|---|---|
| 1 | `sale_order_deliver` | 守卫写死 `IN ('draft','confirmed','approved')`，**漏 `picking`**；`server.py` 路由层又漏一次 | 一旦进了拣货，这张单**永远发不出货**，提示还是「只有草稿或已确认才能发货」 |
| 2 | `purchase_order_confirm` | 注释写「状态守卫只放 draft\|approved」，**SQL 里根本没有 WHERE status** | 校验与写入之间隔着整段入库，并发可重复收一次货 |
| 3 | `purchase_order_partial_receive` | 失败只返回两个字「状态错误」 | 分批到货失败时用户完全无从下手 |
| 4 | `server.py` AI 动作 | `approve` / `reject` 裸写 `SET status=… WHERE id=?` | **AI 能把已签收、甚至已作废的单改成「已确认」**，库存不动、AR 不动，零报错 |
| 5 | `ship_packed` | 裸写 delivered，且**先改装箱单再改销售单** | 销售单该拦时，装箱单已被标 `shipped`（半截状态） |
| 6 | `rma_refund_create` | 裸写 refunded，只靠幂等键挡重复 | 换个 key 或前端重试就**退第二次款**，并写出第二条 `cash_flow` |
| 7 | `rma_authorize` / `return_disposition_create` | 裸写 rejected / dispositioned | 已退款的单还能被「驳回」、还能再「处置」——后者 `restock` 会**二次回增库存** |

外加：影子状态机的英文报错、4 处「提示里只有英文状态码」的用户可见文案。

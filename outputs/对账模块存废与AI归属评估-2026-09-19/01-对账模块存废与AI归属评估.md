# 对账模块存废与 AI 归属评估

> 评估对象：侧栏「**对账工作流**」模块（`/reconciliation`）
> 评估日期：2026-09-19 ｜ 全部结论附生产实测证据
> ⚠️ 你原话说的「对账工资流」是侧栏里**相邻两项的合成**：实际是「**对账工作流**」（`/reconciliation`）
> 与「**算工资**」（`/payroll`）两个独立条目，不是一个模块。本评估只针对前者。

---

## 一、结论（先行）

**1. 现在这个页面：移除。** 不是因为它"做成了系统功能"，而是因为**它没有在做事**。

**2. "对账"这件事：必须保留，而且要重做。** 它是真需求，但它现在的形态解决不了它。

**3. 你设想的「AI 比对 + 人工确认」方向是对的，但有一处要改：**

> 🔴 **不要让 AI 去比对。** 让 AI 做**「把不同格式的对账单变成能比对的形状」**，比对交给确定性算子。
> 让模型去做算术，是把它放在它最弱的地方 —— 对账算错是要赔钱的。

**4. 划分依据一句话**（可直接进 BP）：

> **格式识别是"算不出答案的地方"（给 AI）；金额比对是"不能算错的地方"（给确定性代码）；
> 确认与改数是"责任所在"（给人）。**

这跟你已经定下的那句产品主张**完全同构**：「我们把 AI 放在算不出答案的地方，把确定性放在不能算错的地方。」
对账恰好同时踩在两边 —— 这就是它的划分依据，不是权宜之计。

## 二、这个模块现在到底是什么（读代码得出）

| 层 | 实现 | 真实内容 |
|---|---|---|
| 前端 | `Reconciliation.vue`（369 行） | 三步向导：① 欠款客户列表 → ② 看该客户销售单+收款 → ③ **手工输入"客户声称金额"** → 显示两数之差 → 确认 |
| 后端 | `routers/reconciliation.py`（247 行） | 6 个接口：供应商侧 3 个 + 客户侧 3 个 |
| 页面下半 | 复用 `collections.py` | 「催收跟进」队列（**与对账无关，是另一个模块**） |

### 🔴 关键：它的"对账"核心动作是一个减法

客户侧匹配（`reconciliation.py:218`）：

```python
system_total = sum(i['amount'] for i in items)        # 销售单总额 - 收款总额
difference = round(statement_amount - system_total, 2) # 对方报的数 - 系统数
```

**这就是一个减法器。** 它回答的是"两个总数差多少"，**没有回答"哪一笔对不上"** ——
而对账的全部价值恰恰在"哪一笔"。用计算器相减能得到同样的信息量。

供应商侧匹配（`:96-106`）更严重：

```python
if abs(unmatched_total - amt) <= tolerance:  ...'matched'; unmatched_total -= amt
elif abs(unmatched_total) >= amt:            ...'matched'; unmatched_total -= amt   # 🔴
else:                                        ...'partial'; unmatched_total -= amt
```

- 三个分支**对 `unmatched_total` 的操作完全相同** ⇒ 这个 if/elif/else 唯一作用是**贴标签**
- 第二个分支的语义是错的：**"剩余金额 ≥ 这一项"就标"已匹配"**
- 它没有按单号、按日期、按任何业务键去对应 —— 它只是"从头往下减到 0"

**一个 100% 的差异，纯粹由系统自己造成，与客户无关。**

**这不是"没人用"，这是"用了会给出错误答案"。** 两者的处置完全不同。

## 五、为什么这类对账难以做成系统功能（四条可验证的理由）

> 注意：**不是"做不到"，而是"做成固定规则后，会静默算出一个看似合理的错误答案"**。
> 对财务场景，后者比报错更危险。

### ① 格式由**外部**决定，你无权要求对方改
厂家对账单是从**对方的 ERP** 导出的，格式由对方系统决定。这不是有限枚举 —— 每换一个厂家、
厂家每升一次级，就是一个新格式。**每加一个格式就加一个适配器**，维护成本线性增长，
收益只覆盖那一家。这是本次评估里最本质的一条。

### ② 三类场景**难度根本不同**，不能用一个算法覆盖

| 场景 | 两边有共同键吗 | 难度 |
|---|---|---|
| 下游客户对账 | **有** —— 订单号 / 客户名 | 低（现有 `match` 算子直接能用） |
| 上游厂家对账 | **部分** —— 厂家常按"品类 / 期间"汇总，你系统里是"逐单" | 中（**粒度不一致**，需先归到同一粒度） |
| 银行流水对账 | **没有** —— 只有摘要 + 对方户名 + 金额 + 日期 | **高**（必须模糊匹配，见下） |

**银行流水是三个里最难的**：一笔转账可能是"付给 A、B 两家的合款"，
摘要写"货款"，金额对不上任何单一单据 —— 这类**多对一 / 一对多**的匹配，
"按 key 匹配"这个算法**根本不适用**，必须组合判断（金额 + 日期窗口 + 对方名近似）。

### ③ 口径差异是**业务约定**，不是 bug
同一笔货：厂家按**发货日**记，你按**到货日**记；含税 / 不含税；返利是**抵货款**还是**单独结算**。
这些是双方谈判定下来的东西，**写死在代码里必然是错的**，而且改起来要改代码、要发版。

### ④ 一改就错，错了看不出来
硬编码规则遇到没见过的新格式，**不会报错**，会算出一个看着像样的数字。
财务上这意味着**照着错的差异去调账**。

## 六、AI / 确定性代码 / 人 —— 逐环节归属

> 这是本文档的核心。**"对账"不是一个动作，是六个环节**，每个环节的归属不同。

| # | 环节 | 归属 | 判据 |
|---|---|---|---|
| 1 | **认列**（这列是"金额"还是"数量"？表头在哪行？） | 🟢 **AI** | 列名千变万化、无固定词表，是语言问题不是计算问题。现存 `smart-parse` 用**关键词规则**做这件事，换成模型更稳 |
| 2 | **定键**（拿什么当匹配依据？） | 🟢 **AI 提议 + 人点头** | AI 说"建议按订单号 + 日期匹配"，人确认。**不能自动执行**——键选错，后面全错 |
| 3 | **比对**（逐笔找差异） | 🔴 **确定性代码** | **不能算错的地方**。已有写对的实现，见 §6.1 |
| 4 | **归因**（这 23 笔差异是什么原因？） | 🟢 **AI 最该干的活** | "18 笔是运费没冲、5 笔是退货未入账" —— 这一步人要做一小时，且**这是唯一靠算算不出来的** |
| 5 | **确认** | 🔴 **人** | 财务责任，不可代签 |
| 6 | **改数据**（按差异录单/调账） | 🔴 **人**（AI 可代填草稿） | 与既定铁律一致：**AI 工具全部只读**，"AI 能写财务数据"是风险不是卖点 |

### 6.1 🔴 最重要的一条：差异比对**已经在系统里写对了**，而且只有 40 行

`server/spreadsheet_query.py` 的 `_run_query(op="match")` —— 这是**已经存在、逻辑正确**的两表对账算子：

```python
# 按 key 建索引，双向差集 + 同键金额不符
ia, ib = _index(da), _index(db_table)
for k, rs in ia.items():
    if k not in ib:            only_a.extend(rs)        # 只在对方表里有
    else:
        va = sum(...); vb = sum(...)
        if abs(va - vb) > 0.001:
            mismatch.append({"key": k, "a": va, "b": vb}) # 同键金额不符
for k in ib:
    if k not in ia:            only_b.extend(ib[k])     # 只在我方表里有
```

它输出：`only_in_a` / `only_in_b` / `mismatch`（逐 key 双向差集 + 同键金额不符）。

**这直接证明了一件事**：

> **"比对"本身不难做成系统功能 —— 难的是"把两边数据弄成能比对的样子"。**

而现在那个「对账工作流」，恰恰**跳过了"弄成能比对的样子"（第 1、2 环节），
也跳过了"逐笔比对"（第 3 环节），只做了第 5 环节的一个空壳**（一个输入框 + 一次确认）。

**它的失败不在"做成了系统功能"，在"做错了层"。**

### 6.2 给 AI 这条路，底座已经铺好了（不是从零开始）

| 已有能力 | 位置 | 状态 |
|---|---|---|
| 上传对账单（xlsx/csv/图片/PDF） | `chat_attachment.py`（262 行） | ✅ 可用（解析全 sheet 转文本，上限 14,000 字符） |
| **在附件上做计算** | `/api/chat/attachment/query` | ✅ 可用 |
| **两表按 key 匹配对账** | `spreadsheet_query._run_query(op="match")` | ✅ **已实现且正确** |
| 丢文件自动识别类型 | `/api/import/smart-parse` | ✅ 可用（识别"应收/对账单/支付宝/微信"）——但**是关键词规则，不是 AI** |
| AI 读系统数据 | `ai_tools.py` 11 个只读工具 | ⚠️ 有 `tool_ar_aging`（账龄**汇总**），**缺逐笔应收/应付明细工具** |
| Hermes 对账卡片协议 | `hermes_core.py`：`"type":"reconcile"` | ⚠️ **协议已定义，从未被使用** |

⇒ **"AI 比对 + 人工确认"不是设想，是"把已有零件接起来"**：
附件通道 ✅ + 匹配算子 ✅ + 卡片协议 ✅ + 只读数据工具（缺 1 个）。

### 7.2 对账重做成什么形态

```
上传对账单 ──▶ AI 认列 + 提议匹配键 ──▶ 人确认键 ──▶ 确定性算子比对 ──▶ AI 归因 ──▶ 人确认 ──▶ 人改数据
   (任意格式)      (环节1-2)            (环节2)      (环节3, 已有)      (环节4)     (环节5)   (环节6)
```

**三个场景三个入口，不要挤在同一个页面**：

| 场景 | 建议落点 | 理由 |
|---|---|---|
| 上游厂家对账 | 挂在**采购 / 目标与返利**侧 | 对的是"我欠厂家多少、厂家返我多少" |
| 下游客户对账 | 挂在**应收 / 催收**侧 | 对的是"客户欠我多少" |
| 银行流水对账 | 挂在**能力中心**的导入通道 | 本质是"导入 + 匹配"，没有独立业务对象 |

### 7.3 划分依据（三条，可复用）

1. **算得出唯一正确答案的 → 确定性代码**（金额比对、双向差集）
2. **答案依赖语义理解、且允许"提议"的 → AI**（认列、定键、归因）
3. **产生责任或改变账面的 → 人**（确认、改数）

判据一句话：**看错了谁承担后果。** 承担后果的是人，就不许 AI 直接做。

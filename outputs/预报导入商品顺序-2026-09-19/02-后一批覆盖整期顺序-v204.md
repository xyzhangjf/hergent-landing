# v204：后一批直接覆盖整期顺序

> 交付日期：2026-09-19 ｜ 编号：**v204**（本序列 v201 → v202 → **v204**；v203 属同日另一会话）
> 触发：用户在 v202 交付说明的「多批导入的边界」里二选一，拍板原话 —— **「后一批直接覆盖整期顺序」**

---

## 一、结论（一句话）

**改对了，已上线。** 同一期次再导一次，**整期顺序立刻以这一批的模板序为准** ——
本批商品占据整期最前面，其余商品保持原有相对顺序接在其后，全期收敛成连续的 1..M。

验证：**离线 42/42 · 真机 20/20**（真实 HTTP + 生产克隆库 + 154 行存量数据）。

---

## 二、语义（这就是我实现的口径，请核对）

| 场景 | 结果 |
|---|---|
| 单次导入一份模板 | 整期顺序 **完全等于** 模板行序（与 v202 行为一致，没有变化） |
| **再导一份模板（同批商品）** | 本批按**新模板**的行序占据整期 1..N；上一批的商品整体退到其后（保持它们之间的相对顺序） |
| 再导一次**同一份**模板 | 顺序不变（幂等，`sort_no` 不做累加） |
| 导入只有几个商品的**补录**文件 | ⚠️ **这几个商品会跑到最前 1..k**，其余商品整体后移 — 见 §五「边界」 |
| 从上一期复制来的清单 | 保持在「导入批」之后（导入 = 最新动作，复制 = 基础清单） |

**v202 与 v204 的唯一差别**：
- v202 = 累加（后一批**接在**前一批后面，靠 10 万行号跨度分隔）
- **v204 = 覆盖（后一批从第 1 位开始重新定义整期顺序）** ← 你要的那个

## 三、改了什么（纯后端逻辑，**无 DDL、无迁移、前端不动**）

### 3.1 `server/routers/import_router.py`

| 位置 | 改动 |
|---|---|
| 模块级常量 | **删掉 `_BATCH_SPAN = 100000`**，原位换成 v202→v204 的语义演进说明 |
| 登记写入段 | 删掉「取本期 `MAX(sort_no)` → 算批次基准」那段；`_sno` 改为**临时值** = 模板行号 |
| 登记写入段末尾 | **新增「整期重排」**（本次核心）：查回期内在册行的当前顺序（**与读端 SQL 逐字同口径**）→ 组 `_seq` = 本批（按模板行号升序）+ 其余（原相对顺序）→ `executemany` 落连续 `1..M` |
| 重排前 | 加**两行局部前置断言** `if _period_id <= 0: raise` —— 重排是 `WHERE period_id=?` 的**全集覆盖**，防误伤生产的 20 条 `period_id=0` 孤儿行 |

**三个刻意的设计选择（都有理由，不是随手写的）：**

1. **为什么不只重写本批那几行？**
   本批行号直接落 `1..N` 会与往期批次的 `1..M` **同值冲突** ⇒ 读端 `ORDER BY sort_no` 只能退化成 `r.id` 兜底 ⇒ 两批在数值区间上互相交错 —— 正是这套排序键要消灭的东西。整期重排后全期是**连续 1..M**，既无同值也无重叠，tiebreaker 永远用不上。

2. **「同一商品在模板出现两行」取哪一次的行号？**
   取**最后一次**（`_batch_map[pid] = rn` 后者覆盖前者）。理由：必须与写入循环的落值规则**逐字一致**（循环也是逐行推进、后者覆盖前者）。两处若分叉，症状是「改了模板行序、页面只动了一部分」。

3. **`UPDATE ... sort_no=?` 那一句为什么没删？**
   v204 起它的值会被整期重排覆盖，但保留为**纵深防御**：万一下面的重排因故未执行（异常被外层 `except` 吞掉），至少本批行的值不是「无顺序信息」的 0。

### 3.2 `server/erp_db.py`（**只改注释，零逻辑**）

`v202_forecast_import_sort_no` 迁移上方的「列语义」段更新为 v204 覆盖式，并明确写出
「`_BATCH_SPAN` 这个常量**已不存在**，不要再按它理解本列的值域」—— 否则下一个人会照旧注释去猜值域。

### 3.3 前端：**一行未改**

读端（`Forecast.vue` 的 `buildRowBase`）本来就是「有 `sort_no` 用 `sort_no`、没有用数组下标、不在表内排最后」三档。
v204 让**全期都落到第一档**，三档逻辑照常成立 ⇒ 无需重建产物、无需重新部署前端。

### 4.1 ② 为什么用「源码切片」而不是复刻算法

v202 那一轮吃过亏：**复刻实现会与源码漂移，测过的绿不代表线上绿**。
本次改为：从 `import_router.py` **原文件按行号切出**「登记写入 + 整期重排」整段，
`textwrap.dedent` 后 `exec` 进**内存 SQLite**，喂真实 `_reg_rows` —— 被测的就是即将上线的那些字节。

覆盖的 42 项里，行为断言分 8 组：单批 / 部分批（补录）/ 全量倒序 / 幂等 / 存量 `sort_no=0` /
同商品多行 / **跨期隔离** / **存量是 v202 累加值（100001+）**。

> ⚠️ 本轮自己踩的两个**夹具**错误（都不是实现的错，记录备查）：
> ① 内存表漏了 `UNIQUE(period_id, product_id)` ⇒ `INSERT OR IGNORE` 变普通 INSERT ⇒
>    读到 `[1539,1539,1455,1455]` 重复行，**看起来像实现有 bug**；
> ② 「同商品多行」的断言方向写反了 —— last-wins 意味着它排在本批**最后**，不是最前。
>    **实现是对的、断言是错的，症状与真 bug 一模一样**（与 v202 那次「用错列断言」同族）。

### 4.2 ⑤ 真机 E2E 怎么做的

沙箱 `tenant_9999` 克隆自**生产 tenant_1**（真实 154 行存量），全部走真实 HTTP：

```
POST /api/import/preview          （真解析）
POST /api/import/execute          （真落库）
GET  /api/forecast-submissions/summary?period_id=14   ← **读端**，imported_products 的顺序即页面行底
```

三批导入（批 1 = 6 个商品；批 2 = 另 3 个**补录型**；批 3 = 批 1 的同批商品**倒序**），每批后查三条轴：
**A** 本批居最前且顺序 == 模板行序 ｜ **B** 其余保持上一轮相对顺序 ｜ **C** `sort_no` 收敛为连续 1..M。

## 五、⚠️ 边界：**补录型**导入（请确认这是你要的）

按「覆盖」语义，**导入一件只含少数商品的补录文件，也会把这几个商品推到最前**，
其余商品整体后移（它们之间的相对顺序不变）。

- 若你要的就是这个 —— 那现在就对，无需再动。
- 若你其实想要「**补录不动已有顺序，新商品插到末尾**」—— 那是**第三种口径**，
  说一声，改动同样是 `import_router.py` 里那一段（把 `_seq` 的拼接顺序反过来）。

# 预报导入商品顺序一致性 —— 排查与修复报告

> 用户诉求原话（2026-09-19）：
> 「我注意到预报订单模板导入后，系统中显示的商品名称排序与导入模板中的商品名称排序不一致。
> 请调整系统逻辑，使导入后系统中的商品名称排列顺序与导入模板中的商品名称顺序完全保持一致，
> 不受其他排序规则影响。」
>
> 代号 **v202** ｜ 状态：**已修复并上线**（前后端 + 真机验证）

---

## 一、结论（先讲结论）

**用户描述属实，且这是一个「设计缺口」而不是「排序参数配错了」。**

系统此前**从未记录过「商品在模板里的顺序」** —— 导入只落了「有哪些商品」（`forecast_import_products`
按 `(period_id, product_id)` 幂等登记），**没有落它们的先后**。于是读端只能自己发明一套顺序，
而它发明的那套与用户排模板时的意图无关。**缺的是数据，不是排序规则** —— 所以任何「调一下排序」
的修法都治不了本。

修法是给顺序一个**持久化载体**（登记表新增 `sort_no`），并让读端以它为唯一权威。

---

## 二、根因：读端的两套顺序都跟模板无关

行底（表格要显示哪些商品、以什么次序）由前端的 `buildRowBase()` 决定，它有两个来源，
**两个来源各自带一套与模板无关的顺序**：

| 来源 | 接口 / 位置 | 它自带的顺序 | 后果 |
|---|---|---|---|
| **在售商品档案** | `GET /api/products/grid` → `db.product_list` | **`ORDER BY id DESC`**（`db/queries/products.py:392`） | 顺序 = **建档顺序倒排**。模板最后一行若是新商品，它反而顶到最前；模板第一行若是老商品，就沉到末尾 |
| **档案外的本期行** | `refIds`（一个 `Set`）的插入顺序 | 与模板无关 | 同上 |
| （本次未用，但同族） | `summary.rows` | **`ORDER BY total_qty DESC`**（报得多的在前） | 审核页侧的顺序，同样与模板无关 |

而前端 `sortedRows` 在默认状态（`sortKey='none'`）下**原样透传**行底顺序
⇒ 页面**逐行**复现了上面那个错序。

### 实证复现（生产库 tenant_1，期次 9，154 个导入商品）

| | 第一名商品 |
|---|---|
| **导入登记序**（= 用户模板序） | `蒙牛红枣酸牛奶1000g*10桶`（pid **1475**） |
| **页面实际序**（`products.id DESC`） | `简爱酸奶吸吸乐黄皮百香果味100克x40袋（通路版）`（pid **1608**） |

**恰好相反。** 模板的第一行掉到了最后一行。

### 旁证：登记序确实就是模板序

期次 9 与期次 13 的登记序（按 `forecast_import_products.id` 升序取 `product_id`）
**154 行逐行完全相同** —— 同一份模板导两次，落库顺序稳定复现。而期次 14 是另一次
（顺序不同）的导入。这条旁证同时说明：**`r.id` 升序可以当作存量期次的兜底顺序**（见 §五）。

## 三、修法

### 3.1 后端：给顺序一个持久化载体

| # | 文件 | 改动 |
|---|---|---|
| 1 | `erp_db.py` | `forecast_import_products` 新增 `sort_no INTEGER DEFAULT 0`；**两处**补列：`init_db` 的 `v202_forecast_import_sort_no` 迁移 + `_ensure_forecast_tables` 的惰性 `ALTER`（`CREATE TABLE IF NOT EXISTS` 不给已存在的表补列） |
| 2 | `routers/import_router.py` | 导入时记录**模板行号**（`enumerate(data_rows, 1)`）；写入 `sort_no = 批次基准 + 行号`；**`INSERT` 与 `UPDATE` 两条语句都写** |
| 3 | `erp_db.py` | `summary` 的 `imported_products` 下发 `sort_no`，并按 `(有无 sort_no, sort_no, r.id)` 排序 |
| 4 | `erp_db.py` | `_period_copy_products`（复制期次 / 从上一期填清单）一并带 `sort_no` |

**值语义：`sort_no` 不是行号，而是排序键 = 批次基准 + 模板行号。**

```
_batch_base = (本期已有 max(sort_no) // 100000 + 1) * 100000
sort_no     = _batch_base + 模板行号
```

**为什么需要批次基准**：只用行号（1..N）的话，**第二次导入**的行号 1..M 会与第一次的 1..N
互相交错 —— 「先导一批常规品、再导一批新品」本该是「一批在前、一批在后」，交错却是乱序。
加了基准后，本次导入的所有行（含被覆盖的旧行）都落到同一个更大的基准上，
**「一批」在顺序上是一个整体，批内严格按模板行序**。

**为什么 `UPDATE` 也必须写 `sort_no`**：`INSERT OR IGNORE` 在行已存在时整条跳过。
只写 INSERT 的话，「重新导入同一份模板」时老行会保留上一次的 `sort_no`
⇒ **改了模板行序却看不到变化**。这是本列必须「每次导入覆盖」而非「只在新建时写」的原因。

### 3.2 前端：行底按导入序重排

`Forecast.vue::buildRowBase()` 末尾加一段排序，**三档顺序键**：

| 档 | 含义 | 次序取值 |
|---|---|---|
| `t = 0` | 有 `sort_no`（v202 之后导入的） | `sort_no` |
| `t = 1` | 无 `sort_no` 但在 `importedProducts` 里（**存量期次**） | 数组下标（= 后端 `ORDER BY r.id` 的登记插入序） |
| 不在表内 | 小程序报单 / 手工新增 | 排在最后（它们是**另一份清单**，插进模板行之间会把模板序切碎） |

`Array.prototype.sort` 在现代 JS 引擎是**稳定**的 ⇒ 「不在表内」那批的原有相对顺序得以保留。

### 3.3 顺带修掉一个既有缺陷

`applySort()` 的 `none` 分支此前**什么都不做**（只处理 `asc`/`desc`）⇒
「按名称升序 → 再切回默认」后顺序**停在按名称的结果上，且没有任何办法回去**。
现在切回 `none` 会按 `rowBaseOrder`（行底原始顺序）恢复。
—— 这正是用户那句「**不受其他排序规则影响**」的落点：**默认态必须等于模板序**。

> 另外，两处加载点（查看态 `loadCross` / 编辑态 `loadEditGrid`）都必须记录 `rowBaseOrder`；
> 只改一处会让「切回默认」在另一态下按上一个态的顺序恢复（静默错序）。

## 五、存量数据：**零回填**

`sort_no` 是从本次改动起才有的列，存量行一律 `0`。**没有做任何批量回填** ——
因为「存量期次的顺序」用**读端兜底**就能拿到同样效果：

后端 `ORDER BY (sort_no>0), sort_no, r.id` 在 `sort_no` 全为 0 时**天然退化为按 `r.id` 升序**
（= 登记插入序），前端 tier 1 用数组下标承接 —— 于是：

- **tenant_1 期次 9/13 的顺序，修复后立即变成登记序 = 模板序**（实测已生效，见 §四④）
- 期次 14 变成「那次导入的登记序」（它本就是另一次导入）
- 用户**不需要重新导入**就能看到改善

> **判据：能用读端口径解决的，就不要动存量数据。**
> 回填是一次批量生产写入（462 行 × 3 期），而这里它买不到任何额外的东西。

### ⚠️ 一个必须如实交代的边界

同一期次**分多批导入**时，若第二批的模板里包含第一批已有商品，那批商品会随第二批
落到新的批次基准上（= 排到第二批那一段里）。这是「最近一次导入的行序更权威」的**有意取舍**，
不是缺陷；用户的真实用法是**每次导完整模板**（其原话：「模版里有多少产品，导入后就只有那么多产品」），
该场景下顺序**完全等于模板序**。

## 七、需要用户验收的步骤

1. `Cmd+Shift+R` 强刷预报订货管理页
2. 选定有导入的期次（如「9月19日报单9月22日到货」）
3. **第一行商品应与你模板的第一行一致**
4. 向下滚，逐行核对应当**与模板逐行同序**
5. 反悔测试：改一下模板里的行序 → 重新导入 → 顺序应**跟着最新模板变**
6. 若点过表头排序，把排序切回「默认」应**回到模板序**（此前回不去）

**不必重新导入也能看到改善** —— 存量期次已按登记序显示（§五）。
但如果你要 100% 等于**当前这份模板**的顺序，重新导入一次最稳妥。

## 八、本次排查中修正的三处自身错误（留档，避免重犯）

1. **断言写错列**：`imported_products` 的 `id` 是 `product_id`，而排序键是登记表的自增 `id`
   —— 用前者断言「升序」必然假红。**实现对、断言错，两者症状一样。**
2. **复现前端请求时漏了鉴权头**：裸 `fetch` 拿回 `imported_products: []`，
   后端按「无 token」处理**不报错、只给空** ⇒ 与「真没数据」长得一模一样。
   带上 `Authorization: Bearer` + `X-Tenant-Id` 后立刻正常（见 `src/api/client.js`）。
3. **离线脚本首版把「显示全部商品」的行数断言写成 `在售档案数`** ——
   实际应为 `在售档案数 + 档案外但被本期引用的行数`（实测 285 + 3 = 288）。
   被脚本自己抓到。

> 共同点：**每一条 FAIL 都要先回读实现再改断言** —— 否则会把正确的实现改坏去迁就错误的断言。

## 五、⚠️ 事故与恢复（必须记录）

**发生了什么**：端到端验收时，脚本宣称"跑在影子库上、零写入生产"，
但其中一条"合法密码应被接受"的反例请求，**真的写进了生产库** ——
把**微信小程序提审测试账号 `mptestsp`** 的密码从提审登记的那个值改成了脚本里的示例密码。
（若不发现，审核员将无法用登记密码登录，**直接导致提审失败**。）

**根因**：本项目 **DB_PATH 有两份**，且各自独立——
- `erp_db.DB_PATH`：`core._master_db()` 读它 → **认证**路径 ✅ 已 patch 到影子
- `db/connection.py:11` 自己那份：`get_db()` / `_sqlite_connect()` 用它 → **写库**路径 🔴 **没 patch**

⇒ 结果是"认证走影子、写库落生产"。

**处置（已闭环）**：
1. `cp erp.db backups/v289-pwfix/` 备份；
2. 用 `core._hpw()` 把密码**写回原值**；
3. `core._verify_password` 自证：原密码 `True`、误改的密码 `False`；
4. **只读**复查全库 8 个账号、确认无探针账号/会话误入生产；
5. 清理影子库目录。

**修法（已固化进验收脚本）**：两处 `DB_PATH` 都 patch ＋ **跑前自证**——
`get_db()` 与 `_open_master()` 都通过 `PRAGMA database_list` 断言 `main` 指向影子，否则 `exit(2)`。
详见 `验收工具/verify_pwd_e2e.py` 的【1.5】段。

**三条可复用判据**：
1. 「影子库 / 沙盒」**不能靠"我 patch 了"来相信，必须让脚本自证**；
2. 取连接的入口**不止一个**（`_master_db` / `get_db` / `_open_master` / 租户 `_tenant_db`）⇒ patch 必须**穷举**；
3. 判「有没有写生产」**不能只看主库文件 mtime**（WAL 模式下改动在 `-wal`，v289 就被它骗过），
   要用**内容判据**：拿生产代码反查"我这次用过的那个值"是否生效。

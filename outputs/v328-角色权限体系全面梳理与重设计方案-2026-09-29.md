### 1.2 后端已实现、但前端未暴露的权限（勾了也给不了界面）

| 权限模块 | 后端实况 | 前端实况 | 定性 |
|---|---|---|---|
| **marketing（费用管理）** | `_PATH_MODULE_MAP` **0 条接口**映射到它 | 权限页有勾选框「费用管理」 | **幽灵模块**：勾了放开 0 个接口，纯误导 |
| **settings（设置）** | 0 条接口映射 | 有勾选框 | 幽灵模块（代码注释已自认） |
| **tasks（任务与项目）** | `/api/tasks`+`/api/projects` 有接口 | 新前端**无任何页面**消费 | 勾了只能调 API，界面进不去 |
| **projects（项目管理）** | 同上 | 同上 | 同上 |
| **ops-workbench / perf** | boss 默认持有，但 `_ALL_MODULES` 未登记 | 权限页看不到、改不了（保存时逐字回传不丢） | 不可见遗产 |
| **动作粒度（查看/编辑/导出/删除）** | 后端支持 dict 形态 `{module:[read,create,...]}`、`_ALL_ACTIONS` 四动作 | UI 只有模块级单勾选 | 能力闲置（舟谱有「查看/编辑/导出/导入/其他」五列） |
| **自定义角色（新建角色）** | `POST /api/role-permissions` 接受**任意** role_name（未过 normalize_role） | 界面只能改 9 个内置角色，无「新建角色」入口 | 接口裸奔 + 界面缺失 |

前端对模块轴的**真实消费**：全仓只有 `chat`（3 处）与 `payroll`（1 处）直接调 `canModule()`，其余全走 pages.js 注册表（dashboard/payroll/bid/cron/chat 五个模块真正决定入口显隐）。

### 1.3 UI 会误导用户的地方（按危害排序）

1. **「费用管理」勾选框**：许诺"登进来后能用哪些功能"，实际放开 0 个接口。勾与不勾无任何区别 —— 最典型的假配置。
2. **模块勾选 ≠ 页面入口**：多数业务页（/forecast、/rebate、/archive、/loss…）入口走**产品内置角色门槛**（module:null），给某角色勾「销售管理」「仓库管理」**不会让它侧栏多出任何页面**——只放开接口。权限页标题写的"② 功能模块：登进来后能用哪些功能"与实际行为不符（只有让位规则命中的 /cron、/bid-radar 例外）。
3. **tasks / projects（任务与项目）**：勾了在网页端无处可用。
4. **给"仅小程序"角色勾网页模块**：业务员/员工/分销商默认登不进网页端，权限页不提示"勾了这些他也看不到"（登录端与模块矩阵同表但互不解释）。
5. **9 个角色名 vs 界面文案**：权限矩阵列头用 `ROLE_LABELS`（"财务 / 文员"）、员工档案下拉用 `ROLE_NAMES`（"会计"）——同一角色两个名字，跨页对照时容易当成两个角色。

## 二、权限配置方案（重配，以 UI 实际暴露为准）

### 2.1 模块层修整（P0）

| 动作 | 内容 |
|---|---|
| **删幽灵** | `marketing`、`settings` 从 `_ALL_MODULES` 移除（0 接口映射）；存量租户库里这两列的勾选值由迁移脚本清掉。`tasks`/`projects` 移入"后端预留"分组（见 2.2） |
| **登记遗产** | `ops-workbench`/`perf`/`goals`：要么补进 `_ALL_MODULES` + 中文标签（运营工作台/绩效/目标），要么从 `_DEFAULT_PERMS` 摘掉。**不可维持现状**（持有但不可见，违反"权限名与功能一致"） |
| **分组** | `_ALL_MODULES` 顺序按业务域重排：数据（data/cron/bid）→ 销售（sales/buying/stock）→ 财（accounts/reports/payroll）→ 人（hr）→ AI（chat）→ 平台（dashboard/settings） |
| **三处同步纪律** | 任何模块增删必须同时动 ① `core._ALL_MODULES` ② `server.py::_PATH_MODULE_MAP` ③ 迁移脚本（老租户等价性）——v296 已实证漏 ③ = 全员 403 |
| 🔴 **旧前端盘点前置** | 本清单只覆盖 hergent.cn 新前端 + 小程序。**erp.hergent.cn 旧 ERP 前端（hergent-admin）共用同一后端**，收缩 guide/driver 等角色的 sales/stock/crm 前，必须先盘点旧前端页面调用了哪些模块，否则会把旧系统里"访销/车销"页面对这些角色打断 |

### 2.2 建议的角色 × 模块矩阵（目标态）

> 原则：**角色默认权限 = 该角色在界面上真实能到达的页面所需接口的最小集**。
> ⚠️ 以下为建议值；每个改动的默认值都要走"改 `_DEFAULT_PERMS` + 迁移存量租户"同批纪律。

| 角色 | 登录端（现行） | 建议功能模块 | 变更点与理由 |
|---|---|---|---|
| 管理员 admin | both | *（通配，矩阵中隐藏不可改） | 不变 |
| 老板 boss | both | dashboard、data、sales、buying、stock、accounts、crm、hr、payroll、reports、chat、cron、bid ＋ 登记后的 ops-workbench/perf/goals | 去掉无映射的 marketing |
| 会计 accountant | web | dashboard、accounts、reports（+ 可自授 payroll、data、chat） | 去掉 marketing（本就是幽灵） |
| 业务员 sales | **mini** | data（报单链路） | **建议撤 cron/bid**：v310 后业务员仅小程序登录，小程序不调 /api/cron、/api/bid-radar；持有只扩大 API 攻击面（迁移时按"默认持有者"判据同批处理） |
| 主管 supervisor | both | dashboard、data、sales | 保留（盯汇总+冲刺看板+审报单，v293 实证过缺 sales 的坑） |
| 员工 staff | mini | data | 建议**撤 stock/cron/bid**：小程序真实调用面只有 data（v312 已实测）；staff 登不进网页端，stock（/api/loss 等）无界面可达 |
| 分销商 distributor | mini | data | 不变（v307 已是最小集） |
| 导购 guide | web | dashboard | 大幅收缩：BIZ_ROLES 不含 guide ⇒ 网页端只有工作台+趋势可达；sales/buying/stock/crm 四个模块无页面消费（🔴 需先过旧前端盘点） |
| 司机 driver | web | dashboard | 同上（现行 stock 对司机暴露「货损」金额数据，本就是 pages.js 文件头点名的越权反例） |

### 2.3 机制层修整（P1）

1. **`POST /api/role-permissions` 补 `normalize_role` 校验**：现在接受任意 role_name 落库，等于"造角色"走后门；且造出的角色会进 `known_roles()` 变成可派发的合法角色。
2. **自定义角色正门化**：既然后端已支持任意自定义角色，界面应补「新建角色」入口（见 §三），后端补"新建角色"专用端点（带校验、审计、复制模板）。
3. **动作粒度暂不放开**：舟谱的五动作列值得学，但后端 dict 形态的消费方未铺开（UI 入口显隐只看模块粒度），建议作为二期。

## 三、界面优化建议（对照舟谱）

舟谱三张图：① 角色列表页（名称/类型/编辑·复制·更多） ② 向导式三步配置（设角色类型 → 菜单操作配置 → 完成），矩阵按**业务域分组**、列为**查看/编辑/导出/导入/其他**五个动作 + 电脑端/手机端双列 ③ 成功页。

| # | 舟谱做法 | 我们现状 | 建议 | 优先级 |
|---|---|---|---|---|
| 1 | **复制角色**（拿现成角色改） | 无，只能逐格改内置 9 角色 | 权限矩阵加「复制为新角色」：选中一行 → 存成自定义角色（后端已支持任意 role_name，补校验即可） | P1 |
| 2 | **向导式创建**（类型→权限→完成） | 无创建流 | 新建角色走两步弹窗：命名+登录端 → 勾模块；成功页给"下一步：去员工档案分配" | P2 |
| 3 | **矩阵按业务域分组**（档案管理/采销管理/资金管理…，域级全选） | 19 行平铺 + 搜索 | 分组行 + 域头全选；勾选行数从 19 降到 ~8 组，老板视角快一个量级 | P1 |
| 4 | **动作粒度列**（查看/编辑/导出/导入/其他） | 单勾选 | 二期：等后端 dict 形态消费铺开再上，现阶段**不做**（避免又一个"勾了不生效"） | P2 |
| 5 | **每功能分电脑端/手机端** | 每角色两条端 + 模块行只读「手机端」标记 | 现方案更诚实（端是登录入口，不该按功能撒）；保留现状，但把「手机端」列说明挪到列头 tooltip（已有） | 不动 |
| 6 | 角色名编码适用端（"文员(仅登录电脑端)"） | `ROLE_END` 生成标注（仅小程序/两端/仅网页端） | 已等价实现，且是唯一源派生，**比舟谱更好** | 不动 |
| 7 | 「恢复默认设置」一键恢复 | 每角色单独「恢复默认」 | 可加"全部恢复出厂"（带确认+审计），低频但救急 | P2 |
| 8 | 角色搜索 + 批量删除 | 有模块搜索，无角色搜索 | 角色列 ≤10，搜索价值低；**不做批量删除**（删角色牵连员工归属，风险大于收益） | 不做 |
| 9 | 角色类型字段（管理类/业务类） | 无 | 意义不大（我们角色少、分组即类型）；**不做** | 不做 |
| 10 | — | 角色两个名字（ROLE_LABELS vs ROLE_NAMES） | **统一**：权限矩阵列头 tooltip 用 ROLE_NAMES 短名 + 一句职责说明（员工档案已有 `ROLE_DESCRIPTIONS`，复用） | P1 |

## 四、角色 ↔ 员工档案联动机制

### 4.1 已实现且健康的部分（不用重做）

| 链路 | 实现 | 验证 |
|---|---|---|
| 员工配角色 → 权限严格=该角色 | 员工无个人模块权限，全部经 `users.role` → 租户 `role_permissions` → `_check_perm` **每请求实时判**；改角色权限 = 改角色本身，**所有该角色员工即时生效** | 架构性保证，无同步延迟 |
| 角色权限变更 → 前端 UI 跟上 | ① 保存端 `reload_perms(tid)` 失效缓存 ② `perms_rev` 内容指纹 ③ 前端三时机比对（保存后/导航/60s 轮询+切回标签页）→ `loadPerms(true)` 重算 24 处菜单 | v296 |
| 角色登录端 → 新账号默认 | `role_end_for`（租户可覆盖）→ `staff_account_create` 取实际生效端预填 | v312 有单测 |
| 账号端与角色漂移 | 员工档案标「与角色配置不一致」+「按角色对齐」一键回正 | v326 |
| 兼任角色 | `roles` 数组只增权限，非法值整单 400 + 审计 | v266 |

### 4.2 缺口与实现要点

| # | 缺口 | 实现要点 |
|---|---|---|
| G1 | **改角色不重算登录端**：`PUT /users/{uid}/role` 只改 role/roles，`users.login_scope` 保持旧角色的值 ⇒ 员工从"导购"改成"业务员"后仍能登网页端（与"业务员仅小程序"的角色政策相悖） | 改角色时返回 `default_login_scope`；前端弹"按新角色对齐登录端？"（默认勾选）；**不静默强改**（保留 v307"账号事实优先"契约，但把漂移摆到台面上，而不是等员工档案页才发现） |
| G2 | **module:null 页面对权限配置零响应**（§1.3-2 的许诺差距）：给某角色勾「销售管理」，/rebate 入口纹丝不动 | 两条路二选一：A（重）给 BIZ 页面建真模块（动 `_PATH_MODULE_MAP`，大工程）；**B（轻，推荐）**：权限页每行模块下标注"影响哪些页面"（由 pages.js 反查生成），把"勾了会怎样"说清楚——成本一天，消灭误解 |
| G3 | **"与角色配置不一致"只看登录端**，模块权限天然不会漂移（架构性）——但员工档案页没有一句话向老板解释"为什么改了角色权限、员工那边什么都不用动" | 员工档案账号卡补一行说明文案（静态） |
| G4 | **自定义角色让位盲区**：`roleGateOpen` ③ 档让位只对**配了 module 的行**生效（/cron、/bid-radar、/ai-hub、/payroll）；客户给自定义角色（如"库管"）勾再多模块，也进不了 /rebate、/archive 等角色门槛页 | 这是**刻意设计**（防全开），但要在权限页给自定义角色一行提示："自定义角色默认只能看到『按模块放开的页面』，需要更多页面请从相近内置角色复制"——否则客户会以为权限没配生效 |

### 4.3 "角色可见 UI ↔ 角色拥有权限"严格联动的现有保障（结论）

**机制已在位且闭环**：侧栏/路由守卫/命令面板/页内跳转四消费方共用 `PAGE_RULES::roleGateOpen` 唯一实现（结构上不可能"入口在而守卫拦"或反之）；后端 `_check_perm` 是最终边界；`perms_rev` 指纹轮询保证跨会话联动；`custom_roles` 内容判据决定让位。**剩余风险全部集中在"许诺差距"**（G2/G4 的文案层）与 G1 的账号端漂移，不在裁决层。

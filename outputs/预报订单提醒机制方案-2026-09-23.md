# 预报订单模块 · 系统提醒机制设计方案

> 版本：v1（设计稿） · 日期：2026-09-23
> 适用：Hergent 预报订单（本期预报 / 期次 / 报单）模块，覆盖 Web 端（hergent.cn）与微信小程序「小赫智体报单助手」
> 目标读者：产品决策（老板）+ 开发落地

---

## 0. 结论先行

**建议做，但分阶段落地。** 提醒机制是「低成本、高杠杆」的功能——本模块的核心风险是**销售漏报 / 忘报 / 不知道截止时间**，而系统里「通知中心」基建（`message_center`）已经建好，复用成本很低。

- **MVP（P0，零新渠道）**：用已有的「站内信」通道（Web 端铃铛 + 小程序内通知），覆盖 4 个最关键节点——**新期次发布、截止前 3 小时（自适应）、截止前 1 小时、截止后汇总**。
- **P1（补主管触达）**：报单提交回执、未报每日摘要、定稿/加单提醒，需小程序侧补一个通知面板。
- **P2（真移动推送）**：接**企业微信应用消息**做销售/督导手机端真触达；同时补「按用户云端的免打扰偏好」「期次截止时刻字段 + 写入口门禁」。

> 不建议依赖「小程序订阅消息」做关键节点保障——它只能一次性授权、用户点「总是拒绝并记住」后**永久静默**，且长期订阅仅对政务/医疗等类目开放，本小程序类目（工具→效率）拿不到。

## 1. 现状与可复用资产（避免重复造轮子 / 踩已知坑）

| 资产 | 现状 | 对本方案的用处 |
|---|---|---|
| `message_center` 表 + `message_send()` 写入口 | 已上线，全租户可用 | **唯一写入口**，所有提醒都走它 |
| `event_key`（事件键）+ 按类静音 | 已上线（前端 localStorage 级） | 去重、按类「不再提示 / 暂停 7·30 天」 |
| `recipients`（收件人）定向 | 生产上 **100% 为空** | ⚠️ 必须修：不传值 = 全员可见（工资条事故同款） |
| `dedup_window`（去重窗口） | 默认 86400 秒 = 每天一次 | 天然防刷屏 |
| 预报推送触点 `routers/forecast.py:342-344` | 已把预报事件 fan-out 到「站内 + 企微群机器人 + 飞书」 | ⚠️ **别直接复用**：群机器人无法发给个人，会把提醒广播进群；应用消息才是定向通道 |
| 企微应用消息 | 通道**未接通**（需自建应用 + 员工企微 userid，当前两列均空） | P2 真推送的前置依赖 |
| 小程序订阅消息 | 长期订阅不可用；一次性需每次授权 | 仅作非关键补充，**不依赖** |
| 已有预警体系（库存/逾期/效期） | 走 `message_center` 的 `danger/warning` | 报单异常提醒直接接入，不必另建 |

**结论**：基建齐了 70%，真正的工程量是「把提醒节点接进 `message_send` + 修 recipients 定向 + 补企微通道」。

## 2. 报单生命周期与提醒锚点

```
期次创建(OPEN)
   │  ① 新期次发布提醒
   ▼
报单窗口 order_start ~ order_end
   │  ② 截止前 3h（仍未报齐；期次临发则发版即催）
   │  ③ 截止前 1h（仍未报销售）
   │  ④ 有人提交报单 → 回执 + 主管知会
   │  ⑨ 每日未报摘要（窗口期内每天 1 次）
   ▼
order_end / order_deadline（截止）
   │  ⑤ 截止汇总（已报X / 未报Y / 金额）
   ▼
定稿 / 加单（supervisor 审核）
   │  ⑥ 临期未定稿（已关闭但未定稿）
   │  ⑦ 定稿 / 加单知会相关销售
   ▼
关闭(CLOSED)
```

### ⚠️ 两个必须先解决的前置问题
1. **没有"截止时刻"**：期次目前只有 `order_start~order_end` 日期区间，「截止前一小时」无法精确触发。
   → 建议新增 `forecast_periods.order_deadline`（datetime），或约定 `order_end 当天 23:59` 为截止时刻。
2. **`closed` 不拦报单写入**（已知缺陷：`forecast_submission_create` 不校验期次状态）→ "截止"名不副实。
   → 截止提醒应配套**写入口门禁**（参考 `hergent-write-entry-gate` 技能），让"截止"成为硬锁。

## 3. 建议提醒节点清单（按生命周期排序）

| # | 节点 | 触发时机 | 提醒对象 | 内容要点 | 主渠道 | 优先级 |
|---|---|---|---|---|---|---|
| N1 | **新期次发布** | 期次置为 OPEN | 全部销售 / 促销 / 督导 | 期次范围、报单截止时间、各品牌到货周期 | 企微应用消息 + Web 站内 | **P0** |
| N2 | **截止前 3h（仍未报齐）** | 距 `order_deadline` 3h；若期次临截止才发布（窗口 <3h）则改为「发版后 30 分钟」 | 该期次**仍未报齐**的销售（按人算差集） | 「你还有 X 家店未报，距截止还有 3 小时（截止 <时间>）」 | 企微 + Web 站内 | **P0** |
| N3 | **截止前 1h（仍未报）** | 距 `order_deadline` 1h | 仍**零提交**或**未报齐**的销售 | 「仅剩 1 小时，还剩 X 家店」 | 企微 + Web 站内 | **P0** |
| N4 | **报单提交回执** | 小程序提交成功 | 提交人本人 + 其主管 | 「XX 店报单已提交；N 项停售商品已自动剔除」 | Web 站内 + 企微(主管) | P1 |
| N5 | **截止汇总** | `order_deadline` 到达 | 主管 / 老板 | 「本期已报 X 家 / 未报 Y 家 / 合计金额 ¥Z」 | Web + 企微 | **P0** |
| N6 | **临期未定稿** | 期次 CLOSED 但仍无定稿 | 主管 / 老板 | 「期次 X 已关闭但未定稿，请尽快审核加单」 | Web 站内 | P1 |
| N7 | **定稿 / 加单知会** | supervisor 定稿或加单 | 相关销售 | 「您负责的 XX 店被加单 N 件 / 已定稿」 | Web 站内 | P1 |
| N8 | **报单异常 / 拦截** | 缺到货周期、停售剔除等 | 提交人 / 文员 | 具体异常项（接入已有预警体系） | Web 站内(danger) | P2 |
| N9 | **每日未报摘要** | 窗口期内每天 1 次（如 09:00） | 未报齐的销售 | 「今日待报清单：门店 A/B/C」 | 企微 + Web | P1 |

> **"未报"如何判定**：取 `report_mapping`（active 的 store/customer）作为该销售应报门店全集，与 `forecast_submissions`（该期次、该销售）做差集 → 差集即未报门店。判定逻辑已在「期次精确归属」修复中验证可用。

## 4. 渠道选择矩阵

| 渠道 | 可用性 | 适用节点 | 限制 / 备注 |
|---|---|---|---|
| **Web 站内信（铃铛）** | ✅ 立即可用 | 全部节点 | 后台/PC 场景；轮询刷新 |
| **小程序内通知中心** | ✅ 需补面板（P1） | 全部节点 | 小程序不支持保活，靠进前台轮询拉取；最稳的"不打扰"通道 |
| **企业微信应用消息** | ⚠️ P2 接通后 | N1/N2/N3/N4/N5/N9（移动真触达） | 自建应用**无类目限制、无需订阅**；但需先建应用 + 回填 `hr_employees.wechat_userid`（当前为空） |
| **企微群机器人** | ⚠️ 不建议定向用 | 仅团队级播报 | **无法发给个人**；曾用于工资条会泄漏个人金额 → 提醒定向禁用 |
| **小程序订阅消息** | ❌ 不依赖 | — | 一次性授权、易永久静默；长期订阅本类目拿不到 |
| **短信 / 邮件** | ❌ 未接入 | — | 需按条计费 + 资质，暂不列入 |

**渠道策略**：MVP 用「Web 站内 + 小程序内通知」双站内通道兜底；P2 接通企微应用消息后，把 N1/N2/N3/N5/N9 的**移动端强提醒**改走企微，站内信保留为"读时可见"的弱提醒。

## 5. 触发条件 / 频率 / 免打扰策略

**触发方式**
- **事件型**（即时）：期次创建、报单提交、定稿/加单 → 直接 `message_send`。
- **时间型**（扫描）：N2/N3/N5/N9 → 后端 cron 定时扫 `forecast_periods`，匹配 `order_deadline` 前后窗口 + 未报差集。

**频率控制**（对齐已有 `scheduler` 节流范式）
- 每个 `event_key` 去重窗口 86400 秒（每天最多折叠一次）。
- 截止前提醒**只发两次**（T-3h、T-1h），不每分钟刷；若期次临截止才发布（窗口 <3h），T-3h 那次改为「发版后 30 分钟」触发，保证短窗口也至少有一次催报。
- 未报摘要**每天 1 次**（如 09:00），与现有调度器 60s~3600s 节流一致。
- **"无异常不推送"**：已报齐的销售不收到 N2/N3/N9，避免"狼来了"。

**免打扰 / 定向**
- `recipients` **必须传值**（修生产空 recipients 坑），按"角色 + 门店范围"精确收口，绝不广播。
- 按类静音：用户可对某 `event_key`「不再提示」或「暂停 7/30 天」（现有能力）。
- **静默时段**：企微/订阅类推送设 22:00–08:00 不主动弹窗（站内信因为是"打开才看到"不受影响）。
- **不诱导、不强制**订阅消息（运营规范红线，踩了会被限制消息能力）。

## 6. 优先级与分阶段落地

| 阶段 | 范围 | 工程量 | 产出 |
|---|---|---|---|
| **P0（MVP）** | N1/N2/N3/N5 的站内信版 | 低（复用 `message_center`） | 漏报/忘报核心痛点闭环 |
| **P1** | N4/N6/N7/N9 + 小程序内通知面板 | 中 | 提交透明化 + 主管协同 |
| **P2** | 企微应用消息真推送、per-user 云端静音偏好、`order_deadline` 字段 + 写入口门禁 | 高（需前置搭建） | 移动端强提醒 + "截止"成为真锁 |

**为什么 P0 只做站内信**：渠道零依赖、即上即稳；先把"该提醒的节点"跑通验证口径，再叠加企微推送，避免一开始就被"企微未接通"卡住。

## 7. 风险与已知坑（基于本项目真实事故）

1. **别复用 `forecast.py` 群机器人路径做定向**——群机器人无法发给个人，会把"张三未报"广播进群。定向一律走**应用消息**或**站内信**。
2. **`recipients` 必须传值**：生产上该列 100% 为空，不修则所有提醒变全员可见（与工资条事故同源）。写入口径见 `notification-center.md` 的 `CAST(... AS TEXT)` 比较规范。
3. **企微真定向前置未齐**：需 `hr_employees.user_id` / `wechat_userid` 回填（当前为空）+ 渠道配置 UI（当前无入口）。P2 前先用站内信。
4. **"截止"与"closed 不拦写入"矛盾**：N2/N3/N5 的语义要等 `order_deadline` + 写入口门禁落地才严谨，否则会出现"提醒截止了还能报"。
5. **`event_key` 命名要稳定**：避免用带日期的 title 当键（每天变 → 静音失效）。复用 `norm_event_key()` 规范。

## 8. 给开发的执行要点（接口 / 字段 / 判定）

- **写入口**：全部走 `finance.message_send(title, content, msg_type, sender, recipients=..., dedup_window=..., event_key=...)`，收件人用 `recipients=`。
- **新增字段**（P2）：`forecast_periods.order_deadline DATETIME`；或约定 `order_end 23:59` 为截止。
- **未报差集**：`report_mapping(active store/customer)` − `forecast_submissions(period_id, sales_id)`，已在「期次精确归属」修复中验证。
- **cron 任务**：扫描「未来 3h / 1h 内截止且仍有未报门店」的期次 → 触发 N2/N3；每日 09:00 触发 N9；`order_deadline` 到达触发 N5。
- **event_key 建议命名**：`预报·新期次` / `预报·截止前提醒` / `预报·截止汇总` / `预报·提交回执` / `预报·未报摘要` / `预报·定稿` —— 与 `norm_event_key` 同族，便于按类静音。
- **写入口门禁**（配 N2/N3/N5）：`forecast_submission_create` 在 `order_deadline` 后硬拒，回显「本期已截止」。

## 9. 控制面板（用户自配）评估 —— 针对 N2 修订 + 用户提问

### 9.1 「截止前 3h」什么时候发、发什么（细化）

**什么时候发（自适应触发）**
- cron 在 `order_deadline` 前 3h 扫一次，仅向「该期次仍有未报门店」的销售发。
- **自适应兜底**：你们期次常常临截止才发布，若期次在截止前 3h 内才发布（窗口过短），则把这次催报改为「发版后 30 分钟」触发——保证哪怕临发也至少有一次催报。
- T-1h 那次**无论窗口多短都会发**，是截止前最后一道闸。

**发什么（内容模板）**
- 标题：`【报单提醒】期次<编号> 距截止还有 3 小时`
- 正文：`您负责的 <X> 家门店尚未报单（门店A、B、C…）。截止时间：<YYYY-MM-DD HH:MM>。点击前往报单。`
- 收件人：**只发给"自己仍有未报门店"的销售**（差集算到个人），绝不广播；主管收到的是「你团队还有 X 家未报」的聚合版。
- 动作：深链跳小程序报单页 / Web 预报页。
- 前提：`order_deadline` 字段必须先补（当前只有日期区间，无法精确定位"3 小时前"，见 §2 前置问题 1）。

### 9.2 要不要做"用户自配控制面板"

**结论：用户（老板）已拍板「现在就做」，控制面板已于 2026-09-23 全量上线（详见下「9.3 落地状态」）。**

原评估（保留作产品化参考）：MVP 阶段曾倾向「第二个经销商上线（多租户）时再做轻量版」，理由是当前仅 1 个决策人、默认值已够用、面板是负担。但用户认为与其等二租户、不如先把自配能力给用户——故推翻该结论，直接实现 per-tenant 面板。

| 维度 | 评估 |
|---|---|
| 当前（你一人公司，仅 1 个决策人） | 默认值 3h/1h + 站内信已够用，**面板是负担不是红利**；先跑通看实际报齐率再谈 |
| 产品化（卖给其他经销商，多租户） | 各经销商报单节奏不同，per-tenant 自配才有规模价值 → **此时做** |
| 面板形态 | **不做自由 cron / 表达式**（非技术老板极易配错导致漏报）；做成「开关 + 几个带护栏的下拉/数字」 |
| 面板该含什么 | ① 总开关 ② 临近催报提前量（默认 3h，可选 1/2/3/6h）③ 最后催报提前量（默认 1h）④ 渠道（站内信 / 企微，企微需先接通）⑤ 免打扰时段（默认 22:00–08:00）⑥ 哪些节点启用（新期次 / 临近 / 最后 / 汇总） |
| 护栏 | 默认值即安全（无论如何至少 T-1h 必发）；任何阈值不可为 0；免打扰只影响推送、不影响站内信 |

### 10. per-sales 差集定向（2026-09-23 已上线）

**为什么不是"每人独立账号定向"**：实测 `users.employee_code` / `employee_id` 全部为空、`hr_employees` 无 `user_id` 外键 —— "员工档案 ↔ 登录账号"是断的，无法可靠把某门店映射到某人的登录账号。故采用**「分组视图 + 预留真定向」双轨**，既不做出"发了但谁都收不到"的静默失效功能，又为将来留好升级路径：

- **分组视图（现在就能用）**：提醒内容按负责业务员分组，写明「刘小顶 还差：美联保康；张俊峰 还差：东津」，定向发给老板/管理员（`users.role IN ('boss','admin')`，他人不可见）。
- **真定向（将来，零改代码）**：当某业务员的 `users.employee_code == hr_employees.employee_no`（或 `users.employee_id == hr_employees.id`）能解析到登录账号时，自动改为"只发到他本人、他人看不到"。

**实现要点**：
- `_forecast_reminder_state()` 新增 `missing_detail`（带 `store_id`）；`_build_sales_diff(st)` 用 `report_mapping(counterparty_type='store')` 把未报门店归到 `hr_employees`，再尝试解析账号；`_send_aggregate_reminder` / `_maybe_send_summary` 支持分组与逐人定向；`_boss_recipients()` 解析老板/管理员账号。
- 配置新增 `per_sales`（默认 `true`）；前端「报单提醒」面板新增「按销售分组定向（差集）」开关（关闭 ⇒ 退回原广播，作为"销售共用一个账号也想看全量"的兜底）。
- 逐人消息用 `recipients=其账号 + 独立 event_key`，老板汇总用 `recipients='boss'/'admin'`，均走 `_visible_where` 定向可见。

**实测（tenant_1）**：4 个在映射内的门店正确归组到 刘小顶 / 张俊峰 / 微信审核-销售 / 微信审核-主管；因尚未建账号链接，全部经老板/管理员分组视图送达。无账号链接时**零静默失效**：老板仍看到完整"谁还差哪些店"。

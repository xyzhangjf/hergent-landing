## 一、主要取舍（每条都有被放弃的选项）

### 取舍 1：台账做成「能力中心里的一个区块」，不做独立页面

| 选项 | 结论 |
|---|---|
| A. 侧栏新增一级入口「数据报表」 | ✗ 名字与用途反向（舟谱那个是**输出**的报表矩阵，我们要的是**输入**的通道）；且侧栏那一格 **3 天前刚被撤下来**，代码里写着理由：「用户不认可为一个低频动作占一行侧栏」（`routers/zhoupu_documents.py:36-45`） |
| B. 独立页面 `/data-upload` | ✗ 仓里有明文纪律：「上传能力与『上传第一份数据』**同一个接口** ⇒ **避免出现两套导入入口**」（`src/pages/Workbench.vue:13-15`） |
| **C. 能力中心 › 连接器 › ERP 数据源 的下方一个区块** | ✅ **采纳** |

**理由**：这一页本来就有一区叫「ERP 数据源」，标题写着「接入你的业务系统，AI 副驾直接读真实数据」。
**台账正是那一区的另一半** —— 上面说"数据从哪接进来"，下面说"接得全不全"。
同类信息放一起，用户不用在两个页面之间对账；且**零新增入口**。

### 取舍 2：有专门页面的类目只给「去上传」跳转，其余才在本组件里传

| 类目 | 处理 | 为什么 |
|---|---|---|
| 商品档案 / 员工档案 / 库存效期 | **跳转**（`/archive/products`、`/archive/employees`、`/data-fill`） | 这三页已有**完整**的导入界面。再提供一个 = 第二套导入入口 |
| 客户 / 应收 / 订单明细 / 客户专属价 / **收款流水** | **本组件内弹窗上传** | 这五个**前端零界面**（`grep 'importApi.preview'` 实测只命中 ProductArchive / EmployeeArchive / Forecast / DataFill）。是**补洞**，不是开第二条路 |

判定表写在**一处**（`CAT_META[cat].page`）。后端加新类目时，前端不写 `page` 就自动走弹窗 ⇒
**不会出现"新类目没入口"或"两个入口"**。

### 取舍 3：只加 **1 个** 新导入类目，不是 4 个

先前的舟谱报表判定里，"首批 4 张"需要 `客户档案 / 商品档案 / 订单明细 / 收款流水`。
实测其中 **3 个类目后端早已有**（`contacts` / `products` / `order_items`），
**唯一真的缺的是收款流水**。所以本轮的"新建类目"工作量是 **1 个**，不是 4 个 ——
另外 3 个差的只是**前端入口**，而入口由同一个弹窗一次性覆盖。

### 取舍 4：收款流水的去重键**不放单据号**

`payment_receipts` 表没有 `receipt_no` 列。把单据号放进内存去重键、却放进不了库内键，
会出现「同一份文件里同日同额的两笔真实回款，内存判不同（对）、库内判相同（错）」
⇒ **第二笔被静默跳过 = 少记一笔已经收到的钱**。

于是两把尺子统一用 `(客户, 回款日期, 金额)`。代价是：**同日同额的真实两笔会被判为重复**。
但那一侧的失败**看得见**（回执里逐行点名 + 明确告诉用户怎么放行：关掉「跳过已存在的记录」），
而另一侧的失败看不见。**两害相权取"看得见的那一侧"。**

## 四、边界情况与潜在风险（按严重度）

### 🔴 风险 1：撤销**不能**共用通用那条 `DELETE`

收款流水导入的副作用**在别的表上**（`receivables.paid_amount` + `payment_receipt_allocs`）。
若哪天有人把 `_receipt_undo` 里的专用分支删掉、让它落到通用路径：

> `payment_receipts` 的行没了，而 `received_amount` **一分钱都没退**
> ⇒ 客户明明还欠着，催收队列却显示已清。**这是静默错账，不是崩溃。**

已在两处写死警告：`_IMPORT_UNDO_TABLES` 的注释 + `_undo_payment_receipts` 的 docstring。

### 🔴 风险 2：客户名匹配**绝不能**用 `contact_list()`

`db.contact_list(keyword=)` 是 `LIKE %词% ORDER BY id DESC LIMIT 1` —— 给**人**在搜索框里用的。
用在这里的后果是**把钱记到不相干的客户账上**：还钱的人没被冲掉、别人被冲掉了，两边都不报错。

实现改为：**精确同名 → 用；模糊命中 >1 个 → 拒绝并列出候选；0 个 → 报"找不到客户"**（不自动建档）。
用户会因此多看到几条"匹配到 N 个"的错误 —— 那是**有意的**，比静默记错账好。

### 🟡 风险 3：重复导入 = 账上虚增已收

所以这一类**必须**支持增量去重（两张键都登记了），且弹窗在 `payment_receipts` 上会亮黄条提醒
「重复导入会重复冲账，请保持『跳过已存在的记录』开启」。

局限：同日同额的真实两笔会被判为重复（见取舍 4）。**它看得见、有放行开关。**

### 🟡 风险 4：`smart-parse` 的类目判据顺序

舟谱收款表里常同时有「应收金额」列。若「应收」判据先命中 ⇒ 收款表被判成**应收期初**，
导进去变成"收回来一笔钱、反而多记一笔应收"。故收款判据**排在应收之前**（已写成断言 H1）。

### 🟡 风险 5：台账的「查不到」不等于 0

表还没建（新租户从未用过该类目）时后端返回 `count=null` + `count_error`，前端显示「读不到」。
**不返回 0** —— 「确实是空的」与「这张表根本没初始化」是两件事，显示成同一个数就是
本项目反复在修的「恒 0 且零报错」那一族。

### 🟢 风险 6：台账的「上次上传时间」只覆盖**走上传通道**的导入

- 手工录入 / ERP 同步进来的行，没有上传回执 ⇒ 那一栏显示「没有上传记录」（不是缺陷，是事实）。
- 舟谱单据通道（`/zhoupu-import`）的落点不是这 8 个类目，不会体现在台账里。
- 台账**不含** `forecast_cross`：报单矩阵是每期一次的业务动作、有自己的期次列表；
  摆进台账只会让"上次上传"永远显示"昨天"，是噪音。

### 🟢 风险 7：`receipt_no`（单据号）暂不落库

它在字段候选里（列在候选里才会被"消费"掉，否则舟谱表里那一列在映射界面会显示成「不导入」，
用户会以为系统漏读了），标签写明「暂不入库」，且不参与去重（理由见取舍 4）。

### 🟢 风险 8：环境护栏会挡住前端构建

`vite build` 要清空 `dist/assets`（56 个文件 > 护栏阈值 50），会被 safe-delete 挡下。
**这不是代码问题**。构建时用官方开关放行（`dist/` 本来就是每次重建的产物目录）：
`CODEBUDDY_SAFE_DELETE_ENABLED=0 npm run build`。

## 五、没做的事（明确不做，各有理由）

| 不做 | 理由 |

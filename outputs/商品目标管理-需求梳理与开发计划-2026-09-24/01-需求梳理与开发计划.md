## 二、现状核实：系统里的真实单位换算（本需求的地基）

> 你特别提醒"要看系统里的真实单位换算是什么样的"。查完了，先把结论摆出来。

### 2.1 唯一权威 = 商品档案的三级单位（不是规格串）

`products` 表里管单位的列有 6 个，**真实的语义分工是**：

| 列 | 含义 | 生产 tenant_1 实测（285 个在售商品） |
|---|---|---|
| `unit` | **小单位**名 | 瓶 94 · 杯 49 · 组 39 · 袋 34 · **件 32（脏数据）** · 盒 13 … |
| `medium_unit` + `medium_ratio` | **中单位**名 + 每中单位含几个小单位 | 只有 **53** 个商品真有中单位（如「包」，5袋/包） |
| `large_unit` + `large_ratio` | **大单位**名 + 每大单位含几个小单位 | **209** 个商品有大单位：件 202 · 箱 7 |
| `order_unit` | **报单单位**（人工指定，空则回退 `unit`） | 只有 **30** 个商品填了；其中仅 **1 个**与 `unit` 不同 |

**换算层级**（以你最关心的那个商品为例）：

```
蒙牛0蔗糖原味百利包150g*5袋*8包      id=1449   spec=150g*5袋*8包
  小单位 = 袋
  中单位 = 包   medium_ratio = 5    →  1包 = 5袋
  大单位 = 件   large_ratio  = 40   →  1件 = 40袋 = 8包   ★
```

### 2.2 用你的例子反推验证 —— 完全对上

你举的加单例子：

> 「经理加60箱、刘善涛占10%即加6箱即48包，其原报40包即5箱，最终定稿88包即11箱」

拿上表的真实换算算一遍：

| 你的说法 | 系统换算 | 结果 |
|---|---|---|
| 每箱 8 包 | `large_ratio ÷ medium_ratio` = 40 ÷ 5 | **8 包/箱** ✅ |
| 加 60 箱 × 10% = 6 箱 | 60 × 0.10 | **6 箱** ✅ |
| 6 箱 = 48 包 | 6 × 8 | **48 包** ✅ |
| 原报 40 包 = 5 箱 | 40 ÷ 8 | **5 箱** ✅ |
| 最终 5+6 = 11 箱 = 88 包 | 11 × 8 | **88 包** ✅ |

**五个数全部闭环，误差为零。** 你说的"0糖袋"就是 `蒙牛0蔗糖原味百利包150g*5袋*8包` 这类商品（生产库里 `medium_unit='包'` 的一共 8 个，都是同一规格族）。

> 顺带确认另一处：你说「可报15单」—— 生产库 `rebate_target_rules` 里 **「蒙牛低温2026年目标」(id=10) 的 `arrival_count_override` 正好 = 15**（每 2 天到货一次）。所以"可报单数"这个词不是我猜的，系统里真有这个数。

### 2.3 🔴 两个已发现的静默陷阱（不处理，功能上线就会算错）

#### 陷阱 A：SQL 里 `medium_ratio > 0` 是**假判据**，会多算 157 个商品

生产实测：`medium_ratio` 这一列**存了两种类型**——128 行是数字，**157 行是空字符串 `''`**（不是 0）。而 SQLite 的规则是「文本永远大于数字」，所以：

```sql
SELECT '' > 0;          -- 返回 1（true！）
SELECT COUNT(*) FROM products WHERE medium_ratio > 0;              -- 210  ❌ 假阳性
SELECT COUNT(*) FROM products WHERE CAST(medium_ratio AS REAL) > 0; --  53  ✅ 正确
```

**后果**：任何新写的 SQL 只要用 `medium_ratio > 0` 判断"这商品有没有中单位"，就会把 157 个根本没有中单位的商品也算进去 → 均单目标、加单分配、箱数换算**全部算错，且不报任何错**。

> 好消息：前端已有的 `perCase()` 函数里写的是 `Number(arc.medium_ratio) || 0`，JS 的 `Number('')` 是 0 ⇒ **前端是安全的**。所以这是"新代码别踩"的问题，不是"现有代码坏了"。

**本方案的纪律**：所有单位判据收在**一处**（后端 `db/queries/products.py` 新增一个 `unit_levels_sql()` / `per_case()` 实现），SQL 一律用 `CAST(... AS REAL)`，禁止在业务代码里散写 `medium_ratio > 0`。

#### 陷阱 B：小程序报单框显示的单位，与 Web 主表**不同源**

- Web 主表「单位」列 = `order_unit` 优先、空回退 `unit`（`order_unit_master_sql()`）
- 小程序报单框 = `/api/products/fill-search` 下发的是 `p.unit`，**没带 `order_unit`**

生产影响面：30 个填了 `order_unit` 的商品里，**只有 1 个**与 `unit` 不同（id=1596）⇒ 当前风险很低，**但均单目标必须"按用户填报单位显示"**，所以这个源必须先统一，否则会出现"提示说 72 包、输入框单位写着组"这类看不懂的界面。

### 2.4 结论：本功能必须复用的三个唯一实现

| 要算的东西 | 复用哪份实现 | 位置 |
|---|---|---|
| 每箱含几个「某单位」 | `perCase(spec, unit, arc)` | 前端 `Forecast.vue:3132` |
| 报单单位名 | `order_unit_master_sql(i)` | 后端 `db/queries/products.py:46` |
| 「合计(箱)」 | `rowBoxes(r)` / `boxesOf()` | 前端 `Forecast.vue:3177` |

**新代码只调用它们，不再写第二份换算。** 这是本项目已经踩过多次的铁律（同一语义两份来源必然漂移）。

## 四、数据模型设计

### 4.1 `product_targets` —— 商品目标主表（新建）

```sql
CREATE TABLE IF NOT EXISTS product_targets (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  name              TEXT    NOT NULL DEFAULT '',   -- 如「9月0糖袋目标」
  period_month      TEXT    DEFAULT '',            -- '2026-09'（月度桶，唯一键之一）
  product_id        INTEGER NOT NULL DEFAULT 0,
  product_name      TEXT    DEFAULT '',
  brand             TEXT    DEFAULT '',            -- 冗余，便于按品牌筛/查规则
  target_qty        REAL    NOT NULL DEFAULT 0,    -- 目标数量（**一律折算到大单位=箱**）
  target_unit       TEXT    DEFAULT '件',          -- 下发时的大单位名（件/箱）
  target_amount     REAL    DEFAULT 0,             -- 目标金额（元；按金额下发时用）
  basis             TEXT    DEFAULT 'qty',         -- 下发口径：qty(按箱) / amount(按金额)
  order_count       INTEGER DEFAULT 0,             -- 本期可报单数（快照，来自 rebate 规则）
  status            TEXT    DEFAULT 'active',      -- active / closed
  created_by        TEXT    DEFAULT '',
  created_at        TEXT    DEFAULT (datetime('now','localtime')),
  updated_at        TEXT    DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_product_target_month
  ON product_targets(period_month, product_id);
```

🔴 **`target_qty` 一律折算成箱**（大单位）入库。理由：
- 厂商下发就是箱，加单列、定稿、"最终下单(箱)"全部以箱为口径，不引入第三种量纲；
- 舟谱也是"以大单位计 / 以小单位计"二选一，不要多造一层。

### 4.2 `product_target_alloc` —— 分解明细（新建）

```sql
CREATE TABLE IF NOT EXISTS product_target_alloc (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  target_id     INTEGER NOT NULL,
  employee_id   INTEGER NOT NULL,
  employee_name TEXT    DEFAULT '',
  ratio         REAL    NOT NULL DEFAULT 0,   -- 占比（百分数，0~100）
  target_qty    REAL    NOT NULL DEFAULT 0,   -- 分解目标（箱）= 主表 target_qty × ratio/100
  sort_no       INTEGER DEFAULT 0,
  created_at    TEXT    DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_pt_alloc ON product_target_alloc(target_id, employee_id);
```

**服务端硬校验**：`Σ ratio` 必须 = 100（容差 0.01），否则 422 拒绝。前端实时显示"当前合计 98%，还差 2%"。

### 4.3 `forecast_extra_alloc` —— 加单/减单分配到人（新建）

```sql
CREATE TABLE IF NOT EXISTS forecast_extra_alloc (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  period_start  TEXT    DEFAULT '',     -- 与 forecast_extra_qty 同键
  period_end    TEXT    DEFAULT '',
  product_id    INTEGER DEFAULT 0,
  employee_id   INTEGER DEFAULT 0,
  employee_name TEXT    DEFAULT '',
  target_id     INTEGER DEFAULT 0,      -- 来源目标（可追溯）
  ratio         REAL    DEFAULT 0,      -- 快照：当时的占比
  total_delta   REAL    DEFAULT 0,      -- 快照：经理加单总量（箱，可负）
  alloc_qty     REAL    DEFAULT 0,      -- 分到这个人（箱，可负）
  reason        TEXT    DEFAULT '',     -- 通知里要说明的原因
  created_at    TEXT    DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_fea ON forecast_extra_alloc(period_start, period_end, product_id, employee_id);
```

**为什么不是改 `forecast_extra_qty` 加人员维度**：
- 那个表的语义是"经理对这个商品的加单总量"，经理视角**只有一个数**，改成按人会让"经理加 60 箱"这件事消失；
- 分配是**派生量**，必须能从总量 + 比例重算出来 ⇒ 单独落表，且**每次保存时与总量同事务重算覆盖**（否则改一次加单、分配不跟着变 = 静默漂移，这是 v229"三档价联动"踩过的同族坑）。

### 4.4 缺口：达成填报 `rebate_achievements` 缺「单位」列

`rebate_achievements` **已经支持商品维度**（`dimension='product'` + `scope_key` + `actual_qty`），但：

| 现状 | 说明 |
|---|---|
| 表结构 | `id / period_month / dimension / scope_key / scope_name / actual_amount / actual_qty / actual_rebate / source / note` |
| 生产数据 | 4 行，**全是 `dimension='brand'`，且 `actual_qty` 全 = 0**（只填了金额） |
| 🔴 缺口 | **`actual_qty` 没有单位列** —— "150" 到底是 150 箱还是 150 包？没人知道 |

**建议补一个 `actual_unit` 列**（vNNN 迁移），并约定 `dimension='product'` 时 `actual_qty` 的单位必须显式记录。**否则需求 2 的公式会因为没有分母单位而算错**。

## 五、核心算法（唯一实现，禁止第二份）

### 5.1 均单目标（需求 2）

```
① 已达成(箱)      = 达成填报该商品本月的 actual_qty  ×  换算到箱
② 已报单数        = 本月该商品已发生的报单期次数
③ 后续可报单数    = 本期可报单数(order_count) − 已报单数     ← 下限 1，不足则提示"目标已无剩余单数"
④ 均单目标(箱)    = ( 月目标(箱) − 已达成(箱) ) ÷ 后续可报单数
⑤ 显示值          = 均单目标(箱) × perCase(填报单位)        ← 复用唯一实现
```

**⑤ 的换算表**（拿 id=1449 走一遍，月目标 150 箱、后续可报 15 单、已达成 15 箱）：

| 用户填报单位 | perCase | 显示值 |
|---|---|---|
| 件（大单位） | 1 | 9 件 |
| **包（中单位）** | `large_ratio ÷ medium_ratio` = 40÷5 = **8** | **72 包** ← 与你说的"9箱即72包"完全一致 |
| 袋（小单位） | `large_ratio` = 40 | 360 袋 |

> ⚠️ 你的例子里 150 箱 ÷ 15 单 = 10 箱，而你说"约 9 箱"。差额来自"已达成"那一项 —— 按 §7-D2 确认口径后数字会自动对上。**公式本身（先减已达成、再除剩余单数）是你原话里的，我没有改动。**

**边界处理**（必须全部处理，否则又是一个"静默失效"）：

| 情况 | 显示 |
|---|---|
| 该商品本期无目标 | 不显示提示（不猜、不填 0 冒充） |
| 换算不出来（档案缺 `large_ratio` 且规格串解析不出） | **不显示数字**，改显示"该商品缺单位换算，无法提示" ← 绝不能静默当 1 |
| 已达成 ≥ 月目标 | "本期目标已达成" |
| 后续可报单数 = 0 | "本期已无可报单数" |

### 5.2 差额合计（需求 4）

```
差额合计(箱) = Σ_承接人 max( 0, 均单目标(箱) − 该人本月已报(箱) )
```

拿你的例子验算：均单目标 11 箱、10 人各报 8 箱

```
每人差 = 11 − 8 = 3 箱
合计   = 3 × 10 = 30   ✅ 与你说的"显示30"一致
```

**语义**：这个数就是**经理该填多少加单**的建议值。所以它显示在「加单」列附近是合理的（落点见 §7-D5）。

**悬停展示的计算逻辑**（你要求的"鼠标悬停时展示"）建议长这样：

```
差额合计 = 30 箱
├ 均单目标 11 箱 = (月目标 150 − 已达成 0) ÷ 可报 14 单
└ 10 人的缺口（只算没报够的）：
   张俊峰  11 − 8 = 3
   刘善涛  11 − 8 = 3
   …（其余 8 人同理）
   合计 30 箱
```

### 5.3 加单/减单按比例分配（需求 6）

```
① 经理在「加单(箱)」填一个总量 D（可正可负）
② 对每个承接人 i：  alloc_i = D × ratio_i / 100
③ 分到人的填报单位值 = alloc_i × perCase(该人的报单单位)
④ 该人定稿量 = 该人本月已报(箱) + alloc_i
```

拿你的例子验算（D = +60 箱，刘善涛 ratio = 10%，报单单位 = 包）：

```
alloc = 60 × 10% = 6 箱
显示  = 6 × 8 = 48 包          ✅
原报  40 包 = 5 箱
定稿  5 + 6 = 11 箱 = 88 包     ✅
```

**舍入纪律**（必须写死，否则总和对不上被用户投诉）：
- 分配额**保留 2 位小数**，不取整 —— 取整会导致 `Σ alloc_i ≠ D`；
- 若 `Σ ratio ≠ 100`（历史脏数据），**按比例归一化后再分**，并回写一份归一化后的快照；
- 展示层显示"约 N 箱"，但**入库/通知用精确值**。

| 后端 | 差额合计接口：按 (期次×商品) 返回 `{差额合计, 每人明细}` |
| 后端 | 定稿时发通知（`message_send(..., recipients=账号id, event_key=...)`） |
| 前端 | 加单列显示差额合计 + hover 展示计算过程 |
| 前端 | 负数视觉提示 |
| 前端 | 分配结果可查看（点开看"谁分到多少、为什么"） |

**验收**：经理加 60 箱 → 刘善涛收到"分到 6 箱（48包）"通知 → 分配明细求和 = 60（误差 < 0.01）→ 改加单量再保存，分配跟着变（无漂移）。

## 七、必须你来拍板的 5 个口径（决策项）

> 这 5 项不定，写代码就是猜。**每项我都给了推荐**，你可以直接回字母。

### D1【最重要】"已达成"取哪份数？

| 选项 | 含义 | 影响 |
|---|---|---|
| **A（推荐）** | 取**达成填报**（`rebate_achievements`，商品维度）的 `actual_qty` —— 就是你说的"系统读取达成填报" | 需要人工在达成填报页填商品数据；**口径与你原话完全一致** |
| B | 取系统内**报单已提交**的数量（`forecast_submission_items` 汇总） | 全自动，不用人填；但和你说的"达成填报"不是一回事 |
| C | 两者都要，谁有数据用谁 | 会出现"同一屏两个数"，需明确优先级 |

**我推荐 A** —— 你的原话就是 A，且 A 的语义更准（"达成"是厂商认的销量，不是我们内部的报单量）。
🔴 **但要注意**：A 需要有人在达成填报页**按商品**填数，而生产库现在 4 行全是品牌维度。**这是个新的人工动作**，如果没人填，均单目标会退化。

### D2【必答】"后续可报单数"怎么算？

| 选项 | 含义 |
|---|---|
| **A（推荐）** | 用品牌规则里的 `arrival_count_override`（生产实测：蒙牛低温 = **15**），减去本月已发生的报单期次数 |
| B | 按到货节奏实时推算（每 2 天一次 ⇒ 从今天到月末还有几单） |
| C | 固定值，让经理自己填 |

**我推荐 A** —— 15 这个数正好是你说的"可报15单"，说明你心里就是这把尺。B 更"活"但会随日期漂移，同一笔目标今天看 9 箱、明天看 10 箱，经理会困惑。

### D3【必答】减单的分母也是同一比例吗？

你的原话是"减单同理按比例扣减"。确认一下：**减单就是 `alloc_i = D × ratio_i / 100`（D 为负），不做任何保护？**

- 若某人扣完之后变成负数（例如他只报了 5 箱、却要扣 6 箱），是
  - **A（推荐）** 允许负（如实反映），并在通知里点名；
  - B 夹断到 0，其余人分摊差额（更"好看"但会失真）。

### D4【必答】目标的"月"与报单的"期次"怎么挂钩？

系统里是两层时间：**目标按月**（`2026-09`），**报单按期次**（9/24~9/25 这种两天的窗口，一个月有 15 个）。

- **A（推荐）** 目标挂月，期次自动认领同月目标（一个月内所有期次共用同一份均单目标，已达成逐期累加）
- B 目标直接挂到具体期次（更精细，但厂商下发的本来就是月目标，多一层没意义）

### D5【UI 落点】"差额合计"显示在加单列的哪个位置？

| 选项 | 形态 |
|---|---|
| **A（推荐）** | 加单列**表头**显示合计（如「加单(箱) · 差 30」），hover 出计算明细 |
| B | 加单**单元格**内浅色水印提示，点了可以"一键填入" |
| C | 单独新增一列「差额合计」 |

**我推荐 A + 一个"填入"小按钮** —— 符合你"工具栏不新增按钮"的一贯偏好，且这个数就是要填进加单框的，点一下就填最顺手。

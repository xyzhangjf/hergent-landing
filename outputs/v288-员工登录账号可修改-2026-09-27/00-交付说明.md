## 一、你提的两件事，各是怎么落的

### 1. 先纠正一个前提（不是缺陷）

上一轮我留下一个疑点：「`liuxiaoding` / `liushantao` 的 `password_changed=0`，是不是他们登不进去？」
你回「**没有登录过、还在测试阶段、还没给他们配账号**」。

⇒ 这不是缺陷，是**未使用状态**（首登强制改密，人还没登过）。**该疑点已作废，无需排查。**

### 2. 主体需求：账号名也能改

**病根不是「没做」，是「只做了一半」**：

- 后端**早就有**改用户名的能力 —— `PUT /api/auth/profile`（`routers/auth.py:243`，自带长度校验 + 查重）。
- 但它只改**自己**（`WHERE id = 当前登录用户`）⇒ **老板替员工改**这条路根本不存在。
- 而员工档案弹窗的账号管理区只有「重置密码 / 禁用账号 / 生成重置码」，**唯独没有改账号**。
- ⇒ 结果就是你说的那件事：**账号名建错了，只能删账号重建** —— 而删账号会连带丢掉报单配置与工资条链路。

### 为什么强调「唯一实现」

账号名有**两个写入口**（本人自助 / 老板代改）。两份实现必然各漏一半副作用 ——
原 `profile` 那条路就漏了「`phone` 跟随」和「未用重置码同步」：
改完账号名，`users.phone` 还留着旧名，而员工手里那张一次性重置码**当场失效**。

### 三处必须跟着动 / 不能动的副作用

| 对象 | 处理 | 理由 |
|---|---|---|
| `users.phone` | **仅当它逐字等于旧账号名**时才跟随 | 建档时 `phone` 是账号名的拷贝；若是**真实手机号**则绝不动（否则把手机号冲掉） |
| `password_reset_codes.username` | 同步（只改**未使用**的码） | 重置码是按 `username COLLATE NOCASE` 查的；不同步 = 员工手里那张码失效 |
| `login_logs` / `login_attempts` / `audit_logs` | **绝不动** | 那是历史事实，改了等于篡改审计 |
| 审计日志 | 记「旧名 → 新名」 | 原来只写「修改个人资料」，查不出改了哪个字段 |

## 五、过程中被挡下的三个真缺陷（都是「假 PASS」形态）

1. **`admin` 本体也能被改名** —— 不只是「不能改成 admin」。若把 `admin` 改成别的名字，
   `core._init_users()` 下次启动查不到 `username='admin'` ⇒ **凭空再建一个随机密码的管理员**
   （密码只打进日志，谁也不知道）。**单测 C13 挡下的。**
2. **用 HTTP 返回码判端点是否注册 = 假判据** —— 未登录打 `/api/users/4/nonexistent` 同样返回 **401**
   （存在 `/api/{full_path:path}` 兜底路由 + 认证中间件在**路由匹配之前**拦截）。
   唯一可靠判据 = **直读 `server.app.routes`**。**差一点又交出一份「假 PASS」。**
3. **单测 C21 曾「假通过」** —— 补丁没生效，导致内部逻辑根本没走到被测路径，靠另一条连接「碰巧」通过。
   ⇒ 修完重跑才 35/35 可信。

## 一、结论（先讲）

> **「取消」本身没有故障。** 它老老实实调了 `loadCross()` 重取服务端数据。
> 真正的问题是：**你导入时，那一期还不存在** —— 154 个商品被登记进了**上一期（已关闭的「9月提审期-开放填报」）**。
> 而**新建期次之后，页面下拉已经跳到新期次、表格却还挂着旧期次的 154 个商品**，
> 所以「改单 → 取消」时你第一次看到 12 期的**真实状态（空）**，感觉像是取消把数据删了。

一句话说清：**下拉说 12 期，表里装的是 9 期。点「改单」才第一次真的去拉 12 期。**

前端行底公式（`Forecast.vue:1937` `buildRowBase`）：
- 不勾「显示全部商品」→ 行底 = **本期导入登记 ∪ 本期有报单的商品**

**这条公式是 v179 的有意设计**（你当时的原话：「模版里有多少产品，导入后就只有那么多产品」）。
它没错 —— 它精确地告诉你「**12 期确实一个商品都没有**」。问题在于**没有告诉你为什么**。

## 五、根因：后端按设计执行，坏在「页面默认选中」这句前提失效了

`import_router.py:433` 把归属判据写得很明确：

> 导入归属期次 —— 硬判据：**导入落的期次必须等于用户打开页面时默认选中的那个期次**
> （`GET /api/forecast/periods` 的 `current` 字段）。否则会出现「导入成功了，但打开页面看不到」
> —— 用户只会认为数据没进来。

**这条设计是对的，而且它生效了**：导入时 `current` = 9 期，数据落 9 期，页面也显示 9 期，三者一致。✅

**但「页面默认选中」这件事，`loadPeriods()` 每次都会重新算，而表格不会跟着重算。**

```js
// Forecast.vue:6654  createPeriod()   ← 元凶
await forecastApi.createPeriod(b)
toast('期次已创建', 'success')
showNewPeriod.value = false
np.value = { ... }
await loadPeriods()          // ← 只刷新期次名册
                             //   loadPeriods() 内部会把 curPeriod 改成新期次
                             //   （因为新建后 current 就变成它了）
                             //   ★ 但从不重载汇总表 ★
```

```js
// Forecast.vue:6829  loadPeriods()
const cid = d.current ? Number(d.current.id || 0) : 0
if (d.current) curPeriod.value = cid     // ← 下拉跟着变
// 表格数据不变 ⇒「下拉的期次」与「表里的期次」从此不同源
```

**同族对比（说明这不是「设计如此」，而是漏了一处）**：

| 期次变更入口 | 是否重载表格 |
|---|---|
| `onPeriodChange()`（下拉切换，6294） | ✅ 重载（`viewPeriod=null` + `loadOrders()` + 按态 `loadCross/loadEditGrid`） |
| `gotoPeriod()`（多期滚动按钮，5515） | ✅ 重载 |
| `confirmDelete()`（删期次，6328） | ✅ 显式清空 + 重置 |
| `savePeriodEdit()`（改期次，v180 新加） | ✅ 本轮 v180 已补 |
| **`createPeriod()`（新建期次）** | ❌ **只刷下拉，不重载** ← 你踩的就是这个 |

v180 我给「改期次」补了重载，**但「新建期次」这条老路径漏了** —— 同族两处只补了一处。

| 项 | 判定 |
|---|---|
| 数据丢了吗？ | **没丢**。154 个商品登记完好，在 9 期（`forecast_import_products` 154 行） |

## 七、修复方案（按优先级）

### F1「P0」新建期次后必须重载表格 —— 复用期次切换的唯一收口

**不要新写一份重载逻辑**（那就是第二份实现，必然漂移），直接复用 `onPeriodChange()`：

```js
// createPeriod() 末尾
await loadPeriods()
onPeriodChange()   // 期次切换的唯一收口：清 viewPeriod + loadOrders + 按当前态重载
```

改动量：**1 行**。收益：整类「下拉与表格不同源」在此入口彻底消失。

### F2「P0」空态必须可行动 —— 说出「你的商品在哪一期」

现在 12 期的空态只有一句「暂无预报数据」，用户只能理解成「数据丢了」。改为：

> 本期（9月15日报单9月19日到货）还没有商品。
> 你最近一次导入的 **154 个商品**登记在「**9月提审期-开放填报**」（**已关闭**）—— [去查看] [重新导入到本期]

判据：空态必须让用户能**自己回答「我的数据去哪了」**。这正是本项目既有铁律
「空态文案不可行动 + 空态缺 `v-else`」的同族问题。

### F3「P1」取消语义收口 —— 把「取消」真正做成「回到进入编辑前」

`enterEdit()` 强改了两样东西，`exitEdit()` 都没有还原：

1. **`viewMode = 'cross'`**（2462 行）—— 若你在「逐单补录」视图点改单，取消后不会回到那个视图。→ 进入编辑前记一个 `viewModeBeforeEdit`，取消时还原。
2. **草稿被只读视图覆盖**（`Forecast.vue:4540` 的 `watch(() => cross.value)`）：
   `loadCross()` 会给 `cross.value` 换一个新对象 → 触发 watcher → **800 毫秒后 `saveDraftNow()` 把只读视图写进本地草稿**。
   于是「取消」弹窗里那句 **「已录入的数量仍存于本地草稿，再次点「编辑」可恢复」**
   —— **下一轮进入编辑时恢复的是只读视图，不是你的录入**。这是**承诺失效**。
   修法：`loadCross()` 赋值前也置 `_ignoreNextWatch = 1`（现在只有 `loadEditGrid` 置），
   让**只读态永不写草稿**；草稿只由编辑态产生。

### F4「P1」导入落到「已关闭」期次这件事，要显式告知（**需你拍板**）
- 事实：`forecast_period_default()` 的函数文档**自称「仅展示用」**，还专门警告
  「放宽它会静默改变落库归属，属破坏性变更」；而 `import_router` 拿它当了**落库归属**的兜底。
- 后果：一个 open 期次都没有时，导入会静默落到**已关闭**的期次。而全系统其它写路径都拒绝 closed
  （改期次拒绝、删期次要求先 closed）—— **口径不一致**。
- 建议（不改后端）：v180 已在导入弹窗 pick 步显示「本期归属」，**再加一句状态**——
  目标期次已关闭时并列显示「（已关闭，关闭即定稿）」，让用户在点「导入」前就知道。

### F5「需你授权」把 154 个商品挪到 12 期
两条路，**推荐 ①**（不改数据、可自证）：
1. **直接重新导入一次**。我已实测：`GET /api/forecast/periods` 的 `current` **现在 = 12 期**
   （它是唯一 open 期次），所以这次导入会正确落到 12 期。
   台账 `forecast_import_products` 是 **只增不删**、按 `(period_id, product_id)` 幂等，
   因此**不会动到 9 期已有的 154 行**；「清切片」只清 `role='导入'` 的报单（9 期的 2 条不受影响）。
2. 直接改库迁移台账 `period_id` —— 属生产写，需你显式授权 + 在线备份 + 逐项断言。

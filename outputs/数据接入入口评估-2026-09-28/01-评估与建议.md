# 是否新增「数据报表」入口 —— 评估与建议

> 日期：2026-09-28　｜　评估人：AI 助手
> 起因：老板提议「参考舟谱截图新增一个『数据报表』入口，用于解决用户手动上传数据和归档的问题」，
> 并要求覆盖 4 个要点（定位与边界 / 下游价值 / 落地成本 / 便利性与可持续性）。
> **核实方式：实读两个仓库源码 + 只读生产接口取证，不凭印象下结论。**每条结论附 `文件:行`。

## 〇、结论先行

### 一句话

> **需求是真的，入口方案是错的。**
> 「手动上传」**已经建好并且已经在跑**，真正缺的不是一个入口，而是**一份"数据全不全、新不新"的台账**，
> 以及**4 个类目的界面**和**原始文件的留档**。

### 三条硬事实（决定了不建议按截图做）

| # | 事实 | 取证 |
|---|---|---|
| 1 | **名字与用途是反向的**：舟谱的「数据报表」是**输出**（报表矩阵：往来/资金/市场/经营分析…）；老板要用它承载的是**输入**（上传通道）。用"输出"的词命名"输入"的功能 = 我们反复在修的「名不副实」再造一个（参见 `docs/AI能力对照表.md` 第二节）。 | 截图；`docs/AI能力对照表.md:47-54` |
| 2 | **手动上传已经存在，而且有 4 条已接线的路径**（见 §三）。更关键：**3 天前（2026-09-25）刚把「舟谱导入」从侧栏撤下来**，理由写在代码里 —— *「用户不认可为一个低频动作占一行侧栏」*。现在再加一行侧栏 = **3 天内自我推翻**。 | `routers/zhoupu_documents.py:36-45` |
| 3 | 项目里已有一条**明文纪律**：「上传能力与注册后的『上传第一份数据』弹窗**同一个接口** ⇒ **避免出现两套导入入口**」。再加一个 = 第三套。 | `src/pages/Workbench.vue:13-15` |

### 建议（优化后的方案，详见 §六）

> **不加侧栏一级入口。**改为：
> **① 在「能力中心」增设一个「数据台账」区块**（回答"我的数据全不全、上次什么时候传的"）
> **② 补齐 4 个类目的上传界面**（客户 / 应收 / 订单明细 / 客户专属价 —— 后端全就绪，只差前端接线）
> **③ 打通「企微转发 Excel 即入库」**（这是唯一能真正把上传负担降到接近零的路，且后端已写好、只差调用方）
> 若台账日后确实变重、需要独立成页，**页面名用「数据管理」，不要用「数据报表」**。

## 一、入口的定位与适用边界（要点 1）

### 1.1 边界**已经存在**，而且已经在界面上分开了

老板描述的边界（"有 API/MCP 的不需要这个界面；舟谱这类没有接口的走手动上传"），
**在「能力中心 › ERP 数据源」里已经是一个区里的三张卡**：

| 卡片 | 通道类型 | 界面上怎么表现 | 取证 |
|---|---|---|---|
| 畅捷通 / T+ | **OAuth 授权** | 「去连接 / 管理」，状态「待授权 / 已连接」 | `ConnectCenter.vue:182-195` |
| 金蝶 / 云星空 | **OAuth 授权** | 同上，另含库存 / 订单 | `ConnectCenter.vue:196-208` |
| 舟谱 / 导出表 | **人工上传 Excel** | 卡片注释明写「**不是 OAuth** —— 人工上传 Excel 的通道」，**因此不摆「断开/同步」按钮**（没有对应语义的动作就不摆按钮） | `ConnectCenter.vue:209-221` |
| MCP 连接 | **未开放** | 「开发中，暂未开放」 | `ConnectCenter.vue:224-227` |

**⇒ 结论：这条边界不需要新入口来"建立"，它已经建立了。**
需要补的是"**这条边界在界面上被讲清楚**"—— 现在只有舟谱一张卡，且用户很难一眼看出
"我是哪种客户、我该走哪条路"。

### 1.2 边界的判据表（建议直接搬进界面文案）

| 客户情形 | 数据怎么进来 | 需要"上传界面"吗 | 说明 |
|---|---|---|---|
| 用畅捷通 / 金蝶 | OAuth 授权 + 全量同步 | **不需要** | 授权一次，之后自动同步 |
| 用有开放平台的其他 ERP | API / MCP 连接器 | **不需要** | MCP 尚未开放；API 连接器按客户单独立项 |
| **用舟谱等封闭系统** | **人工上传 Excel** | **需要** | 舟谱无公开自助 API（其"系统对接"是面向品牌商的 B2B 实施服务） |
| 纯手工记账 / 无系统 | 人工上传 Excel 或直接录入 | **需要** | 与上一行同一条路 |

### 1.3 一个必须说清的边界（否则会误导销售与客户）

> **本入口解决的是「数据进得来」，不是「数据自动更新」。**

手动上传通道的**本质缺陷**是：它**不会自己变新**。客户今天传了应收，明天收回了 3 万，
系统里还是昨天的数 —— 而 AI 会**拿旧数当真数讲话**。
所以这条通道**必须配一个"数据新鲜度"提示**（见 §六 建议①②），否则它产出的不是"数据"，
而是**过期的确定性错觉**——这比没有数据更危险。

## 二、建成后对下游工作的价值（要点 2）

### 2.1 最硬的证据：导入类目 = AI 只读工具的数据底座（几乎一一对应）

AI 的手脚（`server/ai_tools.py`，11 个**只读** SQL 工具）读的表是：

```
FROM contacts          ← 客户        ← 导入类目 `contacts`
FROM products          ← 商品        ← 导入类目 `products`
FROM inventory         ← 库存        ← 导入类目 `inventory`
FROM receivables       ← 应收        ← 导入类目 `receivables`
FROM sale_orders       ← 销售单      ← 导入类目 `order_items` / 舟谱单据
FROM sale_order_items  ← 销售单明细  ← 同上
FROM expense_orders    ← 费用单      （暂无导入类目）
```
（`grep -o 'FROM [a-z_]*' server/ai_tools.py`，7 张表）

> 🔴 **判据：这些表空着，副驾就只能"讲道理"，不能"讲你的生意"。**
> 产品对外讲的核心差异是"AI 坐在你的真实数据上"—— 那么**数据能不能进来，就是产品成立与否的前置条件**，
> 不是"一个锦上添花的功能"。

### 2.2 逐类目的下游支撑表

| 导入类目 | 落库 | 直接支撑的下游工作 | 代码/功能取证 |
|---|---|---|---|

| `receivables` 应收 | `receivables` | **应收台账 / 账龄 / 催收 / 信用评级** | `reconciliation.py`、`dunning.py`、`reports.py:162` |

### 2.3 价值排序（按"没有它下游就废了"排）

| 排名 | 类目 | 缺了会怎样 |
|---|---|---|
| ★★★ | **客户 + 商品** | 报单无法发起（档案是硬门槛）⇒ 主流程走不动 |
| ★★★ | **预报订单 / 舟谱单据** | 算不出提货与达成 ⇒ 返利、业绩提成全空 |
| ★★ | **库存效期** | 临期/货损/效期三个功能全部空转 |
| ★★ | **应收** | 催收、账龄、信用评级无输入 |
| ★ | **客户专属价** | 报价退回兜底价（**注意：`contacts.channel_id` 列从未被创建过，有守卫 ⇒ 会永久落兜底价且零报错**） |
| ★ | **员工** | 算工资无基数（现网仍有 7 名员工 `salary_structure` 待补） |

> 🔴 **这解释了老板为什么会有"想加个入口"的直觉** —— 因为**下游功能的完备度远高于输入端**，
> 于是"进不来数据"变成了整条链路的瓶颈。直觉是对的，**只是解法不该是"再加一个入口"**。

- 8 个类目 + 3 条摄入路径 + 回执/撤销/映射记忆，是**已经过了工程化的地基**，不是原型；
- 补齐后能**立刻**把 §二 的下游功能从"空转"变成"有数"。

**反面（必须警惕的理由 —— 本项目已经踩过）**
- **后端有 ≠ 值得暴露**。现成的两个"僵尸能力"就是反例（覆盖数**都是实 grep 的 0**）：

- 所以**不能因为"后端有"就顺手全摆上界面** —— 摆上去的每一个入口都要有人用、有人维护、有人解释。
  这正是本轮要防的：**别为了"看起来功能全"而制造一批没人用的入口。**

## 四、上传便利性与可持续性（要点 4）★ 本评估的重点

### 4.1 直接回答：**要求用户"每天上传"是错的**，三条理由

**理由一：节奏错配（用真实数据说话）**

线上真实期次（只读取证）：`2026-09-22/23`、`2026-09-24/25`、`2026-09-26/27` —— **报单约每 2 天一期**。

但"报单"和"上传数据"**根本不是一件事**：

| 动作 | 谁产生 | 频率 | 需不需要"上传 Excel" |
|---|---|---|---|
| 报单（下单） | 我方业务员/主管 | **约 2 天/期** | ❌ **不需要** —— 已经在系统里填报（小程序/网页） |
| 舟谱提货 / 结算 | 舟谱系统 | **按厂家对账周期（月）** | ✅ 需要，但是**一个月一次**的量 |
| 库存 / 效期 | 仓库 | **周** | ✅ 需要 |
| 应收 / 回款 | 财务 | **按对账/回款周期** | ✅ 需要 |
| 商品 / 客户 / 员工 / 专属价 档案 | 一次性 | **建档一次 + 变更时** | ✅ 一次性 |

⇒ **"每 2 天的报单"是系统内动作，不该被误当成"每 2 天要上传一次"的理由。**

**理由二：边际价值递减，但用户的成本是恒定的**
档案类数据（商品/客户/员工）**每天上传 100 次，内容也一样**。
如果 UI 不做增量判断，用户每次都在重复劳动，而系统里什么都没变 —— **这是纯损耗**。

**理由三（最重要）：它把系统的内耗转嫁给用户**
用户为了用我们的 AI，**已经在舟谱里做过一次导出**。再要求他每天做一遍，
等于我们向他收一道"人工数据搬运税"。
**而这个税正是我们相对舟谱的差异化要解决的问题** —— 让用户为了用 AI 而多干一份活，
是把产品的核心卖点反向做成了成本。

> 🔴 **一条判据（建议写进产品纪律）**：
> **凡"为了用这个功能，用户每个周期都要多做一个动作"的设计，默认不通过**，
> 除非能证明该周期发生了**新的、他本来就要处理的业务事件**。

### 4.2 正确的模型：**挂在用户本来就要做的事上**（事件驱动，而不是新增日常任务）

> 不要新增"每天上传"这个任务；要让上传**发生在业务动作的顺路上**。

| 触发时机（用户本来就要做的事） | 顺带完成的上传 | 谁受益 |
|---|---|---|
| **每期报单时**（每 2 天） | 顺手导一次商品/客户（只在有新增时） | 报单主流程 |
| **每月厂家对账时** | 导舟谱销售结算 / 调拨单 | 达成 / 返利 / 提成 |
| **每周盘库存时** | 导库存效期表 | 临期 / 货损 |
| **每次对账/催收时** | 导应收台账 | 催收 / 账龄 |
| **新客户开户时** | 补一条客户 + 专属价 | 报价 / 千店千价 |
| **新员工入职时** | 补员工 + 工资结构 | 算工资 |

### 4.3 降低操作负担的四招（按性价比排序）

| 优先 | 招 | 现状 | 说明 |
|---|---|---|---|
| ★★★ | **企微/微信转发 Excel 即入库** | 🔴 **后端已写好、但没有调用方** —— `import_router.py:2819` 的注释原文就写着「**webhook/企微转发用**」，而全仓 `grep` 无任何调用者（前端、后端、cron 全无） | 用户**本来就把文件发在群里**。转发给一个机器人 = **零新增动作**（这是唯一"不增加工作量"的方案）。技术底座已有：Hermes 网关已支持企微通道 |
| ★★★ | **一次拖多个文件 + 自动判类目** | `smart-parse`（`import_router.py:2709`）已具备，且**副驾抽屉已在用**（`CopilotDrawer.vue:1278`） | 把"先选类目再选文件"反过来：**先丢文件，系统告诉你是谁** |
| ★★ | **映射记忆 + 增量识别** | `mapping-memory` 已具备（`import_router.py:1471`，按表头指纹归一存储）；增量开关已在 `ImportMapping` 组件上 | 同一种表第二次不再问映射；"上次 100 行、这次 103 行"只处理新增 3 行 |
| ★★ | **台账驱动"该更新了"** | **缺** —— 没有任何"数据新鲜度"提示 | 让系统告诉用户"应收数据已 32 天未更新"，**而不是让用户记周期** |
| ★ | 定时提醒（企微推送） | 底座有（`cron_tasks.py` + 企微通道） | 兜底，但**不要做成每日骚扰** |

### 4.4 建议的频率与提醒节奏（可直接落进台账页）

| 数据类目 | 建议频率 | 提醒方式 | 依据 |
|---|---|---|---|
| 商品 / 客户 档案 | **一次性 + 变更时** | 不提醒 | 数据本身不天天变 |
| 库存 / 效期 | **周** | 超过 14 天未更新 ⇒ 工作台一条提示 | 临期是周级决策 |
| 应收 | **按对账/回款周期（月/半月）** | 超过 30 天未更新 ⇒ 提示 | 回款周期 |
| 舟谱提货 / 结算 | **月（对账时）** | 到"该对账了"时提示 | 厂家对账周期 |
| 预报 / 报单 | **期次驱动** | 不提醒（本来就在系统内做） | 约 2 天/期 |
| 员工 / 工资结构 | **入职/调薪时** | 算工资前校验缺失 | 现网仍有 7 名员工待补 |

> ⚠️ 上表的**频率是"上限"不是"任务"**：到期没传**只提示、不阻断**，且提示要能一键静音。

## 五、边界情形：三种客户，三种处置

| 情形 | 处置 | 理由 |
|---|---|---|

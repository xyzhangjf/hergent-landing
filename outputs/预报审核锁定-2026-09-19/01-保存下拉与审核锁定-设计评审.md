## 0. 一句话结论

**交互方向合理，但不能就这么做。** 你要的「保存并审核」在系统里**已经存在**（叫「提交审批」），真正缺的**不是按钮，是"锁"** —— 系统从建库到现在，从来没有过任何服务端"不可编辑"语义。

所以这个需求实际是两件事，第二件才是重点：

| | 内容 | 成本 |
|---|---|---|
| 表面 | 把两个动作合并进一个下拉 | 低（纯前端） |
| **实质** | **给期次引入第一个服务端"锁"** | **中高（前端只是三分之一）** |

如果只做表面那件（下拉 + 前端禁用输入框），你会得到一个**看起来锁了、其实谁都能改**的期次 —— 这是最坏的形态，比不做还糟：它让人以为数据已经定稿。

## 1. 先说三个已证实的事实（方案的形状由它们决定）

这三条都是本轮实际读代码取证的，不是推断。

**① 系统里已经有一整套审批状态机 —— 五态，且已上线**

`routers/forecast_config.py:454`：

```python
nxt = {"submit": "submitted", "approve": "approved",
       "reject": "rejected", "revise": "revised"}.get(action, cur)
```

前端对应五个按钮（`Forecast.vue:1225-1229`），并且有中文标签表：

```js
SUB_LABEL = { draft:'草稿', submitted:'待审批', approved:'已通过',
              rejected:'已驳回', revised:'退回修改' }
```

**② 这个状态存在一张 KV 表里，且是租户级的**

`forecast_config.py:38`：`CREATE TABLE forecast_config(kind PK, payload, updated_at)`，键为 `approval:<period_id>`。
它落在**租户库**（`db.get_db_tx()`）⇒ 天然租户隔离，不会被别的客户看到。这点是好的，可以复用。

**③ 🔴 但它**完全没有锁的作用** —— 这是需求存在的真正原因**

全仓检索 `subStatus`，只出现 5 次：定义、两处赋值、审批弹窗 5 个按钮的 `disabled`、以及回写 ERP 的前置校验。
**没有任何一处拿它去禁用编辑。**

而后端 `save_matrix`（`forecast_submissions.py:317`）的**全部**入参校验是：

```python
if not start or not end or not customers or not isinstance(rows, list):
    raise HTTPException(400, "缺少 start/end/customers/rows")
```

**没有一行检查期次状态。** 连 `forecast_periods.status='closed'` 都不拦 —— 那个 `'open'` 只用在"前端没传 period_id 时猜哪一期"的回退分支里（`save_matrix` 的注释自己写着：「① 编辑**已关闭**的历史期次 → 恒解析到 0」，即**已知且有意允许编辑已关闭期次**）。

**⇒ 结论：现在整条链路上，"不可编辑"这个能力是零。**

## 2. 交互设计合理性评估

### 2.1 合理的部分（不是全面否定）

- ✅ **"保存"与"提交"确实是同一次编辑会话的自然终点**，绑在一起减少一次操作 —— 这个动机成立。
- ✅ **现状的审批入口确实太深**：藏在「编辑态 → 工具箱 → 审批流」三级之下（`Forecast.vue:86/89`）。一个经理每天要做的动作埋在工具箱里，是不合理的。你想把它提出来，方向对。

### 2.2 三个风险（按严重度排序）

#### 🔴 R1（最高）｜不可逆动作与可逆动作同源，误触代价不对称

| 动作 | 可逆性 | 副作用 | 失败后 |
|---|---|---|---|
| 保存 | **可逆**（有「回退」、有草稿） | 无 | 重试即可 |
| 保存并审核 | **不可逆**（要别人退回才能改） | 他人可见、进入流程、**锁定本期** | 本期锁死，需要解锁 |

把具有**完全相反可逆性**的两个动作放进同一个下拉，用户肌肉记忆是"点保存看状态条"（这个习惯是 v201 刚培养起来的，编辑组里就摆着常驻状态条）—— 下拉第二项**就在鼠标下方一行的距离**。
这一条不是理论风险：**用户刚在 v201 这一轮明确要求过「保存后状态必须可见」**，说明"点保存 → 看确认"已经是他固化的操作习惯，下拉恰好会在这个路径上埋一个陷阱。

#### 🔴 R2｜与已有「提交审批」**等价** ⇒ 假旋钮

铁律（`cross-domain-iron-laws.md:31`）判据三步，逐条套：

| 判据 | 本题 |
|---|---|
| ① 界面上哪个数字/哪条行为会变？ | 会（进入 submitted 态）—— **过** |
| ② **是否与已有机制等价？** | **是。** `doSubmit()` 写的正是同一个 `approval:<pid>` 的 `submitted` | 
| ③ 效果是否稳定/不反噬？ | 取决于拍板项，见 §5 |

②判定为"等价"⇒ 如果新按钮**自己另写一个状态字段**，就会和 `approval:<pid>` 形成**两个真相源**。这正是本仓最常见的事故形态（「同一规则的第二份拷贝 = 静默漂移温床」）。**必须复用，不能新建。**

#### 🔴 R3｜「不可编辑」的爆炸半径没有被定义

"进入不可编辑状态"这句话在实现层至少要回答 6 个问题，而需求里都没说：锁谁、锁什么、锁多久、谁能解、锁了解不开怎么办、只读动作是否也被锁。**这是本需求最贵的地方**（§5 逐条拆）。

### 2.3 我的建议：保留下拉，但改三处

1. **改名字：叫「保存并提交审核」，不叫「保存并审核」。**
   "审核"是**审批人**的动作（就是现有的"通过"按钮）；提交人做的是"**提交**审核"。叫「保存并审核」会让用户（以及后来的开发者）以为这一个按钮做完了他和经理两个人的事 —— 而系统里这两件事**是两个状态、两个人**。这是语义错误，不只是措辞偏好。

2. **加二次确认，且确认框里必须写清后果与解除方式。**（本页已有 `window.confirm` 惯例，如 `delRowSoft` 与 `enterEdit`）
   文案要点：提交后**本期将不能修改** → 需要**退回修改**才能改 → 怎么找人退回。不能只说"确认提交？"。

3. **复用状态机作为锁的判据，不新增字段；把"解锁"接到已有的「退回修改」上。**
   这样"锁"不是一套新机制，而是既有状态的**派生后果** —— 只有一个真相源。

## 3. 实现思路

### 3.1 状态落点：复用 `approval:<period_id>`，**不新建字段**

```
forecast_config(kind='approval:<pid>', payload={"status":..., "by":..., "at":..., "reason":...})
```

- 已有、已上线、租户隔离（在租户库里）、已有审计留痕（`_append_audit` 记 `submission.*`）。
- **严禁**再往 `forecast_periods` 加一个 `review_status` 之类的列 —— 那就是第二份拷贝，两套状态必然打架。
- ⚠️ 已知瑕疵（沿用即可，不必顺手改）：`_get` 在无记录时返回 `[]`（列表）而调用方 `or {"status":"draft"}` 兜底 —— 之所以没炸，是因为 `[]` 是 falsy。**新代码不要依赖这个巧合**，统一写 `st = _get(...) or {}` 再取 `.get("status")`。

### 3.2 后端闸门：这是本需求的主体（前端只占三分之一）

**铁律：前端不是安全边界。** 只在前端禁用输入框 = 纸糊的锁：换个标签页、走导入接口、小程序端，照样写进去。

闸门放在**写入口**，**不是**放在"打开编辑态"：

```python
# 位置：forecast_submissions.py::save_matrix，紧跟在 period_id 解析成功之后
_LOCKED = ("submitted", "approved")
if pid > 0:                      # 🔴 必须判：pid=0 的历史/孤儿路径不受影响
    _st = (_get(conn, f"approval:{pid}") or {})
    if _st.get("status") in _LOCKED:
        raise HTTPException(409, f"本期已{'提交审核' if _st['status']=='submitted' else '审批通过'}"
                                 f"，如需修改请先「退回修改」")
```

**三处必须同时收口**（铁律：杀掉一个入口必须「UI 入口 + 接口写入闸 + 读取端」三处同时改，只改 UI = 第二条写入路径仍在）：

| # | 写入口 | 源文件 | 处置 |
|---|---|---|---|
| 1 | 主表保存 `saveEdits` → `saveMatrix` | `forecast_submissions.py:317` | **加锁闸** |
| 2 | 导入 `doImport` → `/api/import/execute` | `routers/import_router.py` | **加锁闸** |
| 3 | 复制商品清单 `seedFromPrev` → `period_seed` | `erp_db.py:15323` | **加锁闸** |
| 4 | 补录批次资料 `saveGap` | `Forecast.vue:1281` | **加锁闸** |
| 5 | 客户列增删 | 随 1 的 payload 走 | 被 1 覆盖，无需单独处理 |
| 6 | **小程序报单**（写同一个后端） | 共享接口 | 🔴 **最大侧门，见 D5** |
| 7 | 商品档案 `bulkUpsert` | `productsApi.bulkUpsert` | ❌ **绝不能锁** —— 商品档案是**全租户共享**的，锁本期不该锁档案 |
| 8 | 导出 / 打印 / 查看 / 修改日志 / AI 建议（只读计算） | — | ❌ **绝不能锁**，见 D4 |
| 9 | 关闭期次 / 删除期次 | `forecast.py:264/274` | 不属本需求（那是经理层的更高级别动作） |

⚠️ **第 7 条是极易踩的坑**：`saveEdits` 一次调用里**同时**发了「商品档案 upsert」和「本期矩阵 saveMatrix」（`Forecast.vue:3667` 与 `:3714`）。闸门**只能加在 `saveMatrix`**，加在 `bulkUpsert` 上就会"锁了报单、顺手锁掉了商品档案"，而商品档案是全租户共用的，后果远超本期。

### 3.3 前端

1. **下拉**：沿用本页已有的下拉范式（`exportMenuOpen` + `.pop-overlay` + `Teleport`，见 `Forecast.vue:125`），不要新造一套。
2. **主按钮仍是「保存」**（单击直接存，不变），下拉第二项「**保存并提交审核**」，**视觉上必须与前一项不同**（警示色/前置图标），并带 `window.confirm` 二次确认。
3. **提交前置条件**：状态必须是 `draft` 或 `revised` —— 与现有 5 个按钮的 disabled 条件**同源**，不要另写一份判断（第二份拷贝必漂移）。
4. **锁定态渲染**：`enterEdit()`（`Forecast.vue:3048`）入口处加判 —— 若锁定，**不进编辑态**，toast 说明原因与解除路径。
   ⚠️ 铁律「新增开关型状态必须同时给出『状态 → 重建数据』的路径」（只改 ref 不重算 = 假旋钮）：锁定态是**服务端状态**，`enterEdit` 已经是异步的（`await loadEditGrid()`），把状态查询挂在它之前即可，不要只在本地 ref 上做文章。
5. **状态条复用**（v201 三态常驻状态条，`Forecast.vue:118`）：进入锁定态后状态条应显示「**已提交审核 · 不可修改**」而不是「尚未修改」。
   🔴 铁律：「**状态条与它旁边的按钮必须说同一件事**」—— 按钮区若已切成"只读"，状态条就不能还在说"尚未修改"。这两处各判一套必然互相打脸（v201 实测过）。

## 4. 状态切换逻辑

### 4.1 状态 → 可编辑性映射

| 状态 | 中文 | 本期可编辑 | 理由 |
|---|---|---|---|
| `draft` | 草稿 | ✅ | 未提交，正常编辑 |
| `submitted` | 待审批 | 🔒 **锁** | 在流程中；改了会让待审内容与审批人看到的不一致 |
| `approved` | 已通过 | 🔒 **锁** | 已定稿；改动会让审批结论失效 |
| `rejected` | 已驳回 | ✅ 开 | 驳回的**目的就是让他改** |
| `revised` | 退回修改 | ✅ 开 | 这就是"解锁"动作本身 |

**这张表不是新发明的** —— 它与现有 5 个按钮的 `disabled` 条件**天然同构**（能"提交审批"的正是 `draft`/`revised`；能"退回修改"的正是 `approved`/`rejected`）。这也从侧面证明复用是对的：**同一套语义系统里已经用了一遍**。

### 4.2 完整流转

```
                    ┌──────────── 提交审核 ───────────┐
                    ▼                                 │
   draft ──提交──▶ submitted（🔒锁）──通过──▶ approved（🔒锁）
     ▲                   │                           │
     │                   └──驳回──▶ rejected（开）    │
     │                                    │          │
     └──────────── 退回修改 ───────────────┴──────────┘
                     （解锁动作，回到可编辑）
```

关键点：**"退回修改"就是"解锁"** —— 不需要新造一个解锁动作，现有状态机已经自洽。

### 4.3 一次「保存并提交审核」的时序（含失败路径）

```
点「保存并提交审核」
  └─ ① 校验（validateAll / 客户列非空 / 行完整性）        ← 已有的，复用它
      └─ 失败 ⇒ 弹错误清单，**不提交**，状态不变
  └─ ② 二次确认弹窗（写明：提交后本期不可修改 + 如何解除）
      └─ 取消 ⇒ 什么都不发生
  └─ ③ await saveEdits()                                 ← 必须先存成功
      └─ 🔴 失败 ⇒ **终止，绝不推进状态**（见 D3）
  └─ ④ await submissionPost({action:'submit'})
      └─ 失败 ⇒ 数据已存但未提交 ⇒ 必须明确告知"已保存，但提交失败，可重试提交"
  └─ ⑤ 状态 → submitted，页面切只读，状态条更新
```

## 5. 边界情况（按"必须拍板"→"必须处理"→"容易误伤"分三级）

### D0【必须拍板】谁能解锁 —— 现状是个洞

`_subAct`（`Forecast.vue:6248`）**零权限校验**：任何登录用户都能点「通过」「驳回」「退回修改」。
在单店自用场景"能用"，但你的目标是**卖给其他经销商**（B2B SaaS）⇒ 这意味着**任何销售都能自己把自己的单子批了、也能自己解锁**。现有系统里的角色权限体系（`core._DEFAULT_PERMS`）在审批流上完全没接。

**这是本需求必须先决策的一条**，因为它决定闸门是 409 还是会 403。

### D1【必须处理】`pid = 0` 绝不能判

`pid=0` 是"没解析到任何期次"的**兜底路径**，历史上还有孤儿行（记忆：生产有 20 条 `period_id=0` 的登记行）。
闸门**必须** `if pid > 0:` 才判 —— 否则会误伤一条与本期无关的路径。（上一轮 v204 刚在同一个地方踩过同形的坑：整期重排必须判 `_period_id > 0`。）

### D2【必须处理】锁的范围 = "本期矩阵"，不是"这个页面"

最容易做错的是把"锁文档"实现成"锁页面"：把整个工具栏灰掉、导出按钮也灰掉。
**只读动作全部必须保持可用**：导出、打印、查看、修改日志、AI 建议（纯计算）、审批流本身。
判据：**锁的是"写数据的动作"，不是"看数据的动作"。**

### D3【必须处理】"存了一半 + 状态已锁"是最坏结果

`saveEdits` 内部是**两个非事务请求**（先商品档案、后数量矩阵，`Forecast.vue:3667/3714`）。
如果先存商品成功、矩阵失败，然后状态又推进到 `submitted` ⇒ 用户拿到一个**被锁住的半成品**，而且他连重试都做不到（锁了）。
⇒ **次序铁律：存成功之后才允许推进状态**；任何一步失败都不推进。

### D4【必须处理】并发：A 提交后，B 手上还有未保存的改动

B 正在编辑 → A 提交 → B 点保存 → 后端回 409。
**B 的改动不能丢。** 必须：① 明确提示"本期已被提交审核"（区分于一般的保存失败）；② 把 B 的改动**留在页面上**（不清空、不自动刷新），让他能自己复制出去。
反面做法：弹个错误就 `loadEditGrid()` 重新加载 ⇒ B 白干一轮，且他不知道为什么。

### D5【必须处理】小程序报单是最大的侧门

Web 与小程序**共享同一个后端**（记忆：11 个接口被小程序调用）。如果只在 Web 侧加锁，小程序端照样能往本期报单 —— 那就是"门禁只有一半"，锁是假的。
⇒ 必须确认小程序报单写的是**哪张表/哪个接口**：若它写 `forecast_submissions` 的**非 `role='导入'`** 行（销售报单），而锁只判 `saveMatrix`（清 `role='导入'`），则**销售还能往已提交的期次加单**。
**这一条要在动手前查清小程序端的写路径**，否则做完就是漏洞。

### D6【易误伤】定稿（`doAdopt`）的语义是反的

`adopt` 写 `forecast_audit_decisions`，且它**没有**任何状态前置（`Forecast.vue:388` 只判了 `adopting`）。
按业务逻辑，定稿是**审核动作**，应该在 `submitted` 态下才允许、`draft` 态下反而没意义。
现在给它加锁时不要顺手把它一起锁了 —— 它不是编辑动作，它属于审批链。

### D7【易误伤】`approved` 之后的「回写 ERP」必须仍可用

`doWriteback`（`Forecast.vue:6360`）的前置就是 `subStatus === 'approved'`，即它**只在锁态下工作**。
如果"锁"被实现成"禁用所有操作"，回写会被一起误杀。

### D8【易误伤】推送企微审批（`pushForecast`）与新的提交是**两条通往同一状态的路**

`pushForecast` 已经在把内容推到企微审批（`Forecast.vue:90`）。
新动作如果也推进到 `submitted`，就要明确：**它和推送是什么关系**（推送 = 通知，提交 = 状态变更？还是推送会自动提交？）。两条路径必须收敛到同一个状态源，否则会出现"推了但没锁"或"锁了但没推"。

### D9【易误伤】老期次的历史数据

存量期次的 `approval:<pid>` 可能为空（KV 表里没记录）⇒ 按 `draft` 处理 = 可编辑。
这**符合预期**（历史上它们确实没被提交过），但要在文档里写明，避免以后有人看到"历史期次能改"就以为是 bug。

## 6. 验收要点（如果要实现）

**五层验证，缺一层就可能验收出一个假锁：**

| 层 | 验什么 | 判据 |
|---|---|---|
| 1 | 离线：状态 → 可编辑性映射 | 五态逐条断言（含 `pid=0` 不判的阴性对照） |
| 2 | 后端 API：**锁态下写请求真的被拒** | 真实租户克隆库上，`saveMatrix` 应回 409 而非 200 |
| 3 | 后端 API：**只读动作仍可用** | 导出/查询/审批流在锁态下不能回归失败 |
| 4 | 真机：锁态下 `enterEdit` 进不去、状态条与按钮一致 | ⚠️ 真机取数必须带 `Authorization: Bearer` + `X-Tenant-Id`，漏了后端**不报错只给空数组**（上一轮最贵的假红） |
| 5 | **侧门**：导入 / seed / 补录 / 小程序 四个入口逐个打 | 这是最容易漏的一层；只验主路径 = 验了个假锁 |

⚠️ **冒烟脚本绝不点「保存」**：`saveEdits` 没有"无改动就短路"分支，点下去就是真实生产写入。

# 「保存」下拉 + 保存并定稿 —— 简化版设计说明（v205 预案）

> 2026-09-19 · 取代 `01-保存下拉与审核锁定-设计评审.md` 中的**方案部分**（01 的诊断取证仍然有效，其"做审批流"的建议已按用户口径作废）
>
> 用户口径（原话）：「我的需求没有那么复杂，毕竟用我们产品的都是小公司，一般情况下不需要那么多审批，
> 报单人从小程序报单后自动显示到这张报单汇总表上，业务经理会根据指标达成情况改单，改完以后点保存就结束了,
> 不需要做成审批流，老板如果想看报单情况，用自己的账号登进去看就可以了。」

---

## 一、结论

**这不是"新建一个审批流"，也不是"新建一个状态机"——系统里已经有一个现成的「定稿」动作，缺的只是把它接到保存按钮上、并兑现它的承诺。**

| | 内容 |
|---|---|
| 现成的定稿动作 | `forecast_period_close(pid)` → `UPDATE forecast_periods SET status='closed'`（`erp_db.py:15557`） |
| 现成的接口 | `POST /api/forecast/periods/{pid}/close`（`forecast.py:264`） |
| 现成的界面 | 关闭期次确认弹窗（`Forecast.vue:1903-1910`），文案已写「关闭后该期次**不可再编辑**」 |
| 生产上已在用 | 期次表：**4 期 `closed` / 3 期 `open`** |
| **缺的** | 上面那句「不可再编辑」**在代码里没有兑现**（见 §四） |

⇒ 本方案 = **复用 `status` 两态 + 把入口提到保存按钮 + 补上那句承诺**。
**不新增状态字段、不新增表、不做审批链、不做权限流。**

## 二、交互设计

### 2.1 保存按钮改下拉（`Forecast.vue:114`）

```
[ 保存 ▾ ]          ← 主按钮单击 = 立即保存（保持可编辑，与现在完全一致）
   ├─ 保存              保持可编辑，继续改
   └─ 保存并定稿        保存成功 → 本期定稿 → 退出编辑态（只读）
```

- **默认动作不变**：单击主按钮仍是「保存」。老习惯不打断（v201 刚把「点保存 → 看状态条」培养起来，不能在这里改掉手感）。
- **「保存并定稿」必须二次确认**（复用已有的关闭期次弹窗），因为它**不可逆**（见 §五 B1）。
- **不叫「保存并审核」**：这个系统里没有审批人，「审核」二字会被读成"我自己审完了"或"要等别人审"。
  叫「保存并**定稿**」—— 它只表达一件事：**这期就这么定了，不再改**。

### 2.2 定稿后的界面

| 位置 | 定稿后 |
|---|---|
| 「改单」按钮（`:81`） | 禁用，`title` 说明「本期已定稿。如需修改，点『继续修改』」 |
| 保存按钮组 | 整组替换为一个 **「已定稿 HH:MM · 操作人 谁」** 的状态标签 + 一个 **「继续修改」** 按钮 |
| 期次下拉 / 往期列表 | 期次名旁挂「已定稿」标签（与 `open` 区分） |
| 只读浏览 | 完全不受影响（**老板登进来看，本来就是查看态，不是编辑态**） |

## 三、状态切换逻辑（只有两态）

```
                    ┌─────────────────────────────────────────┐
                    │  status = 'open'      【可编辑】         │
                    │  · 「改单」可点                          │
                    │  · 「保存」/「保存并定稿」                 │
                    │  · 小程序可报单（期次在列表里）             │
                    └────────────────┬────────────────────────┘
                                     │ 点「保存并定稿」
                                     │ ① 保存全部成功（必须先成功）
                                     │ ② 二次确认
                                     ▼
                    ┌─────────────────────────────────────────┐
                    │  status = 'closed'    【只读 · 已定稿】   │
                    │  · 「改单」禁用，网格只读                  │
                    │  · 后端拒绝一切本期写入                    │
                    │  · 小程序：该期次从列表消失 + 提交被拒      │
                    └────────────────┬────────────────────────┘
                                     │ 点「继续修改」
                                     ▼   （回到 'open'）
```

**三个入口，两个方向**：

| 动作 | 入口 | 方向 |
|---|---|---|
| 保存并定稿 | 编辑态 → 保存下拉 | `open` → `closed` |
| 继续修改 | 只读态 → 状态标签旁 | `closed` → `open` |
| 关闭期次（已有，保留） | 更多工具 / 往期列表 | `open` → `closed` |

**判断依据只有一个**：`currentPeriod.status`（`Forecast.vue:7451` 已有 `currentPeriod` computed，直接可用）。

## 四、实现思路（前端 3 处 + 后端 1 处）

### 4.1 后端：把写入口的闸门补上（**唯一的后端改动，也是最重要的一处**）

`save_matrix` 目前**没有一行检查期次状态**（`forecast_submissions.py:345-379`，
注释自陈那里的 `status='open'` 只用来"猜是哪一期"，且**有意**不拦）。补一行：

```python
# 期次已定稿 ⇒ 拒绝写入。这是「不可再编辑」的唯一执行体（前端只是提示）
if _p and (_p.get("status") or "open") != "open":
    return {"success": False, "error": "本期已定稿，不可修改。如需调整请先「继续修改」。"}
```

🔴 **为什么必须加在后端**：前端禁用输入框**不是安全边界** —— 旧页面、API 直连、
小程序、导入接口都能绕过。**「锁」必须落在服务端**。

🔴 **闸门要覆盖全部本期写路径**，不止 `save_matrix`：

| 写路径 | 现状 | 要加吗 |
|---|---|---|
| `save_matrix`（改单保存） | 无校验 | ✅ **必加** |
| 导入登记（`import_router`） | 有 `_period_id` 守卫，无状态校验 | ✅ 加 |
| 期次复制 seed（`_period_copy_products`） | 无校验 | ✅ 加 |
| **小程序报单提交** | **已有校验**（`forecast_submissions.py:74` 要求 `status='open'`） | — 天然已封 ✅ |
| **小程序期次列表** | **已有过滤**（`forecast_open_periods_all` 只列 `open`，`erp_db.py:15638`） | — 天然已封 ✅ |

⚠️ **一个极易踩的坑**：`saveEdits` 一次调用里**同时**发了「商品档案」和「本期矩阵」两个请求。
闸门**只能加在后者** —— 加错位置就是"锁了报单、顺手锁掉全租户共享的商品档案"。

### 4.2 前端：保存按钮改下拉

- 保存按钮拆成 主按钮 + 一个下拉箭头（沿用现有 `.tb-pop` / `.tb-pop-panel` 弹出范式）。
- 「保存并定稿」= `await saveEdits()` → **确认两个请求都成功** → 二次确认 → `closePeriod(curPeriod)` → 退出编辑态。
- 🔴 **顺序不可颠倒**：**必须保存成功之后才允许定稿**。先定稿再保存 ⇒ 保存被自己的闸门拒掉，
  用户拿到一个**锁住的半成品**（而且连重试都做不到）。这就是 `saveEdits` 两个非事务请求最危险的地方。

### 4.3 前端：按 `status` 管控可编辑性

- `enterEdit()`（`:3048`）开头加一条：`currentPeriod.status === 'closed'` ⇒ 提示「本期已定稿」并返回。
- 只读态下：编辑网格不渲染、`保存` 组不渲染。
- 「继续修改」= `reopenPeriod(curPeriod)` → `status='open'` → 刷新 → 可编辑。

### 4.4 关于已有的「审批流」面板（**建议隐藏，需你拍板**）

| 事实 | 数据 |
|---|---|
| 审批面板（工具箱 → 审批流，`:89` + `:1222-1233`）有 5 个按钮：提交审批 / 通过 / 驳回 / 退回修改 / 回写ERP | 代码在 |
| **审批状态从未被真实写入过** | **`forecast_config` 里 `approval:*` 键 = 0 条**（三个租户全查） |
| 表里实际有的是 `save_changes` 审计 | `audit:N`，来自 v201 的保存留痕 |

⇒ 这套审批状态机**建了但从没被用过**。留着它会有两个后果：
①「定稿了还能点『退回修改』」⇒ **两个真相源互相打脸**（v201 那条铁律）；
② 工具栏 + 工具箱 + 审批面板 + 保存下拉，四个地方都能动期次状态。

**建议：把「审批流」按钮从工具箱里撤掉**（不删代码、只去入口，随时可回滚）。

## 五、边界情况

### 🔴 B1 点错了怎么办（**最高优先级 —— 现在是真缺口**）

`forecast_period_close` 是**单向的**：全仓**没有** `reopen`。
`forecast_period_delete` 还明确拒绝删除 `open` 期次（`erp_db.py:15576`：「进行中的期次不能删除，请先关闭该期次」）。
⇒ **一旦误点「保存并定稿」，那期就永久不可改**（只能删掉重建，而删除会级联清掉全部报单数据）。

**⇒ 必须新增「继续修改」（`reopen`），这是本方案不可省略的一块。**
最小实现：`UPDATE forecast_periods SET status='open' WHERE id=?` + 记一条审计。

### 🔴 B2 定稿会**连带关掉销售的报单通道**（最需要你确认的副作用）

`status='closed'` 之后：
- 小程序期次列表里**这一期直接消失**（`forecast_open_periods_all` 只列 `open`）；
- 就算销售停在旧页面，提交也会被 **400 拒绝**（`forecast_submissions.py:74`）。

**这是"定稿"的天然副作用**（也是它最省事的地方），但意味着：
**业务经理一旦定稿，还没报单的销售就报不进来了。**
⇒ 要么按真实节奏（等所有销售报完再定稿），要么定稿后点「继续修改」让补报的人进来再定稿。

### 🔴 B3 保存失败绝不能定稿

`saveEdits` 是**两个非事务请求**。若「商品档案」成功、「本期矩阵」失败，此时若推进状态 ⇒
用户得到一个**已定稿的半成品**，而且连重试都被自己的闸门挡住。
⇒ **铁律：两个请求都成功，才允许推进状态**；任一失败就停在 `open`，让用户重试。

### B4 已关闭的 4 期会立刻变成真只读

上线后，生产上**已有的 4 个 `closed` 期次**会第一次真正生效（此前能改）。
这是**修复**不是**回退**（文案早就这么承诺了），但你可能已经在那 4 期上改过东西 —— **上线前值得看一眼它们的数据是否如你所愿**。

### B5 老板查看不受影响

你原话「老板用自己的账号登进去看就可以了」。**查看不走编辑态** ⇒ 本方案对只读浏览零影响。
唯一的例外：如果老板现在是靠"进编辑态看某些列"的，那定稿后他进不去了 —— 但正常查看路径不受影响。

### B6 定稿时间与操作人要不要留痕

建议留。载体**已经现成**：`forecast_config` 表的 `audit:<period_id>` 审计数组（v201 已在写 `save_changes`），
再加两条 `period_close` / `period_reopen` 即可，**零新增表**。

### B7 「保存并定稿」与已有的「关闭期次」是同一个动作

两处入口都会把期次置为 `closed`，**不冲突**（同一个真相源）。
差别只是：「关闭期次」在「更多工具」里（低频、可发现性差），新的下拉就在保存按钮旁边。
⇒ 实施后可以**保留**旧入口（不做破坏性删除），也可以后续收敛，视你是否觉得重复。

### B8 权限：谁都能点「保存并定稿」和「继续修改」

按你的口径（小公司、不做审批流）—— **不加权限限制**，谁能改单谁就能定稿/解锁。
这与你现在的实际状态一致（后端目前对改单也没有额外的审批级校验）。
**如果**将来某家客户要"只有老板能解锁"，那一层再加，不影响本方案。

> 日期：2026-10-01 ｜ 范围：`hergent-cn-v2` 前端权限页 + 对应后端权限端点
> 性质：**只读盘点 + 方案**。本文档编写期间未改动任何生产文件、未部署。
> 结论先行：**「批量总览」可以整合掉，而且应该整合。** 本文给出可落地方案、6 处真缺陷、14 项优先级清单。

## 〇、结论先行（一页）

### 三个必须先知道的事实

1. **权限页现在是「三套界面 / 两个数据表示 / 九个后端端点 / 六个开关函数」。**
   这不是设计出来的，是 v311 → v349 共 40 轮补丁**只加不减**堆出来的。每一轮都在解决一个真实投诉，没有一轮做过合并。

2. **发现 2 个 P0 级真缺陷（会导致数据丢失 / 自我锁死），与本次重构无关，今天就该修：**
   - 🔴 **P0-1【自我锁死】** 在「单角色配置」里取消「老板」的「员工管理」中**「查看」这一个勾**（不必 4 个全取消）并保存 ⇒ 老板失去 `hr` 的读权限 ⇒ 权限页**永久打不开**（只显示"权限加载失败"），只能改数据库救回来。
     根因：`GET /api/permissions/modules` 归 `hr` 模块，而 `loadPerms` 用 `Promise.all` 把它和已豁免的 `/api/role-permissions` 绑在一起 ⇒ 一个 403 拉垮整页。**后端 v199 专门豁免 `/api/role-permissions` 来防自我锁死，被这一行 `Promise.all` 全部吃掉了。**
   - 🔴 **P0-2【静默丢输入】** 在「批量总览」勾了若干模块**不保存** → 切到「按角色配置」→ 保存任一角色 ⇒ `loadPerms(true)` 重拉全表 ⇒ **刚才那批勾选全部消失，零提示**。

3. **老板问的"批量总览能否整合"，答案是能，且舟谱根本没有这个视图。** 舟谱是「角色列表 → 一个角色一份矩阵」两步走；「跨角色横向对比」是我们自己造出来的需求，代价是三套界面互相同步。

### 推荐路线

| 路线 | 内容 | 推荐度 |
|---|---|---|
| **A** | 撤掉「批量总览」tab，能力全部并入「角色详情矩阵」；跨角色反查降级为**只读弹窗**（勾 2–3 个角色 → 对比） | ★★★（推荐） |
| **B** | 保留「批量总览」但**降为只读**（去掉全部勾选框与 3 个按钮），写入口只保留一处 | ★★（保守） |
| **C** | 不动结构，只修 2 个 P0 + 清死代码 | ★（不推荐：欠债继续涨） |

## 二、第一部分：逻辑混乱、职责不清、条件分支冗余

> 按严重度排序。**P0-1 / P0-2 是真缺陷（会丢数据 / 会锁死），优先于一切重构。**

### 🔴 P0-1【自我锁死】权限页的两个读接口走了两条完全不同的判据，被 `Promise.all` 绑死

**位置**：`Settings.vue:723-726`
```js
const [r, m] = await Promise.all([api('/api/role-permissions'), api('/api/permissions/modules')])
```

**事实链**：
- `server.py:657` → `"/api/permissions": "hr"`，且**不在豁免列表**
- `server.py:868` → `if path.startswith("/api/role-permissions"): return await call_next(request)`（**豁免模块判定**）
- `server.py:860-866` 的豁免理由原文：「一旦某个租户误把 boss 的 `hr` 撤掉，老板就打不开**唯一能把它改回来**的那个页面了 ⇒ **自我锁死且无法自救**」

**触发路径（可复现，源码链条已逐环验证）**：
1. 「设置 › 权限 › 按角色配置 › 老板 › 配置权限」→ 展开页签「更多」→ 「员工管理」行
2. **取消「查看」这一个勾**（不必 4 个全取消）→ 保存

| 环 | 源码 | 结果 |
|---|---|---|
| ① 前端提交 | `saveRoleDetail:844-847` 只提交"至少勾了一个动作"的模块 | `hr: {read:false,create:true,...}` 原样提交 |
| ② 后端落库 | `server.py:1487` → `normalize_perms_shape`（`core.py:1549-1550` **dict 原样返回**）→ `db.save_role_permissions`（`erp_db.py:2662` **`UPDATE` 整列覆盖**） | boss 覆盖行里 `hr` 只剩 `["create","update","delete"]` |
| ③ 有效权限表 | `perms_for`（`core.py:1050`）`{**_DEFAULT_PERMS, **custom}` —— **按角色整表覆盖** | boss 那一份**整个**被租户行替换 |
| ④ 裁决 | `_perm_granted`（`core.py:1493-1495`）dict 分支 `action in mod_perms`；中间件按 `GET` 推 `read` | **`hr`/`read` ⇒ False ⇒ 403** |
| ⑤ 前端崩 | `Settings.vue:726` `Promise.all` | `GET /api/permissions/modules` 403 ⇒ 整体抛 ⇒ `permRoles.value = []` ⇒ **权限页永久空白**，只能改库 |

**✅ 为什么 admin 不受影响**（说明这条洞的边界）：`Settings.vue:747` 用 `LOCKED_ROLES = ['admin']` 把 admin 从 `permRoles` 里过滤掉 ⇒ 角色列表里**看不到 admin** ⇒ `openRoleDetail('admin')` 永远不被调用。
⚠️ 但这意味着：**如果哪天把 admin 从 `LOCKED_ROLES` 移除、或通过「复制角色」造一个含 `*` 通配的角色再进详情页编辑，`["*"]` 通配符会被降级成一份具体 dict**（`normalize_perms_shape` 对 dict 原样返回，不保留 `*`）⇒ 那是同一族的第二个洞，建议同批加一条断言。

**🔴 为什么这个洞存在 —— 是"防护不对称"**：
「老板/管理员的 `hr`/`data` 必选不可取消」这条规则**只在批量总览视图实现了**：

| 位置 | 是否防护 |
|---|---|
| `Settings.vue:341-342`（矩阵 checkbox） | ✅ `:disabled="isLockedModule(...)"` |
| `Settings.vue:688-701`（`groupChecked`/`toggleGroup` 过滤 `isLockedModule`） | ✅ 跳过锁定项 |
| `Settings.vue:773-777`（`togglePerm` 早退） | ✅ |
| **`Settings.vue:114-118`（详情视图 checkbox）** | ❌ **零防护**：无 `disabled`、无判据 |
| **`Settings.vue:815-819`（`toggleDetail`）** | ❌ **零防护** |
| **`Settings.vue:834-861`（`saveRoleDetail`）** | ❌ **零兜底**（不像 `togglePerm` 有早退） |

⇒ **同一个安全规则抄了两份，其中一份漏了。** 这正是本项目反复栽的「同一规则抄两份」的又一实例。

**修复（三层，前端即可闭环，与重构解耦、可立即上线）**：
```js
// ① 模板 :114 —— 与矩阵视图同源判据（矩阵在 :341-342 用的就是这一句）
<input type="checkbox" :disabled="isLockedModule(permDetailRole, m.id)" ...>

// ② toggleDetail :815 开头 —— 防程序化路径
if (isLockedModule(permDetailRole.value, mid)) return

// ③ 🔴 最关键：saveRoleDetail :843 提交前**强制回补**（① 只防将来，③ 才能自愈已有坏数据）
const _keep = PROTECTED_ROLES.includes(name) ? CRITICAL_MODULES : []
for (const mid of _keep) {
  const cur = { ...(permDetail.value[mid] || {}) }
  for (const a of permActions) cur[a] = true
  permDetail.value = { ...permDetail.value, [mid]: cur }
}
// ④ Settings.vue:726 拆掉 Promise.all 的耦合（任一只读接口抖动不该拉垮整页）
const [r, m] = await Promise.all([
  api('/api/role-permissions'),
  api('/api/permissions/modules').catch(() => ({ modules: [] })),
])
```
> ③ 是必需的：若不加，**已经处于坏状态**的租户（boss 缺 `hr` 读权限）在详情页一保存会把坏状态原样写回，永远修不好。
> 更彻底的做法是**后端**在 `POST /api/role-permissions/detail`（`server.py:1487` 之前）对 `PROTECTED_ROLES × CRITICAL_MODULES` 做同样的强制回补 —— 这样任何写入口（含将来新增的）都被兜住。建议与 ④ 同批。

### 🔴 P0-2【静默丢输入】三个视图共享同一份草稿，切换即互相覆盖

**位置**：`Settings.vue:852-853`
```js
// 旧矩阵那份数据也要跟着刷新（同一张表，别让两套界面显示不一致）
await loadPerms(true)
```

**触发路径**：
1. 在「批量总览」勾了 5 个模块（`role.perms` 是**内存里的草稿**），**没点保存**
2. 切到「按角色配置」→ 点某角色「配置权限」→ 改几个动作 → 保存
3. `saveRoleDetail` 第 853 行 `loadPerms(true)` 重拉全表 → `permRoles.value` **整体替换** → 那 5 个勾**全部消失**

反向同理：详情视图改了 4 个动作不保存，切回批量总览点保存 ⇒ `POST /api/role-permissions` 走 `merge_module_list_into`（`server.py:1301`），它保护的是"库里已有的动作粒度"，**保护不了"你还没提交的意图"**。

**后端已经为这件事打过一次补丁**（`server.py:1284-1302`，注释原文：「用户在新的细粒度界面里配好"该角色只能查看、不能改"，再回旧矩阵随手点一次保存 —— 整行被拍平成"四动作全开"，**不报任何错**，用户只会觉得"我配的权限自己变回去了"」）——
**补丁解决了「形态互相拍平」，没解决「两个界面同时开着、两套草稿互相覆盖」。** 病根是"同一事实有两种表示"，形态收敛只是止痛。

**修复（重构前的最小止损）**：`saveRoleDetail` 成功后不要 `loadPerms(true)`，改为只更新该角色那一项；或 `permDirty` 为真时弹确认"批量总览有未保存的改动，切过去会丢失"。

### P2-3【受控 checkbox 用非受控写法】靠巧合正确

**位置**：模板 `:246-252`/`:258-262` 用 `:checked` + `@change`，`toggleEnd`（`:876-892`）里靠**手动还原 DOM**：
```js
ev.target.checked = true   // 还原控件：别让它停在一个后端必然拒绝的状态上
```
还原的是 **DOM**，不是状态。Vue 的 patch 若判定 `:checked` 值未变 ⇒ 不写回 DOM ⇒ 可能出现"框还空着，而权限实际没变"（或反之）。当前能跑属于**靠巧合正确**。
**正确写法**：状态先改 → 校验失败回滚状态（`role.end = {...}`），**永不触碰 `ev.target`**。

同类 6 处 checkbox（见 §3.2）全是这个模式。

### P2-4【脏检查只挂在一个视图上】`endBase` 快照

`endBase`（:743）是 `loadPerms` 时刻的登录端快照，只在 `savePerms`（:934-935）里比对。
⇒ **登录端这条轴的"是否改过"只被批量总览的保存按钮检查**；`saveRoleDetail` 既不比对也不提交登录端，还会通过 `loadPerms(true)` 重置 `endBase` ⇒ 登录端草稿被静默丢弃（P0-2 的同一机制）。

### P2-5【容错分支掩盖形态差异】`permsToModules`

**位置**：`Settings.vue:717-721`（注释在 :712-716）
它把 list 与 dict 两种形态**都归一成模块名**（丢掉动作）。后果：批量总览天生看不见动作粒度、单角色详情看得见 ⇒ 同一角色、同一模块，两个界面给出**不同信息量**，且没有任何一处告知用户为什么。

## 四、第三部分：可读性与可维护性改进

### 4.1 状态拆分（收益最大的一项）

把 11 个 ref 按"属于哪个视图"重组，装进 `src/composables/useRolePerms.js`：

```js
export function useRolePerms() {
  // ---- 服务端事实（只读，来自 2 个 GET）----
  const roleCatalog   = ref([])   // 角色 + 端 + is_custom + end_locked_web
  const moduleCatalog = ref([])   // 模块 + label + entries

  // ---- 界面状态（1 个对象替代 permView + permDetailRole）----
  const view = reactive({ mode: 'list', role: '' })

  // ---- 草稿：**按角色一份**，切视图不丢（治 P0-2 的根治手段）----
  //   draft[role] = { modules: { mod: {read,create,update,delete} }, end: {web,minai} }
  const draft = reactive({})

  // ---- 脏值：从 事实 ⊕ 草稿 派生，替代 endBase 手工快照 ----
  const dirty = computed(() => /* 逐角色比对 */)
  const dirtyCount = computed(() => Object.keys(dirty.value).length)

  // ---- 写操作（幂等 set，不用 toggle：消除"状态算错就反向"这一整类 bug）----
  function setModule(role, mod, on) {}
  function setAction(role, mod, act, on) {}
  function setRow(role, mod, on) {}          // = 4 个动作同置
  function setGroup(role, group, on) {}
  function setEnd(role, which, on) {}        // 含"至少一端"与"电脑端锁定"校验，失败**回滚状态**
  async function save(role) {}               // 1 个保存，一次提交 模块 + 端
  async function resetRole(role) {}
  async function resetAll() {}
  async function createRole(name, from) {}

  return { roleCatalog, moduleCatalog, view, draft, dirty, dirtyCount, /* ... */ }
}
```

**效果**：
- `Settings.vue` 权限段从 **489 行 → 约 150 行**
- `permLoading/permSaving/permDetailLoading/permDetailSaving` **4 个 → 1 个** `busy`
- 草稿按角色存 ⇒ **切换视图、切换角色都不丢**（P0-2 从"打补丁"变成"结构上不可能发生"）
- `endBase` 手工快照删除，改由 `dirty` computed 派生

### 4.2 渲染逻辑简化

**当前 4 层 computed 管道**：
```
modules ─┬─ filteredModules（搜索过滤）
         └─ permGroups（synthRows + 分组 + 折叠） ─┬─ matrix 模板直接渲染
                                                   └─ groupedModules（过滤 fixed）─→ detail 模板渲染
```

**问题**：`permGroups` 同时服务两个视图（P1-1 的跨视图泄漏），`groupedModules` 只是"再过滤一次"。

**建议合成 1 个**：
```js
const rowTree = computed(() =>
  buildRowTree(moduleCatalog.value, PERM_ALL_GROUPS, {
    query: view.mode === 'list' ? '' : queryFor(view.mode),   // 搜索按视图隔离
    withFixed: true,                                           // fixed 行由行定义决定，调用方不再过滤
  })
)
```
`buildRowTree` 放到 `permView.js`（与 `PERM_ALL_GROUPS` 同文件，行定义与展开逻辑同源）。

其他小项：
- `pageNamesFor()`（`:683`）是 1 行函数且只调用 2 次 ⇒ 内联
- `rowAllOn` / `toggleRowAll`（`:821-832`）⇒ 合并进 `setRow(role, mod, on)`
- `synthRows`（`:618-632`）⇒ 移入 `buildRowTree`

### 4.3 命名统一

| 现状 | 建议 | 理由 |
|---|---|---|
| `permView` / `permDetailRole` | `view = { mode, role }` | 用一个对象表达"当前在哪、在看谁" |
| `permDetail` | `draft[role]` | 它本质是草稿，不是"详情" |
| `permLoading` / `permSaving` / `permDetailLoading` / `permDetailSaving` | `busy = { load, save }` | 4 → 1 |
| `togglePerm` / `toggleDetail` / `toggleRowAll` / `toggleGroup` / `toggleEnd` / `toggleGroupCollapse` | `setModule` / `setAction` / `setRow` / `setGroup` / `setEnd` / `setCollapsed` | **幂等 set 而非 toggle**：调用方必须显式给出目标值 ⇒ 消除"当前状态算错就反向"这一整类 bug |
| `isLockedModule` / `roleHas` / `groupChecked` | 保留名字，移进 composable | 语义已清晰 |
| `permActions` / `permActionLabels` / `permActionHints` | `PERM_ACTIONS = [{key,label,hint}]` | 3 → 1 |
| `PERM_SIDEBAR_GROUPS` / `PERM_MORE_GROUP` | `PERM_ALL_GROUPS`（数组合并） | 组定义分散在两个导出里，遍历时要写两遍（`:648-656`） |

## 五、第四部分：「批量总览」能否整合进「按角色配置」

### 5.1 舟谱是怎么做的（6 张截图归纳）

| 层 | 舟谱 | 我们 |
|---|---|---|
| 第 1 层 | **角色列表**：`角色名称 \| 角色类型 \| 操作`，操作为「查看 / 复制 / 更多」，工具栏右上「新建」「批量删除」。**没有"批量总览"这种跨角色视图** | 角色列表，但操作只有「配置权限」一个；「新建角色」反而藏在批量总览里 |
| 第 2 层 | **一个角色一份矩阵**（三步向导的第 2 步），结构固定三块 ⬇️ | 拆成了两个平级 tab（矩阵 / 详情），各自只覆盖一半 |
| 顶部 | `角色名称` + `☑允许使用手机端` + `☑允许使用电脑端` + `[恢复默认设置]` —— **角色级开关住在角色页顶部** | 登录端两行住在**批量总览的表格底部**（`:242-276`），不在角色详情里 |
| 中间 | **业务模块页签**：档案管理 / 采购管理 / 仓储管理 / 资金管理 / 财务管理 / 员工考核 / 市场营销 / 数据报表 / 舟谱大屏 / 设置 / 对付助手 / 应用中心 | 我们的 `PERM_SIDEBAR_GROUPS`（经营 / 核算 / 配置 / 更多）**天然就是这个页签**，现在却渲染成表格里的 4 个组头行 |
| 主体 | `菜单项（分组+项名）\| 电脑端 \| 手机端 \| 动作列… \| 其他`；**全选在行首一列**（表头 ▪ 全选 / 分组行 ☑ / 行 ☑） | 列 = 角色（横轴），行 = 模块；全选靠组头 checkbox + 每行"整行全选"按钮 |

**舟谱的核心设计哲学：把"这个角色能干什么"用**一个矩阵**说完；权限从来不是按角色横向对比出来的，而是逐角色纵向配出来的。**

### 5.2 结论：能整合，且应该整合

「批量总览」存在的唯一理由是"跨角色横向对比"，但：
- 真实操作里**改权限永远针对一个角色**（老板 v334 的原话就是"从角色列表点进某一角色的详情配置页"）
- 它是下面这一串成本的**唯一来源**：

| 成本 | 明细 |
|---|---|
| 2 套读写路径 | list 端点 vs detail 端点，写同一行同一列 |
| 2 个 P0 缺陷 | P0-2（切视图丢草稿）与它直接同源 |
| 3 个保存按钮 | `savePerms` / `saveRoleDetail` / （新建表单的）`createRole` |
| 3 处静默丢数据 | `loadPerms(true)` 覆盖草稿 / 登录端草稿被丢 / 搜索态部分勾选 |
| 4 层 computed 管道 | `modules → filteredModules → permGroups → groupedModules` |
| 2 套表样式 | `.perm-role-table` / `.perm-detail-table` |
| 6 个 toggle 函数 | 其中 2 个（`togglePerm`/`toggleDetail`）做同一件事 |

| 舟谱做法 | 为什么不能抄 | 正确的借鉴版本 |
|---|---|---|
| **动作列按模块变化**（档案管理 = 查看/编辑/导出/导入；设置只有「查看」；仓储管理有 28 列含"批量出库/反审核/合并拣货"） | 我们的 action 由 **HTTP 方法推导**（`core._ALL_ACTIONS = [read,create,update,delete]`，`_PATH_MODULE_MAP` 决定归属）。没有"导出/导入/审核"这些独立边界（导出常是 GET，导入是 POST）⇒ 硬套会得到**点了不生效的假开关**（v334 注释 :573-577 已经论证过） | **P2 增强**：让后端在 `GET /api/permissions/modules` 多下发一个 `actions` 字段 = 「该模块下**真实出现过**的 HTTP 方法集」（从 `_PATH_MODULE_MAP` 反查路由表可得）。前端按它渲染列 ⇒ 只读模块不再出现"删除"列。**这是真增强，但需要后端配合** |
| **「其他」列**（标记 / 超级标记 / 附件删除 …） | 我们没有这些独立动作边界 | ❌ 不建 |
| **行内「电脑端 / 手机端」两列** | 那是舟谱的**菜单级**端归属。我们的端只有**角色级**（`users.login_scope` ← 角色政策 `role_end`），没有"某个功能只在手机端"这个模型；要做需要新建一张表，且会与 `pages.js` 的角色门槛/模块门槛两条轴冲突 | ✅ **只保留角色级两个开关**（即舟谱顶部那两个），放在角色详情页顶部。**这本来就是舟谱的做法** |

## 二、★2 为什么必须做（问题本体）

审核引擎的统计窗口锚在**数据自己的最新日期**，而不是今天：

```sql
date((SELECT MAX(order_date) FROM sale_orders), '-30 days')
```

生产实测 `MAX(order_date) = 2026-06-15`，今天 2026-09-24 ⇒ 窗口落在
**2026-05-16 ~ 06-15**，**落后今天 101 天**。

后果：285 个在售商品里 **180 个日均销量被算成 0**，判定退化成
「近30天无销售数据，无法自动判断，请人工判断」—— **不报错、数字看着正常**。

🔴 根因**不在那条 SQL**：用 `MAX` 而非 `now` 是**有意**设计（防数据迟到时窗口打空）。
根因是**没有持续更新 `sale_orders` 的通道**（→ 任务 #373，★1）。所以★2 的正确修法不是改窗口，
而是**把「数据有多旧」显式变成读数**，让人自己判断；而不是偷偷给个 0 还附一句
"近30天无销售"的**误导文案**。

### 后端读数（生产实测，与独立核算逐字一致）

```json
{"level":"stale","label":"销量数据已停更 101 天（最新 2026-06-15）",
 "max_date":"2026-06-15","min_date":"2026-04-02","days_stale":101,"order_count":580,
 "window_start":"2026-05-16","window_end":"2026-06-15","window_days":30,"stale":true}
```

分档：`≤7 天` fresh ｜ `≤30 天` notice ｜ `>30 天` stale。新增行级字段 `data_stale_days`。
四个端点（`/products` `/compute` `/audit-period`）全部带回 `sales_freshness`。

### 前端告警条（真机读数）

> **销量数据已停更 101 天（最新 2026-06-15）** —— 系统建议依据的统计窗口是
> 2026-05-16 至 2026-06-15（按数据最新日期回推 30 天，**不是最近 30 天**）。
> 窗口内没有销量的商品，日均销量会被算成 0、建议量退化为人工判断，下方建议量请只作参考。

🔴 **放的位置是这一轮最贵的一次纠错**：第一版写在 `auditState === 'done'` 分支里，
而生产该期次**没有报单商品**（`items` 0 行 ⇒ 走 `empty` 分支）⇒ **告警会被吞掉**，
恰恰是最该看到它的人看不到。已移到 `imp-body` 第一层（`loading` 之前），对 `done`/`empty` 两态都可见。

**业务员（`role=sales`）打开「预报订货管理」= 一张空表 + 一排永久灰按钮。**

| 环节 | 实测 |
|---|---|
| 接口 | `GET /api/forecast-submissions/summary` → **403** |
| 后端原因 | `仅管理员 / 老板 / 主管可查看报单汇总`（`routers/forecast_submissions.py` 硬白名单） |
| 前端回执（1 秒） | toast：**「交叉表加载失败: 仅管理员 / 老板 / 主管可查看报单汇总」** |
| 前端回执（6 秒） | **toast 已消失**，页面**没有任何**常驻提示 |
| 终态 | 表格空、`AI智能建议` 按钮 `disabled=true` 永久不可达、控制台 **0 报错** |

三处问题，严重度不同：

1. **措辞误导**（无产品争议）：权限不足被说成「加载失败」⇒ 用户理解成"系统又坏了"。
2. **回执不持久**（无产品争议）：toast 一过，页面不自解释。
3. **假入口**（**需产品决策**）：侧栏「预报订货管理」对业务员可见（`/api/forecast` 归 `data`，业务员持有），
   点进去却必然失败 —— 与后端注释里刚修过的「会计假入口」是**同一类缺陷**。

🔴 机制：`loadCross()` 是 `Promise.all([summary(), products.grid()])`
⇒ 403 让**整函数 reject** ⇒ `cross.value` 永不被赋值 ⇒ `cross.period` 恒 null。

**候选修法**（← 用户拍板 **A**，已实施，见 §六）

|---|---|---|
| **A（推荐）** | ① 403 单独识别，提示改为「你的角色（业务员）没有查看报单汇总的权限」；② 表格区改成常驻空状态说明，不再只在 toast 里说；③ 侧栏入口对无权限角色**隐藏** | 不动权限矩阵，只把话说对 + 撤假入口；业务员仍可从小程序看自己的报单 |

### 6.1 为什么先要一张「真实权限对照表」—— 本轮探针最大的障碍

做这个修复时，我**找不到任何一个测试账号能同时打开审核台并看汇总**。实测核准：

| 账号 | 角色 | `/api/auth/permissions` | `…/summary` | `…/forecast-audit/*` |
|---|---|---|---|---|
| `mptest` | sales | `dashboard, ops-workbench, sales, buying, stock, crm, data` | **403** | ✅ 200（有 `stock`） |
| `mptestsp` | supervisor | `data, dashboard` | ✅ 200 | **403**（缺「库存」） |

⇒ **两个账号各缺一半权限** ⇒ 探针**必须打桩**才能同时满足两侧前置条件。这也是为什么本轮把桩
从「导航后改 `window.fetch`」升级成 **boot 期注入**（见 6.5）。桩只替换**前端门禁**用的两个接口，
后端一律走真接口 —— 并有**正例自证**断言防止「读数是被桩喂出来的」。

### 6.2 三处实现点

| # | 面 | 文件 | 做法 |

| ① | 后端 | `server/routers/forecast_submissions.py` | 函数体内联元组提为**模块级常量** `SUMMARY_ROLES = ("admin","boss","supervisor")`；`submission_summary()` 改为引用。**403 文案一字未动**（小程序/前端都在读它，改文案是破坏性改动） |

🔴 **必须提成模块级常量的原因**：护栏用 AST 解析，**内联在函数体里的字符串元组护栏看不见 —— 看不见就等于没有护栏**，两侧必然漂移。

🔴 **`canViewForecastSummary` 第一版我自己写错了方向**：写成「在白名单里返回 true」⇒ 角色**未知**（空串）时返回
`false` ⇒ 会隐藏核心模块，老板在启动瞬间会看到「预报订货管理」**先消失再冒出来**。项目纪律是
**fail-open（拉不到 ≠ 没权限，与 `store.canModule()` 同）**。已修：`if (!isCanonicalRole(k)) return true;`。
代价是「未知角色多看一眼入口」，比「核心模块对老板人间蒸发」轻得多。

### 6.5 本轮新增的四条硬教训

1. **🔴 boot 期桩必须用 `Page.addScriptToEvaluateOnNewDocument`。**
   `store.loadPerms()` 在 **boot 期**拉 `/api/auth/permissions` 并把 `role` 落进 store，**同租户只拉一次（有缓存）**
   ⇒ 「导航后再改 `window.fetch`」**根本打不进去**；而且重试也无效（`perms.value !== null` 直接 return）。
   表现极具迷惑性：探针里 `__stubCalls.perm === 0`、页面停在旧角色 —— **看起来像「桩写错了」，其实是时机错了**。
   已给 `.workbuddy/tools/lib/cdp-lite.mjs` 加 `addInitScript` / `removeInitScript`。
2. **🔴 `addScriptToEvaluateOnNewDocument` 不摘会跨相位污染。** 它对该 page 的**所有后续导航**持续生效；
   正例相位被桩喂过 ⇒ 整个探针作废。规程：**用完立刻 `removeInitScript`**（相位 9 第一件事就是摘）。
3. **🔴 测不到前置条件时，桩要打「能让流程跑起来」的最小面，并且必须有正例自证。**
   本轮桩只替换 `permissions`（→ boss，**只影响前端门禁、不影响后端**）与 `summary`（最小合法空表，让
   `cross.period` 成立），其余全走真接口；再用 `st7.audit === 0` 反过来证明「关键读数不是被桩喂的」。
4. **🔴 「逐文件 diff 有 10+ 个不同」是假差异 —— `macOS sort` 与 `Linux sort` 大小写排序不同。**
   目录级 md5 聚合不一致（`17690dee…` vs `12805918…`），`diff` 看似一堆差异，实为 `AdvicePanel-` 之类
   落点不同。两端统一 `LC_ALL=C sort` 后 ⇒ **56/56 完全一致**。**目录级 md5 不能当文件级比对用。**

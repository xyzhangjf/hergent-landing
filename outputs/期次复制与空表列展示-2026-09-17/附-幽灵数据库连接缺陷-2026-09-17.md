# 🔴 产品级缺陷：幽灵数据库连接（SQLite 连接缓存只探活、不验身份）

**日期**：2026-09-17　|　**发现场景**：v184 期次复制的真机验收
**严重度**：**P0（静默数据错乱）** —— 不报错、不抛异常、HTTP 全回 200，但**读写的是另一个库**
**代码位置**：`server/db/connection.py` —— `_sqlite_connect()`（约 200 行）、`set_tenant_context()`（约 80 行）

---

## 一、一句话结论

连接缓存以 **(线程, 路径)** 为键，复用前只用 `conn.execute("SELECT 1")` 探活。
而 SQLite 在**库文件被 unlink 之后，已打开的 fd 依然有效**（inode 还在，只是目录项没了，
`SELECT 1` 照样通过）⇒ **服务进程会继续读写一个"已经从磁盘目录树消失"的库**。

叠加 `set_tenant_context()` 的兜底逻辑，就得到一个**完全静默**的分裂：

```python
tp = os.path.join(DB_DIR, f"tenant_{tenant_id}.db")
_tenant_db.set(tp)
# v88: Auto-create tenant DB if it doesn't exist
if not os.path.exists(tp):
    _ensure_tenant_db(tenant_id, tp)      # ← 文件没了 → 自动建一个**全新的空库**（新 inode）
```

| 请求类型 | 走哪条路 | 实际读到 |
|---|---|---|
| **异步端点**（跑在事件循环线程） | 命中缓存连接 | 🔴 **幽灵库**（旧 inode，旧数据） |
| **同步端点**（跑在线程池） | 新线程 = 新 key = 新连接 | 全新的空库 |

---

## 二、症状：极具误导性

验收时我遇到的是这一组：

| 观察 | 表面结论（❌ 全错） | 真相 |
|---|---|---|
| `POST /periods/{pid}/copy` 全部返回 200，还回了 `id=19`、`id=20` | 「写入成功」 | 写进了幽灵库，**从未落盘** |
| 紧接着 `GET /periods` 看不到刚建的期次 | 「事务没提交 / 读走了别的库」 | GET 也读幽灵库，但它是**另一个时间点**的连接…… |
| 文件里 `sqlite_sequence.forecast_periods` **恒为 12** | 「AUTOINCREMENT 没更新」 | 🔴 **决定性证据**：`sqlite_sequence` 的更新是**事务性**的；它恒为 12 说明**这个文件上从未发生过提交** |
| 我在进程内直连该文件插入一行（id=13），HTTP `GET` 居然**读得到** | 「说明读的就是这个文件」 | 反了 —— 说明 HTTP 读的是**同一个旧 inode** |
| HTTP 写完后再看文件，**文件没变** | 「写丢了」 | 写落在幽灵库上 |

## 三、定案的四个实验（证据链）

| # | 实验 | 结果 | 排除了什么 |
|---|---|---|---|
| 1 | `v184_commit_test`：调 API 前后读**文件**的 `max(id)` | 不变 | 排除「端点根本没写」 |
| 2 | `v184_http_vs_file`：进程内往文件插 `id=13` → HTTP `GET` 读得到；HTTP `POST` → 文件不变 | 单向可见 | 证明「HTTP 与文件是**两个 inode**」 |
| 3 | `v184_inproc`：在服务进程内**直调**写函数 | **提交成功、文件可见** | 证明「代码管道本身无恙」 |
| 4 | `systemctl restart hergent-erp` 后重跑同一组 | 全部正常 | 🔴 **定案：进程内缓存的连接是幽灵** |

**触发条件（本轮实测）**：隔离沙箱先 `down`（删掉 `tenant_9997.db` 及其 `-wal`/`-shm`），
再 `up`（**重建同名文件**）—— 文件路径一字不差，但已是**另一个 inode**。

---

## 四、影响面（生产真实风险）

**这不只是沙箱工具的问题。** 任何「同名库文件被替换」的操作都会命中，且**后果是持续性的**：

1. 运维误删 / `mv` 走了某租户库；
2. 从备份恢复：`cp backup/tenant_9.db /opt/hergent-erp/data/tenant_9.db`（**覆盖**）；
3. 手工重建租户库；
4. 数据迁移脚本用了「先删后建」而不是「原地改」。

⚠️ 触发后的行为**比崩溃更糟**：
- 请求正常返回 200，用户以为改成功了；
- **只有异步端点中毒** —— 而 Hergent 的业务端点里异步占比很高（预报/导入/副驾几乎全是 `async def`）；
- 幽灵连接**会一直存活**（`set_tenant_context` 只在文件缺失那一瞬建库，
  新文件一旦存在就再也不会重建）⇒ 不重启服务就**永远不会自愈**。

---

## 五、修复建议

### 方案 A（最小改动，推荐先做）：把「探活」升级为「验身份」

```python
if conn is not None:
    try:
        # 🔴 只探活不够：文件可能已被替换成另一个 inode，而旧句柄依然可用
        st = os.stat(db_path)
        if getattr(conn, "_hergent_dev_ino", None) != (st.st_dev, st.st_ino):
            raise OSError("db file replaced (inode changed)")
        conn.execute("SELECT 1")
        ...
    except Exception:
        try: conn.close()
        except Exception: pass
        with _sqlite_cache_lock:
            _sqlite_cache.pop(key, None)

conn = sqlite3.connect(db_path)
try:
    st = os.stat(db_path)
    conn._hergent_dev_ino = (st.st_dev, st.st_ino)     # 建连时记下身份
except OSError:
    pass
```

- 成本：约 8 行，**只在命中缓存时多一次 `os.stat`**（微秒级）。
- 覆盖：**所有**「文件被替换/删除」的路径，不必逐个去找触发点。

### 方案 B（更彻底）：加路径级主动失效 `_sqlite_evict_path(db_path)`

遍历 `_sqlite_cache` 里所有 key（key 含 `tid`，需全表扫）、close 并 pop。
调用点：
- `set_tenant_context()` 检测到 `not os.path.exists(tp)` 时（**建库之前**）；
- `erp_db.tenant_db_init()` 返回之后；
- 任何重建/替换租户库的运维脚本里。

⚠️ 方案 B 单独用会**漏**：`os.path.exists()` 为真但 inode 已变的情况（如 `cp` 覆盖）察觉不到。
**建议 A+B 一起**（A 兜底正确性，B 让失效更及时）。

### 方案 C（运营规避，零代码，**立刻可用**）

> **任何「重建 / 替换 / 删除」租户库文件之后，必须重启服务：**
> `systemctl restart hergent-erp`
> **顺序必须是「先动文件，再重启」。** 反过来（先重启、后动文件）等于没做。

本轮 v184 的全部真机验收就是按这个顺序跑通的。
（沙箱工具 `.workbuddy/tools/sandbox_tenant.py` 的 `up` 之后也已明确要求重启。）

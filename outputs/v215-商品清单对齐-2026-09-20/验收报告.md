## 一、你的要求 → 实现方式

> 「Web 端某一期有多少个商品，小程序端就必须展示相同数量的商品，且排列顺序也必须与 Web 端完全一致。
> 报单商品的判定基准不是商品档案……应该以每一期次内实际包含哪些商品作为报单的基准。」

| 你的要求 | 实现 |
|---|---|
| 基准 = **期次内实际包含的商品** | 小程序商品铺开的数据源从 `products`（商品档案）换成 `forecast_import_products`（**期次商品清单**） |
| 数量一致 | 小程序 `total` = 该期清单行数（不再是"档案在售"全量） |
| 顺序完全一致 | 复用 Web 端同一条排序键：`sort_no>0 优先 → sort_no 升序 → id 兜底` |
| 不能只是"显示对齐" | 提交时按本期清单校验，不在本期的商品被剔除并在回执里说明 |

### 改前 vs 改后（你看到的现象）

| | 改前 | 改后 |
|---|---|---|
| 小程序可选商品 | **285 个**（商品档案里所有在售） | **154 个**（= Web 端本期清单） |
| 顺序 | 商品档案顺序 | **与 Web 端逐项相同** |
| 搜索 | 在全档案里搜 | **只在本期清单里搜**（顺序仍按模板行序） |

> 那多出来的 134 个是什么？绝大多数是**从没卖过、而且根本没录价格**的空壳档案
> （只有 6% 有真实销售记录、87% 连价格都没有，成批的「新希望」+ 一个测试商品）。
> 所以 285 不是"更全"，是"没筛"。

## 四、顺手修掉一个**一直在悄悄出错**的地方

排查时发现：小程序商品行里的「日均销量」**恒显示 0**，而且**从不报错**。

原因：后台那段查询 SQL 里有 5 个占位符，但只传了 1 个参数 ⇒ 数据库报错 ⇒
被一个"出错就用默认值"的兜底**静默吞掉**（连日志都没有）。

已修（补参数 + 兜底改为记日志），并加了断言守住：日均 4.0 / 1.0 均正确返回。

> **记一条判据**：画面上某个数字**长期恒为同一个值**（尤其 0）却没有任何报错时，
> 先查它是不是被"兜底"吞了，而不是先怀疑数据源。

# 报单人门店配置收敛为单一入口 · 交付报告

**日期**：2026-09-19　|　**版本**：v200
**需求**：移除「档案管理 → 员工档案」里的门店配置入口，仅保留「预报订单管理 → 报单配置」，
并确保移除后门店配置功能仍可正常使用，同时处理受影响的关联逻辑。

---

## 一、先讲结论

**做完之后发现：这两个入口写的根本不是同一张表。**

| 入口 | 写的表 | 小程序「可见门店」读的表 |
|---|---|---|
| 档案管理 → 员工档案 → 「门店」弹窗 | `employee_stores` | ← **只读这张** |
| 预报订单管理 → 报单配置（映射） | `report_mapping` | 不读 |

实测生产租户 1（永诺）**两表零交集**：

```
employee_stores 只有：张俊峰→一分利(2562)、张俊峰→一扫光(2804)、emp9001→永诺旗舰店(2220)
report_mapping  只有：张俊峰→永辉东津店(2868)、刘小顶→美联(保康店)(2225)、刘善涛→刘善涛仓
交集：0
```

⇒ **在报单配置里给张俊峰配了「永辉东津店」，小程序端根本看不到。**
配完不落到可见范围 —— 这不是"两个入口入口重复"，而是**两个入口各配各的、互相不认**。

所以本轮不是简单删一个按钮，而是必须同时**把读端口径收拢**，否则删掉员工档案入口后，
`employee_stores` 变成「没有任何 UI 能写」的孤儿表，而它偏偏是可见范围的真源 ——
**删了入口 = 门店配置功能整体失效**（正是需求里要求避免的那件事）。

## 二、改了什么

### 后端（hergent-erp `7e502fd`，2 文件 +182/-11）

| # | 改动 | 说明 |
|---|---|---|
| 1 | `employee_stores_get` **读端取并集** | = 报单配置 active 映射派生 ∪ `employee_stores` 历史层。⇒ `report_mapping` 成为真源；**本次收敛零数据迁移、不误删任何人的报单权限** |
| 2 | 新增 `employee_stores_prune_covered()` | 清掉「**已被 active 映射覆盖**」的历史行。删除**不改变可见集合**（映射会派生同一个 store_id）⇒ 安全且幂等 |
| 3 | 写端 4 处挂钩 | `report_mapping_create` / `update` / `toggle` / `import` 提交后调收敛 |
| 4 | 新增 `report_mapping_legacy_stores()` + `GET /api/report-mappings/legacy-stores` | 列出「在历史层、但未纳入报单配置」的员工 × 门店 |
| 5 | `employee_list().store_ids` 改口径 | 由「直接吐 employee_stores」改为「历史层 ∪ 映射派生」的**有序去重 list**，与 `employee_stores_get` **同源** |
| 6 | `employee_stores_set` 保留未删 | docstring 标注「已无 UI 调用」，供脚本 / 旧接口兼容 |

**为什么需要 `prune`（第 2 条）**：读端取并集后，若某门店**既在历史层又在报单配置里**，
用户在报单配置里**停用**该映射，历史层那行仍会让门店可见 ——
就是「**停用无效 / 删了又回来**」（与 v199 客户列「删了又回来」同族）。
`prune` 在「已被 active 映射覆盖」时删历史行；此刻删除**不改变可见集合**，所以它是安全的。

**两个写进代码的坑**：
- `employee_stores_prune_covered(0)` 的语义是「清**全租户**」⇒ 四个调用点全部显式判 0；
- 用 `rowid IN (子查询)` 而非 `DELETE ... AS es`（后者依赖 SQLite qualified-table-name 别名语法，
  写法较新，老版本 / 其他驱动不一定认）。

### 前端（laozhangai-product `26924cc`，6 文件 +603/-51）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `EmployeeArchive.vue` | 删「门店」按钮、删整个「分配门店」弹窗、删 2 个函数 + 4 个 ref + 3 条 CSS；列头「门店」→「**可报门店**」**只读**展示数量（带 tooltip 指路） |
| 2 | `ReportMapping.vue` | 新增「**历史门店授权**」提示条：历史层那批尚未纳入报单配置的门店，入口移除后已无 UI 可改，不列出来就是「小程序看得到、后台没处改」 |
| 3 | `api/modules.js` | `reportMappingApi` 增 `legacyStores()`；`staffAccountApi` 删 `allStores`/`setStores`（后端接口仍保留） |
| 4 | 新增验证工具 | `v200-store-scope-verify.py`（函数级 22 项）、`v200-store-entry-e2e.js`（真机 13 项） |
| 5 | `scoped_stage_by_marker.py` | 新增 `present` **正向断言**（见第五节） |

## 五、过程里发现的两个「静默失败」

### 1. 分 hunk 归属不能靠标记串（已加护栏）

`erp_db.py` 是长期脏工作区：31 个 hunk 里只有 14 个是本轮。首版按**标记串**分类，
把自己 3 个 hunk（`store_map→set` / `touched.add` / 并集 SQL 正文）误判成在途 ——
而工具原有四条自证（黑名单存在性 / 并集覆盖 / 残留计数 / 在途零夹带抽样）**全部照过**。

⇒ 结果是**静默少提交**：提交里 `employee_stores_get` 的 docstring 说「读端取并集」，
而函数体还是旧的单表查询 —— 文档与实现相反。与 v199「`MAP[x] || x` 把缺配置显示成正常值」同族。

**已加 `present` 正向断言**（`gone` 的对称面）：一个验「该没有的没有」，一个验「该有的有」。

### 2. 断言要挑「只有真删掉才会消失」的文本

`gone` 里写 `df-store-list` ⇒ 假失败：我删掉 CSS 规则后**留了一行说明注释**，注释里点了名。
改成规则本体 `.df-store-list{display:grid` 才成立。

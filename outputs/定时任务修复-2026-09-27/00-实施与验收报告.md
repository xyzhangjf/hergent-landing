## 二、根因（三层，逐层排除）

### 第 1 层：为什么 bridge 读不到数据

`hergent-erp.service` 的 drop-in `10-sandbox.conf` 里：

```ini
ProtectHome=true      # 把 /home、/root、/run/user 挂成 mode 700 的**空 tmpfs**
```

🔴 **决定性事实**：systemd 的挂载命名空间是**进程级继承**的 ——
`sudo` / `exec` 都**不会**重置它。所以 `cron_tasks.py::_bridge()` 里的 `sudo -u root`
（HOME=`/root` ⇒ `~/.hermes` = `/root/.hermes`）**一样穿不过去**。

> **判据（把"环境问题"钉死成事实）**：同一条命令
> · 在 SSH 交互 shell（**无沙箱**）⇒ `ok:true` + 真实任务 ✅
> · 从 service 里 `sudo -u root` ⇒ `EROFS /root/.hermes` ❌
> ⇒ 故障在**调用环境**，**不在 bridge 本身**、也不在 sudo 白名单（白名单是通的）。

### 第 2 层：一个**已实测证否**的错解

直觉方案是"把那一棵子树 bind 进来"：`ProtectHome=true` ＋ `BindPaths=/root/.hermes`。

> 🔴 **不成立**。`ProtectHome=true` 会把 `/root` 本身挂成 mode **700** 的 tmpfs
> ⇒ **想到达 `/root/.hermes` 必须先穿过 `/root`**，而它不可 traverse。
> 探针实测：`ls /root/.hermes/cron` 仍 `Permission denied`。
> **父目录不可穿越时，子挂载点无用。**

### 第 3 层（🔴 这才是最值钱的一层）：故障为什么**零报错**

`_bridge()` 把上游失败**编码成 HTTP 200 + `{"ok": false, "error": "<traceback>"}`**。
前端只有 catch 分支能显示错误，而它**永远等不到非 2xx** ⇒ 错误被渲染成空列表。

**同一个假绿机制还有第二个受害者**：`create()` 里
`await api('/api/cron/jobs', {...POST})` 不抛错 ⇒ 前端 `toast('任务已创建','success')`
**谎报成功**，随后列表照旧为空。⇒ 用户会以为"创建成功了但没显示"。

## 三、修复

### 3.1 环境侧：新增 drop-in（不动 `10-sandbox.conf`）

```ini
# /etc/systemd/system/hergent-erp.service.d/11-hermes-cron-bridge.conf
[Service]
ProtectHome=read-only                    # 保留真实 /root（连同它原本的 drwx-----x）
ReadWritePaths=/root/.hermes             # 只把 cron 子树放成可写（CRUD 要写 jobs.json 与锁）
```

**为什么是 `read-only` 而不是关掉 `ProtectHome`**：`read-only` 保留真实 `/root`
（含它原本的 `drwx-----x`），因此 hergent 能 traverse；而 `ReadWritePaths` 只放开 cron 那一棵子树。

### 🔒 暴露面评估（探针实测，不是推测）

| 检查项 | 结果 |
|---|---|
| `ls /root` | **仍 `Permission denied`** —— `/root` 是 `drwx-----x`，other 只有 `x` 无 `r`，**本来就不能枚举** |
| `head /root/.ssh/id_rsa` | **仍 `Permission denied`** —— `/root/.ssh` 是 `drwx------ root root` |
| 新增可见内容 | 仅「世界可读」的文件（如 `/root/.hermes/config.yaml.bak-*` 这类 `root:root 644` 历史备份） |
| `ProtectSystem=full` / `PrivateTmp=true` | **保持不变** |
| `NoNewPrivileges` | 仍由 `20-l1-umask.conf` 覆盖为 `false`（本轮未碰） |

> **与 v258 加沙箱之前对比**：那时 hergent 就是直连 `/root/.hermes`
> （`hermes-gateway.service` 至今如此 —— `WorkingDirectory` 与 `HERMES_HOME` 都指向它）。
> 本次只是把这个**既有事实恢复给后端进程**，并未放宽到 `/root` 的其它内容，也未放宽 `/home`。

### 3.2 代码侧（提交 `aa91928`）

**① `_bridge_or_502()` 替换 5 个端点** —— 上游失败一律 **502**，不再伪装成 200 空列表。
**前端零改动**：它已有 catch 分支，只是过去永远等不到非 2xx。

**② list 的「空结果对照」** —— bridge 说 0 条、而权威 `jobs.json` 明确有 N>0 条 ⇒ 502：

> 🔴 **保守设计**：读不到权威文件就返回 `None` 并**保持沉默**。
> 否则会把「客户真的没有定时任务」误判成故障 —— 宁可少报，不可误报。

这条守的是**另一个尚未发生的坑**：一旦有人去掉 `sudo -u root`（或 HOME 解析变化），
bridge 不会报错，而是 `mkdir` 一份**空**的 `.hermes/cron` 并返回 `ok:true, jobs:[]`
⇒ 又是一次"页面空、零报错"。探针已实测复现该形态。

**③ 三条硬依赖写进文件头** —— 必须 `sudo -u root` ／ `~` 必须解析成 `/root` ／
沙箱必须放行该路径。放在代码旁边，改这个文件的人一定看得见。

### 关于验收设计的两个要点

**（a）「HTTP 200」这一条单独不算数。** 修复**前**它也是 200。
所以判据必须落到**正文**：不含 `Traceback` ＋ `ok:true` ＋ `jobs.length===1` ＋ id 与权威数据一致。

**（b）三条反例对照，防止「一律 502」的空断言**：

| 反例 | 期望 | 为什么必须有 |
|---|---|---|
| `jobs:[]` 且权威也空 | **放行** | 证明"客户真的没任务"不会被误报 |
| 权威文件不存在 | **放行** | 证明"读不到就沉默"的保守设计生效 |
| 权威文件是坏 JSON | **放行** | 同上 |

# 登录 IP 限流加固落地报告

**日期**：2026-09-12
**触发**：用户提问「我们登录页要不要加一个滑动验证条」
**结论**：**不加滑块**，改为落地「nginx 层 IP 限流 + 应用层 IP 维度锁定」两层加固
**状态**：已上线并三级验证通过

---

## 一、结论与决策依据

### 1.1 为什么先不做滑块

滑块解决的是「自动化撞库」，但排查生产数据后发现：**威胁真实存在，但量级很小**，而用 IP 限流能以约 1/10 的成本覆盖同一威胁。

更关键的是架构约束（见 1.3）：**滑块放在前端等于零收益，放在后端会打断小程序登录**。

### 1.2 生产真实攻击数据（一个月全量，`login_attempts` 表）

| 指标 | 数值 |
|---|---|
| 总登录尝试 | 413 次 |
| 失败尝试 | **仅 24 次** |
| 失败集中点 | **`admin` 被 18 次失败命中，来自 9 个不同外部 IP** |
| 爆发窗口 | 2026-08-12 ~ 08-14（单 IP `27.27.120.15` 试了 6 次） |
| 近 7 天失败 | 共 3 次；09-08 之后为 0 |

**判定**：典型的**分布式弱口令扫描器**猜 `admin`。**没有正在进行的暴力破解。**

**但这条数据同时暴露了一个真实缺口**：现有「按用户名 5 次锁定」**拦不住分布式扫描** —— 9 个 IP 每个只试 1~6 次，谁也触发不了单账号 5 次阈值。

### 1.3 致命架构约束（决定了滑块的性价比）

```
网页端 Login.vue ─┐
                  ├─→ POST /api/auth/login ─→ 网页与小程序共用的唯一关口
小程序 login.js  ─┘        （小程序 apiBase = https://hergent.cn）
```

- 小程序 `forecast-order-miniprogram/miniprogram/pages/login/login.js:78` 调用的是**同一个** `/api/auth/login`
- **滑块只加前端** → 脚本直接 POST 接口绕过界面 → **安全收益 ≈ 0**（纯装饰）
- **后端强制校验 ticket** → 机器人挡住了，但**小程序登录直接中断**（微信小程序渲染不了 HTML 滑块，需另做一套）
- 自研滑块（答案在前端校验）→ 同样可被直接调接口绕过，属安全剧场

### 1.4 滑块的正当价值（保留为后续选项）

滑块真正的价值此刻更多在 **B 端销售侧的「信任符号」**（客户看财务系统时判断"靠不靠谱"），属营销层的账。建议等到**开始对外销售 / 再次出现扫描**时再上第三方方案（腾讯云验证码 / 极验），并采用**风控触发式**（失败 ≥2 次才弹），而非常驻。

## 二、交付内容

### 2.1 后端（3 文件）

| 文件 | 变更 |
|---|---|
| `server/erp_db.py` | `login_is_locked()` 由「仅按用户名」升级为**双维度**：用户名 `LOGIN_LOCK_USER_MAX=5` / 来源 IP `LOGIN_LOCK_IP_MAX=20`（均 15 分钟滑动窗）；新增 `_LOGIN_IP_EXEMPT` 豁免本机与未知来源 |
| `server/core.py` | `_check_login_lockout()` 签名 `ip_address` 默认值由 `"0.0.0.0"` 改为 `""`，并**透传 IP** 给 `login_is_locked()` |
| `server/routers/auth.py` | 新增 `_client_ip()` **可信 IP 解析**；`login()` 改用它取 IP |

**同时修掉一个伪造漏洞（重要）**：

旧实现把**整个 `X-Forwarded-For` 头**原样当作 IP 存库。而 `hergent.cn` 的 nginx 用 `$proxy_add_x_forwarded_for`（把真实对端**追加**在末尾），于是客户端只要自带
`X-Forwarded-For: 1.2.3.4`，该头就变成 `1.2.3.4, 真实IP`，整串被当 IP 存进库 ——
**既污染审计记录，也让「按 IP 计数」的锁定可被随意伪造前缀绕过**。

`_client_ip()` 取值优先级（两种 nginx 写法下都正确）：
1. **`X-Forwarded-For` 的最后一段** —— 伪造值只会落在前面的段里
2. `X-Real-IP` —— `hergent.cn` 的 `/api/` 由 nginx 用 `$remote_addr` 强制覆盖
3. TCP 对端地址

### 2.2 nginx（1 新增 + 2 修改）

| 文件 | 变更 |
|---|---|
| `/etc/nginx/conf.d/hergent-ratelimit.conf` | **新增**：两个 zone + `limit_req_status 429` |
| `/etc/nginx/sites-enabled/hergent` | 在 `location /api/` 前插入 `= /api/auth/login`、`= /api/auth/register`、`= /api/auth/send-code` 三个精确 location |
| `/etc/nginx/sites-enabled/hergent-erp` | 同上 |

```nginx
limit_req_zone $binary_remote_addr zone=auth_login:10m rate=60r/m;
limit_req_zone $binary_remote_addr zone=auth_sms:10m   rate=20r/m;
limit_req_status 429;
```

> `$binary_remote_addr` 取 TCP 对端地址，**客户端无法用 X-Forwarded-For 伪造**。
> 精确匹配 `= /api/auth/login` 优先于前缀 `/api/`，无需担心被覆盖。

### 2.3 前端（1 文件）

`hergent-cn-v2/src/api/client.js`：新增 `_authErrText()`，`login/register/demoLogin` 三处错误文案改用它。

**原因**：nginx 的 429 是 **HTML** 而非 JSON，`res.json()` 解析失败后回落成「登录失败」，**会被用户误读成密码错误**。现在按状态码补一条可读文案（后端自身的 429 带 `detail`，仍优先展示）。

## 三、阈值设计：两层分工（关键设计决策）

| 层 | 阈值 | 职责 |
|---|---|---|
| **应用层**（精确拦截） | 用户名 5 次 / IP 20 次 每 15 分钟<br>（≈ 1.33 次/分钟持续） | **精确**拦截暴力破解与分布式扫描 |
| **nginx 层**（拦洪峰） | 60 次/分钟（burst 30） | 拦**流量洪峰**（脚本秒级连打），保护应用进程 |

**为什么 nginx 阈值要放宽**：精确拦截已由应用层负责（比任何合理限速都严得多），nginx 只需拦洪峰。
阈值过窄会**误伤 NAT 共用出口的正常用户**——办公室多人早上同时登录，每人一次就可能撞上 burst。

> 实测 `burst=10` 时仅放行 5 次，对「10 人同时登录」的场景明显不够 → 因此调宽。

**实测放行容量**：60 次连打中放行 **35 次**（burst 30 + 循环耗时约 5 秒按 1/s 排空 ≈ 35，与理论吻合），3 秒后即恢复放行。

## 五、经验教训：一次测试流程的设计错误

第一次真机验证失败（提示为空），**根因是测试脚本自身逻辑错误**，不是产品缺陷：

- 用**同一个用户名**连打 45 次 → 5 次后返回的 429 是**后端用户名锁定**产生的，**证明不了 nginx 限流**；
- 且 nginx 桶实际没被打满 → 第 4 步用**正确密码**登录反而成功了 → 断言失败。

**正确做法**（已在第二轮采用）：先用一个假用户名打到后端锁定（只落 5 条记录，不触发 IP 锁定），
再**持续用它**反复请求 —— 后端在锁定检查处就返回 429（**不再落库**），
而 nginx 仍按 IP 计数，于是桶被打满且库里不留新记录。

**判据收获**：区分「nginx 的 429」与「后端的 429」要看 `content-type`
（`text/html` = nginx；`application/json` 且带 `detail` = 后端）。

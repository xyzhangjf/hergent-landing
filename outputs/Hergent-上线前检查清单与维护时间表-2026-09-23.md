## 二、上线前检查清单

### A. 多租户数据隔离（你最关心的第 1 项）

> 一句话背景：系统里每个客户的数据放在**各自独立的数据库文件**里（`tenant_1.db`、`tenant_9.db`…），
> 主数据库 `erp.db` 只放"谁是谁"（账号/企业/会话）。隔离是否严密，取决于**每一次数据库读写前有没有正确地"切到自己的库"**。

| # | 检查项 | 结果 | 说明 |
|---|---|---|---|
| A1 | 数据库连接是否按租户隔离 | ✅ 已达标 | 连接按「线程 + 库路径」缓存，**不会串库**；新建租户库已是"只建结构、不带数据"（历史上的"整库复制导致客户看到别人数据"缺陷已修） |
| A2 | **成员归属校验是否读对库** | 🔴→✅ **已修复** | `erp_db.py:4754/4760`。原实现用「跟随当前租户」的连接去读**主库**的成员表；一旦上下文已切到某租户，就会去读 `tenant_N.db` 里的**残留旧行**，把"不属于"判成"属于"= **越权放行且零报错**。已改为**直连主库只读** |
| A3 | **平台级接口是否可被普通客户调用** | 🔴→✅ **已修复** | `routers/platform.py:118 / :210`。建租户、改**任意租户**（名称/套餐/人数上限/启停）原本只校验「是老板即可」，而**每个自助注册用户的角色就是"老板"** ⇒ 任一客户能开租户、能停用别的客户。已收口到「平台管理员名单表」 |
| A4 | **账号管理是否可跨租户** | 🔴→✅ **已修复** | `server.py` 的 `/api/users/{uid}/password`（改密）、`/role`（改角色）、`/status`（启停）、`/reset-code`（重置码）原只判"是老板" ⇒ **A 企业的老板可改 B 企业（乃至平台管理员）账号的密码**，等于跨租户接管。已加「同企业才可管」守卫，并把改密门槛从"≥4 位"提到与登录一致的 8 位含字母数字 |
| A5 | **账号名册是否跨租户泄漏** | 🔴→✅ **已修复** | `routers/platform.py:322` 的 `GET /api/users` 原返回**全部租户**的账号（用户名/姓名/角色/启用态）。已按调用者企业范围收口（前端无调用方，收口无回归） |
| A6 | **第三方对接回调是否可伪造租户** | 🔴→✅ **已修复** | `routers/datasources_v2.py`。金蝶/畅捷通 OAuth 回调的 `state` 原是明文 `tid=1`，且回调**本身无鉴权**（浏览器跳转天然带不了令牌）⇒ 任何人拿自己的授权码就能把连接**绑到别人租户**。已改为 **HMAC 签名**，伪造/篡改一律拒绝 |
| A7 | 数据库文件权限 | 🔴→✅ **已修复** | 生产 `*.db` 原为 `644`（**同机任意账号可读全部客户数据**，含手机号/价格/流水）→ 已收 `600`；`.env` `640→600`；历史副本目录 `incident_20260812/` 收 `700` |
| A8 | 切换租户是否校验归属 | 🔴→✅ **已修复** | `/api/tenants/switch` 原仅要求"已登录"就切上下文并下发 1 年 cookie。已加成员校验（中间件本就会拦，但此处前置拒绝更干净） |
| A9 | 接口层是否有"没带租户过滤"的查询 | ✅ 已达标 | 全量扫描未发现「过滤值直接取自请求参数」的实例（`tenant_id` 均来自登录会话或服务端常量） |

**隔离修复的验证方式（不是"看代码觉得对"）**：用隔离影子库**人为把伪造行种进 `tenant_2.db`**，证明
① 旧写法会读到伪造行并判"属于"（越权）；② 新写法读主库、判"不属于"。14 项断言全过 + 1 项反例对照。

### C. 安全

| # | 检查项 | 结果 | 说明 |
|---|---|---|---|
| C1 | 传输加密 | ✅ 已达标 | HTTP 全量 301 跳 HTTPS；Let's Encrypt 证书有效至 2026-11-09；TLS 1.2/1.3 |
| C2 | 静态站点安全响应头 | 🔴→✅ **已修复** | hergent.cn 首页**原本只有 HSTS**，缺防点击劫持/MIME 嗅探/来源泄露。已补齐 HSTS + `X-Frame-Options` + `X-Content-Type-Options` + `Referrer-Policy` + `Permissions-Policy`。<br>⚠️ 过程中踩到一个坑：nginx 的 `add_header` **不跨层继承**，而首页实际命中 `location ~* \.html$`（它自己带了缓存头）⇒ 只写在 server 级**会失效**；现改为每个 location 内引入同一片段 |
| C3 | 内容安全策略（CSP） | ⏳ **待拍板** | erp.hergent.cn 已启用；hergent.cn 静态站点未启用（怕误伤前端资源），建议真机回归后再开 |
| C4 | CSRF 跨站伪造防护 | 🔴→✅ **已修复（消除潜在后门）** | 原代码对 `/api/v1/` 开了一条无条件豁免，而系统会把 `/api/v1/x` 重写成 `/api/x` ⇒ 理论上给同一批写接口留了绕 CSRF 的门。**实测该豁免此前不可达**（权限中间件更外层、会先拦），故**不构成实际可利用漏洞**；仍已按"防御纵深"修掉 |
| C5 | 密码与账号策略 | ✅ 已达标 | 哈希已修历史缺陷（原来是密码最长只能 8 位）；登录有失败锁定（同一账号 5 次/15 分钟、同一地址 20 次）；重置于与登录同门槛 |
| C6 | 会话与 cookie | ✅ 已达标 | 令牌为加密安全随机数；cookie 为 HttpOnly + SameSite=Lax |
| C7 | 仓库是否含明文凭据 | ⚠️ 已知 | 本次复核未新增；但**历史提交中曾入库过网关密钥与提审账号**（此前已记录）⇒ **远端仓库务必保持 private**，并建议轮换网关密钥 |
| C8 | 管理端后台鉴权 | ✅ 已达标 | 平台级操作走**独立名单表**（不复用"老板"角色），名单表缺失时**默认拒绝**（不会因为表不存在就放开） |

**实测结论（C4）**：cookie 会话不带 CSRF 令牌打写接口 → `403 CSRF token required`；
带 Bearer 令牌的客户端**不受影响**（API 调用照常）。

## 一、结论摘要（先看这段）

| # | 问题 | 判定 |
|---|---|---|
| 1 | 两处是不是同一件事？ | **不是。** 是标准 RBAC 的两层：**A 链定义「角色能干什么」，B 链指派「这个人是谁」**。分层本身是对的（别合并数据表）。 |
| 2 | 数据链连通吗？ | **单向连通，且有一个断点。** B→A 通（指派时按 A 的名单校验）；**A→B 不通** —— A 链配出的**自定义角色**，B 链的下拉里**选不到**。 |
| 3 | 有重复配置吗？ | **有，而且不少。** 角色名清单 **5 份**、适用端文案 **2 份**、权限判据 **2 套口径**。 |
| 4 | 有矛盾吗？ | **有 1 条真红（护栏正在报）＋ 3 条实测矛盾。** 最要紧的是「适用端」文案已与真实权限漂移。 |
| 5 | 该整合吗？ | **分层不动，缝合 UI 与数据链。** 不建议合并数据表（会破坏多租户隔离）；建议 6 项缝合，其中 2 项是**修缺陷**而非优化。 |

**一句话**：这不是"两个功能重复"，而是**同一套 RBAC 的两个半环之间缺了一段线** —— 半环各自完好，接缝处漏了三种人（自定义角色）、两个字（适用端）、一个时机（改角色后不刷新）。

## 二、两处权限的定义 / 数据来源 / 字段映射 / 生效规则

### 2.1 A 链 ——「设置 › 权限」

| 维度 | 实况（真码位置） |
|---|---|
| **它是什么** | **角色 × 模块** 矩阵。回答「这个角色能不能调这个模块下的接口、能不能看见这个入口」 |
| **粒度** | **模块级**（`data`/`hr`/`cron`…）。勾选 = 该模块的**全部动作**（读+增+改+删） |
| **UI 位置** | `pages/Settings.vue` L29–109（`tab === 'perm'`），角色为列、模块为行 |
| **写入接口** | `POST /api/role-permissions`（`server.py:1124`）｜`DELETE /api/role-permissions/{name}` 恢复默认 |
| **读取接口** | `GET /api/role-permissions`（`server.py:1104`）+ `GET /api/permissions/modules`（L1073） |
| **落库位置** | **租户库** `tenant_<id>.db::role_permissions(role_name TEXT PK, permissions TEXT)` —— **每租户一份** |
| **数据形态** | 两种都合法：legacy `["stock","data"]`｜新版 `{"stock":["read","create"]}`（`core._canon_perms` 归一） |
| **权威来源** | `core._DEFAULT_PERMS`（内置默认，8 角色）+ 本租户自定义行，**按角色整表覆盖**（`{**默认, **自定义}`） |
| **鉴权** | 四个端点一律 `core._admin`（`role ∈ {admin,boss}`）；并在 RBAC 中间件里**豁免模块判定**（L770）——防"撤掉 boss 的 hr 导致老板打不开唯一能改回来的页" |
| **防自锁** | `PROTECTED_ROLES=['admin','boss']` × `CRITICAL_MODULES=['hr','data']` 四格锁定不可取消（`Settings.vue:548`） |

**生效规则（A 链是"快"的那条）：**

```
点保存 → 逐角色 POST → tenant_<id>.db 落库 → core.reload_perms(tid)（只失效本租户缓存）
                                              ↓
        ┌─────────────────────────────────────┴─────────────────────────────────┐
        ↓                                        ↓                              ↓
 perms_for(tid) → _check_perm             user_modules() → 前端 store.perms   custom_roles(tid) → store.customRoles
 （后端接口闸门，立即）                     （侧栏模块轴，立即）                 （内置 roles 门槛是否让位）
                                                                                    ↓
                                                          本会话：syncStorePerms() 强制重拉（当场生效）
                                                          其它会话：靠 perms_rev 内容指纹轮询，最迟 1 分钟跟随
```

### 2.2 B 链 ——「员工档案 › 账号与权限」

| 维度 | 实况（真码位置） |
|---|---|
| **它是什么** | **人 → 角色** 的指派。回答「这个账号是谁、干哪份活」 |
| **粒度** | **账号级**：1 个主角色（单值）+ N 个兼任角色（v266 起可叠加） |
| **UI 位置** | `pages/EmployeeArchive.vue` L176–260（「编辑员工」弹窗内的账号卡） |
| **开账号** | `POST /api/forecast-submissions/staff-accounts`（`forecast_submissions.py:1224`）→ `erp_db.staff_account_create`（L18933） |
| **改角色** | `PUT /api/users/{uid}/role`（`server.py:1215`），body `{role, roles[]}` |
| **其它账号操作** | `PUT /api/users/{uid}/username`（v288 改登录名）｜`POST /api/users/{uid}/password`（重置密码）｜禁用/启用｜生成一次性重置码 |
| **落库位置** | **主库** `erp.db::users(id, username, password_hash, display_name, role, roles, is_active, phone, employee_id, password_changed …)` —— **全局单表** |
| **字段映射** | `users.role` → 前端 `account_role`｜`users.roles` → `account_roles`（逗号串）｜`users.id` → `account_user_id`；由 `erp_db.py:6908-6923` 在员工列表接口里 enrichment 下发 |
| **角色白名单** | `core.normalize_role` → `known_roles(tid)` = `_DEFAULT_PERMS.keys() ∪ perms_for(tid).keys()`（L739）——**这就是两条链唯一的接触面** |
| **鉴权** | `_assert_user_manageable`：必须 admin/boss **且**目标账号在调用者企业范围内（v254 防跨租户接管） |
| **是否写 A 链** | **完全不写。** 改角色不触碰 `role_permissions`，也不影响 `custom_roles` |

**生效规则（B 链是"慢"的那条）：**

```
点保存 → PUT /api/users/{uid}/role → UPDATE users SET role=?, roles=? → audit_log
                                                      ↓
                                    🔴 没有缓存失效、没有版本号
                                    ⇒ 该用户当前会话的 store.user.role 仍是旧值
                                    ⇒ 需重新登录（或重拉 /api/auth/me）才生效
```

### 2.3 两条链的接触面只有一处

```
A 链  ──定义──▶  role_permissions（租户库）  ──▶ perms_for / user_modules / custom_roles
                                                        ▲
                                                        │ 唯一的连线：
                                                        │ core.known_roles(tid)  ← 只用于 B 链**写入时**的白名单校验
                                                        │
B 链  ──指派──▶  users.role / roles（主库）  ─────────────┘
```

**这不是设计疏漏，是刻意的**：`known_roles` 复用 A 链的"角色名册"作为合法值域，避免另抄一份角色清单。方向也是对的（A 定义、B 引用）。**问题在于这条线只接了"写"，没接"读"和"提示"** —— 见第三节。

## 三、数据链连通性判定（含生产实证）

取证脚本 `perms-dual-chain-audit.py` 在生产上以 `mode=ro` 跑，判据用 `ast` 从生产 `core.py` 实取（非手抄）。

### ✅ 连通的部分

- **B → A 单向连通**：指派角色时走 `known_roles(tid)` ⇒ B 链"知道"A 链里有哪些角色（含自定义）。
- **同一份角色名册被复用**：`normalize_role` 是两处写入口（开账号 / 改角色）**共用的唯一判据**，没有各写一份。

### 🔴 断点：A 链配得出、B 链指派不了

生产实证（`01-生产双链数据链透视.txt`）：

```
[⑤] A 链配得出权限、但 B 链下拉里选不到的角色（只能手改库）：
     自定义角色共 4 个：['accountant', 'staff', 'supervisor', '库管']
     🔴 下拉选不到的：['库管']
```

- **A 链**：`tenant_1.db::role_permissions` 里**有 `库管` 行**，权限 = `['chat','dashboard','data','stock']`（4 个模块，**客户真配过**）。
- **B 链**：`EmployeeArchive.vue::ROLE_OPTIONS`（L390-399）是**前端写死的 8 项**，**不含 `库管`** ⇒ 下拉里选不到 ⇒ **无法把员工指派成 `库管`**。
- **后端其实是允许的**：`known_roles(tenant_1)` = 9 个（含 `库管`）⇒ `PUT /api/users/{uid}/role` 会**放行** `库管`。
- **净效果**：一条**只有 API 能走、UI 走不通**的路。生产上 `users.role` 里 **0 个 `库管`** ⇒ 这条配置**配了但没有任何账号在用**（死配置）。

### 🔴 断点之二：自定义角色即使被指派，也**看不到该看的页面**

`pages.js::roleGateOpen` 第③档「让位」要求 `r.module` 非空：

```js
function roleGateOpen(r, role, customRoles) {
  if (!r.roles) return true                              // ① 不按角色收紧
  if (roleIn(role, r.roles)) return true                 // ② 在名单里
  if (r.lock === true) return false                      // 产品硬锁
  if (!r.module) return false                            // 🔴 没有 module 可判 ⇒ 让位 = 全开，不许
  if (!Array.isArray(customRoles)) return false
  return customRoles.includes(normRole(role))            // ③ 用户配置优先
}
```

而 `/archive`（档案管理，`module: null, roles: BIZ_ROLES`）、`/rebate`、`/loss`、`/forecast` 这些页面的 **`module` 都是 `null`** ⇒ 自定义角色在它们上一律 `return false`。

**后果**：租户给 `库管` 勾了「档案管理」（`data` 模块），但 `库管` **进不去「档案管理」页面** —— 因为那一页按 `roles` 收窄、`module` 为 `null` 不让位。⇒ **勾了等于没勾，且界面零提示。**

### 数据链现状图

```
「设置 › 权限」                                 「员工档案 › 账号与权限」
 role × module                                  账号 × role/roles
      │                                               │
      ▼                                               ▼
 tenant_<id>.db::role_permissions              erp.db::users.role/roles
      │                                               │
      │  perms_for(tid) ──▶ 后端接口闸门 ──────────────┤（模块轴，两条链在此**间接**相遇）
      │  custom_roles(tid) ──▶ 让位（有 module 才算）   │
      │                                               │
      └──── known_roles(tid) ─────────────────────────┘  ← 唯一的直接连线（仅写入校验）
             ▲
             └── 🔴 断点①：自定义角色不在前端下拉 ROLE_OPTIONS 里（写死 8 项）
             └── 🔴 断点②：自定义角色对 module=null 的页面拿不到让位
             └── 🔴 断点③：B 链改角色后无缓存/版本号失效 ⇒ 不重新登录不生效
```

## 四、重复配置盘点（同一件事被写了几份）

| # | 被重复的东西 | 份数 | 位置 | 护栏 |
|---|---|---|---|---|
| 1 | **角色名清单** | **5** | ① 后端 `core._DEFAULT_PERMS`（**权威**）② 网页端 `constants/roles.js::ROLE_NAMES` ③ 小程序 `utils/roles.js::ROLE_TEXT` ④ `EmployeeArchive.vue::ROLE_OPTIONS` ⑤ `Settings.vue::ROLE_LABELS` | ✅ 有（`role-registry-consistency-check.py`，AST 解析后端 · 35/37） |
| 2 | **「适用端」文案**（网页端/小程序） | **2 + 1** | ① `ROLE_OPTIONS` 的 label 文字 ② `roles.js::MINI_PROGRAM_ROLES`（硬编码名单）③ `canUseMiniProgram()` 的**注释** | ⚠️ 有但**正在报红**（见 §5.1） |
| 3 | **权限判据口径** | **2** | ① `canUseMiniProgram()` 函数体用硬编码 `MINI_PROGRAM_ROLES`｜② 同一函数的**注释**说判据是"有 `data` 或 `chat`" | ❌ 无 |
| 4 | **角色中文名** | 3（已收敛）+1 | 网页端 `ROLE_NAMES`｜小程序 `ROLE_TEXT`｜`Settings.vue::ROLE_LABELS`（措辞更长，**故意留本地**） | ✅ 有（含跨仓逐字比对） |
| 5 | **"权限"这个词** | 2 个不同事物 | `/settings` 的「权限」= RBAC 模块矩阵｜`/roles`「AI 团队」= `ai_roles`（AI 人设，`/api/ai/roles`） | ❌ 无（纯术语问题） |

### 重复配置的**结构性根因**

第 1 项里，④⑤ 两份是**同一张表的两个消费场景**（下拉 vs 矩阵列头），措辞不同是合理的；**问题是它们与 ①②③ 之间靠"人记得同步"**，靠护栏兜。

而真正无法靠护栏解决的，是 **`ROLE_OPTIONS` 写死了 8 项** —— 护栏是**静态**的（构建前跑），而**租户自定义角色是运行时数据**。⇒ 这一类重复**不可能**有护栏，只能改成**动态取**。这是 §7 建议第 1 项的直接依据。

## 五、矛盾之处（逐条实证）

### 5.1 🔴 「适用端」文案 vs 真实权限 —— **护栏正在报红（真红）**

```
D 员工档案 · 角色下拉的「适用端」标注 ↔ 后端模块权限
  FAIL  标了「小程序」的角色集 = 后端有 data/chat 权限的角色集   [文案多 [] / 少 ['accountant', 'driver', 'guide']]
        admin=小程序 | boss=小程序 | accountant=小程序 | sales=小程序 | guide=小程序 | driver=小程序 | staff=小程序 | supervisor=小程序
```

**读法**：按后端**真实模块**判，8 个角色**全都"能用小程序"**（因为 v292/v293 给**所有**角色补了 `chat`，为了让每个人都能走 AI 代理降级通道）。但员工档案页的文案仍写着 `accountant: '会计（仅网页端 · 账务 / 报表 / 营销）'` —— **文案说"仅网页端"，权限说"能用"**。

**这是真的，不是护栏误报**（判据 `can_use_miniprogram` 直接从 `_DEFAULT_PERMS` 实取模块列表）。

**根因**：`chat` 被当成"通道保护"的开关加给了所有角色，但"适用端"文案的判据（最初是 `data` 有无）**没跟着改**。

**同时**：`roles.js::canUseMiniProgram()` 的注释还写着「对照 `_DEFAULT_PERMS`：admin/boss/sales/staff/supervisor 有，accountant/guide/driver 没有」—— **这句话已经过时**。且函数体用的是硬编码 `MINI_PROGRAM_ROLES`（不含 accountant），与它自己上半段的判据注释**互相矛盾**。

### 5.2 🔴 自定义角色：配得出 / 指派不了 / 进了也看不到页（三段不连通）

见 §3。**三个环节各自都对，串起来是断的**：

| 环节 | 状态 |
|---|---|
| A 链给 `库管` 配权限 | ✅ 成功（tenant_1 有 4 个模块） |
| B 链把员工指派成 `库管` | ❌ 前端下拉选不到（写死 8 项） |
| 假若手改库指派成 `库管`，他能看到的页 | ❌ 只有工作台 / 经营趋势 / AI 中心；**`module: null` 的业务页一律进不去**（含他刚被授权的「档案管理」） |

### 5.3 🟡 内置默认迭代 vs 租户库整表覆盖 —— **实测到的存量差异**

`_DEFAULT_PERMS` 只管**未被租户库覆盖**的角色；一旦某角色在租户库里有一行，就是**整表覆盖**。生产实测：

| 租户 | 角色 | 租户库实际 | 内置默认 | 差异含义 |
|---|---|---|---|---|
| tenant_10 | `staff` | `[cron, data, stock]` | `[bid, chat, cron, data, stock]` | **少 `chat`** ⇒ 该租户员工**用不了 AI 对话**（v292 加的默认对它无效） |
| tenant_10 | `supervisor` | `[cron, dashboard, data]` | `[bid, cron, dashboard, data, sales]` | **少 `sales`** ⇒ 主管**看不了返利冲刺看板**（v293 加的默认对它无效），且是"页面进得去、数据恒空、零报错" |
| tenant_1 | `supervisor` | `[chat, cron, dashboard, data, sales]` | 同上一行 | 少 `bid`（有意，`bid` 未迁给 supervisor） |
| tenant_10 | `boss` / `sales` / `guide` / `driver` | 与默认**逐字相同** | — | 证明 `custom_roles` 的**内容判据**是对的：若按"表里有行"判，这 4 个角色会被误判成"改过" ⇒ `roles` 门槛全让位 |

⇒ **`tenant_10` 的 `supervisor` 少了 `sales`，这是一个现存的功能缺口**（v293 那轮只改了 `_DEFAULT_PERMS`，注释里也点明了"必须同时改租户库"，但该租户库没改）。

### 5.4 🟡 `boss` 行里的 3 个"幽灵模块"

`tenant_10` 的 `boss` 行有 **19 个模块**，含 `ops-workbench` / `perf` / `goals` —— 三者**不在 `_ALL_MODULES`(17 项)** 里。⇒ 权限页**不渲染这 3 行**，但它们**确实存在数组里**（v296 已修"保存时静默抹掉"的缺陷，现在逐字回传）。

⇒ 影响：这 3 个模块**客户改不了、也看不见**，但它们在判定中生效（`_perm_granted` 认它们）。

### 5.5 ⚪ 护栏的 1 条**假红**（不是缺陷，但会误导）

```
F 后端 · 角色白名单与两处写入口接线
  FAIL  开账号接口（staff-accounts）接入了白名单
```

**实情：接口是接了的。** `forecast_submissions.py:1245` 就是 `role = normalize_role(d.get("role","staff"))`，且 1238 行 `from core import normalize_role`。

**真因**：护栏正则 `async\s+def\s+create_staff_account[\s\S]{0,900}?normalize_role\s*\(` 的 **900 字符窗口太紧** —— v289 在那段插了一长段中文注释（密码策略归一），把调用点推到了 900 字符之外。

⇒ 按项目纪律（`local-machine-pitfalls.md §12/§13`）：**这是探针自己的错，不是被检对象的错**，应修护栏窗口。

## 七、是否整合？—— **分层不动，缝合接缝**

### 7.1 先给结论

> **不该合并数据表，也不该合并页面；该把两个半环之间的三种"接缝"接上。**
>
> 现状不是"两个功能重复"，而是**同一套 RBAC 的两个半环之间漏了线**。合并会砸掉正确的分层，缝合才是对症的。

### 7.2 方案对比

| 方案 | 做什么 | 利 | 弊 | 判定 |
|---|---|---|---|---|
| **A. 物理合并**（把角色定义塞进员工档案页，或把账号指派塞进设置页） | 一个页面管全部 | 概念上"一处配完" | ① 破坏多租户隔离（`role_permissions` 在租户库、`users` 在主库，合并必然要跨库事务）② 员工档案页要渲染「角色 × 模块」矩阵 = 把配置页塞进档案页 ③ 与现有 RSBAC 分层（用户→角色→权限）背道而驰 ④ 改动面 = 40+ 文件的鉴权链 | ❌ **不做** |
| **B. 保持分层 + 缝合接缝**（推荐） | 6 项小改动，其中 2 项是修缺陷 | ① 分层保留（这是对的）② 每项改动局部、可单独验收 ③ 直接消灭 P0 的 4 个风险 ④ 顺带修掉护栏假红 | 需要接受"仍然有两个入口" | ✅ **推荐** |
| **C. 只做只读双向导航** | 两页互相加个深链 | 改动最小 | 不解决自定义角色指派不了、不解决生效时机不一致 | ⚠️ 不够 |

### 7.3 推荐方案 B 的 6 项（按价值排序）

| 优先级 | 改动 | 解决 | 说明 |
|---|---|---|---|
| **★1** | **B 链角色下拉改为动态取自后端** | P0#3 | `ROLE_OPTIONS` 的**值域**改从 `GET /api/role-permissions` 的 roles keys（= `known_roles(tid)`）取；`value` 用后端角色名，**中文名**用 `roles.js::roleName()`。文案里那句「仅小程序/仅网页端」改成**从该角色的真实模块权限现算**（判据收敛到 `_DEFAULT_PERMS`/租户表），不再手写 ⇒ **一并消灭 P0#1 的文案漂移** |
| **★2** | **员工档案「角色/权限」区加只读预览 + 深链** | P0#3/P0#4、P2#9 | 选中角色后展示「该角色可进哪些页 / 可调哪些接口」摘要（读 A 链），并给「去设置页配置这个角色 →」深链（`/settings?tab=perm`）。让"指派"与"定义"在同一屏可见，且方向明确 |
| **★3** | **A 链矩阵页每列加「在用账号数」** | P0#3、P1#7 | 读 `users` 按 role 分组计数。让"改这个角色会影响谁 / 这个角色是不是没人用"**当场可见** —— `库管` 那条死配置就是这么被发现的 |
| **★4** | **修 tenant_10 的 `supervisor`（补 `sales`）** | P0#2 | 这是**存量数据缺口**，不是代码缺陷。用 v296 迁移脚本的同款做法（备份 → 迁库 → 复验），并在迁移脚本里加一条"默认值迭代后租户库等价性"的检查项 |
| **5** | **B 链接入版本号刷新** | P1#5 | 复用 `perms_rev` 的同款思路（改角色后 bump 一个 `roles_rev`，前端轮询比对）⇒ 两条链的生效承诺一致。**注意**：这会动到 `store`，需评估与现有 60 秒轮询的合并 |
| **6** | **修护栏 900 字符窗口 + 术语消歧** | P2#11、P2#9 | 护栏窗口放宽（或改为不依赖字符数的定位）；`/roles` 页标题从「AI 团队」在**侧栏**已区分，但**权限页文案**里应明确"此角色非彼角色" |

### 7.4 明确**不做**的

- ❌ 合并 `users` 与 `role_permissions`（跨库、破坏隔离、无收益）
- ❌ 把「权限」tab 从设置页挪走（`lock: true` 与 `_admin` 鉴权是精心设计的防自锁机制，别动）
- ❌ 让自定义角色自动获得 `module: null` 页面的让位（那等于"勾一个模块放开一整类页面"，正是 v296 刚收紧的方向）
  - 若客户确实需要给自定义角色放开业务页，**正确做法**是让这些页面挂上 `module`（如 `/archive` 挂 `data`），而不是放宽让位条件。**这需要单独评估**（会改变现有 `roles` 收窄的语义）。

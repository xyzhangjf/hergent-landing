## 一、结论（只看这一段也够）

### 1.1 一句话

> 你点「保存」后，前端**第一步**就把 154 行商品档案发给后端；后端在一个**写事务里面**逐行调用
> `track_brand()` 去登记品牌，而 `track_brand()` **自己又开了一个新连接**去写 `brand_pending`——
> 新连接要写，事务还没提交 ⇒ **撞在自己身上**，每次白等 SQLite 的 `busy_timeout = 5 秒`。
> 你的数据里有 **28 行**的品牌不在册，于是 **28 × 5 秒 = 140 秒**。
> 前端在 **20 秒**处就放弃了 ⇒ nginx 记 **499** ⇒ 弹「保存失败（网络或服务器异常）」。
> **保存按钮你点到了、请求也发出去了，是它一直回不来。**

### 1.4 量化模型（可以直接拿去估算）

```
失败 ⟺ (品牌不在册的行数 N) × 5 秒  >  20 秒
     ⟺ N ≥ 4
```

| N（不在册品牌的行数） | 后端耗时 | 结果 |
|---|---|---|
| 0（全部品牌都已登记） | < 1 秒 | ✅ 正常保存 |
| 1 ~ 3 | 5 ~ 15 秒 | ⚠️ 能保存成功，但每次白等；期间**全库写锁** |
| **≥ 4** | **≥ 20 秒** | ❌ **必然超时 → 499 →「保存失败（网络或服务器异常）」** |

你现在的 N = **28** ⇒ 稳定失败，**每次都会**。

```python
# connection.py:200-237（摘，注释是它自己写的）
def _sqlite_connect():
    """... Re-entrant calls (same thread already holds a cached conn for this key)
       get a fresh throwaway connection to preserve transaction isolation."""
    reentrant = _sqlite_in_use.get(key, 0) > 0                     # 209
    conn = _sqlite_cache.get(key) if not reentrant else None        # 210
    conn = sqlite3.connect(db_path)                                # 224
    conn.execute("PRAGMA busy_timeout=5000")                       # 228  ← 每次白等 5 秒
```

**这是「自锁」，不是「竞争」**：外层事务不提交就等不到内层返回，内层在等外层释放锁 ⇒
**永远失败、且每次都要走满 5 秒超时**。所以它是**确定性的 5 秒 × N**，不是偶发。

**品牌数据现状（`tenant_1` 实测）**：

```
products.brand 分布：18 个不同值（438/449 个商品带品牌）
  不在 brands 里的（⇒ 每行都触发 5 秒等待）:
```

## 四、排查思路：写操作失败**七步法**（第 0 步本轮再升级）

### 🔴 第 0 步 · 定日志归属 —— 而且要**两层都查**

**旧版第 0 步只写了「查应用日志」。本轮证明这不够，必须补反向代理层：**

| 层 | 命令 | 独有信息 |
|---|---|---|
| 应用日志 | `journalctl -u hergent-erp --since <t> -o short-iso` | 业务异常、trace id、`database is locked` |
| **反向代理** | `zgrep <path> /var/log/nginx/access.log*` | **`499 / 502 / 504`**、**客户端 UA**、`Referer`、返回体积 |

**三条硬规则**：

1. **`499` 只存在于 nginx**：客户端在服务端回包前断开。**应用日志里不会有任何一行。**
   👉 反推请求起点：`请求起点 = 499 时刻 − 客户端超时（本项目 20 秒）`。
2. **nginx 是唯一带 UA 的层** ⇒ 分辨「真实用户」与「我的探针」全靠它。
   （本次判据：`QQBrowser/21.9.0.213` = 你；`HeadlessChrome` / `curl` / `node` = 我的探针。
   注意**出口 IP 相同**，IP 无法区分归属。）
3. **应用日志的保留窗口可能比 nginx 短**，且**格式不带 UA** ⇒ 归属判定不能只靠它。

**顺带记下：`journalctl` 里 `database is locked` 的日均量级并不高**（6/26 至今只有 3 天出现：
`Aug 02` 1 次 / `Sep 01` 63 次「另属 `POST /api/rebate-rules`，待查」/ `Sep 18` 97 次）。
所以**不能**用「日志里锁错误很多」当常态理由——**它就是异常**。

### 第 1 步 · 读界面上的原文，别读它的归类

「保存失败（**网络或服务器异常**）」括号里是**前端猜的**。看到 `网络/超时` 这类归类，
**先假设「后端可能根本没回包」**，而不是「网络有问题」。

### 第 2 步 · 数一下这个动作发了几个请求

`saveEdits` 是**三阶段三请求、非事务**。先定失败在第几个 ⇒ 本次是**第一个**。
判据：`prodDone` 是否为 `true`（`true` = 「①成②败」）。

### 第 3 步 · 抓真实载荷

Network 面板看该请求的 Request Payload；重点不是 `customers` 长度，而是**这个端点本身要跑多久**。

### 第 4 步 · 后端该接口的**全部**失败点逐个过

grep 出函数体内所有 `HTTPException` / `raise`。
👉 **本次的教训：还要额外检查「不 raise 但会慢」的路径**（吞异常的 helper、事务内嵌套连接）。
`save_matrix` 全文只有 1 处 400，但它**不是本次的接口**。

### 第 5 步 · 查生产日志拿时间戳（**两层**）

```bash
# 应用层
journalctl -u hergent-erp --since "<t0>" --until "<t1>" -o short-iso | grep -e save-matrix -e bulk-upsert -e "database is locked"
# 代理层（关键补充）
zgrep -e "save-matrix" -e "bulk-upsert" /var/log/nginx/access.log* | awk '$9!=200'
```

⚠️ 别用 `sed 's/.../\1/'` 提时间戳（会静默丢时间），用 `-o short-iso` 或 `awk`。
⚠️ `awk` 里写 `$4 ~ /\[18\/Sep/` 会因为 `[` 未转义直接 fatal，**用 `grep "18/Sep/2026"` 更稳**。

### 第 6 步 · 看「慢」的节拍，识事务自锁

**新判据（本轮新增）**：如果日志里同一 trace 出现**等间隔重复**的 `database is locked`，
间隔恰好等于某个 `busy_timeout` 值 ⇒ **事务自锁**，不是竞争。

```bash
journalctl -u hergent-erp --since "<t0>" | grep "track_brand" | sed -E 's/.* ([0-9:]{8}) .*/\1/'
# 看到 :57 :02 :07 :12 ... ⇒ 精确 5 秒 ⇒ 命中 busy_timeout=5000
```

### 第 7 步 · 隔离沙箱直连接口复现

`.workbuddy/tools/sandbox_tenant.py`（id ≥ 9997，只在服务器跑）。
⚠️ **本轮新增**：沙箱复现「慢写超时」必须**让客户端愿意等**（我的探针等了 ~140 秒才拿到 200），
否则会误以为「后端坏了」。**同一请求：等 140 秒 → 200；等 20 秒 → 499。**

### ⚠️ 本方法论踩过的坑（本轮新增 5 条）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 🔴 **只查应用日志，不查反向代理** | 得出「后端无记录 ⇒ 只能是前端异常」的**错误结论**（v1/v2 连错两轮） | 第 0 步两层都查；`499/502/504` 只在 nginx |
| 🔴 **把「请求已经发出去了」当成「后端处理了」** | 499 的请求在应用日志里**什么都不留** | `499` = 客户端主动断开；要反推请求起点 |
| 🔴 **拿「等间隔 5 秒」当网络抖动** | 会去查网络/nginx 超时，方向全错 | 等间隔 = `busy_timeout` ⇒ 事务自锁 |
| 🔴 **只按 `e.message` 分类，不看 `e.name`** | `AbortError` 的 **message** 无关键词，但 **name** 就是 `AbortError` | 分类器同时读 `e.name` 与 `e.message` |
| 🔴 **假设「后端没记录」=「用户没操作」** | 忽略「请求进去了但没出来」这一第三种状态 | 加一层 nginx |
| 部署目录不留历史 dist | 无法事后回答「用户当时跑的是哪一版」 | 每次部署留 `dist-<ts>.tar.gz` 若干天 |
| 探针 `summarize()` 结构未兜底 | `res.reqs` 为 `undefined` ⇒ FATAL，480 秒白跑 | 所有 `res.*` 一律 `\|\| []` / `\|\| {}` |
| 探针循环上限 < 实际条数 | 决定性用例没跑到，而断言仍打印相邻结论 | 上限 ≥ 实际条数 |
| `console` 抓 Error 得到 `JSHandle@error` | 等于没抓 | `m.args()` + `arg.evaluate(e => e.stack \|\| e.message \|\| String(e))` |
| `grep "A\|B"` 在 zsh 里静默失效 | 返回空，像「没有匹配」 | 一律 `grep -e A -e B`（本次**又踩一次**） |
| 用本地时间匹配 `created_at` | 查不到行（`created_at` 默认 `CURRENT_TIMESTAMP` = **UTC**；服务端 `datetime('now','localtime')` = **CST**） | 两个口径都打 |

**B. 连带的技术风险（比 A 更值得看）**：`bulk-upsert` 与销售单导入的商品匹配都是
**「条码优先」**（`barcode` 命中即返回，不再看名称）。于是对上面这些**共用条码**的组：
- 录入「24 瓶」那一行的规格，**会被写进「÷6 组」那一行的商品**（命中 id 较小者）；
- 录「草莓」，会被挂到 **「巧克力」**（id=1388）上 —— **销量、库存、厂价全部记到错的口味**。

**建议（未实施，等你一句话）**：把匹配顺序改为 **`条码+名称` 精确 → `条码` → `名称`**。
多一层「条码+名称」的精确优先只会在原逻辑**错配**时生效，对单规格场景**行为完全不变**，属严格更准。
（`#504` 加的 `ORDER BY id LIMIT 1` 只是让结果**确定**，并没有让它**正确**。）

**C. `products.barcode` 缺 UNIQUE 约束**（见 9.3 根因）：补它需先清完存量重复；

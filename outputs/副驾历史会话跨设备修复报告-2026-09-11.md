# AI 副驾「换设备看不到历史会话」— 根因定位与修复

**日期**：2026-09-11
**症状**：在同一账号上换另一台设备（或另一个浏览器）登录，AI 副驾的「历史会话」看不到原设备聊过的对话。
**结论**：后端一直在正常落库，**问题 100% 在前端读取策略**——本地缓存一旦存在就永久拦住了服务端拉取。

---

## 一、排查过程与证据

### 1. 后端是好的（先排除）

`server/routers/ai_assist.py` 有一套完整的会话持久化：`chat_sessions` 表，按 `user_id` 隔离，`_who(u)` 取 `username`（稳定、非设备相关）。

直接查生产库，**会话确实在**：

```
/opt/hergent-erp/tenant_1.db
  ('boss', 's1789104653383', '今天该订什么货？',       '2026-09-11 13:30:53')
  ('boss', 's1789089783742', "Hi~ I don't recognize…", '2026-09-11 09:26:56')
```

接口也是通的：

```
GET /api/ai/sessions  →  200
{"ok":true,"sessions":[{"session_id":"s1789097066461","title":"今天该订什么货？",...}]}
```

→ **服务端有数据、接口 200**，所以不是后端问题。

### 2. 全新设备其实能拉到（把范围收窄到"有本地缓存时"）

用**全新浏览器配置**（`userDataDir` 独立，localStorage 必为空）登录演示账号：

```
历史会话：2 条（今天该订什么货？ / E2E session）
会话接口：GET /api/ai/sessions → 200 ×2
```

→ 全新设备**正常**。

### 3. 加上本地缓存立刻失效（命中根因）

给同一个新配置**预置** `hergent_chat_sessions_v1` 再登录：

| 场景 | 是否请求服务端 | 历史列表 |
|---|---|---|
| 本地是 `[]`（空数组） | ❌ **从未请求** | 空 → 显示「还没有历史会话」 |
| 本地有别的会话 | ❌ **从未请求** | 只显示本地那一条 |

---

## 二、根因

`hergent-cn-v2/src/store/index.js` 旧实现：

```js
function loadSessions() {
  try {
    const raw = localStorage.getItem(CHAT_KEY)
    if (raw) { chat.sessions = JSON.parse(raw); return }   // ← 元凶
  } catch { chat.sessions = [] }
  loadSessionsFromServer()   // 只有本地为空才会走到这里
}
```

三个致命点：

1. **本地优先被写成了"本地有就返回"**。`raw` 是字符串 `"[]"` 时也是真值 → 本地数组就算空的，也照样 `return`，永不去服务端对齐。
2. **`CHAT_KEY` 是全局单键，不按账号隔离**。同一台浏览器上任何人用过（哪怕只是把会话删空、留下一个 `"[]"`），这个 key 就永久存在，从此该浏览器再也拉不到服务端历史。
3. **"历史会话"按钮在列表为空时是 `disabled`**，用户连点都点不进去，只能看到一个空面板，无从察觉是"没拉"还是"没有"。

这解释了为什么"原设备能看到、新设备看不到"——**原设备看的是它自己 localStorage 里的那份**。

---

## 三、修复内容（3 个文件）

### `src/store/index.js`

- **`loadSessions()` 重写**：本地缓存只用于**秒开渲染**，之后**无条件**向服务端对齐一次。本地要不要渲染，和要不要拉服务端，彻底解耦。
- **`loadSessionsFromServer()` 改成合并**：以服务端会话为主，本地独有的（尚未同步成功的）追加保留，避免"聊了却消失"；按时间倒序排列。
- 新增 **`tsNum()`**：本地存 `Date.now()` 数字、服务端回 `'YYYY-MM-DD HH:MM:SS'` 字符串，排序前统一归一（混排会让排序错乱）。
- 新增 **`clearChatCache()`** 并导出。
- 新增 **`chat.sessionsLoading`** 状态。

### `src/components/Shell.vue`

- `logout()` 里调用 `clearChatCache()`：会话按账号存服务端，本地若跨账号残留，会让下一个登录的人看到上一个人的对话。

### `src/components/CopilotDrawer.vue`

- 「历史会话」按钮**去掉 `disabled`**，列表为空也能打开。
- 空态区分文案：加载中 →「正在加载历史会话…」，确认无数据 →「还没有历史会话」。
- 每次打开历史都调一次 `loadSessions()`，保证看到别的设备刚聊过的会话。
- 列表元信息：服务端会话只回了标题、没回全文，原来固定渲染 `· 0 条` 会被误读成"空会话"；改为**只在已知条数时才显示**。

## 五、需你确认的第二件事（不同根因，我没动）

生产实测，**非管理角色会被 RBAC 拦掉**：

```
mptest   (sales)       GET /api/ai/sessions → 403  权限不足：'sales' 不能访问 'chat' 模块
mptestsp (supervisor)  GET /api/ai/sessions → 403  权限不足：'supervisor' 不能访问 'chat' 模块
```

`server.py` 里 `/api/ai` → `chat` 模块（fail-closed）。但副驾对话本身走 `/hermes/`，**不经过这条 RBAC**。于是这类角色出现一个别扭状态：**能用副驾聊天，但会话永远存不到服务端**（POST 同样 403，且是静默失败）→ 他们的历史天然只能留在本机，换设备一律没有。

这不是本次前端 bug，是权限边界的设计问题，需要你拍板：

- **A. 保持现状**：只有具备 `chat` 权限的角色（管理岗）享受跨设备历史，一线员工的历史就是本机的。
- **B. 把会话读写从 `chat` 模块里豁免出来**：只放行 `/api/ai/sessions*`（自己的会话，天然按 `user_id` 隔离），其余 `/api/ai/*` 仍按 `chat` 管。能让一线员工也跨设备接续，安全性影响很小。
- **C. 给相关角色补 `chat` 权限**：改动最小，但等于把整个 AI 模块对一线开放，面太大。

我建议 **B**，但这是权限边界，等你说。

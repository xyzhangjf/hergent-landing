**核心结论（也是对最初那个设计问题的回答）**：**不做**「导入完成 → 弹窗逼命名期次」。

- 归属期次是**导入那一刻**由后端解析定死的（`import_router`: `forecast_period_current()` → 兜底 `forecast_period_default()`）；
- 导入后再命名**不会**把已落库的数据挪过去 ⇒ 那个时机问用户是无效提问，还会让人以为「导入没结束」而回头重导；
- 正确做法 = **导之前**把归属摆出来（pick 步「本期归属」），只有真的没归到任何期次时才在回执里给一次条件引导。

## 二、变更（逐文件）

### 后端 · `server/erp_db.py`（+112 / −3）

1. **P0 修复（根因）**：`forecast_submission_summary` 里 `imported_products` 原为**单口径** `r.period_id=?`，
   而同函数的 `rows` / `date_cond` 是**双口径** `(s.period_id=? OR (s.period_id=0 AND s.order_date BETWEEN ? AND ?))`。
   期次刚建好、历史导入还是 `period_id=0` 时，行底（`rows ∪ imported_products`）会**丢掉全部导入登记商品**。
   现改为与 `date_cond` 分支结构**逐条同构**。
2. **新增** `period_validate(name, order_start, order_end, arrival)`：硬校验**唯一实现**
   ——名称非空且 ≤80 字、三日期必填且格式合法、开始≤截止、到货≥截止。POST 与 PATCH 共用。
3. **新增** `forecast_period_update(pid, ...)`：仅 `status='open'` 可改；缺省字段沿用现值；
   **只返回真的变了的字段**（同值重提 = noop，不落库不留痕）；旧库 NOT NULL 的
   `order_start_date/order_end_date` 按列存在性双写。
4. `forecast_period_create` 接入 `period_validate`。

### 后端 · `server/routers/forecast.py`（+56 / −1）

- 新增 `PATCH /api/forecast/periods/{pid}`：`ValueError→400`、期次不存在→404、无字段→400；
  改动**事务提交之后**写审计 `_audit_period_op(u, pid, "period_update", "<期次名>｜字段 旧 → 新")`
  （`by` 只从登录态取，绝不接受请求体）。
- `create_period` 把 `ValueError` 转 `HTTPException(400)`。
- RBAC 无需新增权限项：`_PATH_MODULE_MAP` 前缀 `/api/forecast → data`，`method_map` 已含 `PATCH→update`，
  且 `_DEFAULT_PERMS` 全为 legacy list 形态（持 `data` 的角色天然具备 `data:update`）。

### 前端 · `src/pages/Forecast.vue`（+250 / −12）

1. **pick 步「本期归属」**：显示 `<期次名>`；无期次时转告警态（「你现在还没有期次 —— 这次导入不会归到任何期次，
   之后再新建期次它也不会自动跟过去」+「先建一个期次」）；查看往期时追加「你正在查看的是 A，但导入会归到 B」。
   - 🔴 **真机抓到的缺陷（本轮修正）**：归属原取 `curPeriod`，而 `curPeriod` 会被期次下拉 / 往期「查看」改写 ⇒
     ① 查看往期时归属被显示成那一期（错）；②「归属不一致」提示**恒为假**（`curPeriod` 与 `cross.period.id` 是同一个值 ⇒ 死分支）。
     现另立 `curOpenPeriodId`（只由 `GET /periods` 的 `current` 赋值，与后端 `forecast_period_default()` 同源），
     且**无条件赋值**（期次被全删时归零，否则会继续显示一个已不存在的归属）。
2. **done 步条件引导**：仅当后端回执 `results.period_id === 0` 时出现引导块（判据用后端权威值，不用前端预告）；
   归属正常时**什么都不显示**（工具栏已有常显「新建期次」，常态再引导一次是噪音）。
3. **名称解析条件覆盖**：`npTouched` 标记手改字段，`onPeriodNameInput` 只填空字段；
   新增条件出现的「按名称更新日期」按钮（名称含日期时才显示）做**显式**覆盖。
4. **软警告一处实现两处共用** `periodSoftWarn()`：同名 / 窗口重叠。硬规则在后端 `period_validate`，前端不重复实现。
5. **pe-modal**（改名/改日期）：只提交真的变了的字段；仅 open 期次可开。
   - 🔴 **真机抓到的缺陷（本轮修正）**：历史期次列表在子组件里自己 `load()`，改名后未重挂 ⇒
     弹窗关了、库里也改了、表格仍显示旧名称（用户会以为没保存成功）。补 `historyKey++`（与该页 close/delete 同范式）。

### 前端 · `src/pages/ForecastHistory.vue`（+4 / −1）· `src/api/modules.js`（+3）

## 五、需确认事项

1. **新期次表单的预填窗口**：`openNewPeriod()` 预填「下单开始=截止=今天、到货=今天+4」= **1 天窗口**，
   而你实际的节奏是「提前 4 天下单、2 天到货」。1 天窗口偏紧，但这是你的真实业务节奏定义，
   **本轮未擅自改**。要不要改成「今天 ~ 今天+4」？（会改变默认值，不改变任何已有数据）
2. **改期次窗口会改变该期的达成 / 返利归属口径**：弹窗里已写明这句话、每一次改动都写审计。
   是否需要把「改动期次窗口」也纳入某个更强的确认（如二次确认）？
3. **历史期次页的「修改」只在 open 期次可见**（与后端一致：关闭即定稿）。若某期已关闭但名字确实打错，
   目前仍只能走「删除」——而删除会级联清掉该期全部报单/明细/定稿/付款/订单。
   是否需要为「已关闭期次仅改名（不动窗口）」单开一条通道？（属新增能力，需你确认要不要做）
4. **同文件在途改动**：`Forecast.vue` / `modules.js` / `erp_db.py` / `forecast.py` 里另有他人在途改动
   （`loadEditGrid` 的 sources 合并、`.imp-errs` 搬家、`summary` 加 `periodId`、`bulkUpsert` 与
   `importApi.template` 搬家、products DDL `extra_json`、`login_is_locked`、付款通知 sender 展示名），
   **未随本次提交**，但**已随工作区部署在产**（本项目「工作区即部署产物」的常态）。

# 员工账号开通能力核查 —— 诊断报告

**日期**：2026-09-19
**触发问题**：「系统已具备给员工开通小程序账号的能力，但给使用 web 端的员工开通账号的页面是不是没有」
**结论一句话**：**不存在也不需要第二个页面；但你的直觉指向三处真问题** —— 其中一处是后端真 bug（已在生产复现）。

---

## 一、直接回答：账号不分端，所以只有一个入口（且是刻意的）

### 1.1 数据模型里没有「端」

| 事实 | 证据 |
|---|---|
| 登录账号只有一张表：主库 `users` | `core.py` `_init_users()`；`erp_db.staff_account_create()` 写的就是它 |
| 只有一个登录接口，小程序与网页端共用 | `routers/auth.py:114` `SELECT * FROM users WHERE username=? AND is_active=1` |
| 同一接口同时服务 `wx.request` 与浏览器 fetch | `routers/auth.py:138` 注释原文：`v108-fix: Resolve tenant_id BEFORE building JSONResponse (wx.request doesn't auto-handle cookies)` |
| 权限按「角色 → 模块」授予，**没有端维度** | `core.py:375-389` `_DEFAULT_PERMS`：`{role: [module, ...]}` |

⇒ 给员工开账号 = 建一行 `users` + 一行 `user_tenants`。**这件事小程序和网页端是同一件**，所以没有、也不该有「web 端专用开通页」（否则同一个人两套账号 = 工资条发错人那一类漂移源）。

### 1.2 唯一入口是被有意收口的

三处注释互证：

- `Settings.vue:28` —— `权限（仅角色权限矩阵；成员/账号归位「员工档案」）`
- `EmployeeArchive.vue:61` —— `开账号已整合进「编辑员工」弹窗`
- `EmployeeArchive.vue:305` —— `小程序账号（整合进"编辑员工"弹窗）与门店`

⇒ 现状：**入口**＝ 档案管理 › 员工档案 › 编辑 → 弹窗内「小程序账号」区。

### 1.3 但整块语义被写死为「小程序」，共 7 处

| 位置 | 原文 |
|---|---|
| `EmployeeArchive.vue:31` | 表头 `<th>小程序账号</th>` |
| `EmployeeArchive.vue:155` | 区标题 `小程序账号` |
| `EmployeeArchive.vue:160` | 提示 `开通后可用此手机号 + 密码登录预报小程序` |
| `EmployeeArchive.vue:305` | 注释 `小程序账号（整合进"编辑员工"弹窗）` |
| `routers/forecast_submissions.py:515` | docstring `为员工开小程序账号` |
| `erp_db.py:16649` | docstring `为员工开小程序账号（users 表）` |
| `api/modules.js:338` | 注释 `小程序员工账号与门店（老板配置）` |

**而角色下拉里其实已经备好了网页端角色**（`EmployeeArchive.vue:306-314`）：会计（账务/报表/营销）、老板（几乎全开）、管理员（全开）。

⇒ 结论：**能力齐、入口在，只是对「网页端员工」不可发现**。一个老板在界面上找不到任何线索，得出"没有这个页面"完全合理。这是 UI 语义缺陷，不是缺功能。

## 二、核查中发现三处真问题

### 🔴 缺口 1（P0，真 bug，已在生产复现）：`employee_account_map()` 只返回 1 个员工

`erp_db.py:6022-6054`：

```python
	out = {}
	for r in rows:
		out.setdefault(int(r["emp_id"]), dict(r))
		return out          # ← 缩进 2 个 tab，在 for 循环体内
```

`return out` 与 `out.setdefault(...)` **同级（均为 2 个 tab，已用 Python 逐行打印 `repr` 核实）**⇒ 第一次迭代即返回，函数最多只产出 **1 个员工**的账号映射。

**生产只读实证**（2026-09-19，`/opt/hergent-erp`）：

```
主库 users：6 行
  id=1 admin         role=admin      active=1  employee_id=1
  id=2 boss          role=boss       active=1  employee_id=7
  id=4 demo_boss     ...
  id=5 mptest        ...
  id=6 mptestsp      role=supervisor ...
  id=7 18671058882   role=admin      active=0  ...

tenant_1：租户成员 5 个 · 员工 7 个
employee_account_map() 命中 2 行，实际只返回 1 行：
  uid=1 admin → emp_id=1   ← 唯一返回
  uid=2 boss  → emp_id=7   ← 被 return 截断
```

⇒ **员工 #7「张俊峰」在员工档案里显示「未开通」**，尽管 `boss` 账号正绑着他。

**连带症状是一个死循环（单向门）**：

1. 员工 #7 因 `has_account=False`（`erp_db.py:6261`）⇒ 编辑弹窗显示「**开通账号**」表单，而非账号管理区（`EmployeeArchive.vue:159`）
2. 真去填表提交 ⇒ 被 `staff_account_create` 防重逻辑拦下（`erp_db.py:16671-16675`）：
   > 该员工已有关联账号：boss（启用中）。请在员工档案的账号管理区启用或重置密码，勿重复开通
3. **但那个「账号管理区」正是因为 `has_account=False` 才显示不出来** ⇒ 用户按提示操作却无处可去

这与 `erp_db.py:6256-6260` 注释里此前修过的同族缺陷（`has_account` 写成 `is_active` 导致禁用后单向门）是**同一族的复发形态**。

**影响面（两个调用点）**：

| 调用点 | 后果 |
|---|---|
| `erp_db.py:6244`（员工列表） | 最多只有 1 个员工显示「已开通」，其余全显示「未开通」 |
| `routers/salary_send.py:245`（发工资条） | 只有第 1 个员工能解析出账号 uid，其余员工的**工资条发不出去** |

**为什么此前没被发现**：被租户收口掩盖。`employee_account_map()` 用 `user_tenants` 收口（`erp_db.py:6041`），隔离沙箱租户里只有 1 个成员 ⇒ 只命中 1 行 ⇒ 上一轮真机探针 24/24 全绿也照不出来。

### 🟠 缺口 2（P1）：`supervisor`（主管）角色前后端不一致

| 位置 | 是否有 supervisor |
|---|---|
| 后端 `core.py:388` `_DEFAULT_PERMS` | **有** —— `["dashboard", "data"]` |
| `Settings.vue:512` `ROLE_LABELS` | **有** —— `'主管'` |
| `Settings.vue:516` `ROLE_DESCS` | **有** —— `'审批 + 数据'` |
| `EmployeeArchive.vue:306-314` `ROLE_OPTIONS`（开通账号 + 改角色下拉） | **没有** |
| `EmployeeArchive.vue:521` `ROLE_NAMES`（角色显示名） | **没有** |

两个后果：

1. **开不出主管账号** —— 下拉里选不到，只能退而选 staff/sales，权限就不对（而小程序侧主管是实际在用的角色，提审测试账号 `mptestsp` 就是 supervisor）
2. **已是主管的员工显示裸英文** —— `roleName()` 缺 key 时回落原始值，员工列表角色列会显示 `supervisor` 而不是「主管」

### 🟠 缺口 3（P2）：「只允许登录小程序、不给网页端权限」目前**做不到硬隔离**

这是上一轮需求的隐含前提，需要讲清：

- `auth.py` 登录成功后**没有任何端校验**；`Login.vue:250/258` 拿到 `require_password_change` 处理完就一律 `router.push('/workbench')`
- ⇒ 一个 `staff`（`_DEFAULT_PERMS` = `["data","chat","stock"]`）账号**照样能登录 hergent.cn**，只是侧栏按权限过滤后只剩几个模块

也就是说「业务员只能用小程序」在**权限上成立、在门禁上不成立**。真要硬隔离，需要新增能力（`users` 加端白名单列，或按角色设端约束）。

**另注（P3，提权面）**：`routers/forecast_submissions.py:523` 的 `role` 参数**无白名单校验**（直接透传 `d.get("role","staff")`），`server.py:1000` 的改角色接口同样无校验；而下拉里含 `boss`（几乎全开）/`admin`（全开）。⇒ 任何 admin/boss 可一键造出新的 admin/boss。一人公司下无妨，**作为 B2B SaaS 卖给他人时需收口**。

### 新增回归护栏：`.workbuddy/tools/role-registry-consistency-check.py`

这条缺陷的本质是**静默失败**（`roleName(r) { return ROLE_NAMES[r] || r }` —— 缺映射不报错，
只是把英文原样吐出来），没有断言就一定会再漂。脚本以后端 `core.py::_DEFAULT_PERMS`（AST 解析）
为**唯一权威源**，断言四组：

- A `ROLE_OPTIONS` 值集无缺、无多、无重复
- B `ROLE_NAMES` 键集覆盖全角色；两表值集一致；无「中文名 = 英文角色名」的空映射
- C `.df-role.r-*` 色板覆盖全角色、无重复定义
- D 其它清单（`Settings.vue` / `Forecast.vue` / 小程序 `roles.js`）差异**只告警**，并横向打印
  「同一角色在各页的译名」——名称漂移只有摆在一起才看得见

**判别力自证（断言必须有牙齿）**：造三份「各破坏一处」的副本，用同一脚本跑 ——

| 反例 | 结果 |
|---|---|
| `ROLE_NAMES` 去掉 supervisor | **6/8**，FAIL 项 = 「键覆盖全角色」+「两表值集一致」 |
| `ROLE_OPTIONS` 去掉 supervisor | **6/8**，FAIL 项 = 「值集覆盖全角色」+「两表值集一致」 |
| CSS 去掉 `r-supervisor` | **7/8**，FAIL 项 = 「色板覆盖全角色」 |

好代码 8/8（rc=0）、三份反例分别 rc=1 ⇒ 断言真的能抓住回归。

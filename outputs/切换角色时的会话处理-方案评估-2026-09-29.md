# 切换 AI 角色时的会话处理：自动新建 vs 自动切回历史

> 2026-09-29 · 产品设计评估 · 结论先行
> 前置：`outputs/AI团队角色切换-设计评估-2026-09-29.md`（诊断）＋ v319 已上线的能力边界与切换标记

---

## 一、结论先行

**两种都做得出来，但都不该做成「无提示的自动行为」。**

| | 判断 |
|---|---|
| **A 自动新建会话** | ❌ **不推荐作为默认**。它挡住的恰恰是老板最高频的动作（换个角色把刚聊的事再看一遍），且每次切换都切碎历史（不可逆） |
| **B 自动切回该角色历史会话** | ❌ **更不推荐作为默认**。它比 A 更糟：**静默替换整屏内容**，用户会以为自己点错了；且"上次那段"未必是此刻想接的那段 |
| ✅ **推荐：B 的显式版** | 会话**打角色归属** + 切换**不自动动屏幕** + 在切换标记上给**两个按钮**：「新开对话」/「接着《上次那段》聊」。两者都是**用户点出来的**，系统只提供默认值 |

**一句话判断依据**：切换角色时的用户意图是**真二义的** ——「换个视角看同一件事」与「换个岗位干另一摊活」概率相当，
而这两种意图要的处理方式**恰好相反**。任何自动策略都必然赌错一半；赌错的代价（上下文被切 or 屏幕被换）都是用户当场可感、且**无法自己撤销**的。

---

## 二、判断的地基：我们真实的会话模型（先看事实，再谈取舍）

| 事实 | 含义 |
|---|---|
| 表 `chat_sessions(user_id, session_id, title, messages_json, updated_at)`，`UNIQUE(user_id, session_id)` | 会话按**用户**归属，**与角色无关** |
| **没有 `role_id` 列** | 做 B 需要**加列 + 迁移**；存量行 `role_id` 为空 ⇒ 过滤逻辑必须让它们对所有角色可见，否则用户会看到"会话凭空消失" |
| 后端按用户持久化（换设备可拉回）＋ 前端本地镜像合并 | 会话是**跨端共享**的 ⇒ 任何"隐式指针"（如"该角色上次的会话"）在**多端之间会打架** |
| `saveCurrentSession()` 是**整段覆盖** `messages_json` | 🔴 两端同时聊同一条会话会**互相覆盖**（既有缺陷）。B 会主动把用户**送回旧会话**，从而**放大**这个缺陷 |
| 发消息时后端**无状态**（只透传 messages，不传 Hermes 的 session id） | "会话"目前**纯前端概念** ⇒ 方案 A 的实现成本几乎为 0（清空数组即可） |
| 已有**消息级角色快照** ＋ 切换分隔标记（v319 上线） | 🔴 **关键**：一条会话里多角色混着说话，**已经不会串味**了 —— 每条回复都标了是谁答的。这消掉了"必须用会话隔离来防串味"这个最常见的理由 |

最后一行是本评估里最要紧的事实：**很多人做"每角色独立会话"是为了防止上下文串味，而我们已经用更细的粒度（消息级）解决了它。**

---

## 三、方案 A：切换角色 → 自动创建一个全新会话

### 适用场景
- 角色 = **互不相干的顾问**，你只是想"另起一摊"（例：问完货损，切到会计专门从零开始核对账单）
- 演示/教学：希望每个角色都从干净的开场白开始

### 优点
- **上下文绝对干净**：新角色看不到旧角色的上下文，不存在"被上文带偏"
- 实现成本**极低**（`newChatSession()` 已有，一行调用）
- 会话标题、条数都可预期

### 缺点与潜在问题
| 问题 | 具体表现 |
|---|---|
| 🔴 **挡住最高频动作** | 老板看完"今日建议订货"，想切到会计问一句"那这批货的返利怎么算" —— 自动新开会话把上文**全断了** |
| **历史被切碎**（不可逆的数据代价） | 4 个角色来回切几次，历史列表里全是一两条消息的碎片；`chat_sessions` 行数随切换次数线性增长 |
| **草稿丢失风险** | 正在输入时点切换 ⇒ 输入框内容与附件被清空（必须显式处理，否则是"静默丢用户输入"） |
| **用户以为"聊没了"** | 屏幕突然变空，第一反应是"我刚才那些去哪了" |

---

## 四、方案 B：切换角色 → 自动切换到该角色已有的历史会话

### 适用场景
- 角色 = **常驻岗位**（会计每天上班，接着昨天那摊账继续；客服接着上周那批客诉继续）
- 单个角色的**长期跟踪**场景（每周复盘同一个问题）

### 优点
- **上下文承接**：回到角色 = 回到它的上下文，符合"找同一个人接着聊"的心智
- 会话数**不膨胀**：每个角色一条主线，历史列表干净
- 与"角色是常驻岗位"的产品叙事一致

### 缺点与潜在问题
| 问题 | 具体表现 |
|---|---|
| 🔴 **静默替换整屏** | 用户聊到一半点切换，页面**内容整个换掉**。这比"新开空白"更糟：空白是"我开了个新的"，换内容是"**我的东西被换走了**" |
| 🔴 **"上次那段"未必是想接的那段** | 会计角色可能有 20 段历史，凭什么跳"最后那段"？用户要么被迫接受，要么每次都得手动去历史里找 |
| 🔴 **存量会话会"消失"** | `role_id` 空的历史（今天就全是空的）若被按角色过滤掉，用户视角 = **历史会话丢了**（零报错）。必须定义"空 = 所有角色可见" |
| 🔴 **多端打架** | "上次会话"是**隐式指针**：A 端切了角色，B 端不知道；两端对同一条会话**整段覆盖写** ⇒ 互相吃掉对方的对话 |
| **无法回退** | 用户想"回到我刚才那段"没有一键路径（得翻历史） |
| 实现成本中等 | 加列 + 迁移 + 列表接口带角色 + 每角色记住 currentId + 切换时打开逻辑 + 空值兜底 |

## 五、三维度对比

| 维度 | A 自动新建 | B 自动切回历史 | 显式版（推荐） |
|---|---|---|---|
| **用户体验** | 屏幕变空 ⇒ 像"我丢了对话"；挡住"换视角"这一高频动作 | 屏幕**被换走** ⇒ 像"点错了"；"上次"未必是想要的 | 系统**不抢屏幕**，只给按钮与默认值 ⇒ 用户永远知道发生了什么 |
| **上下文连续性** | 默认**切断**（多数场景下是倒退） | 默认**承接**（但接错的风险由用户承担） | 默认**保持**（同一条会话内多角色可读，靠快照与分隔标记）；想切历史时**一键** |
| **数据一致性** | 会话数膨胀、碎片化；草稿可能丢 | 空 `role_id` 会上演"会话消失"；多端指针不同步 + 整段覆盖写 = 互相吃对话 | 只加一列（空 = 对所有角色可见）；**不引入隐式指针**；覆盖写缺陷不被放大 |
| 实现成本 | 极低（1 行） | 中（后端加列 + 迁移 + 前端指针 + 兜底） | 中（≈B，但少了"自动跳转"的连带问题） |
| 可撤销性 | 能（历史还在） | **难**（用户得自己找回去） | 能（用户没被移动过） |

## 六、推荐方案：显式 + 默认值（用户点出来的，不是系统猜的）

切换角色时的行为：

1. **不自动动屏幕**（保持 v319 的分隔标记，它就是给"我知道换了人"用的）
2. **在分隔标记上给两个按钮**：
   - 「新开对话」= 方案 A（已有，v319 已上线）
   - 「接着《上次那段》聊」= 方案 B，**仅当该角色有历史会话时出现**，按钮上写清**那段是什么**（标题 + 时间），让用户能判断
3. 每个角色**记住它上次用的会话**，但只把这个当作**按钮的目标**，不主动跳
4. 会话**打角色归属**（`chat_sessions.role_id`，新增列）
   - 🔴 **空值 = 所有角色都可见**（存量会话不许"消失"）
   - 归属只用于"接着聊"的默认值与历史列表的分组显示，**不做过滤**

### 为什么默认应该是"不切"（而不是"切"）
- **默认值要选"可撤销代价最小"的那个**：不切 = 用户点一下就能切；切错 = 用户得自己找回去
- 同一条会话里多角色混排**已经可读**（消息级快照 + 分隔标记），所以"不切"**不是妥协**，是当前信息架构下的正解
- 等出现真实困扰（"我老是要在历史里找会计那段"）再考虑把默认值改成"接上次" —— 那时有依据

## 七、若要做，必须先满足的数据一致性要求（否则别做）

1. `chat_sessions` 加 `role_id TEXT DEFAULT ''`；**存量空值对所有角色可见**（不许按角色过滤）
2. **禁止用"上次会话"做自动跳转**；它只能作为**按钮的目标**
3. 多端一致性：打开某会话前先 `loadSessionsFromServer()` 对齐（已有 `toggleHistory` 是这个行为，可直接复用）
4. 🔴 **修掉"整段覆盖写"**：现在是 `saveCurrentSession()` 把整条 `messages_json` 覆写。
   一旦用户被"送回旧会话"，两端同时聊就会互相吃对话。**做 B 之前必须先把它改成"按消息追加/带版本号"**，或至少在并发写时提示冲突。
5. 草稿保护：任何自动动作（包括"新开对话"按钮）前先落盘当前输入，避免静默丢用户输入

---

## 八、现在该不该做

**建议：先不做 B，A 保持为按钮即可。**

依据：
- 当前真实用户只有老板 1 人、单端使用 ⇒ B 的收益（承接上下文）**尚未被验证为痛点**，而它的成本（多端覆盖写缺陷要先修）已经明确
- B 的价值随"角色数 × 使用时长"增长；角色还没配能力（`skills/data_scope/guard` 全空）时，角色之间的**实质差异**还很小 ⇒ 现在做隔离，隔离的是"几乎没有差异的两段对话"
- **更该先做的**：在「设置 › AI 团队」里给角色**配上能力**（技能包/数据范围/权限档）。角色有了真实差异之后，"要不要各自一段会话"这个问题才会自己浮现答案

**建议的观察判据**（出现任一条就做 B 的显式版）：
- 老板自己在历史列表里**手动找**某个角色的旧会话 ≥ 3 次
- 出现"我想接着跟会计聊昨天那批账"这类**明确点名角色 + 点名上下文**的诉求

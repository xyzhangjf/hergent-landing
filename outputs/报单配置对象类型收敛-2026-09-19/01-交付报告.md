# 报单配置「对象类型」收敛为 门店 / 本人仓（v203）

> 日期：2026-09-19 ｜ 触发：「在报单配置里有门店和客户两个入口，实际上门店和客户是一个意思，只保留门店这个入口吧」

---

## 一、结论

报单配置里那个「门店 / 客户 / 本人仓」三选一，现在是 **「门店 / 本人仓」二选一**。全站相关文案（含员工档案页、导入模板说明）统一成「门店」。

**但真正值得记的是这个发现**：那两个入口**不是"两个功能"，而是指向同一批对象的两个标签**。

```
/api/report-mappings/refs  →  contacts WHERE type IN ('customer','both')
                              ↑ 「门店」和「客户」下拉里是**同一个池子**
```

`counterparty_type` 这个字段从来不是"对象种类的区分"，它只是当年给同一批客户档案打的分类标签。所以合并它们**零语义损失**。

## 三、兼容策略：`customer` 降级为「历史别名」

用户看到的是"少了一个按钮"，但工程上必须回答一个问题：**存量的 `customer` 数据怎么办？**

实测生产三个租户库：

```
tenant_1.db   self_warehouse=1  store=2   customer=0     ← 生产主租户
tenant_10.db  self_warehouse=1  store=0   customer=0
tenant_9.db   （空）
```

⇒ **全租户 `customer` 行为 0**，本轮无需任何数据迁移。但不能因此就把 `customer` 从代码里删掉，因为还有两条真实路径会产生它：

1. 用户手里可能已经存着**旧版导入模板**（说明写着 `store / customer / self_warehouse`）
2. 备份恢复 / 未查到的租户 / 人工写入

于是定下**写端收敛、读端放宽**：

| 面 | 策略 | 理由 |
|---|---|---|
| **写端**（UI + create + update + import） | 只出「门店 / 本人仓」；`customer` 静默归一成 `store`，**不报错** | 旧 Excel 仍可导入，落库统一 |
| **读端**（7 处 `IN ('store','customer')`） | **保持原样，不收紧** | 万一有存量 `customer` 行，收紧会让它**从列表与可见门店范围里静默消失**（v199「读端来源 ≠ 写端作用域」同族缺陷） |

**判据只写一份**：`REPORT_CP_TYPES` + `REPORT_CP_ALIASES` + `normalize_report_cp_type()`，三条写路径共用，不再各自写白名单。

> 🔴 **update 里有个不写就会静默失效的点**：归一后的值必须**回写进 `data`**。因为 `report_mapping_update` 后面有个通用字段循环会遍历 `counterparty_type` 并把原始值写进 SET 子句 —— 不回写就会被它覆盖，净效果「改了等于没改」且**毫无报错**。

## 五、明确边界：这次**没有**动的东西

| 项 | 为什么不动 |
|---|---|
| `/api/report-mappings/refs` 的 contacts 池（`type IN ('customer','both')`） | 那是**客户档案**的对象池，不是本次要收敛的 `counterparty_type`。门店和客户共用它是设计事实，不是缺陷 |
| 「取价渠道」文案里的「客户档案」（`ReportMapping.vue` 3 处） | 渠道取价确实绑在客户档案上，与对象类型无关 —— **改了就错** |
| 读端 7 处 `IN ('store','customer')` | 见第三节：写端收敛 ≠ 读端收紧 |
| `report_mapping_list(counterparty_type=...)` 过滤参数 | 它是读端条件，归一成 `store` 就查不到存量 `customer` 行了（该参数当前无前端调用，保留是按既有 API 契约兼容） |
| 数据库 schema（`CHECK(counterparty_type IN (...))`） | 不改 schema ⇒ 零迁移风险。改 CHECK 要重建表（SQLite 原生不支持），收益为零 |

## 六、一个过程中的坑（值得记住）

生产只读探针首跑报了 2 个 BAD：`映射总数 0`、`员工 7 可见门店 0 家`。

**看起来像"数据被删光了"，实际是我漏了 `set_tenant_context(1)`** —— 租户上下文是 `ContextVar`（默认 `None`），服务进程之外裸调业务函数时不设它，`get_db()` 会落到非租户库。症状与「代码没生效 / 数据被删光」**一模一样**。

修法：直调业务函数前第一件事就是设租户。已写进脚本注释与记忆。

## 1. 为什么要重做：三条代码级实证

### 1.1 上线以来没人用它

- 页面访问 **39 次**、确认 **0 次**（`audit_logs` 里 `action='对账确认'` / `'客户对账确认'` 合计 0 条）
- 同一页面上唯一活着的功能是「催收跟进」：**514 次真实动作**

**判据：一个页面 39 次访问 0 次确认，不是「入口不明显」，是「走完流程没有回报」。**

### 1.2 同一屏上两个「系统应收」差了 17.7 万

不是显示 bug，是**取了两个不同口径**。代码级解释（`server/routers/reconciliation.py`）：

| 位置 | 算法 | 语义 |
|---|---|---|
| 页面头部「系统应收余额」 | `receivable_list(contact_type='customer')` 聚合 `amount - paid_amount` | **应收台账余额**（跨全部时间） |
| 匹配结果里的「系统算出」 | `system_total = Σ sale_orders.total_amount − Σ payments.amount`（受 `date_from/date_to` 约束） | **区间内发生额净额** |

前者是**余额**、后者是**发生额**，且后者的分母被日期区间切过。**两个数本来就不该相等**，同屏展示却都叫「系统」，必然被读成对不上。

### 1.3 那个「自动匹配」是假算法

`match_statement()`（`reconciliation.py:96-106`）的循环：

```python
for item in items:
    amt = item['amount']
    if abs(unmatched_total - amt) <= tolerance:
        matches.append({**item, 'match': 'matched'});  unmatched_total -= amt
    elif abs(unmatched_total) >= amt:          # ← 恒真分支
        matches.append({**item, 'match': 'matched'});  unmatched_total -= amt
    else:
        matches.append({**item, 'match': 'partial'});  unmatched_total -= amt
```

逐条**无条件**标 `matched`（`abs(unmatched_total) >= amt` 在绝大多数步成立），并把余额逐条减掉 ⇒ `matched_total` ≈ 全部单据之和。**它不是在配对，它是在遍历。**

> **判据：把用户口述的一个数字（`amount: float`）当输入去做对账，在建模层就错了** ——
> 一个标量承载不了「哪几笔、什么时候、什么方向」。这也是 `customer-match` / `customerConfirm`
> 无法承载三类场景格式差异的根因（已写进 `api/modules.js` 的注释）。

## 2. 决定性发现：系统侧没有资金流水（本次生产实测）

**这一条推翻了三步向导的隐含前提** —— 它假设「系统里有账可对」。实测（`/opt/hergent-erp/tenant_1.db`，真实租户）：

| 表 | 行数 | 判定 |
|---|---|---|
| `sale_orders` / `sale_order_items` | 580 / 15,539 | ✅ 业务单据齐 |
| `receivables` | 181 | ✅ 应收台账有 |
| `contacts` | 730 | ✅ 主数据齐 |
| `forecast_submission_items` | 638 | ✅ 预报体系活跃 |
| **`cash_flow`** | **16** | ❌ **几乎没有资金流水** |
| **`journal_entries`** | 248 | ⚠️ 凭证少量 |
| **`bank_transactions` / `bank_flows` / `bank_statements`** | **0 / 0 / 0** | ❌ **表建好了，一行没写过** |
| `accounts` | 4 | ⚠️ 账户登记在（现金/微信/支付宝/银行），但 **`code` 字段全空** |
| `prepayments` | 1 | ❌ 供应商预付款无数据 |

`cash_flow` 那 16 行的账户取值实测是 **`微信`(8 笔) / `现金`(7 笔) / `银行`(1 笔)**，
**不是**舟谱账户号（如 `1003011`、`10021`）；`ref_type` 13 行是空串。

**推论（三条，都直接决定架构）：**

1. **对账的两个操作数都不在系统里** ⇒ 必须允许「两侧都是上传的文件」。
2. **系统侧账户与外部渠道账户之间没有连接键** ⇒ 需要一层账户映射（舟谱账户号 ↔ 银行账号 ↔ 微信商户号）。
3. **`bank_transactions` 等三张表建了从未写入** ⇒ 曾经的银行直连打算从未落地。**本轮不要重启它**
   （银行直连=对抗封闭系统，与用户 strategy 里的既有结论一致）。上传路线是对的。

## 3. 真实对账长什么样（从用户既有资产反推）

`~/Documents/流水对账/` 是用户（与 AI 协作）已经跑通的**手工版**。它是本方案的真源，不是参考。

### 3.1 资产清单

**数据源 9 个**（含 3 种文件格式）：

| 源 | 文件形态 | 说明 |
|---|---|---|
| 农信 / 农行 / 建行 / 邮储个人 / 邮储公户 | `.xlsx` `.xls` **`.pdf`** | 银行，**含 PDF** |
| 工行 | `.xlsx` | 银行 |
| 支付宝 / 微信 | `.xlsx` | 支付渠道；微信有标准导出 `微信支付账单流水文件(起止)_时间戳.xlsx` |
| 舟谱流水 | `.xlsx`「**账户收支明细表**」 | **内部账真源**，按月、**按账户**导出（含"全账户"合并导出） |

**脚本 8 个**：`读取流水.py` / `提取余额.py` / `汇总检查.py` / `应收分析.py` / `应收尾行.py` / `核实应收.py` / `修正预收.py` / `资产负债表生成.py`

**报告 15 份**：
- **收付账户对账 8 份**（= 场景 A）：工行对账报告（4 月 / 5 月 / 4-6 月）、邮储对账报告（4 月 / 4-7 月 / 3 月）、微信对账报告（2 月 / 3 月）
- **业务分析 7 份**：货损报告 ×6、催收看板 ×1

### 3.2 真实产出的形态（照搬，不要另设计）

以 `微信对账报告_2026年3月.md` 为例，产出**恰好是四象限 + 原因 + 建议**：

| 象限 | 组数/笔数 | 金额 | 报告给出的「建议」 |
|---|---|---|---|
| 已匹配收入 | 130 组 | — | — |
| 已匹配支出 | 40 组 | — | — |
| 渠道有·系统无（收入） | 14 笔 | ¥17,991.59 | **补录** |
| 系统有·渠道无（收入） | 9 笔 | ¥11,814.00 | **核查** |
| 渠道有·系统无（支出） | 10 笔 | ¥5,754.80 | **补录** |
| 系统有·渠道无（支出） | 7 笔 | ¥70,065.00 | **核查** |
| **单列（跨账户）** | 6 笔 | ¥78,070.00 | **不计入本账户对账** |

对照两侧总量：微信流水 收入 ¥75,222.66（144 笔）/ 支出 ¥46,956.12（50 笔） vs 舟谱 `1003011` 收入 ¥69,045.07（139 笔）/ 支出 ¥111,266.32（47 笔）。

**从这份报告可以读出 5 条硬规则（全部是确定性规则，不是 AI 判断）：**

1. **匹配单位是「组」，不是「笔」** ——「已匹配收入 130 组」而渠道 144 笔、系统 139 笔。
   报告正文里直接写着「微信40+20」⇒ **一笔系统单据可由多笔渠道流水凑成**（组合匹配）。
2. **跨账户动作要单列排除** ——「提现到银行卡不计入微信账户对账，在银行账户对账中处理」。
   报告把 6 笔提现（¥78,070.00）单独拉出，**不进四象限**。
3. **退款要识别并冲减** —— 报告末尾有「舟谱退款记录（收入为负数）」小节，5 笔 ¥-… 与前面未匹配项一一对应
   （如 `零售 ¥-570.00` ↔ `零售 ¥570.00`）。**不识别退款就会把它当成两笔独立差异。**
4. **差异必须带「原因 + 建议」两列，且落到枚举值**（退款/补录/核查/跨账户），不是自由文本。
5. **必须支持「只有一侧数据」** —— 工行 5 月报告开头就是
   `⚠️ 状态：仅舟谱数据，缺少工行银行流水，无法完成完整对账`，并给出「需要您做以下操作」。
   **缺失一侧是常态，不是异常**，产品必须能输出「半成品报告 + 待办」。

### 3.3 另一类真实产出：余额表校验

`应收款明细表.xlsx`（**39,644 行**，汇总在第 39,644 行）的校验逻辑（`核实应收.py`）：

```
期初余额 + 应收变动 − 已结变动 = 期末余额
```

并额外区分 **正余额（应收）** 与 **负余额（预收/多付）**，脚本里明确提示：

> ⚠️ 差异: ¥X — 注意可能存在**某客户的负余额被正余额抵消**的问题

**这是一个真实账务坑，产品必须显式区分，不能只给一个净额。**

## 5. 目标流程（用户原话的七步拆分）

> 原话：`上传 → AI 认列定键 → 人确认键 → 确定性算子比对 → AI 归因 → 人确认 → 人改数`

| # | 步骤 | **代码**做 | **AI**做 | **人**做 | 验收判据 |
|---|---|---|---|---|---|
| 1 | **上传** | 存文件、返回 `file_id`、读出 sheet 名 / 列名 / 前 N 行 | — | 选文件，并**声明这是什么**（舟谱账户明细 / 银行流水 / 微信账单 / 客户对账表） | 文件可被 `_locate` 定位 |
| 2 | **AI 认列定键** | 出候选列（`COLUMN_PATTERNS` 扩展）+ 每列 `samples` + `validation` | 在候选中判定**对账键**（单号/日期/金额/方向/对方/账户），给 `confidence` 与**理由** | — | 每列一条建议，**不重不漏**（`len(set(index)) == len(suggestions)`） |
| 3 | **人确认键** | 渲染可改表格；把用户的改判写进 `mapping` 并**真的用它执行** | — | 改判并确认，尤其「金额是收/支两列还是单列带符号」「哪列是账户」 | **改判真生效**：被拒绝的列的值在落库结果里 0 命中 |
| 4 | **确定性算子比对** | 按键配对（含容差 / 组合 / 跨期 / 排除规则）→ 四象限 + 金额差 | 🔴 **禁止参与** | — | **同输入同输出、可重放**；同一份文件跑两次字节级一致 |
| 5 | **AI 归因** | 只提供上下文（摘要 / 备注 / 操作人 / 该客户历史 / 该金额附近的其他单） | 对每条差异给**原因 + 建议**，且**必须落到枚举值** | 否决 / 修正 AI 的归因 | 原因 ∈ {退款, 未录, 重复录, 跨账户, 跨期, 手续费, 金额不符, 待核查}；建议 ∈ {补录, 冲销, 核查, 忽略} |
| 6 | **人确认** | 写快照 + 锁定期次账户 + **解除下游阻塞** | — | 确认 | 🔴 **确认必须产生后果**（见 §5.1） |
| 7 | **人改数** | 只在授权下写；过写入口门禁；写前留旧值 | 可起草（人工逐条确认后才落） | 点「补录 / 冲销」 | 每条写操作有 `audit_log` + 可回滚 |

### 5.1 🔴 第 6 步是上一版失败的直接原因

上一版的 `confirm` 只做了这一件事：

```python
db.audit_log(user_name="系统", action="对账确认", module="finance",
             ref_id=str(supplier_id), detail=f"…")
return {"success": True, "message": f"已确认与{supplier_name}的对账"}
```

**不改任何状态、不推进任何流程、不解除任何阻塞。** 用户点完确认，世界没有任何变化 ——
所以 39 次访问 0 次确认是**理性行为**，不是产品没曝光。

**重做后的确认必须锚定一个下游后果（建议选①或②）：**

| 方案 | 后果 | 代价 |
|---|---|---|
| ① **结账门禁** | 该期间该账户「未对平」时，禁止结账 / 禁止出该期损益 | 需接入结账流程（已有 `accounting_periods` 表，目前 0 行） |
| ② **催收联动** | 确认后，差异清单里「客户少还/多还」自动进入催收队列（`/api/collections`） | 需定义映射；但 514 次真实调用说明催收是活跃场景，**性价比最高** |

**建议：先做②**（贴着现有活跃功能，改动小、回报可感知），①留到结账模块正式上线时再挂。

## 6. 缺口与工作项

### G1｜比对算子撑不住真实数据（**最大的一块**）

现有 `_reconcile_files` 的实际能力边界（读代码得出的硬事实）：

```python
k = str(r.get(key, "")).strip()          # 只支持「同名列、精确相等」的键
if k not in ib: only_a.extend(rs)
else:
    va = sum(to_float(x.get(amount)) or 0 for x in rs)     # 只支持「单金额列求和」
    vb = sum(to_float(x.get(amount)) or 0 for x in ib[k])
    if amount and abs(va - vb) > 0.001:                    # 固定容差
        mismatch.append(...)
```

**需要补的 7 项能力（按真实报告反推，每项都有出处）：**

| # | 能力 | 真实出处 | 归属 |
|---|---|---|---|
| 1 | **组合匹配**（1 系统单 ↔ N 渠道笔） | 微信报告「微信40+20」= ¥60 | 确定性（子集和，设上限） |
| 2 | **日期容差** | 银行 T+1/T+2 到账；报告按日期分节 | 确定性（默认 ±3 天，可配） |
| 3 | **方向规范化** | `excel_recognizer` 已有 `amount_in` / `amount_out` 分离 | 确定性（认列层已支持，算子层未用） |
| 4 | **手续费拆分** | 微信提现 `¥50,050 + ¥50 服务费` | 确定性（`fee` 字段已在 `COLUMN_PATTERNS` 里） |
| 5 | **多账户拆分** | 舟谱「账户收支明细表**4月全账户**.xlsx」 | 确定性（先按账户列分组，再逐账户对） |
| 6 | **排除规则**（跨账户动作不计入） | 「提现到银行卡不计入微信账户对账」 | 确定性（规则表，可配） |
| 7 | **退款识别与冲减** | 舟谱退款单 `¥-570.00` | 确定性（同键负额优先配对） |

**唯一需要「模糊」的那一项**：对方户名 / 摘要的相似度 —— **但只能用来推荐候选给第 5 步 AI，
绝不能自动判平**。（`counterparty` / `description` 字段已在 `COLUMN_PATTERNS` 里。）

**产出形态应是新模块 `hergent-erp/server/recon_engine.py`**，纯函数、无 IO、可单测：
- 输入：两侧 `rows`（已认列）+ `ReconSpec`（键列 / 金额列 / 方向列 / 容差 / 组合上限 / 排除规则 / 账户）
- 输出：`{matched_groups, only_internal, only_external, mismatch, excluded}` + 每条的 `group` 明细
- **`spreadsheet_reconcile_files` 与前端都改为调它**，删掉 MCP server 里那份自带实现（消除双份漂移源）

### G2｜账户主数据没有连接键

`accounts.code` 实测全空。需要映射层：

```
account_channel_map(id, account_id → accounts.id, channel ∈ {舟谱,工行,农信,…,微信,支付宝},
                    external_id（舟谱账户号 1003011 / 银行账号 / 商户号）, alias, is_active)
```

**这一层不做，第 5 步的 AI 就没有「这个 1003011 是哪个账户」的上下文**，归因只能瞎猜。

### G3｜MCP server 不在版本控制 → 见 §4.1

### G4｜缺「只有一侧数据」的半成品状态

工行 5 月报告证明这是常态。批次状态需为：
`draft → one_sided（缺一侧）→ compared → attributed → confirmed`
且 `one_sided` 必须能输出「需要您做以下操作」式的**待办**（照搬报告里的三条操作指引写法）。

### G5｜写入口（第 7 步）与「订单 CRUD 冻结」的边界

**必须写清的红线**：本轮新增的写操作**只碰资金流水与对账状态**，**不碰订单**。

| 允许新增的写 | 表 | 与 CRUD 冻结的关系 |
|---|---|---|
| 补录一笔渠道流水 | 新的对账明细表（**不写进 `cash_flow`**） | 无关订单 ✅ |
| 标记差异「已核查 / 已忽略」 | 对账差异表 | 无关订单 ✅ |
| 确认锁定批次 | 对账批次表 + `audit_log` | 无关订单 ✅ |
| 🔴 回写舟谱/ERP 原始账 | — | **禁止**。差异只能「记录 + 提示人工去原系统改」 |

> **判据：对账模块的职责是「发现问题」，不是「修改源头」。** 一旦它开始回写客户 ERP 的凭证，
> 就从分析层越界成了交易层 —— 与「不造 ERP、订单 CRUD 冻结」的既定战略直接冲突。

### G6｜`excel_recognizer` 目前只认 CSV 文本，不认 xlsx 二进制

`detect_format(text)` 入参是 **text**（`_split_line` 手写 CSV/TSV 切分）。
对账场景的文件**几乎全是 `.xlsx` / `.xls`，且银行还有 `.pdf`**。

- `.xlsx/.xls` ⇒ 复用 `spreadsheet_query._load_sheets`（openpyxl，已验证）
- `.pdf`（农信/农行/邮储公户）⇒ **建议 P2 再做，且明确告知用户「PDF 请先另存为 Excel」**；
  不要在本轮引入 PDF 解析依赖

## 7. 三场景分置入口

### 7.1 场景定义（两族 + 一个子视图）

| 场景 | 一侧 | 另一侧 | 真实频次 | 系统侧可用度 |
|---|---|---|---|---|
| **A｜收付账户对账** | 舟谱「账户收支明细表」（内部账） | 银行 / 微信 / 支付宝流水（渠道实收实付） | **月末必做**（报告覆盖 2/3/4/5/6/7 月） | 🔴 零（`cash_flow` 16 行） |
| **B｜下游客户对账** | 舟谱「应收款明细表」（39,644 行） | 客户认账（回签对账单 / 口述） | 月或季（与催收联动） | 🟡 有台账（`receivables` 181 + `sale_orders` 580） |
| **C｜上游厂家预付款** | 舟谱预付款单 | 银行付款流水 | 按付款批次 | 🔴 零（`prepayments` 1 行） |

**C 不是独立场景，是 A 的一个子视图**（同一份银行流水，按「对方户名=厂家」筛出来的那一段）。
**建议：C 并入 A，不单开入口** —— 界面上一句「只看付给厂家的钱」即可。

### 7.2 🔴 建议顺序：先 A，再 B（与上轮口头建议相反）

上轮建议「先下游客户、厂家次之、银行最后」。**看完真实报告后我建议反过来，先 A（含银行）**，三条理由：

1. **需求已被实证。** 15 份报告里 A 类占 **8 份**（工行 ×3、邮储 ×3、微信 ×2），
   且是**跨 2 月—7 月反复做**的月度动作；B 类**零份**独立报告（只有 1 份催收看板）。
   **A 是真正的高频痛点。**
2. **B 场景在 Hergent 里做不出有意义的结论。** 系统侧 `sale_orders` 只有 580 单，
   而舟谱真实应收明细是 **39,644 行** —— 差两个数量级。用 580 单去对客户的账，
   对出来的「差异」绝大部分会是「系统里没录」，**结论没有价值**。
   要做 B，前置是「39,644 行应收明细怎么进系统」，那是另一个更大的工程，
   且会撞上「应收录入」的写入口边界。
3. **A 是流程最严苛的测试床。** A 同时需要：组合匹配、日期容差、方向规范化、手续费、
   多账户拆分、排除规则、退款识别 —— **七项全用上**。B 只需要「单键 + 单金额」。
   **先在 B 上做，会把 `recon_engine` 的接口做窄，回头做 A 时必须推翻重来。**

> **这是本方案最需要用户拍板的一条（§11-1）。** 若用户坚持先 B，
> 方案仍可行，但需要额外接受「B 首版结论仅供参考」这一前提。

### 7.3 入口落点

**不新增侧栏项**。两个场景并入现有页面结构：

```
侧栏「催收跟进」（现有，13 项位置不变）
   └─ 页面右上「发起对账」→ 选场景 → 进入对账工作台
侧栏新增？ ❌ 不加。理由：工具栏/侧栏不新增是本项目既定偏好；
              且对账是「低频重操作」，适合从催收页与工作台待办进入。
工作台「今日待办」→ 增加「本期有 N 笔未对平」待办项（照 Workbench.vue 现有 todoItems 机制）
```

## 8. 数据模型（建议）

```sql
-- 对账批次：一次「某账户某期间」的对账
recon_batches(id, scene ∈ {account, customer, supplier_view}, account_id,
              period_from, period_to, status ∈ {draft,one_sided,compared,attributed,confirmed},
              internal_source_id, external_source_id, rule_json, created_by, confirmed_by, confirmed_at)

-- 数据源两侧（各存 file_id + 认列映射 + 原始行列数）
recon_sources(id, batch_id, side ∈ {internal, external}, file_id, sheet, role_hint,
              mapping_json, header_row, row_count, loaded_at)

-- 配对结果（四象限 + 排除项）
recon_pairs(id, batch_id, group_no, kind ∈ {matched, only_internal, only_external, mismatch, excluded},
            key, internal_amount, external_amount, diff,
            internal_rows_json, external_rows_json, date_span, direction ∈ {in,out})

-- 归因（AI 产出 + 人工修正，两份都留）
recon_attributions(id, pair_id, ai_reason, ai_suggestion, ai_raw, human_reason, human_suggestion,
                   decided_by, decided_at)

-- 账户映射（G2）
account_channel_map(id, account_id, channel, external_id, alias, is_active)
```

**三条设计约束：**
1. `internal_rows_json` / `external_rows_json` 存**原始行快照** —— 差异条目必须能回溯到源文件的具体行，
   否则用户无法「去源头改」（这是第 7 步的前置）。
2. `ai_reason` 与 `human_reason` **分列存**，不覆盖 —— AI 归因的准确率是重要的产品指标，
   被覆盖就永远测不出来。
3. `confirmed` 状态要存**锁定哈希**（两侧源数据的指纹），源数据变了则自动回退到 `compared`。

## 10. 红线与风险

| # | 红线 | 说明 |
|---|---|---|
| R1 | **AI 不得参与比对判定** | 「算」归代码、「判」归人。AI 只做归因（第 5 步）与起草（第 7 步），且必须落枚举值 |
| R2 | **不回写客户 ERP / 舟谱原始账** | 对账模块只发现问题、记录结论；改数由人去原系统做（G5） |
| R3 | **不做多租户下的跨租户对账** | 对账始终在单租户内；文件目录已按 uid 隔离 |
| R4 | **脱敏** | 对账报告含客户名与实际金额 ⇒ 对外材料一律用**演示租户**，不得截图真实报告（既有脱敏红线） |
| R5 | **不引入银行直连** | 三张银行表建了从未写入，说明这条路没走通；继续走上传 |
| R6 | **P0 未过不提 B 场景** | 否则会把 `recon_engine` 接口做窄（§7.2-3） |

**已知风险：**
- **组合匹配的复杂度**：子集和是 NP-hard。**必须设组合上限**（建议 ≤4 笔、金额倒序剪枝），
  超出则只给「候选」不自动判平，交第 5 步标注。**没有上限的组合匹配会在某份大文件上卡死。**
- **PDF 银行流水**：6 家银行里 3 家给过 PDF。本轮**明确不做**，走「请先另存为 Excel」。
- **`_load_sheets` 的性能**：舟谱「全账户」导出行数可能上万，`_run_query` 是全量内存计算。
  需在对账入口加行数上限与超时（建议 5 万行 / 30 秒），超限提示分月上传。

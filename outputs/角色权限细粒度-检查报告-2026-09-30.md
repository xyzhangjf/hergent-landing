# 角色权限细粒度改造 · 检查报告

> 对标：舟谱云管家「角色列表页 →（点击角色）→ 角色权限配置页」两步式 + 每功能项 4 动作列（查看 / 编辑 / 导出 / 导入）
> 检查日期：2026-09-30　范围：hergent-erp（后端）+ hergent-cn-v2（前端）
> 结论口径：**只写实测可证的事实**，每条附文件 + 行号

---

## 一、结论先行（三句话）

1. **你要的「角色列表 → 详情配置页」两步式，前端完全没有** —— 当前是一张「角色当列、权限项当行」的大矩阵，全角色横向平铺，没有角色详情页。
2. **「更细粒度」的后端地基其实已经全部建好了，一行后端代码都不用改** —— 存储、判定、中间件、专用读写端点**四层全通**；缺的只是**前端从没接上去**，以及**出厂默认值把这一维写成了"全放行"**。
3. **但有一个必须先解决的硬阻塞**：后端存在**两个写端点写同一张表的同一列**，一个收 `list`、一个收 `dict`。直接上前端会让它们**互相覆盖且不报错** —— 这是"静默失效"家族的新变种，必须先合并。

## 三、后端：地基已建成（实测证据）

### 3.1 action 轴的四层链路，全部已通

| 层 | 位置 | 实测 |
|---|---|---|
| ① HTTP 方法 → action | `server.py:737-740` | `GET→read` / `POST→create` / `PUT,PATCH→update` / `DELETE→delete` |
| ② 中间件按 action 裁决 | `server.py:835` | `_check_perm(user, module, action, tenant_id=_perm_tid)` |
| ③ 判定支持 `{模块:[动作]}` | `core.py:1334-1351` | `_perm_granted`：dict 时判 `"*" in mod_perms or action in mod_perms` |
| ④ 存储无形态限制 | `erp_db.py:2567-2578` | `json.dumps(permissions, ensure_ascii=False)` —— **列是 JSON 文本，天然支持 dict** |

### 3.2 还专门为 CRUD 级权限准备了读写端点（**前端从未调用，是孤儿端点**）

| 端点 | 位置 | 作用 |
|---|---|---|
| `GET /api/role-permissions/detail` | `server.py:1344-1366` | 返回 `{角色: {模块: {read/create/update/delete: bool}}}` 完整矩阵 |
| `POST /api/role-permissions/detail` | `server.py:1368-1383` | 保存 `{模块: [动作]}` dict 形态 |

已核实：**前端 `src/` 全仓对 `role-permissions` 的调用点里，没有任何一处打 `/detail`**（`Settings.vue` 用的是 `GET/POST /api/role-permissions`，list 形态）。

### 3.3 🔴 但 action 轴在生产上是**死的** —— 实测数据

只读查生产两个租户库的 `role_permissions`：

| 库 | 行数 | 形态 |
|---|---|---|
| `tenant_1.db` | 9 | **全部 `list`** |
| `tenant_10.db` | 7 | **全部 `list`** |

样例：`accountant = ["dashboard","data","sales","accounts","reports","stock","messages"]`

**推论（这是全篇最要紧的一条）**：`_perm_granted` 遇到 `list` 直接 `return module in perms`，**`action` 参数从头到尾没被读过一次**。
⇒ 生产上**任何角色调任何模块的任何方法都放行**（只要该模块在名单里）。`DELETE` 和 `GET` 待遇完全相同。
**这就是你感觉"缺少细粒度配置"的机械原因。** 出厂默认 `_DEFAULT_PERMS`（`core.py:522`）也**全是 list 形态**（`admin` 是 `["*"]`）。

## 四、前端：三条轴的真实分布

| 轴 | 单一权威源 | 作用面 | 消费点 |
|---|---|---|---|
| `roles`（角色门槛） | `constants/pages.js:164-300` `PAGE_RULES`（23 条） | 页面入口 + 路由守卫 | `canSee` **29 处**；守卫 `pageRoleAllowed`（`router/index.js:180-214`） |
| `module`（模块） | 后端 `_PATH_MODULE_MAP` + `_DEFAULT_PERMS` | 侧栏/命令面板显隐 | `store.canModule`（`store/index.js:137`） |
| `customRoles`（让位） | 后端 `custom_roles()` | 角色门槛是否让位 | 随 `canSee` 一起传 |

**🔴 没有第四条轴（action）** —— `canModule(m)` 只判模块名，签名里根本没有动作参数。

### 4.1 页内操作层几乎无门禁（实测盘点）

- `canModule` 在**业务页写按钮上 0 处使用**。
- 唯一做了角色级判据的页面是 `Forecast.vue`（`canEditRules` @4904、`canEditClosedPeriod` @4032）。
- 其余 8 个页面（`Rebate` / `DataFill` / `CustomerArchive` / `EmployeeArchive` / `LossAccounting` / `LossWorkflow` / `PayrollWorkflow` / `Settings`）的写按钮**一律无权限门禁**，只有 `:disabled` 表"异步忙/期间关闭"，靠路由守卫 + 后端 403 兜底。
- 两处 `editMode`（`Forecast.vue:2761`、`LossAccounting.vue:534`）都是**期间状态锁**，与权限无关。

⇒ 你要的"UI 与实际权限强绑定"，**当前只绑定了"能不能进这一页"，没绑定"进去能做什么"**。

## 五、🔴 三处硬约束（决定方案可行性，必须如实说）

### 约束 A：action 是 **HTTP 语义**，不是业务语义 ⇒ 舟谱的「导出/导入」**映射不上去**

因为 action 由 HTTP 方法推导，而：
- **「导出」**常常是 `GET`（会被判成 `read`）或 `POST`（会被判成 `create`）；
- **「导入」**是 `POST`（与"新建"同判成 `create`）。

⇒ 「导出 / 导入 / 新建」三者**挤在同一个 action 里，无法区分**。
**要真的做出舟谱那四列，必须新增一层显式登记**：`(路径前缀, 能力位) → 业务动作`。本仓已有同构先例可抄 —— `core.py:1428 _PLAN_CAPS`（套餐能力位，含 `export` / `bulk_export` / `api`）。

### 约束 B：POST 型"只读"接口会被误伤 —— 实测 **17 个**

全仓 `/api` 端点 **373 个**（GET 176 / POST 157 / PUT 26 / DELETE 14）。其中 POST 但名字是"读/算/导出"的至少 17 个，例如：

```
/api/ai-query                    /api/price-change/preview
/api/salary-batch-calculate      /api/report-mappings/import
/api/report-mappings             /api/order-templates
/api/display-checks              /api/message-templates
/api/price-lists/{lid}/clone     /api/pricing/invalidate-cache
```

⇒ 一旦给某角色取消 `create`，这些**查询类**接口会立刻 403（页面表现为"某个按钮点了没反应/数据空了"）。**上手前必须逐个核定归类**，否则必踩。

### 约束 C：🔴 **两个写端点写同一张表的同一列**（最危险的一条）

| 端点 | 收的形态 | 落库 |
|---|---|---|
| `POST /api/role-permissions`（`server.py:1188`） | `permissions: list` | `db.save_role_permissions(role_name, permissions)` |
| `POST /api/role-permissions/detail`（`server.py:1368`） | `permissions: dict` | `db.save_role_permissions(role_name, permissions)` |

两者写的是 `role_permissions` 同一行的同一个 `permissions` 列（`erp_db.py:2567`）。

**后果**：若前端一部分界面用 list 端点、另一部分用 dict 端点，**后保存的会把先保存的整体覆盖**，且**不报任何错**。
⇒ 前端**绝不允许两个端点混用**。要么全走 `/detail`（dict），要么先把旧端点改成"形态透传"。

## 七、三个方案（按工作量 / 风险递增）

### 方案 A ——「两步式 + 真动作轴」**（推荐先做）**
- 做 ① 角色列表页 → ② 详情配置页；动作列用 **Hergent 真实的 4 个 action**（查看 / 新增 / 修改 / 删除）
- 后端只做 B1 + B2 + B3 + B5 + B6（**不新增能力位**）
- **「不影响已有权限」的保证**：迁移把现有 list 转成**四动作全开的等价 dict** ⇒ 逐条行为不变，**零回退**
- 用户拿到：逐角色、逐模块、逐动作的自主配置权 ✅
- 工作量：前端 2 个新页 + 后端 4 处；**风险低**

### 方案 B ——「A + 舟谱式导出/导入列」（完全对标截图）
- 在 A 之上做 B4：新增 `_CAPABILITY_MAP`（路径 → 导出/导入能力位）
- 动作列变成 **查看 / 编辑 / 导出 / 导入**（与舟谱一字不差）
- 代价：需要**逐个核定**哪些接口算"导出"、哪些算"导入"（373 个端点里人工过一遍），且**导出在 Hergent 多为前端生成 CSV**（`utils/csv.js`）⇒ "导出权限"在当前形态下只是**界面门禁**，不是硬边界（这一点 `core.py:1423` 已诚实记录）
- 工作量：+1 张映射表 + 人工核定；**风险中**

### 方案 C ——「页内按钮与权限真强绑定」
- 做 F5 + F6 + F7：建 `canDo()`，给 8 个页面的写按钮加门禁，"可见即可用、不可见即没有"
- **彻底消灭**项目里反复出现的「假入口」（页面进得去、按钮点了 403）
- 风险**最高**：判据写错会**把老板自己锁住**（Settings 页已靠 `lock: true` 豁免自救，其它页没有这层保护），且需要逐页回归
- 工作量：8+ 页面 + 全量回归；**建议在 A/B 稳定运行一段时间后再做**

## 八、必须提醒的两点

1. **不建议照抄舟谱的"功能项"粒度**。舟谱页面里的叶子（"商品档案 / 口味属性 / 单位档案 / 品牌档案…"）在 Hergent 里**没有对应物** —— 本仓是「路径前缀 → 模块」的扁平分法，没有"叶子功能项"这一层。硬造需要重建一层 `_FEATURE_MAP`，工作量大且与现有护栏全部冲突。**按 Hergent 的真实粒度做模块 × 动作，比假装有叶子更诚实。**
2. **`admin` 的 `["*"]` 必须在 dict 形态下继续通配**。`_perm_granted` 判的是 `"*" in perms`（**键级**），dict 形态下 `{"*": [...]}` 同样命中 —— 逻辑上成立，但**必须有测试锁住**，否则管理员会被自己锁死。

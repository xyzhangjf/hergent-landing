## 一、登录范围隔离（v307）

### 1.1 落点：**只能写在登录端点内部**

`/api/auth` 整段在 `server._PUBLIC_PATHS`，RBAC 中间件对登录请求**根本不执行**（登录时还不知道你是谁）⇒ 写在中间件、装饰器、路由守卫里一律无效。判定写入 `routers/auth.py::login()` 密码校验之后、发令牌之前。

### 1.2 三条硬约束（都写进代码注释）

| 约束 | 内容 | 不这么做的后果 |
|---|---|---|
| **缺头视为小程序**（fail-open） | 请求头 `X-Client: mini\|web`；缺头/未知 ⇒ 判小程序 | 存量小程序不带这个头且**已备案上线**，设成"必带头"会**当场切断所有存量小程序登录** |
| **不计失败尝试** | 端被拒**不**调 `_record_login_attempt` | 那不是密码错误，记进去会累加「5 次锁 30 分钟」，把账号主人**误锁在门外** |
| **可回滚** | `LOGIN_SCOPE_ENFORCE=0` ⇒ 整段跳过 | 故障时无需改代码重发版 |

另：这是**产品约束（防误登 / 防串岗），不是安全边界** —— 客户端可伪造该头；真正的边界仍是后端模块权限 `core._check_perm`。

### 1.3 判据收敛为一份（都在 `core.py`）

`normalize_login_scope`（取值收敛）· `login_scope_of`（兼容缺列的老行对象）· `client_of_request`（端识别）· `login_scope_allows`（裁决）· `login_scope_deny_detail`（面向业务员的中文文案）。

新增 `PUT /api/users/{uid}/login-scope`，并**禁止改自己的** —— 把自己设成「仅小程序」＝ 当场失去网页端入口，而唯一能改回来的人正是自己。

### 1.4 实测（17/17）

```
— 取值收敛 —       空值→both  拼错 app→both  大写 MINI→mini  web→web
— 端识别 —         无头→mini  X-Client: web→web  mini→mini  未知 app→mini
— 裁决 —           both放行两端  mini放行小程序/拒绝网页端  web放行网页端/拒绝小程序
— 缺列容错 —       老行对象缺该列→both（fail-open，不会把人锁在门外）
```

### 1.5 生产验证（部署后，只读）

```
users 列：… password_changed, employee_id, roles, login_scope, external_ref   ← 两列已补
存量账号按登录范围分组：[(10, 'both')]     账号总数：10                        ← 全部 both
```

⇒ **零破坏性收紧**：没有任何一个在用账号被收掉能力。登录实测两端均 200。

## 二、分销商角色与外部客户账号（v308）

### 2.1 🔴 一个关键决策：角色键用 `distributor`，**不用** `dealer`

`dealer` 是**演示期遗留的视图令牌**（`constants/roles.js::ROLE_VIEW_TOKEN_NAMES` 里 `dealer: '经销商'`），历史 localStorage / 老配置里存着它。若复用为真实角色键，`isCanonicalRole('dealer')` 会**由假变真**，把那些没人复核过的历史值**就地召回成真实权限**。

⇒ 中文名仍是「分销商」，只换内部键名，零用户可见影响。

### 2.2 外部账号：绕过「必须有员工档案」这道硬校验

原 `staff_account_create` 强制要求一个**真实存在的员工** ⇒ 外部客户没有员工档案 ⇒ **走不通系统里唯一的开账号链路**。这才是「分销商没有权限入口」的技术根因。

新增 `external_ref` 参数（非空 = 外部客户）：跳过员工校验、`employee_id` 保持 0、**跳过**「同一员工重复开账号」防重（否则所有外部账号会互判重复）。

🔴 **角色闸门**：外部账号**只允许 `distributor`**。外部账号的持有人不在本企业人事体系内，给他 `admin`/`boss` 等于把后台钥匙发给客户，且没有任何人事流程能回收。

🔴 **只加一列、不加 `is_external` 标记列** —— 两列表达同一件事是漂移源（历史上 `employee_code` 与 `employee_id` 双写就是这么来的）。

### 2.3 入口位置：员工档案的「外部客户账号」分区（**不是**客户档案）

三条理由：① 登录账号在**主库**、客户业务数据在**租户库**，放客户档案要跨库写两处；② 本系统**没有客户主数据表**（`CustomerArchive.vue` 是数据源同步页），为放一个入口先造整套主数据成本是前者的数倍；③ 放员工档案可复用现成的密码策略、角色白名单、自助改密通道。

### 2.4 实测（影子库 5/5）

```
用例1 外部客户账号（无员工档案）      → {'success': True, 'user_id': 2}        ✅
用例2 外部账号 + 角色 admin           → '外部客户账号只能使用「分销商」角色'      ✅ 闸门生效
用例3 第二个外部账号                  → {'success': True, 'user_id': 3}        ✅ 防重未互判
用例4 内部员工账号无员工档案          → '请先保存员工档案，再为其开通登录账号'    ✅ 存量行为不变
用例5 账号名重复                      → '账号已存在: ext001'                    ✅
落库：role=distributor, login_scope=mini, external_ref=永辉超市(分销), employee_id=0
登录判据：范围=mini | 小程序 True | 网页端 False                                ✅
```

## 三、小程序权限闸与网页端同口径

| 改前 | 改后 |
|---|---|
| 只看 `data` 的**单个布尔** `canReport` | 按后端模块集判：`canUse('report'\|'stock'\|'chat'\|'cron'\|'bid'\|'summary')`，与网页端 `canModule` **同口径** |
| 客户在网页端改权限，小程序**不会跟着变** | 回到前台时按需刷新（缓存未过期不发请求） |

🔴 两处语义必须分清（写错就是静默失效）：
- `known:false`（权限还没拉到）⇒ **fail-open**（`canUse` 返回 true）。一次接口抖动不能把能干活的人挡在门外。
- 已知 + 空数组 ⇒ **真的没有权限**。混成一个假值 ⇒ 客户清空某角色权限后，小程序反把人放进填报页到处 403，看着像「改了权限没生效」。

实测 9/9（含「分销商能报单、不能看库存」「会计不能报单」「未登记能力点收紧」）。

**第 ① 项在小程序侧无需改代码**：登录失败文案已天然透传后端 `detail`（`utils/api.js:99` 取 `body.detail`）⇒ 网页端专属账号在小程序登录会直接看到「该账号只能在电脑网页端登录」。

## 三、统一入口 `write_stock_movement()`

新文件：`db/queries/stock_movement.py`（阶段 1 开发副本，尚未落地后端仓）

```python
def write_stock_movement(db, *, product_id, warehouse_id, delta_qty=0,
                         set_qty=None, cost_price=None, row_id=None,
                         batch_no='', expiry_date='', production_date='',
                         change_type='adjust', ref_type='', ref_id=0,
                         allow_negative=False, atomic_guard=True,
                         force_new=False):
```

### 三写顺序（同一 SAVEPOINT 内）

1. **定位台账行**：`row_id` 指定 → 或按 `商品+仓+批次` 定位 → 都没有就新建（`force_new=True` 强制新建，保住 `batch_in` 无批次号时「每次新开一行」的原语义）
2. **改台账**：`quantity` / `cost_price` / `stock_value` 一起改；扣减时给 `UPDATE` 追加 `AND quantity>=?` 并发守卫
3. **追加流水**：`inventory_logs` 只 INSERT，永不 UPDATE/DELETE，含 `stock_value_before/after/difference`
4. **滚动余额**：`inventory_balance` 按台账**实时 SUM 重算**（不靠增量累加，避免漂移），只写 `actual_qty` / `stock_value` / `valuation_rate` 三列

### 三条不能碰的红线

- **不接管事务边界**：不 `commit`、不回滚整个事务、不自建连接 —— 调用方传进来的就是事务连接
- **不覆盖别人的列**：`reserved_qty` 是 `reserve.py` 的地盘、`in_transit_qty` 是采购在途的地盘，一律不动
- **SAVEPOINT 名必须唯一**（`stock_mv_<序号>`）：`fefo_deduct` / `batch_out_fefo` 自己已经开了同名 SAVEPOINT，复用固定名会让 `ROLLBACK TO` 命中外层

### 顺带补齐的只读工具

- `assert_triple_in_sync(db, product_id, warehouse_id)`：四项校验「台账数量 = 流水累加 / 余额行存在 / 余额数量 = 台账 / 余额金额 = 数量×成本」，供对账卡与沙箱调用
- `rebuild_balances(db)`：一次性重建全量余额行（只给运维/回放用，**不在迁移里自动跑**），保留已有 `reserved_qty` / `in_transit_qty`

## 四、修掉的三个真实缺陷

### ① `batch_in` 同批次累加不写流水（最要紧）

原代码：查到同批次 → `UPDATE inventory` 改数量 → **直接 `return`**。台账加了 100 件，
流水一条没有 ⇒ 对账卡第①项「台账数量 = 流水累加」必红。现在走统一入口，流水照写。

### ② `transfer_stock` 重复记账

`inventory_adjust` 已经写了 `transfer_out` + `transfer_in` 两条，`transfer_stock` 又手写
第三条 → 一次调拨三条流水，数量被多算一遍。已删除手写那条。

### ③ `inventory_balance` 是死表

迁移 `0012_inventory_balance.py` 建了表、`reserve.py` 只维护 `reserved_qty`，
`actual_qty` / `stock_value` **从没被任何库存变动写过** —— `reserve.py` 注释里引用的
`stock_ledger._BALANCE_UPSERT` 是个**从未实现的符号**（全树无 `stock_ledger.py`）。
现在每次数量变动都重算该行。

## 五、收敛过程中自己引入并抓到的一个回归

**现象**：收敛后跑演示数据，发货出现「流水记了出库 5 件、台账没扣」——三写脱钩。

**根因**：统一入口扣减分支的 SQL 参数顺序错了。

```python
# 错：WHERE id=? 被绑成扣减量，quantity>=? 被绑成行号
params = [after, new_cp, sv_after]
if guard: params.append(-change)
params.append(inv_id)
```

入库（无守卫）不受影响，只有扣减（有守卫）错位 —— 所以缺陷藏在发货路径里。
已按 SQL 里 `?` 出现顺序改成 `[after, new_cp, sv_after, inv_id]` 再 append 守卫值，
并在代码里留了醒目注释。

> **这条是本轮最值得记的教训**：三写内核本身写对了，参数顺序错了照样「看起来成功」。
> 只有演示数据真跑一遍发货才暴露 —— 静态判据和入库测试都抓不到。

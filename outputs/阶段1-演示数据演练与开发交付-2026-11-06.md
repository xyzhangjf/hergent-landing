## 1. 第 1 条：生产日期由用户自由选择

### 1.1 核查现状（先说实话）

| 位置 | 实测 |
|---|---|
| `PurchaseOrderForm.vue` 批次信息面板 | 生产日期 `type="date"`，**无 `required`**；提示「空着也能保存」 |
| 前端校验 | `if (r.production_date && !DATE_RE.test(...))` ⇒ **只在填了时查格式**，空值放行 |
| 后端 `psi.py:_bad_batch_dates` | 空串明确合法，不算脏值 |
| 报单导入「期望生产日期」 | 不带 `*`，非必填 |

⇒ **代码里并没有「写死必须录」**。但查出一个更要紧的缺口：

> 🔴 前端录了生产日期、`purchase_order_items.production_date` 也存了，可
> `purchase_order_confirm → batch_in()` **根本没传这个字段**，
> `INSERT INTO inventory` 里没有 `production_date` 列 ⇒ **台账里永远是空**。
> 也就是说「录」这个选择此前是空头支票（演示数据实测断言判红）。

所以「给选择权」必须**连落库链路一起修**，否则开关只是摆设。

### 1.2 前端：租户级开关（已随源码交付，未部署）

- 位置：采购单「批次信息」小面板，复用同页 `.ipn-unitsw` 原生勾选框长相（不造第二套开关）。
- 默认**关**：生产日期输入行 `v-if="isExtra('recordProdDate', false)"`，不录的人完全看不见它。
- 打开后**仍是选填**，不加强任何必填校验；关着时提交载荷不带该字段（避免编辑旧单误带残留值）。
- 状态存进 `useColSettings` 新增的 `extra` 偏好（与列显隐同一份云端配置、但分开存），后端 `col_pref_save` 把 `cfg` 当任意 JSON 存、只校验 dict 与大小 ⇒ **零后端改动**，换设备不丢。

🔴 **粒度说明（避免造出第二套口径）**：现有 `ui_prefs` 口径明确是**租户级**、不是用户级 —— 代码注释写着「同一张表不同账号看到不同列，就是第二套口径」。你说的「每个用户」按 B2B 语境＝**每个客户公司/每个经销商**，租户级正好对上：不同经销商各自配置，同公司内部所有人看到一致。若你确实要「同一公司内按账号各配各的」，那是另一个产品决策，需要单独拍板。

### 1.3 后端：落库补丁（已验证，**未落地**）

补丁：`.workbuddy/stage1/patches/production-date-chain.patch`（2 个文件、相对 `server/` 可 `patch -p1`）

| 文件 | 改动 |
|---|---|
| `db/queries/inventory.py` | `batch_in` 末尾新增 `production_date=''` 关键字参数；新建批次时把该列写进 `INSERT INTO inventory` |
| `db/queries/purchases.py` | `purchase_order_confirm` 从明细行读 `production_date` 透传给 `batch_in` |

- 新参数放在 `db_conn` **之后**，既有按位置调用零影响；不传时写空串，与改动前逐字一致。
- 空串合法 ⇒ **不强制必录**，与第 1 条要求一致。
- 🔴 **没有直接改 `~/Documents/hergent-erp`**：那个仓有并行会话在途改动，且生产/ git 双轨（21 个核心文件不一致）。补丁先在独立开发副本验证通过，**等你拍板再落地**。
- 已知边界：同批次累加分支不回填生产日期（原批次为空、新单带值时不会补写）。如需补，列入阶段 1 后续项。

## 2. 第 2 条：演示数据演练

### 2.1 沙箱怎么隔离（一条都不能少）

| 项 | 做法 |
|---|---|
| 库 | `~/Documents/hergent-erp/server/erp.db` 的**副本**，落在 `.workbuddy/stage1/demo-sandbox/`，每次运行重建 |
| 源码 | 本地仓 `server/` 的**副本**，再用阶段 0 生产快照覆盖 `db/queries/{inventory,purchases,sales}.py` ⇒ 核心链路按**线上版本**测 |

### 2.2 四组对照（真实业务函数，不是静态检查）

链路：`purchase_order_create` → **`purchase_order_confirm`（入库确认）** → `sale_order_create` → **`sale_order_deliver`（发货）**

| 组 | 生产日期 | 落库修复 | 判定 | 关键结果 |
|:--:|:--:|:--:|:--:|---|
| A | 不录 | 未应用（现状） | ✅ 6/6 | 草稿不写库存；入库写 `batch_in`、发货写 `sale`；批次号/到期日落库；库存 12→7 件 |
| B | 录 | 未应用（现状） | 🔴 6/7 | **坐实缺口**：明细行有 `2026-11-01`，台账 `production_date` 仍是空 |
| C | 录 | 已应用 | ✅ 7/7 | 台账 `production_date = 2026-11-01`，链路全通 |

## 3. 第 3 条：按计划开阶段 1

对齐计划 §6.2「阶段 1 · 账可信」第②项：**自动对账卡（余额对台账、流水链自洽、金额对得上），异常显式告警、禁止静默**。

工具：`.workbuddy/tools/stage1-reconcile.py`（只读判定内核）

| 判据 | 作用 | 演示数据结果 |
|---|---|:---:|
| ① 台账数量 == 流水累加 | 防「只改台账不写流水」 | ✅ |
| ② 流水链自洽 `前值+变动=后值` | 防流水断链 | ✅ |
| ③ 台账金额 == 数量×成本 | 防「库存看着对、成本全错」 | ✅ |
| ④ 存在非 `opening` 的真实交易 | 🔴 防阶段 0 那个**镜像快照假绿**（281 条全是快照、三项完美相等） | ✅ |

**坏样本自证 4/4 全部判红**（造在独立临时副本，不污染沙箱）：

| 脏数据 | 判红项 |
|---|---|
| 只改台账 +3 件、不写流水 | ① 台账 10.00 vs 流水 7.00 |
| 流水 `after_qty` 改大 1 | ② 0 + 12 ≠ 13 |
| 台账金额 +100 | ③ 170.00 vs 70.00 |
| 把流水全改成 `opening` | ④ 疑似一次性快照镜像 |

计划里「故意制造只改台账不写流水测试**必须变红**」这条验收标准，本轮已达成。

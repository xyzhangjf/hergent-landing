### 2.2 状态机：生产没有 CHECK，风险性质变了

生产 `tenant_1.db` 的实际 DDL（`sqlite_master` 原文）：

| 表 | status 定义 | 有无 CHECK |
|---|---|:--:|
| `sale_orders` | `status TEXT DEFAULT 'draft'` | ❌ 无 |
| `purchase_orders` | `status TEXT DEFAULT 'draft'` | ❌ 无 |
| `receivables` | `status TEXT DEFAULT 'unpaid'` | ❌ 无 |

- 原报告依据的 `CHECK(status IN (...))` 来自**本地镜像／开发版 DDL**，生产表已被迁移或从未加约束。
- `status='picking'` 实测 **0 条**、`status='voided'` 实测 **0 条** ⇒ 原报告担心的「SQLite CHECK 会让 UPDATE 直接抛错」**在生产不成立**。
- 真实风险反而更隐蔽：**任何字符串都能写进 status，没有任何拦截面**；且 `sale_orders` 22,505/22,506 全是 `signed`，状态机在实践中基本没被使用。

→ 修法不变（统一 `docstatus` + 跃迁白名单 + 中文拦截），但**理由从「防报错」改成「防脏状态、为真实交易做准备」**，且不必处理 DDL 迁移冲突，工作量下降。

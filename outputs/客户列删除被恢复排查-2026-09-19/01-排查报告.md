# 「删除『永诺旗舰店』列后被自动恢复」排查报告

**排查日期**：2026-09-19 ｜ **对象**：`hergent.cn` → 预报订单管理 → 改单（编辑网格）
**现象**：删掉「永诺旗舰店」这一列 → 点保存**成功**（无报错）→ 该列**又出现**，反复无效
**结论一句话**：**这是设计缺陷，不是操作失误。** 客户列的来源与「保存」的作用域是**两套完全不相干的东西**，
中间**没有任何一处记录「这一列被删了」**，所以删列在当前系统里**没有持久化载体** —— 尤其是本例这一列，
`forecast_submissions` 里它有 3 条记录，而保存只清得掉其中 1 条。

---

## 一、机制：一个闭环（不是 bug 偶发，是三重设计叠加的必然）

| 步骤 | 发生了什么 | 为什么没解决问题 |
|---|---|---|
| ① 你删列 | 只把该列从屏幕上的 `cross.units` 数组里去掉 | **没有任何地方记下「这列不要了」** |
| ② 点保存 | 后端 `save_matrix` 只做一件事：**删掉本期的 `role='导入'` 记录 → 按你提交的客户列重建** | 「永诺旗舰店」另有 **2 条不是「导入」角色**的记录（`sales` 测试单 / `boss` 单），**保存碰不到它们** |
| ③ 重新加载 | 客户列由后端 `all_units`（**全历史客户名册**）生成 | 该名册**不按期次、不按角色**过滤，且排除条件 `status != 'rejected'` **恒为真**（全库 `rejected` 为 0 行）= **等于完全没过滤** |
| ④ 结果 | 名册里那条记录还在 ⇒ 列被重新渲染出来 | 回到 ①，无限循环 |

> **一句话对照**：
> 你以为「删列」是在删**一个客户**；实际上系统里「删列」只等于**本期不生成这个客户的导入记录**。
> 而这一列**本期根本没有数据** —— 它是由名册"凭空"补出来的空列，所以你删的是一个**没有实体可删**的东西。

## 三、为什么删不掉：3 条硬证据

### 证据 1 —— 这一列有 3 条记录，保存只清得掉 1 条

```sql
SELECT id, role, status, period_id,
       (SELECT COUNT(*) FROM forecast_submission_items i WHERE i.submission_id=s.id) items,
       (SELECT COALESCE(SUM(i.quantity),0) FROM forecast_submission_items i WHERE i.submission_id=s.id) qty
FROM forecast_submissions s WHERE s.store_name='永诺旗舰店' ORDER BY s.id;
```

| id | role | status | period_id | 明细行 | 数量 | 说明 |
|---|---|---|---|---|---|---|
| **187** | `sales` | `recalled` | 9 | 2 | 29 | 🔴 **小程序提审测试账号**产生（`user_id=5` = `mptest` / 微信审核-销售） |
| **189** | `boss` | `pending` | 9 | 4 | 4 | 🔴 **你本人**（`user_id=2` = `boss` / 张俊峰） |
| **291** | `导入` | `pending` | 12 | 1 | 0 | 矩阵保存生成的（**只有这条** `role='导入'`） |

⇒ 保存时的两个 `DELETE` 都带 `role='导入'`，**只有 id=291 会被清掉**。
**187 与 189 永远留下** ⇒ `all_units` 永远含 `永诺旗舰店`。

### 证据 2 —— `all_units` 的排除条件在当前代码里**恒不成立**

| 事实 | 证据 |
|---|---|
| 全库 **`rejected` = 0 行** | `SELECT status,COUNT(*) FROM forecast_submissions GROUP BY status` → `pending 102` / `recalled 1` |
| **没有任何代码能产生 `rejected`** | 源码注释（`erp_db.py:16641`）：「**2026-09-07 下线：`forecast_submission_pending` / `_approve` / `_reject` 三个函数已删除**」；现在的期次审核走 `/api/forecast-audit/audit-period` |
| 唯一的**状态变更**路径只能产生 `recalled` | `erp_db.py:16647 forecast_submission_recall()` → `SET status='recalled'`；全仓 `UPDATE forecast_submissions ... status=` **仅此一处** |
| 新建提交的 status **硬编码 `'pending'`** | `erp_db.py:16298` `VALUES (..., 'pending', ...)` |
| ⇒ **`recalled` 不在排除名单里** | `all_units` 只排除 `'rejected'`；而 summary 的口径是 `NOT IN ('rejected','recalled')` |

🔴 **口径不一致**：
- summary 主查询（`erp_db.py:16469` / `:16480`）：`status NOT IN ('rejected','recalled')`
- `all_units`（`erp_db.py:16487`）：`status != 'rejected'` ← **少了 `recalled`**

⇒ 连「撤回」这个**真实存在且界面上有**的动作，也不能让一个客户列消失。
**「已撤回的报单」照样占着一个客户列**（如果它没有别的记录）。

## 四、🔴 由此暴露的一个更大的问题

**当前系统里，「客户列」这件事只能加、不能减。**

- 想在改单页**新增**一个客户列 → 有入口（`addMasterCol` / 右键「新增客户」/ 模板表头），能保存；
- 想**删掉**一个客户列 → 有按钮（`delCol`，就是上一轮我们加过守卫的那个函数），
  **但它只能在屏幕上删**，保存时**不产生任何"这个客户不要了"的持久记录**；
- 而且**界面上没有任何其他办法**：撤回（→`recalled`）不计入排除、驳回（→`rejected`）**功能已被删除**。

⇒ **完全闭环，没有任何一条用户可走的路径能删掉一列。** 这不是"你操作不对"。

**方案 B 的具体实现步骤**

1. **加表**（复用既有租户库迁移机制，`erp_db.py` 的 `_ensure_forecast_tables`）
   ```sql
   CREATE TABLE IF NOT EXISTS forecast_hidden_units (
     store_name TEXT NOT NULL PRIMARY KEY,
     hidden_at  TEXT DEFAULT (datetime('now','localtime')),
     hidden_by  TEXT DEFAULT ''
   );
   ```
   > 为什么是**租户级**而不是像 `forecast_col_schemes` 那样**按用户级**：
   > `all_units` 本身就是**租户级**名册，隐藏名单必须与之同口径；否则会出现「你删了、同事还看得到」的错位。

2. **`all_units` 加过滤**（`erp_db.py:16485`）
   ```sql
   ... WHERE s.status != 'rejected' AND s.store_name != ''
       AND NOT EXISTS (SELECT 1 FROM forecast_hidden_units h WHERE h.store_name = s.store_name)
   ```

3. **`save_matrix` 落库**（`routers/forecast_submissions.py`）
   - 载荷新增 `hidden_customers: [name...]`；
   - 保存事务内：把 `hidden_customers` 里的名字 `INSERT OR IGNORE` 进隐藏表；
   - **同时**把 `customers`（= 当前保留的列）里的名字 `DELETE FROM forecast_hidden_units`
     ⇒ 「重新加回一列」也自然生效，不会出现"删了就再也加不回来"。

4. **前端提交被删列**（`Forecast.vue` 的 `saveEdits`，现 `customers: cross.value.units.map(u => u.name)` 所在处 ≈`3473`）
   - 与加载时保存的**初始列集**做差集，得到 `hidden_customers`；
   - 一并放进保存载荷。

5. **一次性数据迁移（只此一次）**
   ```sql
   INSERT OR IGNORE INTO forecast_hidden_units (store_name, hidden_by)
   VALUES ('永诺旗舰店', 'AI运维');
   ```
   ⇒ 该列**立刻在所有期次消失**，且**不动 `forecast_submissions` 一行** ⇒ 历史数字**零变化**。

## 8.1 设计：一条新的「隐藏名册」链（B）

| 层 | 位置 | 内容 |
|---|---|---|
| **表** | `erp_db.py::_ensure_forecast_tables` + 主 DDL 块（两处） | `forecast_hidden_units(store_name PK, hidden_at, hidden_by)` —— **租户级**，口径与 `all_units` 同源 |
| **读端** | `erp_db.py:16521`（`all_units`） | 加 `AND NOT EXISTS (SELECT 1 FROM forecast_hidden_units h WHERE h.store_name = s.store_name)` |
| **读端·口径对齐（C）** | 同句 | `s.status != 'rejected'` → `NOT IN ('rejected','recalled')` |
| **写端** | `routers/forecast_submissions.py::save_matrix` | 新增入参 `hidden_customers`；**双向** —— 入参里的名字 → `INSERT OR IGNORE`（带 `WHERE EXISTS` 守卫）；`customers` 里的名字 → `DELETE`（这就是"加回列"） |
| **前端** | `Forecast.vue` × 5 处 | `cross.hiddenUnits` 待提交集合；`delCol` 记入 / `addUnit` 移出 / 每次 `loadEditGrid` 重置；`saveEdits` 提交 `hidden_customers` |

**三个关键设计判断（为什么这样做，不是别的做法）**

1. **表为什么是租户级、而不是按 `user_id` 隔离** —— 与 `all_units` 同口径。按用户隔离会让同一张表在不同账号上看到不同列，**又造出第二套「读端 ≠ 写端」**（这次故障的同一个病根）。
2. **为什么用「显式记录删列动作」而不是「保存时算名册差集」** —— 差集会把**改名**也算成删列（`renameCol` 后旧名从 `units` 消失），而用户的意图只是改显示名。显式记录只认「用户真的点了删列」这一个动作。
3. **`hiddenUnits` 为什么放进 `cross` 而不是单独的 `ref`** —— `snapshot()` 是 `clone(cross.value)` **全量深拷贝** ⇒ 放进 cross，**Ctrl+Z 撤销删列时集合自动回退**；若另起 ref，用户撤销了删列、集合却还留着名字，一保存仍把列隐掉 —— 看起来像「撤销没用 / 系统自己删数据」。

**可逆性**是本方案的硬指标：隐藏名册里的记录 = 一条 SQL 就能撤销的软状态，**不碰任何报单数据**。

**收口时自查发现的两处「自相矛盾」，一并修掉（4 处）**

🔴 两处都是**改完才看出来的**，不是一开始就设计好的 —— 值得记下来：

1. **基线被置成 `null`，把自己的设计目标否掉了**
   `loadEditGrid` 里那条注释的第 ② 个目标写着「「回退」按钮从进编辑起就可用」，
   而紧接的代码在"草稿含实质改动"时把基线置 `null` ⇒ 按钮变灰。
   ⇒ 改为取**合并草稿之前**的那份服务端快照（`preDraftSnap`，必须在就地覆盖 `rows` 之前克隆）。
   ⚠️ 这里有个隐蔽点：草稿恢复是**就地改** `rows`、并往 `units` 里补列，赋值对象与这些数组
   是**同一份引用** ⇒ 事后 `clone(cross.value)` 拿到的已经是"草稿内容"，拿它当基线等于没基线。

2. **状态条与相邻按钮各判一套**
   按钮原为 `:disabled="!lastSavedSnap"`，状态条看 `dirtySinceSave` ⇒ 会出现
   「状态条说有未保存改动、紧邻的「回退」却是灰的」。改为**同源**（都看 `dirtySinceSave`）。
   顺带修掉 `draftRestored` 残留：无草稿分支原先不置假 ⇒ 某次加载命中草稿后，
   即使草稿已被清，横幅仍会宣称「已从本地草稿恢复」（状态由**上一次加载的残留**决定）。

## 11.8 尚需你亲手验一条（我无法在不写库的前提下验）

状态条的第三态 **「已保存 HH:MM」** 只在**真实保存成功**后出现。
代码层面已只读核对过顺序（`lastSavedAt` 先记、`loadEditGrid` 重载**不会**冲掉它），但需要你点一次。

**验收步骤**
1. `Cmd+Shift+R` 强刷
2. 进「改单」→ 看工具行右侧应显示 **「尚未修改」**（灰点）
3. 改任意一个格子或删一列 → 应立刻变 **「有未保存的改动」**（橙点）
4. 点「保存」→ 提示成功后应变成 **「已保存 13:0x」**（绿点），且**页面仍停在可编辑状态**（这是有意的）
5. 保存后再点「取消」→ 提示**不应**再提「未保存的改动」

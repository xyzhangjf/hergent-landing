## 0. 一句话结论（更正后）

**我们的两层结构（文本独占整行 + 下沉工具条）与 WorkBuddy 一致，且"配置放底部"也是对的。**

## 6. 优化建议（更正后）

### 🔴 P0 · 把「两个开关」收成「一个模式 chip」（对齐 WB 的 `mode`）

**现状**：`只建议` + `自动降级` 两个并列开关，语义边界模糊。
**做法**：合并为一个带下拉的模式 chip，档位用业务语言：`提问（只给建议） / 执行（可直接操作）`；需要再扩到 WB 的四档。
- **预期**：底部 **6 → 5** 控件；老板一眼看懂"现在 AI 会怎么做"。
- **风险**：低。**但必须注意**：`readonly` 是**有后端硬门禁的真实权限状态**（今天刚补的 `disabled` 拦截同源系列）⇒ 合并时**不得把它降级成纯 UI 文案**。

- **思考强度**：DeepSeek 支持 `effort: low / high / max`（今天已实测），且**客户端侧「深度思考」折叠块已完成并验证 9/9** —— 只等上游把 `reasoning_content` 转出来。
- **预期**：**产品级差异**（老板能感知"想得久/答得快"），价值高于所有视觉细项。

### 9.6.1 先解掉一个架构前置问题
ERP 带 systemd 沙箱、**读不到 `/root/.hermes/config.yaml`** ⇒ "改配置文件换模型"走不通。
**但实测发现更好的路**：Hermes 的 `/v1/chat/completions` **认请求里的 `model`**
（`api_server.py:2290` → `model = body.get("model") or self._model_name`），
而我们的代理**本来就转发这个请求体** ⇒ **按请求换模型，完全不必碰任何配置文件**。

### 9.6.2 🔴 思考强度：**决定不做**（有证据，不是偷懒）
`reasoning_effort` 在 `api_server.py` 里 **0 命中**；实测：
- 带 `reasoning_effort: max` 请求 **HTTP 200**（被接受，不报错）
- 但 `reasoning_content` **始终为 0**（Hermes 不转发推理，与「深度思考」那条同源）
- 用**耗时**当代理做对照（同一道推理题，各 2 次）：`low` 10.96/12.64s · `max` **8.44/10.77s**
  ⇒ **max 反而更快、两组完全重叠** ⇒ 该参数**不生效**

**结论**：做一个"思考强度"控件会是个**假控件**（点了没有任何效果）—— 正是老板明确要求避免的"死路径"。
⇒ **本轮不做**；等上游支持（Hermes 转发 `reasoning_content` 或提供配置项）后，UI 侧只是两行的事。
（附：真要让强度生效，得写 Hermes 配置 `agent.reasoning_effort`，而沙箱进不了 `/root`。）

### 9.6.4b 🔴🔴 重大更正（2026-09-25 23:0x，老板追问「是真功能还是摆设」）
**结论：模型选择目前是「摆设」。** 我 9.6.4 里那条「**证明不是假控件**」**结论下早了**。

**证据链（这次到服务端）**
| 检查 | 结果 |
|---|---|
| 浏览器请求体带 `model=deepseek-v4-pro` | ✅（**但这只证明"管道通了"，不证明"模型换了"**） |
| 响应里的 `model` 字段 | ✅ 回显 `deepseek-v4-pro`（**OpenAI 兼容行为的回显，不等于真的用了它**） |
| **Hermes 服务端账本** `session_model_usage` | ❌ **近期全是 `deepseek-v4-flash`，一条 `deepseek-v4-pro` 都没有** |

**根因（代码级）**
```python
def _resolve_route(self, model_alias):
    if not self._model_routes or not isinstance(model_alias, str): return None
    return self._model_routes.get(model_alias)
```
`/root/.hermes/config.yaml` 里**没有 `model_routes`** ⇒ 路由表为空 ⇒ 请求的模型名**匹配不到任何路由** ⇒ 回落默认模型（`deepseek-v4-flash`）。

**全部 `/v1` 路由已枚举**（health / models / capabilities / skills / toolsets / chat/completions / responses / runs）——
**没有任何"切换模型"的端点**，也没有执行斜杠命令的端点。

**要变成真的，只有一条路**：在 `/root/.hermes/config.yaml` 加
```yaml
model_routes:
  deepseek-v4-pro:
    model: deepseek-v4-pro
```

### 9.9 逐字动画（流式打字机）：**实测后决定不做**

> 老板问「逐字动画有什么副作用？一定要做吗？」—— 不凭感觉答，先量「当前输出到底是逐字到达还是成块跳」。

**实测（经代理的真实链路，一条 310 字回答）**

| 指标 | 实测值 |
|---|---|
| 内容帧数 / 总字符 / 总耗时 | 236 帧 / 310 字 / 5.6 秒 |
| 每帧字符（中位 / 均值 / p90 / 最大） | **1 / 1.3 / 2 / 3** |
| 帧间隔（中位 / 均值 / p90 / 最大） | **1ms** / 5ms / 13ms / 68ms |
| 「1 帧只有 1 字」占比 | **72%** |
| 「1 帧 ≥ 8 字」占比 | **0%** |
| 静默 >300ms 的次数 | **0** |

⇒ **上游本来就是逐字吐**（≈55 字/秒），前端渲染节奏已达 **≈42 帧/秒**（接近 60fps 上限）。
**逐字动画能带来的"平滑"收益 ≈ 0**；典型打字机 30 字/秒还**比现状更慢**：
310 字回答从 5.6 秒拉到 10.3 秒（**+4.7 秒**），2000 字长回答会多等 **≈33 秒**。

**副作用（均有代码依据，按严重度）**

| # | 副作用 | 依据 |
|---|---|---|
| 1 | **与「答完了」的判定打架**：`store.chat.streaming=false` 在 `hermesChat` 返回时**立即**置位，工具条折叠(`toolsLive`)、参考来源、评价按钮全挂它 ⇒ 正文还在打字、工具条已收起 | `CopilotDrawer.vue:130/207/580/1580` |

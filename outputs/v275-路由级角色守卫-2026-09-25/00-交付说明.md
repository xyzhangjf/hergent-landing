# v275 交付说明 —— 路由级角色守卫（深链不再绕过入口显隐）

> 日期：2026-09-25｜生产：hergent.cn（前端）
> 真机验收：**50 项断言全绿 / 0 失败**（七个相位，全程只读）
> 落地范围：`/zhoupu-import` 一个页面（后端唯一一个"整页级拒绝"的页面）

## 一、起因

v274 把「舟谱单据导入」的入口从侧栏迁进「能力中心 › ERP 数据源」卡片后，主管角色**看不到那张卡**了。
但只要**手敲 URL `#/zhoupu-import`**（书签、浏览器历史、别处贴过来的链接），页面**照样能打开**——
点到"读取"才被后端 403 拒掉。

这属于**假封锁**：看起来"权限做过了"，其实没有。它比假入口更难发现 ——
假入口是"看得到进不去"（用户会来报），假封锁是"看不见却进得去"（没人会来报）。

根因：入口显隐靠 `v-if`，而 **`v-if` 只藏 DOM，不藏路由**。

## 二、改了什么

| 面 | 文件 | 改动 |
|---|---|---|
| 判据层 | `src/constants/roles.js` | 新增通用判据 `roleIn(r, allowList)`；`canUseMiniProgram` / `canViewForecastSummary` / `canImportZhoupu` **全部改为调它**（原来是三份各自 `includes` 的写法） |
| 路由 | `src/router/index.js` | 加 `async beforeEach` + `meta.roles` 白名单；`/zhoupu-import` 的 meta 挂上 `ZHOUPU_IMPORT_ROLES` |
| 外壳 | `src/components/Shell.vue` | 消费 `?denied=<页面名>`：弹一条说明 + 把 query 清掉 |

## 三、三个设计决策（都是取舍，不是顺手）

### 1. 判据必须收成一个函数

「能不能看到入口」与「能不能进页面」是同一件事的两面。两边各写一份，就必然出现两种界面级假象
（假入口 / 假封锁）。所以路由表的 `meta.roles` 与侧栏的 `v-if` 现在引的是**同一个数组、同一个算法**。
以后加受限页面，只需要在路由表多写一个 `roles:` 字段，不用再造判据。

### 2. 守卫必须 `await` 权限，且**失败要放行**

`roleIn('')` 对"未知角色"是 fail-open（返回 true），这是刻意的 ——
启动瞬间 `store.user.role` 就是空串，此刻判 false 会把老板弹走。

但路由守卫的语义不同：**页面还没渲染，没有"闪一下"的问题**。所以守卫在判之前先
`await ensureRoleLoaded()`（内部就是 `loadPerms()`，幂等、命中缓存不发请求），把"未知"消掉。

🔴 而 `loadPerms()` **失败时仍然放行**（网络抖动 / 401）。取舍很明确：
让一个终将被后端 403 的人多看一眼页面，远比**把管理员挡在自己系统门外**轻。
这条在探针里有专门的反例对照（桩模式 `boom`）。

### 3. 拒绝必须看得见

守卫里**没有**用 `return false` —— 那会原地停住、页面一片空白，是"死按钮"的变体。
改为 `return { path: '/workbench', query: { denied: '舟谱单据导入' } }`，由 Shell 弹一条
**「没有「舟谱单据导入」这一页的访问权限，已回到经营工作台」**，并立刻把 query 清掉
（不清的话刷新 / 回退 / 把链接转给别人都会再弹一次）。

### 4. 为什么只给这一个页面加

| 页面 | 为什么**不**加 |
|---|---|
| `/forecast` | 业务员能进（页内只是看不到汇总表那块），**整页拦会误伤** |
| `/payroll` 等模块级页面 | 判据是 `perms` 数组（模块权限），未授权时页面自己会渲染常驻说明；按模块拦会把"接口抖一下"放大成"进不去" |
| `/zhoupu-import` | ✅ 后端 `_guard()` 就是"非 admin/boss 一律 403" —— 整页不可用，拦在门口不会误伤任何合法用法 |

### 第七相位：三组桩对照（本轮最锋利的一组）

同一个**管理员令牌**，只改权限接口返回的角色 ⇒ 行为必须翻转：

| 桩 | 桩造的响应 | 期望 | 实测 |
|---|---|---|---|
| `sup` | `user.role='supervisor'`（权限给 `*`，即模块全放行） | **拦截** | ✅ 弹回工作台 + 提示条在场 |
| `norole` | `user.role=''`（接口正常但没角色） | 放行 | ✅ 落在 `/zhoupu-import` |
| `boom` | 权限接口 500 | 放行 | ✅ 落在 `/zhoupu-import` |

`sup` 那一格是**核心判据**：模块权限给的是 `*`（全部放行）、只有角色不是 admin/boss ⇒ 仍然被拦。
⇒ 守卫读的是 **`role`**，不是令牌、也不是模块权限。截图 `05` 里右上角显示的身份是桩造的 `probe`、
侧栏里「算工资」还在（权限全放行），但页面照样进不去 —— 一眼就能看出这两件事是分开的。

三个桩各断言了 `桩被调用 ≥1 次` —— 否则"没拦住"可能是"判据压根没跑"的假绿。

## 六、探针自身踩的三个坑（记下来，下次别再犯）

1. **短命元素（toast 只活 3 秒）**：轮询取样必漏；截图也要抢在窗口内。
   第一版在 +3.5s 处截图 ⇒ 拍出来是"页面对了、提示没了"，等于没拍到本轮最该给人看的东西。
   改法：`MutationObserver` 在它出现的当拍落账（当判据），截图挪到 +950ms。
2. **想造"store 里角色为空"的起点，只能靠新文档**：Pinia store 是全局单例，
   Shell 卸载**不会**清空它。所以流程是「清 token → `hardGo #/login`（守卫放行、且不挂载 Shell
   ⇒ 不拉权限）→ 装桩 → 种回 token → hash 导航到目标路由」。
   `/login` 是唯一同时满足"放行"和"不挂载外壳"的落点。
3. **断言里的数字要按"当前登录角色"算**：侧栏管理员 **12** 项、主管 **11** 项（差的那项是「算工资」，
   `v-if="store.canModule('payroll')"`）。第一版照抄了管理员的 12 ⇒ 报了一条红，
   **那是断言写错、不是产品缺陷**。现在探针会把侧栏条目清单打出来自证。

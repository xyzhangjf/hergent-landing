## 一、一句话结论

本轮修了 **2 件事**，但真正重要的是**第 3 件没打算找、却撞上的**：

1. **工资条通道**：把「能群发、不能定向」的企业微信通道**拦在发送之前**（原实现会把每个人的实发工资发进同一个群）。

   并且顺着它做了一次全量审计，**发现 104 个同类幽灵符号**（详见 §四）。

## 二、改了什么

### 2.1 工资条：企微通道 fail-closed（`routers/salary_send.py`）

| # | 问题 | 修法 |
|---|---|---|
| ① | 群机器人 **没有「发给某个人」的能力**（`touser` 对它无效）→ 「群发工资条」= 把**每个人的应发/实发**逐条发进同一个群 | `CHANNEL_IMPLEMENTED.wechat: True → False`，**删除**群机器人发送代码（不留死路径） |
| ② | 原顺序**先查配置再查能力** → 隐私拦截会被误报成「通道未配置」/「暂未接入」 | **能力闸提到配置闸之前** |
| ③ | 报错文案不可执行 | 新增 `CHANNEL_BLOCKED_REASON`，说明「为什么 + 怎么办」，透出到 `GET /channels` 的 `blocked_reason` 与 `POST /send` 的 `channel_status.note` |
| ④ | **in-app 也要查渠道配置** → 生产三库该表均空 ⇒ 员工即使已关联账号、站内通知完全可用，也会失败 | 配置闸**只对需要外部凭据的通道**生效（站内通知靠 `recipients` 定向，不需要任何配置） |

> 判据原话：**宁可不发，不可群发。** 工资条含实发金额，发错对象是隐私事故，事后再报错没有意义。

### 2.2 工资条：根因修复

```python
# 旧（必崩）
employee = db.hr_employee_get(slip.get("employee_id", 0))    # ← erp_db 上不存在！且在 try 之外
try:
    ...
```

- `db.hr_employee_get()` **全仓从未定义过**（唯一调用点就是这一行）→ 每次发送 `AttributeError`
  → 冒泡成 **HTTP 500** → `salary_send_logs` **连一条失败记录都写不下**。
- **这才是「工资条从未发过」的直接原因**（前几轮我修的是 `recipients` 定向，看不到这一层）。
- 改用真实存在的 `db._get_employee(eid)`，并**移入 `try`**：拿不到档案也走「不投递 + 明确原因」，不是 500。

### 2.3 报单映射 `/mine` 收紧（`server/server.py`）

- 现状：解析不到员工 → `employee_id=0` → `report_mapping_list()` 对 0 的语义是**跳过过滤**
  → 该账号拿到**全租户**的报单映射（别人的门店/客户简称、单型、调拨仓库）。
- 修法：**返回空数组 + warning 日志**。
- 返回形状**保持数组**（该端点目前零消费方，契约不变）；底层 `report_mapping_list(employee_id=0)` 语义不动（管理端列表照旧）。

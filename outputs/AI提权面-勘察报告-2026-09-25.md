# AI 提权面勘察报告（2026-09-25，只读勘察）

> 起因：副驾代理层专项 P3 修复后，暴露两条残留风险 —— ① Hermes 可绕过 `execute_tool` 直接打 ERP REST；② 租户技能明文教「从 `erp.db` 取 token」。
> 结论：**两条是同一条攻击链，且每一环都已验证为真。它能让 P3 的门禁与 ai_mode 管控整体失效。**

---

## 1. 结论先行

| 环节 | 状态 | 证据 |
|---|---|---|
| ① Hermes 有 shell / 代码执行能力 | ✅ **成立** | Hermes 工具包含 `terminal_tool.py`、`code_execution_tool.py`、`file_tools.py`、`file_operations.py`、`computer_use*` |
| ② Hermes 能读 `erp.db` | ✅ **成立** | `erp.db` 权限 `-rw------- hergent hergent`；**Hermes 网关进程就以 `hergent` 运行** ⇒ 可读 |
| ③ 技能明文给出取 token 配方 | ✅ **成立** | `hergent_t1/skills/hergent-erp-tools/SKILL.md:12`、`.../erp/hergent-erp-diagnostics/references/known-bugs.md:42`；**且 `_seed/` 里有同样两份**（⇒ 每个新租户都会被复制） |
| ④ 拿到的 token 可用 | ✅ **成立** | `SELECT token FROM sessions ORDER BY rowid DESC LIMIT 1` 取的是**最新会话**（实测最新为 `user_id=2`，通常就是老板）；`sessions` 有 `expires_at = created_at + 24h` ⇒ **24 小时有效** |
| ⑤ 用它打 REST 可绕过门禁 | ✅ **成立** | REST 走 auth + RBAC，与 `execute_tool` 无关 ⇒ **完全绕过 P3 的 readonly / disabled 拦截** |

**⇒ 净效果**：被提示词注入的 AI（或任何能指挥它的通道）可**以老板身份**直接调 ERP REST 写单/收款/改档案，`ai_mode` 形同虚设。

## 2. 攻击链（三段）

```
提示词注入 / 恶意指令
  └─ Hermes 用 terminal/code_execution 执行：
       python3 -c "import sqlite3;print(sqlite3.connect('/opt/hergent-erp/erp.db')
                  .execute('SELECT token FROM sessions ORDER BY rowid DESC LIMIT 1').fetchone()[0])"
  └─ 拿到一个**活着的、隶属老板的**会话 token（24h 有效）
  └─ curl -H "Authorization: Bearer <token>" -X POST http://127.0.0.1:8700/api/sale-orders ...
       ⇒ REST 直接写库，**不经过 execute_tool** ⇒ P3 门禁与 ai_mode 管控全部旁路
```

🔴 **必须诚实指出**：上一轮 P3 修的 `execute_tool` 门禁是**真有效但可绕过**的 —— 它只封了「正门」，而 `erp.db` 里的明文 token 是「后门钥匙」。

## 3. 附带的两个发现

> ⚠️ **本节第 1 条已更正（2026-09-25 14:4x）**：初版写「`hrt_` 令牌是死代码」是**误报** —— 起因是我用了 `grep "A\|B"`（本机已知会静默失效的写法），返回空就当成"没有"。**复核后事实如下：**

1. **`hrt_` 令牌通道是通的，但 `scope` 未接线**：
   - ✅ **`hrt_` 令牌会被 auth 校验** —— `core.py:286` 有专门分支：`if token.startswith("hrt_"): SELECT u.* FROM bot_tokens bt JOIN users u ON bt.user_id=u.id WHERE bt.token=? AND u.is_active=1`；`server.py:249` 也注明 hrt_ 前缀**免 CSRF**。
   - ❌ **`bot_tokens.scope` 列从不被判读** —— 上述查询不带 scope 条件，创建时恒写 `readwrite` ⇒ **拿到的就是一个"等于该用户的完整权限"的令牌**，没有最小权限能力。
   - ⇒ 结论修正为：**「受限作用域」名义存在、实则未接线**；**令牌本身可用**。
   - 🔴 **方法学教训（已第二次踩）**：`grep "A\|B"` 在本机**静默返回空**，会被误读成"不存在"。多模式**必须** `-e A -e B`，或用 Grep 工具。
2. **`sessions` 有 `ip_address` / `user_agent_hash` 列**，但本次未发现对它们做强制绑定校验（未深查，列为待核）。

**对方案的影响（重要）**：既然 `hrt_` 令牌通道**本来就是通的**，那么「给 AI 一条合法令牌」**不需要新开发**（原方案 D 的前半已是现成能力）。⇒ 让 AI 停止"偷会话 token"、改走 `hrt_` 令牌，**是纯文档 + 发一个令牌的事**，零代码风险。

## 4. 缓解方案（按「根治 → 缓解」排序）

| # | 方案 | 效果 | 代价 / 风险 |
|---|---|---|---|
| **A** | **拆 Unix 用户**：Hermes 网关以独立用户（如 `hermes`）运行，`erp.db` 仅归后端用户 `hergent` | 🟢 **根治①**：AI 执行上下文再也读不到 token | 中高：改 systemd unit + 大量文件属主；`/opt/hermes-tenants` 的技能同步、`hermes_memory_bridge` 等跨进程桥要重新对齐；**需停机窗口** |
| **B** | **会话 token 落库即哈希**（`sessions.token` 存 hash，auth 改为 hash 后比对） | 🟢 **根治②**：即使读到库也拿不到可用 token | 中：改 auth + 建会话两处；需兼容存量会话（可强制全体重新登录一次） |
| **C** | **清掉技能里的「取 token」配方**（`hergent_t1` + `_seed` 共 4 处） | 🟡 缓解：抽掉"现成配方"，显著降低被提示词引导的概率 | 低：纯文档改动。⚠️ 副作用：AI 自助排障会变难（那份 note 本就是排障产物）⇒ 建议**改为「通过 /api/bot/* 调用，勿直连 REST」**而非简单删除 |
| **D** | **把 `scope` 列真正用起来**：给 AI/桌面端发受限令牌，并在 REST **写端点**强制校验 scope | 🟢 根治③：即便有令牌，写操作仍被 scope 拦 | 中：需接线 auth + 各写端点；涉及桌面端兼容 |
| **E** | **给 AI 的 REST 调用加「AI 来源」标记并复用 ai_mode 门禁** | 🟡 缓解：让 AI 的 REST 写也受同一套管控 | 中：需统一出口（推荐让 AI 只走 `/api/bot/*`，即 C 的目标形态） |

**建议路径**：先做 **C**（低成本、立刻降低触发概率）→ 再评估 **A 或 B**（二选一即可根治；A 更彻底但要停机，B 在本仓库内、更可控）→ 最后用 **D** 补齐最小权限。

## 4.5 已实施：方案 C（2026-09-25 14:45，已落地 + 已验证）

**为什么先做 C**：复核发现 `hrt_` 令牌通道**本来就是通的**（见 §3 更正）⇒ 「给 AI 一条合法令牌」不需要新开发。于是 C 从"缓解"升级为**几乎零代码风险的根治第一步**。

**做了什么**
1. 走**既有官方端点** `POST /api/bot/create-token` 发了一个专用令牌（`hrt_…`，绑定 boss 用户），落到 `/opt/hermes-tenants/hergent_t1/.erp_bot_token`（`0600 hergent`）。
   - ✅ 实测该令牌调 `/api/bot/tools/check_inventory` → **200**。
2. 改掉 **4 个技能文件**里"从 `sessions` 抓会话 token"的配方（`hergent_t1` + `_seed` 各 2 处），改为读专用令牌文件，并写明**为什么禁止**（冒充真人用户、绕过 AI 管控与审计）。
3. 给 `known-bugs.md` 的「直接查 erp.db 备用 SQL」段加**只读约束**（那段排障价值真实，没有删；但明确禁止取 token / 写库）。
4. 改动均为**精确断言替换**（旧串必须恰好命中 1 次 + 回读校验），改前已备份 4 个原文件到 `/root/backup_skills_20260925_144554/`。

**为什么不会被同步覆盖（已核实）**
- `recipe_sync.py:307` 只写 `skills/hergent-milk-*/SKILL.md`（loss/forecast/commission/rebate 四个配方），**不碰** `hergent-erp-tools` 与 `erp-diagnostics` ✅
- `hermes_tenants.py:234` 用 `shutil.copytree` 把 **`_seed`** 复制给新租户 ⇒ **改 `_seed` 即改了"未来所有新租户"** ✅

**验证**：全租户 grep `SELECT token` 仅剩**禁止性警告**中的引用；新 token 段/只读约束均已就位。

**遗留项已补齐（同日 14:49）**：`_seed` 技能指向 `hergent_t<N>/.erp_bot_token` 后，租户开通流程**原本不会生成该文件** ⇒ 新租户 AI 会取不到令牌。

**已修**：`hermes_tenants.py` 新增 `_ensure_erp_bot_token(home, tenant_id)`，并在 `ensure_home()` 末尾调用。
- **身份选择**：绑到**平台 boss/admin 用户**。原因：`users` 是**全局表（无 `tenant_id`）**，开通时无法确定"本租户老板" ⇒ 取最低 id 的活跃 boss/admin。效果与被替换的旧配方（取"最新会话"）权限相当，但从"谁最后登录就是谁"变成**显式、可审计、可单独吊销**。
- **幂等**：令牌文件已存在且非空 ⇒ 直接返回，不重复发。
- **绝不抛错**：整段 `try/except` 兜底 —— 开通流程不能因为发令牌失败而中断。
- 与 `bot.py` 的 `create_bot_token` 保持同构（同表、同 `hrt_` + 32 hex 格式、同 `readwrite`）。

**验证（零副作用）**：
| 场景 | 期望 | 实测 |
|---|---|---|
| 对**已就位**的真实租户目录（t1） | 幂等空转、不改文件 | ✅ 行数 1→1、令牌未变 |
| 对**空目录**（临时） | 真发令牌、写 0600、入库 | ✅ `hrt_c211b3…`、36 字符、`0o600`、库中 `(user 2, readwrite)` |
| 测试后清理 | 行数还原 | ✅ 1→1 |

**⇒ §4.5 与本节完成后，方案 C 全链闭合（技能 + 开通流程）。**

**仍未做**：**B**（会话 token 落库哈希 —— 做到"读到库也拿不到可用 token"，才是断根）；**D 的 `scope` 强制接线**（让 AI 用受限令牌而非等于该用户的完整权限）。

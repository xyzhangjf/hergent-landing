## 二、「清」—— 名册只列真实列头

### 2.1 病根

名册里的名字来自**三个来源**，混在一起展示，导致「配过但没落地」的名字看起来像「历史列头」：

| 来源 | 含义 | 是不是真列头 |
|---|---|---|
| `mapping` | `report_mapping.report_alias`（**含已停用的配置行**） | ❌ 不一定 |
| `report` | `forecast_submissions.store_name`（报单**真的落地过**） | ✅ 是 |
| `hidden` | `forecast_hidden_units`（用户手动隐藏过的列头） | ✅ 是 |

一个经销商看到名册里有 `美联（保康店）`，很自然会认为"这就是历史列头、照它填没错"，但实际真列头是 `美联保康` —— 保存后**照样新增一列**（裂列 / 数量分家）。这正是 v247 裂列的病根。

### 2.2 修法（唯一判据）

后端 `report_mapping_alias_pool` 新增第 ⑥ 步，给每个候选打 `listed` 标记：

```python
# ⑥ 「这个名字是不是**真实列头**」—— 前端「历史列头名册」候选的**唯一准入判据**。
for _it in aliases.values():
    _it["listed"] = ("report" in _it["sources"]) or ("hidden" in _it["sources"])
```

* `aliases` **仍然保留全部名字** —— 撞名检测（`used_by`）、同对象查重、`suggest` 相近列头**都还需要**"配过但没落地"的名字。
* 只有**展示**这一层被 `listed` 收窄。
* `stats` 同步改为：
  * `total` = **真实列头数**（表头数字 = 用户看到的条数，不再对不上）
  * 新增 `configured_only` = 只在配置里出现过的名字数（供排查用）

前端 `ReportMapping.vue` 的 `aliasFiltered` 过滤 `a.listed`；`aliasTotal` 优先取 `stats.total`（缺失时回落到数组长度）。

### 2.3 生产数据清理

| 处置 | 对象 | 动作 | 理由 |
|---|---|---|---|
| 保留 + 改名 | `report_mapping` id=6 | 简称 `美联（保康店）` → **`美联保康`** | 「改简称」而非「停用」：**接管真列头**，账号仍能正常报单；改名后 `美联（保康店）` 这个名字彻底不存在，误导消失 |
| 停用 | `report_mapping` id=7 | 置为停用 | 可逆（随时能再启用）；保留历史配置行 |

> **为什么这么选**：id=7 停用后，提审-主管账号少一个演示门店，但**审核流程不受影响**；改名则是对 id=6「不降低能力」的最小改动。

### 2.4 清理后的现状（线上只读复核）

```
stats = {total: 21, in_use: 5, hidden: 2, configured_only: 2}
```

* 名册列出 **21 个真列头**。
* 「只在配置里出现过」的名字剩 **2 个**（`永辉东津店` / `永诺（江山店）`）—— 二者都来自**已停用的配置行**，因为 `listed=false`，**已经不再出现在用户可见的名册里**（仅保留在 `aliases` 里供撞名/查重使用）。
* 活跃的 5 条配置（id=1/2/3/6/8）的简称**全部都是真列头**。

## 三、「要」—— 同一对象只能有一条活跃配置

### 3.1 为什么必须硬拦

汇总表列头与**舟谱导入模板的客户列**都按 `report_mapping` **逐条**派生。同一对象存在两条活跃配置 ⇒ 模板出现两列：
* 两条简称**不同** ⇒ **裂列**；
* 两条简称**相同** ⇒ **重复列**。

两种都会让数量分家。

### 3.2 三处唯一实现（避免四条写路径各写一份）

| 函数 | 职责 |
|---|---|
| `report_cp_kind(counterparty_type)` | 对象类型 → 归类轴（`warehouse` / `store`）。**唯一判据实现** |
| `report_mapping_find_same_object(db, ctype, cid, exclude_id=0)` | 返回冲突的活跃行或 `None` |
| `report_mapping_same_object_error(row, system_name)` | **唯一**错误文案（四条写路径逐字复用） |

错误文案：

> 对象「{who}」已有一条活跃配置（简称「{row['report_alias']}」）—— 同一对象只能有一条活跃配置，否则报单汇总表和舟谱导入模板会把它拆成两列、数量分家。请先停用那一条，或直接改它。

### 3.3 两个必须踩过的坑

1. 🔴 **必须按「类型轴」比，不能只比 id**：`counterparty_id` 在两张表里**各自独立编号**（仓库 7 ≠ 门店 7）⇒ 只有 `report_cp_kind` 同为 `store`（或同为 `warehouse`）才算撞。
2. 🔴 **必须归一化历史写法**：`counterparty_type` 在库里**有两种写法** —— `store` 和早期别名 `customer`（`REPORT_CP_ALIASES = {"customer": "store"}`）。用裸 `counterparty_type = ?` 比会**漏掉**历史行。`report_cp_kind` 内部走 `normalize_report_cp_type` 归一。

### 3.4 四条写路径全部覆盖

| 路径 | 拦截点 |
|---|---|
| `report_mapping_create` | 查重后 |
| `report_mapping_update` | 用**改后的** `counterparty_id` 查（排除自己） |
| `report_mapping_toggle` | **只拦「启用」方向** —— 防「先停用旧的 → 再启用新的」绕过 |
| `report_mapping_import` | 查重后（**含批内自撞**） |

前端 `save()` 额外加了一道**本地预检**（红字即时提示），后端仍独立复核 —— 前端只是体验，权威在后端。

### 3.5 同时修掉的一个前端缺陷

`toggle()` 原先**没检查 `res.error`** ⇒ 后端拒绝、界面却说"已启用" = **静默失效**。已补：

```js
if (res && res.error) { toast(res.error, 'err'); return }
```

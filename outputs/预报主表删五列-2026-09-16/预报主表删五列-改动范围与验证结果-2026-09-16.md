## 四、删列前必查的三件事（核查记录）

这是本轮唯一可能「删出问题」的三个面，逐一查过：

1. **有没有消费方按 key 精确查找该列？**（`visibleCols.find(c => c.key === 'safety_stock')` 之类）
   → 全仓 grep 这 5 个 key 的**列定位式**用法：**零命中**。说明这些字段只被当**数据**读，
   没被当**列**定位 —— 这是删列唯一会崩的地方，确认安全。
2. **金额口径是否吃这一列？**
   → `rowAmount(r) = (parseFloat(r.dist_price) || 0) * rowSum(r)` —— 取 **分销价**，**不是**标准售价。
   故删「标准售价」**不影响下单金额**。
3. **服务端列注册表是否也登记了它？**
   → `server/db/queries/forecast_columns.py` 的 `PROTECTED_COLUMNS` 仍把 `sale_price` 列为系统列。
   但前端**从不据它渲染**（`cols.system` 只喂 `canDeleteMaster` 的「能不能删」判断），
   故为**惰性残留、不构成口径漂移**。为遵守「不影响数据结构」，本轮**未做 DB 迁移**。

## 六、两处如实记录的副作用 / 残留

### 6.1 起订量 / 到货天数：它们**从未落库**

实测 `products` 表的物理列只有 `sale_price` / `safety_stock` / `expiry_days`，
**没有** `moq` / `lead_days`；`routers/data.py` 的 `bulk_upsert_products`（第 330-343 行 fields
字面量）**不写**这两个键，`products_grid` 也**不回传**它们。

⇒ 在本次改动之前，这两个字段也只是「在报单网格临时填 → `syncMoq()` 存 localStorage →
**会话级**功能消费」。所以：

- **无持久数据损失**（本来就没存过）；
- 删掉这两列 = 该会话级功能的**入口消失** ⇒ 「起订量」面板、`moq-below` 合计列告警、
  到货周期提示将**失去数据来源**。这与你「预报场景不需要这两个字段」的判断一致，属预期；
  如果你希望保留这套告警，需要另建入口（例如放到「商品档案」页并真正落库）—— 请另行拍板。
- 「安全库存」「保质期天」「标准售价」不受此影响：它们**有物理列**，且仍可在
  「商品档案」页维护 ⇒ 低库存/短保告警继续有数据可用。

### 6.2 服务端列注册表仍有 `sale_price`

`forecast_columns.PROTECTED_COLUMNS` 仍登记 `sale_price` 为系统列（不可删）。因前端不从它渲染，
它是**惰性残留**：唯一可见后果是「想在列设置里新建一个叫『标准售价』的自定义列」会被拒
（提示「已存在名为…的列」）。按你「不影响数据结构」的要求，本轮**未做 DB 迁移**去清这行；
如需彻底清掉，属于独立的一次数据迁移，请另行确认。

### 6.3 关于告警徽标数

沙箱真机里 `.warn-badge` 计数为 **0**。已核实**不是回归**：该租户
`safety_stock > 0` 的商品数为 **0**（275 个在售商品全部未设安全库存），
`expiry_days` 在 1-7 天的也是 **0** —— 无数据可触发。告警代码路径本轮在 diff 中零改动。

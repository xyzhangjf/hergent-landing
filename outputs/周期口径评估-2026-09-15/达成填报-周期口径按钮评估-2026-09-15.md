# 「周期口径」按钮评估 —— 还有必要保留吗

> 评估日期：2026-09-15 ｜ 对象：目标与返利 › 达成填报 › 工具行「周期口径」（按月 / 按季 / 按年）
> 结论一句话：**按钮不能直接删（删了季度/年度规则就没法填报达成），但它现在的形态是错的 —— 应该由「用户手选存储桶」改为「系统按规则自动分桶」。**

---

## 一、先说结论

| 维度 | 判定 |
|---|---|
| 是冗余控件吗？ | **不是**。后端确实按规则周期分桶读取，删掉会让季度/年度规则的达成永远是 0 |
| 现在有用吗？ | **对现有租户没用**。季/年两个桶的**唯一消费方是「返利合同」**，而你两个租户的合同数都是 0 |
| 它在帮用户还是误导用户？ | **误导**。它把「数据库存储键」暴露给用户去手工对齐；填错了图表照样显示、合同却读不到 |
| 建议动作 | **改造为自动分桶（方案 A）**，不是删除 |

---

## 二、这个下拉到底控制什么

它不是「同一个数据的三种视图」，而是**「往哪个抽屉里放 / 从哪个抽屉里拿」**。

后端读取端是**精确等值**匹配，不是范围匹配：

```python
# server/routers/rebate_achievements.py:258-260
m = _norm_month(month) or _current_month()
sql = "SELECT * FROM rebate_achievements WHERE period_month=?"
params = [m]
```

写入端把用户选的口径直接当主键存：

| 你选的口径 | 时间键长这样 | 数据躺在这行 |
|---|---|---|
| 按月 | `2026-09` | `period_month='2026-09'` |
| 按季 | `2026-Q3` | `period_month='2026-Q3'` |
| 按年 | `2026` | `period_month='2026'` |

三个键**互不相通**：在「按季」下填的数，切回「按月」看不见；反之亦然。

---

## 三、谁读哪个抽屉（决定一切的矩阵）

后端的返利计提只读一个接口，但它**按规则的周期口径去挑抽屉**：

```python
# server/domain/rebate_calc.py:573
def period_key_for(period_type, year, month_no):
    """month→'2026-08'  quarter→'2026-Q3'  year→'2026'  custom→''"""
```

这条 `period_key_for` 在全仓只有 **3 处调用，全部在「返利合同」上下文**：

| 调用点 | 用途 |
|---|---|
| `erp_db.py:10092` | 合同月度计提（算返利金额） |
| `erp_db.py:10260` | 合同全年达成额汇总 |
| `erp_db.py:10370` | 合同月度全景试算 |

而它依赖的 `_achievement_index()` 的 5 处调用，同样**全部**在合同上下文。

**反过来，被订阅最多的三个地方，全部硬编码只认「月」这个键：**

| 消费方 | 代码 | 取数方式 |
|---|---|---|
| 仪表盘「全年月度达成」 | `useMonthlyAchv.js:109/134` | 键 `` `${period_month}::dim::scope` ``，查 `` `${YYYY-MM}::` `` |
| 达成填报「全年月度对比」 | `Rebate.vue:1649` | `String(period_month).slice(0,7) === '2026-01'…` |
| 预报页「返利冲刺看板」 | `Forecast.vue:5714` | 强制 `^\d{4}-\d{2}$` |

### 由此得出的消费方矩阵

| 数据放在 | 图表看得到 | 看板看得到 | 合同计提读得到 |
|---|---|---|---|
| 月桶 `2026-09` | ✅ | ✅ | ❌（年度规则读 `'2026'`） |
| 季桶 `2026-Q3` | ❌ | ❌ | ✅（仅季度规则） |
| 年桶 `2026` | ❌ | ❌ | ✅（仅年度规则） |

**这就是病根：两套读取口径互斥，而页面上没有任何东西告诉用户该选哪个。**

## 四、实测：三个口径各渲染出什么

在隔离沙箱（`tenant_9997`，克隆自你的真实租户 `tenant_1`）逐档切换实测：

| 口径 | 渲染行数 | 第 3 列表头 | 该列显示的值 | 接口实际响应 |
|---|---|---|---|---|
| **按月** | 2 行 | **月度目标** | 蒙牛低温 ¥674,000 / 简爱 ¥80,000 | `?month=2026-09` → 2 条 |
| **按季** | **1 行** | 目标值 | 蒙牛低温 **¥8,684,000** | `?month=2026-Q3` → **空数组** |
| **按年** | **1 行** | 目标值 | 蒙牛低温 **¥8,684,000** | `?month=2026` → **空数组** |

实测发现的三件事：

1. **「按季」和「按年」渲染结果完全一样** —— 同为 1 行、同为 ¥8,684,000、同为空。两个选项在界面上等价，只差时间键字符串。
2. **有规则被静默吃掉**：「简爱」规则（生效期 2026-09-01 ~ 2026-09-30）在按季、按年两个口径下**都消失**。原因见下方缺陷 ①。
3. **目标值退化为年度总额**：按季视图里一行显示 ¥8,684,000（年目标），而同屏下方的「全年月度对比」表把它拆成 12 个月合计 ¥8,764,000。同一屏幕里两个金额，用户无法建立对应关系；用它做分母算出的「达成率」没有业务含义。

## 五、你的数据其实填在哪个桶（生产实测）

```
tenant_1.db（真实租户）
  规则：2 条，period_type 全部 = year
        · 简爱9月目标      8 万
        · 蒙牛低温2026年目标 868.4 万
  达成：4 行，全部在月度桶
        · 2026-08 蒙牛低温 323,776   · 2026-08 简爱  98,914.5
        · 2026-09 蒙牛低温 405,461   · 2026-09 简爱   8,500
  季桶 0 行、年桶 0 行
  rebate_contracts 0 行  ← 关键
```

**读出来的事实：**

1. 你一直在「按月」口径下，给两条**年度**规则填达成。
2. 这些数据对**图表/看板是对的**（它们只认月键），所以你在界面上看得见、以为没问题。
3. 但对**合同计提是错的** —— 它拿着 `period_type='year'` 去找 `'2026'` 这个键，**永远找不到**。一旦将来开返利合同，这两条规则的达成会被算成 0。
4. 季/年两个桶是空的，因为**唯一的读取方（返利合同）你还没用**（`rebate_contracts` 0 行）。

### 因果验证（不是推理，是实测）

往沙箱里注入两条明显金额的非月度数据，再刷新页面看图表：

```
注入：2026-Q3 记 ¥999,999 ＋ 2026 记 ¥888,888  （合计 ¥1,888,887）

「全年月度对比」实际达成合计：
  注入前   ¥836,651.5
  注入后   ¥836,651.5
  变化     ¥0        ← 季/年桶数据图表侧完全读不到
```

同时切到「按季」口径，那条 ¥999,999 **在填报表格里看得见**（行显示 `品牌 | 简爱 | 目标值 — | 999999 | …`）。

**即：数据进得了库、在填报页看得见、图表上却消失了。** 这正是用户最容易被骗的场景 —— 以为填进去了，其实主看板读不到。

## 六、顺带发现的三个缺陷

### ① 季/年口径下规则被错误过滤（`Rebate.vue:1719`）

```js
function ruleEffectiveInMonth(rule, m) {   // m 可能是 '2026-09' / '2026-Q3' / '2026'
  const e = rule.effective_end ? String(rule.effective_end).slice(0, 7) : ''
  if (e && e < m) return false             // ← 字符串比较
```

JS 字符串比较里 `'0' < 'Q'`，所以 `'2026-09' < '2026-Q3'` 成立：

- **按季**：`effective_end` 落在本季度内的规则全被误删（`2026-07/08/09` 都 `< '2026-Q3'`）→ 简爱规则消失
- **按季**：`effective_start` 在 `2026-10`~`12` 的规则**不会被删**（`'2026-10' < '2026-Q3'`）→ Q4 规则错误地出现在 Q3
- **按年**：`'2026-09' > '2026'` 恒成立 → **任何有生效起始日的规则全部消失**，只剩生效期为空的

后果：用户切到「按年」想填年度达成，最想填的那条规则恰好不显示。

### ② 季/年口径的目标值与达成不在同一粒度（`Rebate.vue:1742`）

```js
const monthTarget = isMonth ? monthTargetOf(r, yy, mm) : (r.target_value || 0)
```

非月口径一律取规则整期额。季度达成 ÷ 年度总额 = 一个没有业务含义的百分比。

### ③ 死代码

`Rebate.vue:1738-1739` 为季/年口径解析出的 `yy` 变量，在非月分支里**从未被使用**（只有 `isMonth` 分支用到 `monthTargetOf`）。是 v112 R2 引入后未清理的残留。

## 七、方案对比

### 方案 A：改为「系统按规则自动分桶」⭐ 推荐

- **做法**：去掉「周期口径」下拉，只保留时间（月）。表格每行显示一条规则时，按它自己的 `period_type` 决定写入哪个键；加一列「周期口径」标签（`periodText()` 已有实现）。
- **用户视角**：不再需要知道 `2026-Q3` 这种存储键的存在。年度规则自动进 `'2026'` 桶、月度规则自动进 `'2026-09'` 桶。
- **收益**：① 彻底消除「填对图表、填错合同」的错位；② 顺带修掉缺陷 ①；③ 工具行少一个控件。
- **改动面**：`buildAchvRows`（键生成）、`doSaveAchv`（`period_month` 取值）、表头、去掉模板里三个分支与 `onAchvPeriod`。
- **风险**：契约变化 —— 后端接口不变（仍收 `period_month`），只是前端算出来的值变准了。已有数据无需迁移（月度桶本来就对）。

### 方案 B：保留下拉，修三个缺陷

- **做法**：保留下拉，但 ① 修字符串比较（季/年按区间比较）② 目标值改为汇总该期内月度分解 ③ 加提示「你的规则为年度口径，请切到按年」。
- **收益**：改动小，保留能力。
- **代价**：用户仍要先理解「口径」这层概念；「按季/按年等价」的问题仍在。属于把复杂度留给用户。

### 方案 C：暂时收起

- **做法**：当租户没有任何 quarter/year 规则时，下拉只渲染「按月」一项（或整块隐藏）。
- **收益**：改动最小，视觉上立刻干净。
- **代价**：治标不治本；一旦建了年度规则（你**已经有 2 条**），问题原样回来 —— 而且因为控件被藏过，用户更找不到它。

### 我的建议

**选 A。** 理由：你现在的 2 条规则全是年度口径，是「方案 A 能自动解决、方案 B 仍需用户学习、方案 C 会藏起唯一入口」的典型场景。而且 A 的改动集中在 `Rebate.vue` 一个文件的两个函数里，不需要动后端、不需要数据迁移。

如果你想先看效果再定，可以只做 A 的**第一半**：保留按月视图，在表格加「周期口径」列把每条规则的周期显式标出来 —— 这样即使不动写路径，你也能立刻看出「我这条规则是年度的，正在用月度的分母比」。

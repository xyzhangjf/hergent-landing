# 员工角色在 Web 端也能登录 —— 诊断报告

> 受理时间：2026-09-27 11:40（GMT+8）
> 现象：把员工「刘善涛」的角色改成**员工（staff）**后，该角色按设计应仅能登录小程序端，但实测在 **Web 端也能成功登录**。
> 本轮为**只读诊断**（零代码改动、零数据写入），故**不占用版本号**。

---

## 〇、结论先说（三句话）

1. **「员工角色仅能登录小程序端」不是一条被绕过、被缓存或未同步的规则，而是一条从未被实现的规则。** 它只存在于 `EmployeeArchive.vue` 角色下拉框的**标签文字**里（`'员工（仅小程序 · 报单 / AI 对话 / 库存）'`），全仓**没有任何一行代码消费它**。
2. **Web 端与小程序端共用同一个登录端点** `POST /api/auth/login`（小程序 `pages/login/login.js:112` 直接调它），而该端点**逐行不看角色**，且 `/api/auth` 整段在 `_PUBLIC_PATHS` 里**豁免 RBAC 中间件** ⇒ 角色权限在「能不能登录」这一步**根本不参与判定**。
3. **角色变更本身是即时生效的（后端生效了）**；看起来"权限没生效"是**前端**造成的：Web 侧栏 12 条菜单里只有 2 条装了权限门禁，路由表里 26 条路由只有 1 个页面有角色守卫，其余对 staff 一律可见可进 ⇒ 登录后侧栏几乎满配（staff 可见 10 条），观感等同"权限没生效"。

全平台 8 条账号的 `role`/`roles` 分布也全部 `roles=''`，无一人使用兼任。

## 二、根因：为什么 Web 端能登录（三层叠加）

### 2.1 第一层 —— 登录端点没有「端」这个维度

`server/routers/auth.py:115` `POST /api/auth/login` 全文逐行：

| 步 | 代码 | 与角色有关？ |
|---|---|---|
| ① | `_check_login_lockout(u, ip)` | 否（防爆破） |
| ② | `SELECT * FROM users WHERE username=? AND is_active=1` | **否**（只看账号存在 + 启用） |
| ③ | `_verify_password(p, user["password_hash"])` | 否 |
| ④ | 写 `sessions`、发 token、返回 `user.role` | **只是把角色读出来带给前端** |

**没有任何一处读 `request.headers` 判断来源端**（无 UA 判别、无 Origin 判别、无端标识参数），也**没有任何一处按 `role` 决定是否签发 token**。

### 2.2 第二层 —— `/api/auth` 整段豁免 RBAC

`server/server.py:655`：

```python
_PUBLIC_PATHS = {"/api/auth", "/api/system", "/api/health", ...}
```

`server.py:690` 中间件开头：

```python
if not path.startswith("/api/") or any(path.startswith(p) for p in _PUBLIC_PATHS):
    return await call_next(request)      # ← /api/auth 在这里直接放行，根本不走到 _check_perm
```

⇒ RBAC 中间件（`server.py:799` 的 `_check_perm`）**在登录请求上永远不会执行**。
这不是缺陷，而是必要条件：登录时系统还不知道你是谁，无法按角色裁决。

**推论（关键）**：只要 Web 与小程序共用这一条登录入口，**任何角色权限都不可能约束到"从哪个端登录"**。要约束，必须**新建**「登录端」这个能力，且只能在登录端点内部实现（不能在 RBAC 里）。

### 2.3 第三层 —— 「仅小程序」只是下拉标签的文字

| 位置 | 原文 | 性质 |
|---|---|---|
| `EmployeeArchive.vue:354` | `{ value: 'staff', label: '员工（仅小程序 · 报单 / AI 对话 / 库存）' }` | **纯文案**，无代码消费 |
| `EmployeeArchive.vue:148` | 「开通后可用此手机号 + 密码登录**网页端**与**预报小程序** —— 同一个账号，能进哪些页面由下方角色决定。」 | **同页文案，与上一条相反** |
| `constants/roles.js:110` | `MINI_PROGRAM_ROLES = ['admin','boss','sales','staff','supervisor']` | 语义是「能否在**小程序里干活**」，**不是**「能否登录小程序」 |
| `constants/roles.js:98` 注释 | 「该角色能否在小程序里干活（报单 / 商品 / 门店 / 汇总 / 库存 / AI 对话）。**判据是后端模块权限，不是猜的**」 | 明确定义为**能力**判据，而非**入口**判据 |

⇒ 「仅小程序」的真实含义是「**这个角色的模块权限只够撑起小程序那批接口**」，被写成了「仅能登录小程序端」的**口吻**。
**同一页面第 148 行的文案已经把正确答案写出来了**（"可登录网页端与预报小程序"），两句话并存且相反 —— 这是**文案层的自相矛盾**，也是本问题被误解的起点。

## 三、角色变更后，权限到底生效没有

**答案：后端生效了，前端没做。**

### 3.1 后端：生效（用生产真代码实测，非推断）

在生产服务器上 `import core`，直接调中间件所用的**同一个函数** `core._check_perm`（`server.py:799` 调的就是它），得到 tenant_1 的真实矩阵：

| 角色 | 授权模块 |
|---|---|
| admin | `*`（通配） |
| boss | dashboard, ops-workbench, data, sales, buying, stock, accounts, crm, marketing, hr, payroll, projects, reports, chat, tasks |
| **staff** | **data, chat, stock** |
| supervisor | data, dashboard, chat（租户覆盖后） |

按 `_PATH_MODULE_MAP`（301 条已登记前缀）逐条判定 staff：

| 判据 | 结果 |
|---|---|
| **staff 可通过模块判定的前缀** | **122 个**（data 82 + stock 35 + chat 5） |
| **staff 被拒绝的前缀** | **179 个** |
| 被拒模块清单 | dashboard、ops-workbench、sales、buying、accounts、crm、marketing、hr、payroll、projects、reports、tasks、settings |

⇒ **后端权限确实按新角色收紧了**，`/api/dashboard/*`、`/api/sale-orders`、`/api/reports/*`、`/api/employees` 等对 staff 一律 403。

### 3.2 前端：只做了 2 处入口门禁 + 1 处路由守卫（这是"看起来没生效"的根因）

`components/Shell.vue` 侧栏共 **12 条菜单**，其中**只有 2 条**装了权限门禁：

| 菜单 | 行 | 门禁 |
|---|---|---|
| 经营工作台 `/workbench` | 42 | ❌ 无 |
| 预报订货管理 `/forecast` | 59 | ✅ `canViewForecastSummary(role)` → staff 不在白名单 ⇒ **隐藏** |
| 目标与返利 `/rebate` | 60 | ❌ 无 |
| 货损核算 `/loss-accounting` | 61 | ❌ 无 |
| 算工资 `/payroll` | 62 | ✅ `store.canModule('payroll')` ⇒ **隐藏** |
| 档案管理 `/archive` | 68 | ❌ 无 |
| 渠道与价格 `/price-channels` | 69 | ❌ 无 |
| 能力中心 `/connect` | 70 | ❌ 无 |
| 招投标雷达 `/bid-radar` | 71 | ❌ 无 |
| 定时任务 `/cron` | 73 | ❌ 无 |
| AI 中心 `/ai-hub` | 74 | ❌ 无 |
| 设置 `/settings` | 75 | ❌ 无 |

移动端底部导航与「更多」抽屉（`Shell.vue:96-118`）同样只有那 2 处。

**路由守卫**（`router/index.js`）全表**只有 1 个页面**填了 `meta.roles`：

```js
{ path: 'zhoupu-import', ..., meta: { title: '舟谱单据导入', roles: ZHOUPU_IMPORT_ROLES } }   // 第 75 行
```

⇒ 其余页面**无角色守卫** ⇒ staff **手敲 URL 可以打开任意 Web 页面**（`/archive`、`/payroll`、`/settings` 都能进）；进去之后页面内的接口才 403。用户看到的不是"被拦在门外"，而是"**门都开了，里面到处报无权限**"。

> 注：**通用机制早在 v206 就建好了**（`store.canModule()` + `Shell.vue` 的 `v-if`），但**只有 `payroll` 一条菜单接上了它**，其余 11 条从未接入。
> ⇒ 精确的说法是「**机制存在，覆盖不完整**」，而不是"机制没做"。这解释了为什么 `payroll` 能正确隐藏、而"设置""档案管理"照样可见。
> ⚠️ 记忆文件 `topics/backend-auth.md` 缺口 B 里那句「侧栏按 `_DEFAULT_PERMS["staff"]` 过滤后**只剩几项**」是**基于 v206 设计的推断，本轮实测证伪**（实为 **12 条可见 10 条**），已同步更正。

### 3.3 前端权限缓存：改角色后不刷新页面，用的还是旧角色

`store/index.js:79-104`：

```js
async function loadPerms(force = false) {
  const tid = String(auth.tenant || '')
  if (!force && perms.value !== null && permsTenant.value === tid) return perms.value   // ← 幂等：同租户不重发
  ...
  const r = d && d.user && d.user.role
  if (r) user.role = r        // 角色是从接口回填的
}
```

`router/index.js` 的 `ensureRoleLoaded()`：

```js
if (store.user.role) return store.user.role       // ← 角色已有值就不再拉
```

⇒ **三处缓存叠加**，任一处命中都会让前端继续用旧角色：

| 缓存 | 位置 | 失效条件 |
|---|---|---|
| SPA 内存 `store.perms` / `permsTenant` | `store/index.js:81` | 只按租户比 —— **改角色不使键失效** |
| SPA 内存 `store.user.role` | `router/index.js` `ensureRoleLoaded` | 已有值即不重拉 |
| `localStorage: hergent_v2_token / hergent_v2_user` | 登录时写入 | 只有重新登录才更新 |

**实测时间线也印证了**：11:31:23 改角色 → 11:34:28 登录（新登录 ⇒ 拿到新角色，所以本次不是缓存问题）；但**如果刘善涛在改角色前已开着网页，他不刷新就仍是旧角色视图**。

## 五、附带发现（与本次现象正交，但会放大后果）

`data` 模块归了 82 个前缀，其中若干**看上去是管理级**的路径。**抽查 5 个端点的内部守卫**（中间件放行 ≠ 端点能执行）：

| 端点 | 内部守卫 | staff 能否调用 | 性质 |
|---|---|---|---|
| `GET /api/users`（`server.py:1329`） | ✅ `_admin(request)`（57 处同类兜底之一） | ❌ 403 | **有兜底，安全** |
| `GET /api/export/all`（`server.py:5089`） | ⚠️ 仅 `_auth` | ✅ 判定通过 | 本租户全量导出 |
| `POST /api/import/products`（`server.py:3984`） | ⚠️ 仅 `_auth` | ✅ 判定通过 | 可写商品档案 |
| `POST /api/import/contacts`（`server.py:3991`） | ⚠️ 仅 `_auth` | ✅ 判定通过 | 可写联系人 |
| `POST /api/datasources/business-source`（`server.py:1885`） | ⚠️ 仅 `_auth` | ✅ 判定通过 | 可切业务数据源 |

**说明与边界（务必读）**：
- 上述 4 项是**代码判定链推出**的结果（中间件 `server.py:799` → `_check_perm` → 归 `data`），**本轮未做真机 HTTP 复现**（需为 staff 造临时令牌，属写库操作，未获授权）。
- 这些端点**小程序也会调**，`data` 模块本身就是给「报单数据」用的 ⇒ 严格说这不是"角色变更没生效"，而是「**模块粒度粗 + 端点无二次守卫**」这一**既有加固缺口**。
- 多租户隔离仍由 `db` 层按租户上下文兜底 ⇒ **影响面限于本租户内**，不是跨租户泄漏。
- `/api/admin` 虽登记为 `data`（注释写「admin only，但 RBAC 走 data 模块」），但**全仓无该前缀的实际路由** ⇒ 不构成风险。

## 六、修复方向（供决策，本轮未实施）

| 档 | 内容 | 涉及 | 备注 |
|---|---|---|---|
| **A（最小、治本观感）** | ① 把侧栏 **12 条**菜单全部接上门禁（两处：桌面 `.sb-item` + 手机 `.md-item`；**建议按角色白名单而非模块**，理由见 §7.5）② 给主要页面补 `meta.roles`/`meta.modules` ③ 改角色后让前端权限缓存失效（`loadPerms(true)` 或在 `/api/auth/permissions` 带 `perms_version`）④ 同步 `CommandPalette.vue` | 前端 | 直接消除"登录后满配"的观感；**不解决"能不能登录"**；**效果与坑见 §7** |
| **B（文案止血）** | 改 `EmployeeArchive.vue:354` 的标注为「员工（小程序为主 · 网页端仅见少量入口）」，并修正与实际权限的对应；同步 `roles.js` 注释 | 前端 1 处 | 成本极低，先把"误导性承诺"去掉 |
| **C（真做端限制）** | 新建「允许登录端」能力：`users.login_scope`（`web,mini` / `mini`）＋ 登录端点内按 `X-Client: mini\|web` 判定 ＋ 小程序侧统一加该头 ＋ 前端 `Login.vue` 处理 403 文案 | 后端 + 小程序 + 前端 | 见下方三条硬约束 |
| **D（加固，与本次正交）** | 给 `/api/export/all`、`/api/import/*`、`/api/datasources/*` 等"仅 `_auth`"的写/导出端点补二次守卫（或把前缀拆到更窄模块） | 后端 | 建议**单独排期**，先出完整清单再动 |

### 方案 C 的三条硬约束（⚠️ 不满足会出事）

1. **必须在登录端点内部实现**，不能放 RBAC 中间件 —— `/api/auth` 在 `_PUBLIC_PATHS` 里（`server.py:655`），中间件对它**不执行**。
2. **不能在登录端点加「必须带某头」的硬门槛** —— `topics/backend-auth.md:32` 已记录：`/api/auth/login` 被网页端与小程序共用，加任何前置必填门槛都会**断掉小程序登录**。
3. 🔴 **存量小程序不带新头** —— 小程序请求虽集中封装在 `miniprogram/utils/api.js`，但**已发布版本不会带 `X-Client`**，且小程序有备案/审核周期、无法要求用户即时更新。
   ⇒ 若服务端对「缺头」判为拒绝，会**把存量小程序用户全部挡在门外**。安全做法：**缺头 = 视为小程序（fail-open）**，只在**明确识别为网页端**时才按 `login_scope` 拒绝；并给出可回滚的开关。
4. 定位要说清：客户端可伪造 `X-Client` ⇒ 这是**产品约束**（防止员工误从网页端进来看见不该看的入口），**不是安全边界**。真正的边界永远是 RBAC + 端点守卫。

## 七、A 方案做完后是什么效果（2026-09-27 追加评估）

> 口径：以**当前生产代码**为准（`Shell.vue` 桌面侧栏 **12 条**菜单；`router/index.js` 26 条路由里只有 1 条带 `meta.roles`）。
> ⚠️ 上一节 A 档原文写「11 个菜单」，实测为 **12 条**，此处更正。12 条＝`/workbench` `/forecast` `/rebate` `/loss-accounting` `/payroll` `/archive` `/price-channels` `/connect` `/bid-radar` `/cron` `/ai-hub` `/settings`。

### 7.1 确定会变的三件事（与"挂哪个模块"的选择无关）

| # | 现象 | 现在 | A 之后 |
|---|---|---|---|
| 1 | 侧栏菜单受权限控制的比例 | 12 条里只有 **2 条**（预报＝角色白名单、算工资＝`payroll` 模块） | **12 条全受控**（桌面 `.sb-item` ＋ 手机 `.md-item` 两处，共 24 处） |
| 2 | 手敲 URL 的深链 | 除舟谱导入 1 条外**全部可直达**（`router/index.js` 26 条路由只有 1 处 `meta.roles`） | 被守卫拦在页外（现在是"进得去、进去才 403"） |
| 3 | 改了角色之后 | `store.perms` 同租户幂等、`store.user.role` 有值不重拉 ⇒ **不刷新页面就一直用旧权限** | 权限缓存失效 ⇒ 菜单**当场**变化，不必重新登录 |

### 7.3 ⚠️ 三个会反咬的坑（不处理会"越修越糟"）

1. 🔴 **「设置」菜单不能挂 `settings` 模块。**
   `_PATH_MODULE_MAP` 里**没有任何前缀登记为 `settings`**（幽灵模块），而生产权限矩阵显示 **`boss` 的 `read_denied` 恰好是 `['settings']`** ⇒ 若写 `canModule('settings')`，**老板自己的「设置」菜单会消失**。应挂 `hr`（`/api/users`、`/api/permissions`、`/api/platform` 全是 `hr`）：老板有 `hr` ⇒ 不受影响；其余角色隐藏 ⇒ 正是想要的效果。
2. 🔴 **会计会被砍到只剩 2 项（工作台 ＋ AI 中心）。**
   会计的模块是 `accounts / reports / marketing / chat`，而**侧栏里根本没有"报表 / 账目 / 客户 / 营销"这几条菜单** ⇒ 菜单结构与模块体系**不同构**。机械挂模块的结果是会计几乎无菜单可点。**这是功能回退，不是修好。**
3. 🔴 **员工仍剩 7 项，其中 5 项是管理入口**（档案管理 / 渠道与价格 / 能力中心 / 招投标雷达 / 定时任务）。
   原因：`data` 是覆盖 **82 个接口前缀**的公共大口袋，`/api/datasources`、`/api/import/*`、`/api/cron`、`/api/bid-radar` 全归它。只要给某角色 `data`，"管理入口"就**全留**。

### 7.4 A 治不了什么（诚实边界）

| 问题 | A 能否治 |
|---|---|
| 员工能从 Web 端**登录** | ❌ 只有 C 能治（登录端点无"端"维度，且 `/api/auth` 整段豁免 RBAC） |
| 后端**越权** | ❌ 前端隐藏 ≠ 拒绝。手改 `localStorage` / 直接调 API 仍能打到后端，但**后端会 403** ⇒ 安全边界没退步，改的只是"看不看得见" |
| 模块粒度太粗（`data`=82 前缀） | ❌ A 动不了，要改的是后端映射表 |
| 会计/导购这类"模块与菜单不同构"的角色 | ❌ 机械映射会**误伤**（见 7.3 第 2 条） |

### 7.5 建议：A 应做成「**角色白名单**」，而不是「模块门禁」

项目里**已有同范式的先例**：`constants/roles.js::FORECAST_SUMMARY_ROLES = ['admin','boss','supervisor']` ＋ `roleIn()`（fail-open）＋ AST 护栏，且注释明写「与后端名单必须是同一份」。

按它做「角色 → 可见页面」清单，好处是能精确达成目标（例如"员工 Web 端只留 AI 中心"）、不受 `data` 粗口袋影响、与后端常量同源。代价是前端多一份表，**必须与后端同源维护**（现有护栏机制可覆盖）。

### 7.6 一起要动的第四处：命令面板

`components/CommandPalette.vue` 也有页面条目，且**已有 `when` 门禁机制**（第 74–77 行，用的就是 `canViewForecastSummary`）。
⇒ 侧栏藏了、命令面板还能搜到 = v267 那类**假入口**回归。**必须同步**。

### 7.7 可测验收判据（A 做完后逐条验）

1. 每个角色登录后，侧栏条数 **==** 7.2 表里的数字（逐角色截图或探针断言）。
2. 手敲未授权 URL（如 `#/payroll`）⇒ **停在页外**，不进页面（现在能进）。
3. 在权限页改某角色模块后（不重新登录、不刷新）⇒ 该账号的菜单**当场变化**。
4. 命令面板搜被隐藏的页面名 ⇒ **搜不到**。
5. 老板与管理员：**12 条一条不少**（防止 `settings` 幽灵模块把老板自己藏了）。

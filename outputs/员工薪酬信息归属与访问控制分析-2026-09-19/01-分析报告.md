# 员工「薪酬与账户」信息归属与访问控制 —— 可行性分析

日期：2026-09-19 ｜ 范围：hergent.cn（前端 hergent-cn-v2 / 后端 hergent-erp）
方法：静态代码核实 + 生产库只读抽样。所有结论均标注判据位置，未标位置的属推断。

> 🔴 **已修订**：本文发出后你答复「**有的客户是会计可以算工资**」—— 这把问题升级成「权限表必须按租户分叉」。
> 复查后确认：**角色 → 模块权限是全平台一份（存主库），因此「按客户差异化」今天做不到**。
> 该结论与配套的修订方案见 **`02-按租户差异的权限设计（修订）.md`**；本文第六节第 1 项的答复也已由该文承接。
> 本文其余结论（迁移不改变权限 / 缺字段级 / 加密与留痕缺口 / 时机窗口）**维持不变、继续有效**。

## 一、结论先行（三条与直觉相反）

### 1. 迁移位置**不会改变任何人的访问权限** —— 两者现在就是同一把钥匙

「员工档案」与「算工资」在后端**已经落在同一个权限模块 `hr` 下**：

| 接口前缀 | 模块 | 判据 |
|---|---|---|
| `/api/employees` | `hr` | `server.py:541` |
| `/api/payroll-workflow` | `hr` | `server.py:315` |
| `/api/payroll` · `/api/salary-batch-calculate` · `/api/salary-save` · `/api/salary-summary` | `hr` | `server.py:371-375` |
| `/api/salary-details` · `/api/salary-slip` · `/api/salary-bank-file` | `hr` | `server.py:598-600` |
| `/api/social-insurance-config` | `hr` | `server.py:375` |

中间件按 `路径前缀 → 模块 → 动作` 授权（`server.py:311`、`638`、`core.py:450 _check_perm`）。
**两边模块名都是 `hr` ⇒ 把字段从 A 页搬到 B 页，门没换、钥匙没换。**
纯粹换 UI 位置在本项目里**产生零安全收益**。

### 2. 真正的缺口是**权限粒度只有「模块级」**，没有字段级

`_check_perm(user, module, action)` 的判据只有一个模块名 + 一个动作（read/create/update/delete），
不存在「这个角色能读姓名但不读银行账号」的表达力。

⇒ 后果一：`GET /api/employees` 用 **`SELECT *`**（`erp_db.py:6247`）返回全表，
**身份证号、开户行、银行账号、社保基数、公积金基数、底薪一次性全给**。要么全有，要么全无。
⇒ 后果二：敏感度天差地别的字段**绑在同一行、同一接口、同一权限里**。

### 3. 会计现在**两边都进不去** —— 这才是「迁移」真正能解决的问题

`core.py:375 _DEFAULT_PERMS` 里拥有 `hr` 的角色**只有 `boss`**（`admin` 是 `*` 通配）：

| 角色 | 权限模块 | 有 `hr` 吗 |
|---|---|---|
| `admin` | `*` | 是 |
| `boss` | dashboard / ops-workbench / data / sales / buying / stock / accounts / crm / marketing / **hr** / projects / perf / goals / reports / chat / tasks | **是** |
| `accountant` | dashboard / accounts / reports / marketing | **否** |
| `supervisor` | dashboard / data | 否 |
| `sales` · `guide` · `driver` · `staff` | 各自业务域 | 否 |

⇒ **会计算不了工资、看不了社保** —— 业务上通常由会计承担的工作，现在只有老板能点。
⇒ 而给会计加 `hr` 又是错的：会连带拿到身份证 + 银行账号 + 改角色能力。

**所以「把薪酬迁到算工资模块」的真正价值不是换页面，而是：
让「算工资」成为一个比 `hr` 更窄的权限单元，从而能安全地单独授权给会计。**
这是本次分析唯一支持迁移的实质性理由。

## 二、现状盘点（已核实）

### 2.1 敏感字段清单（都在 `hr_employees` 单表内）

```
id_card                身份证号          ← L3 实名
bank_name / bank_account  开户行 / 银行账号  ← L3 资金
social_insurance_city / social_insurance_base / housing_fund_base  ← L2 薪酬
salary_structure       底薪 JSON         ← L2 薪酬
warehouse_id           个人仓            ← L1 业务必需
name / employee_no / position / hire_date / department_id / is_active  ← L1 业务必需
```
建表见 `erp_db.py:272-279`。**全部字段在一张表、一个接口、一个权限下。**

### 2.2 数据安全三条实质缺口

| # | 缺口 | 判据 | 说明 |
|---|---|---|---|
| ① | **明文落库** | `hr_employees.id_card`/`bank_account` 均为 `TEXT`；全仓 `crypto_utils` 未被引用 | 而 `crypto_utils` 是**现成的 AES-256-GCM**（密钥派生自 `ERP_SECRET`），其 `SENSITIVE_FIELDS` **已包含 `bank_account`**，且**已用于客户档案** `db/queries/contacts.py:3`。⇒ 同一套能力在员工档案上没接 |
| ② | **无修改留痕** | `routers/_field_log.py` 已覆盖商品档案 / 客户档案 / 销售订单 / 达成填报 / 返利规则 / 货损；**未覆盖 `hr_employees`** | 底薪 / 银行账号被谁改过**无记录**。而薪酬恰是最需要「改前 → 改后」留痕的字段 |
| ③ | **导出与枚举无额外约束** | `erp_db.py:6742 export_salary_bank_file` 明文拼 `账号\|姓名\|金额\|CNY\|备注`；`server.py:4928 /api/salary-slip/{employee_id}/{month}` 可按任意员工+月份拉取 | 两者都只过 `hr` 一道门，无二次确认、无留痕、无「只能看自己」检查 |

### 2.3 🔴 时机：**整块能力尚未投产，现在是零数据风险窗口**

生产只读抽样（`tenant_*.db`）：

| 项 | 实测 |
|---|---|
| 员工总数 | 11 名（tenant_1 七名 + tenant_10 四名） |
| `id_card` / `bank_account` 已填 | **0 行** |
| `social_insurance_base` / `housing_fund_base` / `salary_structure` 已填 | **0 行** |
| `salary_details`（工资快照） | **0 行 —— 工资从未真正算过** |
| `social_insurance_config` | **0 行** |

**这是决定性的**：现在拆表 / 加密 / 改权限，**没有任何存量数据要迁移**；
一旦员工真的填了银行账号和身份证，同样的改造就从「改结构」变成「带数据改结构」，
需要在线备份 + 逐行加解密 + 回滚预案。**改造成本随时间单调上升，且第一个填数据的人就会引爆它。**

### 2.4 前端不构成任何边界

- `router/index.js` 的路由 `meta` **只有 `title`，无权限字段**；
- `components/Shell.vue:41-57` 侧栏菜单**硬编码**，所有人看到同样的「算工资」「档案管理」入口。

⇒ 在页面上「把区块藏起来」只是 UX 优化，**零安全效果**。
所有判断必须发生在中间件之后、SQL 之前。

### 2.5 迁移的技术耦合点（改起来会牵动谁）

| 依赖 | 位置 | 影响 |
|---|---|---|
| 算工资读档案底薪 | `routers/payroll_workflow.py:96-99`「档案优先，配方兜底」 | 底薪若搬家，此处读路径要改 |
| 银行代发文件读银行账号 | `erp_db.py:6742-6753` | 银行账号天然属于**发薪流程**（L3 的出口在算工资侧） |
| 算工资页面现状 | `PayrollWorkflow.vue` —— **不含任何银行/身份证字段**，只显示「已生成工资台账与银行文件数据」 | 若迁过去**必须新建 UI**；不建，则迁移在用户视角「看不见」 |
| `/api/employees` 的消费方 | `employeeApi` 仅被 `EmployeeArchive.vue` 使用 | 接口拆分**不会波及其它模块**，改动面可控 ✅ |

## 三、三种方案对比

| 维度 | **A 物理迁移**（字段搬到算工资） | **B 逻辑迁移**（不动数据，改归属+入口） | **C 最小止血**（补三个真缺口） |
|---|---|---|---|
| 做法 | 拆表 `employee_payroll_profile` + 数据迁移；薪酬前缀改映射到新模块 | `hr_employees` 保留全字段，但**拆接口**：列表脱敏、完整值走独立单条端点；档案页「薪酬与账户」改为只读摘要 + 跳转，完整编辑落在算工资侧 | 显式列 + 掩码；`id_card`/`bank_account` 接现成加密；`hr_employees` 接 `_field_log` |
| **权限控制** | **不改善**（粒度仍是模块级，只换模块名）。除非同时引入字段级/新模块拆分 | **部分改善**：列表接口天然安全，完整值可挂更严的门 | **不改善**，但为改善留出结构 |
| **数据安全** | 收益依赖是否同时加密；**带迁移风险** | 中（读路径口径统一后才生效） | **直接命中 ①②③ 三条**，风险最低 |
| **操作流程** | 用户要在两个页面之间跳（或算工资页新建一整块表单） | 档案页看身份、算工资页管薪酬 —— **流程与业务心智一致**（人事归人事、发薪归发薪） | 流程不变，只多一次「查看完整值」的点击 |
| 改动面 | 大（拆表 + 迁移 + 全部读点 + 新 UI） | 中（接口拆分 + 两页 UI 调整 + 调用点收敛） | **小**（2 个接口 + 1 个 helper + 1 处接线） |
| 回滚 | 难 | 容易 | 容易 |
| 现在做的风险 | 中（当前空表，实际低，但结构改动大） | 低 | **极低** |

### 推荐顺序：**C 立即做 → B 作为结构方向 → A 不单独做**

理由：
1. **权限与位置是正交的两件事。** 隔离单位是**字段组**，不是页面。A 若不伴随模块拆分，就是「搬了个地方，门还是那道门」。
2. **C 的三条与归属决策无关** —— 无论最终字段放哪，明文、无留痕、`SELECT *` 都是错的，且**现在改是零数据风险**。先做 C 不浪费任何后续工作。
3. **A 里唯一有价值的部分，是把薪酬前缀从 `hr` 拆成一个更窄的模块**（见 3(b) 建议）—— 这部分可以独立于「字段搬家」实施，且不需要迁移数据。
4. **B 是 A 的正确轻量替身**：用户感知到的是「档案页不再暴露敏感值」，而后端不必承担拆表迁移的风险。

## 四、信息归属建议：按「信息域」分三层，不按页面分

不要问「这块 UI 放哪个页面」，要问「这组信息属于哪个**信息域**、谁有业务必要看、泄露后后果多大」。

| 层 | 内容 | 归属模块 | 应授权给 | 读出口设计 |
|---|---|---|---|---|
| **L1 身份层** | 姓名 / 工号 / 岗位 / 入职日期 / 在职状态 / 个人仓 | 宽（可留在 `hr`，或下放到 `data`） | 有业务必要的角色 | 列表接口全量返回，无掩码 |
| **L2 薪酬层** | 底薪 / 绩效规则 / 社保基数 / 公积金基数 | 新模块 `payroll` | 老板 + **会计** | 需显式进入算工资流程才读到 |
| **L3 实名与资金层** | 身份证号 / 开户行 / 银行账号 | 最严（留 `hr`，或 boss 专属） | **仅老板** | 单条读取 + 操作留痕 + 导出二次确认 |

### 🔴 最关键的一刀：**L3 必须与 L2 分开**

- 底薪泄露 = **商业信息泄露**（同行可比价、可挖人）；
- 身份证 + 银行账号泄露 = **可用于诈骗/盗刷的实名信息**（不可撤销、后果不可逆）。

现在它们绑在同一行、同一个接口、同一个权限里 —— **这是本次分析里最该拆的一刀**。
把 L3 和 L2 一起交给会计，等于为了让她算工资，把全公司的实名信息一并交出去。

## 五、访问控制建议（可执行）

### 5.1 先做（不依赖任何归属决策，零数据风险）

1. **`GET /api/employees` 改显式列 + 掩码**
   `SELECT *` → 显式列清单；`bank_account` 只回后 4 位、`id_card` 只回前 6 后 4。
   判据位置：`erp_db.py:6247`。
2. **完整值走独立单条端点**（如 `GET /api/employees/{eid}/sensitive`）
   单条、GET、过 `hr`、**每次读取记 `entity_change_logs`**。
3. **`hr_employees` 接 `_field_log`**
   改底薪 / 银行账号必须留痕（改前 → 改后）。
   ⚠️ **不要把敏感值本身写进日志** —— `db/queries/contacts.py:105` 已有先例
   （用加密前明文比较、但**排除 `SENSITIVE_FIELDS`** 防日志泄密），照抄即可。
4. **导出与枚举加约束**：`/api/salary-bank-file`、`/api/salary-slip/{eid}/{month}`
   至少先加留痕；可枚举/可批量导出的接口应限流或收为 boss 专属。

### 5.2 加密存量（趁现在 0 行）

- `id_card` / `bank_account` 走 `crypto_utils.encrypt_value`（AES-256-GCM，密钥派生自 `ERP_SECRET`）；
  `SENSITIVE_FIELDS` **已含 `bank_account`**，无需新造轮子。
- 🔴 **动手前必须先把全部读点找齐**：至少 `employee_list`（`erp_db.py:6247`，`SELECT *`）、
  `export_salary_bank_file`（`erp_db.py:6750`）、以及任何 `_get_employee` 的调用方 ——
  漏一处就是线上直接坏。**这是本轮唯一需要「先查全再动手」的改动。**
- 当前 0 行 ⇒ **无需迁移脚本、无需回滚预案**。这就是窗口期的价值。

### 5.3 让会计能算工资（这才是「迁移」的正解）

二选一，**必须选 (b)**：

- ❌ (a) 给 `accountant` 加 `hr` —— 会连带拿到身份证 + 银行账号 + 改角色能力，**不可接受**。
- ✅ (b) **新增 `payroll` 模块**，把薪酬类前缀从 `hr` 改映射到 `payroll`：
  `/api/payroll*`、`/api/salary-*`、`/api/social-insurance-config`；
  然后给 `accountant` 开 `payroll`（read + create）而**不给 `hr`**。

(b) 同时解决三件事：
① 让「需要会计算工资的租户」能算（**不是你的租户** —— 你已明确你公司会计不算工资；这是产品化的按客户差异需求，见 `02-…（修订）.md`）；
② 权限单元收窄到「只管发薪」，L3 敏感字段仍锁在 `hr` 里；
③ 前端「算工资」入口对相应角色**真正可用**（否则点进去只能 403）。

> 配套：`_PATH_MODULE_MAP` 是**前缀匹配、首个命中者优先**（`server.py:638`），
> 而 `/api/payroll-workflow` 等已存在于表中 —— 改动是**改既有条目的值**，不是加新条目；
> 加新条目还要注意前缀顺序（`/api/salary-*` 与 `/api/salaries` 可能互相抢先）。
> **必须同步 `_DEFAULT_PERMS`、`rows.py` 角色清单、前端 `constants/roles.js` 与角色护栏** ——
> 这是一次「角色/权限清单变更」，走 `hergent-role-registry-change` 那套 SOP（28 条护栏）。

### 5.4 原则：前端永远不是边界

菜单隐藏、区块隐藏、`v-if` 判断 —— 都只是 UX。
本项目的判定链只有一条有效的：**中间件（前缀→模块→动作）→ 业务函数**。
任何「只在前端做」的权限设计，等于没有。

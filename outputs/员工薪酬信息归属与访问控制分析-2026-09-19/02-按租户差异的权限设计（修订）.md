# 02 · 按租户差异的角色权限 —— 现状核查与修订设计

> 承接 `01-分析报告.md`。
> 触发：你答复「**我的公司会计不能算工资，也看不到别人的工资，但有的客户是会计可以算工资**」。
> 这句话把问题从「敏感信息放哪个页面」升级成「**权限表必须按租户分叉**」—— 于是我去核了「按租户配置」这件事到底成不成立。
> **核查日期**：2026-09-19 ｜ 全部结论附代码锚点与生产实测，可复核。

---

## 一、结论先行

**你的要求今天做不到 —— 不是因为缺 UI，而是因为「角色 → 模块权限」这张表是「全平台一份」，存在主库。**

⇒ 一旦给某个客户开「会计能算工资」，**你自己的会计也会立刻能算**。反过来说，你为了保住自己而把会计收回，客户的会计也跟着一起不能用。两边共用一把锁。

**好消息**：代码里本来就有「租户库一份 role_permissions」的表和迁移，方向是对的（v110 注释白纸黑字写着「收敛方向 = 以租户库为准」），只是**读写路径锁在了主库**，导致那份租户数据从来没被读过。所以这不是重做，是**接线**。

---

## 二、决定性证据（4 条，均可复核）

### 证据 1（实测）：同一个权限接口，换租户头，返回**逐字相同**

同一令牌分别带 `X-Tenant-Id: 1 / 9 / 10` 请求 `GET /api/role-permissions`：

```
X-Tenant-Id: 1  → 8 个角色  accountant=['dashboard','accounts','reports','marketing']
X-Tenant-Id: 9  → 8 个角色  accountant=['dashboard','accounts','reports','marketing']
X-Tenant-Id: 10 → 8 个角色  accountant=['dashboard','accounts','reports','marketing']
```

三次响应**完全一致**。租户头对这个接口没有任何影响 ⇒ 它读的不是「你这个租户的」权限。

### 证据 2（代码）：权限接口被登记为「主库专属」

| 位置 | 内容 |
|---|---|
| `server.py:50-51` | `_TENANT_MASTER_PREFIXES` 里含 **`/api/role-permissions`** |
| `server.py:87-92` | 命中该前缀 ⇒ `db.set_tenant_context(None)` ⇒ `get_db()` 落到**主库 `erp.db`** |
| `server.py:597` | 同时它在 `_PATH_MODULE_MAP` 里映射到 `hr`（所以只有 boss/admin 能用） |
| `erp_db.py:2011` | `get_all_role_permissions()` 用 `get_db()`（**租户感知**）读 `role_permissions` |
| `core.py:394/406` | `_load_perms()` 在 **import 时**执行（此刻无租户上下文 ⇒ 主库） |
| `core.py:408` | `reload_perms()` 只在**保存权限**时被调用（三处，`server.py:940/950/987`） |
| `core.py:450/455` | `_check_perm` 读的是**进程级全局** `ROLE_PERMS` —— 它拿不到、也不看当前租户 |
| `db/connection.py:80/277` | 租户上下文是 `ContextVar`（每请求正确），但 `_check_perm` 根本没用它 |

**关键错配**：中间件在 `server.py:679` 调 `_check_perm` 之前，**已经**在 `server.py:109/125` 正确设好了租户上下文 —— 而 `_check_perm` **无视它**，去读一个全局。

### 证据 3（实测）：租户库那份 `role_permissions` 是**死数据**

生产实际内容：

| 库 | `role_permissions` 行 |
|---|---|
| `erp.db`（主库） | 1 行：`supervisor = ["data","dashboard"]` |
| `tenant_1.db` | 2 行：**`库管` = ["dashboard","stock","data"]**、`supervisor` |
| `tenant_9.db` | 1 行：`supervisor` |
| `tenant_10.db` | 1 行：`supervisor` |

而证据 1 的接口返回里**根本没有「库管」**。⇒ 这一行**既读不到、也改不了**（接口读主库、写主库）。
它是 `erp_db.py:17045` 那次 v110 一次性迁移（master → tenant，`INSERT OR IGNORE`）留下的痕迹 —— **迁移的意图（以租户库为准）从未真正落地**。

### 证据 4（顺带确证）：不是「串味泄漏」，是「能力缺失」

因为读路径与写路径**都锁在主库**，系统内部是**自洽**的 —— 我最初的怀疑（保存后全局被某租户覆盖、波及他租户）**不成立**，特此更正。
真正的缺陷是：**租户级差异无处安放**。这不是安全事故，是产品能力缺口。

## 三、对账你的两条要求

| 要求 | 现状核查 | 判定 |
|---|---|---|
| **我的会计不能算工资** | `accountant = [dashboard, accounts, reports, marketing]`，无 `hr`；而 `/api/payroll-workflow`、`/api/payroll*`、`/api/salaries`、`/api/salary-*`、`/api/social-insurance-config` **全部** → `hr` ⇒ 请求在中间件就 403 | ✅ **已满足**（默认即如此） |
| **会计看不到别人的工资** | 同上，无 `hr` ⇒ 连自己的工资条也拿不到 | ✅ **已满足** |
| **客户的会计可以算工资** | 权限表全平台一份，**没有按租户配置的位置** | 🔴 **做不到** —— 需改造 |
| （隐含）会计应能看**自己的**工资条 | `/api/salary-slip/{eid}/{month}`（`server.py:4928`）与 `/api/payroll/payslip/{eid}`（`routers/hr.py:204`）**无自我作用域**，只按 `hr` 判；员工拿工资条靠 `routers/salary_send.py` **推送**，不是自助查询 | ⚠️ **缺口** |

## 四、必须如实说明：一个与上一轮改动相关的连带缺陷

tenant_1 的 `库管` 角色已确认是**孤儿**：

- 不在 `ROLE_PERMS`（来自主库）⇒ `_check_perm('库管', …)` 命中空表 ⇒ **零权限僵尸账号**（能登录、每个模块都 403）
- 而 2026-09-19 刚上线的角色白名单（`core.normalize_role`，判据 = `known_roles() = _DEFAULT_PERMS ∪ ROLE_PERMS`）会**直接 400 拒绝**派发 `库管`
- **当前无实际影响**：生产 `users.role` 只有 `admin / boss / sales / supervisor`，无人使用 `库管`
- 但它说明：**白名单的判据来源本身被这个缺陷污染**。修好 P0 后 `库管` 会自动回到 `ROLE_PERMS`，白名单随之变正确 —— 不用单独补

> 另：`user_tenants.role`（值 `admin` / `member`）**不参与任何鉴权** —— `check_user_tenant`（`erp_db.py:4442`）与 `get_user_tenants`（`:4458`）只查 `user_id` / `tenant_id`。
> 那是一列**成员关系元数据**，别误当成「按租户角色」的机制。

## 五、另发现：字段级权限表**有表、有 API、无人消费**

`field_permissions(role, module, field_name, can_view, can_edit)` 每租户一张（`erp_db.py:8783` 建表），
tenant_1 里有一条**真实配置**：`('sales', 'product', 'purchase_price', 0, 0)` —— 说明有人认真配过。

但全仓**只有** `routers/platform.py:573/577` 的 GET/POST 读写它（平台管理员 API）；
`GET /api/products`、`GET /api/employees` 等**没有任何读路径**调用 `get_field_permissions` 过滤字段。

⇒ 这是「**配置能改、但不生效**」的典型。**不要把它算作已有能力**。
（这也解释了为什么 L3 敏感字段现在只能"要么全给、要么全不给"。）

---

## 六、修订后的设计（三档，按顺序）

### P0 — 让权限表按租户分叉（地基，必须先做）

- 把 `/api/role-permissions` 从 `_TENANT_MASTER_PREFIXES`（`server.py:51`）**移出** —— 它本该读**当前租户**的库，这正是 v110 的原意
- `core.ROLE_PERMS` **不能再是单值全局**：改成按租户缓存（`{tenant_id: perms}` + TTL）或按请求取
- 迁移：把主库那份作为「默认覆盖」下发到需要的租户；`库管` 这类孤儿行随之复归
- 兜底：租户库缺表/缺行必须 **fail-safe 回落** `_DEFAULT_PERMS` —— 否则一个坏库 = 该租户全员 403
- 🔴 **不做 P0，P1 的差异化对客户无效**（给客户加了 `payroll`，你自己也一起加上了）

### P1 — 拆出 `payroll` 模块（让「能算工资」≠「能看实名与银行」）

把「算工资所需」的前缀从 `hr` 改映射到新的 `payroll`：

```
/api/payroll-workflow  /api/payroll*  /api/salary-batch-calculate
/api/salary-save       /api/salary-summary  /api/social-insurance-config
```

**`/api/employees` 保持 `hr`**（身份证 / 开户行 / 银行账号 都在里面）。

| 租户 | `accountant` 配置 | 结果 |
|---|---|---|
| 你的（tenant_1） | 不加 `payroll` | 维持现状：算不了工资 ✅ 符合你的要求 |
| 某客户 | 加 `payroll` | 能算工资，但**拿不到身份证与银行账号** ✅ 安全 |

⇒ 这一步是「按客户差异化」能**安全**成立的前提。否则差异化 = 把 L3 实名信息一并送出去。

### P2 — 补自我作用域（小而必做）

`/api/salary-slip/{eid}/{month}` 与 `/api/payroll/payslip/{eid}`：无 `payroll` / `hr` 时**只允许 `eid` == 自己**。

⇒ 否则一旦某客户给会计开了 `payroll`，该会计就能按 `eid` + 月份**枚举全公司工资**。
⇒ 顺带解决「员工能不能查自己工资条」这个公开缺口。

### 不建议：把 `field_permissions` 当主手段

虽然它现成且「更细」，但字段级过滤要在**每一个出参点**记得滤 —— 易漏、难审计（今天它就已经空转）。
**模块级拆分是硬边界，先做硬边界。**

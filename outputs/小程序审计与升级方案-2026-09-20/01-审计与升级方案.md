## 〇、一句话结论

**这份代码的质量明显高于「未上线的小程序」的平均水平** —— 分页竞态、购物车按门店分键持久化、401 复核防误踢、幂等覆盖、停售/厂价双闸门、隐私四件套，这些通常要踩过坑才会补。**不要推倒重来。**

真正的风险不在代码里，在**三处「声明与实现不一致」**，而且**其中一处会直接挡住提审**：

| # | 问题 | 严重度 | 一句话 |
|---|---|---|---|
| **①** | **提审用的两个测试账号，在系统里没有任何门店可见范围** | 🔴 **提审硬阻断** | 审核员登进去选不到门店 ⇒ 提交预报必然失败 ⇒ 大概率判「功能不可用」 |
| **②** | **3 类角色（会计 / 导购 / 司机）能登录，但每个页面都 403** | 🔴 上线即投诉 | 员工档案里能把人设成这些角色，设完他拿到账号登录 = 一片空白 |
| **③** | 会计**看得见**「汇总总表」入口，**点进去必报错** | 🟠 | 前端收它、后端不收它 —— 两层判据不一致 |

第 ② ③ 条是**地雷**不是已爆：生产 6 个账号里没有这三种角色。但**地雷的排法不因当前没人踩而改变**。

## 二、问题清单

> 每条都给出「哪一行没做到」。✅ = 已核对有；❌ = 已核对没有。

### 🔴 P0 —— 提审 / 上线前必须解决（不解决 = 白跑一趟）

#### P0-1【提审硬阻断】两个提审测试账号取不到任何门店

**判据（一条命令可复现）**
```bash
curl -s https://erp.hergent.cn/api/forecast-submissions/stores \
  -H "Authorization: Bearer <mptestsp 的 token>" -H 'X-Tenant-Id: 1'
# 实测返回：{"ok":true,"stores":[]}      ← 空数组
```

**根因链**
1. `users.employee_id = 0` 且 `employee_code = ''`（**两个关联列都空**）⇒ `resolve_employee_id(u)` 返回 `0`（`erp_db.py:6237-6252`）。
2. `/stores` 里 `emp_id = 0` 且角色不是 boss/admin ⇒ 直接 `return []`（`forecast_submissions.py:581-587`）。
3. 前端拿到空门店 → 门店选择器显示「选择门店」→ 提交时 `_doSubmit` 判 `!store.id` → toast「请先选择报单门店」（`fill.js:543-546`）⇒ **死路，且没有任何解释**。

**为什么会有 `employee_code=''` 这种状态**：这两个账号建于 2026-08-30，当时 `staff_account_create` 还会写 `employee_code='9001'` 这类值；2026-09-15 该函数改为**只写 `employee_id`、停写 `code`**（`erp_db.py` 注释自陈），存量 `code` 被清理后就**两列全空** ⇒ 连兼容读（`_emp_link_expr` 会兜数字型 `employee_code`）都救不回来。

**连带问题**：同一条链上，`emp_id = 0` 会让**门店越权校验整段跳过**（`forecast_submissions.py:50` 的 `if emp_id > 0:`）—— 这是代码注释里自己记录过的 fail-open。

**影响**：`mptest` 完全无法填报；`mptestsp` 只能看汇总（实测 200）。**审核员用这个账号走不完主流程。**

#### P0-3【假入口】会计看得见「汇总总表」，点进去必报错

**两层判据不一致**（**实测已证明两层各自独立生效**）：

| 层 | 判据 | accountant 的结果 |
|---|---|---|
| 前端 | `isApprover(role)`，名单 `['admin','boss','accountant','supervisor']`（`utils/roles.js:25`） | ✅ **放行** ⇒ 「我的」页 `canManage=true` ⇒ **显示入口** |
| 前端第二道 | `summary.js:12` 同一个 `isApprover` | ✅ 放行 ⇒ 不显示「无权限」页，直接发请求 |
| 后端中间件 | `/api/forecast-submissions` → `data` 模块 | ❌ **403** |
| 后端路由 | 硬编码 `("admin","boss","accountant","supervisor")`（`forecast_submissions.py:273`） | ✅ 放行（但根本到不了这里） |

**结果**：会计点进去看到空表格 + 一条 toast「权限不足：你的角色'accountant'不能访问data模块」。

**实测对照**（证明后端两层确实独立）：
```
mptestsp (supervisor, 有 data) → /summary → HTTP 200
mptest  (sales,     有 data) → /summary → HTTP 403（被路由内角色名单挡下）
```

`utils/roles.js:19-24` 的注释里**已经记录了这个矛盾**（「两处后端判据互相矛盾，尚未修」），并选择"保持原样等待后端拍板"。本轮把它列入 P0，因为它就是**入口可见但必报错**这一类缺陷。

### 🟠 P1 —— 上线首月会痛

#### P1-1 退出登录不销毁服务端会话
`mine.js:83-104` 的 `logout()` 只清本机 storage + `globalData`，**从不调 `/api/auth/logout`**（全仓 `auth/logout` **0 命中**）。后端 `/api/auth/logout` 本来是会删 `sessions` 行的（`auth.py:239-256`）。
⇒ 用户点了「退出」，那枚 token 在服务端**仍然有效最长 24 小时**。同一问题在 `privacy-settings.js:36-71` 的「撤回同意」里重复了一遍。

#### P1-2 撤回之后，填报页仍然显示「本期已报」
`mine.js:60-82` 撤回成功后只 `this.load()`（刷新自己的列表），**不清理填报页用的本地快照**。
而填报页的「本期已报」回执与重复提交拦截，读的是 `fs_sub_<店id>_<期次id>`（`fill.js:255-258, 552-566`），**它们不会被撤回动作触及**。
⇒ 员工撤回后回到填报页，看到「✓ 本期已报 N 项」，再提交还会弹「本期已报过…再提交会新增一单，确定继续？」—— **一句不成立的警告**。用户若信了，就会**多报一单进汇总** ⇒ 采购量偏大。

#### P1-3 「断网自动补传」是半截能力
| 声明 | 实现 |
|---|---|
| WXML 横幅：「网络已断开，数据已存本机，**恢复后自动补传**」（`fill.wxml:57`） | 触发条件是 `pendingSubmit && cartCount && !offline`（`fill.js:80`） |
| | ❌ `pendingSubmit` **只存在于 `data`**，`setStorageSync` 的全部键里**没有它**（`fill.js` 全文 15 处 `setStorageSync` 已逐条核对）⇒ **杀进程/切后台后丢失** |
| | ❌ `onNetworkStatusChange` 回调里只有 `restoreCart()`，**没有 `resumeDraft()`**（`fill.js:43-53`）⇒ 用户停在填报页时网络恢复，不会自动补传 |

⇒ 真正能自动补传的只有一种情形：**不重启应用、且页面重新可见**。购物车确实落盘了（不丢数据），但「自动」二字兑现不了。

#### P1-4 汇总页是「单日」口径，Web 是「期次」口径
`summary.js:21` 只传 `date`，**从不传 `period_id`**。
后端的 `period_id` 是 2026-09-12 专为「期次窗口重叠导致重复计入」加的精确归属口径（`erp_db.py:16799-16801`）。
⇒ 只要出现**跨日期次**，主管在小程序看到的「本期合计」与老板在 Web 看到的**不是同一个数**。生产已有跨日期次（期次 #9：2026-08-30 ~ 2026-09-15）。
另外：日期选择器初值为空 ⇒ 后端默认**今天**（`erp_db.py:16810-16812`）；而期次 `order_start` 常常不是当天（如 #14 是 09-19）⇒ 主管默认进来大概率看到「今天还没有预报提交」。

## 四、具体改进方向

### ✅ G1 / P0-1：让提审账号真能报单（3 步）

| 步 | 动作 | 落在哪 | 风险 |
|---|---|---|---|
| 1 | 在**员工档案新建一个真实员工**（如「微信审核-销售」「微信审核-主管」），或复用现有员工 | Web 端操作 | 零 |
| 2 | 在**报单配置**（新真源 `report_mapping`）给他们各配 1~2 家门店 | Web 端操作 | 零 |
| 3 | **通过员工档案的「开通账号」重开账号**（走 `staff_account_create`，它会强制要求真实员工、并写 `employee_id`）—— 而不是手工改库 | Web 端操作 | 零 |

> ⚠️ 现有 `mptest` / `mptestsp` 的 `employee_id` 是 0，**建议不要手工补列** —— 手工补会绕过「必须先有真实员工」这道闸（`erp_db.py::staff_account_create` 里专门加了这道闸，注释写明"生产上 `employee_code='9001'/'9002'` 这类脏值正是这么来的"）。**走正规路径重开**，验证完再删旧账号。

**同时补一条前端兜底（代码改动，很小）**：门店列表为空时，不要只让选择器空着 —— 显示一段说明：
> 「你还没有被配置报单门店。请联系管理员在『报单配置』里把你的门店加上。」

依据：现在是**空选择器 + 一个说不清原因的 toast**，用户与审核员都不知道该找谁。这正是「单向门」的反面 —— **只进不出的约束最坏**，所以必须给出解锁动作。

### ✅ G2 / P0-2 + P0-3：把「角色死路」与「假入口」一次修干净

**改动点只有两处，但需要你先做一个业务决定：**

**决策题：导购 / 司机 / 会计，要不要能报单？**

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 补权限**（给 `guide`/`driver`/`accountant` 加 `data`） | 改 `core._DEFAULT_PERMS` 一行 ×3 | 这些人立刻能报单 | 权限面扩大：`data` 模块还管着 `/api/products`、`/api/import`、`/api/export` 等 —— 他们会顺带拿到这些读权限 |
| **B. 明确关门**（小程序端按权限判角色，无权限进「无权限」页 + 说明找谁） | 前端 +1 个页面分支 + 复用 v206 刚做的 `/api/auth/permissions` | 零权限扩散；用户知道发生了什么 | 这些人确实用不了小程序 |
| **C. 两者都做**（先用 B 兜底文案，业务确认后再对真正需要报单的角色用 A 精确放权） | 先 B 后 A | 风险最低 | 两步 |

**我的建议：先 C，落地顺序 B → A。** 理由：① `data` 是个**宽模块**，用它来实现"能报单"是拿大炮打蚊子，历史上已经因为这种事拆过一次窄模块（`payroll`）；② 你现在还不知道到底哪些岗位会用小程序（生产真实使用才 2 次），**先让系统诚实地说"你不能用、去找谁"，比先放开权限再收回安全得多**；③ B 是纯增量、可逆。

**P0-3 的修法（与 B 同一批做）**：把「哪些角色能看汇总」的判据**收敛成一处**。
- 现状：前端 `APPROVER_ROLES`（`roles.js:25`）+ 后端路由硬编码名单（`forecast_submissions.py:273`）+ 后端 `_DEFAULT_PERMS` 的 `data` —— **三处**。
- 目标：**前端只问后端**「我能看到哪些模块」（`GET /api/auth/permissions`，v206 刚在小程序外的 Web 端接好线），用 `data` 是否授权 + 一个「汇总」子判据决定入口显隐；后端路由名单改成从同一处派生。
- 验收：会计在「我的」页**看不到**汇总入口；若给他 `data`，入口出现且点进去 200。

## 五、优先级与推进顺序

```
① P0-1 提审账号（配置 3 步 + 前端空门店引导）        ← 不解决，提审白跑
   ↓
② P0-3 假入口（会计入口显隐，判据收敛）              ← 与 ③ 同一批，改动小
   ↓
③ P0-2 角色死路（先 B 文案兜底，再按你的决定上 A）
   ↓
④ P1-1 退出销毁会话 ⑤ P1-2 撤回清快照 ⑥ P1-3 真自动补传   ← 一批做，都是"说法要对得上行为"
   ↓
⑦ P1-4 汇总按期次                                    ← 要后端配合但改动小
   ↓
⑧ P2-2 埋点 → P2-1 拆文件 → P2-3/4/6/7              ← 上线后按真实数据驱动
```

**排序理由**：前 3 项决定「提审能不能过、上线后会不会立刻被投诉」；第 4~7 项是「用户骂不骂你」；第 8 项是「你以后改得快不快」—— 而它**依赖埋点先有数据**，所以埋点排在其他 P2 之前。

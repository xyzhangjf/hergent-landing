# 期次「复制」与空表列展示 —— 调整方案

**日期**：2026-09-17　|　**性质**：设计可行性评估 + 具体调整思路（**未改动任何代码/数据**）
**前置**：本方案**取代** `期次数据流程优化方案-2026-09-17.md` 的 §五（建议流程）中
「新建期次对话框里做三选一」的设计 —— 改成**在往期预报列表上直接指着某一期点「复制」**。
其余结论（四桶矩阵 / 闸门 / `origin` 列）**继续有效**。

---

## 结论：两点都可行，而且第 2 点你抓到的是一个**真缺陷**

| 你的提案 | 判定 | 关键理由 |
|---|---|---|
| ① 往期列表加「复制」，复制后改名称即可用 | ✅ **可行，且优于我上一轮的方案** | 选源 = **指着一期**，比抽象三选一直观；点「复制」本身就是意图声明 |
| ② 创建期次后要展示「不可删除的列行」 | ✅ **可行性 = 真缺陷** | 只读态 0 行时空态**把整张表（含列头）整个替换掉** ⇒ 连列头都没有，右键都点不到 |

⚠️ 但 ① 里「**仅需修改名称即可使用**」这一句**不能照做** —— 只改名称会串数据。见 §一。

## 一、🔴 「只改名称」不够 —— 归属键是窗口，不是名称

| 桶 | 归属键 |
|---|---|
| 报单明细 `forecast_submissions` | `period_id`（兼容 `period_id=0` + `order_date` 区间） |
| **加单 `forecast_extra_qty`** | 🔴 **`(period_start, period_end, product_id)`** |
| **定稿 `forecast_audit_decisions`** | 🔴 **`(period_start, period_end)`** |

证据：`routers/forecast_submissions.py:462`、`erp_db.py:15200`。

**如果复制出来的新期次沿用旧窗口**（完全重叠）：

1. v180 刚加的「窗口重叠」软警告会响（说明这确实会发生）
2. 🔴 更严重：**两期会共用同一份加单与定稿** —— 因为它们的键是窗口，不是期次。同屏不会报任何错。

### ✅ 解法成本极低：把「名称 → 日期」设为默认联动

v180 已经做好了这两件工具（`Forecast.vue`）：

- `parsePeriodDates(text)` —— 从「9月15日报单-9月19日到货」这类名称里解析出日期
- `applyPeriodDates(dates, force)` —— 把解析到的日期写进表单，`force=true` 时无视「手改保护」

而**期次名的习惯本来就是带日期的**。所以只要在复制弹窗里：

- 名称**预填原名 + 自动全选**（点进去直接打字即覆盖）
- 名称 → 日期走 **`force` 联动**（新期次没有「手改保护」的需求）

⇒ 用户改名称里的日期，窗口自动跟着变 —— **真的做到「仅需修改名称」**，而且不牺牲正确性。

## 二、🔴 第 2 点：空态把整张表吞掉了（这是真缺陷）

`Forecast.vue` 表体的渲染链（557–744）：

```html
<div v-if="crossLoading" ...>                              ← 加载骨架
<div v-else-if="!editMode && (!cross.rows.length || …)"     ← 561  只读态空：整块空态
<div v-else-if="!editMode" class="grid-area">               ← 570  只读态表格
<div v-else class="grid-area">                              ← 744  编辑态表格（v-else = 无条件渲染）
```

| 状态 | 表头（含不可删除列）可见？ |
|---|---|
| 只读态 + 有行 | ✅ |
| **只读态 + 0 行** | 🔴 **整张表不渲染 —— 连列头都没有** |
| 编辑态（任意行数） | ✅ 无条件渲染 |

**这就是「创建期次后看不到列」的真相**：新期次零引用 ⇒ 只读态走空态 ⇒ 表没了。
用户被迫先点「改单」进编辑态才能看到表 —— 这也正好解释了他为什么会把「改单」当成查看入口。

**「不可删除」这个概念今天只存在于列右键菜单里**（`Forecast.vue:1530`：
「该主档列不可删除（可在列设置中隐藏）」），而**右键要点在列头上** ⇒ 空期次里这个概念
**完全不可达**。

### 不可删除的列的权威口径（核实结果）

| 层 | 内容 |
|---|---|
| 服务端**唯一权威** | `forecast_columns.PROTECTED_COLUMNS` —— 恰好 5 个：`name` / `barcode` / `sale_price` / `dist_price` / `product_code` |
| 前端**实际展示口径** | **4 个**：商品名称 / 条码 / 分销价 / 厂家编码（`sale_price` 已在 v177 从主表下线，属惰性残留） |
| 前端降级兜底 | `MASTER_COL_DEFS[].deletable`，**仅在注册表拉取失败时**用，且降级必 toast |

⚠️ **列是全局的、不按期次**（`MASTER_COL_DEFS` 是唯一渲染源，派生 5 个面）。所以列**不需要「复制」** ——
它本来就在，只是空态下**看不见**。

## 三、调整思路（具体）

### A. 往期预报：把「修改」扩成「复制 / 修改」

现状 4 个按钮（`ForecastHistory.vue:35-42`）：`查看` `修改` `关闭` `删除`

**改为**：`查看` · **`复制`** · `修改` · `关闭` · `删除`

| 按钮 | 可见条件 | 说明 |
|---|---|---|
| **复制** | 🔴 **`Number(row.id) > 0`** —— 所有**真实**期次都可点，**不限 open** | 复制的**源**可以是已关闭期次 —— 这正是「复制满意的那一期」的场景 |
| 修改 | `row.status === 'open' && id > 0` | v180 语义不变 |
| 关闭 / 删除 | 现状不变 | |

⚠️ **必须屏蔽合成行（`id < 0`）**：`GET /api/forecast/order-board` 的 `board` 里含合成期次
（如「2026-07-24 报单」），它们**没有 `forecast_periods` 记录**，没有 id 可引用。
现有「关闭/删除」已经用 `Number(row.id) > 0` 处理过这个坑，复制必须同样处理。

> 📌 顺带说明：**当期也在这个列表里**（`status='open'` 显示「进行中」）。
> 所以「照着当前这一期建下一期」这个最高频动作，在这里可以一步完成。

**点「复制」→ 弹窗**（复用 v180 的 `.pe-modal` 范式）：

```
复制自：9月15日报单-9月19日到货（已关闭）

  期次名称   [9月15日报单-9月19日到货        ]   ← 预填原名 + 自动全选，直接打字覆盖
  下单开始   [2026-09-15]   下单截止 [2026-09-15]   预计到货 [2026-09-19]
             ↑ 与名称默认联动：改名称里的日期 → 这里自动跟着变

  顺延：[+7 天]   ← 一键把三个日期整体后移（可选便捷项）

  ────────────────────────────────────────────────
  将带过来：154 个商品（不含报单数量、加单、定稿）
  ⚠️ 同名 / 窗口重叠软警告（v180 已实现，直接复用）
  [取消]  [创建并复制]
```

**校验沿用既有实现，不写第二份**：硬规则（名称非空 / 窗口不反向 / 到货不早于下单截止）走
后端 `period_validate`；软警告（同名 / 窗口重叠）走前端 v180 的 `periodSoftWarn()`。

### B. 创建期次后：把表渲染出来，别让空态吞掉列

**改法**：把 561 的空态从「**替换整张表**」改成「**表格里的一行**」。

| | 现在 | 改后 |
|---|---|---|
| 0 行时的表头 | 🔴 完全没有 | ✅ 正常渲染（含不可删除列，列设置/右键全部可用） |
| 0 行时的表体 | 整块空态 div | 表体内**一行**：「本期还没有商品行」+ 三个动作 |
| 「不可删除」可达性 | 需先点「改单」 | ✅ 直接右键列头就能看到说明 |

表体内那一行给三个动作（正好对应三条填数路）：

```
本期还没有商品行
  ［从上一期复制］   ［下载模板导入］   ［显示全部在售商品（285）］
```

> 📌 这同时解决了上一轮讨论的「新期次是空表」问题，而且**比在新建对话框里做三选一更省事**：
> 表就在那儿，用户**看着表**选，而不是先做一道抽象选择题。

### C. 与这两点强相关的两件事（不做会互相拖累）

| # | 事项 | 为什么必须一起做 |
|---|---|---|
| 1 | **`createPeriod()` 末尾补表格重载**（`Forecast.vue:6722`，**1 行**，复用期次切换的唯一收口） | 否则点完「创建/复制」表格还挂着**上一期**的数据 ⇒ 用户会以为复制没生效。这正是昨天那次事故的根因 |
| 2 | **登记台账加 `origin ∈ {import, seeded}`**（幂等 ALTER） | 让「复制来的清单」与「导入来的清单」可区分；导入时才敢「替换本期清单」。否则「复制 154 + 导入 159 = 275」会**复活老 bug** |
| 3 | 复制成功写留痕 `period_copy`（复用 `_audit_period_op`） | 与 v180 的 `period_update` 同族，让「这期清单从哪来」可查 |

### D. 本次要动的文件（预估）

| 层 | 文件 | 改动 |
|---|---|---|
| 后端 | `server/erp_db.py` | 新增 `forecast_period_copy(src_pid, name, order_start, order_end, arrival)`：建期次 + 复制 `forecast_import_products`（打 `origin='seeded'`），**不碰**报单/加单/定稿/付款；登记台账补 `origin` 列（幂等 ALTER） |
| 后端 | `server/routers/forecast.py` | 新增 `POST /api/forecast/periods/{pid}/copy`（复用 `period_validate` + `_audit_period_op`） |
| 前端 | `src/pages/ForecastHistory.vue` | 加「复制」按钮 + `copy` emit（`id > 0` 才显示） |
| 前端 | `src/pages/Forecast.vue` | 复制弹窗（复用 `.pe-modal`）+ `createPeriod()` 补重载 + **空态改为表内一行** + 表内三动作 |
| 前端 | `src/api/modules.js` | 加 `copyPeriod: (pid, body) => api(..., { method: 'POST', body })` |

## 四、需你确认（3 条）

1. **「复制」对已关闭期次开放吗？** —— 我建议**开放**（源可以是任何真实期次，你要的就是「复制满意的那一期」）。
2. **复制时窗口默认怎么给？** —— 我建议：① 默认**按名称解析**（用户改名称里的日期即变）；
   ② 另给一个「顺延 N 天」的便捷按钮。要不要**默认就顺延**（比如默认 +7 天）？
   若默认不顺延，新窗口会与原期完全重叠 —— 靠用户改名来改，但**改名前那一刻是重叠状态**。
3. **工具栏的「新建期次」要保留吗？** —— 往期列表有了「复制」之后，两个入口有部分重叠。
   我建议**都留**：工具栏「新建期次」= 从零开始；往期「复制」= 有源。
   若你希望彻底简化，也可以只留「复制」，但那会**失去「从零建期次」的入口**（复制一个空期次也能达到，只是多一步）。

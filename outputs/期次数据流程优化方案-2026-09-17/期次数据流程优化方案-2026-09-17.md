# 期次数据流程优化方案

**日期**：2026-09-17　|　**触发**：用户提案「导入前必须先建期次 + 按新老用户区分清单来源」
**性质**：设计评估 + 流程方案（**未改动任何代码、未改动任何生产数据**）
**关联**：`outputs/改单取消后空表-排查结论-2026-09-17/`（昨天的同类事故，本方案是它的根治）

---

## 摘要

| 用户提案 | 判定 | 一句话理由 |
|---|---|---|
| ① 必须先点「新建期次」才能导入 | ✅ **强烈支持** | 归属在导入那一刻定死、事后不可回填 ⇒ 必须在写之前把闸门关上 |
| ② 新用户建期次后「预制模版已显示」 | ⚠️ **部分成立** | 只对「已有商品档案」的租户成立；全新租户 0 档案，没东西可预制 |
| ③ 老用户建期次后**自动**复制上期基础数据 | ⚠️ **改为「默认勾选 + 可见 + 可撤销」** | 「静默自动」的继承不可追溯、错了会逐期继承（详见 §四-3） |
| ④ 导入后自动覆盖已有基础数据 | 🔴 **必需，但今天没做到** | 登记台账 `INSERT OR IGNORE` + `UPDATE`、**全仓无 DELETE** ⇒ 会复现「模版 159 → 系统 275」老 bug |

**两个必须先纠正的前提**：

- 🔴 **「基础数据」不是一个东西，是四个桶**（§二）。它们的**归属键不同**——有两个用的是「日期窗口」而不是期次 ⇒ 无脑复制会让两期共用同一份加单/定稿。
- 🔴 **「新建期次后表格里还有上一期的数据」这件事今天就会发生**，但它**不是复制，是残留**（`createPeriod()` 不重载表格）。**把这个 bug 扶正成需求，会把一个错的实现固化下来**（§三）。

## 一、先把三个概念拆开（它们现在被混着说）

| 概念 | 含义 | 现状载体 |
|---|---|---|
| **期次归属** | 这份数据算哪一期的 | `forecast_submissions.period_id`、`forecast_import_products.period_id` |
| **行底 / 商品清单** | 这一期表格上**有哪些商品行** | 登记台账 ∪ 有报单 ∪ 手工补录行（`buildRowBase`） |
| **报单数量** | 业务员报了多少 / 加单 / 定稿 | `forecast_submission_items.quantity`、`forecast_extra_qty`、`forecast_audit_decisions` |

你说的「复制基础数据、不复制报单数据」，准确翻译是：**只复制「行底」中的「登记台账」这一个桶，不复制「数量」及衍生桶**。

## 二、🔴 关键发现：「基础数据」是四个桶，而且有两个的键不是期次

| # | 桶 | 表 | **归属键** | 该复制吗 |
|---|---|---|---|---|
| A | 商品清单（导入登记） | `forecast_import_products` | ✅ **`period_id`（真按期次）** | ✅ **该复制 · 唯一该复制的** |
| B | 报单明细（业务员报的量） | `forecast_submissions` + `_items` | ✅ `period_id`（兼容 `period_id=0` + `order_date` 区间） | ❌ 不复制 |
| C | 加单 | `forecast_extra_qty` | 🔴 **`(period_start, period_end)` 日期窗口** | ❌ 不复制 · **窗口重叠会串期** |
| D | 定稿 | `forecast_audit_decisions` | 🔴 **`(period_start, period_end)` 日期窗口** | ❌ 不复制 · 同上 |
| E | 客户列 / 户头配置 | `report_mapping` · `business_profile` | **全局，根本不按期次** | — 无需复制（本来就在） |

实现证据：
- C：`routers/forecast_submissions.py:462` → `ON CONFLICT(period_start, period_end, product_id)`
- D：`erp_db.py:15200` → `DELETE FROM forecast_audit_decisions WHERE period_start=? AND period_end=?`
- E：`routers/import_router.py::download_template_file` 的客户列来自 `report_mapping.report_alias`

**为什么这条最要紧**：C / D 的键是**窗口**，不是期次。v180 刚给「新建期次 / 改期次」加了「窗口重叠」软警告——说明重叠是**真会发生**的。一旦有重叠，两期会**共用同一份加单与定稿**，而同屏不会报任何错。

⇒ **「复制」的边界必须逐桶定义。只能复制 A，其余一律不复制。**

## 三、🔴 第二个关键发现：你看到的「延续」是 bug，不是特性

你描述的「老用户点新建期次后自动复制上一期基础数据」——**这个现象今天就会发生，但它的成因不是复制**：

```js
// Forecast.vue:6715  createPeriod()
await forecastApi.createPeriod(b)
toast('期次已创建', 'success')
showNewPeriod.value = false
await loadPeriods()          // ← 只刷了期次下拉，**从不重载表格**
```

而 `loadPeriods()` 内部会把 `curPeriod` 改成新期次（下拉跟着跳）。结果是：

```
下拉 = 新建的第 12 期          表格 = 仍然挂着第 9 期的行与数量
                              ↑ 而且是上一期的**完整视图，含数量**
```

**这解释了为什么你会提这个方案 —— 你看到的就是「新建之后上一期的东西还在」。** 但它有两个问题：

1. **它不是复制，是残留**：归属没变、数量还在、而且你一点「改单」就会看到第 12 期真实的（空的）数据——正是昨天那次「取消改单后空表」事故的外观。
2. **把它扶正成需求 = 固化一个错的实现**：你要求的是「复制基础数据但**不复制报单数据**」，而残留的行为是「连数量一起带过来」。也就是说——**你其实不满意现在看到的东西，只是想让它更合理**。

📌 **因此这条不能「照现状认下来」。** 正确做法见 §五。

（同族入口核对：下拉切换 ✅ / 多期滚动 ✅ / 删期次 ✅ / 改期次 ✅（v180 已补）— **只有「新建期次」漏了重载**。）

## 四、逐条评估

### 1. 「导入必须先建期次」→ ✅ 支持，但表述要改一个字

**不是「必须先建期次」，而是「必须有一个『进行中』的期次」。**

三条理由：

| 理由 | 依据 |
|---|---|
| 归属**事后不可回填** | v180 定论：归属在导入那一刻由后端定死，之后再命名期次不会把数据挪过去 |
| 昨天事故的直接根因 | 导入时 7/8/9/10 期**全 closed** ⇒ 兜底 `forecast_period_default()` 把 154 个商品挂到了**已关闭的 9 期**，用户根本看不到 |
| 符合本项目 fail-closed 铁律 | 「宁可不发，不可群发」同族：**做不到正确归属，就不要写进去** |

🔴 **加闸门时必须同时做的一件事**：`forecast_period_default()` 的函数文档**自称「仅展示用」**，还专门警告「放宽它会静默改变落库归属，属破坏性变更」，但它**被导入路径当成了落库归属的兜底**。闸门若只加在「有没有期次」而不收窄这个兜底，**闸门形同虚设**（closed 期次仍会被兜底选中）。

⇒ 收窄为：**导入侧只接受 `status='open'` 的期次**；`default()` 继续服务 `GET /periods` 的展示。

**现有实现事实**：`routers/import_router.py:441-449` 的 `_period_id` 可以是 `0`（此时数据落 0 = 幽灵归属），且**客户端从未传 period_id**（全文件只在 431 行注释与 714/745/811 行以服务端变量出现）⇒ **闸门必须做在后端**，否则直接调接口就绕过了。

---

### 2. 「新用户点新建期次后预制模版已显示」→ ⚠️ 部分成立

**成立的场景**：租户已有商品档案、本期还没导入过。此时「预制模版」= 全量在售商品档案（tenant_1 实测 **285** 个）。**而且这个能力今天就有** —— 工具栏「显示全部商品」勾选框（`Forecast.vue:578`，`showAllProducts`）。

**不成立的场景**：**真正的新租户，商品档案是 0**。没东西可预制。此时唯一正确的路径是**下载导入模版填写再导入**——因为导入会**自动建档**（v132 起的「自动建档」，新用户无需先去档案管理录商品）。

⇒ **「预制模版」不是新用户/老用户的区别，而是「有没有商品档案」的区别。** 这是数据事实，不是用户身份——**不需要引入「用户类型」这个新维度**（否则又是第二份状态、必然漂移）。

**你提到的「手动填写或复制粘贴」**：✅ **已有能力，无需新建**。编辑态表格已挂 `@paste="onPaste"`（`Forecast.vue:824`），支持从 Excel 复制交叉表区域粘贴（`onPaste:2987` → `pasteRegion:4390`），且区分「主档列粘贴」与「交叉表区域粘贴」两条路径。

---

### 3. 「老用户自动复制上一期」→ ⚠️ 建议改为「**默认勾选 + 可见 + 可撤销**」

先说**为什么不能是「静默自动」**：

| 风险 | 说明 |
|---|---|
| **来源不可追溯** | 第 12 期的清单从 11 期继承，11 期从 10 期继承……**几轮之后没人知道这份清单最初是谁定的、按什么定的** |
| **错误逐期继承** | 若某一期是测试数据、或某期被改坏，错误会**静默复制到之后每一期**，且用户看不出来 |
| **与 v179 口径正面冲突** | 你自己拍板过「模版里有多少产品，导入后就只有那么多产品」（默认收窄）。自动铺一份清单，用户会以为「系统里就是这些品」 |
| **不可撤销** | 复制进来就是数据了。要不满意只能一行行删——而你说「若对复制的模版不满意」本身就是在承认这个需求 |
| **边界很难定义** | 见 §二：C/D 两个桶的键是窗口，无脑「复制整个期次」会串期 |

**再说为什么仍然值得做**（不否定你的直觉）：

- 经销商每期报的品**高度稳定**，逐行重建是纯粹的浪费
- 新期次**不空** ⇒ 不会被误读成「系统坏了」（昨天事故的外观就是「空表」）

⇒ **折中方案：把「复制」从「新建期次的副作用」改成「新建期次时的一次显式选择」。**

用户在**创建对话框里**就看见「本期商品清单沿用自『9月提审期』（154 个商品）」，**默认勾选**，点「创建」= 一次点击同时建期次 + 沿用清单。

- 便利性 = 你要的「点一下就自动带过来」
- 可追溯 = 意图在**点击之前**就声明了，不是事后发现
- 可撤销 = 顶部横幅常驻「本期清单沿用自 X，共 N 个 ［清空重选］」

**同时必须**：留痕一条 `period_seed` 到 `forecast_config` 的 `audit:<pid>`（复用既有留痕设施，**不新建第二份**）。

### 4. 「导入后自动覆盖已有基础数据」→ 🔴 必需，但今天**没做到**，且有冲突要你拍板

**现状（两半，方向相反）**：

| 桶 | 现状语义 | 代码 |
|---|---|---|
| B 报单明细 | **覆盖**，但按 **`order_date` 切片**（不是期次）⇒ **同一天导两次覆盖、隔天导就累积** | `import_router.py:490-495`：`DELETE … WHERE role='导入' AND order_date=?` |
| A 登记台账 | **只增不删**：`INSERT OR IGNORE` + `UPDATE`，**全仓搜不到 `DELETE FROM forecast_import_products`** | `import_router.py:744-756` |

⇒ **你的第 ④ 条要求今天只满足了一半。** 如果按你的方案「先沿用上期清单、再导入」，登记台账会变成 **上期 154 ∪ 本次 159 = 并集**，用户看到的行数会涨到 275 左右——

🔴 **这正是你 8 月底报过的那个原症状**：「我导入模版里只有 159 个产品，导入后系统里有 275 个品」。**照现状实现你的方案 = 精确复活那个已修好的 bug。**

**冲突点（需要你拍板）**：台账「只增不删」是 v179 **刻意**的（注释原文：「与报单的『同日期先清后写』相反 —— **分批导入应累积**」）。而你现在要的是「覆盖」。两者对同一张表给了相反语义。

**建议解法**：给登记台账加**来源标记** `origin ∈ {import, seeded}`，然后**语义分工清楚**：

| 时机 | 清什么 |
|---|---|
| 导入（默认「替换」） | 清本期 `origin='seeded'` **+** 本期 `origin='import'` ⇒ 本期清单 = 本次导入的品 |
| 导入（选「追加」） | 只清 `origin='seeded'` ⇒ 保留之前分批导入的品 |
| 手工删行 / 点「清空重选」 | 只清 `origin='seeded'` |

这样**分批导入能力保留、覆盖语义也成立**，且用户每次导入都能看到「替换了 N 个 / 新增 M 个」。

⚠️ ⚠️ **新增列必须幂等补列**：`CREATE TABLE IF NOT EXISTS` **不给已存在的表补列** ⇒ 必须在 `_ensure_forecast_tables()` 里 `PRAGMA table_info` + 幂等 `ALTER TABLE`，否则**只在该存量租户上炸**（这是本项目踩过的同族坑）。存量行一律回填 `origin='import'`（它们确实都是导入来的）。

## 三、N3 为什么是「最深的一条」（值得单独看懂）

代码里**想要的**表（`erp_db.py:16506`）：

```sql
CREATE TABLE IF NOT EXISTS credits_accounts (
    user_id INTEGER PRIMARY KEY,        -- ← 主键就是 user_id ⇒ 天然唯一
    balance INTEGER DEFAULT 0, ...
)
```

生产库**实际是**：

```sql
CREATE TABLE credits_accounts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- ← 主键是自增 id
    user_id INTEGER NOT NULL,               -- ← 普通列，无唯一约束
    ... , updated_at TEXT ...
)
```

**因为写的是 `CREATE TABLE IF NOT EXISTS`，表已存在 ⇒ 代码里那份 DDL 永远不生效。**

后果链条（每一步都有实测）：

```
生产表 user_id 无唯一约束
        ↓
credits_ensure_account 用 `INSERT OR IGNORE ... (user_id)`
   —— 没有唯一约束 ⇒「没有冲突可以忽略」⇒ 每次调用都插一行
        ↓   实测：单用户 399 条
SELECT ... WHERE user_id=? + fetchone()  ⇒  读到哪一条不确定
UPDATE ... SET balance=? WHERE user_id=? ⇒  一次改 399 条
        ↓
积分账本不可信
```

> 这是本项目**反复出现的同一族缺陷**：`CREATE TABLE IF NOT EXISTS` + 「代码里写 DDL、库里已有另一版」
> ⇒ **静默失效**（不报错、语法正常、功能悄悄不成立）。
> 与「只下发表不下发索引」「白名单漏字段」「租户覆盖 vs 代码默认」是同一个病根。

## 五、需要你拍板的三个决策

### D1 · 变现口径：**套餐档位** 还是 **积分**？（必须先定，否则 P0-2 白做）

| 选项 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A** | 以**套餐档位**（轻量/标准/托管）为对外口径，**积分冻结** | ① 经销商听得懂「轻量版/标准版」，听不懂"积分" ② `_PLAN_CAPS` 已有能力分层基础 ③ **少维护一套系统**（符合红线①：运维成本不可失控） | 落地页上的积分套餐要改口径 |
| **B** | 坚持**积分**为主 | 落地页已经这么卖了；按用量收费更公平 | **必须先修 N3 账本**（P0-2），否则计费不可信 |
| **C** | 两者并存（现状） | — | ❌ **不推荐**：两套账、两套价，客户问"我该买哪个"你答不上来 |

> **我的推荐：A**。理由是「一套系统能少维护就少维护」，且验证期真正要回答的是
> 「有没有人愿意付钱」，不是「按什么单位付钱」。

### D2 · 收款方式：验证期要不要做在线支付？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **不做**。人工报价 + 对公转账/微信收款，后台手工记一笔。**但要能把「客户用了多少、该收多少」看清楚** |
| **B** | 做在线支付（微信/支付宝）。成本高（要商户资质、回调、对账），且**验证期客户数少，收益低** |

# 舟谱导入模板 · 源单据号唯一性与分批追溯（需求说明 + 方案）

> 场景提出：2026-10-24
> 核对对象：生产 `routers/forecast.py`（`_build_zhoupu_data` / `_arrival_compact` / `import_template_generate`）、租户库 `forecast_periods`
> 结论依据：代码逐行实读 + 期次真实数据，非推测

---

## 摘要（先讲结论）

> **状态：v665（2026-10-24）已全部落地并上线**。下文 §一 描述的是**修复前**的事实（保留作根因记录），
> 设计与实测见 §三、§六、§七。

1. **（修复前）同一期次第二次生成，单号会与第一次逐字相同** —— 不是"偶尔撞号"，是必然撞号。
2. 原因只有一条：序号是**每次生成在内存里从头重编**（自提从 `zt_seq_start` 默认 21 起、调拨固定从 01 起），库里没有任何"上次用到了几号"的记录。
3. 日期段也帮不上忙：单号里的 8 位日期取的是**期次的到货日**（`forecast_periods.arrival_date`），同期次恒定一个值 —— 各品牌到货时间不同这件事，系统里**没有建模**（`products` 只有 `arrival_lead_days` 提前天数，没有品牌级到货日）。
4. 顺带还有两个同源缺陷：两次下载**文件名完全相同**（`自提订单导入模板_20261029.xlsx`，浏览器自动加 `(1)`）；**系统里查不到导出过一次还是三次**，无法追溯。
5. 修复不需要动舟谱单号格式。单号维持 `ZT{8位日期}{2位序号}` / `DB{8位日期}{2位序号}`（这是舟谱格式契约），唯一性做在**序号空间的持久化分配**上，批次信息落到**导出记录表 + 文件名**里。

## 一、现状（实测）

### 1.1 单号是怎么来的

`routers/forecast.py`：

```python
# 自提（第 1664 行起）
seq = int(prof.get("zt_seq_start") or 21)   # 每次生成都从这里重新开始
for g in zt_groups:
    no = f"ZT{date_compact}{seq:02d}"       # ZT + 到货日 + 2位序号
    seq += 1

# 调拨（第 1709 行起）
seq = 1                                      # 每次生成都从 01 重新开始
for g in db_groups:
    no = f"DB{date_compact}{seq:02d}"
    seq += 1
```

- `seq` 是**函数内局部变量**，生成结束即销毁，不落库。
- `date_compact = _arrival_compact(start, end)`（第 1812 行）：读期次 `arrival_date`，取不到才回退报单起始日。
- 实测期次 37（2026-10-25 期次）：`order_start=2026-10-24`、`order_end=2026-10-25`、`arrival_date=2026-10-29`。

### 1.2 撞号的具体形态

假设第 1 批导了 9 个客户，第 2 批导 6 个客户（同一期次）：

| 批次 | 现在会生成的单号 | 舟谱结果 |
|---|---|---|
| 第 1 批（9 客户） | `ZT2026102921` … `ZT2026102929` | 正常导入 |
| 第 2 批（6 客户） | `ZT2026102921` … `ZT2026102926` | **报错：源单据号重复** |

而且**不是只有重叠的那几张报错** —— 舟谱是整份文件校验，第 2 批很可能整份被拒，等于这一批白导。

### 1.3 三个伴随问题

| 问题 | 现象 | 后果 |
|---|---|---|
| 文件同名 | 两批都叫 `自提订单导入模板_20261029.xlsx` | 下载目录里靠 `(1)(2)` 区分，**发错文件**的概率不低 |
| 无导出记录 | 库里无任何模板导出表（`forecast*` 系列 18 张表，无一张记导出） | 谁在什么时候导了哪批、含哪些商品，**事后查不到** |
| 序号上限只告警 | 第 1666 行：`seq + len(zt_groups) - 1 > 99` 仅追加 warning | 会生成三位号（`ZT20261029100`）继续下载，舟谱是否接受**未验证** |

### 1.4 目前唯一能绕开的土办法（这也是用户现在的痛点）

把批次**错开到不同到货日** —— 但 `arrival_date` 是期次级单一值，改它等于改整期口径，会连带影响别的地方。所以实际上绕不开。

## 二、需求要点

| # | 需求 | 判据（可验收） |
|---|---|---|
| R1 | 同期次可**多次生成**，每次一批 | 同窗口连续生成 3 次，3 批单号互不相交 |
| R2 | 每批单号**全程唯一** | 同租户内 `(前缀, 到货日, 序号)` 永不重复，跨批、跨期次、跨重下都成立 |
| R3 | 每批**可追溯** | 给一个单号，能查出：第几批、哪个期次、什么时候、谁导的、含哪些报单对象、共几行 |
| R4 | 保住舟谱格式 | 单号仍是 `ZT`/`DB` + 8 位日期 + 序号；**不擅自加字母/加段**（舟谱可能校验格式） |
| R5 | 重复下载不占号 | 同内容再点一次"生成"，返回上次同一批、同一号段，不消耗新号 |
| R6 | 号段不够要**明说** | 剩余号不足时明确报错并给处置选项，绝不静默变三位 |
| R7 | 文件可区分 | 文件名带批次与范围标识，导错文件能一眼看出 |

> R5 容易被忽略但很关键：没有幂等，"手抖点两下"就会白吃一段号，多批之后很快撞上 99 上限。

## 三、唯一性约束的处理逻辑

### 3.1 约束的正式定义

**唯一键 = (租户, 单据前缀 `ZT`/`DB`, 到货日 8 位, 序号)**，四元组在库内全局唯一。

> 为什么要把"租户"放进去：`ZT2026102921` 这种短号在小经销商之间**必然会撞**。舟谱那边如果是多个客户各自导入、互不可见，撞号无碍；但只要有一家客户有两套账（两个户头）导进同一个舟谱账套，就必须区分。存约束时带租户，生成时不额外编码 —— 把这一条作为**已知边界**写清，不在单号上做文章。

### 3.2 号段分配：从"内存自增"改成"库内水位"

新增一张表：

```sql
CREATE TABLE forecast_doc_seq (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  period_id    INTEGER NOT NULL,     -- 期次
  arrival_date TEXT    NOT NULL,     -- 8 位到货日（= 单号里的日期段）
  prefix       TEXT    NOT NULL,     -- 'ZT' | 'DB'
  last_seq     INTEGER NOT NULL,     -- 已发放到的水位
  updated_at   TEXT
);
UNIQUE(period_id, prefix)            -- 一个期次一个前缀一条水位
```

分配算法（**在同一个事务里**完成，不靠文件锁、不靠进程内存）：

```
1. 计算本批需要 N 个号
   N = 本批分单数（自提=客户数，调拨=业务员仓数）
2. 取水位 base：
   read last_seq  from forecast_doc_seq where period_id=? and prefix=?
   无记录 → base = 起始值（自提 zt_seq_start 默认 21；调拨 1）
3. 检查上限：base + N - 1 ≤ 99，否则拒绝（见 3.5）
4. 发放区间 [base, base+N-1]，写回 last_seq = base+N-1，COMMIT
5. 按分组顺序把区间里的号依次发给每张单
```

要点：

- **先占号、后生成文件**。号在事务里先确定并提交，再拼 xlsx。生成抛异常 ⇒ 该批标记 `voided=1`，号段不回收（理由见 3.4）。
- 因为水位在库，两人同时点导出也只会拿到两段不重叠的号 —— 事务隔离就够，不需要额外锁。
- 单号生成从"循环里 `seq += 1`"改成"读分配结果"，两处循环各改一行取号来源即可，格式一行不动。

### 3.3 批次号与内容的绑定（幂等）

新增导出记录表：

```sql
CREATE TABLE forecast_template_exports (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  period_id   INTEGER NOT NULL,
  batch_no    INTEGER NOT NULL,       -- 期次内第几批：1,2,3…
  prefix      TEXT    NOT NULL,       -- ZT | DB
  arrival_date TEXT   NOT NULL,
  seq_from    INTEGER NOT NULL,
  seq_to      INTEGER NOT NULL,
  doc_count   INTEGER NOT NULL,       -- 分单数
  item_count  INTEGER NOT NULL,       -- 明细行数
  scope_label TEXT,                   -- 本批范围（如「蒙牛低温」「全部」）
  fingerprint TEXT NOT NULL,          -- 内容指纹
  filename    TEXT NOT NULL,
  created_by  TEXT,
  created_at  TEXT,
  voided      INTEGER DEFAULT 0,
  UNIQUE(period_id, prefix, batch_no)
);
```

**内容指纹** = `sha1(排序后的 (报单对象, 条码, 单位, 数量, 单价) 全集 + scope_label)`

判定顺序：

```
算指纹 fp
  ├─ 命中同 (period_id, prefix, fp) 且 voided=0 的旧批
  │    ⇒ 直接返回那一批：同 batch_no、同号段、同文件名（R5 幂等）
  └─ 未命中 ⇒ 新批：batch_no = 上批 +1，走 3.2 分配号段
```

这样：
- 手抖点两次 → 第二次不占号
- 改了某客户数量再导 → 新批，新号，且能对比两批差异
- 同一批想重新下载 → 回原批

### 3.4 作废：**号段不回收**

作废只置 `voided=1`，号段**保持已用**。

理由（这是本方案最重要的一个取舍）：

> 回收号段 = 允许"作废的第 3 批"和"新补的第 3 批"用同一批号。而用户作废的典型原因正是"这批已经在舟谱里导过了、但打错了要重打" —— 重打的那批如果复用旧号，舟谱侧就会遇到"这个源单据号已存在"，**又回到撞号原点**。
>
> 所以宁可号段留洞（`…28, 29, 33, 34`），也不能重号。洞是可以解释的，重号是不能解释的。

### 3.5 上限与兜底

| 前缀 | 起始 | 可用号数 | 备注 |
|---|---|---|---|
| 自提 `ZT` | **1**（✅ 用户 2026-10-24 定：默认 01 起，账套里 ZT 段 01–20 未占用） | 99 个（01–99） | 起始值租户可配（「报单配置 → 模板参数」） |
| 调拨 `DB` | 1 | 99 个（01–99） | 固定从 01 起 |

剩余不足时**拒绝生成**，并给出三条明路（不让用户猜）：

1. 拆到下一到货日生成（改期次口径，需确认）
2. 把起始序号调小（仅在该租户历史号不冲突时允许，配置页要给冲突校验）
3. 允许三位序号 —— **需先向舟谱确认是否接受**，未确认前不开放

> 现在代码是"只报警告、照样生成三位号"。这个行为要改成硬拒绝：三位号一旦被舟谱拒收，用户会以为是"我们生成错了文件"，排查成本远高于当场报错。

### 3.6 追溯链（R3）

从任一端反查：

| 入口 | 查到 |
|---|---|
| 单号 `ZT2026102930` | 第 2 批 · 期次 37 · 到货 2026-10-29 · 蒙牛鲜奶 · 张三 2026-10-24 15:20 导出 · 6 张单 42 行 |
| 期次 37 | 导出过 3 批（第 2 批已作废），号段 21–29 / 30–35 / 36–37 |
| 批次号 2 | 明细清单：每个报单对象 → 单号 → 行数 |

### 3.7 配置项语义变更（必须讲清，否则用户会困惑）

`zt_seq_start`（「自提单号起始序号」，**现默认 1**，v665 起）的含义从：

- 旧：**每次生成**的起点（改它 = 每次重来都从这起）
- 新：**该租户/期次的首次起点**（之后水位自动上涨，配置只管起点）

界面文案要同步改成「自提单号起始序号（仅新期次的第一个批次生效）」，并在改动已有期次的数据时提示"已用号段不会被覆盖"。

### 落地后的实现要点（与本文设计的差异，均为收敛而非放宽）

1. **水位表主键加了 `arrival_date`**：`(period_id, arrival_date, prefix)`。理由：单号里的日期段就是 `arrival_date`，舟谱真正的唯一性判据是 `(前缀, 日期, 序号)`；而且在「查不到期次」（`period_id=0`）时，按到货日仍然隔离，不会跨窗口共用一个计数器。
2. **幂等命中不写新台账**：同内容重复下载只回原批原号段，台账保持 1 条 —— 否则「导了 3 次」会被记成 3 批，追溯反而失真。
3. **生成分两次 build**：先不占号构建一次拿指纹与分单数 → 判幂等 → 占号 → 用真实号段重建行。代价是一次重复取数（几十毫秒），换来「幂等命中不吃号」这条硬语义。
4. **探针占用的号段在验收后清理**：内部测试不该吃掉用户第 1 批的 01–02（`DELETE` 台账与水位），用户的号段从 01 开始。

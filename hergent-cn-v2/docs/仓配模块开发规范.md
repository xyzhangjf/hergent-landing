## 2. 🔴 开工第一步：后端能力盘点法（别凭印象造轮子）

仓配 90% 的后端**旧前端已建**（`warehouse-features-overview.md`），新前端是**接**不是**造**。
每次开工先跑这三步，**先证有没有，再决定写不写**：

```bash
# ① 列全部后端前缀
grep -h "APIRouter(prefix" server/routers/*.py | sort -u
# ② 查每个前缀归哪个权限模块（首个 startswith 命中即停）
grep -nE '"/api/(inventory|expiry|vehicle|stock-take|wms|assembly|delivery|...)'
# ③ 🔴 带 token 实测（这一步才是判据）
TOK=$(ssh root@47.113.224.140 'python3 /tmp/v392-probe-tokens.py boss' | cut -f3)
curl -s -o /dev/null -w "%{http_code}  %{url_effective}\n" -H "Authorization: Bearer $TOK" https://hergent.cn/api/xxx
```

**状态码判读**：`200`=可用 ｜ `403`=**未映射**（fail-closed，前端会显示「无权限」，看不出是路径问题）｜ `404`=无此路由 ｜ `401`=未登录。

> 🔴 **无 token 的探针没有判别力**：RBAC 中间件在 **auth 之后** ⇒ 已映射与不存在的路径**都返回 401**。
> 必须带 token。~~拿 401 当「路由存在」~~ 会得出「端点都在」的假结论。

**已实测前缀（P0 期）**：
`/api/vehicles`→stock ｜ `/api/vehicle-stock/*`→stock ｜ `/api/inventory/*`→stock ｜
`/api/wms/*`→stock ｜ `/api/stock-take/*`→stock ｜ `/api/assembly/*`→stock ｜
`/api/delivery/*`→sales ｜ `/api/expiry/*`→**v465c 前未映射（403）**、v465c 补为 stock。

### 2.1 P2 库存作业 · 六页能力盘点结论（2026-10-11 实测）

带 token 打生产（tenant 1，`boss`）逐条实测，**这是判据**：

| 页面 | 候选后端 | 实测 | 结论 |
|---|---|---|---|
| 静态盘点单（整仓） | `GET /api/stock-freezes/list` / `/{fid}` | **200** | ✅ 直接用（`scope='full'`） |
| 静态盘点单（部分） | 同上 | **200** | ✅ 直接用（`scope='partial'`） |
| 组合单 | `GET /api/assembly/list` / `/summary` / `/{aid}` + `POST /create` · `POST /{aid}/confirm` · `POST /{aid}/void` | **200** | ✅ 直接用（`type='assemble'`） |
| 拆分单 | 同上 | **200** | ✅ 直接用（`type='disassemble'`） |
| 盘点差异单 | `GET /api/wh/stocktake`（P1 自建引擎） | **200** | ✅ 直接用（**纯前端视图**：列表读 `/api/wh/stocktake`，点开某期才逐条 `/{tid}` ⇒ 已知 N+1，只在点开时发生，可接受；**零新后端**） |
| 损益单 | `GET /api/wastage/list`（**报损单**，`v92`） | **200** `{"orders":[],"total":0}` | ✅ 直接用（**不是** `/api/loss`，见下） |

**顺带两条（对后阶段有用）**：
- `GET /api/stock-take/list` = **404** ⇒ legacy 盘点**没有列表端点**（只有 start/update/finalize）。
  再次印证 P1 的判断：legacy 那套不能接。
- `GET /api/delivery/list` = **404** ⇒ **P3「配送单」后端不存在**，开工 P3 时要按"新建"而非"接"来估工。

**三项关键技术判断（写下来免得后来者重踩）**：

1. 🔴 **静态盘点与 P1 的「盘点单」是两个引擎、两张表，不是重复建设。**
   `stock_freezes`（v108，旧前端建的）= **冻结快照 + 状态标识**，`scope='full'|'partial'`，
   语义是"盘点期间以快照为计数基准"；P1 的 `wh_stock_takes` = **录数 + 差异落库存**。
   两者在舟谱形态里也是两张单据（静态盘点单 / 盘点单）⇒ **都保留、各挂各的页**。
   ⚠️ 但两者**没有任何数据联动** —— 在静态盘点单页上"完成盘点"不会去动冻结单，
   反之亦然。P2 落地时要**在页面口径说明里写清这一点**，否则仓管会以为冻结单自动解冻。

2. 🔴 **`/api/assembly` 的写路径是「批次盲」的（与 `inventory_adjust` 同族缺陷）。**
   `erp_db.py::_asm_apply_inventory` 定位行用的是
   `SELECT ... WHERE product_id=? AND warehouse_id=? AND batch_no=''`，
   且 `max(0, ...)` **静默把负数夹到 0**（库存不足不报错、直接记 0）。
   ⇒ 只要出现**多批次**（P1 的入库单/其它入库立刻会造出），
   组合/拆分就会「扣不动该扣的批次」且**不报错**。
   **P2 的处理**：页面**照原样调用**（不动 `erp_db.py`，它被多处共享），
   但在「组合/拆分」页的**口径说明里明确写出**该限制，并在规范里登记为**待单独一轮修**的欠账。
   ⚠️ 不要在本轮顺手改 `_asm_apply_inventory` —— 它属 `erp_db.py`，
   而该文件正被其它会话在途修改（v465f 只动了自己那一段）。

3. 🔴 **「损益单」= 既有 `v92` 报损单（`/api/wastage/*`），不是 `/api/loss`。**
   `/api/loss/*` 是 **AI 货损核算域**（`GET /api/loss/recipe` 返回的是算法配方
   `threshold_days/pricing/near_loss_pct`），**不是单据列表** —— 一开始我按名字猜成它，实测才发现。
   真正的报损单在 `domain/wastage_tracker.py` + `wastage_orders` / `wastage_order_items`（v92），
   路由**不在 `routers/` 里**而是内联在 `server.py`（4075–4121），前缀 `/api/wastage` → 模块 **`stock`**（`server.py:737`）。
   已实测：`GET /api/wastage/list` = **200**。

   **该域的真实语义（写页面前必须先看，否则会做错交互）**：
   · `create_wastage_order()` **立即扣库存**（`inventory_adjust(..., ref_type='wastage')`）
     并且**直接落成 `status='approved'` + 过账 GL 分录**（`wastage_tracker.py:151`）
     ⇒ **没有"提交后待审"这一步**。页面上的「新建报损单」= **一次性生效的库存+账务动作**，
     必须二次确认 + 显著提示。
   · `POST /api/wastage/{wid}/reject` = **撤销**：恢复库存 + 冲销分录（且只对 `approved` 生效）。
   · 类型→科目映射**已内置**：`expired/damaged`→6401 主营业务成本，`transport`→6601 销售费用，
     `quality/theft/other`→6602 管理费用。页面**不许**再抄一份科目名。

   🔴 **顺带查到两个既有缺陷（本轮不修，登记 + 上报）**：
   · **(A) 路由遮蔽**：`server.py` 把 `/api/wastage/{wid}`（4096 行）注册在
     `/api/wastage/summary`（4108）与 `/api/wastage/suggest-from-expiry`（4115）**之前**
     ⇒ 后两者被当成 `wid` 解析 ⇒ 实测**恒 422**（`wid: Input should be a valid integer`）。
     与 P1 记录的「静态段必须排在 `{id}` 之前」是**同一类**缺陷（`routers/wh.py` 头部已写进纪律）。
     ⚠️ 修它要动 `server.py`（多会话共用文件）⇒ **等一个无并行改动的窗口**再修。
   · **(B) 批次盲扣减**：`create_wastage_order` 用的正是那个已知的**批次盲** `inventory_adjust`
     （`SELECT ... WHERE product_id=? AND warehouse_id=?` + `.fetchone()`）。
     报损场景里**这个缺陷是会真出事的**：报损对象就是过期批次，而它只扣"表里第一条"。
     同族缺陷已在 P1 登记（`db/queries/wh.py` 模块 docstring），此处**再加一个调用方证据**。

## 3. 🔴 前缀命名与映射（三条例）

1. **优先挂在已映射前缀下**（如 `/api/inventory/low-stock` 天然落 `stock`）⇒ **零登记、零权限数据变更**。
   本模块 `routers/inventory.py` 的 `APIRouter` prefix = **`/api`**，所以「加一条 `/inventory/...`
   子路径」就是挂在已映射的 `/api/inventory` 下。
2. **要新前缀 ⇒ 必在 `server.py::_PATH_MODULE_MAP` 登记**，否则 `module is None` ⇒
   中间件 fail-closed **403**（静默：前端只显示「无权限」）。
3. **反向自查前缀嵌套**：`new_prefix.startswith(any_existing_prefix)` 为真 ⇒ **改名**。
   本表「首个 startswith 命中即停」，嵌套前缀登记了等于没登记（静默走错权限域）。

> **v465c 实例（一处历史静默 403 的修复）**：`routers/inventory.py` 的
> `GET /api/expiry/forecast` 因前缀 `= /api`、而 `/api/expiry` **从未登记** ⇒ 带 token 恒 403
> （旧「临期预警表」实为坏点）。修法：`_PATH_MODULE_MAP` 补 `"/api/expiry": "stock"`，
> 与 `/api/inventory` 同域、零权限数据变更、无缝嵌套。

## 4. 🔴 落真身四步（占位页 → 真实页）

占位页（v465 批量挂的「开发中」骨架）转正页，**四步缺一即出 bug**：

| # | 落点 | 做什么 | 漏了的后果 |
|---|---|---|---|
| 1 | `pages.js::PLACEHOLDER_PAGES` | **移出**该 path | 合并循环会用 `{module:null, roles:BIZ_ROLES}` **覆盖**第 2 步的正式行 |
| 2 | `pages.js::PAGE_RULES` | 写**正式行**（`module` 配真实域 + `roles`） | 可见性无真源 ⇒ 侧栏不亮 / 守卫拒 |
| 3 | `router/index.js` | 加组件 import + 真实路由，**排在 `PLACEHOLDER_PAGES.map(...)` 之前** | 静态段不在前 ⇒ 被占位路由吞 |
| 4 | `src/api/wh.js` | 加 API 方法（路径/方法/参数与后端**逐个对齐**） | 取数 404/参数错 |

**验收（可证伪）**：
- `grep` 三处：`PLACEHOLDER_PAGES` 里已无该 path、`PAGE_RULES` 有正式行、`router` 路由唯一；
- 构建产物有该页**独立 chunk**；
- **真机探针**：真页 `h2` 命中且**无 `.ph-card`**；同时跑一个**仍是占位**的同模块页做**反例自证**
  （它必须有 `.ph-card`）⇒ 证明判据有判别力。

## 6. 文案与单位（红线）

1. **界面一律不出现英文枚举**；状态/级别走**中文词表**（`src/constants/psiLabels.js` 的 `textOf/tagOf` 已覆盖进销存；仓配新状态若要展示英文值，先补词表再展示，别 `switch` 硬编）。
2. **数量**：整数按整数显示（包/箱**不带小数**），非整数保留 2 位；**单位取商品档案**（`products.unit`）。
3. 🔴 **阈值由后端给**：效期红/黄分档（≤30 / 31–60 天）在后端算好；前端**只做展示换算，不重新判定档位**——否则「屏幕颜色 ≠ 后端口径」。
4. **金额**显示唯一实现 = `psiLabels.js` 的 `fmtMoney`（页面只 `import`，不各抄一份）。
5. 失败**显式抛出**：`api()` 抛 `Error`，页面必须显示 `.state-error`，**不许 `catch {}` 吞掉**（恒空恒 0 零报错 = 静默失效）。

## 8. 坑清单（P0/P1 实测 / 差点踩到）

### 8.A 通用（P0 起）

1. 🔴 **未映射前缀 = 静默 403**：`/api/expiry/forecast` 就是这样一颗历史地雷（见 §3 实例）；`/api/inbound` 更久 —— 后端 5 个端点早存在，但从未登记进 `_PATH_MODULE_MAP` ⇒ 旧前端那页**一直是坏的**（P1 才补映射）。
2. 🔴 **无 token 探针无判别力**：401 对「已映射」「不存在」都一样（auth 先于 RBAC）。
3. 🔴 **占位页不彻底移出 ⇒ 合并循环覆盖正式行**（`module:null` 盖掉 `module:'stock'`）。
4. 🔴 **真实路由必须排在 `PLACEHOLDER_PAGES.map` 之前**。
5. 🟡 真机探针 API：`cdp-lite` 的 page **没有 `close()`**（只有 `browser.close()`）。
6. 🟡 **探针自身断言要覆盖全部 `need` 分支** —— 漏一个分支会造出**假 FAIL**（P0 首跑就踩到：占位页的 `.ph-card` 分支没写，页面对但探针红）。
7. 🟡 **BSD grep 的 `\|` 交替会静默失效** —— 多模式一律 `grep -E` 或拆两条。

### 8.B 前端（P1 实测）

8. 🔴 **「前端可见」和「后端能取数」必须同域**：建单下拉的商品/供应商/客户**必须**走
   `/api/products` + `/api/contacts`（归模块 `data`，`BIZ_ROLES` 五类全持）；
   **不能**走 `/api/psi/refs`（归 `inventory`，只有 boss/admin）或 `/api/customers`（归 `crm`，
   会计/主管都没有）—— 否则会造出「入口看得见、一开下拉就 403」的**局部假入口**。
   判断方法：`pages.js` 里该页的 `roles` ∩ 各接口模块的持有角色，**每个接口都要非空**。
9. 🔴 **全局 `.input{width:100%}` 在 flex 行里会吃满整行**：`flex-basis` 变成整行宽，
   `flex-shrink` 按基准宽度分摊 ⇒ 一个 `min-width:150px` 的下拉实际能占掉 900px、
   把右边的说明挤到下一行。窄下拉必须写 `width:<定值>; flex:none`。
   ⚠️ 覆盖得住的原因：scoped 规则被编译成 `.cls[data-v-*]`，特异性 (0,2,0) > `.input` 的 (0,1,0)。
10. 🔴 **`ProductCombo` 未选中时渲染的是一个空 `<span class="ipn-v">`**（它**没有** `placeholder`
    prop，只有 `SupplierCombo`/`CustomerCombo` 有）⇒ 在明细表格里就是一个**空白单元格**，
    用户不知道那儿能点。修法：父页 scoped 里 `:deep(.ipn-v)` 补输入框外观 +
    `:deep(.ipn-v.is-ph)::before{content:'选择商品'}` 补占位文案。
    ⚠️ **不要改 `ProductCombo.vue` 本体** —— 它被进销存 4 个建单页共用，加参数属跨模块共享件变更。
11. 🟡 同屏两个数字要对不上之前先问「是不是两个 populations」：KPI 走服务端全表、表格走本地截断，
    必然出现「说 3 张、表里 2 行」。见 §5.2。

### 8.C 后端与库存原语（P1 实测，代价最高的一批）

12. 🔴 **SQLite SAVEPOINT 事务陷阱**：`fefo_deduct` 内部 `SAVEPOINT` → `RELEASE`；
    若该连接上**没有**外层显式 BEGIN，`RELEASE` **就是提交** ⇒ 失败路径的「不 commit」
    退化成空操作，留下**半出库**。修法 = 每个写入口先 `_begin_write(db)`
    （SQLite-only `BEGIN IMMEDIATE` when `not db.in_transaction`；PG 不需要）。
    ⚠️ 这个坑**是否踩到取决于执行顺序**：连接上之前若已有过 INSERT/UPDATE，
    python sqlite3 会隐式 BEGIN，SAVEPOINT 就变内层、现象消失 —— 所以验证必须用
    **干净连接 + 只做 SELECT 的对照组**（`v465e-shadow-verify.py` Phase 5b 就是这么钉住的）。
13. 🔴 **同一单据里同一商品拆成多行** ⇒ 必须**按商品聚合后再预校验**（`_by_product`）。
    逐行校验会放过（每行都够），然后扣到第二行才炸 = 半出库。
14. 🔴 **`db/queries/inventory.py::inventory_adjust` 是批次盲的**：它
    `SELECT id,quantity FROM inventory WHERE product_id=? AND warehouse_id=?` 用
    **`.fetchone()`** 只取一条 ⇒ 多批次时 ① 误报「库存不足」② 扣错批次（不是 FEFO）。
    ⚠️ **不要顺手改它**（18 处调用：采购入库/退货/调拨/装车/还车/报损/期初/舟谱导入…），
    那是系统性变更。本模块自带 `_gross_deduct` 把自己这条链修对，并把缺陷登记在 docstring。
    （实测 tenant_1：`inventory` 54 行 = 54 个 `(商品,仓库)`，**还没有多批次** ⇒ 今天无损失；
    但本模块的入库单/其它入库**立刻**会造出多批次行。）
15. 🔴 **legacy `stock_take_*` 在批次级库存下必然算错三处**：① `start` 按 inventory 行（=批次行）建明细；
    ② `update` 的 WHERE **只有 product_id**（无仓库、无批次）⇒ 一次录入改掉该商品所有行；
    ③ `finalize` 逐行 `inventory_adjust(diff)` ⇒ 差额按批次数**放大 N 倍**。
    ⇒ **不复用**，本模块自建 `wh_stock_takes` / `wh_stock_take_items` + `/api/wh/stocktake`；
    **legacy 一个字符不改**（旧前端仍在用那套，两个引擎各管各的表）。
16. 🔴 **`batch_in` 的 `change_type` 是硬编码 `'batch_in'`**，不透传 `ref_type`/`ref_id`
    ⇒ 盘盈在 `inventory_logs` 里与**普通入库不可区分**（盘亏那条因为走自建 `_gross_deduct`，
    能带上 `wh_stocktake_loss` + 期次号）。**登记不修**（要改共享原语签名），
    `_apply_variance` docstring 与影子脚本 Phase 9 各钉了一处，将来修好会变红提醒同步。
17. 🔴 **`batch_in` 的同批次累加分支不写 `inventory_logs`**（同一处欠账的另一面）。
18. 🟡 **失败信封的形状要背下来**：`fefo_deduct` / `_gross_deduct` / `_apply_variance` 的失败返回是
    `{'error': ..., 'used': []}` —— **没有 `success` 键**。断言写 `r.get('success') is False`
    会永远是假 FAIL（`None is False` 为假）。正确判据 = `bool(r.get('error'))`。
    另外：`_ok()/_fail()` 必须把数据层的 error 翻成 **4xx**，**不能**把 `success:false` 塞进 200
    ——前端 `api()` 只在 `!res.ok` 时抛错，200 里的失败会被当成功（静默失效）。
19. 🟡 **不可复现的探针 = 没跑**：影子脚本忘了套 `tenant_scope(1)` 时，`get_db()` 落到**主库**，
    现象是「刚用裸 sqlite3 插进去的库存看不见、一律可用 0」——看起来像实现坏了，其实是探针跑错库。

### 8.D 本地探针（不部署时怎么验）

20. 用户要求「不提交、不部署」时，**打生产探针只能证明"还没上线"**。改用
    **本地构建产物 + 打桩 `fetch`**：`vite build --outDir /tmp/xxx` → Node 起静态服务器 →
    `cdp-lite` + `addInitScript`（**必须在 boot 前**注入 token 与 fetch 桩，
    否则 `store.loadPerms()` 这个 boot 期请求打不进去 —— v267 踩过）。
21. 🔴 打桩要**给全前置检查依赖的数据**：`openCreate()` 有「供应商没加载到就拦住并 toast」，
    桩不给 `/api/contacts` ⇒ 弹窗压根不开。第一版探针就栽在这，把**正确的守卫**误判成 bug。
22. 🔴 桩脚本若写成模板字符串，**内部不能出现反引号**（会被当结束符截断）；
    注释里想引用标识符就写 `openCreate()` 而不要写带反引号的版本。
23. 🟡 必须有**反例自证**：同一模块里仍是占位的 `/wh/pnl` 必须落到 `.ph-card` —— 否则
    判据分不清「已落真身」与「仍是占位」，整个探针没有判别力。

### 8.E 上线后真机验证（v465e 实测，与前四组互补）

24. 🔴 **「接口零 4xx」这条断言天生会假红 —— 必须减基线。** 真机上每个页面都会发一批
    **全站公共**请求（`/api/auth/permissions`、`/api/ui/col-prefs`、`/api/weather/pref` …）。
    其中任何一个既有缺陷都会把 6 个真页**全部**判红，而它们和本轮改动毫无关系。
    正解：**先跑本模块里一个本轮未改动的页面**（占位页 `/wh/pnl`），把它的坏接口集合当基线，
    真页只断言「**减基线后无新增**」；同时另立一条**强断言**「本轮相关前缀
    （`/api/wh/*`、`/api/inbound*`）零失败」。豁免项要**打印出来**，不能悄悄吞掉。
25. 🔴 **「200 是因为映射配好了」需要反例对照才成立。** 只看到 `/api/wh/*` 返回 200，
    无法排除「中间件放水 / 全局都 200」。必须同时打一条**未登记前缀**（如 `/api/__v465e_nope__`），
    断言它 **403 且 detail 含「模块」** —— 正反两侧都成立，判据才有判别力。
26. 🔴 **`md5sum -c` 单向全量包含 > 「交集 md5 一致」。** 把本地 `dist/assets/*` 逐文件 md5
    生成清单、scp 上机 `md5sum -c`，要求 **120/120 OK、0 缺失**。交集一致只证明"两边都有的没变"；
    单向包含才证明"**生产上跑的就是我这份产物**"。
27. ⭐ **干净树构建的顺序**：`git archive HEAD` 导出 → 先构建**HEAD 原样版** → 比
    `index.html` 的 md5 与生产是否逐字节相同（**证明 线上 == HEAD**）→ 再把本轮的
    **暂存版**文件铺进去构建。第 ① 步不能省：它是后面"产物差集可归因"的前提，
    也是"我这次部署的基线"的书面证据。
28. ⭐ **产物差集要按「逻辑名配对 + 归一化」归因**，不看文件名：把 `-<hash8>.js|css`
    归成 `-X`、`data-v-<8hex>` 归成 `data-v-X` 后再比 —— 归一化后仍不同的才是**真实改动**。
    本轮 59 个 md5 不同里 **50 个是纯 hash 级联**，真实改动只有 9 个，且逐个能对上我改的文件。
    ⚠️ **新增 chunk 会让旧 chunk「缩水」**：本轮 `SaleDocForm` 少了 2067 字节，
    原因是新页面也 import 了 `CustomerCombo` ⇒ rollup 把它抽成独立 chunk。
    看似"回退"，实则**模块换位**；判据是**中文串不能少**（`没有匹配的客户` 从 SaleDocForm
    挪到 CustomerCombo，总数不变），不是"字节数必须不变"。
29. 🔴 **新页面会把「早就坏掉的后端」第一次暴露出来。** 本轮 `出入库策略` 一上线，
    `/api/wms/replenishment/needed` 立刻 500 —— 根因是**既有**的建表缺陷（见 §9 末尾），
    与本次改动无关。⇒ 真机探针出现 5xx 时，**先做归因三问**：
    ① 报错接口在不在本轮 diff 里（`git grep <版本>~1 -- <路径>`）？
    ② 同一坏接口在**本轮未改动**的页面上能不能复现？
    ③ 生产日志的 traceback 指向的文件，是否在本轮改动清单里？
    三问都"不是我的" ⇒ 在报告里**如实标注为既有缺陷**并给出证据，
    **不要**顺手改（可能是别人的在途功能，也可能要动生产库/需老板授权）。
    > v465f 补：老板随后选了「(a) 改代码对齐现 schema」⇒ 已修（见 §9 末尾）。本条仍是
    > **默认动作**：先归因上报，拿到授权再改。

### 8.F 列名 / 状态词 / 建表（v465f 实测，代价最高的一组"隐形错"）

30. 🔴 **DDL 与查询各写一套列名 ⇒ 漂移永久隐形。** `CREATE TABLE IF NOT EXISTS` 只在库
    **没有**该表时才生效；表一旦存在，DDL 写什么都不落地。本仓 `pick_face_config` 的 DDL 写
    `pick_face_qty/min_qty/max_qty/location_code`，而 `erp.db`/`tenant_1.db`/`tenant_10.db`
    实际都是 `forward_min/forward_max/reserve_bin` ⇒ 代码里"改过名"这件事**从来没生效过**，
    两边各说各话，直到新页面第一次调用才炸。
    **纪律**：① 动表前后都 `PRAGMA table_info(<t>)` 对**生产快照**核一遍，**别信 DDL**；
    ② 改列名 = 改 DDL + 所有读写点 + 迁移，三处一起；③ 探针/验收里钉一条"列名与生产一致"的断言。
31. 🔴 **状态词不许顺口写 —— 必须抄本系统既有口径。** `cross_dock_opportunities` 写
    `po.status='confirmed'`，而生产库三个库都没有该状态（真实只有 `draft/received/cancelled`）
    ⇒ 查询**合法但恒空**，还被 `try/except` 吞成"正常空态"（比 500 更危险）。
    **找口径**：`grep -n "status IN (" server.py` ⇒ 在途采购 = `draft/confirmed/pending_approval`、
    可发货销售 = `draft/confirmed`。**纪律**：任何"按状态筛"的 SQL，先在库里
    `SELECT status, COUNT(*) FROM <t> GROUP BY status` 看清真实取值域再写。
32. 🔴 **`INNER JOIN contacts` 会整行丢弃。** 单据表里 `supplier_id/customer_id` 常为 `0`
    或指向已删联系人；tenant 1 那两张 draft 采购单的 `supplier_id` 就是 `1`（无此联系人）与 `0`
    ⇒ INNER JOIN 把两行全丢，界面显示"无在途进货"。
    **纪律**：列页/只读统计一律 `LEFT JOIN`；宁可显示空名字，也不要静默少行。
33. 🔴 **懒建表函数里的 DDL 清单必须覆盖所有被引用的表。** `bin_locations` 的 DDL 被误放进
    `check_scheduled_price_lists()` 的**函数体**里（13518 行）⇒ **全新库（新租户）没有该表**，
    `putaway_strategy` / 补货查询对新库直接 `no such table`。
    **纪律**：① 建表语句只放"初始化 / 懒建表"函数里，不塞业务函数体；② 记住测试库是**全新库**——
    只在生产存在的表，在测试里才会暴露；③ 新写一个读别人表的函数时，把该表的懒建表一并纳入前置。
34. ⭐ **部署窗口纪律 + 日志侧证据法。** 本仓**多会话并行**（见
    `topics/parallel-dev-protocol.md` §四：同一时刻只允许一个会话碰生产）。动生产前后各看一眼
    `find /opt/hergent-erp -maxdepth 2 -name "*.py" -mmin -20` 与
    `systemctl show hergent-erp -p ActiveEnterTimestamp`，确认别人的窗口**已关**再上。
    **证据法**：`journalctl -u hergent-erp --since "<重启后>" | grep -c -e "query failed" -e "Traceback"`
    应为 **0**，并与修复前的同一窗口对比（本轮 **15 → 0**）—— 这比"接口返回 200"更能证明
    「**静默失败**真的没了」。
35. 🔴🔴 **懒建表禁止用「进程级」幂等缓存 —— 表是每租户一套（v465g 实测，本轮最严重的一个）。**
    本模块 `_ensure_wh()` 初版写的是：

    ```python
    _ensured = False                      # ← 模块级（= 进程级）
    def _ensure_wh(db):
        global _ensured
        if _ensured: return
        for stmt in _DDL: db.execute(stmt)
        _ensured = True
    ```

    看着很合理（"只建一次"），**但 `wh_*` 六张表是每租户库一套**（`tenant_<id>.db` 各一份）——
    于是**只有第一个**调用它的租户真的建了表，其余租户被 `_ensured=True` 跳过。
    线上实证（`/opt/hergent-erp`）：

    | 库 | `wh_*` 表 |
    |---|---|
    | `tenant_10.db` | 6 张**齐全**（P1 真机验收走 demo 登录，先命中它） |
    | `tenant_1.db`（老板自家） | **一张都没有** ⇒ 出库/出入库/盘点三族页面点一下就 500 |
    | `erp.db` | 无（主库不当业务库用） |

    **纪律**：① 任何**懒建表 / 懒迁移 / 缓存计算**的幂等标志，先问"这个对象是**进程级**还是
    **租户级**"；租户级对象一律**每次入口都跑**（`CREATE TABLE IF NOT EXISTS` 本身就是幂等，
    已存在时只是一次极廉价的 no-op），**幂等由 SQL 保证、不由进程标志保证**；
    ② 若确实要缓存，key 必须是 **租户 / 库文件路径**，不能是布尔；
    ③ ⭐ **单租户测试结构性地测不出这类缺陷** —— P1 影子验收 135/135 全绿就是这么漏掉的。
    多租户代码的验收**必须两个租户 + 两种顺序**都跑（见坑 36）。
36. 🔴 **验收"某种写法已消失"时，不能用会匹配到注释的文本 grep —— 改 AST。**
    v465g 验收脚本 Phase 4 初版写的是 `"global _ensured" not in src`，结果 **2 条假 FAIL**：
    修复说明的注释块里**逐字引用了旧实现的这几行**（为了让后人看懂"修了什么"），
    文本匹配命中的是**注释**，不是真代码。
    **纪律**：① 校验"代码里不再有 X"用 `ast.parse` + `ast.walk`（注释与字符串**天然不在语法树里**）：
    `ast.Global.names` / `ast.Name.id` / `ast.Attribute.attr`；
    ② 判别力**必须自证**：把同一组断言打到**修复前**的版本（`git show HEAD:<file>`）上，
    断言**必须失败**，否则"全绿"没有意义；③ 行为型取证写相位反转（本模块 P1 的
    `_ensure_wh` 就靠"内联复刻旧实现 ⇒ 第二个租户必然缺表"证明断言有判别力）。

### 8.G 信封 / 标题 / 参数化（v465h 实测，P2 六页）

37. 🔴 **`api()` 已经剥掉一层 `{success,data}` —— 仓储层不许再剥第二次。**
    `client.js:248` 的契约是 `data.data !== undefined ? data.data : data`。
    v465h 初版 `freezeGet` / `kitGet` 写成 `.then(d => (d && d.data) || null)` ⇒ **恒 `undefined`**。
    **症状极具误导性**：点「查看」报「冻结单不存在」，与"后端真没这张单"**长得一模一样**，
    而列表页完全正常（列表走 `_list()`，没有二次剥壳）。
    **纪律**：① 信封归一化只收在 `src/api/wh.js` 一处，页面不许写 `d.data || d.items || d`；
    ② 详情方法契约统一为「给对象，或给 null」，判真身用**业务字段**（`d.id`）而不是信封字段；
    ③ ⭐ 本地探针**必须给详情端点铺桩** —— 只铺 list，点「查看」就进错误态，明细用例根本没被执行。
    实测代价：修前 4 个明细用例 **3 FAIL / 1 PASS**，而唯一 PASS 的恰好是**没多剥一层**的
    `/api/wastage/{wid}`（它后端返回的是自定义 `{order,items}`，没有 `data` 可剥）。

38. 🔴 **页面 `<h2>` 必须与 `meta.title` 逐字一致。**
    v465h 初版「损益单」页把 h2 写成「损益单（报损单）」，而 `meta.title` 与侧栏都是「损益单」
    ⇒ 同一个页面出现**两个不同标题**（导航一个、页头一个）。
    口径澄清属于**副标题**（`.page-sub`），不要塞进 h2。
    **纪律**：探针的「标题逐字命中」这条断言**同时**守住 `meta.title` ↔ h2 的对齐；
    h2 一带后缀这条立刻红 —— 它比人眼可靠（人眼反而会觉得"（报损单）写得挺清楚"）。

39. 🔴 **一个组件参数化服务两个导航条目，用 `props` object-mode 注入。**
    「静态盘点单（整仓/部分）」= `StaticFreeze.vue` + `props:{scope:'full'|'partial'}`；
    「组合单/拆分单」= `KitOrder.vue` + `props:{type:'assemble'|'disassemble'}`。
    路由侧写 `props: { scope: 'full' }`（**object 模式**），不要用函数式或 query 参数。

    P2 把 `/wh/pnl` 落成真身后**该反例失效**（占位断言套到真页上会静默无意义）。

40. 🔴 **同一个"集合"在相邻端点上的信封可以完全不同 —— 归一化必须在 api 层，页面零兜底。**

### 8.H 批次账 / 路由遮蔽 / 共享原语（v465i 实测，清 P2 带出的后端欠账）

42. 🔴 **「不带 `ORDER BY` 的 `fetchone()`」取哪一行由*索引*决定，不是插入顺序。**
    这正是 `inventory_adjust` 的取法（`SELECT ... WHERE product_id=? AND warehouse_id=?`）。
    v465i 判别力脚本第一版把批次命名成「B01=过期、B02=新鲜」，并**假设**它会取到先插入的 B02，
    结果旧实现**碰巧扣对了** ⇒ 8 条判别断言里 2 条在旧代码上也 PASS，**判别力归零**。
    真相：`inventory` 上有 `(product_id,warehouse_id,batch_no)` 索引 ⇒ 扫描顺序按 **batch_no 字典序**，
    与插入顺序无关。
    **纪律**：写"证明旧实现错"的场景时，**先弄清被测 SQL 的实际取行顺序**，再刻意让
    「旧实现的顺序」与「正确顺序」**相反**（本轮改成 新鲜=B01 / 过期=B99：索引序取 B01、
    效期序取 B99）。两种顺序一致时，再严密的断言也证明不了任何事。

43. 🔴 **批次账的扣减与回滚必须成对修；只修扣不修退，撤销一次就打回原形。**
    本轮 `create_wastage_order` 改成批次精确扣减后，`reject_wastage`（撤销）若仍用批次盲的
    `inventory_adjust(+qty)`，就会「从 B99 报损、却加回 B01」——总量看着平了，**批次账是错的**，
    而错账会自己往下传（下一次按批次报损 / FEFO 出库照着错账走）。
    ⚠️ **这类缺陷用"终态断言"抓不到**：旧实现的「扣错批」与「加回错批」**正好抵消**，
    终态与正确实现**逐字相同**。
    **判别力做法**：改用 `inventory_logs.before_qty` **反推撤销究竟作用在哪个批次上**
    （撤销前 B99 已被扣光 ⇒ `before_qty` 必须是 0；旧实现打在 B01 上 ⇒ 是 20）。
    ⇒ 通用教训：**当"错误 A"与"错误 B"会互相抵消时，终态断言无效，必须看过程数据。**

44. 🔴 **同一类修复第二次出现时，就该提升为共享原语，而不是再写一份骨架。**
    「不过滤效期的批次扣减」这条骨架的第一份在 P1 的 `db/queries/wh.py::_gross_deduct`
    （当时为了绕开 `inventory_adjust` 的批次盲而写）。v465i 清欠账时发现**报损单**与
    **组拆单**各自又被同一个批次盲咬了一口 —— 若再各写一份，就是这套骨架的第 3、4 份拷贝。
    ⇒ 把它提到 `db/queries/inventory.py` 成 `gross_deduct`，与 `fefo_deduct` 成对
    （一个管销售、一个管非销售）；`wh.py` 只留一个委派壳，2 个内部调用点零改动。
    **判据**：一个函数里出现「排序键 + `quantity>=?` 原子守卫 + 写 inventory_logs」这套组合，
    就说明它是共享原语的候选 —— 写第三份之前先停下来找前两份。

45. 🔴 **静态路由段必须排在 `{id}` 之前 —— 本模块内已第二次遇到。**
    `/api/wastage/{wid}` 注册在 `/summary` 与 `/suggest-from-expiry` **之前** ⇒ 后两者被当成
    `wid: int` 解析 ⇒ **恒 422**，这两个端点从 v92 落地那天起就没能用过（P2 盘点时才发现）。
    **纪律**：① 同一前缀下，**先注册所有静态段，最后注册 `{id}`**；
    ② 有 `{id}` 的模块，**每加一个静态端点都要回头看一眼顺序**（这是"加了新功能才发现旧功能没通"的典型）；
    ③ 能力盘点时对每个端点**实测**，不要只看路由定义存在 —— 「路由写在那」≠「路由能访问」。
    （`/{id}/reject` 有两段，不会被单段的 `/{id}` 吃掉，留在后面是安全的。）

46. ⭐ **`tenant_db_init()` 建出的租户库缺表 —— 登记时以为缺 4 张，实测 **75 张**（v465j 已修）。**
    这两张表的 DDL 只在 `_ensure_tenant_module_tables()` 里（`erp_db.py:1442` 那段 self-heal），
    而 `tenant_db_init()`（`:13880`）**不调**它；真正调它的是两处**模块级**调用（`:15232`/`:19030`），
    只在 import 时对「当时已存在」的 `tenant_*.db` 补表。
    ⇒ **新建的租户要等下一次服务重启**才有这两张表，期间组拆单 / 静态盘点单会
    500 `no such table`（本轮实测：`tenant_db_init(999)` 出来的 234 张表里确实没有）。

### 8.I 新租户建库 / schema 对账（v465j 实测）

47. 🔴 **补「缺哪些表」时，绝不能枚举表名清单 —— 权威源必须是"真实存在的库"。**
    v465j 上线实测：**主库 328 张 / 租户库 391 张**，差集 **75 张**全是「只存在于租户库」的表
    （`kit_orders` `stock_freezes` `wh_outbound_orders` `fund_*` `loss_*` …）。
    这 75 张的 DDL 散落在 `erp_db.py`(25) `routers/loss_accounting.py`(9) `db/queries/wh.py`(6)
    `routers/collections.py`(3) 等 **16+ 个文件**里，另有 **14 张**（含并行会话在做的 `fund_*`）
    连 `CREATE TABLE` 都 grep 不到（f-string 拼表名）。
    ⇒ 任何"把表名抄进清单"的修法都是**第二份会漂移的清单**（v465g 坑 35 同族）。
    **正确做法 = 对账**：权威源 = 主库 ∪ 其它租户库（系统里已经存在的**真实库**），
    把新库缺的表补上 —— 不知道有哪些表也能补对，且**自愈**：任何模块将来 lazy 建的新表，
    只要某个租户库里有，新租户就能拿到。
    **纪律**：遇到"把 X 补上"类需求，先问「X 的权威源在哪」；
    答不出就说明该用对账，不该用清单。

48. 🔴 **`iterdump()` 复制不到 FTS5 虚表** —— 顺带修掉的第二个问题。
    `tenant_db_init()` 的复制循环是 `if line.startswith("CREATE TABLE") or startswith("CREATE INDEX")`，
    而 FTS5 虚表在 `iterdump()` 里是 **`CREATE VIRTUAL TABLE ...`** ⇒ 被静默跳过
    ⇒ 新租户库**没有** `products_fts` / `contacts_fts`。
    这与 v131f 注释里写的「tenant_10 缺 products_fts/contacts_fts → 演示租户搜索必然 500」
    **是同一个病根**（那边是历史租户没补，这边是新租户没复制）。
    **纪律**：schema 复制不能只认 `CREATE TABLE` 前缀；凡是"另走一段"的特殊对象
    （虚表 / 触发器 / 视图），复制侧要么一并处理，要么显式交给下游自愈段 —— 别让它静默缺失。

49. 🔴 **判别力断言与契约断言必须分开归组，否则"附属断言"会被误判成回归。**
    v465j 第一版把 B4（"补进来的表必须是空表"）放进了「新旧都必须 PASS」的契约组，
    结果 **旧树 FAIL** 被当成回归 —— 但旧树 FAIL 的真正原因是「连表都没补进来」，
    它 FAIL 得**完全正确**，且与 B1-B3 同源。
    **纪律**：判据的依赖链要先理顺 —— 「表存在」是「表为空」的**前提**，
    前提在旧代码上不成立时，结论断言必然 FAIL，**它不是回归，是判别力**。
    反过来也有一条：**契约组里不能放恒假断言**（v465j 第一版 D1 写成
    "排除集里的表不在租户库"，实测 `_migrations` / `tenants` 本来就在租户库里 ——
    是主库复制带过去的，与本轮改动无关 ⇒ 新旧都 FAIL 的**恒假**断言，零判别力）。

## 0.1 现状盘点（基于代码实证，非推测）

| 层 | 现状 | 一线 ERP 对应物 |
|---|---|---|
| 数据模型 | `rebate_target_rules`（维度仅 **brand/product**；`trigger_mode: on_target/tiered`；`tiers_json` 单块 JSON）、`rebate_achievements`（周期键 + 维度 + 达成值）、`rebate_contracts`（年度合同 + `brand_id`）、`rebate_contract_months`（月度分解）、`rebate_accruals`（月度计提，含 `receipt_id`） | SAP Condition Record + Scale（**带有效期与版本链**）、Business Volume 表、Oracle Offer、D365 Rebate Agreement |
| 计算内核 | `domain/rebate_calc.py`：`compute_rule_rebate`（规则口径）、`calc_contract_amount`（合同累进口径） | SAP Scale 计算（graduated / non-graduated） |
| 口径债 | **两套并存**：规则 `rebate_rate`＝小数（0.03），合同 `rebate_pct`＝百分点（3）——代码注释自认"历史遗留" | SAP/Oracle 全系统统一单位 + 显式 UoM |
| 前端 | 4 Tab：仪表盘 / 目标规则 / 达成填报 / 年度合同；2122 行单文件 | D365 工作区 + 向导式配置 + Claim 工作队列 |
| 可复用资产 | **`bpm_engine.py`（完整 BPMN-lite：节点/网关/定时器）**、`routers/reconciliation.py`（供应商对账，已含 rebates）、`routers/cron` 定时能力 | 审批流与对账无需重造 |
| 缺失项 | **无版本、无审批状态机（`settled` 仅 0/1）、无冲销（reversal）、无溯源单号、无多币种、无异步批处理、无审计日志** | — |

### 总体判断（先讲结论）

> **你们的架构在"能算对数"上是及格的，与国际一线 ERP 的真实差距不在算法，而在三件事：**
> **① 没有版本与有效期链 → 规则一改就"说不清当时按哪版算的"；**
> **② 没有状态机与审批 → 结算是"一按到底"的布尔跳变，无法审计；**
> **③ 没有业务量（Business Volume）自动累积 → 达成靠填报，计算再准也是"人工输入的函数"。**
>
> 反常识的一点：**不要先做多组织多币种**。系统当前零外币、单一主体，上多币种会把所有金额字段变成"金额+币种+汇率+换算日期"四元组，成本暴涨而收益为零。**先补版本 + 状态机 + 审批，这三件才是从"能用的工具"升级为"可卖的产品"的分水岭。**

## 1. 维度一：前端交互

### 1.1 目标设定与下达

| 项 | 内容 |
|---|---|
| **差距** | SAP 的 Rebate Agreement 与 D365 的 Rebate Program 都是**向导式（Wizard）多步创建**：选合作方 → 选范围（品类/客户/商品）→ 设周期 → 设阶梯 → 预览 → 提交审批。你们是**单页表单一次性填完**（`contractForm`），阶梯配置与月度分解混在同一弹窗，认知负担高、易漏填。 |
| **方案** | ① 把「录入年度合同」弹窗拆为 **4 步向导**（基本信息 → 适用范围 → 返利政策 → 预览确认），每步独立校验，顶部显示步骤条；② 增加**「引用上一年度合同」**按钮（一键复制上年度配置，仅改年份与金额），对标 SAP 的 "Copy condition record"；③ 增加**「引用模板」**（把常用政策存为模板）。 |
| **收益** | 新建合同时间从 ~5 分钟降至 ~90 秒；漏填导致"计提时才发现没挂规则"的返工（当前 `accrue_rebate` 会直接报错）**消除**。 |
| **优先级 / 成本** | **P1**；**短期**；前端约 **2～3 人日**（纯前端，无后端改动，复用现有 `contractForm` 数据结构） |

### 1.2 目标分解与达成率计算

| 项 | 内容 |
|---|---|
| **差距** | 当前月度分解是**手工逐月填金额**（`buildMonthsMap` 平均或全零），没有**按历史权重/季节性自动分解**；D365 支持按历史同期占比、按周权重、按增长率三种分解策略。 |
| **方案** | ① 月度分解区加 **「分解方式」下拉**：平均 / 按去年同期占比（自动读 `rebate_achievements` 去年数据算权重）/ 自定义比例；② 分解后即时显示 **「合计 vs 年度目标」校验条**，不等保存就提示倒挂；③ 支持**锁定已发生月份**（已计提月份不可改，对标 SAP 期间锁）。 |
| **收益** | 分解准确率提升，消除"12 个月加起来不等于年度目标"的低级错误；**已计提月份被误改导致返利重算**的资损风险归零。 |
| **优先级 / 成本** | **P1**；**短期**；**1～2 人日**（前端 + 复用现有月度数据接口） |

### 1.3 返利政策配置（阶梯 / 累进 / 按品类 / 按客户）

| 项 | 内容 |
|---|---|
| **差距（关键）** | ① **维度只支持 brand/product，缺「按品类」「按客户」「按渠道」**——你明确要求的按品类/按客户当前**做不了**；② **`tiered` 是"命中档 → 全量×该档率"（non-graduated），不是累进（graduated）**。SAP 明确区分两种 Scale 类型且累进是主流；你们的合同侧 `calc_contract_amount` 反而**是累进**，导致"规则侧与合同侧算法不一致"，同一业务两种算法并存。 |
| **方案** | ① 规则表 `dimension` 扩展 `category`（品类）/ `customer`（客户）/ `channel`（渠道），前端下拉同步；② **阶梯加「计法」显式开关**：`scale_type = 'graduated'（累进）/ 'non_graduated'（全量按档）`，UI 上用一行说明文字 + 实时示例让业务方看懂差异；③ **统一规则侧与合同侧算法**为同一函数（见 §2.3）；④ 阶梯编辑改为**可拖拽排序的表格**（当前 JSON 无排序校验）。 |
| **收益** | 支持按品类/按客户政策（**打开新的可卖场景**）；消除"全量按档 vs 累进"的口径歧义——这是**返利争议最常见的技术根因**，预估可**消除 80% 以上的对账分歧**。 |
| **优先级 / 成本** | **P0**；**短期（维度扩展+计法开关）约 3～4 人日**；**中期（算法统一与迁移）约 5 人日** |

### 1.4 返利计提与预估

| 项 | 内容 |
|---|---|
| **差距** | ① 计提是**单合同单月点击式**（`accrue_rebate(contract_id, month)`），无**批量计提**与**作业状态追踪**；② 无 **What-if 模拟器**："如果 Q4 多进 200 万，返利变多少？"——Oracle OTM 与 D365 都把模拟器作为标配；③ 无**差额计提（Delta Accrual）**：SAP 的核心能力，重算后只补差额而非整月重来。 |
| **方案** | ① 「月度全景」页加 **「批量计提本月」** 按钮：异步作业 + 进度条 + 结果清单（成功/跳过/失败逐条可查）；② **新增「返利试算器」Tab**：拖动达成金额滑块 → 实时显示命中档位、返利金额、边际返利率（"再多进 100 万多拿多少"），这是**最打动经销商老板的交互**；③ 重提时按 **Delta 口径** 生成差异行。 |
| **收益** | 月末计提从"逐合同点 N 次"变为**一次点击**；试算器直接支撑**与厂家谈判**（谈判前先算出最优进货量），是高感知价值功能。 |
| **优先级 / 成本** | **P0（试算器）/ P1（批量）**；**短期 4～5 人日**（试算器纯前端复用 `computeRebateFront`，批量需后端作业封装） |

### 1.5 核销与结算审批

| 项 | 内容 |
|---|---|
| **差距（最大）** | 结算是 `settled = 0 → 1` 的**布尔跳变**，无状态机、无审批、无冲销。Oracle 的 **Claim（索赔）机制**与 D365 的 **Deduction Management** 是这类系统的核心价值区：经销商提交 Claim → 厂商审批 → 生成抵扣/付款 → 差异再协商。你们**完全没有这一层**。 |
| **方案** | ① 建 `rebate_claims` 表 + **Claim 工作队列页**（待审 / 已批 / 驳回 / 已结算 四栏看板）；② 审批接入**现有 `bpm_engine.py`**（已具备节点/网关/定时器，无需自研）；③ 结算状态机：`draft → submitted → approved → settled → (reversed)`，**反结算不再是物理删除而是冲销凭证**；④ Claim 支持**部分核销**（本次只核销 80%，余 20% 挂账）。 |
| **收益** | 结算过程**可审计、可追溯、可驳回**，这是把模块卖给其他经销商时的**合规门槛项**（老板最怕"钱算错了还说不清"）。 |
| **优先级 / 成本** | **P0**；**中期**；**8～12 人日**（新建表 + 状态机 + 审批接入 + 前端队列页） |

### 1.6 对账与溯源

| 项 | 内容 |
|---|---|
| **差距** | 无**单笔可溯源**：`rebate_achievements` 无来源单号、无批次号、无审核状态；改一个数字不留痕。SAP 的 Business Volume 每条都指向原始单据；Oracle 的 Claim 全程留痕。 |
| **方案** | ① 达成数据加 `source_ref`（来源单号/批次号）+ `batch_id`（导入批次）+ `status`（草稿/已确认/已锁定）；② **「计算过程透明化」面板**：点任意返利金额 → 弹出"基数 234.5 万 × 命中第 2 档（80%~100%）× 3% = 7.03 万"的**完整算式链**（后端 `compute_rule_rebate` 已返回 `detail`，前端未充分呈现，属**低成本高收益**）；③ 对账页（`reconciliation.py`）直接挂接返利明细。 |
| **收益** | 与厂家对账时**从"我们的数"变成"有据可查的数"**，争议处理时间从小时级降至分钟级。 |
| **优先级 / 成本** | **P1**；**短期 2～3 人日**（透明化面板）+ **中期 3 人日**（溯源字段与批次管理） |

## 2. 维度二：后端架构与数据模型

### 2.1 数据模型：版本化（**最高优先级**）

| 项 | 内容 |
|---|---|
| **差距** | `tiers_json` 是**单块 JSON 直接挂在规则行上**，改一次就覆盖一次，**没有任何历史**。SAP 的 Condition Record 以**有效期 + 版本**存储，可查询"2026-03-15 那天生效的是哪一版"。**规则频繁变更时，你们无法回答"上季度这笔返利是按哪版政策算的"**——这是合规硬伤。 |
| **方案** | ① 新增 `rebate_rule_versions` 表：`(rule_id, version_no, valid_from, valid_to, snapshot_json, changed_by, change_reason, status)`；② 规则变更时**不 UPDATE 原行，而是关闭旧版本有效期 + 插入新版本**（SAP 标准的 "delimit and insert" 模式）；③ 计算时按**业务发生日期**选版本（`as_of_date` 参数贯穿 `compute_rule_rebate`）；④ 计提结果表 `rebate_accruals` 增加 `rule_version_id`，**永久锁定"算的时候用的是哪版"**。 |
| **收益** | 彻底解决"追溯重算"与"政策变更审计"；让"按当时版本重算"从不可能变为一次查询。**这是从工具升级为产品的关键一步。** |
| **优先级 / 成本** | **P0**；**中期**；**8～10 人日**（建表 + 双写迁移 + 计算链改造 + 历史数据回填） |

### 2.2 状态机与冲销（Reversal）

| 项 | 内容 |
|---|---|
| **差距** | `settled`（0/1）无法表达"审批中""部分结算""已冲销"；`uns_settle_rebate` 是**删除式反结算**，不留痕迹。SAP 用 **Delta Settlement + Reversal Document** 保证账面可追。 |
| **方案** | ① 统一状态枚举：`draft / submitted / approved / partially_settled / settled / reversed`；② 所有冲销写成**反向记录**（`amount` 取负 + `reversal_of_id` 指向原记录），**永不物理删除**；③ 加 `rebate_audit_log`（谁、何时、从什么值改到什么值、原因）——D365 的标准审计能力。 |
| **收益** | 结算链路**可审计、可对账、可回滚**；误操作从"数据丢失"降级为"一条冲销记录"。 |
| **优先级 / 成本** | **P0**；**中期**；**5～7 人日**（与 §1.5 Claim 合并实施可省约 3 人日） |

### 2.3 计算内核：消除双份实现与口径债

| 项 | 内容 |
|---|---|
| **差距** | ① 前端 `computeRebateFront` 与后端 `compute_rule_rebate` **双份实现**（代码注释已用 R40 互相警告）——这是**必然漂移**的结构；② 规则 `rebate_rate` 小数 vs 合同 `rebate_pct` 百分点**两套单位**；③ 硬编码 `round(x, 2)`，无精度策略配置；④ 累进/全量两种口径散落在不同函数。 |
| **方案** | ① **前端不再自带算法**，改为调用后端 `/simulate` 批量接口（前端只做渲染）；或退一步：用**同一份规则 JSON schema + 共享常量表**并加**契约测试**（前后端跑同一组用例比对结果）；② **统一为百分点**存储（业务可读），转换只在展示层；③ 精度策略外置为 `rounding_policy`（四舍五入/向上/向下 + 小数位）；④ 所有返利计算走**单一入口函数**，累进/全量作为该函数的 `scale_type` 分支。 |
| **收益** | 消除前后端结果漂移（**当前仪表盘预估与后端计提可能不一致**）；口径统一后新增政策类型只需改一处。 |
| **优先级 / 成本** | **P0**；**短期（统一入口+契约测试）3～4 人日**；**中期（单位统一迁移）5 人日** |

### 2.4 业务量（Business Volume）兼容层

| 项 | 内容 |
|---|---|
| **差距** | 达成数据靠手工/Excel 填报，**无单据级来源**。SAP 的 Business Volume 从销售/采购单据自动累积，是返利计算的**可信数据源**。 |
| **方案** | ① 建 `rebate_business_volume` 表：`(period, dimension, scope_key, source_type, source_table, source_id, amount, qty, currency, posted_at)`，作为**统一事实表**；② 手工填报与 Excel 导入**写入同一张表**并标记 `source_type='manual'/'excel'`，未来对接 ERP 单据只需新增 `source_type='document'` 的写入器，**上层计算完全不用改**；③ 现有 `rebate_achievements` 保留为**汇总视图**。 |
| **收益** | 为"从填报切到自动取数"铺路，**改动被隔离在数据接入层**；同时立刻获得单据级溯源能力。 |
| **优先级 / 成本** | **P1**；**中长期**；**6～8 人日**（建议与 §1.6 溯源合并做） |

### 2.5 批量计算与作业化

| 项 | 内容 |
|---|---|
| **差距** | `accrue_rebate` 是同步单条调用，无作业状态；月末几百个合同逐一点是**不可接受的操作负荷**。SAP 用后台作业（batch job）+ 作业日志，Oracle 用并发程序。 |
| **方案** | ① 建 `rebate_jobs` 表（`job_type/status/params/progress/started_at/finished_at/error_log`）；② 计提/试算/结算批量化，接口立即返回 `job_id`，前端轮询进度；③ **幂等设计**：同一 `(job_type, period, scope)` 重复提交只产生一份结果（用 `UNIQUE` 约束 + `INSERT OR REPLACE`）；④ 大批量走**分批提交**（每 500 条一 commit），避免长事务锁表。 |
| **收益** | 月末结算从"逐合同点击 + 焦虑等待"变为"一次提交 + 看进度"；失败可续跑不必全量重来。 |
| **优先级 / 成本** | **P0**；**中期**；**5～6 人日**（含前端进度轮询） |

## 4. 复杂场景专题

### 4.1 返利规则频繁变更

**一线实践**：SAP 用 **"Delimit & Insert"**（关闭旧有效期 + 插新记录）而非 UPDATE；Oracle 用 **Offer 版本 + 生效日期**；D365 用 **Rebate Agreement 修订版**。

**推荐方案（三层策略）**：

| 层 | 做法 |
|---|---|
| **存储层** | 规则与阶梯**永不 UPDATE**，只做有效期分割（§2.1）。任何时点的政策状态可由 `as_of_date` 精确重建 |
| **计算层** | `compute_rule_rebate(rule, ...)` 增加 **`as_of_date` 必填参数**；计提时按**业务发生月**取版本；重算历史时传历史日期即可得到**当时的结果** |
| **结果层** | 计提/结算记录**冗余保存 `rule_version_id` + 计算快照 JSON**（"算的时候用的档位与比率"）。**即使规则后来被改，历史结果也不受影响** |

**变更时的三种处理口径**（必须在 UI 显式让用户选，这是业务决策不是技术决策）：
1. **不追溯（Prospective）**：新政策只对未来生效，已计提不动 —— 默认，最安全
2. **追溯重算（Retrospective）**：按新政策重算已发生期间，**生成差额计提行（Delta Accrual）**，不删除原记录 —— 可审计
3. **部分追溯**：指定起始月，之前不动

> **关键设计**：无论哪种口径，**原记录永不删除**，差异以 Delta 行体现。这样"改错了"可以再改回来，账面始终自洽。

**成本**：含在 §2.1（8～10 人日）。

### 4.2 多组织与多币种

**先说结论：当前不建议做，但数据模型要预留。** 全库检索 `currency` 零命中，说明业务当前无外币；多组织同理。**过早引入会使每个金额字段退化为四元组（金额/币种/汇率/换算日期），成本翻倍而收益为零。**

**若未来确有需求，正确做法（对标 SAP 的 Company Code + Currency Type 体系）**：

| 主题 | 方案 |
|---|---|
| **多组织** | 引入 `org_id`（公司主体）+ `rebate_rule_org_scope`（规则适用组织范围）。**关键设计：目标与达成必须同组织对齐**，跨组织调货需 `intercompany_flag` 标记并明确计入哪一方返利基数（这是多组织返利最容易算错的地方） |
| **多币种三币种法**（SAP 标准） | ① **交易币种**（原始单据币种）② **本位币**（主体记账币种，返利政策与计提**只在本位币上定义与计算**）③ **集团币**（合并报表用）。**绝不在交易币种上做阶梯比较**——汇率波动会导致档位跳动 |
| **汇率** | 建 `exchange_rates(rate_date, from_ccy, to_ccy, rate_type, rate)`；计提用**月度平均汇率**，结算用**结算日即期汇率**，差额进**汇兑损益**科目。汇率缺失时 **fail-fast 报错**，绝不静默按 1.0 计算 |
| **阶梯判定** | 政策阶梯阈值以**本位币**定义；跨币种达成先按既定汇率折算再比较，**折算汇率与日期必须记录在计算快照里**（否则无法复算） |
| **合并** | 复用现有 `routers/consolidation.py`（合并报表路由已存在） |

**成本**：**多组织 8～10 人日 + 多币种 12～15 人日**（且需全量回填历史数据）。**建议触发条件：出现第一笔外币采购或第二个经营主体时再启动。**

### 4.3 大额批量计算性能

**现状瓶颈**：单合同单月同步计提；`_achievement_index` 已做内存索引（这点做得好），但无批量作业、无增量累积、SQLite 单文件写锁。

**分层优化路径（按性价比排序）**：

| 优先级 | 手段 | 效果 | 成本 |
|---|---|---|---|
| ★★★ | **增量累积（Delta Accrual）**：不为每次查询重算历史全量，只算"本期新增达成 → 新增返利"，结果落 `rebate_accruals`。SAP 核心手法 | 计算量从 O(全历史) 降为 O(本期)，**性能提升 1～2 个数量级** | 3 人日 |
| ★★★ | **预聚合事实表**：按 `(period, dimension, scope_key)` 预先聚合达成与返利，仪表盘读聚合表而非明细扫描 | 仪表盘从秒级降至毫秒级 | 2～3 人日 |
| ★★ | **作业化 + 分批提交**（§2.5）：每 500 条 commit 一次，避免长事务持有写锁 | 消除大批量时的全局锁表 | 含在 §2.5 |
| ★★ | **索引补齐**：`(contract_id, month)`、`(period, dimension, scope_key)`、`(rule_id, version_no, valid_from)` 覆盖索引 | 查询提速 3～10 倍 | 0.5 人日 |
| ★ | **计算与 I/O 分离**：纯函数计算在内存中批量完成，最后一次批量写入（当前 `compute_rule_rebate` 已是纯函数，**只需改调用方式**） | 消除逐条写放大 | 1 人日 |
| ★ | **SQLite 调优**：`PRAGMA journal_mode=WAL`、`synchronous=NORMAL`、批量期临时关闭 `foreign_keys` 检查 | 写吞吐提升 3～5 倍 | 0.5 人日 |
| （远期） | **迁 MariaDB/PostgreSQL + 读写分离** | 支撑多租户 SaaS 规模 | 15～25 人日，**当前不必要** |

> **性能红线建议**：单租户 **10 万行/年达成 + 500 规则** 以内，SQLite + 上述优化完全够用（毫秒～秒级）。**超过此量级再考虑换库，不要提前优化。**

## 6. 明确建议「不要做」的清单

在做加法之前，这几件事**建议明确不做**，避免把模块做成又一个重型 ERP：

1. **❌ 不要现在做多币种多组织** —— 当前零收益、成本巨大、会污染所有金额逻辑。只预留字段。
2. **❌ 不要自研审批流** —— 现有 `bpm_engine.py` 已是完整的 BPMN-lite（节点/网关/定时器），直接接。
3. **❌ 不要重造对账模块** —— `routers/reconciliation.py` 已能取供应商 PO/expenses/**rebates**，挂接即可。
4. **❌ 不要为"将来可能"的需求提前抽象** —— 你们的优势是轻量 + AI-driven，重型抽象会拖慢一切并让非技术维护者失控。
5. **❌ 不要追求与 SAP 功能对等** —— 目标客群是经销商老板，**D365 的 Claim 工作量级 + SAP 的版本严谨度**是上限参考，不是功能清单。

## 7. 与 AI 副驾定位的协同建议（差异化机会）

一线 ERP 做得重、做得贵的地方，恰好是 AI 可以跳过的地方：

| 传统 ERP 的痛点 | 你们可以用 AI 弯道超车 |
|---|---|
| 政策配置复杂、需培训 | **自然语言配置**："蒙牛低温全年 2000 万，超 80% 部分按 3.5% 累进" → AI 直接生成结构化规则 + 可视化预览 |
| 达成需手工填报、易错 | **Excel/截图智能识别入库**（已有 Excel 导入 + Hermes 能力，可扩到图片识别） |
| 争议需人工核对 | **AI 对账助手**：上传厂家对账单 → 自动比对本方计算 → 标出差异行并**生成争议说明** |
| 谈判靠经验 | **试算器 + AI 建议**："按当前进度，Q4 再进 180 万可跨档，多拿 6.3 万，建议进货量 180～220 万" |

> **护城河判断**：**算法本身不是护城河**（SAP/Oracle 都有且更全）。护城河是**「低温奶行业的政策语义理解 + 老板看得懂的交互 + AI 把复杂配置变一句话」**。建议把前两批中省下的精力，重点投在 ★★★ 的**试算器**与**自然语言配置**上。

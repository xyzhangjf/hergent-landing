## 2. 收口前真实状况（动手前盘点）

- 采购单 `purchase_order_update` 是「整单重写」：只要状态不在 `draft/pending_approval/cancelled` 就整单拒改——**粒度太粗**，已提交但未入库的单（如 `pending_approval`/`confirmed`）连备注都改不了，而作废单（cancelled）反而能整单重写，逻辑反了。
- 采购单 `purchase_order_update_header` 只改安全字段，但**没有任何状态/字段校验**：已入库（received）的单照样能改仓库、改期望日期，与「仓库锁死」的业务预期冲突。
- 全仓**无 `version` 列**，并行编辑无并发保护；多人同时改同一单会互相静默覆盖。
- 销售/调拨/退货单**无独立编辑函数**，它们的「改」只发生在状态跃迁（由第 3 项守卫），本项不碰。

## 3. 字段锁设计

### 3.1 相位（三档，单一源 `_phase`）

| 相位 | 触发条件 | 可改范围 |
|---|---|---|
| `full` | `draft`；采购单 `cancelled`（保留怪癖） | 整单（核心字段 + 安全字段） |
| `submitted` | `pending_approval`/`approved`/`confirmed`/`picking`/`completed` | 安全字段 + 同仓（未入库时） |
| `terminal` | 其余（含 `received`/`partial`/`returned`/`signed`/`cancelled` 非采购） | 仅安全字段 |

### 3.2 字段分类

- `_CORE_FIELDS`（按单据类型）：supplier/customer/warehouse/items/product_id/quantity/unit/unit_price/amount/total_amount；销售单另含 discount/tax_rate/tax_amount/driver_id/vehicle_id/delivery_date/delivery_address。
- `_SAFE_FIELDS`：note / handler / department_id / expected_date / order_date。
- `_PO_STOCKED_STATUS = (received, partial, returned)`：已入库，仓库锁死，连 `warehouse_id` 都不让改。

### 3.3 乐观锁习语

```
UPDATE purchase_orders SET ... WHERE id=? AND status=?   -- 令牌=提交时的 status
rowcount == 0  ⇒  刚被别人改过状态，本次修改未生效，请刷新后重试
```

零迁移、不回填；复用业务已有的 `status` 列做并发令牌。

## 6. 遗留缺陷 / 未做

- **销售/调拨/退货单字段级锁定未做**：它们无独立编辑函数，现状是「状态守卫兜底 + 整单重写在状态闸门」，提交后字段并不按白名单逐字段锁。需后续评估是否要加编辑入口并按 `_phase` 收口（建议阶段 2 统一做，避免采购单孤军）。
- **同状态并发改不同字段仍可能互相覆盖**：乐观锁只挡「状态被别人改过」，同一状态并行改不同字段不挡。业务可接受（提交后字段基本锁死，并行编辑极罕见）。
- **采购单 `cancelled` 仍归 `full`**：保留原 `purchase_order_update` 把作废单重新整单保存并维持作废的怪癖；若未来要把作废单也锁死，需先确认回滚/重开流程不受影响。
- **未部署**：与第 1/3 项一起攒够再统一上线；部署前仍待定第 1 项遗留的 `rebuild_balances()` 历史库存余额一次性重建。

## 7. 风险与落地步骤

- **风险**：字段锁改动只接了采购单两处入口；若后续在别处新增编辑入口，必须也查 `editable_fields`，否则会出现「采购单已锁、别的入口还能改」的绕过。护栏脚本（`stage1-doc-state-guard*`）目前只盯状态守卫，未盯字段锁——建议在部署前补一条静态护栏：所有 UPDATE 采购单表头的语句，SET 字段必须落在 `editable_fields` 集合内（或带 `# field-lock-exempt` 注释）。
- **落地步骤（部署时）**：
  1. 先 `git commit` 当前 vNNN（构建号注入需要）→ `vite build` → 部署前端。
  2. 后端：把 `stage1-accumulated.patch` 落到 `~/Documents/hergent-erp`（10 文件），`git apply` + 全量单测 + 复跑 `stage1-verify-all.py`。
  3. 决定 `rebuild_balances()` 是否执行（影响历史库存余额）。
  4. 灰度：先用 boss 账号自测一笔「提交后改字段被拦 / 并发改被拦」，确认无误再放开。
- **零迁移**：不新增列、不回填，直接上线即可；回滚只需 `git apply -R` 补丁。

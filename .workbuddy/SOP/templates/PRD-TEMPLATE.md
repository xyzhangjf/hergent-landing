# PRD 模板（需求文档）

> **用途**：新功能立项 / 大改动前必写。即便是 P0 也至少 1 页纸。
> **配套**：`RISK-CHECKLIST.md` 风险评估 + `TECH-TEMPLATE.md` 技术方案。
> **AI 接到新需求时**：必须主动问「PRD 写了吗」，未写则先问 5W（什么 / 为谁 / 场景 / 验收 / 风险）。

---

## 1. 元数据

| 字段 | 值 |
|---|---|
| **PRD ID** | PRD-YYYYMMDD-<短名> |
| **作者** | 张俊峰 |
| **创建日期** | YYYY-MM-DD |
| **最后更新** | YYYY-MM-DD |
| **优先级** | P0 / P1 / P2 |
| **风险等级** | R0 / R1 / R2 / R3 / R4 |
| **影响端** | Web / 小程序 / 后端 / 桌面 / 全端 |

---

## 2. 用户场景（核心）

> 一句话讲清楚：**谁**在**什么场景**下想**解决什么问题**？

```
场景：<用户类型>在<业务场景>下，<具体痛点/动机>
例如：销售员在每日早 8 点，需要把微信里客户的报单转成厂家系统下单格式
```

---

## 3. 业务目标与验收口径

### 3.1 业务目标

> **这个改动让什么变好**？用量化的口径。

- [ ] 例：销售员每日下单耗时从 30 分钟 → 5 分钟
- [ ] 例：返利计算误差从 ±5% → ±1%
- [ ] 例：客户自助下单率从 0% → 30%

### 3.2 验收口径（功能完成 = 全部勾完）

- [ ] 验收项 1：<具体可测功能>
- [ ] 验收项 2：<具体可测功能>
- [ ] 验收项 3：<边界场景>
- [ ] 验收项 4：<错误处理>
- [ ] 验收项 5：<向后兼容（已有 11 个共享接口是否被影响）>

---

## 4. 真伪需求判断（与用户对话 1-3 轮后填）

> **避免做错需求**——5 个必答问题。

| 问题 | 答案 |
|---|---|
| 哪类用户？ | <经销商老板 / 销售员 / 文员 / 财务 / 厂家？> |
| 在什么场景下用？ | <早会 / 月度对账 / 报单时 / 巡店时？> |
| 不做会怎样？ | <影响生意哪一块？数据/收入/效率？> |
| 做了能赚/省多少？ | <量化：时间/钱/风险> |
| 是否经样本验证？ | <群里 / 现场 / 真实客户访谈？> |

> **没填完 = 风险 R2+ 必须先填完再继续**。

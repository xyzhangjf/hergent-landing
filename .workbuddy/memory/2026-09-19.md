## Q29：小程序自助改密 + 忘记密码自助重置（管理员发一次性重置码）

**触发**：用户原话「小程序需要支持自助改密和忘记密码自助改密，因为可能不会给业务员/分销商/导购等分配网页登录权限，只允许登录小程序」。三条路线里用户选定**管理员发一次性重置码**。

**提交**：后端 `88f3225`（hergent-erp / upgrade/v84-international，4 文件 +367/-2）· 前端 `62f3b63`（laozhangai-product / main，25 文件 +1354/-4）

### 先审计出来的四个真实缺陷（这才是需求的本体）
1. 小程序**完全不读** `require_password_change` ⇒ 强制改密闸门在小程序侧形同虚设
2. 小程序登录页写着「首次登录请修改密码」，但小程序**没有任何改密入口**（网页端是唯一入口）
3. 两条管理员重置路径**策略分叉**：`/api/users/{uid}/password` 只要 4 位且不写 `password_changed`；`/api/auth/reset-password` 要 8 位 + 字母数字
4. **防杀进程绕过**：首次改密没做完就杀掉小程序重进，token 仍在 ⇒ 只看 token 就放行

### 为什么「忘记密码」不能真的完全自助（可复用判据）
系统里**没有任何可信身份凭据**可用于免登录验证：短信网关是占位域名 `sms-api.example.com`；`REGISTER_MODE=invite` 时 `send-code` 直接 400；生产 5 个启用账号里**真实手机号 0 个**（2 个是 `mptest`/`mptestsp` 假值）；补手机号还会牵动**已提交、正在审核**的备案材料与隐私申报。
⇒ 把「完全自助」重构为「管理员发码 + 员工自助设密码」，责任边界反而更好：**管理员全程不知道员工最终密码**。

### 🔴 关键技术判断
- **`password_reset_codes` 必须是主库表**（与 `users` 同理）：免登录路径没有租户上下文，`get_db()` 落主库；若建进 `tenant_N.db`，`/api/auth/forgot-reset` 就**查不到码**（静默不生效）
- **`CSRF_EXEMPT_PATHS` 必须加免登录路径**：未登录请求既无 Bearer 也无 CSRF cookie，漏了必被中间件 **403**
- **一次性 = CAS**：`UPDATE ... WHERE used_at=''` 的 rowcount 判定，而非「先查后写」
- **错 5 次当场作废**是本地验证 T3 抓出的真缺陷（不是设计时想到的）
- **改密成功清空该用户全部会话**：忘记密码场景下账号可能已被他人掌握
- **原密码只放 `app.globalData` 内存、绝不落 storage**（避免明文密码留存在本机）
- **scoped 提交的语义耦合实例**：我的 `forgot_reset` 调 `_client_ip(request)`，而该函数在 HEAD 里**不存在**（属并发的 XFF 伪造修复，在途）⇒ 若只提交自己的 hunk，HEAD 会在调用处 **NameError**、接口一进来就 500 ⇒ 在途 hunk 必须**同批带入**。**教训：hunk 级归属不能只看「谁写的」，必须看「谁依赖谁」**
- **前端「样式搬移两半」**：`EmployeeArchive.vue` 的 os=3（模板 `page-hd`→`page-hd split`）与 os=649（删本地重复 CSS）是**一对**，必须一起排。已核全局层 `styles/variables.css:266-270` 在 HEAD 里已有 `.page-hd` / `.page-hd.split` / `.page-sub` 定义 ⇒ 两半都不带时文件等价于「HEAD + 我的插入」，自洽零位移

### 🔴🔴 本轮最重要的方法论发现：**HTTP 状态码不能判定 Hergent 的路由是否存在**
第一版探针判据「删掉后应返回 404」**全错**。判别性实验（打一个从未存在的路由）暴露真因：
`rbac_middleware`（`server.py:617`）**在路由匹配之前**跑，按**静态前缀表** `_PATH_MODULE_MAP`
（`server.py:311`，表里有 `"/api/ai": "chat"`）解析模块 —— **完全不看 `app.routes`**：
- 未带凭证 → **401**（任何 `/api/*` 都是，包括从不存在的路由）
- 命中前缀但权限不足 → **403**（`/api/ai-learning/*` 被 `/api/ai`→chat 吞掉，supervisor 无 chat ⇒ **恒 403**）
- 未命中前缀 → **403 MODULE_NOT_CONFIGURED**（同样与路由无关）

⇒ 匿名/supervisor 视角**永远看不到 404**。但「中间件放行后不存在的路由确实 404」这条链路是通的
（实测 `GET /api/forecast/periods` → 200；`GET /api/forecast/definitely-not-real-xyz` → 404
`"接口不存在：…"`）⇒ **判据必须成对：同前缀 + 同 token，一个存在的子路径（正例 200）+

## v205-INC（16:00–16:09）—— 交付后复核抓出一场**生产静默劣化**：幽灵租户库让调度器每 2 分钟报错（已止血，**根因未修**）

**这不是 v205 引入的**，而是**收尾「最终健康复核」独立跑才发现的**（若只看冒烟脚本自报 `32/32`，会完全错过）。

### 一、症状
```
[Scheduler] Cron tasks check error: attempt to write a readonly database        ← 每 2 分钟 ×2
[Scheduler] ai reminders tenant=2 error: attempt to write a readonly database
[Scheduler] ai reminders tenant=3 error: attempt to write a readonly database
[Tenant patch] FTS products_fts in /opt/hergent-erp/tenant_3.db: attempt to write a readonly database
```
`journalctl | grep -ci "readonly database"`：**00:00–15:44 = 0 条；15:44 之后 = 1268 条。**

### 二、现场
`/opt/hergent-erp/tenant_2.db`、`tenant_3.db` = **0 字节、`root:root`**、
两者 ctime **同一纳秒 `15:44:21.889513029`**（⇒ 单个 root 进程的一次 `[2,3]` 循环）。
而主库 `tenants` 表**只有 id 1 与 10**，`user_tenants` 里**没有任何 2/3 的成员关系**
⇒ **不存在客户数据，也没有数据丢失**（这两个号历史上曾是真实租户，
`/root/backup_colsync_20260913-091053/` 与 `/opt/hergent-erp/incident_20260812/` 里都有它们的旧库）。

### 三、机制（三个缺陷串联，缺一不可）
1. `db.connection.set_tenant_context(tid)` 有 **v88 兜底「缺库就建库」** ⇒ 以 root 跑的任何脚本，
   只要碰过一次 `set_tenant_context(2)`，就落一个 **0 字节 root 文件**（SQLite 首次写才写头）。
2. `scheduler._tenant_ids()`（`scheduler.py:956`）**扫文件系统**（`glob tenant_*.db` + `fullmatch`），
   **不查 `tenants` 表、也不查 `user_tenants`** ⇒ 幽灵文件被当成真实租户 2/3。
3. 服务以 `hergent` 运行、文件归 `root` ⇒ 每次 tick 写它都失败；调用处是 `except ... print`
   ⇒ **不抛不中断、每 2 分钟刷一行，永久静默劣化**。

### 四、归属判据（**很硬，值得记住**）
> **服务以 `hergent` 运行 ⇒ 它创建的文件必然 `hergent:hergent`。**
> 所以 `root:root` 的幽灵库**只可能来自 root shell / root 脚本**，不可能是应用产生的。

时间线：服务 15:43:28 重启 → 幽灵文件 **15:44:21**（重启后第 53 秒）→ 首个错误 15:44:39。
那段窗口正是**部署验证以 root 跑片段**的时候（冒烟脚本 15:45:02 才起）。
⇒ **照实说：来自一个 root 进程，进一步归因证据不足**；但这正是「以 root 裸跑生产库脚本」的高危区。

### 五、处置（已做，可回滚）
```bash
mkdir -p /root/quarantine_ghost_tenants_20260919
mv /opt/hergent-erp/tenant_2.db /opt/hergent-erp/tenant_3.db /root/quarantine_ghost_tenants_20260919/
```
（**`mv` 而非 `rm`** —— 保留可回滚；文件是 0 字节，回滚成本为零。）
⚠️ **移动后不会立刻止血**：16:01 移动 → **16:02:39 仍报**（进程已把连接/列表握在手里）
→ **16:04:39 起为 0**。判据：`--since 16:01` 的计数在 16:06/16:07/16:08 三次采样里**冻结在 8**
（此前每个 tick 增 ~8）⇒ 确证停止。
终态：`/opt/hergent-erp/` 只剩 `tenant_1.db`(12.1MB) / `tenant_9.db`(2.0MB) / `tenant_10.db`(2.9MB)，
全部 `hergent:hergent`；服务 `active`；内网 `GET /api/health` = 200。

### 六、⚠️ 危险的不是报错，而是它的**另一种结局**
若那个文件恰好归 `hergent`（比如脚本用 `sudo -u hergent` 跑），`set_tenant_context(2)` 会把它
**补成完整 schema** ⇒ 系统从此**认真对待一个不存在的「租户 2」**（无人属于它，但简报 / 提醒 /
监控都会去跑）。**`root:root` 反而挡住了这一步。**

### 七、待拍板（**根因未修**）
🔴 `_tenant_ids()` 既不看 `tenants` 表、也不跳过不可写文件 ⇒ 系统的「租户集合」有**两个真相源**
（磁盘文件 vs `tenants` 表）。生产里 `tenant_9.db` 就是现成例子（有库、不在 `tenants` 表，
因为能写所以既不报错也不报异常）。
**建议**：`_tenant_ids()` 与 `tenants` 表取交集，或至少 `os.access(f, os.W_OK)` 为假就跳过。
**本轮不动**（超出用户授权范围 P0/P1），已记入 `topics/deploy-ops.md`「幽灵租户库」一节 + 技能。

### 🔴 放开三档的前提：先统一量纲，否则库存会混着加

「按件订 1」记 1 与「按袋订 40」记 40 是同一批货 —— 库存是交易系统，这个错是真金白银。

### 实现（后端 9 处 / 前端 3 处）

1. **新建 `server/db/queries/units.py`** —— 数量换算**唯一实现**（纯函数、不连库）：
   `norm_ratio` / `unit_options` / `ratio_to_base` / `default_tier` / `base_qty_of` / `conversion_text`。
   🔴 单独成文件的理由：换算比一旦在采购 / 销售 / 导入各写一份，就会在「空串 vs 0」
   「中单位不存在时怎么办」上分岔，且**零报错地给出不同数**。
2. `purchase_order_items` 加 **`base_ratio`**（换算比**快照**）+ **`base_qty`**（折小数量），
   两处登记（主库 ALTER + 租户列清单）。
   🔴 列名叫 `base_ratio` 不叫 `unit_ratio`：`purchase_order_get` 的注释里早就用
   `unit_ratio` 指**另一件事**（`spec` 规格口径），同名会让后来人按错口径改代码。
3. 建单：**换算比由后端现查商品档案算**（`unit` 为空 ⇒ 不加两列 ⇒ SQL 逐字不变）。
   🔴 **不允许**前端传比值 —— 那是把库存量纲交给浏览器算术。
4. 入库成对折算：`confirm` 用 `_poi_base_qty` + `_poi_base_price`；`partial_receive` 同口径。
   🔴 **只折数量不折价会让 `inventory.cost_price` 错一个量级**（40 袋 @100 元应为 2.5 元/袋），
   且零报错。`(qty×ratio)×(price÷ratio) == qty×price` ⇒ 金额口径一个字都不变。
   🔴 `received_qty` **刻意不折**（要跟订单量比「到齐没有」）。
5. `PurchaseItem.unit` **显式声明进 Pydantic 契约**（此前靠 `extra='allow'` 侥幸取到
   ⇒ 字段名打错会零报错落空单位）。

7~9. 前端：单位改三档下拉 + 换算提示 + 双单位价 + 折小数量；详情页只读回显同口径；

### 探针自身的坑（写下来免得下次再踩）
1. `noImport` 只剥 `import` 不够 —— `.js` 还有 `export const/function/default` 三形态要剥。
2. **模块级 `const` 暂时性死区**：加载器要用 `LIST_CLEAN` 而它声明在调用点之后 ⇒
   运行时报 "Cannot access before initialization"。缓存挂**函数对象属性**，别用模块级 `let`。
3. 路由收集用 dict 会让同路径的 GET/POST 与 PUT/DELETE **互相覆盖**（4 条压成 2 条）⇒ 改列表 + 配反例。
4. 影子库读要"每次新开连接" —— 复用长命连接会读到 SQLite **旧快照**，让判据变假。

### 收尾补的一个洞：依赖闭包（值得记成纪律）

新 import 出现时这两件事会分叉：A 被暂存、A import 的 B 不在库 ⇒ 提交后 HEAD 是**编译不过**的树。

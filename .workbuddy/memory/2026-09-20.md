`Esc` 只换态**不回退内容**（回退归「回退」按钮 / Ctrl+Z）。

**同路径顺带修掉的两个静默缺陷**（不修就会立刻以「随机失灵」出现）：
1. `_pendingCell` 必须**每格一套** —— 原 `if (!_pendingCell)` 会让「先点没改的格、再改另一格」那次改动**既不进撤销栈、也不点亮状态条**（用户明明改了，界面说「尚未修改」）。方向键跳格会让这条路径从偶发变常态。
2. **跳到的格子被粘性冻结列盖住 ⇒ 光标看不见**（v210 **新开出来的**路径）：原生 `focus()` 的最小滚动把格子停在滚动口**边缘**，而左边缘是冻结列（`.seq-cell` 46 + `.frozen` ~200，`left:0`）、上边缘是粘性表头 ⇒ 新增 `keepCellClear()`（边界**量出来**不写死；只在被遮住时才滚；粘性格自身跳过）。

**结论（最值钱三条 + 两条数据安全级）**：
① 商品名称列补全（系统已有主档 + 条码后四位搜索，只差接进这一格，还能顺带治重复商品行）

⑤ 多端并发编辑同期次的冲突提示（最后写入覆盖 ⇒ 静默丢数）

**七维成熟度**（自评）：数据校验/快捷操作=成熟；输入方式/错误提示=中等；**自动补全/多端交互=最薄弱**；格式识别=偏薄（只处理千分位，**不处理全角数字** —— 中文输入法下最高频的隐性错，报错文案「必须是数字」会让用户觉得系统坏了）。

## 小程序 · 登录按钮文字垂直居中（2026-09-20，用户报「登录两字在垂直方向未居中」）

**根因不是「少写一条属性」，而是微信 `button` 组件带了一条看不见的默认值。**
内置默认样式里有 `line-height:2.55555556`（**无单位倍数**，按元素自身 `font-size` 计算）。
`.btn` 只写了 `height`、没写 `line-height` ⇒ 行高 = 2.5555…×32rpx = **81.78rpx**，
而 `height:96rpx` ⇒ 行盒贴内容盒顶部 ⇒ 文字中心比按钮中心**高 (96−81.78)/2 = 7.11rpx**。
🔴 **病根是耦合**：正确性押在「`height` 与 `line-height` 两个数字永远相等」上，改一个忘另一个就复发。

**判据（判据缺一层就看不见）**：给 `<button>` 设了**显式 height**，却**既没设 line-height、也没设 flex 居中**
⇒ 必然偏移 `(height − line-height)/2`。反例（不算缺陷）：line-height 与 height 相等；
`display:flex`+`align-items:center`；不设 height 靠**上下对称 padding** 撑高。
全仓 9 页普查：**6 处**按钮设了 height，缺陷 **3 处**（login 96rpx / password 92rpx / forgot 92rpx 的 `.btn`，三份同源代码）。

**改法**（3 个文件）：`.btn` 加 `display:flex;align-items:center;justify-content:center;line-height:1.2;padding:0`。
`align-items` 管垂直、`justify-content` 管水平（`flex-direction:row` 时主轴是横的）。
**没选「只补 line-height」**：那会保留耦合。已实测「只改 height」下修复后偏移**恒定 −1.00rpx 不随高度变**，
而修复前是 −7 / −19 / −59 rpx（96/120/200rpx，精确命中预言 −7.11/−19.11/−59.11）⇒ 解耦已证实。

**实测（像素级，非估算）**：登录 −7.00→−1.00；首次改密 −5.50→−1.50；找回密码 −5.50→−1.50 rpx（阈值 ±1.5）。
**探针保真三坑**（都踩过，已写进技能）：
① 不能用 HTML `<button>` 模拟 —— Chrome 对它额外做了「内容垂直自动居中」，**会把缺陷掩盖掉**（实测同一份 CSS：原生 1.00rpx vs `wx-button` 7.11rpx）；
② `mobile:true` 必须配 **viewport meta**，否则布局视口回落到 ~980px、与写死的 rpx 换算基准脱钩（量出 916px 这种离谱宽度）；
③ 掩膜必须**向内侵蚀 3 像素** —— 按钮自身轮廓的「青↔白」抗锯齿像素 r 通道会被抬到 >90 而误判成文字（把 −8 污染成 −19.5）。
**图的坑**：用 `top:50%` 画基准线会因 `.btn` 自带 `margin-top:8rpx` 而**偏高 4.5 像素**，看上去像「文字没居中」其实是线画错了 ⇒ 基准线必须按按钮实测矩形摆放，且**图本身要过校验**（`png-button-center-verify.py`）。
**残留 1～1.5rpx ≈ 0.5 CSS 像素是量化下限**（墨迹包围盒只能取整像素），不是缺陷，阈值不能设 0。

**未做 / 边界**：小程序**无构建步骤**，需在微信开发者工具重新编译预览才能看到；真机样式建议用户扫码确认一次
（探针在浏览器引擎里复现微信默认样式做测量，开发者工具无法无人值守运行）。**本轮不占 vNNN 号**（小程序侧按日期标记，改动仅 3 行 CSS）。
新增三件工具：`tools/btn-text-center-probe.mjs`（11 项断言含判别力自证 + 高度无关性）、
`tools/btn-height-without-lineheight-scan.py`（静态普查，含反向对照）、`tools/png-button-center-verify.py`（校验对照图不说谎）。
没有改其它按钮 —— 提交预报/撤回/隐私弹窗两键/退出/一键复制**不属于该模式**（普查 0 命中，已用反向对照证明它能抓出来）。

# v214-A 「全角数字自动转半角」全链闭环（用户原话：「全角数字自动转半角单开一批」→「开工」）

> 交付：`Forecast.vue` 17 处数字格 + 后端 `forecast_rules.py` 归一化；生产已上线并真机取证 10/10。
> 技能：`hergent-numeric-input-ime-tolerance`（新建）· `hergent-frontend-deploy-verify` 第⑥层（新增）

## 一、🔴 本轮最重要的认知修正：病根不在校验层，且 `type=number` 是「静默加工」不是「收不到」

**我最初的判断（写进了第一版注释）是错的**：以为 `<input type=number>` 会「丢弃非 ASCII 字符、
`e.target.value` 恒为空串」。真机取证当场推翻：

```
裸元素能力矩阵（只差 type 一个变量，灌同一批输入）
  '１２'      number → "12"     text → "１２"
  '１２。５'  number → "125"    text → "１２。５"   ← 中文句号被删 ⇒ 小数点消失 ⇒ 数量放大 10 倍
  '1，200'    number → "1200"   text → "1，200"
  '12箱'      number → "12"     text → "12箱"       ← 脏值变合法数字
  '12.'       number → "12"     text → "12."        ← 中间态被打断 ⇒ 小数根本打不出来
```
⇒ 危险的是**静默改掉用户敲的东西、且用户看不到任何异常**，比「输不进去」贵得多。
   与 v213 刚立的「宁可标红，不要静默丢/改」完全同向。**这是必须换 `type="text"` 的唯一理由。**

🔴 **同时确认：校验层早就是好的** —— `cellErrMsg`（前端）与 `normalize_qty`（后端）**早已走 NFKC**，
   全角数字本来就能过校验。所以本轮改动**一行都没碰校验逻辑**，只在输入层 + 解析层。

## 二、NFKC 不够：`。`(U+3002) 是「小数点打不出来」的真凶

NFKC 只折**全角形**（`．`U+FF0E → `.`），而中文输入法在**中文标点态**下打出的是
**`。`U+3002（表意句号）**，NFKC **对它不做任何事** ⇒ 被 `_NUM_RE` 拒收。

新增唯一实现 `normalize_num_text()`（后端）+ `toHalfNum()`（前端，逐字同源）：
`NFKC → 容错表 → 去千分位逗号 → strip`。容错表 9 条：`。、—–−．，－＋`。
- 🔴 **只收「数字格内语义唯一」的字符**，不做 `O→0`/`l→1` 这种歧义映射（会把用户真打错的字静默改成合法数字）。
- 🔴 `　`(U+3000) **刻意不写进表里**：NFKC 先把它折成普通空格 ⇒ **永远匹配不到 = 死条目**
  （实测抓到：前端 `toHalfNum('　12　')` 返回 `' 12 '`）。兜住它的是末尾 `.strip()`/`.trim()`。

## 三、🔴 `\d` → `[0-9]`（由变异体「仍然全绿」牵出，本轮第二个大发现）

`_NUM_RE` 原来用 `\d`。**Python 的 `\d` 是 Unicode 感知**（放行 `１２`/`١٢`/`१२`，`float("١٢")`=12.0），
**JS 的 `\d` 是 ASCII-only**（`Number("١٢٣")`=NaN）⇒ **两端分裂：后端收货、前端标红**。

暴露方式极有价值：**去掉 NFKC 的变异体 M6「仍然全绿」** —— 因为 `\d` 的宽容把 NFKC 变成了冗余层。
> **判据：变异体「全绿」比「变红」信息量更大 —— 它在说「这条判据在替解释器的宽容背书，不是在测代码」。**

改成 `[0-9]` 后 M6 立即恢复有效（变红 7 条），并补 `١٢`/`१२` 两条样例。

## 四、三条实现细节（都踩过）

1. **光标换算不能用原 `selectionStart`**：全角→半角 1:1（长度不变），但**去逗号会让文本变短** ⇒ 会把光标顶到逗号右侧。按「光标左侧文本转换后的长度」重算。
2. **IME 组合期（`e.isComposing`）一律不碰 DOM**（改 value 会打断候选框）；组合结束时浏览器会补一次 `input`（此时 `isComposing` 已 false）⇒ 不漏。
3. **中间态只能 `@change` 收敛，不能 `@input`**：`Number("12.")`=12 ⇒ 边打边收敛 = **永远打不出小数点**；不收敛 ⇒ 后端 `_NUM_RE` 判「非数字」**用户填 12 却见红框**。两头都错，只有「离开时收敛」对。
   `@input` 内还必须**显式写 model**（不能只靠 `v-model`：执行顺序取决于原生监听器注册次序，反转就把全角原串写进 model ⇒ `parseInt('１２')`=NaN ⇒ **合计静默按 0 累加**）。

# 小程序保活 / 长时间不退出（v221）

> 结论：**微信小程序不支持「保活」，这是平台设计而非技术难题。**
> 正确目标 = 「退出再回来，用户感觉不到」，不是「不让它退出」。
> 报告见仓库根 `小程序保活机制调研-2026-09-21.md`。

## §1 平台硬限制（三层，逐层收紧）

| 阶段 | 时点 | 平台行为 | 能否干预 |
|---|---|---|---|
| 前台 | — | 正常执行 | — |
| 后台（前 5 秒） | 点胶囊 / 切桌面 / 切聊天 | 代码仍在跑，但**网络请求未完成返回 `fail interrupted`** | 只能「抓紧存」 |
| 挂起 | 进后台约 5 秒后 | **JS 线程被暂停**，定时器 / 心跳 / 长连接全停 | ❌ 不可拦截 |
| 销毁（冷启动） | 后台累计约 **5 分钟** | 容器回收，再打开 = 全新启动、data 清空 | ❌ 不可拦截 |
| 提前销毁 | iOS：5 秒内 ≥2 次内存告警 | 微信主动销毁并提示用户 | ❌ |

⚠️ 「挂起 5 秒 / 销毁 5 分钟 or 30 分钟」各渠道口径有出入 ⇒ **一律按「随时可能被销毁」设计**。

### 其他会撞到的硬限制
- WebSocket：同一小程序最多 **5 条**；进后台约 5 秒被中断；空闲 30–120 秒断 ⇒ **心跳不能保活，只能优雅重连**（前台维护、后台优雅断开、回前台立即重连）。
- 网络并发：`request` + `uploadFile` + `downloadFile` 合计 ≤ **10** ⇒ 需自建请求队列。
- 本地缓存：**10 MB / 小程序** ⇒ 草稿必须瘦身存（只存 ID + 数量，别塞整份商品档案）。
- 订阅消息：**长期订阅仅政务民生 / 医疗 / 交通 / 金融 / 教育** 开放；工具类只能一次性订阅，**点一次只能发一条**。

## §2 唯一合法的「后台运行」= requiredBackgroundModes

| 能力 | 声明 | 门槛 |
|---|---|---|
| 后台音频 | `["audio"]` | 需音乐 / 在线教育类目；且正式版还需过审 |
| 后台定位 | `["location"]` | 国内主体仅 **12 个开放类目** + 资质证明 + 业务场景流程图 + 录屏 |

🔴 **订货类目申请不到。硬申会被以「过度申请权限」驳回** ⇒ 不要为了保活去动「工具→效率」类目。

## §3 四条思路的落点分工

| 思路 | 适用场景 | 实现要点 | 平台限制 | 可行 |
|---|---|---|---|---|
| A 白名单后台运行 | 音乐 / 导航 / 配送 | `requiredBackgroundModes` + 指定 API | 类目绑定 + 审核 | ❌ |
| **B 状态韧性** | 表单 / 录入 / 长流程 | `onHide` 存草稿 → `onShow` / `onLaunch` 恢复 | 无 | ✅ 首选 |
| **C 服务端常驻 + 推送召回** | 需事后触达 | 后端 cron + 企业微信应用消息 | 订阅消息额度受限 | ✅ 次选 |
| D 换承载形态 | 真需后台常驻 | App / 桌面端 | 系统省电策略 | ⛔ 成本高 |

### B 的三级防御
1. **内存级**：全局 `Map` 缓存页面状态，`onHide` 存、`onShow` 取 → 覆盖 5 分钟内热启动。
2. **存储级**：`onHide` 写 `wx.setStorageSync`（草稿 / 筛选 / 滚动位）→ 覆盖容器被销毁后冷启动。
3. **服务端级**：草稿同时回写后端，`onLaunch` 拉取比对 → 覆盖换手机 / 清缓存 / 多端同账号。

⚠️ 反面教材：只在 `onShow` 里 `setData` 恢复（冷启动时 `data` 已是空对象、**无源可溯**）；在 `onUnload` 里清空表单（加剧状态断层）。
⚠️ 草稿恢复要**询问**而不是静默覆盖 —— 用户可能故意放弃；跨期次 / 超时长只提示不直接恢复；提交成功后清草稿。

### C 的推送通道选择
| 通道 | 可用性 | 门槛 |
|---|---|---|
| 小程序一次性订阅 | 可用 | 每次都要用户点授权；「总是拒绝并记住」后永久静默 |
| 小程序长期订阅 | ❌ | 仅政务服务领域 |
| ⭐ 企业微信应用消息 | 可用 | 自建应用**无类目限制、无需订阅** |
| 公众号服务通知 / 短信 | 可用 | 需关注 / 按条计费 |

## §4 同类平台横向对比
微信 ≈ 支付宝（其官方文档直接出现「保活期间（5 分钟）」）≈ 抖音 / 百度小程序：**都是临时会话 + 后台回收**。
企业微信自建应用 H5 同样被挂起，**但推送无类目限制** ⇒ 内部场景性价比最高。
真能后台常驻的只有 App / 桌面端（Android 前台服务）—— 为 20 人内部工具维护，撞运维红线，不建议。

## §5 红线（不要做）
1. 不要伪造类目申请后台音频 / 定位 —— 以「过度申请权限」驳回；不要为保活动「工具→效率」类目。
2. 不要用静默音频循环保活 —— 需类目 + 耗电 + 投诉 + 后台音频本身会被系统省电策略回收（Android 尤其明显）。
3. 不要指望 WebSocket 心跳保活 —— 平台在 JS 层就挂起了进程。
4. 不要诱导 / 强制订阅消息 —— 违反运营规范，投诉累积会限制消息能力；用户勾「总是拒绝并记住」后不可挽回。
5. 不要混淆「用户上滑关闭」与「切后台」—— 前者是主动销毁意图，恢复草稿要更谨慎。

## §6 验收口径（重要）
「保活」需求的正确验收 **不是** 测「进程还在不在」，而是：
**填单 → 切微信聊天 → 锁屏 > 5 分钟 → 回来 → 数据仍在。**
另需验：杀进程后重进草稿可恢复；双设备同账号编辑同一期次有冲突提示（不静默覆盖）。

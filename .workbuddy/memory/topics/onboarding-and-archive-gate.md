## 一、结论（可落地判据）

**不走「强制建档 vs 延迟建档」二选一，走「按链路分层门禁」：拦写入、不拦浏览；隐式建档优先，只拦系统猜不出的。**

三条评审 checklist：
1. **拦写入不拦浏览** —— 拦截点必须落在**动作处理函数**，**不能落 `beforeEach`**（会死锁：用户进不了建档页）。
2. **隐式建档优先** —— 凡导入/同步能带出全部必要字段的，一律自动建，不拦人。
3. **只拦「系统猜不出来」的** —— 即需要人做业务决策的：报单对象映射（客户归属）、厂价、对账主体编码。

## 八、补充（2026-09-21）：单位换算 与 渠道定价 的真实能力

> 用户提出「建好大/中/小单位换算 → 预报与档案对齐」和「建好价格方案 → 舟谱模板自动带出」。
> 核实结论：**两个想法方向都正确，且系统已建好 90%，但代码都没接上。**

### 🔴 判据形态：「后端有表有端点、前端零处调用」= 能力存在但未接线
这是 `hergent-capability-reality-audit`（声明有 vs 代码真的读写它）的一个**子形态**，极易误判为"没这功能"。
判据：**查能力是否存在，必须分三段各自证明** —— ① 表/DDL 在不在 ② 后端端点在不在 ③ **前端/消费方有没有调用**。三段都 ✅ 才算"真的到用户面前"。

### 单位换算（三段里 ①②✅ ③❌）

- ✅ `unit_archive(name, unit_type, sort_order, conversion_ratio, base_unit, is_base_unit)`（`db/queries/sales.py:662` + `erp_db.py:2216-2220`）

- ❌ 舟谱模板单位优先级 `条码映射 > 提交明细单位 > 名称关键词推断`，**不查档案**（`forecast.py:853`）

### 渠道定价（三段里 ①②✅ ③❌）

- 📌 `prices.py:365-370` 注释已写明这套**就是为订单文件设计的**，且警告：None 会传成「价=0 / missing」，**在生成订单文件时表现为静默取错价**

### 🔴 量纲陷阱（会复制 v217 的 990）
舟谱 `*单价(折后价)` 配 `*数量`（明细单位，如桶）⇒ **单价必须是元/桶**。三价源单位不同：

| 价源 `price_source` | 取值 | 单位 | 直接带出？ |
|---|---|---|---|
| `products_dist` 分销价 | `products.dist_price` | 元/小单位 | ✅ |
| `products_factory` 厂价 | `factory_price_sql()` | 🔴 **元/箱** | ❌ **= 复制 v217 的 990** |
| `matrix` 商品×渠道矩阵 | `product_channel_prices.price` | ⚠️ 由录入决定 | ⚠️ 须显式声明 |

⇒ **`product_channel_prices` 录入界面必须显式声明价格单位**（元/箱 vs 元/小单位），带出时按 `unit_conversions` 换算。
（v217 已反推 `分销价 = 厂价 ÷ 规格 ÷ 0.9`，即**厂价是箱价、分销价是单件价** —— 这是换算依据。）

### ⭐ 两者是同一条链的两半，必须一起做
单位换算解决「箱↔桶」，价格方案解决「哪个门店什么价」。只有前者价格仍错，只有后者量纲仍错。

### ⚠️ 切换顺序：必须先有数据、再切代码
`perCase` 改读换算表后，**没有换算记录的商品会返回 0**（v217：无数字返 0）⇒ 箱数算不出来。
且 `product_backfill_from_import` **只补空不覆盖**（`products.py:464`）⇒ v217 实测的 **114 行单位不一致不会自动更新**，须一次性迁移。
兜底要求：**缺换算时显式告警，绝不静默归零**。

### 修正后的裁定变化
- 客户档案「必须前置」**换理由**：不是防孤儿单，而是 `report_mapping.counterparty_id` 要指向它（`prices.py:399` `SELECT channel_id FROM contacts WHERE id=?`）⇒ **前置性更强**
- 单位档案 可延迟 → ⬆️ **预报链路前置**（前置的是 **`unit_conversions` 换算数据**，不是 `unit_archive` 字典表）
- 价格方案 可延迟 → ⬆️ **生成舟谱模板前置**（但先解决价格单位显式声明）
- 孤儿单（`sales.py:100-115`）**P0 → P2**（销售开单非主链路，只做预报）

## 九、舟谱真实结构（权威口径，2026-09-21 从两个附件实证）

> 来源：`~/Documents/舟谱截图/ 导出的报表/价格方案.xlsx`（舟谱导出）+ `舟谱档案导入模版.xls`（舟谱官方模板，6 sheet）
> 用户确认：**「本店」= 客户 = 客户档案里的客户**（永辉东津店/美联檀溪店）；价格**可按渠道也可按门店**；录入要支持手工 + 导入模版

### 9.1 🔴 决定性：舟谱里「渠道」与「门店」是**同一层概念**，都叫「价格方案」
`价格方案.xlsx`：1 sheet、364 行 × 44 列、数据 358 行。第 5 行价格方案列头（每组 **3 列 = 小/中/大单位价**，第 6 行二级表头）：
`分销`(渠道) ｜ `中百` `沃尔玛` `永辉` `武商`（门店）⇒ 并排同层。
表格形态 = **行=商品，列=方案 × 三级单位**的宽表。**同品不同门店不同价实证**：每日鲜语250ml\*24瓶 → 分销 5.27 / 沃尔玛 6.94 / 永辉 8.01 / 武商 7.10 元/瓶。
**大单位价 = 小单位价 × 换算数**（光明学生奶 200ml\*24盒：`1.80元/盒` × 24 = `43.20元/件` ✅ 自洽）。
其他：公式格 **0 个**（双视图）；358 商品中**仅 67 个**配了方案价；价格格是**文本**（`"1.80元/盒"`，导出勾了「展示价格单位」）。

### 9.2 三级单位 = **商品档案的内嵌字段**，舟谱**没有独立单位档案表**
「商品档案」sheet 共 **52 列**，单位字段组：`*小单位类型`（计数/计重/计体积）`*小单位` `大单位` `中单位` + `条码（小/中/大单位）` + `大单位换算` `中单位换算`。
**换算规则（模板说明原文，可直接当校验口径）**：

| 类型 | 规则 |
|---|---|
| 计数 | 换算值**正整数**；大单位换算 = 中单位换算的 **>1 的整数倍** |
| 计重 | 小单位 `g/kg/斤/公斤`；g 须正整数；kg/公斤≤3 位小数；斤≤2 位小数；大÷中须**可除尽** |
| 计体积 | 小单位 `ml/毫升/L/升`，规则同计重 |
| 通用 | 填大单位必填大单位换算；填中单位必填中单位换算；**有中单位时大单位必填**，且大单位换算须**能被中单位换算整除** |

⇒ 模型 = **以小单位为基准，中/大单位按换算值向上，最多三级**。Hergent 比它多一层（`unit_archive` 字典表 + `unit_conversions` 商品级换算 + `products.unit` 列，三层并存）。

### 9.3 价格：「单位是**列名的一部分**」，不是值的属性 ⭐
- 商品档案内嵌 **12 个价格列** = `批发价`/`零售价`/`最低售价`/`进价` × `（小单位/大单位/中单位）`，另独立 `税率（%）` 列（示例 `13.50`）
- sheet 4「价格方案」22 列：`*商品名称` ｜ `进价`(B:D) ｜ `批发价`(E:G) ｜ `零售价`(H:J) ｜ `最低售价`(K:M) ｜ `价格方案1~3`(T:V)，**每组固定小/中/大 3 列**
- sheet 5「渠道最低售价」9 列：`*渠道` `*商品名称` … `小/中/大单位最低售价` ⇒ **渠道是独立维度**
⭐ **舟谱把单位写进列名（`批发价（小单位）`）⇒ 量纲永不含糊** —— 这正是 v217 那个 990 陷阱的官方解法。

### 9.4 🔴 Hergent 与舟谱的三处关键差异
| # | 差异 | 舟谱 | Hergent |
|---|---|---|---|
| D1 | **价格缺单位维度** | 每方案 ×3 列（小/中/大） | `product_channel_prices` 只有**单个 `price` 列**（`prices.py:439`）⇒ **不加单位维度，量纲歧义必然复发（=990）** |
| D2 | **导入删除语义相反** | 模板说明第 4 条：**不填且未勾联动 ⇒ 导入时清除系统中已有价格** | `product_backfill_from_import` **只补空绝不覆盖**（`products.py:464`）⇒ **必须让用户显式选，不能默认任一方** |

## 十五、🔴 单位换算的两个静默陷阱（2026-09-24 实测发现，**未修，写代码前必读**）

起因：用户提「商品目标管理」需求，特别叮嘱「**要注意单位换算，要看系统里的真实单位换算是什么样的**」。
按提示实测生产 `tenant_1.db`（285 个在售商品），抓到两个会让换算**静默算错**的陷阱。

### 15.1 🔴🔴 `medium_ratio > 0` 是假判据 —— SQLite 文本恒大于数字

**根因**：`medium_ratio` 这一列**存了两种 SQLite 类型**（`REAL DEFAULT 0` 的列，但存量导入写进了空串）：

```
typeof(medium_ratio) 分布（285 行）：real = 128 · **text = 157**（全是 `''` 空串）
```

SQLite 的类型排序规则是「NULL < INTEGER/REAL < TEXT」，所以**文本永远大于任何数字**：

```sql
SELECT '' > 0;      -- 返回 1（true！）
SELECT '' > 0.0;    -- 返回 1
```

**后果对照（同一份数据，两个判据差 157 行）**：

| 判据 | 命中数 | 结论 |
|---|---|---|
| `medium_ratio > 0` | **210** | ❌ 假阳性 —— 多算 157 个**根本没有中单位**的商品 |
| `CAST(medium_ratio AS REAL) > 0` | **53** | ✅ 正确 |
| `medium_unit <> '' AND CAST(medium_ratio AS REAL) > 0` | **53** | ✅ 同答案（互为交叉验证） |
| `medium_unit` 非空 | **53** | ✅ |
| `large_ratio > 0` | 209 | ✅ 安全（`typeof(large_ratio)` 恒 real，285/285） |
| `has_multi_unit = 1` | 209 | ✅ 与上同数（此前记忆里说「漏标 9 条」，本轮实测已对齐） |

⇒ **`large_ratio` 系列可以用裸比较，`medium_ratio` 一律必须 `CAST(... AS REAL)`。**

**为什么一直没被发现**：前端唯一实现 `Forecast.vue::perCase()` 里写的是
`const mr = Number(arc.medium_ratio) || 0` —— JS 的 `Number('')` = `0`（假值）⇒ **前端天然安全**。
所以这条只在**新写的 SQL** 里才会咬人，而且咬得完全静默（数字偏大但不报错，只是"算出来的均单目标/箱数不对"）。

**纪律**：单位判据必须收口到**一处**（建议后端 `db/queries/products.py` 新增 `per_case_sql()` /
`unit_levels_sql()`），业务代码禁止散写 `medium_ratio > 0`。与 `ORDER_UNIT_COALESCE` 同族
（"别在别处再写一遍这个 COALESCE —— 第二份必然漂移"）。

### 15.2 🔴 小程序与 Web 主表的「单位」不同源

| 端 | 下发/显示的单位 | 唯一实现 |
|---|---|---|
| Web 报单主表「单位」列 | `order_unit` 优先 → 空回退 `unit` | `db/queries/products.py::order_unit_master_sql()` |
| 小程序报单框（`prod-spec`） | **只有 `p.unit`** | `routers/data.py::fill_search_products()` 的 `sel_rest` |

实测影响面**当前很小**：30 个填了 `order_unit` 的商品里，**只有 1 个**与 `unit` 不同（id=1596
`现代牧场0乳糖软牛奶185ml+2到货`，unit=瓶 / order_unit=组）。
⇒ 现在不构成故障，但**任何"按填报单位显示数量"的新功能**（如均单目标提示）必须先打通这一处，
否则会出现「提示说 72 包、输入框单位写着组」这类看不懂的界面。

### 15.3 同期核实的既有事实（供养新功能复用）

- **三级单位真实语义**：`unit` = 小 · `medium_unit`+`medium_ratio` = 中 · `large_unit`+`large_ratio` = 大 ·
  `order_unit` = 报单单位（空回退 `unit`）。`large_unit` 取值：件 202 / 箱 7。
- **实测好样本（做换算测试的首选锚点）**：
  - `id=1449 蒙牛0蔗糖原味百利包150g*5袋*8包` → 袋(小) / 包(中,5) / 件(大,40) ⇒ **1件 = 8包 = 40袋**
  - `id=1339 高钙骨力风味酸奶90g*8袋*12包（新）` → 袋 / 包(8) / 件(96) ⇒ 1件 = 12包 = 96袋
  - `id=1162 蒙牛双拼果蔬风味酸牛奶圆周杯90g×8杯×12组` → 杯 / 组(8) / 件(96)
- **`perCase()` 的三级分支**（前端唯一实现，`Forecast.vue:3132`）：按大单位报单 → `1`；
  按中单位报单 → `large_ratio / medium_ratio`；否则 → `large_ratio`。
  实测 `id=1449` 按中单位「包」⇒ `40/5 = 8` ✅ 与用户口述的「每箱8包」一致。
- **`rebate_target_rules.arrival_count_override` = 本期可报单数**（生产：蒙牛低温2026年目标 = **15**，
  简爱9月目标 = 8）。天然可作「均单目标」分母的来源；`arrival_cadence_days` / `arrival_mode` 是节奏。
- **`rebate_achievements`（达成填报）已支持 `dimension='product'`**（`DIMENSIONS` 五维，
  `scope_key` + `actual_qty`），但生产 4 行**全是 brand 且 `actual_qty` 全 0**
  ⇒ 🔴 **该表没有「单位」列**，`actual_qty=150` 无法判断是 150 箱还是 150 包。
  任何要用「达成填报数量」的功能，必须先决定这一列的单位口径。

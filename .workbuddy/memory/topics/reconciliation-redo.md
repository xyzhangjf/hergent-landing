## 四、旧版为什么必然失败（两条代码级实证）

1. `reconciliation.py:96-106` 的「自动匹配」是**假算法**：逐条**无条件**标 `matched` 并递减余额，
   `matched_total` ≈ 全部单据之和 ⇒ **它不在配对，在遍历**。
   根因是**建模错误**：用 `amount: float`（一个口述标量）做对账输入，承载不了「哪几笔、何时、什么方向」。
2. 同屏两个「系统应收」差 17.7 万：页面头部 = `receivables` **余额**；
   匹配结果 = `Σ sale_orders − Σ payments` **区间发生额**。**两者本来就不该相等，却都叫「系统」。**
3. **39 次访问 0 次确认是理性行为**：`confirm` 只写一条 `audit_log`，**不改状态、不解除阻塞、无后果**。

## 五、🔴 七步分工（用户原话的拆解）

`上传 → AI 认列定键 → 人确认键 → 确定性算子比对 → AI 归因 → 人确认 → 人改数`

| 步骤 | 代码 | AI | 人 |
|---|---|---|---|
| 1 上传 | 存 `file_id`、读 sheet/列/前 N 行 | — | 声明「这是什么」 |
| 2 认列定键 | 出候选（`COLUMN_PATTERNS`）+ `samples` + `validation` | 判定键列、给 `confidence` 与理由 | — |
| 3 人确认键 | 渲染可改表；**execute 照用 mapping** | — | 改判并确认（尤其收/支是否分两列） |
| 4 **确定性比对** | 按键配对（容差/组合/跨期/排除） | 🔴 **禁止参与** | — |
| 5 归因 | 只提供上下文（摘要/备注/操作人/历史） | **原因 + 建议，必须落枚举** | 否决/修正 |
| 6 人确认 | 写快照 + 解锁下游 | — | 确认 |
| 7 人改数 | 过写入口门禁 + 留旧值 | 可起草 | 点「补录/冲销」 |

**🔴 第 6 步必须产生后果**，否则重做后仍然 0 次确认。建议先挂**催收队列**
（514 次真实调用说明它是活跃场景，回报可感知）；「未对平不许结账」留到结账模块上线。

### 7.1 🔴 人工报告自己有 4 处错（本轮的意外结论）

回放不只是验引擎 —— 它**同时验了那份人工报告**。4 处差错**全部精确归因**：

1. **同额同日漏配** $103.50 —— 人的一对一配对被同额冲掉
2. **退款符号误记** $6,912.40 —— 舟谱退款单在「收入」列里是**负数**，报告把符号吃掉了
3. **合计剔除闭合验证**：`62,236.17 + 6,912.40 − 103.50 = 69,045.07` ✓ —— 三处错误恰好互相抵消，
   所以报告**总额看起来是对的**，只有逐笔回放才能抓出来
4. **组合匹配漏 1 笔**（把「1 笔对 2 笔」漏成 1 组）

⇒ **判据：人工报告不是黄金标准，只是「另一个待验证的实现」。** 验收口径 = 逐笔可解释，不是「与报告数字相同」。

### 7.2 🔴 反推人工算法的方法（本轮加速最多的技巧）

**别猜算法 —— 读报告自己给的计数。**

微信报告写「已匹配收入 **130 组**、支出 **40 组**」。而微信原始侧是 144 笔 / 50 笔。
用「金额相等 + 同日一对一」暴力匹配，得 `144−14=130`、`50−10=40` —— **与报告完全吻合**。

⇒ 人工算法 = **金额相等 + 日期容差 ≥1 天**。一次试算就锁定了容差参数，比读代码/问用户都快。
**通用判据：报告里的每一个「组数/笔数」都是一个约束方程，先把它当已知量解出参数，再动手实现。**

### 7.3 🔴 两个只有真实数据能抓出的引擎缺陷（45 项单测全绿也没抓到）

1. **`bisect` 要求被搜索的序列自身有序** —— 我把「按日期排序后的金额列表」喂给 bisect，
   真实数据上**已匹配组数从 170 掉到 13**。必须单独维护 `_by_amount = sorted(rows, key=(amount, ...))`
   这条平行数组。⇒ 新增 **T11 规模回归**（60 组乱序 + 同日多笔乱序）；小数组（1–5 行）上 bisect 会偶发命中，
   **所以单测绿 ≠ 引擎对**。
2. **退款冲减不能用「单据编号」当同键判据** —— 舟谱收款单是 `SK…`、退款单是 `XD…`，编号本就不同，
   永远配不上 ⇒ 该能力会**永久静默失效**。改为默认 `refund_group_field="counterparty"`（同结算单位）。

### 7.4 顺手还的三笔债

- `KIND_COMBINATION` 与 `combination_mode` —— 组合匹配默认 **`candidate`（只给线索、不判平）**，
  `"match"` 需显式开启。实测 3 组组合里 **1 组对方名零交集** ⇒ 默认保守是**正确**的不是偷懒。
- `reconcile_by_key()` 兼容层 —— 把既有两处同一套语义（`spreadsheet_query._run_query(op="match")`
  与生产 MCP 工具 `spreadsheet_reconcile_files`）收拢到一处，消除双份漂移源。
- 确定性契约：所有遍历顺序显式全序 `(date, amount, counterparty, key, orig_index)`；
  119,396 字符结果**两次字节级一致**。

## 九、红线

1. **AI 不得参与比对判定** —— 算归代码、判归人；AI 只做归因与起草，且必须落枚举值。
2. **不回写客户 ERP / 舟谱原始账** —— 对账只发现问题、记录结论；改数由人去原系统做。
   一旦回写就从分析层越界成交易层，与「不造 ERP、订单 CRUD 冻结」直接冲突。
3. **组合匹配必须设上限** —— 子集和 NP-hard；≤4 笔 + 金额倒序剪枝，超限只给候选不判平。

   不占用四象限行），`"match"` 需显式开启。候选按「对方名是否有交集」分 `strong` / `weak`。
   实测真实数据 3 组组合里 **1 组对方名零交集** ⇒ **只能给候选、不能自动判平**，默认保守是正确取值。

## 🔴 应收 / 催收的**数据地基现状**（2026-09-27 只读实测 tenant_1）—— 做资金类功能前必读

**结论先行**：「自动提醒哪个客户欠多少钱、逾期多久」**现在做不出来**；
而原因**不是"没有欠款数据"，是"没有收款数据"**。

| 表 | 实测 | 含义 |
|---|---|---|
| `sale_orders` | 22,505 行，但 `created_at` **全部集中在 09-25 一天**（11:27–16:11）；`order_type` = `self_pickup` 22,254 + `transfer` 251 | **一次性历史导入，无增量** |
| `receivables` | 181 行，`ref_type` **全部 = `opening`**；`paid_amount` **全 0**；`due_date` 统一 **2023-12-31**；`ref_id` 全 0 | **期初建账**，从未更新还款 ⇒ 余额**恒等于期初值** |
| `cash_flow` | **仅 16 行**，集中在 6/14–6/17，金额 500/56/120/280 量级 | 明显是**测试数据**，不是真实收款 |
| `collection_followups` | 181 行，但 `created_at` **全部同一秒**（2026-08-16 18:00:06） | 批量生成 ⇒ 「自动提醒」目前是**单向展示**，无真实跟进闭环 |

**⇒ 两条判据**：

1. 🔴 **资金类功能的第一优先是「把收款录进来」，不是做提醒界面。**
   否则提醒会**每天显示同一个数**，老板看一眼就判定"系统不准"，连带毁掉整个模块的信任
   （与「恒空恒 0 且零报错」同族，但更隐蔽：**它有一个看起来合理的非零值**）。
2. **欠款本可由系统自算**：`sale_orders` 已在库里 ⇒ 应收账龄 = 销售累计 − 收款累计，
   **不必依赖对方系统再给一份应收表**。但——**分子有了、减数没有**，所以仍卡在收款。

**顺带查出的数据质量缺陷**：`cash_flow` 里「部分回款」「全款结清」这类**收款**记录的 `type`
被标成 `expense`（应为 `income`）⇒ 导入链路必须**按语义校验借贷方向**，不能照抄源列。

**对账页处置不变**（见上文）：页面已移除、后端接口暂留；催收队列独立成模块（514 次调用 = 真需求）。

### ② 🔴 两种对账口径之上，还差一层判据：**「0 差异」的两种成因必须分开**

| 口径 | 何时用 | 用错的后果 |
|---|---|---|
| 键对账 `reconcile_by_key` | 两侧**存在共同单号**（订单号/凭证号）= 同源导出互核 | 两侧无共同单号时 → 见下方 🔴 |
| 账户对账 `reconcile` | 银行/微信/支付宝流水 ↔ 舟谱账户明细（**两套编号体系、无共同单号**） | 用键对账会得出「几乎全不匹配」的**假象** |

🔴 **键对账最危险的形态不是「全不匹配」，而是「什么都没比出来」**：
`_index()` 把 **key 为空的行静默丢弃** ⇒ 两侧单号列全空 / 编号体系完全不同时，两个索引都为空
⇒ 返回 `only_in_a=0 / only_in_b=0 / mismatch_count=0`，**一份看起来「完全一致」的报告**。
「全不匹配」用户一眼看得见异常；这个形态会让人直接下结论「账是对的」。

**判据（已落到代码，只增键不改旧键）**：`reconcile_by_key` 回
`rows_a_total / rows_b_total / skipped_no_key_a|b / keys_a / keys_b / common_keys / vacuous / warning`。
`vacuous=True` 时 `warning` 明说「0 差异不代表一致」，并区分三种成因（两侧空表 / 单号列全空 / 无共同取值）。
前端 / AI **必须先看 `warning`**，不许把 0 差异说成「账是对的」。

**验收探针**：`tools/probe-t16-mcp-recon.py` C 段 = 正反两侧对照
（正：有共同单号 ⇒ 正常工作；反：同一份账户流水 ⇒ `vacuous=True`）。
判据写法：**同一份数据两种口径给出相反观感**，才证明探针有判别力。

### ③ 三入口同源（曾是**两份**实现，且两份 docstring 都谎称「已收拢」）

### 8.1 🔴 最贵的一条：「被过滤的单」会从总数与分项里**同时**消失 ⇒ 恒等式失效

`do_import_money` 里「单据类型 / 单号前缀 / 金额」三处过滤原写在累加 `orders_total` **之前**，
被挡的行 `continue` 掉，而成单计数在之后的**单号边界**才发生。
⇒ 这些单**同时**从 `orders_total` 与各分项里消失
⇒ `created + existed + failed + empty + blocked == orders_total` **两侧同为 0、照样成立**。

**这不是「少个数字」，是恒等式变成了恒真式**：首轮跑出的「29/29 全绿」正是这种**假绿** ——
探针认同了 bug。实测票：收入明细表真实 **6 单**（3 供应商 + 3 内部）却只报 3 张；
费用表真实 **158 单**却只报 1 张。

**修法**：新增 `_pre_block(no, bucket)`，在**任何过滤之前**先认单（`pre_blocked` 集合保证一单一记）；
三处过滤点落 `orders_failed`（类型/前缀对不上）与 `orders_blocked`（本批不导入）。
被挡单号与落库路径**不相交**（被挡的行一律 `continue`，从不成为 `cur_no`）⇒ 不会重复计数。

🔴 **通用律**：**「总数 == 各分项之和」这类恒等式，只有在「总数是在任何过滤之前统计的」时才有判别力。**
写完这类断言必须自问一句：**有没有一类数据，能同时逃出总数与全部分项？** 有 ⇒ 该恒等式无效，
它会在最该报警的时候显示全绿。

**⚠️ 连带**：`can_execute` 原判据 `orders_total > 0` 会把「本批不导入的单」也算进去
⇒ 上传「纯客户费用单」的文件会显示「可执行」却导 0 张（用户以为系统坏了）。
已改为 `orders_total − orders_blocked − orders_failed > 0`。
**不扣 `orders_empty`** —— 那会改变采购路径既有行为（空库预览 62 单全 `empty` ⇒ 变不可执行）。

### 8.2 🔴 探针纪律：期望值必须来自**独立来源**，不能取自被测代码（也不能凭印象硬编码）

首轮 `EXPECT` 硬编码 3/1，而那个 3/1 是**照着当时那个错的读数抄的** ⇒ 「两个错的一致」，
探针与 bug 互相作证。现在 `v313-m01-verify.py` 内置 `scan_file()`：用 `openpyxl` **独立**数一遍

## 8.8 v313b：档案「认领」的三条硬判据（别名 / 建档 / 促销品）

🔴 **一、多户头主体：别名不能用归一化代替。**
判据不是「名字像不像」，而是「**两者是否在同一个文件里同时出现**」：

| 例 | 证据 | 结论 |
|---|---|---|
| `蒙牛酸奶`（706 行 / ¥687,568.60）vs `蒙牛酸奶（湖北恒滋）`（4 行 / ¥11,832.00） | 同文件**同时存在** | **两个签约主体**（福宝 / 恒滋户头）⇒ 去括号归一会把恒滋的钱**静默挂到福宝账上、零报错** |
| `美联（卞和店）` vs 美联名下 **15 家店** | 去括号后 15 组撞车 | 只能**逐条显式别名** |

⇒ 别名**排匹配链最前**（人工确认的业务事实 > 模糊推断），且**不参与任何归一化**。
落 `contacts.alias`（多值用半角/全角逗号、顿号、分号分隔 —— 只认半角逗号会让填顿号的人「填了没生效」且零报错）。
建索引时**撞车即作废**；`has_alias` 先 PRAGMA 探测列（未迁移的库不崩，退化不静默）。

🔴 **二、建档前先查「是不是两个池子」，别默认一一对应。**
员工在生产有**两套**：`contacts.type='employee'`（11 人，**导入匹配读它**）与 `hr_employees`
（10 人，HR 薪资）—— 只交叉 **5/11** ⇒ 不是漂移，是两个用途不同的池子。
⇒ 只建导入需要的那一套；**不要顺手同步**到薪资表（误建 = 把外人写进工资表，风险更大）。

🔴 **三、「促销品 / 赠品」按**金额**判，不按名字。**
`蒙牛玻璃杯大号` 名字像赠品，实为 **3840 个 × ¥1.4 = ¥5,376 的真实采购且独占一张单**
⇒ 不建档 = 整单进不来 = 每月对账凭空少这笔钱。**先查金额与是否独占整单，再决定建不建。**

⚠️ **四、`POST /api/contacts` 传 `type` 会静默失效**（范围外缺陷，未修）：
实现是 `contact_create(_user=..., **d)`，形参却叫 **`contact_type`** ⇒ `type` 不在白名单被丢弃、
落默认 `'customer'` ⇒ **返回 200 + success + id，实际建成客户**。建档后必须按 `type` 复核。

### 8.9 判「是不是同一件东西」时，**相似度是假信号，条码才是判据**（v313c）

系统里 `简爱PROTÑ …135mLx2杯x12组`（条码 **3330**、单位「件」）与舟谱
`简爱…135mL*2杯*12组`（条码 **3316**、单位「杯」）**相似度 0.83** —— 看着就是同一商品。
但**条码差一位、单位也不同** ⇒ 不是同一商品（大概率厂家换码或两个规格）。
⇒ **建档**（新条码），不动旧档案。**按相似度绑别名会把两个不同条码并成一条、金额记到错的档案上。**

对照：`美联（卞和店）` vs `美联（卞河店）` 相似度 0.80 却是**同一家店**（同音错别字，
由用户人工确认）⇒ 走**别名**。
⇒ 一句话：**同物异名 = 别名（须人工确认）；同名义物 = 建档（条码不同就不许合并）。**

🔴 **约束要看「库里的建表语句」，不能看代码里的 `CREATE TABLE`**（v313c 更正两条记错的拦路石）：
 `erp_db.py:1739` 的 `CREATE TABLE IF NOT EXISTS receivables` **有** `CHECK(amount>=0)` 与
 `REFERENCES contacts(id)`，但**生产/dev 的真实库是老版本建的、两个都没有**
 （`IF NOT EXISTS` 不会改它）⇒ 真实库**不崩**（静默写入负数，更危险），全新库才崩。
 实测三张单据表 `PRAGMA foreign_key_list` **外键数全是 0**。
 ⇒ **代码判据取更严的那个**（不写 `contact_id=0`），不能因为「现在能写」就写。

### 8.10 验收要**逐单**，不能只验总额（v313c M0.3）

总额对得上但逐单错配是可能的（A 单多 100、B 单少 100，合计一模一样），
而对账场景下**错配的那张单**才是要找出来的东西。
⇒ 逐张比对「库里金额 vs 文件里该单金额」；采购单**头没有 `amount` 列**，改验明细合计。
   另加**幂等重跑**（created=0 / existed=全部）与**整库回滚**（业务表回 0 行）两段。

⚠️ **影子库 schema ≠ 生产**（v313c 踩到两次）：
 ① dev 的 `products.barcode` 是 **UNIQUE**，生产是**普通索引**（实测同条码可挂多行）
    ⇒ 不照生产重建索引就会「测到」一个生产上不存在的约束；
 ② 准备影子库要**关外键**：dev 的 `stock_locks.customer_id REFERENCES contacts(id)` 挡住
    `DELETE FROM contacts`。这只是**准备**、不是被测行为；导入仍走 `get_db()`（外键 ON）。

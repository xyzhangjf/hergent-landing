## v251 商品名称拖宽仍出省略号（commit `f83dfc5`）

- **根因**：`.pname{max-width:200px}` 写死。表是 `table-layout:fixed`，列宽由 colgroup（拖动的 `colWidths`）决定，但这条硬上限把名字永远卡在 200px —— **拖再宽也没用**。
- **修法**：`max-width:200px` → `max-width:100%`，跟着列宽走；列窄时省略号照旧（内容仍不反推列宽）。
- 安全性核对：`.row-ops` 是 `position:absolute` 的 hover 浮层，不参与 pname 排版 ⇒ 放开宽度无遮挡风险。
- 🔴 复用判据：**table-layout:fixed 的表，别在单元格内容上加写死的 px 宽度上限** —— 它会让用户「拖列宽」彻底失效且零报错（典型的「功能能用但没效果」）。要限宽用百分比或让 colgroup 管。

## 产品决策：小程序「记住密码」（00:34，用户提出，未拍板）
- **现状**：**既没有**记住密码、**也没有**记住账号。登录态 = 后端 session `expires_at = created_at + 24 小时`
  ⇒ **每 24 小时必须重登一次**（这才是用户想"记住密码"的真实痛点，不是退出后的问题）；
  退出走 `utils/session.js::doLogout` = 本机清态 **+ 服务端销毁会话**（v2026-09-20 已修）。
- 🔴 **结论：不做「记住密码」** —— 明文口令落 `wx.setStorageSync` 是**安全与合规红线**（PIPL / 等保：
  口令不得明文存储）；且本项目定位是**卖给其他经销商的 B2B SaaS**，客户安全审查必挂；
  更糟的是**同一账号可登 Web 端** ⇒ 密码泄露的影响面不止小程序。
- **推荐替代**：① **记住账号**（只存账号名、不存口令，零风险，省一半输入）；
  ② 把登录态 **24h → 7 天**（真正解决"每天要登录"，风险低 —— 企业内部工具且退出即销毁会话）。

### 🔴 建完必须实跑一遍 —— 一跑就暴露 3 个会「天天误报」的设计缺陷（关键教训）
1. **备份日志看"最后几行"会读到修复前的历史失败行** ⇒ 明天也会误报高危。
   修法：**只看产物**（当天目录存在 + 全部文件 >0 字节）为主判据；日志**必须按日期过滤** `grep "$(date +%F)"`。
2. **Python 弃用警告 `warnings.warn(message, stacklevel=1)` 每天刷 17 次**（且是多行堆栈，内容在续行上）
   ⇒ 会被「同一条 ≥5 次 = 疑似静默失效」规则命成假阳性。修法：统计前 `grep -v` 剔除，且只保留**带时间戳前缀**的行。
3. **「24h 内 Started 次数」在部署日必然偏高**（今天 14 次 = 多次主动重启）⇒ 不能一刀切报警。
   修法：**NRestarts（systemd 自动拉起）才是崩溃判据**；Started 次数只作「需关注」且注明「部署式重启属正常」。

### 🔴 跨设备副驾历史不可见 —— 根因定位（用户问，已查实）
- **现象**：公司笔记本用 boss 账号在副驾对话框完成对账，家里电脑同账号看不到。
- **用户澄清**：对账是在**副驾对话框**里做的（不是网页对账页、不是 v198 算子）。
- **决定性证据（生产库只读查询）**：

  2. **但 tenant_1 里没有任何一条"对账"会话** —— 那次对账不在服务器上。
  3. 桌面端副驾**只存本机 localStorage**（键 `hermes_session_<role>` 等，`desktop-app/js/app.js:3075/3082`），全桌面端代码 grep `/api/ai/sessions` = **0 命中** ⇒ 桌面端对话**从不写服务器**，本地 Hermes 引擎跑在机器上。
- **结论**：那次对账发生在**桌面端 App（Hergent 桌面端）的副驾**，对话锁在公司笔记本的 localStorage + 本地 Hermes，家里用网页端登录只从服务器拉历史 ⇒ 看不到。
  🔴 **2026-09-11 跨设备修复只覆盖 web↔web**（本地缓存拦住服务端拉取），对**桌面端↔网页无效**——因为桌面端根本不写服务器。
- **四个维度回顾**：① 认证归属：网页按(租户,username)隔离；桌面端不归属服务器。② 存储：网页→服务器 `chat_sessions`；桌面端→本机 localStorage。③ Hermes 关联：网页副驾调后端、历史落 `chat_sessions`；桌面端 Hermes 本地运行。④ 同步：网页↔网页可跨设备；桌面端↔任何设备不同步。

**关键判据（可复用）**
- 🔴 **`can_delete` 必须由服务端给，不能前端判**：`/my` 范围是「我报的 **OR** 我负责门店报的」（v224），**不全是本人单** —— 前端按「在列表里」就给删除入口 ⇒ 督导能抹掉销售的单据（越权）。且期次锁定时 UI 给了入口也会被硬拒 = 假入口（本项目反复出现的缺陷族）。
- 🔴 **撤回 = 软删（status='recalled'，留痕）/ 删除 = 硬删（不可逆）**：两者不可互相替代。撤回**允许管理员代劳**（纠偏他人误报），删除**只认本人**（不可逆，放开等于让督导删销售的单）。
- 🔴 **`data-*="布尔"` 会变成字符串**（`"false"` 也是真值）⇒ 一律传 `1/0` 再 `+x === 1` 比较。
- 左滑 vs 纵向滚动冲突：小程序 touchmove **没有 preventDefault**，只能靠**轴向锁定**（首次位移超 8px 定调，横向接管 / 纵向放手并收起）。
- 删除按钮宽度 `DEL_RPX=160` 写在 `mine.js`，`.swipe-act` 宽度写在 `wxss` —— **同一个数分处两文件**，靠注释互相对齐（改一处必须改另一处）。

**🔴 顺带修掉一个既有 P0 缺陷（与 v259 同因同修）**
`forecast_period_writable()` 里 `conn = get_db()` 是**裸调 @contextmanager 生成器**（`db/connection.py` 的 `get_db` 是 yield 生成器）⇒ 拿到的是上下文管理器不是连接；`conn.execute()` 先在 try 里 AttributeError，**`finally` 里的 `conn.close()` 又抛并覆盖前者**（Python 中 finally 异常替换 try 异常，只留 `__context__`）⇒ 栈看起来像"只错在 close"，极易误判。
- **后果：所有不传 `db_conn` 的调用方、period_id>0 时一律 500** —— 实测**既有的「撤回」接口就是 500**，撤回任何挂期次的单都只报 "Internal server error"，期次锁定原因一次都没到用户面前。
- **修法**：`db_conn is None` 时 `with get_db() as c: return forecast_period_writable(pid, db_conn=c)`（递归传真连接）。
- 排查同类：全仓其它裸用处都正确写了 `_cm.__enter__()`，**仅此一处**。
- ⚠️ **教训（取证方法）**：别只看栈顶那一行。`finally` 抛异常会替换 `try` 里的原始异常 —— 遇到"栈指向的行看起来不该错"，先想是不是 finally 覆盖了。

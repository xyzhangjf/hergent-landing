### 七、🔴🔴 v269 最深一层发现：**同一商品在系统里有两份档案**（这是单位对不上的根因）

不是「换算比缺失」，而是**舟谱条码被绑定到了另一份档案上**：
| | 正式档案 | 简称档案（被舟谱条码占用） |
|---|---|---|
| 例 | id=1422「蒙牛原味CD圆周杯100g*8杯*12组（新）」 | id=1538「CD杯8杯」 |
| `unit` | **杯**（与舟谱一致） | **组**（中单位） |
| 三档换算 | 中=组(8.0) 大=件(96.0) **完整** | 中=(0.0) 大=(0.0) **全空** |
| 条形码 | 空 | **6934665091117（舟谱在用的）** |

⇒ 按条码匹配**必然命中简称档案** ⇒ 数量单位对不上（舟谱说「杯」、档案说「组」），而简称档案又**没有换算比**，
   所以「换算」这条路在系统里根本走不通。涉及 **36 个商品 / 抽样 30,001 行里 7,830 行（26%）**。

✅ **好消息（实测 36/36 全部命中）**：每一个简称档案都能找到**名字几乎完全相同（30 个相似度 1.00）**
   且 `unit` 与舟谱一致的孪生正式档案，换算比就在孪生档案的 `medium_ratio` 里。

## §v275 路由级角色守卫（深链不再绕过入口显隐）· 已上线

### 起因（一句话）
v274 撤了侧栏入口，但 **`v-if` 只藏 DOM、不藏路由** ⇒ 主管手敲 `#/zhoupu-import` 照样能进页面
（点到"读取"才 403）。这是**假封锁**，比假入口更难发现 —— 假入口用户会来报，假封锁没人报。

### 三个设计决策（都是取舍，不是顺手）
1. **判据收成一个函数**：`roles.js::roleIn(r, allowList)`，`canUseMiniProgram`/`canViewForecastSummary`/
   `canImportZhoupu` 三处全部改为调它。路由表 `meta.roles` 与侧栏 `v-if` 从此引**同一个数组、
   同一个算法** ⇒ 不可能再出现"卡片没了但 URL 还能进"。
2. **守卫必须 await 权限，但失败要放行**：`roleIn('')` 对未知角色 fail-open（启动瞬间 role 是空串，
   判 false 会把老板弹走）。守卫语义不同（页面还没渲染、没有"闪一下"问题）⇒ 先
   `await ensureRoleLoaded()`（= `loadPerms()`，幂等、命中缓存不发请求）把"未知"消掉；
   **拉取失败仍放行**（「拉不到 ≠ 没权限」：宁可让终将被 403 的人多看一眼，不能把管理员挡在门外）。
3. **拒绝必须看得见**：不用 `return false`（原地停住、白屏 = 死按钮变体）⇒
   `return { path:'/workbench', query:{ denied:'舟谱单据导入' } }`，Shell 弹说明并**立刻清 query**
   （不清则刷新 / 回退 / 转发都会再弹一次）。

| `/forecast` | 页内某块按角色 | ❌ 业务员能进页面 ⇒ 整页拦**误伤** |
| `/payroll` 等 | `perms` 模块级 | ❌ 未授权时页面自带常驻说明；按模块拦会把"接口抖一下"放大成"进不去" |

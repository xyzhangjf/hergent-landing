  ⇒ 进改单也是服务端原值（临时改动被丢弃）。

### 🔴 判据
- **查看态内联编辑 = 只脏内存、不脏库**，但它污染「用户拿去做真实动作的派生数字」：合计/金额/最终下单/

## 08:45 🔴 判据：「勾品牌筛选 → 保存」不等于「把该品牌商品加进本期清单」
用户设想：「改单 → 筛选品牌（如新希望）→ 保存」就把该品牌商品上架到小程序。
**结论：不行，白点。**两道卡口（均已核源码）：

1. **筛选筛的是已进表的行，不从档案拉行。** `buildRowBase`（Forecast.vue:2658-2688）：
   `keep = showAll ? allProds : allProds.filter(p => refIds.has(p.id))`，
   `refIds` = 本期清单（`imported_products`）∪ 本期已有报单。默认状态下，清单里没有的商品
   **勾品牌也不会出现**；行显隐（`rowVisible`/`rowBaseShown`）只是 `v-show`。
2. **入清单的够格条件不含"被筛选到"。** `_sync_period_product_list`（forecast_submissions.py:819）
   的 `eligible` = 该行 `qty_by_unit` 里有 **>0** 的数 **或** 前端 `is_new`（addRow/粘贴置位）。
   所以即便先勾「显示全部商品」把 285 个 SKU 调出来再筛品牌，数量全 0 ⇒ 不入清单（小程序搜不到）。
   顺带确认：`save_matrix` 只给 `qty>0` 的行建 item ⇒ 也不会产生 0 数量报单明细，等于纯白跑一趟。

判据级结论：**「进本期清单（上架）」与「填数量（报单）」是两件事，现有 UI 把它们绑在一起了。**
批量上架目前唯一入口是期次管理里的「复制商品清单」（整期复制，不认品牌筛选）；单个靠 v612 补录。
若要做，正解是加显式动作（筛选后「加入本期清单 N 个」→ 载荷带独立标记，不动 eligible 的既有两支）。

  下次任何保存都会被当「小程序先报、Web 后加进表」自动加回清单 ⇒ 「撤下了又自己回来」且零报错。
  qty 恒 0 ⇒ 不 eligible ⇒ 撤下是持久的。被跳过的数量在确认框里明说，不静默少撤。

## v615（10:22-10:32）选行复选框 + 批量操作（替代 v613/v614 的「按筛选整批」）

### 为什么这个设计更好（记下来，别再退回 v613/v614 的形态）

1. 撤某品牌会**连带撤掉原本就在清单里的同品牌商品** —— 筛选表达不了「只要这几个」；
2. 按钮数 = 候选总数（实测 156），手滑一下就是一次大批量动作，且无法逐项复核。

- seq 列 46→76（装复选框）；`loadColWidths()` 里迁移老 localStorage 的 46（不迁移则本人正常、

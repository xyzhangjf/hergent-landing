## 08:00 核查「查看态也能改数量」对数据链的影响（只诊断，未改代码）
用户问：「非编辑态填报的数字也能修改，这个对后面的数据链有影响吗？」

### 实测事实（线上 v609，`v610-viewmode-edit-diag.mjs`）
- 查看态单击数量格 ⇒ `onCellClick`（`col.type==='qty'`）→ `editCell()` → 渲染 `<input.cell-qty>`；
  `commitCell()` 只写 `cross.rows` 内存（`qtyByUnit/total/amount/boxes` + `recomputeTotals()`），**不调任何 API**。
- 改 10 → 777 后：该行「最终下单」17 → 94、页脚合计金额 2,985.12 → 10,608.12；**改完零提示**（toast 为空）。
- 复制报单弹层的计数与「下单数量」复制源都是 `rowFinalQty(cross.rows)` ⇒ **复制出去的就是改后值**。
- `Page.reload` 后回落到 10 ⇒ 不落库。`enterEdit()` → `loadEditGrid()` 重新 `forecastApproveApi.summary`
  ⇒ 进改单也是服务端原值（临时改动被丢弃）。

### 🔴 判据
- **查看态内联编辑 = 只脏内存、不脏库**，但它污染「用户拿去做真实动作的派生数字」：合计/金额/最终下单/
  复制下单量。危险在于**复制给厂家下单**这一步 —— 屏幕上改了、库里没改 ⇒ 两边对不上，且全程无「未保存」提示。
- 同族风险：任何「内存派生 → 剪贴板/导出/下发」的动作，都要先确认它读的是**已保存值**还是**当前内存值**。
  若读内存，就必须在存在脏改动时显式告警（或直接禁用该动作）。
- 权限提醒：`editCell`/`commitCell` 无 `canDo('data','update')` 判断 ⇒ 无权限用户也能点改（只影响自己屏幕，
  但会误以为自己改了）。若要收口，加门禁即一行。

## 08:20-08:40 v612 补录的报单商品同步进「本期商品清单」（小程序实时可见）
用户：「我想增加报单商品，增加后小程序实时可以看到，正确的路径是什么」→ 给出 A/B 两案 →
用户回单字 **「B」**（= 删行也同步从清单移除）。

### 机制（改完要记住的三层）
- 小程序报单页 `GET /api/products/fill-search` **只读** `forecast_import_products`（本期清单），
  按 `sort_no` 排序；提交时的本期校验也用同一份（`forecast_period_product_ids`）。
- `save_matrix` 此前**只写报单明细、从不写清单** ⇒ 改单里补录的商品 Web 端当场可见、小程序永远搜不到。
- 能写清单的旧入口（新建期次沿上期 / 复制清单 / 重新导入）都只能"整期"，且导入会先删本期已导入明细。

### 改动
- 后端新增 `_sync_period_product_list(conn, pid, start, end, rows, operator)`，在 save_matrix
  **同一事务内**执行：新增（append 到末尾，`origin='manual'`，`sort_no=max+1`）/ 移除（物理 DELETE）。
  两条安全闸：`pid<=0` 不动；**payload 一个档案号都没有时不做移除**（防畸形请求清空整期）。
- 🔴 **新增的资格**必须限定为「有正数量 **或** `is_new`」。原因：勾「显示全部商品」时编辑表行底
  是**全部在售档案**（buildRowBase 的 showAll 分支），不加限定一次保存就把 285 个 SKU 全灌进清单 ——
  而 v215 的口径恰恰是「档案里的赠品不需要报单」。
- 后端 `bulk-upsert` 回执新增 `ids`（与入参 rows **同序**），前端按索引把新建档案的自增 id 回填。
- 保存回执新增 `list_added/list_removed/list_sync_error`，前端 toast 点名「小程序商品清单：新增 N / 移除 M」。

### 🔴 真机首轮就抓到一个真事故（这条最值钱）
第一版只做了"清单同步"，B4 判定 FAIL：候选商品 pid=1614 保存后 **spec='' / unit='件' /
sale_price=0**。根因是一条**既有的**隐患，被我这次流程踩响：
补录时商品名从候选面板挑（`useNameSuggest.nameSugPick` **只写 name**、不带档案号）⇒ 行 `product_id=0`
⇒ 保存时当"新商品"发给 `bulk-upsert`，而后端字段是**无条件覆盖**（缺省写 0）⇒ 把该商品档案整行清零。
（`prodBaseline` 只含**本期网格里**的行，所以"档案里有、这期没进表"的商品拿不到基线 ⇒ 判不出脏、必发。）
修法两条：① 保存前按「条码 → 名称」把档案号认回来并补空字段；② 认回档案的行**一律不发** bulk-upsert。
**判据：任何"看起来只是加一行"的补录，都要问一句「这一行会不会被当成新商品写进档案」。**

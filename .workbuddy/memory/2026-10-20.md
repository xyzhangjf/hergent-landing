**用户指令**：只回了一个「改」（承接上一轮列出的三项待拍板）。

**先做了三项侦察，结论与上一轮的判断对不上，已按实测纠正：**

**根因（数学）**：`.cross-viewport` 写 `max-height: calc(72vh + 119px)`，而「不溢出」要
`上方 +(0.72H+119)+ 下方 <= H` ⇒ **H >= 1539px**。也就是**任何真实视口都溢出**
（850/954/1080 实测溢出 193/154/129），用户必须滚页面才看得到合计栏与页脚；
编辑态却是按视口精确算的「恰好填满」⇒ 两态差 251px。

**落地（`src/pages/Forecast.vue`）**
- 抽出 `_belowSpan / _offsetInScrollHost / _availHeight` 三个函数，`editMaxH` 与新增的 `viewMaxH` 共用一份算术。
- `.cross-viewport` 加 `:style` 写内联 max-height；CSS 旧值降级为「首帧兜底」：`min(calc(72vh+119px), calc(100vh - 300px))`。
- 重算入口统一成 `recalcHeights()`（两态一起），调用点：resize / editMode / gridFullscreen / 三个筛选开关 / confirmInfo / rows.length / selRange。
- `recalcViewHeight` 找不到 `.cross-viewport`（在编辑态）时**保留旧值不清零**，否则退出编辑态那一帧会先撑高再塌。
- 全屏返回 0 = 不写内联（交回 CSS `max-height:none`）。

**真机验收（生产 hergent.cn，5 档 × 1080/954/900/768 视口，全 PASS）**

## v640 排查「后端稳态 754MB」→ 结论推翻：不是后端泄漏，是 cgroup 记账把租户网关算进后端预算

**上一轮（v639）结论错了，此处更正**：说「FastAPI 稳态吃 754MB」是错的。那是**整个 cgroup** 的数，后端自己只有 258~264MB。

**真实构成（hergent-erp.service 一个 cgroup 里住着 9 个进程）**：

| 进程 | 用户 | RSS | 该不该归后端 |
|---|---|---|---|
| `server.py`（后端本体）| hergent | 258MB | ✅ 是 |
| `hermes gateway` t1（老板企微）| hergent_t1 | 404MB | ❌ |
| `hermes gateway` t10（web API）| hergent_t10 | 249MB | ❌ |
| MCP `server.py` ×2（每个网关一个）| 租户 | 152MB | ❌ |
| gateway 的线程子进程 ×2 | 租户 | 24MB | ❌ |
| `hermes send --to wecom` ×2（**卡死 20 分钟**）| hergent_t1 | 200MB | ❌ |
| sudo 包装 ×2 | root | 11MB | ❌ |

**根因链（四环，缺一不成立）**
1. v635 用 `sudo -n -u hergent_tN` 作为**后端子进程**拉起网关 ⇒ 子进程**继承后端 service 的 cgroup**（cgroup 沿 fork 继承，且 `start_new_session` 不影响）。
2. 于是租户网关 + 其 MCP 子进程 + 其 send 子进程全部记在 `hergent-erp.service` 头上。
3. `MemoryHigh` 无论设 640 还是 1024 都会被总量（~1130MB）顶穿。
4. 🔴 **关键放大项：`vm.swappiness=0` + cgroup 内 `file=0`（全是 anon）** ⇒ 顶穿后 reclaim **无任何可回收页** ⇒ 每个任务在系统调用返回用户态时被 `mem_cgroup_handle_over_high` 挂住 ⇒ 表现为 **D 状态（像 disk sleep，实为节流）+ 请求全超时 + 整站白屏**。

**证据（真机）**
- `ps` 后端 RSS **258MB** vs cgroup `memory.current` **1127MB** —— 差值就是不在主进程里的那些子进程。
- 主进程自身 `State:D`、`/proc/PID/task/*/stack` = `mem_cgroup_handle_over_high` ⇒ 白屏的直接解释。
- 三段采样 1129/1130/1130MB ⇒ **稳定，不是泄漏**（排除「Python 堆泄漏」这条假线索）。
- 节流速率 **356 次/秒**（425963→468671，2 分钟 42708 次）。
- `hermes send` 两个进程 `wchan=mem_cgroup_handle_over_high`、**无 socket fd**（排除"卡在网络"）。
- 用户可见症状：企微 16:20 的提问 `response ready ... time=1148.9s` —— 卡了 **19 分钟**才回。

**已处置**
1. `kill -9` 两个卡死 `hermes send` ⇒ 释放 107MB，主进程立刻从 D 回到 `Ssl ep_poll`，**并当场解锁了那条企微回话**（16:39:53 发出）。

## v640 落地：租户网关迁出后端 cgroup（用户选 A，根治）

**交付物**

- 新增 sudoers `/etc/sudoers.d/hergent-tenant-cgroup`（`hergent ALL=(root) NOPASSWD: <脚本>`）。
- `hermes_tenants.py`：常量 `TENANT_CGROUP_HELPER / TENANT_CG_ROOT / TENANT_CG_HIGH_MB=640 / TENANT_CG_MAX_MB=768`；
  函数 `_tenant_cg / _tenant_cg_rel / in_tenant_cgroup / move_to_tenant_cgroup`；
  `_spawn` 在 `return p.pid` 前**立刻**搬（越早搬，滞留在后端账上的"在途页"越少）；
  `ensure_running` 在"进程在"分支自愈补搬（已在组内则只读一次 /proc，不打 sudo）。备份 `hermes_tenants.py.bak-v640-cg`。
- `hergent-erp.service`：`MemoryHigh 1536→768M / MemoryMax 1792→1024M`（网关不再占它的账，可以降回来）。

**🔴 新坑①：`/proc/<pid>/cgroup` 是相对挂载点的路径**
形如 `0::/hergent_tenants/t10`，不是 `/sys/fs/cgroup/hergent_tenants/t10`。
拿绝对路径去比 ⇒ `in_tenant_cgroup()` 恒 False ⇒ 每 60 秒白搬一次、还误报"新搬 3 个"。
**且必须整段相等**：`/hergent_tenants/t1` 是 `/hergent_tenants/t10` 的前缀，子串匹配会串号。

**🔴 新坑②：`sudo` 会把信号转发给子进程 ⇒ 只搬 hermes 不搬 sudo 包装＝白搬**
第一次只按 UID 搬了 hermes（uid hergent_tN），`sudo` 包装（uid 0）留在后端 cgroup 里 ⇒
`systemctl restart hergent-erp` 的 control-group kill 打到 sudo ⇒ sudo 把 SIGTERM 转给 hermes
⇒ **重启 ERP 顺手掐断所有租户副驾通道**（实测 t1/t10 网关 PID 一起消失）。
修法：脚本额外接第 4 参（刚拉起的 pid）+ 向上最多 4 层找 `sudo … gateway … run` 一起搬。
好处双重：① 重启 ERP 不再掐断通道；② hermes 子进程**从出生**就在租户 cgroup，
不会先在错的账上分配几十上百 MB（cgroup v2 已记账页不随进程迁移，只能等重新分配）。

**🔴 新坑③：`memory.reclaim` 在 systemd 托管的 service cgroup 上写不进去**（Permission denied，root 也不行）
⇒ 旧记账只能靠**进程重启**清干净，不能靠回收把账赶过去。所以"迁移存量网关"这一动作本身
不能立刻降低后端记账——真正生效要等那次重启。

## v648：企微通道疑点排查结论（推送踢网关，2.2s 自愈，可接受）
**背景**：v647 收尾核对时发现网关日志约每 5 分钟一次 `websocket closed`→`Reconnected`，且误读过一个
`logs/gateway_state.json` 显示 disconnected，一度以为「推送把网关踢了」又被「日志零新增」推翻，来回摆两次。今晚坐实：
- **真相：每次进程外推送确实踢掉网关长连接**。机制：后端 `send_message`→`hermes send` CLI→
  `send_message_tool`（in-process runner 只有网关进程自己有）→ 企微插件 `_standalone_send` 临时开一条
  WS（aibot_subscribe）发完即断 ⇒ 同 bot 单订阅规则挤掉网关 ⇒ 2.2s 后重连成功（closed/Reconnected 成对，无 846609）。
- **「5 分钟周期」是推送驱动不是服务端轮换**：close 与推送一一对应；23:40 cron 无告警 ⇒ 23:43 网格点无 close。
- **架构上免不了**：aibot 协议纯 WS（subscribe/callback/send_msg/upload 全在 WS），无 HTTP 发送 API；
  网关 api_server 路由表（sessions/chat/jobs/runs）也没有代发端点。心跳 30s，排除空闲被踢。
- **误导源作废**：`/root/.hermes/logs/gateway_state.json` 是无代码引用的历史遗留（已消失）；
  权威状态文件是 `/root/.hermes/gateway_state.json`（现显示 wecom connected@23:37:58，socket ESTAB）。
- **决策：接受现状**（推送能到、自愈 2.2s、正常态一天一两条）。彻底方案列 P1：把库存预警/巡检推送

  「日志当时没新增」≠「没发生」——close 可能延迟几十秒才写盘。

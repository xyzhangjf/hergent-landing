## 侧栏「档案管理」点击无高亮 —— 修复
- **现象**：侧栏点档案管理，URL 到 `/archive/employees`，但 `.sb-item` 拿不到 `router-link-active`，切到客户/品牌/商品 tab 更不可能高亮。
- **根因**：原路由是**一条纯 redirect record + 4 条平级 record**（`{path:'archive',redirect:'/archive/employees'}` + `archive/employees|customers|brands|products`）。vue-router `useLink` 的 active 判定 = 取 `router.resolve(to).matched` 的**最后一项**，去 `currentRoute.matched` 里 findIndex；而 `router.resolve()` **不跟随 redirect**（只有 `pushWithRedirect` 的 `handleRedirectRecord` 才展开）→ link 解析出的 redirect record 永不出现在当前 matched 链里 → 永远 -1。其它模块都是单 record，天然 self-match，所以只有它坏。
- **修复**：改标准父子路由 —— 父 `{path:'archive', component: ArchiveShell, redirect:'/archive/employees'}`，4 个 tab 降为 children；新增薄壳 `src/pages/ArchiveShell.vue`（仅 `<router-view />`）。父 record 进 matched 链，侧栏 `to="/archive"` 的 record 成为任意子页面的祖先 → active 自动命中，零特殊分支、零 meta 约定。
- **踩过的坑（重要）**：先试了 `path: 'archive/:tab?'` 单 record 方案，DOM 上点击时高亮、切 tab 就掉 —— 因为 `isActive` 还要过 `includesParams(currentRoute.params, route.params)`，可选参数未匹配时 link 的 `params.tab = ''`，与 `{tab:'products'}` 比较 `'' !== 'products'` → false。**带动态段的参数路由不能用于纯菜单高亮**。
- **另注**：无 component 的父 record 不会进 `matched`（vue-router `isMatchable()` = `name || components || redirect`），纯分组父路由救不了高亮，必须有 component（薄壳即可）。
- **验证（真机）**：刷新直入 `#/archive/products` → tab 正确 + 高亮在；点侧栏 → 跳 `/archive/employees` 且高亮；四个 tab 逐个切换 → `sidebarActive:true` 全通过；与「预报订货管理」active 态 computed style **完全一致**（bg `rgba(6,182,212,.06)` / color `rgb(8,145,178)` / weight 500）。

## 调研：WorkBuddy 的「MCP 连企业微信」到底是什么（用户提问）

**用户问**：「我看 workbuddy 现在是用 mcp 连接企业微信，我们是否也应该采用这种方式呢？」

### 实测结论（有证据）
1. **不是 MCP**。`~/.workbuddy/connectors/<id>/mcp.json` 里有 `connector:qq-mail`/`lexiang`/`tencent-docs`/`linear`/`canva` 等 HTTP MCP，**但没有 wecom 条目**。
2. 企微走的是 **`@wecom/cli`（腾讯官方 npm 包）**，本机 v1.2.1（2026-09-08 构建），装在 `~/.workbuddy/binaries/node/cli-connector-packages/bin/wecom-cli`；授权 `wecom-cli auth init`（扫码 或 `--manual` 手填 Bot ID + Secret）。
3. **它是纯出站工具，没有入站能力**。命令全清单：`auth / calendar / chat / contact / disk / doc / mail / media / message / meeting / sheet / smartpage / smartsheet / todo`。
   - `message send`、`message aibot send`（以智能机器人身份发 md/图片/文件/语音/视频）
   - `chat messages list`（**按时间范围分页拉取**历史消息，非实时）
   - 全库 grep `listen|subscribe|hook|callback|stream|socket|watch|receive` → **0 命中**。
4. ⭐ **关键同一性**：`auth init --manual` 要的 Bot ID + Secret **就是** Hermes 侧我们写的 `WECOM_BOT_ID` + `WECOM_SECRET` —— 两边接的是**同一个企业微信智能机器人**，只是接法不同（CLI 走出站 API / 我们走长连接）。

### 判断
- **不能替代**：Hergent 要「老板在企微里发一句、AI 回一句」＝必须实时入站；CLI 无此能力。用 `chat messages list` 轮询模拟 → 有延迟、需先知会话 ID、每租户一进程，比长连接更贵更脆。
- **但它暴露了我们缺的一块**：Hermes 的企微适配器只覆盖消息；CLI 覆盖 doc/sheet/smartsheet/calendar/meeting/todo/mail/disk。这块是 AI 副驾做高价值动作的地方（读返利政策文档、日报写成企微文档、库存预警排待办、到货节点排日程）。
- ⭐ **MCP 方向是反的**：MCP 需**宿主**（WorkBuddy/Claude Desktop 这类 AI 客户端来跑），Hergent 是服务端产品当不了宿主 → 「用 MCP 连企微」这条路本身不成立。正解是**Hergent 对外提供 MCP server**，让客户自己的 AI 助手来查 Hergent 数据。

### 待用户拍板（已给选项 A/B/C）

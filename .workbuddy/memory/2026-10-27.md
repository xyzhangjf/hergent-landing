## v698：修「采购单审核后 付款/预付款/入库 三个入口全不显示」（P0 事故）

老板早上反馈 v697 上线后线上看不到任何入口。根因是**状态值凭印象写**：

- 生产 `purchase_orders` 状态分布实测：`received=79, confirmed=2, draft=2, cancelled=1`
  —— **`approved` 一张都没有**。真实的「已审待执行」是 **`confirmed`**（v417「保存并审核」定的）。
- v697 判定写成 `_st_v == "approved"` ⇒ 2 张已审单永远拿不到 `prepay`。
- `received_amount` 是 **v403 才加的列**，79 张舟谱导入单（导入时直接标 `received`、没走 confirm）
  这一列全是 0 ⇒ 「已到货」判据不成立 ⇒ 付款按钮也不显示。
- **后端自身状态机断裂（最致命）**：`purchase_order_confirm` 守卫原本是
  `status IN ('draft','approved')`，**不收 `confirmed`** ⇒ 审核通过的单根本入不了库。
  前端 `canConfirm` 与后端逐字对齐 ⇒ 按钮同样不显示。

修法（`tools/hergent/patch_v697c_confirmed_state.py`，8 锚点全命中）：
1. 两处入库守卫补 `confirmed`（`approved` 保留兼容）
2. `pay_mode` 认 `("approved","confirmed")`
3. 新增 `_po_received_amount(o)`：**到货金额的唯一读法**。`received_amount<=0` 且
   `status='received'` ⇒ 真值 = 订单金额。**只对 `received` 兜底，`partial` 不猜**
   （分批到货金额未知，猜就是造数）。`_po_unpaid` / `_po_overpaid` / pay_mode / 接口返回全部改走它。
4. 前端 `canConfirm`/`canReceive`/`inbActionTitle`/`approvalProgressText` 加 `confirmed`。

验证（`tools/hergent/test_v697c_state.py`，**只读**生产真实数据）：28 项全过。
线上真实页面（`tests/perf/v698/real-prod.mjs`，**不 mock**，用老板真实会话）：6 项全过。
部署：v698，三处 md5 双侧一致，线上 `data-build=v698`。

## 🔴 部署踩坑：rsync 不能加 `--no-delete`

我写了 `rsync -av --no-delete` 传 assets —— 该参数不存在，rsync 报用法错误**没传任何文件**，
但后面的 `scp index.html` 照样执行 ⇒ 线上 index.html 已指向**不存在的 chunk**，差点白屏。
发现后立刻用 `rsync -av`（不加任何 delete 参数，默认就不删）重传修复。
**纪律：rsync 与 scp 串在 `&&` 后面时，前者失败不会阻止后者 ⇒ 传完必须立刻 ls 校验新 chunk 存在。**

## v699：修「同屏两个 分批到货/确认入库」

老板反馈详情页出现两套入库按钮。原因：v697 在「入库单」页签内加了操作条
（老板要求「已审核后可在入库单页直接发起入库」），但**顶部动作区那两个按钮没做互斥**
⇒ detail/payments 页签顶部一组、inbound 页签顶部一组 + 页内操作条一组。

修法：顶部两个按钮加 `tab !== 'inbound'` 条件 —— **同一时刻只露一处，落在当前正在看的那一页**。
两处「分批到货」行为不同且都对：顶部 `showRecv = !showRecv` 在当前页展开逐行填数面板；
入库单页那条 `gotoPartialReceive()` 跳回详情页再展开（那页才有明细表）。不是重复实现。

验证 `tests/perf/v699/single-entry.mjs`（线上真实会话，12 项全过）：
detail/payments 整页「确认入库」=1 且操作条=0；inbound 操作条=1 且顶部=0。
v699 已部署，三处 md5 双侧一致。

## 线上真实登录探针的做法（可复用）

前端登录态是**两个 cookie 缺一不可**：
- `erp_token` = 真凭证（httpOnly，后端 Set-Cookie 下发）
- `hergent_auth` = `'1'` 标记 cookie（非 httpOnly，路由守卫 `auth.hasSession` 读它）

只注 `erp_token` ⇒ 守卫恒 false ⇒ 跳回登录页，**看起来像"部署没生效"**，极易误判。
playwright `addCookies` 用 `url` 时**不能同时给 path**（会报 "Cookie should have either url or path"）。
探测脚本必须放在项目目录内（`/tmp` 下 import 不到 playwright）。

## v700：副驾头像「又回退成 🚀」= 租户中间件把 <img> 拦成 403

老板报「副驾的角色头像怎么又回退到火箭图标」。**数据与文件全是好的**，坏的是访问链路。

先纠正一个容易查错的事实：头像**不在** `/opt/hergent-erp/static/role-avatars/`。
`ai_roles.py::_AVATAR_ROOT` 用 `dirname(dirname(abspath(__file__)))` 解析 ⇒ 落在
**`/opt/hergent-data/role-avatars/<tenant>/<role>.png`**（故意放部署目录之外，
避免后端 deploy 的 rsync --delete 误删）。现有 tenant 1 的 5 张：copilot 96928B /
accountant 89033 / cs 95862 / secretary 98690 / ops 97395（一角色一图，256x256）。

根因（四条 curl 实测）：
```
无 cookie                        → 200 image/png 96928B
有效 token（能推导出租户）        → 200
有效 token + hergent_tenant=无权租户 → 403 TENANT_FORBIDDEN
过期/无效 token                  → 403 TENANT_REQUIRED   ← 老板最可能是这条（session 已过期）
```
`tenant_middleware` 对 `/api/ai` 前缀一律 fail-closed 要求租户上下文，而
**`<img src>` 是浏览器自发请求，带不了 `X-Tenant-Id` 自定义头**，只能靠
`hergent_tenant` cookie 或 token 推导。业务接口自己带头（client.js）所以全正常
⇒ **「只有头像坏、别的都好」就是这个形状**。端点 `ai_role_avatar_get` 本身设计是对的
（拿不到租户就走 `find_role_avatar_fallback`），但它根本没机会被执行。

修法（patch_v700_avatar_tenant.py，1 锚点，幂等 + 备份 + 编译校验 + 自动回滚）：
在 G2 强制判定**之前**插头像专用分支 —— GET 且路径匹配 `/api/ai/roles/*/avatar` 时，
能解析到租户就照常用（**租户隔离不放松**），解析不到或无权则 `set_tenant_context(None)`
放行，交给端点走 fallback；非法 tenant id 仍返回 400（校验不吞）。

验证：五条路径（A/B/C/D 全 200、E 非法 id 仍 400，五张头像体积各不相同）；
`tests/perf/avatar/v700-regress.mjs` 线上真实会话 14 项全过，其中 case2 **故意塞
无权 cookie**（修复前必 403 的场景）现在也是 256×256 真图。视觉：顶栏 /
「将由X回答」/ 输入框左侧三处同一张 3D 人像，无 🚀。

🔴 判据（可复用）：**业务接口一切正常、只有图片/附件裂** ⇒ 先怀疑「不能携带自定义头的
请求」被中间件拦了（`<img>` / `<link>` / 下载 / `window.open`）。这类请求只能吃 cookie，
任何「必须带 X-Tenant-Id」的 fail-closed 设计都会在这里出现静默降级。

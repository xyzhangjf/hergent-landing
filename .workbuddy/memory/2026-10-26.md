## v688 采购建单表 125% 缩放下不再横滚（老板选 A）

### 🔴 迁移范式的三条硬判据（下次别重新试错）
1. **内部布局必须留在 slot wrapper**（`.ba-fields`/`.df-body`/`.cc-body`…），不能放组件里：
   父页 scoped 的后代选择器（`.xx-modal .xx-field`）命中不到子组件内部元素。
2. **类名透传（overlayClass/panelClass）不是解法**：v-if 挂载下父页规则照样打不到组件内部元素，
   透传只是拿到类名、拿不到对应规则。试过、放弃。
3. **`#header` 只替换标题区，不替换关闭按钮**：否则每个自定义头部的页面都要自己再写一个 X。

### 🔴 收编带来的唯一行为变化必须补齐
16 页原本**没有** ESC / 遮罩关闭。收编后组件统一提供 ⇒ 等于给 18 个表单页开了
「一按就关、改动全丢」的入口。解法：组件加 `guardClose`（默认关），19 页开启。
- 判据 = **纯 DOM 级**：打开后只有真实 `input`/`change` 事件才算「动过」
  （程序化赋值不触发事件 ⇒ 自动带出字段不算改动）；纯查看弹窗无控件 ⇒ 永不拦。
- 交互 = 第一下只提示（`.ui-modal-guard` 琥珀条）、第二下才关。
- 不给 19 页各写 isDirty：那等于把 SupplierArchive 的基线 bug 复制 19 遍。

### 探针抓到的真 bug（已修）
`SupplierArchive.tryClose` 原为 `if (isDirty.value) { closeHint=true; return }`，
**缺 `&& !closeHint.value`** ⇒ 只要改过字段就永远关不掉（ESC/X/遮罩全失效，只能点「放弃改动」）。
与下方 `onCancel` 口径不一致才埋下的。修正为 `if (isDirty && !closeHint)`。

## v692 第 1 期落地：副驾真实 token 计量（用户选 A）

### 🔴 实测确定的三条上游口径（这是本轮全部设计的地基）
1. **一次用户请求只发一个 `usage` 块，且是「整个 agent 循环的累计值」**
   - 单问「说两个字」→ `prompt_tokens = 20,867`
   - 多轮工具（内部 8 次 API 调）→ `prompt_tokens = 185,281`
   - 与 Hermes 账本交叉验证**分毫不差**：`sessions.input_tokens(5,057)` +
     `session_model_usage.cache_read_tokens(180,224)` = `185,281`
   ⇒ **一次请求落一行，绝不按 chunk 累加**（累加会翻 N 倍，这是最容易写错的）
2. **`prompt_tokens` = 未缓存 + 缓存命中**（`134 + 20,734 = 20,868` 对得上）
   ⇒ 作为**用量**准确；但**不能乘全价算成本** —— 那次实际 `$0.00008`，
   按全价估会**高估约 40 倍**
3. usage 里**没有** `cached_tokens` 字段（不像 OpenAI 有 `prompt_tokens_details`）
   ⇒ 缓存命中只能从 Hermes 账本取，而那张表 `api_server` 会话 `user_id` 全 NULL
   ⇒ **不能做用户归因**，只能做租户级总量

另：SSE 里回显的 `model` 是 `hermes-agent`，**不是真实模型**
（账本显示内部会在 `deepseek-flash` / `deepseek-v4-flash` 之间自己切）。

## v697 采购「预付款 + 入库单页发起入库」（22:50 部署）
### 老板定的三条口径
① 预付记**货款流水**（cash_flow），不建预付台账；② 只有 `approved` 能预付；③ **预付不设上限**（推翻我的建议）。

### 这个需求踩在三处既有缺陷上（不修就是假功能）
1. `_po_unpaid` 只减 paid ⇒ 未入库时 received=0 ⇒ 未结恒 0 ⇒ 付款闸会拒掉每一笔预付。**改：减 prepaid_amount**。
2. `purchase_order_partial_receive` **不生成 receivables 应付行** ⇒ 分批到货后 `ap_exists=false` ⇒ 「这张单没有应付单，不用付款」⇒ 部分到货的货永远付不了钱。**已补**。
3. 货款页「已预付」原是**供应商维度**（prepayments WHERE ref_id=0），不是本单。**已改本单口径**，供应商维度仍在 `supplier_prepay`。

### 「不设上限」的必要配套：`_po_overpaid`
未结用 `max(0,…)` 兜底、永不为负 ⇒ 多付的钱被 max 吃掉 ⇒ 显示「未结 0」看似刚好、实际多给了钱。
新增独立 `overpaid_amount`：未入库比订单金额、已入库比到货金额。货款页显式提示。
🔴 **凡「用 max 兜底防负数」的地方，都要问一句「被吃掉的那部分需不需要单独报出来」。**

### 最隐蔽的一条：预付必须在应付行上留痕
预付不进 receivables ⇒ 入库后往来账仍显示「欠 2000」，而货款页显示「未结 1500」⇒ 两处记账分叉（正是那个黄警告要报的错）。
**修法**：`confirm` / `partial_receive` 建应付行时把 `min(已预付, 应付金额)` 写进 `receivables.paid_amount`，状态置 partial。
- 🔴 **只在首次创建时写**，后续到货不覆盖（覆盖会把真实付款额重置回预付额，真丢账且不报错）。
- 口径自洽证明：unpaid = received − prepaid − paid；ap_unpaid = amount − (prepaid+paid)；整单入库时 amount=received ⇒ 两者恒等。

### 会计科目：预付也记 2202（不记 1123）
若预付记 1123，入库时 `auto_journal_for_purchase` 贷 2202 全额 ⇒ 2202 虚高、1123 挂永不平余额，还得补转账凭证。
统一 2202 时「入库贷全额 − 预付借部分 = 真实应付」自动平。小企业口径叫「应付账款借方余额」，实质是预付。

### 前端
- 按钮/弹窗**完全按后端 `pay_mode`**（prepay|pay|none）渲染，前端零推导。
- 未入库时「未结金额」显示 `—`（写 ¥0.00 会被读成"不用付"，而这页正是来预付的）。
- 流水表加「类型」列（预付/付款）+ **分行合计**：`paid_amount` 不含预付，合并成一个数会让预付凭空消失。
  🔴 合计改**按行加总**：实测踩过「表里有一行 ¥500、合计却写 ¥0.00」（数据与汇总不同步）。
- 预付款**不预填金额**（付款预填未结额是对的；预付预填会诱导直接点确认，钱就出去了）。
- 入库单 tab 新增操作条，条件复用 `canConfirm`/`canReceive`（**不另写判断**，否则两处不同步）；
  「分批到货」是跳详情页并自动展开，不复制第二套表单（复制的那套迟早漏单位换算）。
- 🔴 **`draft` 允许入库是既有设计**（<5000 免审直接落 draft，没有审批链）。不要为字面「已审核才能入库」收紧守卫，会让所有小额单静默进不了库。

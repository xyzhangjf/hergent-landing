#### 「登录页加『电脑端』跳转 Web 端」—— 合规判断 + 方案（14:5x，新问题）

- **用户问**：小程序登录页加"电脑端"字样，点击跳转 Web 端，是否合规？怎么设计更好？
- 🔴 **本轮核实的关键事实**：
  1. 小程序 `appid = wxf8ce9b8e4b5693be`，`libVersion 3.4.3`，**从未使用 web-view / openEmbeddedMiniProgram**（全库 grep 空）。
  2. 🔴 **hergent.cn 已做移动端适配**：`index.html:5` viewport 齐全；`Shell.vue:112`「移动端底部 Tab」、`:121`「移动端更多抽屉」、`:600` `@media(max-width:768px)` ⇒ 手机上打开网页版**是可用体验**（不是 PC 页塞进手机）。
  3. **Web 端登录路由 = `/login`**（`hergent-cn-v2/src/router/index.js:48`），hash 模式 ⇒ 完整地址 `https://hergent.cn/#/login`。
  4. 🔴 **无任何免登/一次性票据机制**（`hergent-erp/server/routers/auth.py` 无 ticket/sso/免登）⇒ 走 web-view 用户**必须再登录一次**。
  5. `login.js:44-45` 已有纪律注释：「不做记住密码 —— 明文口令落 storage 是合规红线，且**同一账号可登 Web 端**，泄露影响面远大于小程序本身」⇒ 免登票据若要做，**必须一次性 + 短时效 + 不可复用**，绝不能把长效 token 塞 URL。
- 🔴 **核心结论（已告知用户）**：
  - **"点击跳转 Web 端"在微信小程序里只有一条合规路径 = `web-view` 内嵌**；"跳到外部浏览器/唤起电脑/引导下载 App" = **违规且技术上做不到**。
  - **认知纠正**：手机上点"电脑端"**到不了电脑** —— 微信小程序无任何能力唤起 PC 浏览器；web-view 打开的也是**手机上的网页**。
  - `<web-view>` 是**页面级组件、必须独占整页** ⇒ 不能嵌在登录页当小窗口；实现 = `wx.navigateTo` 到新页 `/pages/webview/webview?url=...` 整页加载。
  - 首次带 web-view 提审**会触发更严人工审核**；类目「工具→效率」下 web-view 只能指向**功能页**（登录/报单），**不能指向营销页**。

## 核实：预报「加单」列是否强制分摊到业务员（2026-10-02 下午，纯只读核查，未改任何代码）

**用户问题**：「加单列是否强制要求分摊到业务员头上？用户能否自由选择分摊或不分摊？
加单有时只是用于**备货**、无需归属到业务员。请说明当前校验逻辑与分摊规则，
并指出在哪些条件下可以不分摊。」

### 🔴 核心结论：「没有任何校验，但你也无法选择不分摊」

判「是否强制」**不能只看校验**（这是本题最容易答错的地方）：

| # | 查什么 | 结果 |
|---|---|---|
| ① | **硬拦**（422/409/前端 `return`/按钮 disabled） | ❌ **全无** —— `save_matrix` 唯一的 4xx 是缺参数 / 期次不可写 / 乐观锁冲突；定稿 `close_period` 也**不校验**分摊 |
| ② | 🔴 **缺省路径**（不做时系统是否替补） | ✅ **会** —— 保存汇总表时**无条件**跑 `plan_extra_allocs()`（**不在任何 if 里**），只要 ≥1 个可分摊对象就自动落 `forecast_extra_alloc` |
| ③ | 派生量下游 | 定稿通知 / 付款金额（`alloc_box`）/ 留痕都读它 |

⇒ **「没有校验」≠「可以不做」**。用户问「能不能不做」，要答的是「**谁会替你做**」。

### 三层分流（`_alloc_members_of()` 唯一实现，四处共用：保存落库 / 界面判据 / 弹窗 / 预演）

| 层 | 触发条件 | 可分摊对象 | 结果 |
|---|---|---|---|
| **L1** | 该商品在**到货月**有 `active` 商品目标 | 目标分解承接人 | **必分** |
| **L2** | 无目标 / 目标没填承接人 | **本期报过该商品的人**（按报单量推导占比，`ratios_from_reported`） | **必分** |
| **L3** | 无目标 **且** 本期无人报过 | 无 | ✅ **不分**（唯一自动不分的情形）|

**占比规则**（`domain/product_targets.allocate()`，**别重写**）：
- 加单：`alloc_i = D × ratio_i / 100`（**绝对比例，不归一化**；Σ<100 的缺口 `ratio_gap` **如实上报、不重分**）
- 减单：`min(|D|×ratio_i/100, reported_box_i)` **夹断到 ≥0**，被夹掉的 `clip_gap` 在**还有余量的人**之间按相对占比重分（≤64 轮）
- `ratio_gap`（占比不足）与 `clip_gap`（报量不足）**分开算**，只有后者会重分

### 🔴 逐条回生产验可达性（不能穷举完就交差）

- 商品目标**创建时强制 ≥1 承接人**：`_validate_allocs()` → `if not allocs: raise 422 "请至少选择一位承接人"`
  ⇒ **L1 恒成立** ⇒ L2 的「目标没填承接人」这条入口**生产 0 条、不可达**
  （对照：tenant_1 共 4 条目标，承接人 2/3/3/4，**0 条为 0 承接人**）
- ⇒ 生产里**唯一能"不分摊"的路径 = L3**

### L3 的两类成因（= 「谁能算可分摊对象」的反面）

| 成因 | 判据 | tenant_1 实测 |
|---|---|---|
| 本期真没人报过 | `_reported_by_operator()` 返回空 | — |
| **报过，但列头挂不上人** | `alias_map` 要求 **`is_active ≠ 0` 且 `employee_id > 0`** | 9 个列头里**只有 5 个能接上人**（东津/吾悦/刘小顶/美联保康/刘善涛）；`唐成`=外部客户账号（`external_user_id>0`，v317 口径**不参与内部分摊**）；`永诺旗舰店/永诺（江山店）/永辉东津店`=已停用（v343 起不计入汇总）；**其余绝大多数（黄家伟/谢总/程欢欢/民发/汴河…）= `nomap` 从没登记过** |

🔴 **第二类才是用户说的"备货"场景**：生产里**真实存在一个叫「备货」的报单列头**（1 单，`nomap`）

⇒ **「备货要不要归到业务员」取决于「这笔量记在哪个列头下」，不取决于有没有开关。**

## 一、🔴 本轮最有价值的方法论：**「精确到时分」这类问题必须分三层答**

用户问「能不能精确到时分」，**只有一个整数答案就一定会答错**。三层各自独立：

| 层 | 问的是 | 本轮实测 |
|---|---|---|
| **记录层** | 数据里存的是什么粒度？ | `forecast_periods.order_start/order_end` = `TEXT`，生产 **7 期全部 10 字符**（`YYYY-MM-DD`）⇒ **只到天**；**时分不在期次上**，在品牌规则 `rebate_target_rules.auto_open_time/auto_close_time/supplier_deadline_time` |
| **执行层** | 系统**几点真的开/关**？ | **已到分** —— `T_open = order_start @ open_time`、`T_close = order_end @ close_time`（`_period_close_at()`）；生产规则 id=10 = 16:00/21:00/22:00，与通知里的「关单时刻 2026-10-03 21:00」**互相印证** |
| **闸门层** | **能不能提交**按什么判？ | 🔴 **只到天** —— `forecast_period_writable` 是 `oe < today`（`erp_db.py:17840`），**纯字符串比较，时分不参与** |

⇒ 正确答复 = 「**支持**，但支持的是"几点开/几点关"那一层；**期次记的是哪天**，而**闸门只判到天**」。
**只答"支持"或"不支持"都是误导。**

🔴 **附带的硬技术风险（必须提前说，否则后人会踩）**：**不能**把 `order_end` 直接改成 `'2026-10-03 21:00'` ——
`oe < today` 在两侧都是字符串：`'2026-10-03 21:00' < '2026-10-03'` = **False**（等长前缀后更长者更大）
⇒ **当天永远不会被锁**，闸门静默失效。要做得改判据（截前 10 位比较），**不是加个时间输入框就行**。

### 三、数据模型：存档「**停单日**」而不是「少几次」

旧实现 `rebate_target_rules.arrival_count_override` 是规则上的**永久标量**，两处错：
① 10 月填的次数会一路生效到 11/12 月（实测蒙牛鲜奶长期 16，而 11 月系统推算只有 15
⇒ **均单分母偏大、均单偏小**）；② 只有"几次"、没有"哪一天" ⇒ **"停一单"无处表达**，
而到货日历仍按含停单日的排程算 ⇒ 日历 / 次数 / 均单分母**三处口径互不相同**（同屏两把尺子）。

⇒ 新表 `rebate_arrival_skips(rule_id, ym, skip_dates, count_override)` + 唯一索引。
**为什么必须按 `ym` 存**：这正是「下月自动以系统推算为准」的实现 —— 记录自带 ym，
查下个月自然查不到，**不需要任何"月初重置"动作**（数据模型自带的性质 > 定时任务）。

### 🔴 一、v363 报告的误报（本轮最重要的发现）

**误报内容**：v363 说「`st-*` / `sev-*` / `has-*` / `soft-*` / `oe-c*` **5 组拼接类全部无定义** ⇒ 状态色静默失效」。**实际 5 组全部有定义，缺定义数 = 0。**

**根因三条（都定位到具体代码）**：
1. **CSS 复合选择器只抽了第一个类** —— `.tag.st-draft{background:var(--st-draft-bg);color:var(--st-draft-txt)}` 这种写法里，旧提取器只记 `tag`，把 `st-draft` 丢了 ⇒ 整个 `.tag.st-*` 家族被判「零定义」。**正解：选择器内抽全部 `.cls`**（`re.finditer(r'\.(-?[_a-zA-Z][_a-zA-Z0-9-]*)', sel)`）。
2. **`\bclass=` 把 `:class=` 也匹配了** —— `\b` 在 `:` 与 `c` 之间成立 ⇒ `:class="{ on: activeTab === 'summary' }"` 被当静态 class 拆词，`activeTab`/`d`/`ri` 等**变量名**混入 ⇒ 差集虚涨（实测 60）。**正解：`(?<!:)class=`**。
3. **基准缺全局 CSS** —— 只拿本页 `<style>` 当「已定义」，`card`/`btn-sm`/`tbl`/`state-empty` 等全局类全被误报。**正解：基准 = 本页 scoped ∪ `src/styles/variables.css`**（本项目全局 CSS **只有这一个文件**，34KB）。
4. **另有一条：猜值域而不是实证值域** —— v363 拿 `has-warn/risk/info` 去测，而实际值域是 `void`/`short`/`done`/`gap`（见 `ptExtraMark()`）；`soft-` 实际只有 `miss`/`over`。**正解：值域必须从源码实证（`grep` 到赋值点），不能凭类名猜。**

# v365 停单 ⇒ 该期次不再自动新建（后端 + 前端 · 已上线 2026-10-02 21:19）

## 三点回答（老板要的就是这三条）

- **触发条件**：在「目标与返利 → 品牌目标 → 到货节奏」里点掉某一天（落 `rebate_arrival_skips`）。
  **没有独立开关** —— 停单本身就是触发。
- **生效范围**：① 只影响**自动建表**（手动建表不受影响，本轮刻意）；
  ② 只影响**那天到货**的那一期（`期次.arrival_date == 停单日` 的**等值比较**，不是「同月」）；
  ③ 已存在的期次**不删不关**，只阻止新建。
- **自动模式处理逻辑**：判定写在 `build_period_plan`（预览与调度器**唯一共享实现**）；
  **全停才排除**（保守侧）；被排除的期次仍留 `periods` 带 `excluded=True`（不静默消失）；
  调度器把被排除的期次**最先** `continue`（不建也不关 ⇒ 不碰「同时只有一个 open 期次」硬闸、

## 🔴 本轮抓到并修的四个缺陷（全是「界面与事实相反 / 算对了看不见」类）

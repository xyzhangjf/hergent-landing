# 2026-08-12 工作日志

## 预报订单流程梳理 + 微信小程序可行性（对话）
- 用户口述当前预报订单全流程：4 类人（业务员/促销/导购/分销商）经**企业微信智能表格**填报 → 文员导 Excel 粘贴"下单表" → 同事审核（综合 ①厂家总/单品指标+返利 ②库存）→ 文员执行（查厂家余额、群通知付款差额、厂家系统确认到账并下单）→ 到货前 Hermes 生成**舟谱导入模板**手动导入+通知打印。每 2 天到货、提前 4 天下单，报单主要依赖员工经验。
- 用户问：做成**微信小程序**可不可行？
- 我的结论：技术上可行，但须摆正边界——**小程序接管"中间段"**（多角色填报 + 汇总校验 + 智能审核台[指标达成率+库存可销天数→建议订单] + 审批流转/通知 + 一键生成厂家粘贴模板/舟谱导入模板），**接管不了"最后一步"**：厂家系统（查余额/确认到账/下单）与舟谱均无开放 API，必须人工（模板生成仅辅助搬运）。最大价值 = 把"审核全靠经验"变成"系统算+人确认"，正好是可卖给其他低温奶/快消经销商的第一个真模块（同痛点：预报订单+厂家指标返利+库存）。
- 关键决策点（待用户定）：①选型——分销商是外部，微信小程序比企业微信智能表格更顺；若四类人都在企微内、可只补"智能审核引擎"不换前端。②范围——先 MVP（填报+智能审核台+模板生成）自用验证，再谈卖。
- 下一步：等用户确认选型/范围后，细化 MVP 方案或出高保真原型。

## ✅ 预报订单 智能审核引擎 上线（2026-08-12，生产验证通过）
- **新增** `server/routers/forecast_audit.py`（v1 原型）：复用当前租户库(products/sale_orders/sale_order_items/inventory/rebate_contracts)，所有算法内联在 router（若形成范式再下沉 erp_db）。`APIRouter(prefix="/api/forecast-audit")`。

- **算法**：`avg_daily_sales = SUM(sale_order_items.qty)/days`；`suggested_qty = max(0, round(avg*coverage_days + safety_stock - current_stock))`，`coverage_days = lead_time + arrival_cycle`。**窗口锚定到 `MAX(order_date)` 而非 `now`**（真实数据停在 ~2026-06-15，约 58 天前，硬用 now 匹配不到）。
- 端点：`GET /products`(搜索+avg+库存)、`POST /compute`(items→suggested_qty+verdict)、`GET /rebate-summary`(graceful degrade 无数据返回 null)、`POST /save`、`GET /orders`。
- **server.py 改 3 处**：`_PATH_MODULE_MAP` 加 `"/api/forecast-audit":"stock"`（否则 RBAC fail-closed 403 MODULE_NOT_CONFIGURED）；`import forecast_audit_router`；`app.include_router(forecast_audit_router)`。
- **生产 E2E 验证**：商品1523 现代牧场鲜牛奶百利包 → avg=370.8、库存=1914、可销天数=5.2、safety=2595、lead=7、coverage=9、required=5932、**suggested_qty=4018**、verdict「低于系统建议 4018（约 10.8 天销量）可能缺货」；`COMPUTE(按建议量)`→「与系统建议基本吻合」；`SAVE`→`{'success':True,'ids':[6],'count':1}`。测试数据已清理。

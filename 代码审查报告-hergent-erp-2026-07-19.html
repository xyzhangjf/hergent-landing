核心判断

Hergent ERP 的业务功能深度已达到中端 ERP 水平（财务 IFRS 15、多 GAAP、税务引擎、WMS、CRM、AI 能力）， 但工程质量和安全防护严重滞后于功能增长。v83→v89 期间模块数翻倍，但前端无构建工具、无 TypeScript、无 ESLint、无前端测试， 后端上帝文件持续膨胀（erp_db.py 从 6,700 行增长到 10,368 行），安全方面存在多个可直接利用的漏洞。

建议立即进入"工程质量回补"阶段——暂停新功能开发，集中清除 P0/P1 级问题，建立工程化基线后再恢复功能迭代。

P0 — CRITICAL（安全漏洞 / 崩溃风险）14 项

这些问题可被直接利用导致数据泄露、身份伪造或系统被接管，必须在 24-48 小时内修复。

P0-1 未认证数据库下载 — 任何人可下载完整数据库
后端安全
文件：server/routers/platform.py:138-143

/api/backup/download 端点没有任何认证调用（无 _auth()、无 _admin()），同时路径在 _PUBLIC_PATHS 白名单中绕过了 RBAC 中间件。

curl https://erp.hergent.cn/api/backup/download -o stolen.db
sqlite3 stolen.db "SELECT username, password_hash FROM users"
立即添加 _admin(request) 认证，并从 _PUBLIC_PATHS 中移除 /api/backup。
P0-2 SAML 断言签名未验证 — 可伪造任意用户身份登录
后端安全
文件：server/routers/sso.py:292-369

SAML ACS 端点用正则表达式提取 NameID，但从不验证 XML 签名。攻击者可构造未签名的 SAML Response 声称是任意邮箱用户，直接获得该用户会话。

使用 xmlsec 或 python3-saml 库验证签名。在验证通过前不得提取任何身份信息。无法引入签名验证则禁用 SAML ACS 端点。

P0-5 esc() 转义不完整 — 全项目级 XSS 根因
前端安全
文件：static/js/core/utils.js:2 及 25 个重复定义

esc() 只转义 & < > 三个字符，未转义双引号和单引号。当返回值放入 HTML 属性上下文时，攻击者可通过引号逃逸注入任意事件处理器。

function esc(s){return String(s).replace(/&/g,"&").replace(//g,">")}

// 属性上下文中使用：
html += '<input data-name="'+esc(p.name)+'">'
// 若 p.name = '" onmouseover="alert(1)'，esc 不转义引号 → XSS

同一项目存在 25 处重复定义，实现分为三派（转义引号/不转义引号/只转义&<），开发者无法判断当前文件的 esc() 是否安全。

统一 esc() 实现到 utils.js，必须转义 & < > " ' 五个字符，删除所有重复定义。区分 escapeHtml()（文本上下文）和 escapeAttr()（属性上下文）。
P0-6 document.write 写入未转义的服务端内容
前端安全
文件：static/js/modules/ai-assistant/forecast.js:189、static/app.js:3043

服务端返回的 HTML 被直接 document.write 到新窗口，完全信任服务端数据。若预报订单中包含用户输入字段且服务端未严格转义，将导致 XSS。新窗口脚本可访问 opener 影响主应用。

使用 DOMParser 或 iframe srcdoc 替代 document.write，对内容进行 HTML 转义。
P0-7 onclick 拼接函数体字符串 — 代码注入
前端安全
文件：static/app.js:3065, 3226, 3261

右键菜单、最近操作、最近访问中，将函数调用字符串直接拼接到 onclick 属性。值来自表格单元格文本，若包含引号可逃逸字符串字面量注入代码。

_ctxMenu.innerHTML = actions.map(function(a){
  return '<div onclick="('+a.a+')();...">'+a.l+'</div>'
}).join("")
改用 addEventListener + dataset，或对值进行 JS 字符串转义。彻底消除内联 onclick。
P0-8 contacts-v2.js 联系人渲染完全未转义
前端安全
文件：static/js/modules/contacts-v2.js:33-44

c.name、c.role、c.phone、c.channel 直接拼接进 innerHTML，无任何 HTML 转义。c.id 在 onclick 中仅用 escapeJs（只转义单引号），不转义 HTML 字符。

对所有用户数据字段调用统一的 esc() 函数进行 HTML 转义。
P0-9 8 处 **d 参数注入 — 请求体直接展开为函数参数
后端安全
文件：server/routers/ 多处

多个路由端点将 await request.json() 的结果用 **d 直接展开为数据库函数参数，攻击者可注入非预期参数名覆盖默认值或触发意外行为。

d = await request.json()
result = db.some_function(**d)  # d 中的任意 key 都会成为函数参数
显式提取参数：db.some_function(name=d.get("name"), qty=d.get("qty"))，禁止 **d 展开。
P0-10 3 处 SQL 注入风险
后端安全
文件：server/erp_db.py — get_expiring_soon, employee_list, get_churn_risk

三处函数使用 f-string 或字符串拼接构建 SQL，将用户可控参数直接嵌入查询语句。

全部改为参数化查询：cursor.execute("SELECT ... WHERE col=?", (value,))。
P0-11 密码策略逻辑 bug — 纯数字或纯字母可通过
后端安全
文件：server/core.py:43-49
def _validate_password(pw):
    if not pw or len(pw) < 8:
        return False, "密码至少需要8位"
    if not (any(c.isdigit() for c in pw) or any(c.isalpha() for c in pw)):
        #         ^^^^ or ^^^^ — 应该是 and！
        return False, "密码需要包含至少一个数字或字母"

使用 or 意味着 aaaaaaaa 或 12345678 都能通过验证。

改为 and，并增强策略：至少 10 位，必须同时包含大小写字母和数字，检查常见弱密码字典。
P0-12 _safeExec 仍存在动态求值风险
前端安全
文件：static/app.js:5-12

注释声称"replaces eval()"，但 JSON.parse('['+m[2]+']') 本质上仍是对用户输入的动态求值。白名单机制不完善，若 fn 是危险函数（如 window.open），可构造 open('javascript:alert(1)') 类调用。

建立严格的函数白名单 + 参数类型校验，或改用事件委托 + dataset 完全消除动态函数调用。
P0-13 renderTasks / AI 洞察中部分字段未转义
前端安全
文件：static/app.js:6067, 1112, 342

t.freq、t.run_time、n.msg、p.name（来自 API）等字段在 innerHTML 拼接中完全未转义。

所有 innerHTML 拼接中的动态数据必须经过 esc() 转义，无一例外。
P0-14 静态文件服务路径遍历
后端安全
文件：server/server.py:2457-2460

path 直接来自 URL，未经清洗就与 STATIC 拼接。攻击者可使用 ../ 或 URL 编码的 %2e%2e%2f 遍历到服务器任意文件。

使用 os.path.normpath + startswith 校验路径在 STATIC 目录内。

P1 — HIGH（严重质量问题）15 项

这些问题严重影响可维护性、安全防护深度和系统稳定性，建议在本周内修复。

P1-1 120+ 处裸 except: pass 静默吞异常
后端质量
文件：server/erp_db.py 及全后端

核心业务逻辑中大量使用 except: pass 或 except Exception: pass，异常被完全静默。这导致：数据库操作失败无人知晓、事务可能在不一致状态下提交、问题排查极其困难。

至少改为 except Exception as e: logging.getLogger("hergent").warning(f"...: {e}")。对关键路径（财务、库存）的异常应向上传播而非吞没。
P1-2 erp_db.py 10,368 行上帝文件
后端架构
文件：server/erp_db.py

单一文件包含几乎所有数据库操作（用户、商品、订单、库存、财务、CRM、HR...）。v83→v89 从 6,700 行增长到 10,368 行，持续膨胀。任何修改都有 side effect 风险，无法独立测试，多人协作冲突严重。

db/queries/ 目录已有 11 个按领域拆分的文件，继续推进迁移。目标：erp_db.py 仅保留 init/migrate，业务逻辑全部移入 db/queries/{domain}.py。
P1-3 app.js 7,466 行上帝文件
前端架构
文件：static/app.js

单一文件包含登录认证、API 封装、离线队列、路由导航、所有业务页面渲染、表单处理、右键菜单、打印、剪贴板等数十个职责。60+ 处 window.xxx 全局变量赋值。

按业务域拆分（auth、sales、stock、reports 等），逐步迁移到 js/modules/。全局变量迁移到已有的 HergentStore。
P1-4 4 种 API 调用模式并存
前端质量
文件：全前端模块

存在 4 种 API 调用模式：window.api()、ApiClient.get/post、直接 fetch()、模块自定义 _api()/A(p,o)。token 读取逻辑重复 30+ 次，错误处理不一致，401 处理不统一。api-client.js 虽然是规范实现但注释自述"Legacy bridge"，实际使用率低。

强制所有模块使用 ApiClient，删除所有 apiGet/apiPost/A(p,o)/_api 重复封装。
P1-5 未设置 Content-Security-Policy
后端安全
文件：server/server.py:158-167

服务器设置了 6 个安全响应头（X-Content-Type-Options、X-Frame-Options、HSTS 等），但完全没有 CSP。XSS 攻击没有第二道防线。

先以 Content-Security-Policy-Report-Only 模式收集违规，逐步收紧到 default-src 'self'; script-src 'self'。需配合消除内联 script/onclick。
P1-6 会话 token 生成方式不一致
后端安全
文件：auth.py:185, mfa.py:205, sso.py:182,356

正常登录用 secrets.token_urlsafe(32)（256 位），但注册、MFA、OAuth、SAML 登录用 uuid.uuid4()（仅 122 位有效熵），且格式可被识别为 UUID。

统一使用 secrets.token_urlsafe(32) 生成所有会话 token。
P1-7 Dockerfile 默认密钥可预测
后端安全
文件：Dockerfile:18

ENV ERP_SECRET=change-me-in-production — 若直接 docker run 不覆盖环境变量，密码哈希加盐和 PII 加密密钥将使用硬编码弱默认值。

从 Dockerfile 中移除该行，让应用在缺少密钥时直接拒绝启动（core.py:11-12 已有此逻辑）。
P1-8 微信 OAuth 密钥在 URL 查询参数中

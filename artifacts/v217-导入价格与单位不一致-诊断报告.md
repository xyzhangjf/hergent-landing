## 一、结论先行

|---|---|---|---|
| 1 | 模版价格 99 → 系统 990 | **是缺陷，你的判断正确** | **导入没有公式、也没放大**。放大发生在**页面的一列计算**上：主表「单价(厂价/箱)」= **厂价 × 规格**。而厂价本来就是「元/箱」，再乘一次规格 ⇒ 大了 **10 倍**（规格 = 10） |

### ⑤ 厂价到底是「元/箱」还是「元/桶」—— 数学上唯一解

这是判定的关键。三条独立证据全部指向 **厂价 = 元/箱**：

**(a) 后端「本期需付款」的口径**（`routers/forecast.py:489`）：

```python
order_amount += qty * fp      # qty = final_qty（定稿量，单位=箱）；fp = 厂价
```
⇒ 后端的式子是「**箱数 × 厂价**」，说明后端认为厂价是「元/箱」。**若厂价是元/桶，这个乘式没有意义。**

**(b) 分销价与厂价的比值 = 规格 × 0.9（7 个商品全中，无一例外）**：

| 商品 | 规格 | 厂价 | 分销价 | 厂价 ÷ 分销价 | 规格 × 0.9 |
|---|---|---|---|---|---|
| 1475 红枣1000g*10桶 | 10 | 99 | 11.0 | **9.0** | 9.0 ✓ |
| 1495 原味桶1100g*10桶 | 10 | 110 | 12.2222 | **9.0** | 9.0 ✓ |
| 1477 圆周杯100g*8*12组 | 12 | 94.8 | 8.7778 | **10.8** | 10.8 ✓ |
| 1250 简爱400g*12杯 | 12 | 108.86 | 10.0833 | **10.8** | 10.8 ✓ |
| 1476 圆周杯100g*16杯*6组 | 6 | 94.8 | 17.5556 | **5.4** | 5.4 ✓ |
| 1539 160红枣5连杯 | 8 | 62 | 8.6111 | **7.2** | 7.2 ✓ |
| 1494 预制瓶450g*15瓶 | 15 | 75 | 5.5556 | **13.5** | 13.5 ✓ |

⇒ `分销价 = 厂价 ÷ 规格 ÷ 0.9`。含义非常清楚：
**厂价按「箱」计、分销价按「最小销售单位」计，中间是统一的 11.11% 加价（÷0.9）**。
若厂价按「桶」计，则 99 元/桶 vs 分销价 11 元/桶 = **卖一瓶亏 88 元**，业务上不可能。

**(c) 业务常识**：1000g 低温酸牛奶桶，批发 9.9 元/桶（= 99 元/箱）合理；99 元/桶 = 零售价水平。

### ⑥ 同族缺陷：明细行的金额也是同一个错

`routers/import_router.py:782`：

```python
"price":  pr["price"],                      # = 厂价（元/箱）
"amount": round(qty * pr["price"], 2),      # qty = 数量（桶）⇒ 桶 × 元/箱 = 错的
```

实测落库行（`forecast_submission_items` id=44）：

```
product_id=1475  红桶（福宝下单）  unit=桶  quantity=10  price=99.0  amount=990.0
```

10 桶 = 1 箱，应付应为 **99 元**，系统记 **990 元**。⇒ **同一个「厂价按小单位乘」的错，在导入层又犯了一次。**

## 三、单位：完整证据链

### ① 单位有两个来源，导入只补空

- **明细行**（`forecast_submission_items.unit`）= 模版里那一格 → 实测 `160红枣5连杯` 的明细 **unit = '条'** ✓ 你填的进去了。
- **商品档案**（`products.unit`）= 舟谱导进来的老值 = **'件'**（该商品 2026-07-28 建档，早于任何一次导入）。
- 导入对已有档案走 `product_backfill_from_import`，其规则是 **「只补库内为空的字段，绝不覆盖」**：

```python
for k, v in (("spec", spec), ("unit", unit), ("brand", brand), ("factory_price", ...)):
    if cur[k] in (None, "", 0, 0.0):
        patch[k] = v      # 库内为空才补；'件' 非空 ⇒ 不补
```

⇒ **单位「条」被静默丢弃**，档案保持「件」，**回执只写「复用 N 个」，一个字都不提**。

### ② 主表显示取的是**档案**那一份

`erp_db.py` 的 `forecast_submission_summary`：

```sql
COALESCE(NULLIF((SELECT unit FROM products WHERE id=i.product_id),''), i.unit) AS unit
```

⇒ **档案优先、明细兜底** ⇒ 你看到「件」。而系统里另一处（`routers/forecast.py:634` 生成舟谱单据）用的是 **`明细单位`**：

> `# 单位来自提交明细（导入下单表时已落库），缺失按名称关键词推断兜底。`

⇒ **同一条业务数据，主表说「件」、发去舟谱的下单文件说「条」**。这是真正的病灶：一个列位承担了两个概念（**档案基本单位** vs **报单单位**）。

### ③ 影响面量化（实测，不夸大）

| 项 | 数量 |
|---|---|
| 明细单位 ≠ 档案单位的**明细行** | **114 行**（包→件 45、组→件 39、条→件 19、板→件 10、提→件 1 等） |
| 其中**规格是纯数字**（如 `10` / `8` / `12`）的行 | **109 行** ⇒ 对箱数换算**无影响**（纯数字规格下，单位不参与计算） |
| 其中**规格是描述串**（如 `100g*8杯*12组`）的行 | **5 行** ⇒ 这些会**实际改变箱数**（例：`90g*16杯*6组（单杯）` 按「杯」= 96、按「件」= 6，差 16 倍） |

⇒ **单位问题当前主要是"口径/显示"问题**（你填条、系统显示件、舟谱文件又是条），**不是大面积算错箱数**；但存在会算错的小尾巴（5 行）。

## 六、修复建议

### P0-1（价格，3 行改动，零迁移）

`Forecast.vue` `priceAuto()`：**去掉 `× perCase`** —— 厂价本身就是「元/箱」：

```js
function priceAuto(r) {
  const fp = factoryPrice(r)
  if (fp <= 0) return null
  return Math.round(fp * 100) / 100      // 厂价已是元/箱；不再乘规格
}
```
连带把列名/提示文案里的「厂价(元/件) × 规格」改成「厂价(元/箱)」，并让 `priceTitle` 的自证文案同步。
**风险**：所有期次金额同比下降规格倍 —— 这是**纠错**，不是回归。需在期次 15 上先只读比对本期合计。

### P0-2（导入明细金额，同族缺陷）

`import_router.py:782`：金额必须用**箱口径**，或干脆改用**分销价（元/小单位）**：

```python
# 方案甲：箱口径（与后端「本期需付款」同源）
"amount": round((qty / per_case) * pr["price"], 2)     # per_case 需后端也可用
# 方案乙：小单位口径（与舟谱「单价(折后价)」同源，用分销价）
"amount": round(qty * (dist_row or 0), 2)
```
⇒ **建议先决定「明细金额要表达哪一件事」**（厂家结算额 / 门店应收额），再改；两者是不同的量，别再混用一个字段。

### P1（单位）两种做法，建议先做 B1

- **B1（零风险，先做）**：**把静默变响**。导入回执里点名「以下 N 个商品的**单位/规格/厂价**与档案不一致，已保留档案值（不覆盖）」，并给出改哪里（商品档案）。这治的是**"我以为按模版复制了，其实一项没生效"**这个真正的病根，不动任何计算。
- **B2（口径对齐，需验收）**：主表 `_master_unit` 改成**明细优先**（`COALESCE(NULLIF(i.unit,''), 档案)`），与舟谱单据同源。**必须先量化**：仓库里 96 组里 29 组两处不同；翻转后那 5 行描述串规格的箱数会变（多数是**变对**，但必须逐条核）。
- **B3（治本，长期）**：给 `products` 增加 `order_unit`（报单单位）列，把「档案基本单位」与「报单单位」**拆成两列**。`perCase(spec, unit)` 与舟谱单据都读 `order_unit`，主表就能同时正确显示两者。

2. 用真实商品行喂**切出来的真实函数**（本次已建好范式：`.workbuddy/tools/v217-price-realcode.mjs`）；

## 一、一句话结论

**P0 的「新代码」只有两样：8 个前端页面 + 一层 `/api/psi/*` 薄壳。
底下所有业务逻辑、表结构、事务、批次与效期算法，**全部复用现成实现，一行不改**。**

关键点：**不能**让进销存页面直接调既有端点（`/api/purchase-orders` 等）——
那些端点归属 `buying` / `sales` / `stock` 三个模块，**司机、导购、会计、主管都持有**，
直接复用等于把「只有 boss 能看」的闸门当场作废（§三 有实测证据）。

## 三 🔴 核心决策一：为什么不直接复用既有端点

实测 `core.py::_DEFAULT_PERMS`（AST 精确解析，非目测）：

| 角色 | 总模块数 | 持有 `buying` | `sales` | `stock` | `data` | **`inventory`** |
|---|---|---|---|---|---|---|
| admin | 1（`["*"]`） | ✅ | ✅ | ✅ | ✅ | ✅ |
| **boss** | 21 | ✅ | ✅ | ✅ | ✅ | ✅ |
| accountant | 8 | ✖ | ✅ | ✅ | ✅ | ✖ |
| sales | 7 | ✅ | ✅ | ✅ | ✅ | ✖ |
| guide | 7 | ✅ | ✅ | ✅ | ✅ | ✖ |
| supervisor | 8 | ✖ | ✅ | ✅ | ✅ | ✖ |
| driver | 3 | ✖ | ✖ | ✅ | ✖ | ✖ |
| staff | 4 | ✖ | ✖ | ✅ | ✅ | ✖ |
| distributor | 2 | ✖ | ✖ | ✖ | ✅ | ✖ |

**如果把 P0 页面的数据直接打到既有端点：**

| 若调 | 归属模块 | 谁就跟着能进 |
|---|---|---|
| `/api/purchase-orders` | `buying` | 业务员、导购 |
| `/api/sale-orders` | `sales` | 会计、业务员、导购、主管 |
| `/api/inventory`、`/api/warehouses` | `stock` | 会计、业务员、导购、**司机**、员工、主管 |

⇒ 🔴 **「只有 boss 看得到」当场失效**，v380 闸门白建。

**唯一正确的做法（本方案采用）：**

```
前端 P0 页面
   │  只调 /api/psi/*          ← module = inventory（仅 boss/admin 持有）
   ▼
/api/psi/*（新薄壳，routers/psi.py）
   │  内部 ~40 行/端点，直接调既有函数
   ▼
db/queries/purchases.py · sales.py · inventory.py   ← 一行不改
```

**收益**：逻辑复用 100%（含信用额度校验、促销自动应用、FEFO 扣减、批次留痕），
门禁单独成轴（`inventory`），**两者不互相污染**。

> ⚠️ 这与「模块拆分」是同一招的镜像用法：v296 拆 `cron`/`bid`、v332 拆 `forecast-audit`、
> v349 拆 `loss` 都是「把接口从粗模块里拆出来」；
> 本次是**反向**——把同一批接口**再挂一个只给 boss 的前缀**，既有前缀（`buying`/`sales`/`stock`）**原样保留**，
> 旧前端与老流程零影响。

## 四 🔴 核心决策二：为什么不复用既有**页面**

| 候选 | 能否直接用 | 原因 |
|---|---|---|
| 新前端 `hergent-cn-v2` 现有页面 | ✖ | 30 个页面里**没有任何采购/销售页**（唯一 `Inventory.vue` 是 v380 占位页） |
| 旧前端 `erp.hergent.cn`（105 模块） | ✖ | ① 技术栈不同（字符串拼 `innerHTML` vs Vue 声明式，见 `erp旧前端功能迁移评估-2026-10-06.md`）；② **旧前端自带完整侧栏，任何能打开旧地址的人都看得到进销存 ⇒ 会直接捅穿 `inventory` 闸门** |
| 既有 `/archive` 档案页 | ✅ **直接复用** | 商品/客户/仓库/员工/渠道价 6 个页签全在，字段已覆盖（`ProductArchive.vue` 实测含条码、单位、中单位/大包装换算、品牌、进价） |

⇒ **P0 的「基础档案」不新建页面，直接深链到既有 `/archive/*`。**
既省 1 页，也避免「同一个商品档案有两处维护」的经典分叉。

## 五、页面拆分总表（P0 = 8 个页面）

| # | 页面 | 路由 | 类型 | 有「创建」入口 | 复用后端 |
|---|---|---|---|---|---|
| 1 | 进销存工作台 | `/inventory` | 总览（只读） | — | 聚合 4 个读函数 |
| 2 | 采购进货 · 列表 | `/inventory/purchase` | 列表 | ✅（双入口） | `purchase_order_list` |
| 3 | 采购进货 · 新建 | `/inventory/purchase/new` | ⭐ 独立创建页 | — | `purchase_order_create` |
| 4 | 采购进货 · 详情 | `/inventory/purchase/:id` | 详情（可确认/到货） | — | `purchase_order_get` + `confirm` |
| 5 | 销售出货 · 列表 | `/inventory/sale` | 列表 | ✅（双入口） | `sale_order_list` |
| 6 | 销售出货 · 新建 | `/inventory/sale/new` | ⭐ 独立创建页 | — | `sale_order_create` |
| 7 | 销售出货 · 详情 | `/inventory/sale/:id` | 详情（可发货/签收） | — | `sale_order_get` + `deliver`/`sign` |
| 8 | 库存查询 | `/inventory/stock` | 纯查询 | ❌ 无（按 v4 实测：纯查询不配创建） | `inventory_query` + `get_expiry_alerts` |

**导航形态**：进销存**独立成侧栏职能区**，P0 平铺 **4 项**
（`进销存工作台` · `采购进货` · `销售出货` · `库存查询`）——
**列表 / 新建 / 详情是页内路由，不进侧栏**。对齐 v4「进销存区子项全部一级直达、不做折叠」。

## 六、逐页设计

### 页 1 · 进销存工作台（`/inventory`）

**职责**：一眼看清「今天进了什么、出了什么、还剩多少、哪天要坏」。
**改造**：v380 的占位页 `Inventory.vue` **就地升级为本页**（保留其 `/api/psi/meta` 自检卡片，挪到底部折叠区）。

| 区块 | 内容 | 数据来源（复用） |
|---|---|---|
| KPI ① | 库存总额（按成本价，万元） | `inventory_query` 聚合 Σ`quantity × cost_price` |
| KPI ② | 今日进货（金额 + 单数） | `purchase_order_list(date_from=date_to=今天)` |
| KPI ③ | 今日出货（金额 + 单数） | `sale_order_list(date_from=date_to=今天)` |
| KPI ④ | **临期 7 天**（条数，🔴 红色，点击直达清单） | `get_expiry_alerts(days=7)` |
| 趋势 | 近 7 天进货 / 出货小柱状图 | 上面两个 list 按日归并 |
| 待办 | 待确认采购单 / 待发货销售单 | `*_list(status='draft'/'confirmed')` |

**空态**：全部为 0 时显示「还没有单据 → [新建采购单] [新建销售单]」，而不是一排 0。

### 页 2 / 5 · 列表页（`/inventory/purchase` · `/inventory/sale`）

**共用骨架**（一个组件传 `kind='purchase'|'sale'` 参数化，同 `Forecast.vue` 的配置化先例）：

| 区域 | 采购 | 销售 |
|---|---|---|
| 筛选 | 单号 / 供应商 / 日期区间 / 状态 | 单号 / 客户 / 日期区间 / 状态 / **出货方式** |
| 列 | 单号 · 日期 · 供应商 · 仓库 · 金额 · 状态 · 操作 | 单号 · 日期 · 客户 · 仓库 · 金额 · 收款 · 状态 · 操作 |
| 右上 | **「＋ 新建采购单」**（双入口的右侧落点） | **「＋ 新建销售单」** |
| 行操作 | 详情 / 确认 | 详情 / 发货 / 签收 |

**状态文案**（必须中文化，按 `status` 列枚举值逐条映射）：
- 采购：`draft` 草稿 · `pending_approval` 待审核 · `confirmed` 已确认 · `received` 已入库 · `partial` 部分到货 · `returned` 已退货 · `cancelled` 已作废
- 销售：`draft` 草稿 · `confirmed` 已确认 · `delivered` 已发货 · `signed` 已签收 · `rejected` 已驳回 · `returned` 已退货 · `cancelled` 已作废

> ⚠️ **不许把英文枚举直接显示给用户**（用户明确要求 UI 不出现英文缩写）。

### 页 3 / 6 · ⭐ 独立创建页（`/inventory/purchase/new` · `/inventory/sale/new`）

**这是 §5.4 那条约束的落点**：舟谱的「创建」之所以能挂，是因为**创建是一个独立路由**。
P0 照做，**不用弹窗表单**。

| 区块 | 采购字段 | 销售字段 |
|---|---|---|
| 表头 | 单号（自动，只读）· 日期 · **供应商**（下拉，`contacts.type in (supplier,both)`）· 仓库 | 单号（自动）· 日期 · **客户**（下拉，`type in (customer,both)`）· 仓库 · **出货方式**（车销 / 访销 / 自提 → `order_type` + `self_pickup`） |
| 明细行 | 商品 · **单位** · 数量 · 单价 · **批次号** · **到期日** · 小计 | 商品 · **单位** · 数量 · 单价 · 小计（出货批次由 FEFO 自动分配） |
| 金额 | 合计（自动） | 合计 · 折扣 · 应收（自动） |
| 其他 | 备注 | 备注 · 司机（车销时出现） |
| 底部 | **[存为草稿]** **[保存并确认]** | **[存为草稿]** **[保存并确认]** |

**三个必须写进代码的细节**：

1. 🔴 **批次号 + 到期日在采购侧是必填**（原型里已红字标注）——
   低温奶的效期全靠入库这一刻登记，晚了就永远算不准。销售侧**不填**（由 `fefo_deduct` 按先进先出发货）。
2. 🔴 **单位真身是 `products.order_unit`，不是明细里的自由文本** —— 落库前必须按档案单位取，
   **永不落大单位**（报单单位铁律）。跨单位填写要带换算，算不出就退回明细行并告警。
3. **信用额度校验交给后端**（`sale_order_create` 内已实现），前端**不重复实现一遍**——
   重复实现就是「同一个规则两份代码」，必然漂移（本项目的老病）。

### 页 4 / 7 · 详情页（`/inventory/purchase/:id` · `/inventory/sale/:id`）

只读展示表头 + 明细 + 状态时间线；按状态给出可用动作按钮：

| 采购单状态 | 可用动作 |
|---|---|
| 草稿 | 编辑 · 确认 |
| 已确认 | **到货入库**（→ 逐行填批次号 + 到期日 → 调 `batch_in`） |
| 已入库 / 部分到货 | 部分到货补录 |

| 销售单状态 | 可用动作 |
|---|---|
| 草稿 | 编辑 · 确认 |
| 已确认 | **发货**（→ `fefo_deduct` 扣减） |
| 已发货 | **签收** |

> 🔴 **按钮必须判 `canDo('inventory','create')`**，不能只判 `canSee` —— 否则只读角色会看到一个点了 403 的按钮（比不显示更糟）。

### 页 8 · 库存查询（`/inventory/stock`）

| 区域 | 内容 |
|---|---|
| 筛选 | 商品（名称/条码）· 品牌 · 仓库 · **效期 ≤ N 天** |
| 列 | 商品 · 仓库 · **批次号** · **到期日** · 剩余数量 · **剩余天数** · 状态（正常 / 临期 / 已过期） |
| 排序 | 默认按到期日升序（最早到期在最上面）—— 这才是每天要看的顺序 |
| 操作 | 导出（复用既有导出管线；**不新增工具栏按钮**，并入现有导出下拉） |
| 创建入口 | ❌ **无**（纯查询，对齐舟谱实测判据） |

## 七、前端路由（`src/router/index.js`）

```js
// 进销存 P0 —— 全部挂在既有 Layout children 下，与 /archive 同形态
{ path: 'inventory',                component: PsiWorkbench,     meta: { title: '进销存' } },
{ path: 'inventory/purchase',       component: PsiPurchaseList,  meta: { title: '采购进货' } },
{ path: 'inventory/purchase/new',   component: PsiPurchaseCreate,meta: { title: '新建采购单' } },
{ path: 'inventory/purchase/:id',   component: PsiPurchaseDetail,meta: { title: '采购单详情' } },
{ path: 'inventory/sale',           component: PsiSaleList,      meta: { title: '销售出货' } },
{ path: 'inventory/sale/new',       component: PsiSaleCreate,    meta: { title: '新建销售单' } },
{ path: 'inventory/sale/:id',       component: PsiSaleDetail,    meta: { title: '销售单详情' } },
{ path: 'inventory/stock',          component: PsiStockQuery,    meta: { title: '库存查询' } }
```

**两点说明（避免踩错机制）**：

1. **`new` 与 `:id` 的顺序**：vue-router 4 按**静态段优先**排序，`/inventory/purchase/new` 不会被 `:id` 吞掉。
   ⚠️ 这与后端 `_PATH_MODULE_MAP` 的「**首个 startswith 命中即停**」是**两套完全不同的机制**，
   不要把后端那种「顺序写反就静默失效」的经验错搬到路由上（反之亦然）。仍建议按上表顺序声明，便于人读。
2. **子路由权限靠继承**：`pages.js::ruleFor` 是「精确匹配 → 逐级去掉尾段再匹配」，
   所以 8 条路由**全部自动继承** `/inventory` 那一行（`module:'inventory'` + `roles:ADMIN_ROLES` + `lock:true`）
   ⇒ **`pages.js` 不需要新增任何行**，深链由守卫按同一份表拦住。
   ⚠️ 但**路由本身必须在 children 里登记**，否则父级只解析到 `/inventory` 这一段、多出的段会落 404。

## 八、后端接口契约（扩展 `server/routers/psi.py`）

| GET | `/api/psi/stock` | `inventory_query` | 筛选透传 |
| GET | `/api/psi/stock/expiring` | `get_expiry_alerts` | `?days=7` |
| GET | `/api/psi/stock/summary` | `inventory_query` 聚合 + 两个 list | 工作台 4 个 KPI 一次取回 |

**薄壳纪律（三条，写进文件头注释）**：
1. **不复制业务规则** —— 信用额度、促销、FEFO、批次留痕一律用既有函数的结果；薄壳里出现第二个实现就是缺陷。
2. **不新增表、不改既有表**。
3. **失败必须显式** —— 既有函数返回 0/空时，要区分「真没有」与「参数没传对」；
   恒 0 且零报错是静默失效的典型形态。

> ⚠️ 一处**需在实现时实测确认**（不写死假设）：建单页的档案下拉**也可以**直接调既有
> `/api/products`、`/api/contacts`、`/api/warehouses` —— 因为能打开本页的只有 boss，
> 而 boss 持有 `data`+`stock`，不构成越权。
> 但那样会让「进销存的门禁」多三个不等于 `inventory` 的依赖 ⇒
> **推荐仍走 `/api/psi/refs`**（门禁自洽 + 少 3 次往返）。两种都可行，实现时按一次真实测速定。

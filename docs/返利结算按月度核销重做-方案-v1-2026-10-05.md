## 一、结论先行

**这不是"改界面"，是换主体。** 现行模型把「年度合同」当结算主体，而你的真实业务主体是**「月度核销批次」**（每月提交上月的核销资料 → 本月上账）。

**三个决定性前提（已实测，只读）**：

| 前提 | 读数 | 含义 |
|---|---|---|
| 结算链路的生产数据 | `rebate_contracts` / `rebate_contract_months` / `rebate_accruals` / `rebate_claims` **全部 0 行** | **零迁移负担** —— 可以新老并存，不需停机、不需搬数据 |
| 真数据只有三张 | `rebate_target_rules` **3 行**（`contract_id` 全 **0**）、`rebate_achievements` **4 行**、`rebate_rule_month_lock` **16 行** | 要保的只有"目标规则 + 达成填报" |
| 凭证能力已有 | `attachments` 表 + `POST /api/attachments`（`ref_type`/`ref_id`/`filename`/`data_b64`）+ 列表/下载/删除；`/api/upload` 已归 `sales` | **#5③ 不用新造附件系统**，直接复用 |

🔴 **这个窗口会关闭**：一旦开始真的用（合同/计提落数据），重构成本立刻上升。现在是**最省的一次**。

## 二、病根：四处结构性错位

你上一轮的口径原话：「结算是以月为单位，本月提交上月核销资料，本月上账，不同厂家不一样，但大部分如此。」

现行实现与这句话的差距：

| # | 真实业务 | 现状 | 病灶 |
|---|---|---|---|
| 1 | 主体 = **月度核销批次** | 主体 = `rebate_contracts`（**年度**合同） | `accrue_rebate()` 以 `contract_id` 为必填外键；`settle_rebate(contract_id)` **一次结一整年** |
| 2 | 核销月 ≠ 上账月（差约 1 月） | `rebate_accruals` 只有**一个** `month`（=达成月） | 缺"提交月/上账月"两个时点；"本月该提交哪个月的资料"无法表达 |
| 3 | 「提交上月核销资料」是**对厂家的动作**，要凭证 | `rebate_claims` 是**内部审批**（submitted→approved），**无凭证概念** | 两件事被混成一个状态机 |
| 4 | 年度合同常只是"一张纸/一个框架" | 年度合同是**必须项**，还是目标录入口 | `rebate_contract_months` 与 `rebate_target_rules.monthly_amounts` **两套年度目标**（2026-09-06 已拍板"同一数据源"，但没落地） |

## 三、目标模型

### 3.1 新表 `rebate_settlements`（月度结算批次）—— 一级对象

```sql
CREATE TABLE IF NOT EXISTS rebate_settlements (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  brand_key      TEXT DEFAULT '' COLLATE NOCASE,   -- 厂家（与 rebate_target_rules.scope_key 同源）
  brand_name     TEXT DEFAULT '',
  settle_month   TEXT NOT NULL,                    -- ① 核销月（业务归属，如 2026-09）
  submit_due     TEXT DEFAULT '',                  -- ② 应交核销资料日（节奏派生，如 2026-10-05）
  post_due       TEXT DEFAULT '',                  -- ③ 应上账日（节奏派生，如 2026-10-20）
  submit_offset  INTEGER DEFAULT 1,                -- 落库时冻结节奏快照（防日后改配置篡改历史）
  post_offset    INTEGER DEFAULT 0,
  status         TEXT NOT NULL DEFAULT 'draft',    -- draft/submitted/confirmed/posted/reversed
  achieved_amount REAL DEFAULT 0,                  -- 厂家确认的达成
  rebate_amount  REAL DEFAULT 0,                   -- 厂家确认的返利
  submitted_at   TEXT DEFAULT '',
  confirmed_at   TEXT DEFAULT '',
  posted_at      TEXT DEFAULT '',
  doc_count      INTEGER DEFAULT 0,                -- 凭证数（真实文件在 attachments）
  receivable_id  INTEGER DEFAULT 0,                -- 上账生成的应收单（若选"生单"口径）
  contract_id    INTEGER DEFAULT 0,                -- 归属年度框架，**可 0**
  note           TEXT DEFAULT '',
  created_by     TEXT DEFAULT '',
  created_at     TEXT DEFAULT (datetime('now','localtime')),
  updated_at     TEXT DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_rsettle_uniq ON rebate_settlements(brand_key, settle_month);
CREATE INDEX IF NOT EXISTS idx_rsettle_status ON rebate_settlements(status, settle_month DESC);
```

### 3.2 状态机（把"对厂家"与"内部审批"分开）

```
draft ──提交核销资料（须附件，若该厂家 need_doc=1）──▶ submitted ──厂家确认（录确认返利）──▶ confirmed
  ▲                                                        │                                    │
  └───────────────── 撤回 ─────────────────────────────────┘                      上账（→ posted）
                                                                                              │
                                                                          冲销（走 uns_settle）▼
                                                                                         reversed
```

| 状态 | 含义 | 触发 | 可见字段 |
|---|---|---|---|
| `draft` | 待核销 | 系统按月提名 / 手建 | 核销月 · 应交日 · 应上账日 |
| `submitted` | 已交资料，等厂家确认 | 「提交核销资料」+ **凭证门禁** | + 提交时间 · 凭证列表 |
| `confirmed` | 厂家已确认返利 | 录入确认金额 | + 确认返利额 |
| `posted` | 已上账（钱到了） | 「上账」 | + 上账时间（+ 应收单号，若选生单口径） |
| `reversed` | 冲销 | 「冲销」（复用 `uns_settle_rebate` 思路） | 冲销留痕 |

### 3.3 月份三拆 —— **直接复用昨天做好的结算节奏**

这是本次重构的**关键复用点**：v375 建的 `rebate_settlement_schedules` 不是死配置，它**驱动**批次的三个日期。

```
核销月 M（如 2026-09）
  ⇒ 应交资料日 = (M + submit_offset) 月的 submit_day
  ⇒ 应上账日   = (M + submit_offset + post_offset) 月的 post_day
```

取"上月 / 5 号 / 当月 / 20 号"⇒ 2026-09 的资料 10-05 前交、10-20 上账。**与你的原话逐字对应。**

> 实现：把 v375 `routers/rebate_settlement.py` 里的纯函数 `_ym_add` / `_month_action` / `OFFSET_LABELS`
> **抽到 `domain/settle_calendar.py`** 供两侧共享 —— 避免第二份月份算术（这域最容易写错的一处）。

### 3.4 年度合同降级为「可选外框」(#5④)

| 保留 | 降级 | 含义 |
|---|---|---|
| 表 `rebate_contracts` **不删** | 语义从"结算主体"→"年度框架" | 已是 20 个 `/api/rebate-contracts/*` 端点的载体，删除=大范围破坏 |
| 结算批次可**选挂** `contract_id` | 从**必填**变**可 0** | 没签年度合同的厂家照样能按月核销 |
| 页签 B 主视图 | 从「合同卡片列表」→「**批次列表**（按核销月倒序，可按厂家筛）」 | |
| 「+ 录入年度合同」 | 降为次级入口（或改名「+ 年度框架」） | 不再挡在首屏 |

### 3.5 取消重复录入 (#1(a))

**问题**：`rebate_contracts.target_amount` + `rebate_contract_months`（页签 B 自己录）与 `rebate_target_rules.monthly_amounts`（页签 A 录）**是两套年度目标**。
**正解**（= 2026-09-06 已拍板的"同一数据源"）：**以页签 A 的 `monthly_amounts` 为唯一源**，页签 B 只读引用。

### 🔴 一个必须先避开的路由坑

`_PATH_MODULE_MAP` 是 **首个 `startswith` 命中即停**（本项目已知坑，曾致 v317 路由遮蔽）：

- 已有：`/api/rebate-settlement` → `sales`
- 若新路径取 `/api/rebate-settlements`，则 `.startswith("/api/rebate-settlement")` **= 真** ⇒ 被前一条吃掉。
- 现在两条同归 `sales` 所以**无害**，但一旦日后拆模块就会**静默走错权限域**。

⇒ **新路径用 `/api/rebate-settle-batches`**（与 `/api/rebate-settlement` 不构成前缀嵌套），并显式登记 `"sales"`。

# v710 对账匹配判据按整数分 + 月度快照与报表同口径

> 部署时间：2026-10-27 深夜｜后端 3 个文件、4 处改动｜已部署、服务 active、health 200
> 提交：见 `git log --oneline -1`｜回滚：`python3 patch_v710_precision_family.py --revert`

## 一句话结论

「两笔钱是不是同一笔」这个判断，后端原来用 `abs(a-b) < 0.01`，**在浮点下同一个业务事实会给出相反结论**——生产真实金额近邻比较 69,186 次，其中 **16,456 次新旧判据结论相反**。现在统一按整数分（`money_eq` / `ROUND(x,2)`）。同时把月度快照换成和报表页同一套口径，并顺修了一个「从来没跑通过」的对账函数。

## 一、改了哪 4 处

| # | 文件 | 位置 | 改前 | 改后 | 语义 |
|---|---|---|---|---|---|
| 1 | `db/queries/finance.py` | `bank_import_parse` 候选 SQL | `ABS(cf.amount-?)<0.01` | `ROUND(cf.amount,2)=ROUND(?,2)` | 两笔钱是否同一笔 = 按分相等 |
| 2 | `db/queries/finance.py` | `bank_auto_match` 金额 | `abs(abs(a)-abs(b)) < 0.01` | `money_eq(abs(a),abs(b))` | 同上，且**会写库** |
| 3 | `db/queries/finance.py` | `bank_auto_match` 日期 | `abs(日期串 - 日期串) <= 3` | `_days_apart(两串) <= 3` | 见下方「存量崩溃」 |
| 4 | `erp_db.py` | `save_monthly_snapshot` | `get_pnl()` / `get_balance_sheet()` | `get_pnl_gl(month)` / `get_balance_sheet_gl(月最后一天)` | 快照与报表页同口径 |
| 5 | `import_zhoupu.py` | 期初平衡校验（v709 我自己加的） | `abs(借-贷) > 0.01` | `not money_balanced(借,贷)` | 与报表判据同源 |

第 2 处和第 4 处/第 1 处属于不同性质：第 2 处会**自动写库**（把 `cash_flow` 标记 `[已对账]`、`bank_transactions` 标记 `matched`），所以判据错了是**真错配**，不是显示问题。

## 二、为什么必须改：双算数据

`abs(a-b) < 0.01` 在二进制浮点下，**「差 1 分」算不算相等，取决于这两个数字怎么被存储**：

```
50.00   - 50.01   = 0.009999999999998010   ⇒ 老判据判「相等」（错配）
2000.00 - 1999.99 = 0.009999999999999787   ⇒ 老判据判「相等」
1234.56 - 1234.55 = 0.010000000000047748   ⇒ 老判据判「不相等」
100.01  - 100.00  = 0.010000000000005116   ⇒ 老判据判「不相等」
```

双算脚本 `tools/hergent/v710/dualcheck_v710.py`（生产只读，5/5 通过）：

| 库 | 真实金额 | 近邻比较次数 | 新旧结论相反 |
|---|---|---|---|
| `erp.db` | 7 | 42 | 8 |
| `tenant_1.db` | 11,515 | 69,090 | **16,443** |
| `tenant_10.db` | 9 | 54 | 5 |
| 合计 | 11,531 | 69,186 | **16,456** |

**这不是理论风险**：`tenant_1` 的 16,443 次里，有大量「差 1 分被当成同一笔」的情况，用在 `bank_auto_match` 上就是给两笔不同的钱打上同一个对账标记。

## 三、顺修：`bank_auto_match` 从来没跑通过

改金额判据时，探针立刻炸在日期条件上：

```
TypeError: unsupported operand type(s) for -: 'str' and 'str'
```

原代码是：

```python
abs((txn['trans_date'][:10] if txn['trans_date'] else '')
    - (pmt['created_at'][:10] if pmt['created_at'] else '')) <= 3
```

**字符串减字符串**。而这个条件在 `and` 的右边 ⇒ 只要金额先匹配上就必然抛异常。也就是说 `POST /api/bank-auto-match/{sid}` 从一开始就是 100% 500，只是生产 `bank_transactions` 一直 0 行，没人发现。

新增 `_days_apart(a, b)`：解析 `%Y-%m-%d[ %H:%M:%S]` / `%Y/%m/%d` 等格式，返回天差；**任一日期缺失或非法返回 999（判不匹配）**——自动匹配会写库，无法验证时宁可漏配让人工确认，不写假账。

## 四、月度快照：改前是两套口径

`save_monthly_snapshot()` 存的是 `get_balance_sheet()`（简化版）：`权益 = 资产 − 负债` 残差凑等式，**返回体没有 `balanced` 字段**。而 `/api/reports/balance-sheet` 自 v708 起只留 GL 版。⇒ 同一个月的「报表页」和「快照页」会给出两个资产数。

现在快照用 `get_pnl_gl(month)` + `get_balance_sheet_gl(月末)`。现金流量表本身属收付实现制，`get_cashflow()` 保持不动。

**生产影响 = 0**：`monthly_snapshots` 全库 0 行，从来没有快照被存过。

## 五、有意不动的

`get_balance_sheet_gl._eff` 和试算表里都有一句 `abs(余额) > 0.005` 判断「科目有没有余额」。**保持原样**，理由写在双算脚本 B 组里：

- 它是「余额是否为 0」的阈值，**不是**「两笔钱是否同一笔」的判据，两件事不该共用一个函数；
- 生产 43 个科目上新旧判据**零分歧**（改成 `to_cents(v) != 0` 收益为 0）；
- 0.005 处两者会分歧（老=零 / 整数分=1 分，因为 `round(0.005,2)=0.01`）⇒ 改了有语义变化、无收益。

**其余仍用浮点容差、但已确认不属于本类缺陷的**（盘点过，不是漏掉）：

| 位置 | 写法 | 为什么不动 |
|---|---|---|
| `erp_db.py:17991` | `abs(a-aql) < 0.01` | AQL 不良率比较，不是金额 |
| `erp_db.py:18508/18514` | `abs(revenue) > 0.01` | 「是不是非零」的守卫，不是相等判据 |
| `erp_db.py:7168/7186/7191` | `abs(diff) > 0.01` | `diff` 已 `round(...,2)`，与字面量同表示，不会翻 |
| `routers/collections.py:307/354` | `>= amount - 0.005` | 允许少收半分算已付清，业务如此 |
| `domain/product_targets.py:290/403` | `abs(resid) >= 0.01` | 目标分摊残差校验，允许 1 分 |
| `erp_db.py:18721` | 内部往来 `abs(差) < 0.01` → matched | **同类缺陷但无数据**：`ic_transactions` 全库 0 行、`entities` 表不存在，该功能未启用 |

## 七、事故记录：回滚测试误对生产执行

**经过**：我给补丁加了「目录可用环境变量覆盖」的能力，改的是本地文件，但**没有重新 scp** 就直接在服务器上跑 `ERP_DIR=/tmp/v710/revtest ... --revert`。服务器上那份脚本还是旧版（`ERP` 硬编码 `/opt/hergent-erp`），于是它**回滚了生产**的 `db/queries/finance.py` 和 `erp_db.py`。

**影响**：磁盘上两个文件回到 v709 状态，约 40 秒。运行中的进程已加载的模块不受影响（Python 不热重载），期间未对外提供不一致结果。

**处置**：立刻重新上传脚本 → 重跑补丁 → 回读校验 18/18 → 重启 → 四套探针重跑 → 三文件状态确认。当前生产 `money_eq=2 / _days_apart=2 / _get_pnl_gl=2 / _mb=1`。

**教训（值得写进纪律）**：**改完脚本先传，再执行**。尤其是带 `--revert`、带 `--apply`、带删除语义的脚本——本地与服务端版本不一致时，它做的事和你以为的完全不同，而输出看起来完全正常（它确实"从备份恢复了"，只是恢复错了地方）。同一族的坑：`rsync` 与 `scp` 串 `&&` 时前者失败不阻止后者。

## 八、遗留：④ 凭证模板的真实状态（等你定，未动）

上一版把「凭证模板整功能不可用」记成了「5 个函数缺失」。这次查到底了，**实际是三层问题**：

1. **`erp_db` 缺 5 个函数**：`voucher_template_list / create / update / delete / apply`，`grep "def voucher_template_"` 0 命中。表 `voucher_templates` 存在但 0 行。
2. **路由层还有 2 处未定义变量**：`create_template`、`update_template` 里读出来的 `body` 没用，却引用从未定义的 `d`（`v707` 只修了 `test_template` 一处）。
3. 🔴 **最要紧的：模板根本不参与真实记账**。`apply_template` 全后端**只有 `/api/voucher-templates/test` 一个调用点**；`auto_journal_for_sale/payment/purchase/cogs` 里**一次都没有引用**模板或 flag。`voucher_engine.is_voucher_templates_enabled()` 也**没有任何调用者**。

也就是说：**即便把 5 个函数补齐、把 `d` 修好，页面能增删改查、能预览，账还是照硬编码走，一分都不会变。** 前端入口是静态 HTML/JS（`window.render_voucher_templates`），不按权限过滤，也没有可用的前端构建链（`outputs/repro-app.js` 不被任何脚本引用）⇒ **想「藏入口」只能改 minified 产物**，那是不该做的事。

三个选择，我的推荐是 **B**：

| | 做法 | 代价 | 风险 |
|---|---|---|---|
| A | 补齐 5 函数 + 修 2 处 `d`，页面可用，但**不接入记账** | 小（~80 行 + 探针） | 🔴 变成「配了不生效」的假绿灯，比现在崩着更危险 |
| **B** | **先补齐 A，再把 `apply_template` 接进 4 个 `auto_journal_for_*`，用 feature flag `voucher_templates` 控制、默认关闭** | 中（改记账路径，须双算 + 老板确认分录口径） | 中（flag 关着一律走硬编码，等于现在的行为） |
| C | 不做，只在文档记着 | 0 | 页面点每个操作都「内部错误」，像坏产品 |

**为什么不推荐 A**：你讨厌的正是「界面看着能用、实际什么都没发生」。A 就是那个形态，而且它比现在的崩溃更难发现。

**B 开工前我需要你确认一件事**：模板一旦生效，销售出库的分录会从「硬编码 1122/6001」变成「按模板配」，**能改账**。要不要这个能力，是经营决定不是技术决定。

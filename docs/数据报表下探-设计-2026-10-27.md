# 数据报表数据下探 — 设计与实现

> 2026-10-27 交付（v701：后端补丁 + 前端 v701）。
> 口径由老板拍板：**点单号直接跳转对应单据** / **两层：单据 → 商品明细** / **销售 + 采购 + 调拨 三张明细报表**。

---

## 一、先说清现状（实测，不是推断）

改造前的情况：

| 能力 | 状态 | 实测依据 |
|---|---|---|
| 三张明细报表有单号列 | ✅ | 销售 `order_no`、采购 `order_no`、调拨 `order_no` |
| 汇总 → 明细的跳转 | ✅ 但**跨页** | 侧栏汇总行的「明细」徽标 + `drillTo()`，跳整页，不是同页展开 |
| `/api/drill/{metric}` | ⚠️ 与本需求无关 | 只有 `today_income` / `total_ar` 两个指标，给仪表盘用 |
| 表格行交互 | ❌ 没有 | `ReportTable` 纯展示，无行点击、无展开、无面包屑 |
| **报表接口返回单据 id** | ❌ **没有** | 三个端点只 `SELECT order_no`，**这是点不动的根本原因** |
| 移动端适配 | ❌ 没有 | `ReportTable` 一条 media query 都没有 |

**最关键的一条**：没有 id。详情页路由是 `/inventory/sale/:id`、`/inventory/purchase/:id`，
拿 `order_no` 拼地址会 404 或打开别人的单。所以第一步必须先把 id 补出来。

---

## 二、层级定义：只有两层，第三层不存在

| 层 | 是什么 | 数据来源 | 入口 |
|---|---|---|---|
| **L0 汇总** | 销售/采购/调拨汇总表的 KPI | 各 `*-summary` 端点 | 侧栏「数据报表」 |
| **L1 单据列表** | 逐单一行（单号、往来单位、日期、金额、状态） | `*-detail` 端点 | L0 的「明细」徽标 |
| **L2 单据真身** | 该单的完整页面：商品明细、审批、入库、付款、附件、日志 | 单据详情接口 | **L1 点单号** |

**为什么没有 L3**：三层「商品 → 批次/流水」被评估过并**否决**。理由不是工作量，而是
数据本身撑不住 —— `purchase_order_items` 生产只有 14 行（84 张采购单里约 3-4 张有），
再往下钻到批次，多数单是空的。给一个大概率空的下钻，比不给更糟。

---

## 三、触发方式

**唯一触发点 = 单号列本身**。

- 渲染成链接的条件：列声明了 `drill` **且** 该行 `r.id != null`
- 视觉：品牌色 + 虚线下划线，hover 变实线（**不用蓝色粗体** —— 一列全是链接会抢掉金额列的视觉重心，报表里老板先看数字）
- 悬停提示：`查看该销售单的完整明细`
- 键盘可达：`focus-visible` 有 2px 描边

🔴 **没有 id 就不渲染成链接**（退回纯文本）。宁可看起来不能点，也不给一个点了会错的入口。

## 四、每层字段与聚合规则

### L1 单据列表（现有字段不动，只加 id）

| 报表 | 字段 | 聚合 |
|---|---|---|
| 销售订单明细 | id / 订单号 / 客户 / 下单日期 / 金额 / 已收 / 状态 / 发货 / 发票 | **不聚合**，逐单原始行；`status != 'cancelled'` |
| 采购订单明细 | id / 订单号 / 供应商 / 下单日期 / 金额 / 已付 / 状态 | 同上 |
| 调拨订单明细 | id / 调拨单号 / 商品 / 调出仓 / 调入仓 / 数量 / 手续费 / 状态 / 创建时间 | 同上（**行即商品**） |

### L2 单据真身

字段由详情页自己决定（商品行、批次、审批节点、入库单、货款流水）。**报表侧不复制一份明细表** ——
复制出来必然与单据页口径分叉，这正是本仓反复踩过的坑。

### 聚合规则的唯一原则

> **前端零重算。** 金额、已收、未结全部由后端算好；前端只做格式化（`rmb` 精确到分，不用「万元」缩写，
> 避免 ¥1.2 万 丢精度）。

## 五、导航：面包屑 + 返回报表 + 筛选保留

三件套同时存在，各解决一个问题：

| 形式 | 在哪 | 解决什么 |
|---|---|---|
| **面包屑** `数据报表 › 销售订单明细` | 报表页标题上方 | 让老板知道"我在哪一层"；末级不可点（`aria-current="page"`），中间级可回跳 |
| **按钮 `返回报表`** | 单据详情页左上（原来叫「返回列表」） | 「返回上一级」的显式落点。**只在从报表跳进来时**变文案，从侧栏直接进来的仍是「返回列表」 |
| **筛选保留** | 报表页 | 回来时日期区间还在 —— 老板是看完一张单接着看下一张，丢了区间等于每次重选 |

**来源判定用 `history.state.fromReport`，不用 localStorage**：它属于"这一次导航"的上下文，
不会在老板下次从侧栏正常进入时莫名把他弹回报表。

面包屑三态（v701 探针当场抓到的缺陷，已修）：

| 位置 | 渲染 | 说明 |
|---|---|---|
| 末级 | 加粗 + `aria-current="page"` | 当前页 |
| 中间级有 `to` | 可点链接 | 能回跳 |
| 中间级无 `to` | **普通灰字** | 如侧栏分组「数据报表」，没有独立首页 —— 给它加 `aria-current` 会让屏幕阅读器说「当前页面：数据报表」 |

## 六、数据准确性怎么保证

四条硬约束：

1. **id 由后端给，前端不推导**（v701 补丁给三个端点各加主键；不拿单号猜 id）
2. **无 id 不渲染链接**（§3）
3. **L2 不复制明细表**（§4，避免两套口径）
4. **跳转目标必须是真实存在的路由**：只登记 `DRILL_BASE` 里的两条（sale / purchase）。
   调拨**故意不给** —— 路由里没有 `transfer/:id` 详情页（v449 注释明确禁止写），
   给了就是 404。

## 七、加载与性能

| 关注点 | 做法 |
|---|---|
| 列表体积 | 后端默认 `limit=500`（上限 1000），不会一次抖一两万行 |
| 首屏 | 三个报表页与两个详情页都是**路由懒加载 chunk**，下探不增加首屏体积 |
| 返回时不重复请求 | 筛选恢复只在 `sessionStorage` 有值时才 `emit('filter')`，没历史筛选不发请求 |
| 点击无白屏 | 报表 → 详情是 `router.push` 的 SPA 切换，详情页自带 `Skeleton` |

## 八、多维数据与移动端

### 多维

本版下探是**单据维度**（单号 → 单据）。跨维度自由钻取（客户 → 单据 → 商品 / 月份 → 日 → 单）
被评估后**未做** —— 那等于重做一套多维分析引擎，不是给现有报表加一个入口。

### 移动端（≤760px）

| 元素 | 窄屏表现 |
|---|---|
| 面包屑 | 字号降到 11px，内边距加大到 4px（指头点得中） |
| 筛选条 | 竖排：快捷档一行 → 日期一行 → 当前口径整行 |
| 表格 | **保持横向滚动**（列多是事实，挤成两行更难读） |
| 单号链接 | `min-height: 28px`，实测 28px |
| 刷新/导出 | `white-space: nowrap` —— 修掉真机上「刷/新」「导/出」被挤成两行的瑕疵 |

## 九、四条已知边界（写进来，不藏）

1. **采购多数单没有商品明细**：`purchase_order_items` 生产只有 14 行（84 张采购单）。
   早期舟谱导入的是**单头金额**、没有逐商品行 ⇒ 点进去商品表为空是**本就没有记录**，不是加载失败。
   这一点已写在采购报表页脚注上，不让老板点进去再猜。
2. **调拨没有下一层**：`transfer_orders` 一行就是一个商品，没有「单头 + 明细」两层，
   且没有详情页 ⇒ 调拨页是末级，页脚已明说。
3. **没有第三层（批次/流水）**：见 §2 的否决理由。
4. **跨维度钻取未做**：见 §8。

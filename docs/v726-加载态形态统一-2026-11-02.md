## 三、顺手查出的三处真问题（都比骨架严重）

### 1. 算工资页：加载中露出的是一套**假配方**

```js
const form = reactive({ base_salary: 5000, commission_rate: 0, ... })  // 硬编码兜底
onMounted(async () => { const r = await payrollApi.getRecipe(); Object.assign(form, r.recipe) })
catch (e) { /* 用默认 */ }   // 接口挂了也照样算
```

`onMounted` 在首次渲染之后才跑 ⇒ 首帧渲染的是一套「看起来像真配置」的默认值。
用户手快直接点「保存并算工资」，**全员工资就按假配方算了**；接口挂了更是连提示都没有。

**改**：`recipeLoading` 初值 `true`，加载期间**整个表单不渲染**（只给骨架）；
`catch` 不再静默，明确提示「当前是系统默认值，请逐项核对后再算」。

### 2. 往来核销：切换客户时，表格里还是**上一个客户的账**

`onContactChange` 只清 `outstanding`，`receivables` / `advances` / `ledger` 原样留着，
直到新数据回来。这期间用户看到的是一份关于别人的结论 —— 差点被当成这个客户的账核销掉。

**改**：切换即清空三份数据 + 加 `blankLoading` 骨架（只在一份数据都没有时出骨架，
点「刷新」时旧数据仍在，不换骨架）。

### 3. 两处 `loading` 初值取了 `false`（v725 病根②原样复发）

- `BidRadar`：`onMounted(load)` 必然发请求，初值 `false` 会先渲染「暂无匹配」= 关于商机的错误结论
- `PriceChannels`：`onMounted` 必然 `load()` + `loadCustPrices()`，两处初值都改 `true`

**判据**：凡 `onMounted` 必然发的请求，`loading` 初值必须是 `true`。

## 七、判据小结（可直接复用）

1. **「整页无骨架」这种清单必须先核源码再动手**。探针的类名漏一个，清单就错一片。
2. **不是所有页面都该有骨架**。上传页、纯表单页、无首屏请求的页，加骨架只会让正常使用先闪一下。
3. **切换主体（客户/仓库/账期）时必须立刻清空旧数据**，
   否则你显示的是另一个主体的结论 —— 这比显示「空的」危险。
4. **「加载中露出了可提交的假值」是加载态里最严重的一类**，
   骨架只能盖住视觉，盖不住「已经渲染成可编辑表单」这件事，得靠不渲染。
5. **`loading` 初值取 `true` 这条判据会复发**，每次动页面都要重新过一遍。
6. **探针卡死要区分「产品慢」与「工具坏」**，别用修产品的耐心去修探针。

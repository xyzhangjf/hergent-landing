# 进销存 P0-5 库存占用/锁定技术方案（侦察 + 设计稿）

> 状态：**已落地（v501 生产生效，2026-10-14）**。后端 B2（by-product 增 occupied/available）+ B3（deliver 闸门扣占用）+ 前端 B4（采购开单三列）均已上线并真机验证。
> 关联：`docs/进销存P0阶段任务卡.md`（P0-5 项）、`docs/进销存模块差距分析与分阶段开发计划.md`（P0 阶段）。

---

## 一、背景与目标

- **为什么做**：当前系统"可用库存 = 可销售库存"，**完全没有"已订未发占用"概念**（`src/api/psi.js:84-87` 自陈：*销售单在 `deliver` 时才扣库存，本系统没有占用/锁定概念*）。结果是——同一商品被多张销售单同时下单、都看到"有货"，但实际库存只够一笔，低温奶又是高频快周转品，**超卖风险真实存在**。
- **目标**：引入"占用/锁定"概念，让"可用可售量 = 可售批次库存 − 已订未发占用"，在开单与发货环节拦截超卖。
- **非目标（P0 不做）**：不引入复杂的行级行锁/分布式锁、不做按客户信用占额、不做预留单独立实体。P0 只做"计算可见 + 开单/发货软硬校验"的最小闭环。

## 三、方案设计

### 3.1 字段模型（在 `stock/by-product` 返回中新增）
| 新增字段 | 语义 |
|---|---|
| `occupied_quantity` | **已订未发占用** = 该商品在该仓、状态为"已确认未发货"的销售单行数量之和 |
| `available_quantity` | **可用可售量** = `saleable_quantity − occupied_quantity`（可为负，负即超卖预警） |

> 不改动 `saleable_quantity` 含义（仍为可售批次总量），让"占用"成为独立可见维度，符合舟谱"可用=可售批次−订单占用"的对标口径。

### 3.2 后端计算（伪代码思路）
```
# 在 stock/by-product 的每行计算里追加：
occupied = SELECT COALESCE(SUM(soi.quantity),0)
           FROM sale_order_items soi
           JOIN sale_orders so ON so.id = soi.order_id
           WHERE soi.product_id = :pid
             AND so.warehouse_id = :wid
             AND so.status = 'confirmed'        # 关键：已确认、未发货
             AND so.deleted = 0
available = saleable_quantity - occupied
```
- "占用"口径取 `confirmed` 态（订单已确认、尚未 `deliver`）。**不取 `draft`**（草稿未承诺）、**不取 `delivered/signed`**（已发货扣过库存）。若真实状态枚举不同，按 §2.5 校对后替换。
- 与既有 `SALEABLE_BATCH_COND`（批次可售过滤）在同一查询内组合，避免 N+1。

### 3.3 防超卖策略（分级）
1. **展示层（必须）**：开单行"实际 / 占用 / 可用"三列；`available_quantity < 0` 或 `< 行数量` 时该行标红 + 提示"可用不足"。
2. **开单软校验（P0 默认）**：销售单 `confirm` 时，若 `available_quantity < 该行数量`，返回明确错误（不静默通过）。
3. **并发硬保障**：`confirm`/`deliver` 在**同一 SQLite 事务**内重算 `available` 再决定放行；依赖 SQLite 的串行写 + 事务隔离，避免两单同时读到旧可用量都通过。若后端已是事务化 `inventory_adjust`，加一道"发货前再校 available"即可。
4. **不回溯改历史单**：已 `delivered` 的单不参与占用，不影响既有账目。

### 3.4 前端改造
- `psi.js`：`stockByProduct` 文档注释补 `occupied_quantity` / `available_quantity` 语义。
- `InvPurchaseNew.vue` / `PurchaseOrderForm.vue`：库存列由"实际/可用"扩为"实际 / 占用 / 可用"，`isAllExpired` 之外的"可用不足"标红逻辑复用现有 `danger` class。
- 销售开单页（§2.5 定位后）：补同样三列 + confirm 前校验。
- 不改 `quantity`/`saleable_quantity` 现有消费逻辑，避免牵一发动全身。

### 3.5 不破坏现有流的边界
- `draft` 不扣库存、不改源单（psi.js:556）——占用只影响"可用可售"的**计算与展示**，不改变"draft 不落账"的既有契约。

## 五、探针验证（上线后真机断言）

- **可用量公式**：开一张"已确认未发货"销售单后，`GET /api/psi/stock/by-product?ids=<该商品>` 断言 `available_quantity == saleable_quantity − occupied_quantity`，且 `occupied_quantity > 0`。
- **超卖拦截**：对 `available_quantity < 行数量` 的商品 confirm 销售单，断言后端返回明确错误（非 200 静默通过）。
- **并发不超卖**：同一低库存商品并发两笔 confirm，断言至少一笔被拦截，或两笔发货后 `quantity` 不为负。
- **不破坏既有**：`draft` 单不计入 `occupied`；`deliver` 后 `occupied` 回落。

## 六、风险与回滚

- **风险 1（最高）**：后端源码不在本工作区，若在生产机直接改且未隔离构建，会踩并行会话/脏构建坑（见 `topics/deploy-ops.md`）。→ 必须先 checkout 正确 erp 仓库、确认 `outDir`/mtime、隔离构建。
- **风险 2**：`sale_orders.status` 真实枚举与前端契约不一致，导致占用口径漏算/多算。→ §2.5 校对后再写 SQL。
- **风险 3**：占用计算放大 `stock/by-product` 的查询开销（多 JOIN）。→ 加在聚合查询内、复用索引；大数据量再考虑缓存。
- **回滚**：占用为只读计算 + 开单校验，不影响库存主数据；出问题只需回退 erp 后端到上一 tag（`bash /opt/hergent-admin/scripts/release.sh rollback <tag>` 不适用 erp，erp 回滚按 `hergent-erp.service` 部署流程）。

## 七、验收标准（对齐 P0 总验收）

1. `stock/by-product` 返回含 `occupied_quantity` / `available_quantity`，且 `available = saleable − occupied` 恒成立。
2. 开单页展示"实际 / 占用 / 可用"三列，可用不足时标红提示。
3. 启用占用锁定后，**并发两单不出现负可用、不出现超卖发货**。
4. 既有 `draft` 不落账、历史单不受影响，回归无破坏。

## 八、实施记录（v501 · 2026-10-14）

### 8.1 关键修正（落地前发现）
- 设计稿 §3.2 假设占用口径取 `confirmed` 且 `sale_orders` 有 `deleted` 列。实机侦察确认：状态机确为 `draft→confirmed→delivered→signed`（`confirmed`=已确认未发货），**但 `sale_orders` 无 `deleted` 列**——占用 SQL 去掉 `so.deleted=0`，仅靠 `status='confirmed'` 自然排除 `cancelled/rejected`。
- 当前生产 `tenant_1.db` 22505 张销售单全是 `signed`，无在途 `confirmed` ⇒ 改动对现网零影响，仅在未来的确认单上生效（低风险）。

### 8.2 后端（生产机 `/opt/hergent-erp`，非 git 仓库）
- **B2** `routers/psi.py::psi_stock_by_product`：在既有 `with db.get_db()` 内新增已订未发占用子查询（`confirmed` 态销售单行按商品+仓聚合），每行补 `occupied_quantity` / `available_quantity = saleable − occupied`。
- **B3** `db/queries/sales.py::sale_order_deliver`：短缺校验的"可发量 = 可售库存 − 其它 `confirmed` 单占用（排除本单）"，在 `get_db_tx()` 事务内重算，防并发双过。

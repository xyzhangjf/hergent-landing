## 一、目标与范围

### 1.1 目标

在不破坏线上功能的前提下，用 5 个阶段把「视觉一致性、组件复用、可访问性」三项高风险降到可接受水平，并顺带消除性能隐患与已知技术债。

### 1.2 三条不可违背的原则

1. **不破坏线上**：每个阶段独立可上线，改动后 `npm run build` + 生产 grep 探针 + 双侧 md5 校验（沿用既有部署纪律）。
2. **证据驱动、小步快跑**：每项改动先定位 `文件:行号` 证据 → 一处一改 → grep 复核 → 构建验证。
3. **复用旧后台资产**：Modal/ConfirmDialog/Skeleton/EmptyState/Pager 等直接移植 `hergent-admin` 的成熟实现，**不重写**。

## 六、Phase 3 — 性能与巨型组件拆分（13 人日）

> 里程碑 **M5**：`Forecast.vue` 拆分第一阶段完成，性能隐患清零。⚠️ **本阶段风险最高，需小步 + 护栏**。

### 6.1 拆分策略（`Forecast.vue` 13800 行）

**禁止一次性重构**。按「先护栏 → 再渐进抽取」：

1. 拆分前先补探针：确认预报主表、交叉表、虚拟滚动、复制列、品牌筛选等关键交互在拆分后行为不变（用既有 `check_sfc.mjs` + 关键路径冒烟）。
2. 按业务域渐进抽取为 `composables/` + 子组件：
   - 交叉表渲染与校验 → `forecast/` 子组件 + `useCrossTable`
   - 草稿保存/节流 → `useDraftSave`
   - 快捷键/全局查找 → `useKbdShortcuts`（顺修监听器泄漏）
   - 列设置/冻结/密度 → 复用既有 `useColSettings`/`useColResize`
3. 每抽取一个域 → `build` → 回归 → 再抽下一个。

| # | 任务 | 工作量 |
|---|---|---|
| 3.1 | Forecast 拆分解耦（含 `deep watch` 优化 + `onGlobalFind` 监听器泄漏修复） | 6 人日 |
| 3.2 | 其余 20 个 >800 行组件按优先级拆分（CopilotDrawer/Rebate/进销存表单） | 4 人日 |

**验收标准**：`Forecast.vue` 行数下降 ≥40%；`grep addEventListener` 无未清理监听器；构建通过 + 生产双侧 md5 校验 + 关键交互回归。

## 十、建议的执行顺序与决策点

**推荐立即启动 P0 三件事**（Phase 0 + Phase 1 的确认弹窗替换 + Phase 3 的 Forecast 拆分护栏）：

1. **先做 Phase 0**（6 人日，风险最低、收益最大，是其余所有治理的地基）。
2. **确认弹窗替换**可与 Phase 0 并行（复用 admin ConfirmDialog 成熟实现）。
3. **Forecast 拆分**延后到 Phase 3，但在 Phase 0 完成后**先补拆分护栏探针**，避免越拖越难拆。

**待你拍板的决策点**：
- 是否接受「AI 协作 + 你确认关键交互」的执行方式（而非引入全职前端）？
- Forecast.vue 拆分是否作为独立专项优先启动（它是最大单一风险点）？
- 两套前端（cn-v2 与 admin）近期是否有合并计划？有则 Phase 4 的 token 统一需提前到 Phase 0。

# 企微副驾「三点动画两个版本上下跳」根因与处置

日期：2026-11-01
影响面：企业微信聊天窗口里的 AI 机器人回复（Web 副驾不受影响）
改动文件：`plugins/platforms/wecom/adapter.py`（Hermes 发行版，v4 → v6）、`/opt/hergent-erp/tools/hermes_wecom_ack_patch.py`

---

## 一、现象

老板在企业微信里跟副驾聊天，等回复时看到**两个三点动画一上一下地跳**：一个灰、一个彩。

## 二、根因：不是 bug，是两套动画叠加

| 动画 | 来源 | 外观 | 位置 |
|---|---|---|---|
| `●··` → `·●·` → `··●` | **我们 9-27 打的补丁**每 0.9s 推一帧字符 | 灰（正文色） | 气泡**正文** |
| 「AI 生成中」 | **企微客户端对 `finish=false` 流式消息自带** | 彩（企微品牌色） | 气泡**状态位** |

补丁本意是解决「发完消息 1~3 分钟没有任何反馈」（企微适配器的 `send_typing()` 原是空实现）。
它用企微原生流式消息建占位、再把占位逐帧改成 `●··`/`·●·`/`··●` 制造「正在输入」的观感。
但企微客户端**对同一条流本来就会显示自己的生成中动效** ⇒ 两者节奏不同、位置不同，就成了「一灰一彩上下跳」。

**结论：我们自己那套是多余的，应该整段让位给企微原生动画。**

## 三、处置（v6）

老板定的口径：**只用企微原生那套，占位文案也不要。**

- 占位内容 → `\u200b`（零宽空格，不可见）⇒ 气泡里没有任何我们自己的文字；
- 帧序列 → `()`（空）⇒ **不再逐帧动画**，改为每 60s 一次**保活重推**（同内容重推，视觉零变化）。
  保活是必需的：官方要求首帧后 10 分钟内 finish，agent 跑长工具链时靠它续上；
  上限从 300s 放宽到 **540s**（9 分钟，留 1 分钟余量）。
- 收口逻辑不变：`finish=true` 原位换成最终答案 ⇒ 聊天记录里仍只有一条。

### 顺带修掉两个静默失效（这才是关键）

1. **帧结果不校验**：`_send_reply_request()` 只在网络/超时层抛异常，**服务端业务拒绝是「正常返回带 errcode」**
   ⇒ 旧代码「看起来发了、其实没显示」，日志一片安静。
   新增 `_hergent_frame_ok(resp)`：errcode≠0 记 WARNING；
   **首帧被拒 ⇒ 不建流**，`send()` 自动退回普通发送；**收口被拒 ⇒ 返回 False 并退回普通发送**。
2. **收口失败会吞答案**：旧 `send()` 收口后无条件 `return SendResult(success=True)`，
   流过期/req_id 失效时答案直接丢。现在收口失败会走 `_hergent_orig_send()` 补一条普通消息
   —— 宁可多一条，绝不吞答案。

## 四、验证链

| 项 | 结果 |
|---|---|
| 脚本离线演练（拿线上适配器副本跑） | v4→v5→v6 升级、幂等复跑、`--check` 全通过 |
| `py_compile`（脚本 + 被改的适配器） | 通过（写入后自检，失败自动回滚） |
| 生产适配器常量 | `_HERGENT_PLACEHOLDER = "\u200b"`、`ANIM_FRAMES = ()`、`INTERVAL = 60.0`、`MAX_SEC = 540.0` |
| 残留旧函数 | `_hergent_anim_loop` 已无引用（改为 `_hergent_keepalive_loop`） |
| 网关重启 | `hermes-gateway.service` active，PID 4188014 |
| 企微通道 | `[Wecom] Connected to wss://openws.work.weixin.qq.com` + `✓ wecom connected` |
| 补丁在位 | `--check` → `补丁在位（v6）✅｜占位=零宽空格(U+200B，不可见)｜模式=纯原生（只保活 60s 一次）` |

**待老板真机确认一条**（只能在客户端看到）：
发一句 → 应只看到**一条**气泡，里面**没有任何文字**，只有企微自己的彩色生成中动效；出结果后原位变成答案。
若企微把零宽空格判为空并拒绝首帧，日志会出现 `首帧占位被拒 ⇒ 本轮不建流` ⇒ 表现退化为「没有占位、只有答案」，不影响答案送达。

### 顺带查实的历史事故：4 条答案曾被静默吞掉

`grep 结束占位失败 /root/.hermes/logs/gateway.log` → **4 次**（10-20 21 点 ×1、10-22 20 点 ×3），
且**这 4 次后面紧跟的都是 `占位已原位替换为最终答案`** ⇒ 收口推送失败了，代码却当成功返回
⇒ 老板那 4 次**什么都没收到**（气泡停在上一条，答案消失）。

这正是上面第 2 条「收口失败吞答案」的实证。v6 起这条路径会退回普通发送补一条，不会再丢。

## 五、回滚

```bash
# 恢复 v4 观感（看得见的跳动占位）
python3 /opt/hergent-erp/tools/hermes_wecom_ack_patch.py \
  --placeholder '●··' --anim-frames '●··|·●·|··●' --anim-interval 0.9
systemctl restart hermes-gateway

# 或整块还原上一次备份
python3 /opt/hergent-erp/tools/hermes_wecom_ack_patch.py --revert
```

备份位置：
- 适配器：`/usr/local/lib/hermes-agent/venv/lib/python3.11/site-packages/plugins/platforms/wecom/adapter.py.bak-hergent-20261101_191743`
- 补丁脚本：`/opt/hergent-erp/tools/hermes_wecom_ack_patch.py.bak-20261101_1917xx`

## 六、两条运维纪律

1. 🔴 **这台机器上有两份 Hermes 引擎**：`/opt/hermes-agent` 与 `/usr/local/lib/hermes-agent`，
   **进程实际跑的是后者**。查补丁/改适配器只看 `/usr/local`，看 `/opt` 会误判成「补丁没打」。
2. 🔴 **这套补丁打在 Hermes 发行版文件上，Hermes 一升级就被覆盖**（现象：又变回「等半天没反应」）。
   升级后必须跑一次 `hermes_wecom_ack_patch.py --check`，rc=0 才算在位。

## ② 清理租户库遗留平台表副本（patch 0003）

### 先证伪，结论是「证伪失败」

`tenant_1.users` 有 6 行**真实 bcrypt 哈希**（历史 seed 快照）、`sessions` 350 行。
所以不能直接删 —— 先要回答"有没有代码在租户上下文读它们"。

为此写了 `tools/hergent/v706/scan_legacy_reads.py`，把 75 个引用函数按
**连接类型 × 路由上下文**两段证据分类（脚本自带解释）：

| 分类 | 数量 | 判定 |
|---|---|---|
| 显式主库连接 / 端点在 `_TENANT_MASTER_PREFIXES` | 56 | 安全 |
| 租户连接但端点在主库前缀（`/api/users` `/api/tenants` `/api/force-logout`） | 17 | 安全：上下文为 None 时**同一函数回落主库** |
| **租户连接 + 租户上下文** | **1** | `GET /api/sales-targets` 的 `LEFT JOIN users` |

那 1 处就是承重点，且它本身**已经在静默出错**：真实员工（主库 id 9999xx）
在租户库那 6 行种子账号里根本不存在 ⇒ `user_name` 恒为 NULL 或旧名字。
（该模块在生产已无 UI 调用、`sales_targets` 两库均 0 行，但既然发现就修对。）

### 三处改动

1. `GET /api/sales-targets`：改为「租户库取目标 + 主库取名合并」，与
   `external_accounts_list` / `employee_account_map` 同一条口径（跨库不做 JOIN）。
2. `tenant_db_init()`：**不再复制** `users/sessions/tenants/user_tenants/invite_*`
   —— 否则下一个新租户立刻再长出一张空 `users`，本版等于白做。
3. patch 0003 删副本。**主库自动跳过**，判定用 `PRAGMA database_list` 的真实路径
   + `realpath` 比对，取不到就 **fail-closed 拒绝执行**。

> 🔴 主库守卫第一版在 macOS 上判错：`/var` 是 `/private/var` 的符号链接，
> `abspath` 比较不相等 ⇒ 会把**主库**当租户库删掉 `users`。
> 离线测试第一次跑就踩中了（测试库建在 `/var/folders/...`），改成 `realpath` 后通过。

## ③ 收编 389 处 `_safe_migrate`（冻结存量、堵住增量）

实际盘点：**389 处**（不是之前记的 359），全在 `erp_db.py`；
0 组"同名不同 SQL"，380 处 SQL 为字面量，7 处为拼接/常量引用，2 处名字是 f-string。

**没有**把这 389 条改写成 patch —— 那对应 DDL 早在生产跑过，改写只会让
"哪台库跑过哪一版"重新变得不可判定，是负收益。真正要治的是两条**静默病**：

| 病 | 后果 | 拦法 |
|---|---|---|
| 改了历史迁移的 SQL（名字不变） | 已跑过它的库**永远**拿不到新逻辑，且不报错 | 内容指纹比对 |
| 新增 `_safe_migrate(...)` 调用 | 新 DDL 绕过版本管理 | 名字集合比对 |

- `migrations/legacy_baseline.txt`：387 条迁移的名字 + 指纹（2 条 f-string 的无法静态取名字）。
- `inventory_safe_migrate.py --check`：生产实测 **387/387 一致**；注入两类漂移均被拦（退出 2）。
- 边界如实写在 README：拼接型指纹落在**表达式**上（抓改片段、抓不到改被引用常量）；
  **账外裸 DDL 还有 341 处**（`db/queries/*.py` 那 42 处是同一批迁移的第二份拷贝）→ 未清欠账。

## ④ 修 `money_balanced` 浮点缺陷

老判据 `abs(dr - cr) <= 0.01`，同样的业务事实结论相反：

```
100.00 - 99.99    = 0.010000000000005116  ⇒ 拒单
1234.56 - 1234.55 = 0.010000000000000009  ⇒ 过账
```

**先双算再改**（`dualcheck_money_balanced.py`，只读）：`erp.db` 6 张凭证、
`tenant_1` 23 张、`tenant_10` 0 张，老新判据**逐张一致、零翻案** ⇒ 只影响今后
"恰好差 1 分"的新过账。改为 `abs(to_cents(dr) - to_cents(cr)) <= MONEY_EPS_CENTS(=1)`。

端到端验证：生产真跑一次差 1 分的 `gl_post`（返回成功、写入 2 行），随后删除，
自证残留 0。影响面：全仓只有 `gl.py::gl_post` 一处调用；
`finance.py:102` 的 `abs(...) < 0.01`（严格小于）**刻意不动**，那是另一件事。

**边界**：三分位输入（`2.675`）按分规整后只差 1 分 ⇒ 判平。这不是缺陷 ——
金额最小单位就是分，三分位金额本身是非法输入（全库写入都经 `round_money()`）。

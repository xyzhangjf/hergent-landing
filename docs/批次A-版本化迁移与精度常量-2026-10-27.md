## 二、为什么要做（两个永远不会报错的窟窿）

### 窟窿 1：改过的迁移不会重跑，也不会报错

`_migrations` 只记 `(name, status)`。改一条已经执行过的迁移的 SQL，名字没变 ⇒
`_migration_applied()` 返回 True ⇒ 直接 `return`。

后果：**一台老库按旧 SQL、一台新库按新 SQL，两台都声称 ok，结构却不同。**
这种差异不产生任何日志，只能靠人肉 `PRAGMA` 一条条比。

**补法**：`schema_patches` 记 `checksum`。同一版本号内容变了 ⇒ 运行器**直接失败**，
逼人新增一个版本号。历史不可改写。

### 窟窿 2：没有版本与顺序

无法回答「这台库是第几版」「哪台落后了」「两台一样吗」。

**补法**：`NNNN_名字.sql|py` 顺序编号 + 每库一张登记表 + `--all-tenants` 一次对齐。

### 四条设计决定（都为了「不骗人」）

1. **本包不 import `erp_db`**。`erp_db` 在**导入期**就执行 359 条 `_safe_migrate`（会写库）。
   体检工具一旦 import 它，「跑一下看看有没有漂移」本身就在改生产。全部直接用 `sqlite3`。
2. **`--check` 只用只读连接**（`mode=ro`），打不开就报错，绝不回落成可写。
3. **SQL 文件逐语句执行 + 显式事务**，不用 `executescript()`（它会隐式提交，中途失败留半截库）。
   实测：一版里第 2 条语句坏 ⇒ 第 1 条也回滚，且失败被记进登记表。
4. **失败版本改内容允许重跑**（它从未生效）；**成功版本改内容直接拒绝**。这条区分是本模块的核心。

## 五、生产实测发现（顺带抓到的真问题）

### ① 迁移漂移是真的，而且不小

| 库 | 表 | 索引 | 缺索引 | 其中唯一索引 |
|---|---|---|---|---|
| master | 334 | 65 | — | — |
| tenant_1 | 397 | 98 | **4** | 1（`idx_caliber_pk_bk`） |
| tenant_10 | 397 | 77 | **9** | 2（`idx_caliber_pk_bk`、`uq_product_target_month`） |

**唯一索引缺失不是"慢一点"，是"可以写进重复数据"**：`uq_product_target_month` 缺在
`tenant_10` ⇒ 同一商品同一月份的销售目标可以被写两条，之后按目标算达成率会翻倍。
`idx_caliber_pk_bk` 缺在两个租户库 ⇒ 行业口径的 `(param_key, bucket)` 唯一性没有保证。

> 这正好复现了历史上「租户库 0 索引上线」那一类事故的机制：`tenant_db_init()` 用
> `iterdump()` 只复制**建库当时**主库的 CREATE 语句，之后主库新增的索引不会自己长过去。

### ② 租户库里躺着主库的 `users` / `sessions` 副本（安全项）

`tenant_1`、`tenant_10` 各有 4 张遗留平台表副本：`users`、`sessions`、`tenants`、`user_tenants`。
成因在 `db/connection.py` 的注释里记着：旧实现用 SQLite `backup()` 建租户库，
而 `backup()` 是**页级整库复制**，把数据一起搬了过去。创建路径已修，**副本还在**。

`users` 里有**密码哈希**。租户库的鉴权从不读它，属于该清理的安全残留。

### ③ 金额里真的存着 3 位小数

`purchase_orders#179` 的 `total_amount = 920.004`（`typeof = real`）。
全库 84 张采购单里有 **2 张**金额超过 2 位小数 —— `money()` 在这条写入路径上没被调用。
这就是 P0-4 要解决的问题本身，不是理论风险。

## 六、这次**没做**的事（避免误会成"架构改造完成了"）

| 没做 | 为什么 |
|---|---|
| 没把 359 处 `_safe_migrate` 搬进 `migrations/patches/` | 那是 P0-3 主体，逐条搬要一版一验；本批只把"新变更"的入口立起来 |
| 没把 356 处 `round(,2)` 换成 `round_money()` | 逐处替换 = 不可验证的批量改写；金额改错当场看不出，要等下月对账 |
| 没统一 `finance.py:102` 的 `< 0.01`（与 gl 的 `> 0.01` 严格性相反） | 统一它是**业务决策**，不是重构：差额恰好 1 分时两者结论相反 |
| 没修 `money_balanced` 的浮点缺陷（`100.00 - 99.99 > 0.01`） | 原样保留是硬要求；修它会让一部分过去被拒的过账开始成功，属口径变更。已在代码里写清并单列为 P0-4 |
| 没接进启动流程 | 启动已有 359 条迁移，再加 10 个库的体检会拖慢启动；先按需手动跑 |
| 没自动 downgrade | SQLite 的 DROP COLUMN 与数据回滚无法保证正确，自动回滚会让人误以为"按一下回到过去" |
| 没清理缺索引 / 遗留副本 | 清理要单独一版、单独验证；本批只**让它们可见** |

```bash
rm -rf /opt/hergent-erp/migrations /opt/hergent-erp/db/precision.py

# ③ 登记表（就这一张，不含业务数据）
python3 -c "
import sqlite3,glob,os,re
for p in ['erp.db']+[f for f in glob.glob('tenant_*.db') if re.fullmatch(r'tenant_\d+\.db',f)]:
    c=sqlite3.connect(p); c.execute('DROP TABLE IF EXISTS schema_patches'); c.commit(); c.close()
    print('dropped', p)"
```

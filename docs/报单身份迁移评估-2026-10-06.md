## 二、先看清现状

### 2.1 这个字段到底是什么

屏幕上「编辑员工 → **报单身份** → 个人仓」这唯一一个下拉，落到数据库就是 **`hr_employees.warehouse_id`**（整数，0 = 未设）。

- 加列时间：v107（`erp_db.py:1150`，`ALTER TABLE hr_employees ADD COLUMN warehouse_id INTEGER DEFAULT 0`）
- 界面入口：`EmployeeArchive.vue:188-209`（编辑弹窗的第 2 个分区，标题就叫「报单身份」）
- 列表展示：`EmployeeArchive.vue:109`（员工列表里一列，显示仓名）

它的业务作用（后端注释原话）：该员工在**报单**时，可以对这个仓报**调拨单**；报单对象**自动锁定**这个仓，报不了别人的仓（防选错）。

它**不参与**工资核算、考勤、绩效、提成。**从天性上讲，它就是报单配置的一部分。**

### 2.2 它和「报单配置」是什么关系

要配通「某人能报自己仓的调拨单」，现在必须**两条腿走两个页面**：

```
第 1 步  员工档案 → 编辑员工 → 报单身份 → 个人仓     ← 给员工"绑一个仓"
第 2 步  预报订货管理 → 报单配置 → 新建配置          ← 把这个仓"挂到汇总表某一列"
                                    对象类型选「本人仓」
```

第 2 步**以第 1 步为前提**：没绑定个人仓的人，在报单配置里选「本人仓」会被**直接拒绝**，提示「该员工未配置本人仓，请先在员工档案设置其个人仓后再映射」（`erp_db.py:7723` / `7819`）。

也就是说：**要办成一件事，得跳两个页面，而且第二个页面会把你赶回第一个页面。**

### 2.3 你这台租户的真实情况（2026-10-06 只读实测）

**⇒ 而会计/主管配到「本人仓」时会看到那句「请先在员工档案设置其个人仓」—— 可他们连员工档案都进不去。**

进一步核过「是不是深链能绕进去」：
- 路由守卫（`router/index.js:185-219`）**只判角色轴**（`roleGuarded` / `pageRoleAllowed`），**不判模块轴**。
- 会计在 `BIZ_ROLES` 里 ⇒ 守卫**放行**，能深链进 `/archive/employees`；
- 但页面数据走 `/api/employees`（模块 `hr`）⇒ **403**；
- 而 403 被 catch 静默吞掉 ⇒ 列表恒空、**零报错**。

⇒ 这正是本项目最忌讳的形态：**假入口**（看得见壳、读不到数、不告诉原因）。

**迁移后的权限轴变化（本方案的关键决策点）：**

| | 改前 | 改后 |
|---|---|---|
| 接口 | `PUT /api/employees/{eid}` → 模块 **hr** | 新增 `PUT /api/report-mappings/self-warehouse` → 模块 **data** |
| 谁能改个人仓 | 仅 admin/boss | **admin/boss/会计/主管**（与「能配报单映射的人」终于同轴） |

> 🔴 纪律：**多写入口 ⇒ 规则必须单一实现**。新端点**不能自己写一份更新逻辑**，必须调用同一个 `db.employee_update` / 同一个校验函数。否则就会出现"两处判断不一致"，这是本仓反复栽过的坑。

## 四、必须先定的一个语义问题

现在「个人仓」是**员工属性**：一个人**只能有一个**自己的仓（后端隐含，没有显式约束，但界面上只能选一个）。

而「报单配置」的一行是 **(报单人 × 对象) 的映射**，天然允许一个员工有多行。

**所以搬过去必须回答：一个员工能不能有 2 个本人仓？**

| 选项 | 含义 | 后果 |
|---|---|---|
| **A1（推荐）** | 保持「一人一仓」：在报单配置里，选中员工后出现**「该员工的个人仓」**这一格（员工级子表单） | 语义完全不变，风险最小，**只是换了地方填** |
| A2 | 允许「一人多仓」：把仓做成**映射行的字段** | 语义扩张。业务上像"一个人管两个仓"，但会连带影响小程序下拉、库存显示（"你所在仓"变多仓）、汇总表列归属 ⇒ **需另立需求** |

> 建议按 **A1**：本次只做"搬家"，**不做语义扩张**。等真的出现"一人管两仓"的业务需求再单独立项。

## 五、方案对比

### 方案 A（推荐）：表单搬家，数据不搬家

- **界面**：员工档案的「报单身份」段**移除**；报单配置里「对象」那格**从只读展示变成仓下拉**（选员工 → 选仓 → 一步配完）
- **数据**：仓仍写 `hr_employees.warehouse_id`（保持"归属"的唯一真身），`report_mapping.counterparty_id` 照旧由它派生
- **权限**：新写端点归 `data` ⇒ 会计/主管终于能设个人仓
- **新增一条约束**（必要）：**一个仓只能属于一个员工** —— 下拉里对已被别人占用的仓给出提示/拒绝（否则会出现两个员工同仓，报单时容易互相覆盖）
- **代价**：后端 3 文件 + 前端 2 页面；**零迁移**；可灰度（新老入口并存，老入口最后再撤）

### 方案 B（更彻底，建议缓做）：把个人仓变成「报单配置」的属性

- 让 `report_mapping.counterparty_id` 成为唯一真身，`hr_employees.warehouse_id` 退化成派生只读（或废弃）
- **好处**：消灭"双份存储" —— `routers/data.py:469` 早就写明「`hr_employees.warehouse_id` 在生产上**并不是报单配置的真身**」，双份必然漂移
- **代价**：读点全改 + 需要迁移 + 上面那个"一人多仓"语义问题必须先定；风险显著高于方案 A
- **建议**：不在本轮做。可作为**方案 A 落地并稳定运行后**的收敛项，届时用同一套"并集读 + 提示补配"的手法平滑过渡（与 2026-09-19 门店收敛完全同款）

**两方案都必须遵守的一条**：`counterparty_id` 与 `hr_employees.warehouse_id` **不能各写一份判断** —— 现成的反面教材就在 `data.py:469` 那段注释里。

## 三、本轮新增问题（按严重程度）

### 低-新1 · 月份偏移标签缺键（前端 + 后端镜像）　严重程度：**低**
- **文件路径 / 行号与代码**
  - 后端 `hergent-erp/server/routers/rebate_settlement.py:156`
    ```python
    f"上账的是{OFFSET_LABELS.get(so + po, '上月')}核销的返利"
    ```
  - 前端 `hergent-cn-v2/src/components/rebate/SettlementScheduleTab.vue:263`（镜像同一公式）
    ```js
    + `即提交的${postAt}）。`
    ```
    其中 `offsetText(Number(f.submit_offset) + Number(f.post_offset))` 调用 `OFFSET_TEXT`（见 `SettlementScheduleTab.vue:235` `const OFFSET_TEXT = { 0:'本月', 1:'上月', 2:'上上月' }`）。
- **判据（可失败的硬规则）**：`OFFSET_LABELS` / `OFFSET_TEXT` 字典**只含键 {0,1,2}**；而 `so∈{0,1,2}`、`po∈{0,1}` ⇒ `so+po` 可达 **3**。代码对缺失键回退字面量 `'上月'`，无判错。
- **可能造成的影响**：当作用对象配置为「提交=上上月（submit_offset=2）+ 上账=次月（post_offset=1）」这一可选组合时，`so+po=3` 被错误显示成「上月」；结算日历句子与预览句会出现内部矛盾的月份标签（如「提交上上月的资料…上账的是**上月**核销的返利」）。**仅标签错误，不影响实际结算日期**（`submit_due`/`post_due` 由 `_day_of(ym, day)` 按真实日计算，正确）。
- **最小改动修复建议**：在两端字典各补键 `3`（"上上上月"），使标签与 `ym-(so+po)` 的真实月份一致：
  - 后端 `OFFSET_LABELS = {0:'本月',1:'上月',2:'上上月',3:'上上上月'}`
  - 前端 `OFFSET_TEXT = {0:'本月',1:'上月',2:'上上月',3:'上上上月'}`

### 低-新3 · 品牌加载失败被静默吞掉（无日志）　严重程度：**低**
- **文件路径 / 行号与代码**：`hergent-cn-v2/src/components/rebate/SettlementScheduleTab.vue:269-275`
  ```js
  async function loadBrands() {
    try {
      const r = await api('/api/brands?include_inactive=1')
      ...
    } catch (e) { /* 品牌加载失败不阻断页面：作用对象仍可选"默认" */ }
  }
  ```
- **判据（可失败的硬规则）**：`catch` 体为空、且**无任何日志/上报**；属设计性降级（品牌列表失败仍可配「默认」），但 `/api/brands` 若异常则完全不可见，违背本仓「静默失效必须暴露」的通例。
- **可能造成的影响**：若品牌接口长期报错，用户只看到「作用对象」下拉里没有具体品牌、却不知道原因；调试时无迹可寻。
- **最小改动修复建议**：至少在 catch 内 `console.warn('加载品牌失败', e)` 或 `toast('品牌列表加载失败，仅可配默认', 'warn')`，与「降级但可见」原则对齐。

### 系统性观察（非本轮新增，适用于本新路由）　严重程度：**低**
- **文件路径**：`hergent-erp/server/routers/rebate_settlement.py`
- **事实**：写接口（`POST ''` / `PUT '/{sid}'` / `DELETE '/{sid}'`）仅经 `_auth(request)` 做**认证**；模块级访问由 `server.py:_PATH_MODULE_MAP` 的 `/api/rebate-settlement → sales` 中间件统一 fail-closed 拦截；但 **create/update/delete 动作级权限未在该路由服务端校验**，只由前端 `canDo('sales','create'/'update'/'delete')` 守门（见 `SettlementScheduleTab.vue:213-215`）。
- **对照**：全仓 101 个路由中仅 2 个用了 `_check_perm`，其余（含 `rebate_rules.py`、`commitments.py`）同此模式 ⇒ **本路由与既有架构一致，非本轮引入的新风险**。
- **连带**：`:313` / `:322` `await request.json() or {}` 未包 `try`，畸形 body 会冒泡为 500（与既有写法一致）。
- **影响与建议**：仅当「某角色有 `sales` 模块读写、但被收掉 delete 动作」时，API 仍可越权删除——属服务端纵深防御缺口，但全仓同源。建议后续统一在写路由接入 `_auth_perm('sales')`（或细到动作）作为系统性整改，而非单点修本文件。

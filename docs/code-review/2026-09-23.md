## 一、潜在 Bug

### [中] hermes_core.py:808 — 裸 `except:` 吞掉 `json.loads` 解析错误
```python
for o in (orders or []):
    ...
    items = o.get("items", [])
    if isinstance(items, str):
        try: items = json.loads(items)
        except: items = []          # ← 裸 except，吞掉 JSONDecodeError
```
- **影响**：当某订单 `items` 为脏字符串（非法 JSON）时，静默变成空列表 → `customer_products` / `product_names` 少算，下游商品画像与向量检索**缺数据且零日志**，问题难以被发现。
- **最小修复**：收窄为 `except (json.JSONDecodeError, TypeError): items = []` 并 `log.warning("... 解析失败，按空处理", e)`。

### [中] hergent-cn-v2/src/pages/Forecast.vue:7209 — `JSON.parse` 未捕获
```js
async function saveSuggestRecipe() {
  const n = (window.prompt('配方名称：') || '').trim(); if (!n) return
  const list = JSON.parse(localStorage.getItem(SUGGEST_RECIPE_KEY()) || '[]')  // ← 未包 try/catch
```
- **影响**：若 localStorage 中该键为损坏 JSON（异常断电 / 手工改坏），`saveSuggestRecipe` 抛未捕获异常，"保存配方"动作整体失败，且无回退。

### [低] hergent-cn-v2/src/pages/Forecast.vue:7524 — `Math.max/min.apply` 大数组隐患

- **影响**：当前 `a = r.history`（固定 ≤6 期），无栈溢出风险；但若未来历史点变多，`Function.prototype.apply` 会因参数过多抛 `RangeError`。

### 9.2 收窄策略（按"被吞掉的到底是什么"分三类，不做一刀切）

| 类别 | 判据 | 收窄为 | 处数 | 理由 |
|---|---|---|---|---|
| A 数据解析 | `json.loads` / `await request.json()` / `float()` | `(ValueError, TypeError)` | 17 | 这三个异常**完全覆盖**解析失败的全部现实成因（`JSONDecodeError`、`UnicodeDecodeError` 均为 `ValueError` 子类）；语义明确，且与仓库既有纪律（`inventory.py`/`forecast_engine.py`）一致 |
| B DDL 幂等迁移 | `ALTER TABLE ADD COLUMN` 撞已有列 | `sqlite3.OperationalError`（`mfa.py` 补 `import sqlite3`） | 3 | duplicate column 的**精确**异常；外层仍有 `except Exception` 兜底，收窄不会让导入期炸掉服务 |
| C 未知操作兜底 | DB 查询 / `zlib` 解压 / `_get_user` / redis ping | `Exception`（`sso.py` 为 `(zlib.error, ValueError)`）+ **补日志** | 5 | 这类无法预判具体异常类型，**保守做法是只从裸 `except:` 升到 `except Exception`**（拦住吞 `KeyboardInterrupt`/`SystemExit` 这一真正危害），并对"静默返回空/兜底值"的 3 处补 `warning`/`debug` 留痕 |

**关键设计判断**：裸 `except:` 的真实危害不是"捕获太宽"，而是**连 `KeyboardInterrupt`/`SystemExit` 一起吞**（二者继承 `BaseException`）。因此 C 类**刻意不硬收窄**——若强行猜具体异常，反而会把原本"静默降级"变成"直接 500"，制造回归。A/B 类才做精确收窄。

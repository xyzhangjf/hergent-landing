# 采购全流程：新建 → 审核 → 入库 → 付款/预付

> 设计 + 实现说明。2026-10-26 交付（v697）。口径由老板当场拍板：
> **预付走货款流水 / 仅已审待执行可预付 / 预付不设上限**。

---

## 🔴 v698 修订（2026-10-27）：v697 上线后老板反馈「看不到入口」

v697 的设计与代码都对，**但状态值是凭印象写的** —— 实测生产库才发现：

```
SELECT status, COUNT(*) FROM purchase_orders GROUP BY status
  → received=79, confirmed=2, draft=2, cancelled=1     （approved：0 张）
```

**生产真实的「已审待执行」是 `confirmed`（v417「保存并审核」定的），不是 `approved`。**
而 v697 判定写的是 `_st_v == "approved"` ⇒ 那 2 张已审单永远拿不到 `prepay`。
加上 `received_amount` 是 v403 才加的列、79 张舟谱导入的历史单全是 0
⇒ 「已到货」判据也不成立 ⇒ **付款 / 预付款 / 入库 三个入口在生产一个都不显示**。

比这更严重的是**后端自身**的状态机断裂：`purchase_order_confirm` 的守卫原本是
`status IN ('draft','approved')` —— **不收 `confirmed`** ⇒ 审核通过的单根本入不了库。
前端 `canConfirm` 与后端逐字对齐，所以按钮也不显示。不是前端写错。

v698 修法（详见 `tools/hergent/patch_v697c_confirmed_state.py`）：
① 两处入库守卫补 `confirmed`；② `pay_mode` 认 `("approved","confirmed")`；
③ 新增 `_po_received_amount()`：`received` 状态且 `received_amount=0` ⇒ 真值是订单金额
（**只对 `received` 兜底**，`partial` 不猜 —— 分批到货金额未知，猜就是造数）。

**教训（本仓最贵的一条）**：v697 那 24 项界面探针是**用 mock 数据跑的**，
全绿却没验到生产真实状态值。**凡是判定依赖枚举值的功能，验证必须落在真实数据上。**

## 一、五环节：前置条件、状态、入口

| 环节 | 页面与操作入口 | 前置条件（后端守卫） | 状态流转 | 副作用 |
|---|---|---|---|---|
| ① 新建 | 采购管理 › 新建采购单 | 采购写权限 | 空 → `draft`（金额 < 5000）或 `pending_approval`（≥ 5000，阈值取 `system_config.approval_threshold`） | 只落表头 + 明细。**不动库存、不动应付、不动钱** |
| ② 审核 | 采购单详情 › 顶部按钮（提交审核 / 通过 / 驳回） | `draft` 可提交；`pending_approval` 需当前节点 role（`approval_chain` 驱动） | `draft → pending_approval → confirmed`；驳回 → `draft`（🔴 v698 更正：落库是 `confirmed`，不是 `approved`） | 写 `audit_time` / `auditor_id` |
| ③ 预付 | **采购单详情 › 货款 ›「预付款」按钮** | `status ∈ {approved, confirmed}`（v698：生产真实值是 `confirmed`）+ 采购写权限 + 会计期间未关闭 | **状态不变** | `cash_flow` 一笔（category=`采购预付款`）+ `prepaid_amount` 累加 + 记账凭证 |
| ④ 入库 | **采购单详情 › 入库单 › 操作条**（v697 新增）<br>采购单详情 › 顶部「确认入库 / 分批到货」 | `status ∈ {draft, approved, confirmed, partial}`（v698 补 `confirmed`，与后端守卫逐字一致） | 整单全收 → `received`；分批 → `partial` → 到齐 `received` | `batch_in` 库存 / `received_amount` / `received_at` / **生成应付行** / 凭证 / 加权成本 |
| ⑤ 付款 | 采购单详情 › 货款 ›「付款」按钮 | 有应付行 + 未结 > 0 + 期间未关闭 | **状态不变**（`paid_amount` 只作标记，不参与状态机） | `cash_flow` 一笔（category=`采购付款`）+ 应付行 `paid_amount` + 凭证 |

### 状态 × 动作矩阵

| 单据状态 | 中文 | 可预付 | 可入库 | 可付款 |
|---|---|---|---|---|
| `draft` | 草稿（小额免审） | ✗ | ✓ | ✗ |
| `pending_approval` | 待审批 | ✗ | ✗ | ✗ |
| `confirmed` | 已确认（**生产真实的「已审待执行」**） | **✓** | ✓ | ✗ |
| `approved` | 已审待执行（兼容保留，生产当前 0 张） | **✓** | ✓ | ✗ |
| `partial` | 部分入库 | ✗（走付款） | ✓ | ✓ |
| `received` | 已入库 | ✗ | ✗ | ✓ |
| `returned` / `cancelled` | 已退货 / 已取消 | ✗ | ✗ | ✗ |

🔴 **`draft` 允许入库是既有设计，不是漏洞。** 建单时 `total < approval_threshold`（默认 5000）
直接落 `draft`，这类单没有审批链，只能从 draft 入库。**不要**为了字面上「已审核才能入库」
把守卫收紧成只剩 `approved` —— 那会让所有小额单永远进不了库，而且按钮是静默消失的。

## 二、付款与预付款的判定规则（唯一实现：后端 `purchase_order_payments`）

```
已入库金额 received_amount > 0 ?
├─ 否  → pay_mode = 'prepay'（货未到）
│        上限 = 订单金额 − 已预付     ← 仅作界面参考，**不拦**（老板定「不设上限」）
│        超付 = max(0, 已预付 − 订单金额)
└─ 是  → pay_mode = 'pay'（货已到）
         未结 = max(0, 入库金额 − 已预付 − 已付)
         超付 = max(0, 已预付 + 已付 − 入库金额)

状态 ∈ {cancelled, returned} 或 已结清 → pay_mode = 'none'（按钮不渲染）
```

三条铁律：

1. **模式由后端下发，前端不推导。** 前端只读 `pay_mode`。一旦前端也按 `received_amount`
   猜一遍，两处口径迟早分叉，出现「按钮写着预付款、后端回你状态不对」这种最难解释的错。
2. **未结金额必须减预付款。** `_po_unpaid` 是唯一算法，列表页 summary、货款页、付款接口的
   返回值全部走它。减之前：入库 2000、预付 500 时未结仍是 2000 ⇒ **会重复收款**。
3. **超付必须单独算（`_po_overpaid`）。** 未结用 `max(0, …)` 兜底、永不为负，好处是界面
   不会出现「−500」，坏处是**多付的钱被这个 max 吃掉了**。「不设上限」下这是必然发生的场景，
   所以单独算一个 `overpaid_amount` 并在货款页显式提示。

## 三、数据关联

```
purchase_orders(id) ──1:n── purchase_order_items        数量按折小单位入库（base_qty / base_ratio）
        │
        ├──1:0..1── receivables(type='ap', ref_type='purchase', ref_id=id)
        │              入库时生成；amount = 本次入库金额
        │              **paid_amount 初始化为当时的已预付额**（镜像，见下）
        │
        ├──1:n── cash_flow(ref_type='purchase', ref_id=id, type='expense')
        │            category='采购预付款' → 计入 purchase_orders.prepaid_amount
        │            category='采购付款'   → 计入 purchase_orders.paid_amount + 回写应付行
        │
        └──1:n── inventory / batch_trace（batch_in 写入，与库存同量纲）

prepayments 表**不参与**（那是按供应商的往来账余额，与本单预付是两个概念）
```

### 为什么要镜像预付到应付行

预付走 `cash_flow + purchase_orders.prepaid_amount`（不建预付款台账）。但往来账读的是
`receivables`。若不在它的 `paid_amount` 上镜像一笔，入库后会出现：

- 货款页：未结 ¥1,500
- 往来账：这笔应付还欠 ¥2,000

两处记账分叉，正是货款页那个黄色警告要报的错，而老板会真的不知道该信谁。
所以 `confirm` / `partial_receive` 建应付行时，把 `min(已预付, 应付金额)` 写进
`paid_amount`，状态置 `partial`（或 `paid`）。**只在首次创建时写**，后续到货不覆盖
（覆盖会把真实付款额重置回预付额，那是真丢账且不报错）。

### 为什么预付也记「应付账款」借方（2202）

看起来预付应记 `1123 预付账款`。但入库时 `auto_journal_for_purchase` 会贷 `2202` **全额**，
若预付记 1123，还得在入库时补一张「1123 → 2202」转账凭证，否则 2202 虚高、1123 挂一个
永远不平的余额。统一走 2202 时，「入库贷全额 − 预付借部分 = 真实应付」**自动就平了**，
不需要任何手工转账。小企业口径里这就是「应付账款借方余额」，报表读得通。

## 六、已知边界（诚实标注）

1. **预付不进 `prepayments` 表** ⇒ 往来账的「预付账款」在预付款台账里查不到，只能从
   货款流水（`cash_flow.category='采购预付款'`）看。这是老板选「走货款流水」的直接代价，
   换来的是不会出现两处记账。
2. **预付超上限的钱**会在货款页提示「已多付 ¥X，请向供应商追回或留抵下次货款」，
   但**不会**自动生成退款单或转账凭证 —— 后续动作是人的决定。
3. **入库单页的「分批到货」不展开表单**，而是跳回详情页并自动展开（那需要按商品逐行
   填数量、看明细表）。这是刻意不复制第二套表单：复制的那套迟早漏掉单位换算。
4. 预付接口的**期间门禁**与付款同一条（`check_period_open`，import 与 check 分开写，
   避免「关账被拒」被吞成「import 失败」）。

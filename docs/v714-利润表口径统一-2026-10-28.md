## 二、根因（四条，全部实测坐实）

### 1. 科目分类名对不上 ⇒ GL 分支从来没被走到（主因）

`get_pnl_gl()` 用 `get_account_codes_by_category("收入"/"成本"/"费用")` 取科目，但本账套
COA 的实际分布是：

```
资产 124   负债 69   权益 15   损益 109   收入 4   成本 9   费用 8   共同 5
```

**109 个损益科目的 `category` 是「损益」**，而唯一有发生额的 `6001 主营业务收入`（98,325.00）
就在这 109 个里面。于是 `revenue`/`cogs`/`total_expense` **恒为 0**：

```
改前 get_pnl_gl("2026-06") = {revenue: 0, cogs: 0, total_expense: 0, net_profit: 0}
改前 get_pnl_gl("2026-09") = 同上
改前 get_pnl_gl("2026-10") = 同上
```

路由的判据 `if gl and (gl.revenue > 0 or gl.net_profit != 0)` 因此**永不成立**，
一律回落 `db.get_pnl()`（现金制 + 业务表 + **不认月份**）⇒ 累计冒充当月。

### 2. `category='成本'` 把 5 开头的存货归集科目算进了营业成本

```
5001 生产成本 / 5101 制造费用 / 5201 劳务成本 / 5301 研发支出 / 5401 工程施工
```

这些是**资产性质**（生产成本要结转到库存商品），不是损益。隔离库实测：只要它们有余额，
老代码会把整笔算成营业成本（探针造 9,999 ⇒ `cogs = 9,999`）。

### 3. 父子科目一起加 + 净额方向只取单边

- P&L 科目同样有父子（`6051` 下挂 14 个、`6402` 下挂 24 个），与 v708 资产负债表是同一个缺陷。
- 收入只取 `SUM(credit)`、成本只取 `SUM(debit)` ⇒ **红冲/退货/冲销全丢**。

### 4. `net_profit` 里有一行死逻辑

```python
net_profit = gross_profit + (cat_sum(rev_codes, "credit") - revenue) - total_exp
#                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 而 revenue 就是这个表达式 ⇒ 恒为 0
```

## 三、改后口径（v714）

损益全集 = `code LIKE '6%'`，另以 `category='损益'` 补漏（补进来的非 6 开头科目进
`unclassified` 上报，**不静默吞掉**）。

| 组 | 科目 | 方向 |
|---|---|---|
| `revenue` 营业收入 | `60*` `61*` `63*`（主营/租赁/其他业务收入、投资收益、营业外收入） | credit − debit |
| `cogs` 营业成本 | `6401*`（主营业务成本） | debit − credit |
| `total_expense` 费用 | 其余 6 开头（`6402*` 客户费用、`6405` 税金及附加、`6411`/`6421`、`66*`、`67`/`68`/`69`） | debit − credit |

**为什么 `6402` 归费用而不是成本**：本账套 `6402 其他业务成本` 下面挂的是
「客户费用 / 月返 / 季返 / 陈列费 / 促销员工资 / 配送费 / 条码费」——实务上是费用。
只把 `6401` 当销货成本，毛利才有意义。

新增字段：

| 字段 | 含义 |
|---|---|
| `has_data` | 该月有没有损益凭证（路由靠它决定用 GL 还是回落） |
| `raw_net` | 全集原始净额（贷−借），**不分父子**，与 BS 的 `unclosed_profit` 同口径 |
| `source` | `gl` / `fallback_business_docs` |
| `unclassified` | 非 6 开头却进损益集的异形科目（正常为空，防口径漂移） |

**可跨表勾稽的判据**（比"看起来对"强得多）：

```
sum(get_pnl_gl(逐月).net_profit) == get_balance_sheet_gl().unclosed_profit
生产实测：98,325.00 == 98,325.00 ✓
```

> 符号同号：`unclosed_profit = -sum(debit-credit)`，收入类 `debit-credit` 为负，两者都为正。

### 按月回落

```python
if gl.get("has_data"):        return gl                      # 权责
cash = db.get_pnl(month)      # 该月业务单据
cash["basis"] = "cash"; cash["source"] = "fallback_business_docs"; ...
return cash
```

`db.get_pnl()` 新增可选 `month`（`cash_flow.created_at` / `sale_orders.order_date` /
`purchase_orders.order_date`）。**不带 month 时 SQL 与返回体逐字不变** ——
仪表盘 KPI、`/reports/daily`、月度快照都走这条。

判据也从「有收入或有净利」改成「有没有损益凭证」：旧判据在「有凭证但净额正好为 0」时
会误回落。

## 四、v715 前端：月份下拉真正生效

真机实测发现下拉**没绑 change**，且渲染函数每次重建 `<select>` 并把默认值写回当前月，
渲染后紧接着读 `P.value` ⇒ 用户选择必然被丢弃。**面板永远只能看当前月**。

不动 1.4MB chunk，在 `index.html` 内联注入（同 v712 手法）：

1. `window.__pnlMonth` 记住选择（null = 跟随默认，行为不变）
2. 事件委托监听 `#pnlGlMonth` 的 change ⇒ 记值 + `switchRptTab('pnl-gl')`
3. 包装 `window.api`，把 `/reports/pnl?month=` 换成用户选的月份
4. MutationObserver（observe `body`）+ 短轮询，把 select 显示值纠正回来

### 两个坑

- **内联脚本比 chunk 先跑**（`type="module"` 延迟执行）⇒ 执行时 `window.api` 还不存在。
  一次性取引用会拿到 `undefined`，之后 chunk 赋值又覆盖 ⇒ **静默失效**。必须轮询挂载。
- **不能 observe `#rptContent`**：本脚本执行时报表页还没创建那个容器，`getElementById` 得到
  null ⇒ observer 根本没挂上 ⇒ 数据是 6 月、下拉显示 10 月，**比不修更误导**。
  第一版就是这么错的，改成 observe `body` 后正常。

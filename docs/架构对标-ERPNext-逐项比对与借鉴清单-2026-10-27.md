# 架构对标 ERPNext v15 — 逐项比对与借鉴清单

- 日期：2026-10-27
- 我方基线：`/opt/hergent-erp`（生产后端，快照分析 352 个 py / 152,677 行）+ `hergent-cn-v2`（前端 273 个文件 / 103,891 行）
- 对标基线：本机 `~/frappe-bench/apps/erpnext` **v15.111.0**（658 个 DocType JSON / 21 个业务模块）+ `frappe` **v15.111.1**
- 方法：源码级静态测绘（不含猜测），每条结论都可在括号内的文件行号复核

## 0. 结论摘要（先看这一页）

**一句话**：我方是「手写 SQL + 手写页面的单体业务系统」，ERPNext 是「元数据驱动的通用单据引擎」。差距不在功能多少，而在**四个机制**：单据不可变、台账为唯一事实源、版本化迁移、模型即界面（元数据驱动）。

**最要紧的三个发现（都能直接对应到钱）**：

1. 🔴 **我方库存不是台账，是余额表直接加减**。`UPDATE inventory SET quantity=quantity+?`（`erp_db.py:3370`）共 **17 处**直接改余额，而写库存流水 `inventory_logs` 只有 **7 处** ⇒ 至少 10 条改库存的路径**不留痕迹**，无法回答"这 500 箱是怎么变成 320 箱的"。ERPNext 恰好相反：SLE 台账是唯一事实源，余额表 `Bin` 只是派生缓存。
2. 🔴 **我方没有"提交后不可改"这回事**。全库 `docstatus` **0 处**；状态字面量 **1,889 处**、`SET status='xxx'` **115 条**、**(列,值) 组合 45 种**；并且同时存在 **3 套互不相通的状态机**（各表 `status` 列 / `document_states`+`VALID_STATES` / v525 多级审批链）+ 1 个未接入的 `bpm_engine`。ERPNext 只有一套 0/1/2，且"取消"是**追加反向分录**，不是改原记录。
3. 🟠 **我方迁移不是版本化的**。Alembic 只有一个 no-op 版本（`alembic/versions/001_initial_stamp.py:24-27` `pass`）；真实结构靠 **349 次 `_safe_migrate` + 480 条 `ALTER TABLE` 在 import 期执行**；`CREATE TABLE` 393 次对应 281 个表名 ⇒ **45 张表被重复定义**（`inbound_orders` 4 次）；而租户库"拿到表、拿不到索引"已经**出过 3 次事故**（`db/indexes.py:48-88` 自己记着 v211 / v277 / v339）。

**优先级判据**：不是"哪个更先进"，而是**"卖客户之前哪一条会让人当场发现账对不上"**。按这个尺子，P0 只有 4 项。

## 2. 六维逐项比对

### 2.1 架构设计

| 项 | 我方 | ERPNext | 差距性质 |
|---|---|---|---|
| 模式 | 三层但**中间层被绕过**：`routers` 直接 `import erp_db as db`（86 个 router）；`db/queries` 号称 repository，但 routers 里另有 **743 处 `.execute(` / 556 处 `SELECT`** | Meta（模型）→ Document（行为）→ Controller 栈（横切能力：StatusUpdater→TransactionBase→AccountsController→StockController） | 分层名义存在、实际穿透 |
| 公共层 | `erp_db.py` **23,048 行 / 930 函数**，被 **125 个文件**引用 **968 个名字**；其中 86.4% 与"公共数据层"无关，按 v4→v692 版本号线性追加（`# vNNN` 349 处） | 无"万能门面"，能力按 DocType 与控制器分层继承 | 🔴 认知负担 |
| 循环依赖 | 8 个 `db/queries/*` 反向 `from erp_db import …`，靠函数内惰性 import 打补丁 | 无（单向依赖：framework → controller → doctype） | 🟠 |
| 扩展方式 | 改代码 + 发版（146 个 `vNNN` 工具脚本作证） | `doc_events` 钩子 / `Custom Field` / `Property Setter` / Workflow 配置，**不改代码** | 🔴 这是 SaaS 的关键 |
| 边界 | 一套 FastAPI 服务同时承载 ERP + AI 副驾 + 小程序 API + 招投标雷达 | 业务模块清晰（`modules.txt` 21 个），技术层（controllers/patches/public）单独抽离 | ✅ 可接受（我们是产品组合） |

## 3. 借鉴清单（按优先级）

**P0 = 卖客户之前必须修**（判据：会让账对不上 / 已被客户问住）；**P1 = 一个人能否持续维护**；**P2 = 工程卫生**。

### P0-1 单据三态不可变（docstatus 0/1/2）

| 项 | 内容 |
|---|---|
| **ERPNext 参考点** | `frappe/model/document.py:880-909`（迁移白名单：0→0、0→1、1→1、1→2，其余抛 `DocstatusTransitionError`）；`document.py:893-909`（每步一个权限点 submit/cancel）；`base_document.py:1054-1085`（`allow_on_submit` 字段白名单 + 旧值比对，越界抛 `Cannot Update After Submit`） |
| **我方现状** | `docstatus` 0 处；`SET status='xxx'` 115 条 / 45 种 (列,值)；3 套状态机并存 |
| **预期收益** | ① "已审单被改"这类事故从机制上不可能发生；② 取消变成可审计动作；③ 三套状态机归一到一处校验；④ 审批链、AI 留痕、审计日志有唯一挂载点 |
| **改造范围** | 表：约 30 张核心单据表加 `docstatus`（先 4 类：采购/销售/调拨/入库，约 12 张）+ 1 张状态迁移日志表。后端：新增一个 `post_document(doc_type, id, action)` 唯一入口，替换现有 115 处 `SET status`；`server.py` RBAC 中间件加动作映射。前端：单据按钮由 `docstatus` 派生（现在各页写 if）。数据迁移：一次性把现有 status 映射成 0/1/2（映射表要显式列出 45 种组合，不能猜）。**规模：大**，但可分批（一类单据一批，每批独立可回滚） |
| **风险 / 不可照搬** | ERPNext 的 cancel 依赖台账反向分录（见 P0-2），只做三态不做台账，取消仍然改不了库存真相 ⇒ **两项要一起上**，否则只得到形式上的不可变 |

### P0-2 库存台账（SLE），余额表降级为派生缓存

| 项 | 内容 |
|---|---|
| **ERPNext 参考点** | `erpnext/stock/stock_ledger.py:830-950`（每笔 SLE 持久化 `qty_after_transaction / valuation_rate / stock_value`，移动平均或 FIFO 滚动）；`:1712-1724`（`Bin` 由 SLE 末尾值派生）；`:1165-1183`（台账逐笔判负库存）；`:1883-1899`（取上一笔 SLE 时 `for update`） |
| **我方现状** | `UPDATE inventory SET quantity=quantity+?` **17 处**；写流水 `inventory_logs` 只有 **7 处** ⇒ ≥10 条路径不留痕；`cost_price` 存在余额表上，改价即改成本 |
| **预期收益** | ① 任何一箱货可追到"哪张单、谁、什么时候"；② 库存与成本可逐笔审计，**月结对平成为可能（这是卖前三关的第 1 关）**；③ 退货/调拨/盘点/报损统一走一个过账函数；④ 负库存可精确拦截 |
| **改造范围** | 新增 `stock_ledger_entries`（product/warehouse/batch/qty_after/valuation_rate/stock_value/ref_type/ref_id/is_cancelled）；新增 `post_stock_movement()` 唯一过账函数，替换 17 处 UPDATE；按日回填历史期初（用现有 `inventory_logs` 7 处可回填的部分 + 期末余额作期初快照）；`inventory.quantity` 保留但改为由台账重算的缓存。**规模：大（最大单项）** |
| **风险 / 不可照搬** | ERPNext 用 `FOR UPDATE` 锁台账；SQLite 无此语法 ⇒ 用**单写者事务 + 条件 UPDATE 乐观锁**（我们已在用，保留）。建议**影子模式**落地：新旧双写 2 周，每日跑一次「台账余额 vs 余额表」差异报表，差异为 0 再切换读路径 |

### P0-3 版本化迁移 + Patch Log

## 4. 明确**不建议**借鉴的 5 项（附理由）

| 不建议 | 理由 |
|---|---|
| **不引入 Frappe 框架本体** | 它是 Python 3 + MariaDB + Redis + RQ + 自研 ORM 的一整套运行时。迁过去等于把 15 万行重写，且 SQLite 单机部署优势（零运维、每租户一文件）全部丢失 |
| **不抄 `parent/parentfield/parenttype` 子表约定** | 我方 `xxx_items` + `order_id` 更直观、更省一次三元组查询；改造收益低、风险高 |
| **不上 RQ/Redis 任务队列与多 worker** | 我方瓶颈是 SQLite 单写者锁，不是吞吐；`scheduler.py` 30 个作业单线程跑得很好。上队列只会多一个故障点 |
| **不做 658 个 DocType 的全景建模** | 我方业务面窄（低温奶经销：采购/销售/库存/返利/报单/资金），元数据只服务档案类即可，不必把单据也元数据化 |
| **不照抄 `decimal(21,9)`** | SQLite 无 decimal，会退化成 REAL 亲和性，看起来改了其实没改。**整数分才是真解** |

## 6. 建议的执行批次

**批次 A（P0-3 + P0-4 前半，2 个独立小项）**：先做迁移版本化（风险最低、立刻止血），同时把"钱的三档精度常量"定下来（不改列，只统一写入点）。产出：`schema_patches` + `migrations/` + 精度常量模块 + 双算脚本。

**批次 B（P0-1 + P0-2，核心，必须同批）**：先在**采购/入库**一条链上落地 docstatus + SLE（选它是因为 v697/v698 已经踩过这条链的状态坑，且供应商侧数据量小）。影子模式双写 2 周，差异归零后再切读路径，然后复制到销售/调拨。

**批次 C（P1-1 试点 + P1-6）**：挑一个档案（供应商或商品）做元数据试点；同时把 9 个重复的汇总报表迁进注册表。这两项都是"加法"，不动存量。

**之后**：P1-2（工作流）→ P1-3（Custom Field，商业价值最高）→ P1-4（行级权限，受取数层制约）→ P2 按需。

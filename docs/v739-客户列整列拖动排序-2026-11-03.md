# v739 客户列整列拖动排序（2026-11-03）

## 1. 需求

> 为报单人列表增加整列拖动排序功能：支持将某一报单人的整列拖拽到其他报单人所在列的前面或后面，
> 并实现列的实时位置调整与顺序持久化。

澄清后确认目标界面 = **预报订单 › 汇总表的客户列**（`cross.units`：一列一个客户/报单对象，
列头显示报单简称）。这里一个报单人可能对应多列（他名下几家店各占一列），所以"整列拖动"
就是搬这一列，而不是搬一个人。

## 2. 交互契约

### ① 触发方式
在**客户列表头**上按下左键，**横向移动 ≥5px** 才进入拖动。

- 阈值是必须的：同一个表头格里还挂着「筛选 / ＋ / 改宽手柄」三个可点件。没有阈值时，
  一次普通点击的 1px 抖动就能被判成拖动 ⇒ 列莫名换位，用户根本不知道是自己碰的。
- 从这三个按钮上按下时**直接不接管**（`closest('button,.col-resizer')`）—— `@mousedown.stop`
  只挡 mousedown，挡不住 pointerdown。
- **改单态不接这套手势**：那里表头 mousedown = 「选中整列」（`onHeadDown`）。同一个手势
  既选整列又挪整列，两件事都会做不好。
- 触屏：`touch-action: pan-y` —— 横向手势留给拖动，纵向仍可滚页面。
- 键盘等价路径：列头可聚焦，**Alt + ←/→** 换一位（拖动对键盘/读屏用户不可达，必须有替代）。

### ② 放置位置判定（前 / 后）
只跟**左右相邻列的水平中线**比较：

- 指针越过左邻列中线 ⇒ 插到它前面（`cur - 1`）
- 指针越过右邻列中线 ⇒ 插到它后面（`cur + 1`）
- 其余情况 ⇒ 不动

一次只走一格 ⇒ 不会在两根列之间来回抖。"插到某人前面/后面"是这条规则的自然结果，
所以**不需要**再维护一个 before/after 状态（那种状态一定会和实际位置漂移）。

### ③ 拖动中的视觉反馈
三层，缺一层用户就会怀疑"到底动了没"：

| 层 | 表现 | 作用 |
|---|---|---|
| 源列表头 `is-drag-src` | 不透明度 .45 + 浅青底 + 2px 青框 | 一眼看到"在搬这一列、它现在落在哪" |
| 实时让位 | 被搬的列**真的**在数组里换了位置，表格当场重排 | 不是虚影，松手前就能看到最终结果 |
| 跟手胶囊 `.cust-drag-ghost` | 深青实底 + 白字 + `⠿` + 客户名，位置由 DOM 直改 | 横向滚很远也不会忘记在搬谁 |

另有：`body.cust-col-dragging` ⇒ 光标 grabbing、整页禁止选中。**Esc** 复位到按下前的顺序且不保存。

> 实现上用 **pointer 事件**，不用 HTML5 `draggable`：后者在"拖动过程中把这一列真的挪走"
> （实时让位）时会把拖动源从 DOM 里搬掉，手感一顿一顿地断掉。

### ④ 顺序的更新与保存
- 落位即更新 `cross.units`（**唯一数据源**）—— 表体格子、表尾合计、导出、复制报单全部跟着走；
- 同时写 `cfg.cust`（本次顺序的客户名数组）：localStorage 立即写 + 云端 `/api/ui/col-prefs`
  debounce 推送，并**立即 `flush()`**（拖完就切页也不丢）；
- 刷新 / 换设备 / 换人登录都按这套顺序（`ui_col_prefs` 是**租户级**，page = `forecast`）；
- 新出现的客户不在数组里 ⇒ 排**末尾**并保持服务端次序（稳定排序）。用户排好的那些一个都不动。

为什么不新建表：`ui_col_prefs.cfg` 存的是 JSON 原样，加一个键**零后端改动**，而且与
「列顺序 / 列可见性」同一语义、同一生命周期。它与「列方案」（`/api/forecast/column-schemes`，
具名多套、要手工点保存）是两条轴。

## 3. 顺带修掉的一个同源隐患（表尾合计按列号反推）

表尾客户列原本写的是 `footUnit((ci - 1) - visibleCols.length)` —— 用**列号算术**反推客户列下标。
这个写法依赖两个前提，现在两个都不成立：

1. 「空列不收起」：`showEmptyCols=false` 时 `colOrderList` 会比 `visibleCols` 少几列 ⇒ 下标偏移；
2. 「客户列次序固定」：v739 起用户可拖动换位。

任一漂移的表现都是**表尾合计整列错位**——数字还是数字，只是挂错了列，谁也不会报错。
现改为 `footUnitOf(col.key)` → `unitIdxOf(name)` 按**名字**取。

## 4. 验收

### 契约护栏 `tests/forecast-cust-col-order.contract.mjs`（接进 `npm test` 第 ㉕ 组）
六组：读写通道 / 列定位按名字 / 触发条件 / 放置判定 / 保存与取消 / 视觉反馈。
每条判据带**坏样本自证**；另做过一次**真实突变测试**（改回旧写法），护栏报出 4 条：
`loadCross 未经 orderedUnits`、`footUnit 退回列号算术`、`footUnitOf 不存在`、`松手不写库`。

### 生产实测（CDP 真实鼠标事件，1600×950，期次 42，23 个客户列）

| 断言 | 结果 |
|---|---|
| 第 1 列拖到第 3 列之后 | ✅ 顺序变为 2,3,1 |
| 列数不变 | ✅ 23 → 23 |
| 表尾合计按列名对得上（先证明本期有 4 个非空合计，避免空转） | ✅ 名→值 映射不变 |
| `cfg.cust` 已写云端 | ✅ `cust[0..3]=黄家伟,易胜琳,唐成,胡奎奎` |
| 刷新（完整重进）后顺序保持 | ✅ |

拖动中实测：`body.class="cust-col-dragging"`、`.cust-drag-ghost` 背景 `rgb(14,116,144)`

`docs/assets/v739/drag-ghost.png`。

部署：`index.html` md5 本地=线上，闭包 274/274 全 200。测试结束后已把顺序还原，探针会话零残留。

## 5. 已知边界 / 后续

- **改单网格内不提供拖动**（理由见 ①）。在汇总表里排好，进改单看到的就是同一套顺序
  （同一个 `cross.units`）。
- **导出 / 复制报单的列顺序随用户顺序**——这是刻意的（屏幕上怎么排、导出就怎么排）。
- 客户列目前**不能隐藏**（跨期名册刻意保留），所以"渲染列数 = units 长度"成立；
  `_custDropIndexAt` 已加等长校验，将来若给客户列加隐藏能力，会退化成"不响应"而不是"拖 A 动 B"。
- 若要按**报单人**整体分组拖动（一个人名下多列一起搬），那是另一套语义（需要在列头上做
  两行分组表头），当前未做。

## 三、顺带修掉三个**既有缺陷**（都不是本轮引入的）

### 🔴 缺陷 1：销售单列表的「下一页」一直是死的
- **根因**：`psi.py::psi_list_sale_orders` 与 `routers/sales.py::list_sale` **都没有声明 `offset`**，
  而 FastAPI 对未声明的 query 参数是**静默丢弃**的 ⇒ 前端 `next()`/`prev()` 只改页码文案、**内容不动**。
- **规模**：生产 tenant 1 有 **22505** 张销售单，用户实际只看得到最新 50 张。
- **旁证**：v443 当时**只补了 `limit` 这一半**，它在 `routers/sales.py` 里留下的注释就写着实测
  「`offset=100` → 与 `offset=0` **同一批** id」—— 取证早就有了，只是没顺手把 `offset` 补上。

### 🔴 缺陷 2：「订单」入口在**前端**剔退货行
- **根因**：`load()` 里 `if (_kindOrder) list = list.filter(r => r.status !== 'returned')` ——
  这是**在服务端分页之后**对本页 50 行做过滤。后果：① 每页显示不足 50 行，而 `total` 不减（用户按页数算总数会算错）；
  ② 上了服务端排序后更糟 —— 一页里被剔掉几行，排序结果看着就是断的。
- **修法**：改服务端 `exclude_status='returned'`（同一件事只有一个说法）。

### 🔴 缺陷 3：五个入口是「同 path 不同 query」，而 URL 只读一次
- **根因**：`_qType`/`_qKind` 原为 setup 里的一次性常量 ⇒ 从侧栏「自提订单」切到「车销订单」时
  **组件被复用、`onMounted` 不再跑** ⇒ 点另一个入口**页面纹丝不动**，且**零报错**。
- **修法**：改 `computed` + `watch([_qType,_qKind])`（与采购单页 `watch(kind)` 同款）。

## 六、诚实边界（必须说清的）

1. **生产未部署**（按您的要求本地待命）⇒ 服务端能力目前只由「本地库副本 + 生产真实数据（只读 SQL）」取证，
   **服务端尚未上线**。上线后建议再跑一次生产真机探针复核。
2. **tiebreaker 的必要性未能用数据复现**：在本地 300 行同值、生产 **22505 行同值**（`status` 全 `signed`）下，
   「不带 `, so.id DESC`」的分页拼接**仍然无重无漏**（SQLite 恰好走索引 `idx_sale_orders_status` ⇒ 顺序稳定）。
   ⇒ 记作**理论风险**（SQL 不保证同值行相对顺序），**不谎称已复现**。
3. 生产 25 个可排键里 **6 个是全同值 / 全 NULL**（`status` 全 `signed`、`delivery_date`、`approval_status`、
   `invoice_status`、`audit_time`、`discount`、`received_amount` 等）⇒ 前端点这些列表头**看不出顺序变化是数据事实**，
   不是缺陷。前端实际可排的 7 键里，`status` 与 `delivery_date` 属此类。
4. 本轮**没有**新增列（列设置仍是 7 列）。若您希望销售单列表像采购单那样有「数量 / 业务员 / 仓库 / 收货地址」等列，
   那需要后端补聚合子查询与 refs 映射，属**另一轮**工作。

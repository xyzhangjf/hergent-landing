## 二、口径：为什么只能有一个「源」

这条不变量是本轮全部设计的根据：

```
Σ比例 = Σ(数量ᵢ ÷ 总量 × 100) = 100 × Σ数量ᵢ ÷ 总量
⇒  Σ比例 = 100  ⟺  Σ数量 = 总量
```

**两者不是两条约束，是同一条。** 既然只有一条，就只能有一个源头；两个都当源头必然打架。

**数量是守恒侧，比例由数量反算。** 反过来「比例当源头」会破守恒——旧实现就是这么算的，且**零报错**：

> 总量 = 101、比例 33.33 / 33.33 / 33.34
> ⇒ `round(101 × 33.33 / 100, 3)` = 33.663 / 33.663 / 33.673
> ⇒ **Σ = 100.999 ≈ 101**（看起来对），但换成 Σ比例校验就是 100.999 ≠ 100

所以规则定为：

1. **谁被编辑，谁就是源** — 源侧**原样保留**，派生侧由源侧推出后**摊平四舍五入尾差**；
2. **尾差补给「小数余数最大者」，不是「最后一行」** — 固定补末行会让那行在用户没动它时突然跳一次；
3. **缺口绝不强行摊平** — 差额 > 人数 个最小单位 ⇒ **如实上报 gap**，让界面标红；
4. **容差必须小于摊平闸门** — 校验容差 `人数 × 0.0005` **<** 摊平的 `|差额| > 人数`（即 0.001），⇒ 过了校验的输入**一定摊得平**。

刻意**不**用教科书式「先下取整、再把缺的补齐」，差别在**什么都不用调的时候**：本写法在 Σ 已对得上时**一个数都不动**。

## 三、本轮修掉的两个真缺陷

### 🔴 缺陷一：「两个空值阴差阳错对上」⇒ 校验被静默空过

原判据只看「`target_qty` 字段在不在」：

```python
has_qty = any(a.get("target_qty") is not None for a in allocs)   # ❌
```

**目标量 = 0 且各人数量全 0** 时：`Σ数量 = 0 == 目标量 = 0` ⇒ 校验**通过**，但那是因为**两边都是空的**，不是因为算对了。

修法——判据**必须带分母**（前后端同一条）：

```python
_tgt = float(total_qty or 0)
has_qty = bool(any(_given)) and _tgt > 0     # ✅
```

前端 `qtyOk` 同步加 `qtyTotal.value > 0`。新增 B10/B11/E13b 三条护栏钉死。

### 🔴 缺陷二：写入口没有「库里两列必须自洽」的自身契约

`_write_allocs` 原来只保证「写进去的东西是调用方给的东西」，不保证「写完之后库里两列自洽」。修法两道护栏：

1. 若以数量为源落定后 `qty_ok=False`，**自动重试另一侧**（比例当源）；成功则落库 + `logger.warning`；
2. 两侧都不行 ⇒ **拒绝写入**（`HTTPException 422`，文案带 Σ 与目标量）。

护栏在 `DELETE` **之前**生效 ⇒ 原明细**一行不动**（有护栏用例专门先塞一行原样、再证明它还在）。

## 四、构建归因：证明「零夹带」

共享工作区风险很高——别人整包构建会带上**你的在途改动**，反之亦然。本轮做了完整取证：

1. **生产上线时刻** = `index.html` mtime **20:19:36**；
2. 工作区最后一个**别人**的在途改动 = `BidRadar.vue` **20:19:28**（早 8 秒）⇒ 那些 M 文件**已全部在 20:19 那次上线**；
3. `find . -newermt "2026-10-01 20:19:36"` ⇒ 之后被改的文件**只有两个**：`src/api/modules.js`（20:42）与 `src/pages/ProductTarget.vue`（20:43）——**就是我本轮改的**；
4. 构建时间 20:45 > 最后编辑 20:43 ✅ 中间产物在最后编辑之后重建。

**为什么不能用「文件名/内容都变了」判夹带**：hash 级联是**两级**的——改任一 chunk ⇒ `__vite__mapDeps` 变 ⇒ 入口 + 所有 importer 改名。本轮 30 个「生产无此名」的文件**内容也全部对不上**，这是级联的**必然**结果，不是源码变了。

**正确判据 = 时间轴取证**（谁在生产上线时刻之后动过工作区），而不是内容比对。

## 一、先说结论

「补销售出库」这个需求，侦察后发现真实问题**不是「少了一个扣库存的函数」**——
`fefo_deduct` 一直在，守卫也写得比一般系统严。真问题是三件：

| # | 问题 | 实测证据 |
|---|---|---|
| 1 | **`allow_neg_inv` 配了但没人读** | 该列自建库起就在 DDL 里（`DEFAULT '允许'`），生产 **11 个仓全部**取值 `'允许'`；但 `grep -rn allow_neg_inv server/` 匹配 **0 行** |
| 2 | **业务员仓的单一张也发不出货** | 仓 7（刘小顶仓）337 张、仓 9（刘善涛仓）2,213 张销售单，这两个仓 `inventory` **0 行** ⇒ 缺货检查恒失败 |
| 3 | **`inventory` 不是库存余额** | 22,505 张签收单批量导入时直接写 `status='signed'`，绕过 `sale_order_deliver`（`pick_waves` 0 行、`delivery_status` 全空串）⇒ 零出库流水 |

第 3 条才是「库存显示 310,409 却不是余量」的根因。

## 二、代码改动（4 处，`patch_v719_negative_stock.py`）

### 1. 新增 `_allow_neg_inv(dbc, warehouse_id)`

读 `warehouses.allow_neg_inv`，**fail-closed**：仓不存在 / 列读不到 / 值不认识 ⇒ 一律当「不允许」。
宁可拦住让人改配置，也不能让一个拼错的值悄悄放开负库存。

### 2. `fefo_deduct`：可售批次扣尽后允许扣成负数

```python
# 预检查
allow_neg = _allow_neg_inv(db, warehouse_id)
if total < qty_needed and not allow_neg:
    return {'error': ...}          # 未配「允许」的仓：一字未改，仍硬拦

# 批次扣完后
if remaining > 0:                  # 只有 allow_neg 能到这里
    # 差额扣进「未分批次」行（batch_no=''），没有就建一行负的
    # cost_price 取 products.purchase_price
```

**为什么必须真扣数而不是只记流水**：只记流水会让台账（`inventory`）与流水
（`inventory_logs`）对不上，等于把一个静默失效换成另一个。

**为什么 `cost_price` 不能用 0**：`domain/profit_reporter.py:98` 会按
`change_type='sale' AND ref_type='sale'` 聚合 `inventory_logs.cost_price` 算批次实际成本，
写 0 会让成本被低估。

### 3. `inventory_adjust`：两条支路去掉 `quantity>=0` 守卫

含「无库存记录」那条（原来直接 `return 库存不足`）。未配「允许」的仓仍走原守卫。

### 4. `sale_order_deliver`：缺货从「拦截」降级为「提醒」

```python
shortage_warnings = []
if shortage:
    if not _allow_neg_inv(db, o['warehouse_id']):
        return {'error': '库存不足', ...}   # 未配「允许」：语义零变化
    shortage_warnings = shortage            # 已配「允许」：照常发货 + 带回提醒
```

返回值新增 `shortage_warnings` 字段。

## 三、数据补记（`patch_v719b_stock_ledger.py`，两阶段）

### 阶段 1 `ledger`：补 v718 的欠账

v718 把 10 月 49 张采购单的 782 行明细聚合进 `inventory`，**一行流水都没写**。
实测 `inventory` 310,409 / `inventory_logs` 27,985 / 差 **282,424**。
后果：`get_inventory_aging()` 按 `change_type='batch_in'` 取最近入库时间算库龄，
这 282,424 没有入库时间 ⇒ aging 报表不可信。

补 **121 行**（`change_type='batch_in'`, `ref_type='v718_backfill'`），数量 282,434。
`before_qty` 是按「当前余额 − 本批数量」反推的近似值（v718 已合并，当时前后值不可还原）。

### 阶段 2 `outflow`：销售出库回补

口径（每条都实测）：

- 数量取 `COALESCE(NULLIF(base_qty,0), quantity)` —— v683 起发货按折小单位量扣；
  实测 142,859 行里**只有 1 行**有 `base_qty`，两口径差 **0.0**，对存量零影响
- **排除 `order_type='transfer'`**：251 张、276,541 数量（金额 0 但成本 55.16 万）
- 只认 `status IN ('signed','delivered')`：草稿单还没出货
- 退货（9,681 行负数量 / -87,629）**不单独处理** —— 它本来就是负数，SUM 自然抵消，
  等价于「退回来的货回到仓里」

结果：**568 行**（`change_type='sale'`, `ref_type='sale_history'`），数量 **-3,923,462**。

### 🔴 为什么「-361 万」是对的，不是坏了

- 它 = **「1-9 月进货单从未进系统」的量化**（销售净出库 3,923,462 vs 入库 310,409）
- 它与资产负债表 1405（**-631 万**）**方向一致**；而改前的 +310,409 与 -631 万
  **方向相反**，那才是最危险的状态：老板看库存表觉得有货、看资产负债表觉得缺货
- 补完进货（A2）后这个负数会自然收敛 —— 10 月 20 天的进货是 282,434，
  按同比例 9 个月约 380 万，与 392 万出库基本吻合

## 七、遗留

1. 🔴 **库存仍是负数，根因是 1-9 月进货没进系统**（A2）。补完后负库存会收敛到接近 0。
2. 🔴 **批次/效期仍无数据源**：10 月采购表 28 列里没有批次号/生产日期/到期日，
   销售明细批次 0 行。低温奶的先进先出与临期预警推不出来。
3. **1 行孤儿流水**：商品 2435 在仓 1 有一行 10 的 `opening`，但该商品已不存在
   （历史清理没删流水）。**不物理删** —— 删流水等于篡改审计痕迹。台账-流水差 -10 即此。
4. **`allow_neg_inv` 的取值是中文字符串**（`'允许'`/`'不允许'`），不是布尔。
   前端若有开关，要注意它写的是中文还是 1/0。`_allow_neg_inv` 已兼容
   `允许/是/1/true/allow/yes` 六种写法。
5. **库存页会显示 497 个负库存商品**，界面没有任何「这是因为进货没导」的说明。
   要让老板看懂，得在库存页加一句口径说明 —— UI 单点，建议单独一轮。
6. **`inventory_query` 用 `LEFT JOIN inventory ON product_id AND warehouse_id`**，
   同商品同仓多行会让商品重复显示。当前只有 1 组多行（带批次的），本次未加剧。
   补批次数据时要留意这一点。
7. `/opt/static` 无源码仓库，v712/v715/v717 的前端改动只在生产文件 + `.bak-*`。

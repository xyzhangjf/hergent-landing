### 8.1 高危 ① `period-close/status` 必崩 500 —— ✅ 已修复

**判据（先判断该列本不该存在，再动手）**：

| 证据 | 结论 |
|---|---|
| 建表语句 `v131d_accounting_periods` | 只有 `month / status / created_at`，**无 `closed_at`** |
| 全仓写入方 | **零个** —— `set_accounting_period` 只写 `month,status` |
| 关账判定 | `is_period_closed()` 读 `status == 'closed'` ⇒ 状态由 `status` 表达 |
| 真正的结转 | `db/queries/finance.period_close` 写的是 **`period_closures`** 表（与 `accounting_periods` 分家） |
| 前端 | `hergent-cn-v2/src` 内**既无 `closed_at` 引用、也无 `/api/period-close` 调用** |

⇒ **结论：这是个凭空造出来的列，不该存在** ⇒ 修法 = **改 SQL，不补列**（补一个永远为空的列等于造假字段）。

**改动**（`server/erp_db.py::period_close_status()`，单处函数）：

```python
# 修前
with get_db() as db:
    try:
        _ = db.execute("SELECT 1 FROM accounting_periods LIMIT 1").fetchone()   # ← 守卫只验「表在不在」
    except Exception as e: logging.getLogger("hergent").debug(...); return []
    rows = db.execute(
        "SELECT month, status, closed_at FROM accounting_periods ...",           # ← 在 try 外，直接崩 500
        (limit,)).fetchall()

# 修后
try:
    with get_db() as db:
        rows = db.execute(
            "SELECT month, status, created_at FROM accounting_periods ...",      # ← 去掉不存在的列
            (limit,)).fetchall()
        return [dict(r) for r in rows]
except Exception as e:
    logging.getLogger("hergent").warning(f"period_close_status 查询失败: {e}")   # ← warning，不再用 debug 吞
    return []
```

**顺带修掉「守卫形同虚设」**：旧 try 只包住 `SELECT 1 ... LIMIT 1`（**只验表、不验列**），真正会崩的 SELECT 在 try **之外** ⇒ 守卫一次都没起作用，且失败时用 `debug` 记录 = **把真实故障吞成静默失效**。现整段纳入 try 且改记 warning ⇒ **今后同类「列缺失」会降级返回并留下告警，而不是崩 500**。

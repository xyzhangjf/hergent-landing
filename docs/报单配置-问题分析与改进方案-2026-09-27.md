# 报单配置：问题分析与改进方案

> 日期：2026-09-27 ｜ 范围：`hergent-cn-v2/src/pages/ReportMapping.vue`（前端）+ `hergent-erp/server`（后端 + 小程序读端）
> 方式：**只读代码分析**，本轮未修改任何生产代码；所有结论均标注 `文件:行号`，可逐条复核。

---

## 0. 结论速览

1. **「一人多店」在数据层是支持的**（`report_mapping` 无唯一约束，一人可多行），但**「本人仓（调拨）」这条链路在小程序端整段缺失**——读端 `employee_stores_get` 只查 `contacts` 且排除 `self_warehouse`，写端 `create_submission` 用同一函数做 403 门禁 ⇒ **调拨单无法从小程序报**。这是「刘小顶只能报一个对象」的代码级根因。
2. **「单型」是只写不读的死字段**：真正决定「自提 / 调拨」的是 `counterparty_type`（`routers/forecast.py:1394`），`order_template` 整个后端零消费 ⇒ 手填的单型可以与实际生成的模板**互相矛盾**（UI 显示「调拨单」，模板却进了「自提订单」表）。所以问题 2 不只是体验优化，而是**口径打架**。
3. **「报单简称(列头)」有现成的权威名册可点选**：`all_units`（`erp_db.py:18028`，租户级历史列头名册，含「已删列」黑名单过滤）。当前是纯自由文本 ⇒ 拼写差一字就会**裂列且永不合并**（v247 已踩过同一坑）。
4. 顺带发现 **2 处代码级缺陷**：`GET /api/report-mappings` 的 `counterparty_type` **未参数化直插 SQL（注入）**；`源仓 / 目标仓` 两个选择器**同样零消费**（配了等于没配）。
5. 建议按 P0（本人仓链路 + 口径单一化）→ P1（可用性）→ P2（清理）三批落地，详见第 6 节。

## 1. 现状还原：报单配置到底影响哪些地方

先把「配了他到底管什么」画清楚，后面 4 个问题都挂在这张图上。

| 配置项 | 实际消费方 | 状态 |
|---|---|---|
| 员工 + 对象（门店 / 本人仓） | ① 小程序可报范围（`employee_stores_get`）② 舟谱模板「自提/调拨」归属（`forecast.py:1394`） | 门店 ✅ ／ 本人仓 🔴 只进②不进① |
| 报单简称(列头) | 汇总表列名（`report_column.py:33`）、Excel 导入改判（`import_router.py:858`） | ✅ 生效 |
| **单型** | **无任何消费方** | 🔴 只写不读 |
| 取价渠道 | 自提行取价（`forecast.py:1375` → `_template_price`） | ✅ 生效（仅自提） |
| **源仓 / 目标仓** | **无任何消费方**（`forecast.py:1313` 投影后即丢弃） | 🔴 只写不读 |
| 模板参数（公司/业务员/仓/序号/户头） | 舟谱模板业务列（`forecast.py:1419-1421` 等） | ✅ 生效 |

> 关键推论：**页面右边那张 9 列表格里，有 3 列（单型、取价渠道-for-本人仓、仓库）呈现的是「没有真实后果」的信息**——用户据此判断，会得到错误的心理模型。

## 2. 问题 1：同一用户无法同时报多个门店 / 多个对象

### 2.1 先说清楚：哪些是「支持」的，哪些是「断了」的

**✅ 支持的（已核实）**：配置层允许一个员工配多条映射。
- `erp_db.py:817-831` `report_mapping` DDL **没有任何 UNIQUE 约束**，全仓也搜不到针对它的 `CREATE UNIQUE INDEX`。
- `erp_db.py:6974-7019` `report_mapping_create()` 的查重**只查 `report_alias`**：
  ```python
  dup = db.execute("SELECT 1 FROM report_mapping WHERE report_alias=? AND is_active=1", (alias,)).fetchone()
  ```
  即：`刘小顶 + 美联保康 + 简称"美联"` 与 `刘小顶 + 本人仓 + 简称"刘小顶仓"` **可以并存**。

**🔴 断掉的（这是「不支持」的真正来源，共 4 处）**：

**断点 ①（致命）本人仓映射不进小程序读端**
`erp_db.py:18390-18405` `employee_stores_get()` 的并集**只从 `contacts` 取数**，且子查询把 `self_warehouse` 排除在外：
```sql
SELECT c.id, c.name FROM contacts c WHERE c.type IN ('customer','both')
  AND (c.is_active IS NULL OR c.is_active=1) AND (
    c.id IN (SELECT counterparty_id FROM report_mapping
              WHERE employee_id=? AND is_active=1
                AND counterparty_type IN ('store','customer'))   -- ← self_warehouse 不在内
    OR c.id IN (SELECT store_id FROM employee_stores WHERE employee_id=?))
```
而「本人仓」映射的 `counterparty_id` 存的是 **`warehouses.id`**（`erp_db.py:6990-6997`），根本不是 `contacts.id`。
⇒ **本人仓这条映射配了也永远不进小程序门店下拉。**

**断点 ②（致命）提交端同一函数做 403 门禁，直调 API 也过不去**
`routers/forecast_submissions.py:163-167`：
```python
allowed = db.employee_stores_get(emp_id) or []
if store_id not in allowed_map:
    raise HTTPException(403, "无权向该门店报单（不在你的报单范围）")
```
同一份「只有 contacts」的集合 ⇒ 就算绕过前端直调接口报本人仓，也是 403。

**断点 ③ 本人仓有前置依赖，未满足时该行根本建不出来**
`erp_db.py:6990-6994`：
```python
emp = db.execute("SELECT warehouse_id FROM hr_employees WHERE id=?", (employee_id,)).fetchone()
if not wh_id:
    return {"error": "该员工未配置本人仓（请在员工档案设置其个人仓后再映射）"}
```
❓**需确认**：刘小顶在「员工档案」里是否设了 **个人仓**（`hr_employees.warehouse_id`）。若没设，他在页面上连这条「自己仓」映射都存不下去——这恰好就是「不支持一人报两个」的最直观观感。
（前端同判据：`ReportMapping.vue:529-533` / `226-232`，未配置时显示红字「该员工未配置本人仓」。）

**断点 ④ 可用性：一人多行散落在列表里，看不出「这是一个人的两条」**
- 列表排序是 `ORDER BY id DESC`（`erp_db.py:6958`）⇒ 同一员工的多行**不相邻**；
- 平铺 9 列、无按员工分组、无筛选、无搜索 ⇒ 一人 3 个对象时要靠肉眼在几十行里找；
- 文档《新用户自主操作全流程.md:143-145》仍写着「**能。动作 B「门店」可勾选多家**」——那个「勾选多家」的入口已于 2026-09-19 移除（`employee_stores_set` 注释：`已无 UI 调用`），文档与现状**已经不一致**。

### 2.2 还有一个未被防住的真实风险：同员工 + 同对象可以配两条

查重只看 `report_alias` ⇒ `(员工, 对象类型, 对象)` 可以重复配。后果沿两条链同时炸：
- **舟谱模板**：`forecast.py:1357` 聚合键是 `(alias, entity)`，别名不同 ⇒ 同一门店被生成**两张单号不同的单**（重复下单）；
- **汇总表列头**：`report_column.py:51-61` 按 `counterparty_id` 取简称、`ORDER BY id LIMIT 1` ⇒ 小程序报的单只会落进「id 最小那条」的列，另一列永远空。

### 2.3 改进方案（问题 1）

| 优先级 | 动作 | 落点 |
|---|---|---|
| **P0** | 让读端下发「本人仓」对象：`employee_stores_get` 返回值增加 `kind`（`store` / `self_warehouse`），并集里补 `self_warehouse` 分支（取 `warehouses.name`） | `erp_db.py:18390-18414` |
| **P0** | 提交端门禁同步扩展：`allowed` 改为「contact_id 集合 ∪ 该员工本人仓 id 集合」，403 文案区分「门店 / 本人仓」 | `forecast_submissions.py:163-167` |
| **P0** | **必须同时给单加类型维度**：`forecast_submissions` 现有幂等键是 `(store_id, period_id)`。仓库 id 与客户 id 是**两套序列、可能撞号**，若直接把 `warehouse_id` 塞进 `store_id`，「门店5」与「仓库5」会被当成**同一张单**（互相覆盖）。建议新增 `store_kind TEXT DEFAULT 'store'` 并入唯一键与列名口径 | `erp_db.py:2020-2034` + `forecast_submissions.py:257-263` |
| **P1** | 前端对象下拉按 `kind` 分组显示（「门店」/「本人仓」），本人仓项加标签 | 小程序 `pages/fill/fill.wxml:1-9` |
| **P1** | 配置页加「按员工分组（可折叠）」或至少员工筛选 + 关键词搜索；列表排序改 `ORDER BY employee_id, id` | `ReportMapping.vue:131-161`、`erp_db.py:6958` |
| **P1** | `create`/`update`/`import` 三处统一增加「同员工 + 同对象类型 + 同对象」去重（返回可读错误） | `erp_db.py:6974` / `7022` / `7126` |
| **P2** | 更新文档 Q3（勾选多家的入口已不存在） | `新用户自主操作全流程.md:143-145` |

## 3. 问题 2：选「门店」应自动＝自提订单，选「本人仓」应自动＝调拨单

### 3.1 你的判断是对的，而且比体验问题更严重

**代码事实：`order_template`（单型）在后端零消费。**
全仓搜索 `order_template` 的消费点只有三处，**全是写入/回显，没有一处读取它做判断**：
- `erp_db.py:825`（DDL）、`6985/7011`（create 写）、`7057/7062`（update 写）、`7141/7163`（import 写）；
- `server.py:5510`（Excel 表头映射）、`5518`（表头必填校验）；
- `ReportMapping.vue:145/243`（列表展示 + 表单输入）。

**真正决定「自提 / 调拨」的是 `counterparty_type`** —— `routers/forecast.py:1394`：
```python
if g["cfg"] and g["cfg"]["type"] == "self_warehouse":
    db_groups.append(g)      # → 写进「调拨订单」工作表
else:
    zt_groups.append(g)      # → 写进「自提订单」工作表
```

所以当前会出现这种**用户无法理解的不一致**：

> 在报单配置里给「永辉东津店」填单型 = **调拨单** → 页面列表显示「调拨单」→ 但生成舟谱模板时它仍被放进**自提订单**表。

这不是显示问题，是**同一业务对象有两个互相矛盾的事实源**。

### 3.2 改进方案（问题 2）

**核心原则：单型必须由 `counterparty_type` 派生，而不是让用户手填。**

| 优先级 | 动作 | 落点 |
|---|---|---|
| **P0** | 后端三处写路径（create/update/import）**忽略客户端传入的单型**，一律按 `counterparty_type` 派生：`self_warehouse → "调拨单"`，其余 `→ "自提订单"` | `erp_db.py:6985 / 7057 / 7141`（在 `normalize_report_cp_type()` 之后统一派生，判据只写一份，建议新增 `report_order_template(ctype)`） |
| **P0** | 前端 `onType(t)` 切类型时**自动联动并置只读**：`form.order_template = t === 'self_warehouse' ? '调拨单' : '自提订单'`，输入框改 `readonly` + hint「由对象类型决定」 | `ReportMapping.vue:572-582`（`onType`）、`241-245`（输入框） |
| **P0** | 列表「单型」列改为**按类型派生显示**（不再直读可能已漂移的旧值）；对存量行做一次性清洗（把历史手填值刷成派生值） | `ReportMapping.vue:145`；数据侧一次性 `UPDATE`（属数据操作，需另行授权） |
| **P2** | 若将来确实需要第三种单型（如「访销单」），必须先有**真实代码分支**再开放可填，否则又会造出第二个死字段 | — |

> 说明：**保留 DB 列**（不删），因为 Excel 导入模板的表头契约里有「单型」是必填列（`server.py:5518`），删列会破坏存量模板兼容；改为「值恒等于派生值」即可。

## 4. 问题 3：「报单简称(列头)」是否应自动解析列头并让用户点选

### 4.1 结论：应该，而且系统里已经有这份名册

**为什么必须做**：简称是汇总表的**列主键**。用户自由输入时，`「东津店」` 与 `「东津」` 是两个不同的列，**永远不会自动合并**——这正是 `db/queries/report_column.py:1-21` 记录的 v247 事故（同一个门店被两种名字写过 ⇒ 列头裂成两列）。让用户「从已有列头里点」是唯一能**从根上**杜绝这类裂列的做法。

**可用的权威数据源（已存在，无需新建）**：
| 候选来源 | 位置 | 用途 |
|---|---|---|
| **已有汇总表列头名册** | `erp_db.py:18028-18033` 的 `all_units`（`forecast_submissions.store_name` 全历史去重，且已过滤 `forecast_hidden_units` 里被用户删掉的列） | 「点击即填」的主候选，保证与现有列**逐字一致** |
| 对象全称 | `report_mapping_refs()` 返回的 `contacts.name` / `warehouses.name` | 「用全称当简称」的快捷项 |
| 已被占用的简称 | `report_mapping.report_alias`（active） | 实时预警重复（现在是保存后才报错） |

### 4.2 改进方案（问题 3）

**交互**：把 `报单简称(列头)` 从纯 `<input>` 改成**可搜索 combobox**（页面里已有现成组件范式：`ReportMapping.vue:201-225` 的 `objCombo`，直接复用同一套键盘/鼠标行为即可）：

- 候选分组：**「已有列头」**（来自 `all_units`）／**「对象全称」**／**「自定义」**；
- 选中「已有列头」→ 灰字提示：**「将合并进现有列 "东津"（不会新建列）」**；
- 输入命中其它 active 映射的简称 → 红字：**「已被『张三 / 美联保康』占用」**（前端本地比对 `list.value` 即可，不必等保存）；
- 输入既不在名册、也不冲突 → 中性提示：**「将新建一列」**。

**后端配套（遵守「判据只写一份」的项目铁律）**：
1. 把 `all_units` 的 SQL **抽成 `db.forecast_unit_names()`**，让 `forecast_submission_summary` 与新端点**共用同一份实现**（否则会再造一条会漂移的 SQL，正是 `report_column.py` 文档里警告的「第二份口径」）；
2. 新增轻量端点 `GET /api/report-mappings/alias-candidates`，只返回 `{existing_columns: [...], used_aliases: [...]}`。
   ⚠️ **不要**让配置页去调 `/api/forecast-submissions/summary`：它受 `SUMMARY_ROLES` 门禁（`forecast_submissions.py:516`，配置员角色可能不在内）且要跑整张汇总，太重。

| 优先级 | 动作 | 落点 |
|---|---|---|
| **P1** | 抽取 `db.forecast_unit_names()` 单一实现 + 新端点 `alias-candidates` | `erp_db.py:18028`、`server.py:5436` 附近 |
| **P1** | 前端简称改 combobox（复用 `objCombo` 范式）+ 三态实时提示 | `ReportMapping.vue:235-240` |

## 5. 问题 4：布局 / 交互 / 数据逻辑 / UI 的其他问题

### 5.1 数据逻辑

| # | 问题 | 证据 | 影响 | 严重度 |
|---|---|---|---|---|
| D1 | **`GET /api/report-mappings` 存在 SQL 注入** | `erp_db.py:6957`：`w += f" AND counterparty_type='{counterparty_type}'"`，值来自查询串且**未做类型/白名单校验**（`server.py:5409` 只声明 `counterparty_type: str`，无 `int` 那类强校验），仅 `_auth()` 一道门 | 任意已登录（`data` 模块）用户可用 `' UNION SELECT ... --` 读**本租户库任意表**，包括 `hr_employees` 的 `id_card` / `bank_account`（PII / 银行账号） | **高** |

| D7 | 简称唯一性只在服务端保存时校验 | `ReportMapping.vue:621-630`（前端只校验非空） | 用户填完点保存才被拒，输入期无预警 | 低 |

## 7. 需你确认的项（无法单方面决定）

1. **刘小顶在「员工档案」里是否设了「个人仓」（`hr_employees.warehouse_id`）？**
   若没设，他这条「自己仓」映射**根本存不下去**（`erp_db.py:6990-6994` 直接返回错误）——这是「不支持」最直接的成因，需先补档案。
2. **「源仓 / 目标仓」到底该不该生效？**
   现状是零消费（调出仓恒 = 租户默认仓，调入仓由对象名/员工名拼）。两种收敛方向：① 让调拨模板真正读取它们（可能改变现有单据行为，**影响已上线流程，需谨慎**）；② 从 UI 撤下这两个字段（承认它无用）。**建议先做 ① 的影响面评估再决定**。
3. **本人仓接入小程序后，幂等键怎么定？**
   建议加 `store_kind`（`store` / `self_warehouse`）并入唯一键；若不加，仓库 id 与客户 id 撞号时「门店5」与「仓库5」会互相覆盖。这是数据模型改动，需你拍板。
4. **是否允许「同一门店由两人报同一期次」？**
   v224 已定为「一店一期一单」（键 `(store_id, period_id)`，与人不绑定）。本方案不改这条，仅确认它仍然成立。

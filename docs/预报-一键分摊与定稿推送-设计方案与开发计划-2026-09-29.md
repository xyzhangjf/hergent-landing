# 预报「一键分摊」与「定稿后推送加单/减单明细」——设计方案与分阶段开发计划

日期：2026-09-29　｜　读者：张俊峰　｜　性质：设计梳理 + 开发计划（本轮不改代码）

---

## 摘要（结论先行）

1. **一键分摊按钮：建议新增，但定位是「预演台」而不是新功能**——分摊算法（`plan_extra_allocs` + `algo.allocate`）和比例档案（`product_target_alloc.ratio`）**都已存在且可用**，缺的只是"在预报现场改比例 + 保存前看到分到谁"。当前要改比例必须跳到「商品目标」页，且分不满时界面**不点名**。
2. **「定稿键」有三个，用户想说的是「关闭期次」**——但**加单/减单通知目前挂在「保存汇总表」上**（v277 需求 7），而真正的「关闭期次（定稿）」**一条通知都不发**。这是需求 2 第一个要拍板的边界。
3. **🔴 存在一个必须先修的阻塞缺陷**：`_notify_extra_allocs` 用 `employee_id` 当收件人，而通知读端只认 `users.id`/`username` ⇒ **通知会送错人或谁都看不见，且零报错**。需求 2 建在它上面会直接继承这个缺陷（P0）。
4. **「通过小程序发送」目前无处可落**——小程序 10 个页面里**没有消息页**，而微信订阅消息对「工具→效率」类目**拿不到长期订阅**（`fill.js:57-59` 已明确记录）。要落地必须新建小程序消息页（P0），不能靠订阅消息。
5. 计划分 **P0（阻塞修复）/ P1（两个需求主体）/ P2（增强）** 三阶段共 7 项任务，每项附可失败的验收判据。

### 1.4 通知现状与一个阻塞缺陷

**通知基础设施（健全）**
- 唯一写入口 `db/queries/finance.py:1167` `message_send()`
- 去重键 = `title + msg_type + recipients`，窗口 86400 秒，**只对 `is_read=0` 生效**
- 读端 `routers/messages.py`（4 端点）；可见性 `_visible_where()` `messages.py:46-64`：
  - `recipients` 为空 = **广播**（全租户可见）
  - `recipients` 非空 = **定向**，只认 **`users.id` 或 `username`**（字符串化比对）

**🔴 阻塞缺陷：`_notify_extra_allocs` 的收件人键不匹配**

```python
# hergent-erp/server/routers/forecast_submissions.py:760, 773
uid = int(r.get("employee_id") or 0)          # ← 这是 hr_employees.id（员工 id）
if uid <= 0: continue
message_send(title, content, msg_type="notice",
             sender=operator or "系统", recipients=str(uid),   # ← 当作 users.id 用
             event_key="forecast_extra_alloc|%d|%s" % (int(period_id or 0), pid))
```

- `employee_id` 的来源已明证是**员工 id**：`routers/product_targets.py:162` 注释「`product_target_alloc.employee_id` 就是 employee id」
- 读端 `messages.py:54-64` 只把 `recipients` 与 `users.id` / `username` 比 —— **两把不同的键**
- 正确的同族实现（工资条，已被修过）在 `routers/salary_send.py:253-260`：
  ```python
  uid = int((db.employee_account_map().get(eid) or {}).get("id") or 0)   # 员工 id → 登录账号 id
  if uid > 0: db.message_send("工资条", msg, "info", recipients=str(uid), event_key="工资条")
  ```
  且该文件 `:235-237` 明确警告：`message_send` 第 4 位是 `sender`、第 5 位才是 `recipients`，**必须用关键字**。
- 而 `_notify_extra_allocs` 的 docstring（`:746-748`）仍写着「`recipients` 传的是 employee_id……与工资条 `salary_send` 同一用法」—— **这句话在工资条被修好之后已经过期**。

**影响（两条，都不报错）**
1. **送错人**：若某 `users.id` 恰好等于另一位员工的 `employee_id`，通知会落到**不相干的人**的收件箱（`users` 是主库全局 id，`employee_id` 是租户内 id，多租户下碰撞概率不低）。
2. **谁都看不见**：若无 user 命中该 id，通知行照常落库但**无人可见**。
- 唯一的"好消息"：它不是广播（收件人非空），所以**没有**把个人加单量全租户暴露——属于"静默错投"而非"静默泄露"。

**⇒ 这是 P0，必须排在需求 2 之前。**

### 1.5 小程序推送的现实约束（决定了"通过小程序发送"怎么做）

- 小程序页面清单（`miniprogram/app.json`）：`login / fill / mine / summary / password / forgot / no-permission / legal/privacy / legal/terms / privacy-settings` —— **没有任何消息页**。`message_center` 目前只有 Web 端 `NotificationPanel.vue`（顶栏铃铛）能看到。
- 微信订阅消息的硬限制（`miniprogram/pages/fill/fill.js:57-59` 原注释）：
  > 企微/站内信是**推出去**，而销售每天必开小程序 —— 这是**零授权、必达**的那一条（**微信订阅消息对「工具→效率」这类目拿不到长期订阅，只能一次性授权，不适合做系统主动催单的主渠道**）

- 通道能力现状（据项目通知中心知识库）：`notification_channels` 生产三库均空；**企微群机器人没有"发给某个人"的能力**（`touser` 对群机器人无效）⇒ 真定向的唯一路径是**企微自建应用消息**，前置条件（缺一不可）：① 企业微信后台建自建应用拿 `corpid`/`secret`/`agentid`；② `hr_employees` 需要新增**企微 userid** 列（**当前不存在**）；③ 员工档案表单加该字段；④ 渠道配置界面（当前不存在）。

**⇒ 结论：「通过小程序发送」= 新建小程序消息页读 `/api/messages`（P0），而不是订阅消息。** 已有可复用的成功先例：v304 的「本期报单进度提醒条」就是「零授权、页面内必达」的同款模式。

## 二、需求 1：一键分摊按钮

### 2.1 是否需要新增？—— 建议新增（定位：预演台）

**判据（三条，缺一即值得做）**

| 判据 | 现状 | 是否命中 |
|---|---|---|
| 能否在预报现场改比例 | 不能，必须跳 `ProductTarget.vue` | ✅ 命中 |
| 保存前能否预演"分到谁" | 不能，只有保存后的只读悬停 | ✅ 命中 |
| 分不满时界面是否点名 | 不点名，只有服务端 warning 日志 + `unassigned`/`ratio_gap` 字段（`forecast_submissions.py:1172-1180`） | ✅ 命中 |

**⇒ 三条全中，建议新增。但它不是"再发明一次分摊"** —— 算法一行都不用改，新增的只是「一屏预览 + 可编辑比例 + 实时校验」的界面层。这与「工具栏不新增按钮」的既有偏好不冲突：入口挂在**加单列的单元格菜单/角标**上，不加主工具栏按钮。

### 2.2 必须拍板的设计岔路：弹窗里改的比例，改哪一份？

| 方案 | 数据落点 | 影响面 | 前置条件 | 评价 |
|---|---|---|---|---|
| **A1. 改目标档案（推荐）** | `product_target_alloc.ratio`，走现有 `PUT /api/product-targets/{tid}`（`product_targets.py:531`） | **全期生效**；`_write_allocs` 会按新比例重算每人 `target_qty` | 无新表、无新接口，`_validate_allocs` 的 Σ=100 硬校验直接复用 | ✅ P1 首选。用户说的"**系统既定分摊比例**"在语义上就是档案里的比例 |
| A2. 仅本次加单一次性覆盖 | 需新增列（如 `forecast_extra_alloc.ratio_override`）或"本期分摊方案"表 | 只影响本期该商品 | 建表 + 改 `plan_extra_allocs` 取数优先级 | ⏳ P2。真实收益待验证，先不做 |
| A3. 两者并存（档案为默认、可临时覆盖） | A1 + A2 | 最灵活 | A1 + A2 全部 | ⏳ P2/P3 |

**推荐 A1 起步**。理由：① 幂等、有硬校验、零新表；② 用户原文「系统既定分摊比例」本就是指档案；③ 分摊结果与档案**永远同源**，不会出现"档案说 30%、本期却按 20% 分"的两套口径。

⚠️ **A1 必须显式告知的副作用**：改比例 = 改商品目标分解，**全期其余月份的加单也会跟着变**。弹窗里要有一行红字说明，且保存前二次确认。

### 2.3 交互逻辑

**入口（三处，同一弹窗）**
1. 加单(箱) 单元格 → 右键菜单 → 「按比例分摊…」
2. 加单(箱) 角标（`ptExtraMark` 渲染的「缺30 / 加6」）→ 点击
3. 已有「缺N」态时，角标文案引导："点此按占比分摊到人"

**弹窗结构（自上而下）**

```
┌─ 按比例分摊 · <商品名> ──────────────────────────── ✕ ┐
│ 本期加单总量  [  60 ] 箱   （= 240 包）                 │  ← 唯一可改的"总量"
│ ⓘ 比例来自商品目标分解；改动将同时更新该商品的目标档案    │  ← A1 的副作用告知
├──────────────────────────────────────────────────────┤
│ 承接人      占比%     本期报量(箱)   加单(箱)   定稿(箱) │
```

**三态角标（沿用现有 `ptExtraMark` 的三态语义，加一个"分不满"态）**

| 态 | 角标文案 | 触发条件 |
|---|---|---|
| 未分配 | `缺N` | 有目标 + 差额 > 0 + 无 `forecast_extra_alloc` 行（现状已实现） |
| 已分配 | `加6` / `减12` | 有 `forecast_extra_alloc` 行（现状已实现） |
| **分不满（新增）** | `加6 ⚠ 差3` | `fully_applied == false`，即 `unassigned > 0`（现状只在日志里） |

### 2.4 数据联动规则（写成"能失败"的形式）

设：总量 `D`（箱，可正可负）、第 i 人占比 `rᵢ`、本期报量 `bᵢ`、加单量 `aᵢ`、定稿量 `fᵢ`。

**正向联动（改总量 / 改比例 → 重算加单量与定稿量）**
1. `aᵢ = D × rᵢ / 100`（**绝对比例，不归一化**——与 `algo.allocate` 同一条规则）
2. `fᵢ = bᵢ + aᵢ`
3. 判据（能失败）：`|Σaᵢ - D| < 1e-6`。不成立即界面红字，不允许应用。

**反向联动（改加单量 → 回推比例）**
4. `rᵢ := aᵢ / Σa × 100`（整体归一化，保证 Σr = 100）
5. 判据（能失败）：改后 `Σr` 与 100 的偏差 `< 0.01`（与后端 `_RATIO_TOL` 同量级，`product_targets.py:409`）

**改单个人比例时的其余人处理**
6. 规则：**其余人按原相对关系等比缩放**，使 Σr = 100。
   - 例：3 人 10/40/50，把第一人改成 20 ⇒ 其余 40/50 等比缩放为 32/48（保留 4:5 的相对关系）
   - 判据（能失败）：缩放后各 `rᵢ ≥ 0` 且 `Σrᵢ = 100`；若某人为 0 则等比缩放无法完成 ⇒ 退化为"差额全部由最后一人承担"并给出提示
7. **禁止**：允许"改 aᵢ 而不改 rᵢ"从而造成 `Σaᵢ ≠ D`。二者必须同时收敛（由 4 + 6 保证）。

**减单的夹断规则（必须原样复用后端语义，前端不得另写一份）**
8. 减单时 `aᵢ = min(|D| × rᵢ/100, bᵢ)` 后取负；被夹掉的缺口在**还有余量的人之间**按相对占比重分。
9. 🔴 **前端不得重算夹断/重分**，必须与 `algo.allocate` 同源。判据（能失败）：用同一组输入分别调 `/api/product-targets/extra-alloc` 与前端预览函数，逐人 `alloc_box` 差值 `< 1e-6`（这是本项目反复栽的"同屏两个同名数对不上"）。**推荐实现：弹窗预览直接调一次后端 dry-run 接口，不在前端实现 allocate。**

**单位联动**
10. 加单量主单位 = **箱**；同步显示小单位（包）换算值 —— 依据用户原文「加 6 箱即 48 包」。判据：换算比值取自 `products.large_ratio`（唯一权威），不得前端硬编码。

### 2.5 实现要点

1. **不改 `algo.allocate`、不改 `plan_extra_allocs`** —— 复用，别重写。
2. **预览必须走后端**：新增只读预览端点（如 `POST /api/product-targets/extra-alloc/preview`），入参 `{period_id, product_id, total_delta, ratios[]}`，内部调 `allocate()` 返回 rows。**理由**：前端另写一份 allocate 一定会漂移（夹断/重分是边界敏感的）。
3. **比例保存走档案**：`PUT /api/product-targets/{tid}`，`allocs` 传全量（`_write_allocs` 是整体替换），保持 `sort_no` 顺序稳定。
4. **落库时机**：比例改动**立即写档案**（因为它是全期属性，不应被"取消保存汇总表"回滚）；加单量仍随 `save-matrix` 落 `forecast_extra_qty` / `forecast_extra_alloc`。
5. **权限**：与 `product_targets` 写权限同源（该路由挂 `data` 模块，见 `forecast.py:525` 同类注释）。前端按钮按角色/`periodClosed` 双重收口（复用 `Forecast.vue:3823-3887` 的 `periodClosed` / 锁定判据，别新造一把尺子）。
6. **撤销栈**：若比例改动进入编辑态，须并入既有 `_pendingCell` 撤销栈（否则 Ctrl+Z 还原不了，重演 `Forecast.vue:1155-1160` 记录过的"商品名改了还原不了"那类缺陷）。**推荐：比例改动不进撤销栈，改为"立即写 + 弹窗内二次确认"**，语义更清楚。
7. **全角容错**：占比输入框必须走既有的 `numInput()` / `parseNumInput()`（`Forecast.vue` 同类实现），支持中文输入法全角数字与「。」—— 这是本项目数字格的既有铁律。

### 3.1 「定稿键」的准确位置与标识

### 3.2 必须先拍板的边界：推送出口放在哪

| 方案 | 做法 | 优点 | 风险 | 评价 |
|---|---|---|---|---|
| **甲（推荐）** | `close_period` 成为**唯一**推送出口；`save-matrix` **停发**通知 | 语义正确（定稿后才通知）；避免"草稿被改一次就发一次"；数据已就绪（`forecast_extra_alloc` 按 `period_id` 直接可读） | 删掉 v277 的现有行为，需用户确认 | ✅ 与用户需求原文一致 |
| 乙 | 双轨：`save-matrix` 发"草稿版"、`close` 发"定稿版" | 改动小 | 业务员收件箱被刷屏；两份口径易混 | ❌ 不推荐 |
| 丙 | 维持 `save-matrix`，只把确认弹窗挂到「保存」按钮上 | 改动最小 | 与「定稿」语义不符；保存是高频动作，每次都发通知是噪音 | ❌ 语义错位 |

**推荐甲。** 且甲有一个实现上的便利：关单时**不需要重算分摊**，直接 `SELECT * FROM forecast_extra_alloc WHERE period_id=?` 就是最终态。

**甲的幂等细节（必须处理）**：现有 `event_key = "forecast_extra_alloc|<period_id>|<pid>"`，而去重窗口是 86400 秒且只对未读行生效。若经理"关单→重开→再关"，第二次会被**折叠进第一条**（`dup_count+1`）。两种处理：
- (a) `dedup_window=0`（逐条落库，牺牲去重）
- (b) `event_key` 里带一个"定稿轮次"（如 `period_confirm.rev` 或 `reopen` 计数）
**推荐 (b)**：既保去重，又能让重开再定稿产生一条新通知。

### 3.3 交互流程（确认弹窗）

**入口：点击「确认关闭」之前（或之后紧接）**

```
┌─ 确认定稿 · <期次名> ─────────────────────────────── ✕ ┐
│ 本次将定稿的加单/减单明细：                              │
│                                                          │
│  商品            加单/减单   涉及   合计(箱)             │
│  蒙牛真果粒…     ↑ 加单      3 人    +60.000             │
│  蒙牛纯甄…       ↓ 减单      2 人    −12.000             │
│                                                          │
│  ▸ 展开逐人明细（刘善涛 +6.000 / 王丽 +24.000 / …）      │
│                                                          │
│ ⚠️ 定稿后修改内容将发送给相关人员（共 5 人），            │
│    且该期次不可再编辑、销售的小程序报单通道同时关闭。     │
│    如需改动，可到「往期预报」点「重开」恢复。             │
├──────────────────────────────────────────────────────────┤
│                          [取消，继续修改]  [确定定稿]     │
└──────────────────────────────────────────────────────────┘
```

**交互规则**

| 动作 | 行为 |
|---|---|
| 点「确定定稿」 | 调 `POST /periods/{pid}/close` → 后端读 `forecast_extra_alloc` → 逐人 `message_send` → 返回 `{success, notified}` → 前端 toast「已定稿，已通知 N 人」 |
| 点「取消，继续修改」 | 关闭弹窗，**留在编辑态**，不改期次状态、不发通知 |
| 明细为空 | 弹窗仍出现，一行「本期无加单/减单，定稿后不发送通知」——**不要静默跳过**（否则用户不知道"为什么没人收到"） |
| 有商品分不满（`fully_applied=false`） | 明细里该行标黄「未分满：占比缺口 X 箱」，并提示可先去分摊弹窗修比例 |
| 通知发送失败 | **不得回滚定稿**（定稿已成功）。改为提示「已定稿，但通知发送失败（N 条），请检查员工账号关联」，并写 warning 日志 —— 与 `forecast_submissions.py:1200-1209` 既有纪律一致 |

## 四、功能边界（明确不做什么）

| 不做 | 理由 |
|---|---|
| 跨期次分摊 | 归属键是 `period_id`（v279 已定），跨期会重演"窗口当主键"那类串期缺陷 |
| 按门店 / 按历史销量自动分摊 | 比例只来自目标档案，多一个来源就多一套口径 |

| 在报价弹窗里重写一份前端 allocate | 必然与后端漂移（见 §2.4 第 9 条） |
| 改 `save-matrix` 的加单落库逻辑 | 本次只调整"通知出口"，不动数据写入 |

## 七、风险与诚实边界说明

1. **P0-1 是真缺陷，不是我推测**：写端传 `employee_id`、读端比 `users.id`/`username`，两把键不同；工资条同族缺陷已被修复（`salary_send.py:253-260`）并有明确事故记录，`_notify_extra_allocs` 是**漏修的那一处**。
2. **"通过小程序发送"目前不成立**：小程序无消息页、订阅消息拿不到长期授权。P0-2 是前置条件，不是可选项。
3. **一键分摊不会让分不满消失**：它只是把"分不满"从日志搬到界面上。真正的成因（占比合计 < 100%、报量不足需夹断）仍需经理决策。
4. **P1-1 停发 `save-matrix` 通知会改变现有行为**（v277 需求 7）。若你希望保留"保存即回执"，应明确改为**双轨**并接受刷屏，或改为"仅当本次保存改变了分配结果才发"——三种都行，但不能不定。
5. **企微通道不在本轮**：群机器人无定向能力是硬限制，真定向要自建应用 + 新列 + 新界面，属独立项目。
6. 本轮为**只读梳理**，未改动任何代码、未部署、未执行任何 git 写操作。

> 日期：2026-09-14
> 范围：多租户场景下如何采集各租户的行业 know-how，使 hergent 越用越聪明
> 性质：**设计分析（只读勘察，未改任何生产/本地代码）**
> 勘察对象：`~/Documents/hergent-erp`（后端，HEAD 工作区）、`~/Documents/laozhangai-product/hergent-cn-v2`（前端）

## 结论（先讲结论）

**不新建"知识采集系统"。hergent 已经有 5 条经验沉淀管道和 8 张相关表，但它们是断的 —— 缺三个接口件，接上就是闭环。**

三个断点，按价值排序：

| 断点 | 现象（代码证据） | 代价 |
|---|---|---|
| **① 只知道"采纳/驳回"，不知道"改成了什么"** | `ai_advice_log.modified_by_user` 只存**人名**（`erp_db.py:15214`），不存用户改后的值 | 经销商 90% 的 know-how 藏在"AI 说 7 天、我改成 5 天"这个 Delta 里；没有 Delta，只剩一个点赞率 |
| **② 采集靠"等人来报"，不是"系统自己发现"** | `recipe_proposals` 只在 AI/人工主动调 `POST /api/ai/recipe-proposals` 时才落行（`recipe_evolution.py:118`），无"同类覆写重复 N 次 → 自动提案"的触发 | 采集率取决于用户勤快程度，必然趋近 0 |
| **③ 跨租户真值共享，且是"一对一"不是"多对多"** | `recipe_sync.py` 把**带租户真值**的 AUTO_RECIPE 块写进同一份 `/root/.hermes/skills/hergent-milk-*/SKILL.md`，且服务侧调用 `trigger_sync_from_service()` 不带 `--tenant-id`（`recipe_sync.py:264`），退化为**恒取 tenant 1** | 单租户下无害；第二个真实租户上线当天即互相覆盖/串味 |

**另有一处必须清理的既有实现**：`routers/ai_learning.py` 号称"自动学正则"，但它的 SQL 读的是 `llm_calls_log` 的 `prompt` / `tool_used` 两列 —— 而该表只有 9 列（`erp_db.py:14146`）**两列都不存在** → `/api/ai-learning/analyze` 与 `/stats` 必然 500，是死代码；其 `/approve` 更会把学到的正则**追加写入全局 `/opt/hergent-erp/server/routes.py`**（`:121`），属跨租户代码级注入。

## 一、采集方式与数据来源

### 1.1 四层采集（按对"越用越聪明"的贡献度排序）

#### L1 显式反馈层 —— 最高价值，最小改动

- **数据来源**：副驾建议卡的「采纳 / 驳回」
- **现状承载**：`routers/ai_assist.py:756 POST /advice`（落 pending）、`:787 POST /advice/{id}/decide`（落 decision）；前端 `components/ResultCard.vue:126`、`components/AdvicePanel.vue:23`、`composables/useCardTrigger.js:330`
- **要采集什么**：把二值反馈扩为三值 —— `采纳` / **`改后采纳`** / `驳回`，并把**改后的值**一起落库
- **落点**：`ai_advice_log` 扩两列 —— `user_value TEXT`（用户改后的值，JSON）、`delta_kind TEXT`（`none`\|`override`\|`refine`）
- **为什么这是第一优先**：这是唯一一个**用户主动告诉你"AI 错在哪"**的信号，成本 = 用户多点一次，信息量 = 一条可直接固化的口径

#### L2 行为隐含层 —— 不需要用户额外动作，采集面最广

| 来源 | 位置 | 采集什么 |
|---|---|---|
| A 配方覆写 | `loss_workflow` / `payroll_workflow` / `forecast_config` 的 PUT；已由 `record_recipe_audit()` 捕获 | 旧值 → 新值（**已有**，只是没进"经验池"） |
| B 导入纠错 | `import_router.py` 预检 warnings / `Forecast.vue::onImportFile` 未读 `validation.warnings` | warnings 被无视的比例 + 被人工改写的字段分布 |
| C 报单人工修正 | Forecast 汇总表的 AI 建议安全库存 vs 最终下单量 | 建议值与终值之差 |
| D 口径冲突裁决 | 返利/货损同屏两口径打架时用户选了哪个 | 裁决方向 |

- **关键工程约束**：L2 的 A 项**已经在写 `audit_logs`**，本方案**不新增写路径**，只新增"把这条审计行再投影一份进经验池"的派生步骤 —— 符合"同一件事只写一遍"的铁律

#### L3 对话语义层 —— 价值中等，必须脱敏后才可用

- **数据来源**：副驾会话文本（生产在 `~/.hermes/state.db`；hergent 侧经 `hermes_core` 走自有 AI loop，与 Hermes 进程版本解耦）
- **采集什么**：只抽取**结构化片段**，不落全文 ——
  - 口径声明（"我们这边临期按 5 天算"）
  - 阈值声明（"提成从 3 个点提到 3.5"）
  - 例外声明（"某某类商品不算返利"）
- **与 L1/L2 交叉验证**：对话里声明了 7→5，且 L2 也观察到同一参数的覆写 → 升级为**高置信经验**（单来源 = 低置信，只入池不提案）

#### L4 跨租户匿名统计层 —— 长期价值最高，合规要求最严

- **采集什么**：只采集**分布**，不采集**值** —— 如"临期阈值在同类经销商中的分位分布"
- **输出形态**：**区间提示**，不暴露任何单租户真值 —— "同类经销商多设在 5–7 天，你当前 7 天"
- **准入**：仅授权了"行业共享"档位的租户贡献；k-匿名 ≥5 才允许输出

### 1.2 采集触发点与改动量（只加列/加函数，不加业务流程）

| # | 触发点 | 代码位置 | 采集什么 | 改动量 |
|---|---|---|---|---|
| 1 | 采纳/驳回 | `ai_assist.py:787` | `user_value` / `delta_kind` | 扩 1 列 + 前端传值 |
| 2 | 配方保存 | `record_recipe_audit()`（已有） | 旧→新 diff | 转发到经验池（**不新增写入**） |
| 3 | 导入预检 | `import_router` / `Forecast.vue` | warnings 是否被无视 | 加 1 条埋点 |
| 4 | 建议生成 | `ai_assist.py:756` | 建议类型 + 置信度 + 上下文档位 | 已有，补 `task_type` 粒度 |
| 5 | 会话结构化 | `hermes_core` 输出后置钩子 | 阈值/口径/例外陈述 | 加 1 个抽取函数 |
| 6 | 周度聚合 | 复用现有 cron 体系 | 由 L1/L2 生成 `recipe_proposals` | 加 1 个 job |

⚠️ **触发点 6 的硬约束**：hergent 的 cron 目前经 `routers/cron_tasks.py:13` 硬编码 `sudo .../hermes_cron_bridge.py`，而该脚本在生产 Hermes v0.19.0 之外的新版本中**已不存在**（详见 `docs/hermes-update-monitor/2026-09-14.md` 耦合点③）。**新增 job 不要挂到这条链路上**，改用后端自有的任务调度（或先修桥接），否则今天写完、升级日全挂。

### 1.3 双写落点：租户真值留租户库，只有去标识条目进主库

```
租户库（含真值，属租户数据，不跨租户）
  ai_advice_log（扩列）        ← L1 raw
  experience_events（新表）     ← L1+L2+L3 的原始事件
  recipe_proposals（已有）      ← 聚合产物，待审批

主库（跨租户，只放去标识条目）
  experience_atoms（新表）      ← 一条经验 = 白名单字段 + 量级桶 + tenant_hash + source_ref
  audit_logs（已有）           ← module='experience' 记录 贡献/消费/撤回
```

`experience_events`（租户库，原始层）：`id / kind(advice_delta|recipe_override|import_ignore|dialog_claim) / param_key / value_from / value_to / task_type / source_ref / created_at`
`experience_atoms`（主库，去标识层）：`id / param_key / value_bucket / kind / tenant_hash / k_support / status(candidate|verified|retired) / source_ref_hash / created_at / consent_basis`

**铁律**：`experience_atoms` **不存 tenant_id 明文、不存原始数值、不存任何标注为敏感的参数**（见 §2.3）。跨租户读取入口**唯一**，且必须经 `_platform_admin()`（独立名单表），**绝不复用 `_auth` / `_admin`** —— 后者只判 `role in (admin, boss)`，而每个自注册用户都是 boss。

### 1.4 从"采集"到"越用越聪明"的四级提升回路

| 级别 | 机制 | 生效范围 | 风险 | 依赖 |
|---|---|---|---|---|
| **R1 本人复用** | 同租户下次遇同类场景，副驾直接引用本人上次的选择 | 本租户本人 | 0 | L1 |
| **R2 本租户配方固化** | 同类覆写重复 ≥3 次 → 自动生成 `recipe_proposals` → 审批 → `recipe_sync` → skill | 本租户 | 低（有审批） | L1+L2 |
| **R3 同型租户推荐** | 跨租户分位 → 区间提示 | 单租户（读提示） | 中（需授权+k≥5） | L4 |
| **R4 行业 skill 升级** | 被 ≥3 租户验证过的口径 → 写入 skill **正文**（非 AUTO_RECIPE 块）→ 全体受益 | 全平台 | 中（须人审） | R3 |

⭐ **R2 是投入产出比最高的一级**，且完全复用了已有的 `recipe_proposals` → `recipe_sync.py` 管道，只需补"自动发现"（断点②）与"租户维度隔离"（断点③）。

## 二、合规：授权、隐私、脱敏、租户隔离

### 2.1 定性：这是**商业秘密**问题，不是个人数据问题

经销商的经营参数（临期阈值、提成率、返利口径）**不是个人信息** —— so 合规主线是：

| 法条域 | 管什么 | 本方案的对应 |
|---|---|---|
| 《反不正当竞争法》第 9 条 + 服务合同 | **商业秘密**：不得披露、不得让竞争对手获取 | 跨租户层只放**量级桶**、不放真值；k-匿名 ≥5 |
| 《个人信息保护法》 | 员工、客户等**自然人**信息 | **全量排除**（见 §2.3 红线） |
| 《数据安全法》 | 数据处理活动的授权与留痕 | `user_consents` 双档位授权 + `audit_logs` 留痕 |
| 与客户的**服务协议** | 谁拥有数据、可否用于"改进服务" | 需在协议里写明"用于匿名改进产品"并给**撤回权** |

**一句话**：合规的靶心是"**不让 A 经销商从 B 经销商的参数里获利**"，而不是"删掉人名"。

### 2.2 六道闸门（按数据流顺序，每道都要有可验证的落点）

**① 授权闸门 —— 双档位，不做一揽子同意**
- 载体：`user_consents` 扩 `consent_type='industry_learning'`
- **档位 A「本租户内自动固化」**：默认开（属基础服务能力，数据不出租户库）
- **档位 B「行业匿名共享」**：**默认关**，需显式勾选，才允许把去标识条目写入主库 `experience_atoms`
- 撤回：切换档位 B → 触发 §2.2⑥ 的撤回流程
- ⚠️ 现状 `gdpr.py` 的 `/consent` 只记录"同意"、不记录"哪一档"、也没有撤回 → 需扩

**② 最小化闸门 —— 白名单 + 显式拒绝清单**
- 落库前必经 `_scrub_experience(atom)` 校验器：**命中拒绝清单 → 丢弃并计数上报**（不是静默过滤，否则又是"零值即健康"陷阱）
- 白名单（只有这些能进跨租户层）：`param_key` 类 —— 临期阈值 / 效期安全天数 / 补货周期 / 安全系数 / 计价口径 / 舍入模式 / 阶梯计法 / dimension 枚举
- 拒绝清单：见 §2.3

**③ 去标识闸门**
- `tenant_hash = HMAC-SHA256(server_secret, tenant_id)`，主库不存明文 id
- 数值**离散化**为分位桶（`5–7_DAYS`、`3–5_PCT`），不存 `5` 或 `3.5`
- **k-匿名 ≥5**：任一取值桶若来自 <5 个租户，则不进基准输出（阈值可配，须落在配置表而非硬编码）

**④ 隔离闸门（读方向）**
- 跨租户读**唯一入口** = `_platform_admin()`（独立名单表）；**禁止**复用 `_auth` / `_admin`
- 跨租户写**唯一入口** = 一个封装好的上下文切换函数：内部走 `set_tenant_context(None)` + `finally` 还原（现有 `erp_db.set_tenant_context` 基于 **ContextVar**，在 asyncio 单任务内是安全的 —— 但**禁止各处手写**，否则迟早漏还原）
- 现有反例：`routers/ai_observability.py` 自己写了 `_main_db()/_restore()` 私有对（`:47-52`）—— 应收敛为单一函数（"同一集合的第二份拷贝 = 静默漂移温床"）

**⑤ 审计闸门**
- 新增 `audit_logs` module='experience'：记录"哪条经验由哪个租户贡献、被哪个租户消费"
- 复用现有哈希链（`prev_hash/current_hash` 已存在）
- **保留期**：跨租户层建议 24 个月滚动淘汰（现在 `audit_logs` 无保留期概念）

**⑥ 撤回闸门**
- 租户撤回档位 B → 按 `tenant_hash` 删除其在 `experience_atoms` 的全部贡献行
- 已进入 `skill` **正文**的条目无法"删"（文件已发布）→ 降级处理：在该 skill 段落加"该口径含已撤回租户样本，待复核"标记，并纳入下一轮 `recipe_sync` 重建
- 挂接点：`gdpr.py` 的 `/delete`（账号匿名化）流程

### 2.3 红线：绝对不进跨租户层的东西

| 类别 | 字段举例 | 理由 |
|---|---|---|
| 员工维度 | 工资额、提成个人值、绩效、津贴 | 个保法（自然人） |
| 客户维度 | 门店名、电话、地址、单店销量 | 个保法 + 商业秘密 |
| 价格维度 | 进货价、渠道价、返利金额、合同费率 | 商业秘密（**最敏感**，泄露即商业损害） |
| 总量维度 | 月销额、库存总值、毛利率 | 可反推规模，等同泄露经营机密 |

→ **跨租户层只保留"算法口径"这一类**（参数名 + 量级桶 + 口径枚举）。理由不只是合规：口径才是护城河，而它**天然不可反推商业机密**——这是本方案能同时"学到东西"又"不越线"的根本原因。

### 2.4 现状的三个合规缺口（必须如实告知）

| 缺口 | 证据 | 影响 | 处置 |
|---|---|---|---|
| **A. skill 文件跨租户真值共享** | `recipe_sync.py:175` 把 `threshold_days=7`、`commission_rate=x%`、`base_salary=5000` 与 `租户 tenant_N` 一起写进 `/root/.hermes/skills/hergent-milk-*/SKILL.md`；且 `trigger_sync_from_service()`（`:264`）不带 `--tenant-id` → `read_live_recipes(None)` 退化为 `or 1` | 当前仅 1 个真实租户（永诺）故未暴露；**第二个租户上线当天即互相覆盖** | **本方案 P0 第一件事**：AUTO_RECIPE 块改按租户分目录 / 或在块内只放"口径结构"不放真值，真值改由后端 API 运行时提供 |
| **B. 主库 audit_logs 含租户真值** | `record_recipe_audit()` 把字段级 diff（含真值）写主库，`ref_id=tenant_N:模块`，无授权记录、无保留期 | 主库 = 跨租户存储，已存在含真值的租户数据 | 二选一：**降级为"只记录变更事实不含值"**，或**补授权 + 保留期 + 去标识** |

## 三、验证：如何判定 know-how 真的被收集到了

分三层，逐层收紧。**任一层不达标，就不能说"收集成功"**。

### 3.1 覆盖率（Coverage）—— 回答"有没有漏"

| 指标 | 定义 | 判定标准 |
|---|---|---|
| 反馈挂载率 | 副驾建议中带 `advice_id` 的比例 | **≥95%**（低于 = 前端漏埋点） |
| 反馈完成率 | 有 `decision` 的建议 / 总建议 | **≥60%**（低于 = 用户不愿点或入口太深） |
| **覆写捕获率** | `delta_kind != 'none'` 的占比 | **5%–40% 为健康；=0 即断点①未修**（注意：不是越高越好，≈100% 说明 AI 建议质量崩了） |
| 配方变更入库率 | `workflow_recipes` / `forecast_config` 变更中被经验池收录的比例 | **=100%**；差集必须能逐条解释 |
| 会话结构化率 | 被抽取出结构化片段的会话 / 总会话 | **≥20%；=0 说明 L3 抽取未生效** |
| 拒绝清单命中数 | 被 `_scrub_experience` 拦下的条目数 | **必须 >0 且被人工复核**（=0 可能是校验器没接上，而不是"没脏数据"） |

### 3.2 准确率（Precision）—— 回答"学得对不对"

| 指标 | 定义 | 判定标准 |
|---|---|---|
| **可回溯率** | `experience_atoms.source_ref` 非空的比例 | **=100%**（每条经验必须能指到一条原始日志；**这是"采到了"的必要条件**） |
| 提案命中率 | 自动生成的 `recipe_proposals` 中被 `accepted` 的比例 | 首月 **≥40%**，稳态 **≥70%**；**<20% = 阈值太松** |
| 覆写一致性 | 同一参数 30 天内改动方向的单向性（改了又改回 = 噪声） | **单向 ≥80%** 才允许自动提案 |
| 跨租户基准稳健性 | 某基准值在纳入/剔除任一单一租户后的变化幅度 | **≤5%**（超过 = k-匿名不足，基准被单租户绑架） |
| **回归否决率** | 采用新经验后，同一批历史算例出现差异的比例 | **必须 =0**（口径变更**不得静默改变已出账结果**） |
| 幻觉率 | 无法在源日志中回溯出处的经验条目比例 | **=0**（>0 即经验层被污染，按 P0 处理） |

### 3.3 效果（Impact）—— 回答"越用越聪明了吗"

| 指标 | 定义 | 判定标准 |
|---|---|---|
| **二次采纳率**（最硬的证据） | 同一 `task_type` 的建议，第 2 次及以后被采纳的比例 vs 第 1 次 | **提升 ≥15 个百分点** |
| 覆写衰减 | 同一参数的覆写次数按月变化 | **月环比下降 ≥30%，持续 3 个月** = know-how 已固化 |
| 冷启动差距 | 新租户第 1 月采纳率 vs 平台老租户均值 | 差距从 **≥20 个百分点收敛到 ≤5 个百分点** |
| 人工干预节省 | 每百单的配方类人工修正次数 | 季度下降 **≥25%** |
| 建议采纳率（已有） | AiHub「建议采纳率」（`AiHub.vue:31`） | 先打基线，**只看趋势不看绝对值** |

### 3.4 ⭐ 判定"know-how 被成功收集"的最小充分条件（三合一，缺一不可）

1. **可回溯** —— `source_ref` 非空，能指到一条原始日志或审计行；
2. **被复用** —— 该经验在 30 天内被**至少 2 个不同场景/时点**复用；
3. **无回退** —— 复用后二次采纳率**未下降**，且回归否决率 =0。

> 只有 ① 是"采到了"；①+② 是"用上了"；①+②+③ 才算"**越用越聪明**"。
> 只看 ① 就宣布成功，是典型的"零值即健康"陷阱的同族错误 —— 把"有记录"误当"有效果"。

### 3.5 反指标（出现即视为采集失败，按 P0 处理）

- 覆写捕获率 **=0** → Delta 未采（断点①没修）
- 幻觉率 **>0** → 经验层出现无法溯源的条目 → 必须清零
- 剔除任一租户后基准变化 **>5%** → k-匿名失效
- 拒绝清单命中 **=0** → 校验器可能没接上（而非"没脏数据"）
- 回归否决率 **>0 而经验仍被采用** → 学习通道绕过了审批闸门
- `experience_atoms` 里出现 §2.3 红线字段 → **合规事故**

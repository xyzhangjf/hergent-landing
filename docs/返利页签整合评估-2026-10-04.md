# 「目标与返利」与「返利结算」两个页签是否应合并 · 评估报告

- 评估对象：hergent.cn › 侧栏「目标与返利」（`/rebate`）页内的两个一级页签
  · A = 「目标与返利」（内部键 `rules`）
  · B = 「返利结算」（内部键 `contracts`）
- 评估日期：2026-10-04
- 依据：`src/pages/Rebate.vue`（3654 行）、`components/Shell.vue`、`constants/pages.js`、后端 `erp_db.py`、生产库 `tenant_1.db` / `tenant_10.db`（只读打开）
- 前置决策：2026-09-06《返利阶段2-品牌目标两层结构落库设计》已由用户拍板 ——「品牌目标(金额) = 厂家年度合同的月度分解，**同一数据源，不是两个独立对象**」

---

## 一、结论

**不建议把两个页签合并为一个页签。** 但「保持现状」同样不行 —— 当前形态有三个真实缺陷（**职责重复、关联断裂、模型口径不符**）。

**推荐形态：两个页签保留，但把职责切干净，并把"谁才是目标的唯一入口"这件事收敛到一处。**

| 页签 | 建议职责 | 判断依据 |
|---|---|---|
| 目标与返利 | **配置面**：年框 + 12 月分解 + 返利层（唯一目标入口） | 该页三条规则**已经**在承载月度分解，是事实上的主入口 |
| 返利结算 | **执行面**：计提 / 结算 / 申领 / 审核 / 余额，**不再重复录目标** | 结算、申领、余额、应收是它独有的，目标规则无法承载 |

一句话：**不是「两个页签该不该并」，而是「这两个页签现在各干了一半对方的事」。合并页签不解决重复，去掉重复才解决重复。**

> 🔴 **2026-10-04 22:17 用户补充口径 —— 它改变了「能不能直接下线」的答案**
>
> 「**结算是以月为单位**：本月提交上月核销资料，本月上账；不同厂家不一样，但大部分如此。」
>
> ⇒ 「返利结算」页承载的是**真实存在、每月都会发生**的业务动作，**不是死页签，不能直接下线**；
> 但它当前按「**年度合同 + 12 个月分解**」建模，与真实节奏「**逐月核销、次月上账**」不匹配 —— 详见 §2.5。
> 另：用户同时确认「现在都还在测试阶段，合同数据都可以删」⇒ §2.2 里那 11 条合同的消失**不是事故**。

### 2.5 结算的真实业务口径 vs 当前实现（2026-10-04 用户确认）

用户口径原文：**「结算是以月为单位，本月提交上月核销资料，本月上账，不同厂家不一样，但大部分如此。」**

把它画成时间轴是这样（以「厂家甲」为例）：

| 时点 | 动作 | 谁做 |
|---|---|---|
| 上月（T-1） | 实际发生销量 / 采购 | 业务自然发生 |
| **本月（T）初** | **提交上月（T-1）的核销资料**给厂家 | 会计 / 老板 |
| **本月（T）内** | 厂家审核确认 ⇒ **本月上账**（返利到账） | 厂家 |
| 下月（T+1） | 同样的循环再来一遍 | — |

⇒ 两个**结构性特征**：① **逐月滚动**（不是年度一次性结算）；② **核销月份 ≠ 上账月份**（存在一个月的错位），且**每个厂家的节奏不同**。

**与当前实现的差距：**

| 真实业务要素 | 当前实现 | 差距 |
|---|---|---|
| 逐月核销批次 | `rebate_contracts` 是**年度**对象（`year` + `target_amount` + 12 月分解） | 🔴 主体搞反了：真实主体是"月度核销批次"，年度合同只是可选外框 |
| 核销月份 ≠ 上账月份 | `rebate_accruals` 只有**一个** `month` 字段 | 🔴 无法表达"核销 T-1 / 上账 T"的错位 |
| 每厂家节奏不同 | **无任何**结算节奏配置 | 🔴 缺配置项（对照：到货节奏已有 `arrival_*` 一整套，结算节奏**没有对等物**） |
| 核销资料提交这一动作 | 无 | 🔴 缺动作与凭证（谁在何时提交了上月的什么资料） |
| 厂家确认的达成 | 无（`rebate_achievements` 只有人工/Excel/AI 录入的**自报**达成，`source` 字段无"厂家确认"档） | ⚠️ 缺"自报 vs 厂家确认"的对账环 |

**这条口径对页签结构结论的影响（重要）：**
- ✅ **不改**「不该合并」的结论 —— 配置（目标）与核销（上账）仍是两件事、两个人、两个时点。
- ⚠️ **改了**「能不能直接下线」的答案 —— 我原先建议的"若不做厂家年度结算就下线"**不成立**：这是每月都要做的真业务，问题只是**当前建错了模型**。
- 📌 **顺带浮出一个更近的亲缘关系**：「核销」= 厂家确认的达成，与页内「**达成填报**」（自己报的达成）是同一条业务链的两端。设计下一步时，`返利结算` 与 `达成填报` 的对账关系，比它与 `目标与返利` 的关系更值得先理。

## 三、四个维度逐项对比

### 3.1 功能重叠度 —— **高度重叠（重复录入）**

| 业务概念 | 页签 A：`rebate_target_rules` | 页签 B：`rebate_contracts` | 判定 |
|---|---|---|---|
| 年度目标额 | `target_value`（年框） | `target_amount` | 🔴 重复 |
| 12 个月分解 | `monthly_amounts`（JSON，键=月份） | `rebate_contract_months`（独立表） | 🔴 重复 |
| 返利率 | `rebate_rate` + `monthly_rates`（按月浮动） | `rebate_pct` | 🔴 重复 |
| 阶梯 / 坎级 | `tiers_json` | `tiers_json` | 🔴 重复 |
| 计提 | 达成填报 → 仪表盘展示实际返利 | `rebate_accruals` + 「计提本月」 | ⚠️ 部分重叠、口径不同 |
| 达成 | 达成填报（`rebate_achievements`） | 卡片上「当年达成 / 进度」 | ⚠️ 同源不同展示 |

**页签 A 独有**：维度（品牌 / 单品）、触发模式（达标 / 阶梯）、生效期、优先级、**到货节奏**（`arrival_*`）、**下单节奏**（`order_*`）—— 这些服务于"报单与冲刺看板"。
**页签 B 独有**：合作方（厂家 / 供应商）、年度、合同类型、**结算 / 申领 / 审核 / 驳回 / 冲销**、**未结算余额**、应收关联、结算日期 —— 这些服务于"资金与账务"。

⇒ 结论：**"目标"这一半完全重复，"返利落地"这一半各有侧重。** 重复的部分正是用户 2026-09-06 明确要求收敛的那部分。

### 3.2 用户使用场景 —— **不同阶段、不同人、不同频次**

| 维度 | 页签 A | 页签 B |
|---|---|---|
| 用在什么时候 | 月初设目标 → 全月盯进度 | **每月循环**：本月提交上月核销资料 → 本月上账（2026-10-04 用户口径） |
| 谁在用 | 销售主管 / 老板（日常） | 会计 / 老板（每月固定动作） |
| 用多频繁 | 高频（规则一设、全月被 Forecast / 冲刺看板消费） | **每月必做**；当前数据为 0 是**测试阶段清空**，不代表低频 |
| 动作可逆性 | 可逆（改目标、停用、删规则） | **不可逆**（结算 / 冲销一旦落账） |
| 失败代价 | 低（改回来） | 高（账务已生成） |

⇒ 场景差异是"不该合并"的**最强理由**：把"随时可改的配置"和"不可逆的结账"放在同一屏，会让期末那个动作暴露在日常高频操作的路径上。

### 3.3 信息层级 —— **同级但不同骨架**

- 页签 A 是**表格骨架**：一行一条规则，十列（规则名 / 维度 / 周期 / 对象 / 目标值 / 触发 / 返利 / 生效期 / 状态 / 操作）。几十上百行是常态。
- 页签 B 是**卡片骨架**：一张卡一个合同，卡片内再展开阶梯表 + 12 月明细表。合同数量天然是个位数。

两者信息密度差一个数量级。硬合到一个页签后，屏幕上会同时出现"一张 100 行的规则表"和"几张带两级展开的合同卡"，**层级会塌**。若真要合并，必须重新设计一级 / 二级分组（例如"合同"作为分组头、"规则"作为组内行），这是一次重构而非一次挪动。

### 3.4 交互流程 —— **交汇点存在，但当前是断的**

设计上两者的交汇点是 `rebate_target_rules.contract_id`（后端 `_contract_rules()` 按 `WHERE contract_id=? AND is_active=1` 取合同下挂的规则，参与合同计提）。**现状是：**

| 环节 | 状态 |
|---|---|
| 后端支持"合同挂规则" | ✅ 列存在（迁移 `v111_rbr_contract_id`）、读取实现存在 |
| 前端**写**入"归属合同"的入口 | 🔴 **不存在**（规则表单 / 合同表单都没有这个字段） |
| 前端**读**筛选入口 | ⚠️ 存在但恒空 —— 页签 A 有一个"全部合同"下拉，因 0 合同 / 0 挂接，选任何值都筛出空表 |

⇒ 这是一条**假功能**：UI 上有筛选器，后端有字段，但没有任何一条路径能把两者连起来。用户看到的「挂载规则 0 条」不是数据巧合，而是**链路上根本没接线**。

## 四、为什么不合并（逐条）

1. **合并解决不了当前的真问题。** 用户的重复感来自"同一件事能录两遍"（两套表都能表达年框 + 12 月分解），不来自"分成了两个页签"。把两页压成一屏，字段重叠一分不减，只是把两段长内容摞在一起。
2. **不可逆动作与可逆配置混排，误操作代价高。** 结算 / 冲销按 `create` 动作判权，配置按 `update` 判权，合并后同一屏出现两套不同门禁的按钮。
3. **层级会塌。** 表格密度（100 行）与卡片密度（个位数）差一个数量级（见 3.3）。
4. **两个人、两个时间点。** 目标配置在月初、结算在期末；配置者和结账者通常不是同一个人。
5. **单页签会过长。** 即便不算脚本，两个页签的模板已合计 271 行；合并后是页面内最长的一屏。当前页已有 5 个页签，属于"重页"，再加负担会牺牲可发现性。

## 五、若整合会带来什么（优点 vs 潜在影响）

### 5.1 优点

| 优点 | 说明 |
|---|---|
| **认知简化** | 用户不再需要在两个地方各录一次年度目标，只留一处 |
| **消除"到底在哪设目标"的困惑** | 当前两处都能设年度目标额 + 12 月分解，谁说了算没有界面依据 |
| **少一个页签**（5 → 4） | 降低导航噪音；侧栏名与页签名撞车的问题也随之消解 |
| **一次操作闭环** | 目标 → 计提 → 结算 → 申领不必来回切页签 |
| **迁移成本极低（时机优势）** | 合同表现有 **0 条数据**，若要统一数据模型，现在是最省事的时候 |

### 5.2 潜在影响（风险）

| 风险 | 严重度 | 说明 |
|---|---|---|
| 单页签变长、需新分组设计 | 中 | 不是"挪一下"，要重做一级 / 二级结构，否则反而更难用 |
| 不可逆动作暴露在日常路径上 | **高** | 结算 / 冲销混排后，误点代价是账务数据 |
| 权限门禁需重新核对 | 中 | 两条链路当前都归后端模块 `sales`，但动作轴不同（配置走 `update`、结算走 `create`），合并后要逐按钮复核 |
| 历史数据迁移 | 低（当前） | 合同 0 条，但存在 **12 行孤儿月份 + 2 行孤儿计提**需一并决策清理 |
| 报表 / 接口连带 | 中 | `GET /api/rebate-summary` 同时供给合同卡片与页签 A 的筛选下拉，动模型要连同校验 |

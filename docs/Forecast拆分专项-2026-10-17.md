## 一、结构诊断（数据驱动）

`src/pages/Forecast.vue` 是全站最大的「上帝组件」，把 P1–P13 全部预报功能堆在一个文件里。

| 指标 | 数值 | 说明 |
|---|---|---|
| 总行数 | **13800 行** | 全站唯一破万行的文件 |
| 模板 | 2850 行（1–2850） | 只读表 + 编辑网格 + 40+ 弹层 |
| 脚本 | **9800 行（2852–12653）** | 占 71%，是绝对大头 |
| 样式 | 1145 行（12655–13799） | scoped |
| 顶层声明 | **600+ 个** | ref/computed/function/watch 混排 |
| API 方法 | **96 个锚点** | forecastApi 56 + auditApi 7 + productsApi 8 + approveApi 8 + targetsApi 7 + 其他 |
| 主 chunk | **446 KB**（JS）+ 104 KB（CSS） | 全站最大，懒加载时首屏阻塞 |

**为什么这么大**：核心是「交叉表编辑网格」（类似 Excel 的预报填报）——这一个交互牵扯到单元格编辑、选区拖拽、键盘导航、右键菜单、撤销重做、列设置、草稿、校验、导入、审核、返利冲刺、目标分配等几十个子功能，全部内联在一个 `<script setup>` 里。

**已有的拆分先例（可循模式）**：
- Composable：`useColMenu.js`、`useColPrefs.js`（列设置/列权限已抽）
- 子组件：`AutoPeriodBlock.vue`、`ReminderConfig.vue`、`TemplateParams.vue`、`ForecastHistory.vue`、`ReportMapping.vue`、`ProductTarget.vue`、`ImportMapping.vue`、`GridZoomCtl.vue`

## 二、拆分策略（三层，风险递增）

**核心原则：先拆「无状态纯函数」，再拆「有状态 composable」，最后拆「模板子组件」。** 每拆一层，跑护栏探针 + 构建 + 部署，独立 commit，失败可单独回退。

| `qty.js` | rowFinalQty / rowExtraQty / rowSum / rowSumOf（🔴 金额唯一口径） | 4784–4807, 9545–9546 |

## 三、回归基线 + 护栏探针

**护栏探针已就位**：`.workbuddy/tools/forecast-split-guard.py`

```
# 拆分前（已跑）：
python3 .workbuddy/tools/forecast-split-guard.py baseline

# 每次拆分后：
python3 .workbuddy/tools/forecast-split-guard.py verify           # 锚点零丢失校验
python3 .workbuddy/tools/forecast-split-guard.py verify --build   # + 编译通过校验
```

**基线锚点（已生成 `forecast-split-baseline.json`）**：

| 锚点类型 | 数量 | 判据 |
|---|---|---|
| API 锚点 | **96 个** | 全库调用点零丢失、零变化（丢 = 删了功能） |
| 核心函数白名单 | **74 个** | 全库必须仍存在（跨功能域代表函数） |
| 构建 | — | `--build` 时 vite build 通过 |

**核心函数白名单覆盖**：期次 / 编辑网格 / 撤销重做 / 导出 / 审核建议 / 列设置 / 筛选排序 / 价格口径 / 最终下单口径 / 草稿 / 校验 / 单元格导航 / 导入 / 右键菜单 / 期次操作 / 返利冲刺 / 目标分配 / 打印推送。

**手工验收清单（拆分后逐项过）**：
1. 首屏汇总表正常加载（含权限分支）
2. 期次切换 / 新建期次（沿用上期清单）
3. 编辑网格：单元格编辑 / 粘贴 / 删除行 / 键盘导航（Enter/Tab/Esc）
4. 名称建议（拼音首字母 / 条码后 4 位）
5. 排序 / 分组 / 筛选（品牌多选 + 全局搜索）
6. 列设置：显隐 / 拖拽宽 / 冻结 / 右键菜单
7. 导出：xlsx / 舟谱模板 / 选中行
8. 补货建议（AI 审核）+ 撤销重做 + 草稿恢复
9. 导入（舟谱 Excel）+ 校验红框 + 定位错误行
10. 返利冲刺 / 目标分配弹层

## 四、批次计划（按依赖递进）

| 批次 | 层 | 内容 | 风险 | 预估改动 |
|---|---|---|---|---|
| F1 | 第 0 层 | 纯函数 5 个 utils 文件 | 🟢 低 | ~500 行移出 |
| F2 | 第 1 层 | 4 个 composable | 🟡 中 | ~800 行移出 |
| F3 | 第 2 层 A | CtxMenu + ImportPanel | 🔴 高 | ~1500 行移出 |
| F4 | 第 2 层 B | AuditPanel + RebateSprint | 🔴 高 | ~1200 行移出 |
| F5 | 第 2 层 C | AllocPanel + PeriodOps | 🔴 高 | ~1400 行移出 |

**每批交付纪律**：scoped commit → `verify` → `verify --build` → 部署 dist-vNNN → 生产探针 → 手工清单核对 → 下一批。任何一批 verify 失败立即停下回滚，不叠下一批。

## 五、风险与红线

1. 🔴 **金额口径唯一源不可动**：`rowFinalQty` / `rowExtraQty` / `factoryPrice` 是全站「最终下单」「进价」唯一实现（v188/v226b 铁律）。拆到 utils 时函数体一字不改，只动 import。
2. 🔴 **跨域铁律**：`useRouter` + `useRoute` 必须同时导入（v265 教训，删一个运行期崩页）。
3. 🔴 **one-Edit-at-a-time + grep 复核**：不同时开多个拆分文件编辑，防静默丢弃。
4. 🔴 **拆分是「移动」不是「重写」**：函数体、注释、口径说明原样搬运，避免顺手「优化」引入回归。
5. 🟡 **共享状态传递**：第 2 层子组件抽离时，cross/rows/liveRows 等核心状态用 props 下传 + emits 上抛，不用全局 store 硬塞（避免二次耦合）。
6. 🟡 **先跑通再优化**：拆分目标是把 13800 行降到可维护粒度，不是顺便重构业务逻辑。

---

## 六、预期收益

- 主 chunk 从 446KB 降到 ~200KB 以下（纯函数/composable 抽离后 tree-shaking + 子组件懒加载）
- 单文件 13800 行 → 主文件 ~4000 行 + 若干 200–800 行模块
- 后续改「返利冲刺」「目标分配」等单点功能，只需动对应模块，不再翻 13800 行
- 护栏探针让每次改动有「零回归」的机器证明，而非靠记忆

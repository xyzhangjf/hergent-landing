### v0.21.3 Release Notes 摘要（自 v0.21.2 以来：1,036 非合并提交 / 338 合并 PR / 2,642 变更文件 +131,690 −37,096）

补丁版本，把 v0.21.2 以来的滚动 main 汇总为稳定标签，供 Docker 镜像 / Hermes Cloud / 托管部署消费。正文只点了两项：

1. **远程仪表盘会话不再因刷新突发而过期（#110061）** —— 网关两条刷新路径（cookie gate 与桌面原生 bearer 路由）合并携带相同轮换刷新令牌的并发请求，避免 Desktop 唤醒突发时重放已轮换令牌、触发 Portal 重用检测而撤销整个会话；刷新移出事件循环，慢速身份提供者不再冻结 `/api/status`。
2. **长生命周期进程不再泄漏重复的 state.db 写入句柄（#110934）** —— 网关、仪表盘/Desktop 后端、ACP 与 CLI 读取器改为只读附加，进程内写入器共享注册表句柄。

**破坏性变更**：Release Notes **未标注任何 breaking change**；完整精选说明仍推迟到 v0.22.0。

**取向判断**：两项修复都属 **v0.21.x 自建运行时/Cloud/Desktop 面**（Portal 刷新令牌、state.db 写入器注册表）。生产 v0.19.0 既无 Portal 会话，也无 v0.21.0 引入的 state.db 写入器注册表 —— **收益对 hergent 为零**。

### ② `server/routers/ai_skills.py` 调 `GET /v1/skills` —— ✅ 兼容

### ③ `server/routers/cron_tasks.py` 硬编码 `sudo .../hermes_cron_bridge.py` —— ❌ **断裂（否决项，连续第 4 轮未修复）**
- hergent 侧：`server/routers/cron_tasks.py:14` `BRIDGE = "/usr/local/lib/hermes-agent/hermes_cron_bridge.py"` —— 仍硬编码指向本地脚本。
- v0.21.3 证据：全仓（含非 `.py`）grep `cron_bridge` / `hermes_cron_bridge` → **零命中**（v0.21.2、v0.21.1、v0.21.0、v0.21.3 连续四轮）。`cron/` 目录下亦无任何 `bridge` 相关文件；`pyproject.toml` 的 `[project.scripts]` 仅 `hermes` / `hermes-agent` / `hermes-acp`，**无 cron 桥接入口**。
- 官方替代路径：`api_server.py:1558-1565` 完整 cron CRUD —— `GET/POST /api/jobs`、`GET/PATCH/DELETE /api/jobs/{job_id}`、`POST /api/jobs/{job_id}/{pause,resume,run}`；另有 `POST /api/cron/fire`（Chronos NAS→agent 回调，需 NAS 签发 JWT，非 `API_SERVER_KEY`）。

- 判定：升级后 hergent 定时任务的创建/管理链路**必然全挂**。**这是当前升级的最大单点成本，且连续四轮未出现回归迹象。**

## ④ 结论与建议

### **结论：A —— 无需升级，维持生产 v0.19.0。**

理由（按权重）：

1. **新版本收益对 hergent 为零。** v0.21.3 的全部实质内容 = Portal/Desktop 刷新令牌合并 + v0.21.0 自建 state.db 写入器注册表的句柄泄漏修复。生产 v0.19.0 既无 Portal 会话，也不含该写入器注册表 —— 两项修复对生产**无适用面**。hergent 近期 AI 优化 90% 走自有 AI loop（`server/hermes_core.py` 直连 DeepSeek），与 Hermes 版本解耦。

2. **升级成本项（cron 桥接断裂）连续第四轮确认未修复。** `hermes_cron_bridge.py` 在 v0.21.3 全仓零命中，官方替代是需 `API_SERVER_KEY` 的 gateway HTTP `/api/jobs`。升级 = 必须改写 `cron_tasks.py` + 重配 nginx 端口（18765→8642）+ 实测 config 桥接 + 核对 `API_SERVER_KEY` 强度门禁，属**破坏性升级**。

3. **耦合点静态核查未发现任何"新版更好"的强制理由。** ① ② ⑤ 逐行未变；④ 是**改善**（5 键白名单 → 通用提升），但该改善只在升级后才用得上，不构成升级理由。

4. **风险不对称。** 升级须承担新运行时（`gateway/` + `API_SERVER_KEY` + 8642 + 插件兼容层时限）的部署/回滚风险，而收益为零。

### 🔴 本轮重要更正：安全面并非"无影响"，此前几轮结论有误

- **更正事实**：前几轮报告记为"PyPI 2 条历史漏洞，上界均早于 v0.19.0，生产不在受影响区间"。**本轮经 OSV / PyPI 逐条核对，该判断错误**：
  - OSV 机读区间为 `introduced=0, last_affected=0.19.0`，且 `versions` 数组**显式枚举了 0.13.0 → 0.19.0**；
  - **PyPI 自身在 `hermes-agent/0.19.0/json` 的 `vulnerabilities` 字段中，明确把 0.19.0 标为受这 2 条 advisory 影响**（4 条记录 = GHSA/PYSEC 两份重复）。
  - 两条为：**CVE-2026-10221 / GHSA-xq8w-9jvx-gm3v**（MODERATE，`run_agent.py` `_compress_context` 注入）与 **CVE-2026-10224 / GHSA-pmqc-57g8-c22c**（MODERATE，`gateway/platforms/feishu.py` `_handle_webhook_request` 资源消耗）。二者**均无已发布的修复版本**（PyPI 停在 0.19.0，`last_affected` 无 `fixed`）。
- **实际暴露面评估（这才是决定 A 的关键）**：
  - CVE-2026-10224（飞书 webhook DoS）：仅当启用 `platforms.feishu` webhook 模式可达。hergent 生产未接飞书渠道（耦合面为自建 web 前端 + 企业微信 + `mcp_servers.spreadsheet`）⇒ **生产不可达**。
  - CVE-2026-10221（压缩注入）：参考修复提交 `2ca38e5d` 日期为 **2026-07-23**，**晚于 v0.19.0 的 2026-07-20** ⇒ v0.19.0 很可能确未含该加固。但利用需能影响进入上下文压缩的内容，而 18765 入口为带 `API_SERVER_KEY` 的内部通道、仅内部员工使用，且业务 AI 主链路不经 Hermes 压缩 ⇒ **理论受影响、实际暴露面小**。v0.21.3 中 `_compress_context` 已随九月模块化分解不存在，`feishu.py` 亦已重构 → 升级可消除这两条。
- **不改生产即可做的零成本缓解（本轮仅建议，未执行）**：① 确认 18765 **不对外暴露**（仅本机/内网 + nginx 鉴权）；② 不启用飞书渠道；③ 收紧 `API_SERVER_KEY` 的分发面。
- **判定**：两条均为 MODERATE、需内网可达/特定渠道前提，**未达到"立即升级"门槛**，但安全面已从"无影响"上调为「**低风险已知暴露 · 观察项**」。

### 升级触发条件（保持监测，满足任一条即重新评估为 B/C）
- 官方发布 headless/server 侧正式发行说明，或明确恢复/提供与 v0.19.0 等价的 cron 本地入口；
- 出现**可远程未认证利用、且波及 v0.19.0 实际暴露面**的新公告（CVE/GHSA 上界 ≥ v0.19.0 且命中 hergent 已启用渠道）；
- **🔴 新增**：18765 因业务需要对外暴露，或启用飞书渠道，或 API 入口开放给非受信用户 → 立即重评为 C；
- 官方提供 `18765` / 旧 config 键的完整兼容层或自动迁移工具；
- hergent 业务出现必须依赖 v0.21.x 新能力的明确需求（当前无）。

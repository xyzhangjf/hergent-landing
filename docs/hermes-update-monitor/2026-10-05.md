## ④ 结论与建议

**结论：A 无需升级，维持生产 v0.19.0。**

理由：
1. **官方无新进展**：自 09-28 以来 GitHub 最新仍止于 v2026.9.24（v0.21.5），无新 tag、无 hergent 需要的修复/能力/安全补丁。
2. **否决项未消除**：v0.21.x 仍未恢复 `hermes_cron_bridge.py`，升级会直接打挂 hergent 全部定时任务（每日简报/Excel 对账排程等）——这是硬阻断。
3. **增益≈0、风险高**：v0.21.x 新能力 90% 桌面向，hergent 90% AI 已走自有 hermes_core 解耦；升级实为运行时重架构 + 无外网生产机部署工程，收益/风险严重失衡。
4. **5 耦合点现状不需动**：①②④⑤在新版兼容/软迁移，③断裂但维持 v0.19.0 即不涉及。

## ⑤ 若将来建议 B/C，最小改动清单与风险提示（仅作建议，本次不改生产）

**触发升级的条件（任一出现即重评估）：**
- 官方发布 **headless / server 正式发行说明**（明确面向服务端部署而非桌面）；
- 官方**恢复 cron bridge 或提供 18765 兼容的 HTTP cron 入口**，消除否决项③；
- 官方提供 **config 旧键（cors_origins / api_server）零手改迁移**的正式工具；
- 出现**波及 v0.19.0 暴露面的严重安全公告**（当前 PyPI 旧漏洞记录 ≤0.12.0 + 飞书 webhook，不波及单 profile 服务端，未达阈值，入观察）。

**最小改动清单（供未来 staging 验证用，非本次执行）：**
1. `server/routers/cron_tasks.py:13`：把 `sudo .../hermes_cron_bridge.py` 子进程调用改为对 Hermes gateway 的 HTTP cron 接口（需 gateway 常驻 + API_SERVER_KEY）。
2. `server/routers/ai_skills.py:26`：维持 `/v1/skills`（v0.21.x 已恢复，无需改；但若官方再次改前缀需同步）。
3. 生产 `~/.hermes/config.yaml`：验证 `cors_origins` / `api_server` 旧键经 config_loader 自动桥接无遗漏；spreadsheet MCP `mcp_servers.spreadsheet.stdio` 顶层键保留。
4. 部署：先破生产机无外网阻塞（Docker 构建 Linux venv 或临时开网），staging 独立端口跑 6 探针（chat/skills/cron/config/SOUL.md/spreadsheet MCP）→ 全绿再切生产 + 回滚锚点。

**风险提示：**
- cron 重写为 HTTP 调用复杂度高，任一环节出错即影响线上副驾/每日简报/Excel 对账。
- 生产机无外网，`pip install` 依赖需 Linux 构建环境（Mac 建的 venv 含 macOS wheel，rsync 到 Linux 不可用）。
- 配置迁移若不全，可能连 Hermes 自身都起不来。

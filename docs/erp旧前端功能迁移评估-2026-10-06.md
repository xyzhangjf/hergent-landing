# erp.hergent.cn 旧功能 → 当前项目 迁移评估

> 评估对象：`erp.hergent.cn`（旧前端）上已实现的功能，能否迁到「当前项目」= `hergent.cn`（新前端 hergent-cn-v2）
> 方法：实地读取两个前端的真实代码结构（非凭印象）
> 日期：2026-10-06

---

## 一、结论（先看这里）

**不能「直接完整迁移、零二次开发」。但可以直接复用的部分比想象中大得多——省掉的是整个后端与数据层，真正要重做的只有「看得见的那层皮」。**

| 层 | 能否直接复用 | 说明 |
|---|---|---|
| **后端接口** | ✅ **100% 复用，一行不用改** | 两个前端**共用同一个后端**（生产 `/opt/hergent-erp`）。旧前端调的 `/api/wms`、`/api/procurement`、`/api/inbound`… 新前端照样能调，接口路径一字不变 |
| **数据库 / 表结构** | ✅ **100% 复用** | 同一个库（`erp.db` + `tenant_*.db`），**零数据迁移**，不存在"搬数据"这件事 |
| **业务规则 / 字段 / 校验 / 流程** | ✅ **可"照图施工"** | 旧代码可以当**规格说明书**读（字段叫什么、边界怎么判），但**不是把代码复制过去** |
| **界面（页面）** | ❌ **必须重写** | 这是唯一真正的二次开发。旧前端是「字符串拼网页」，新前端是 Vue 组件，**两种写法无法互相复制** |

**一句话**：**接口和数据是现成的，页面得重画。** 所以要评估的不是"能不能搬"，而是"哪些页面值得重画"。

## 二、事实基线（实测，不是推测）

| 对比项 | `erp.hergent.cn`（旧） | `hergent.cn`（新 · 当前项目） |
|---|---|---|
| 技术形态 | 普通 JavaScript + **全局共享变量**，靠脚本加载顺序运行 | Vue 3 单文件组件 + 构建工具 + 路由 + 状态管理 |
| 功能模块数 | **105 个**（`static/js/modules/`，合计 **18849 行**） | **30 个** `.vue` 页面 |
| 页面怎么画出来的 | **字符串拼 HTML** → 塞进 `innerHTML` | 声明式模板（数据变了页面自动更新） |
| 侧栏怎么来的 | `ModuleRegistry.register()` 动态注册 | `pages.js` 注册表 + 路由 |
| 侧栏分组 | 经营看板 / 仓库操作 / 财务工具 / 系统工具 / 扩展功能 | 经营 / 核算 / 配置 |
| 后端 | ← **同一个** → | ← **同一个** → |
| 数据库 | ← **同一个** → | ← **同一个** → |
| 最近改动 | 2026-09-13（9 月还在改，但已不是主线） | 持续活跃（主线） |

### 两条决定性证据

**证据一 · 旧代码依赖"全局共享"**（旧前端构建配置 `vite.config.js` 里的原话，我逐字读了）：

> "the legacy codebase relies on shared global scope — many helpers … are declared as top-level `function`/`var` in unwrapped modules and called bare from other modules. Under ESM each module is scoped, so those become module-local and **bare calls throw ReferenceError**."

翻译：旧代码里 `esc()`、`fmt()` 这类小工具是**在文件最外层直接定义、被别的文件裸着调用**的（靠"同一个大池子"共享）。一旦改成现代模块化，这些调用**立刻报错**。为此旧前端还专门写了个插件，**把每个文件的顶层函数强行再挂回全局池子**才能跑。

⇒ 这说明旧代码**天然依赖"全局一个池子"**；而 Vue 是**每个组件各管各的作用域**。两者是**相反的设计**。

**证据二 · 旧页面的画法是「拼字符串」**（以 `wms-console.js` 为例，原文）：

```js
return '<table><tbody>' + pairs.map(function(p){ return '<tr><td>'+esc(p.k)+'</td>…' }).join('') + '</tbody></table>';
// 然后：
el.innerHTML = _listTable(data);   // 直接改 DOM
```

新前端（Vue）里**没有"拼字符串塞 innerHTML"这个位置**——模板由框架编译，数据驱动。**这段代码无法移植，只能重画。**

## 三、差异点（为什么"直接搬"不成立）

| # | 差异 | 后果 |
|---|---|---|
| 1 | **作用域模型相反**：全局共享 ↔ 组件隔离 | 旧函数裸调用在新前端会报错 |
| 2 | **渲染范式相反**：手动改 DOM ↔ 数据驱动 | 页面代码必须重写 |
| 3 | **状态管理不同**：散落全局变量 ↔ 中心状态库 | 跨页数据流要重接 |
| 4 | **路由不同**：`navTo`/`pgMap` ↔ 路由表 | 跳转逻辑要重接 |
| 5 | **🔴 权限模型不同** | 旧前端侧栏自己判断可见性；新前端走 `pages.js` + 后端网关（含 v380 的 `inventory` 能力闸门）。**两套并存会出现"谁都能从旧地址进"的漏洞** |
| 6 | **主题不同** | 旧前端固定浅色；新前端支持深色模式 |

## 四、可直接复用的四层资产（这是省力的地方）

1. **后端接口（最值钱）**：旧前端用到的进销存接口在新后端**全都还在**——实测旧前端调过：`/api/wms`（仓储）、`/api/procurement`（采购）、`/api/inbound`（入库）、`/api/assembly`（组合拆装）、`/api/batch`（批次）、`/api/expiry`（效期）、`/api/wastage`（损耗）、`/api/stock-freezes`、`/api/stock-locks`、`/api/dunning`（催收）、`/api/profit-report`（利润）… 新前端**目前一条都没接**（实测搜 `src/` 为空）。
2. **数据库**：同一个库，**没有数据迁移这一步**。
3. **业务规则**：旧模块里的字段名、校验条件、计算方式，可以直接当**需求文档**用（省掉"重新想清楚业务"的时间）。
4. **侧栏归类设计**：旧前端的 `经营看板 / 仓库操作 / 财务工具 / 系统工具` 分组，本身就是一套成熟的进销存归类，**可直接借鉴**（与我在《舟谱侧边栏复刻建议》里提的 5 组方案互相印证）。

## 五、最小改动方案（三条路，我给推荐）

### 方案 A：把旧页面「内嵌」进新前端（零前端开发）
在新前端放一个框，里面直接显示旧前端的页面。
- ✅ 真·零开发，立刻能用
- 🔴 **硬伤**：会**绕过新前端的权限闸门**——旧前端自带完整侧栏，任何能打开旧地址的人都能看到进销存，**与老板"只有 boss 能看到"直接冲突**
- 🔴 登录态、深色模式、侧栏都会"两套并存"，体验断裂
- **结论：不推荐**（除非临时应急，且必须另加一道鉴权）

### 方案 B：逐页用 Vue 重画 + 后端一行不改（推荐）
- 每迁一个功能：**后端不动** → 写一个 Vue 页面 → 调**同样的接口** → 在 `pages.js` 登记一行
- ✅ 体验统一、权限统一、深色模式自动生效
- ⚠️ 代价：每个页面要重写（但**只需要重写"展示壳"**，业务逻辑照旧前端抄）
- **结论：正式迁移走这条**

### 方案 C：两个前端并存，各干各的（现状，保底）
- `erp.hergent.cn` 继续当**"功能机器"**（仓储/财务/单据这些重度操作）
- `hergent.cn` 专注**AI 经营副驾** + 已迁过来的高频页
- ✅ 成本最低、风险最小
- ⚠️ 代价：用户要在两个地址之间来回跳；两套权限要各自维护
- **结论：dogfood 阶段最务实**

### 🔴 我的建议：**C 保底 + B 渐进**
1. **现在**：不动旧前端，它就是现成的"进销存功能库"，先自己用起来（正好服务"先自用"的战略）；
2. **每个真正常用的功能**，再按 B 逐页迁到新前端（后端零改动）；
3. **绝不用 A**（会捅穿权限闸门）。

## 七、一句话总结

**旧前端 `erp.hergent.cn` 的价值不是"能搬的代码"，而是"现成的后端接口 + 数据库 + 一套已经想清楚的业务规则"。**
- **接口与数据**：直接复用，**零成本**；
- **页面**：必须重画（技术栈相反），但**只需重画展示层**，业务规则照抄；
- **路径**：`erp.hergent.cn` 先当自用功能库（方案 C），常用的逐个用 Vue 重画迁到 `hergent.cn`（方案 B），**别用内嵌（方案 A）**——它会捅穿 v380 刚建的 `inventory` 权限闸门。

## 二、先厘清：「定稿」在系统里其实有 4 个含义

这是所有混乱的根源。同一个词指向四个互不相同的动作/状态：

| 代号 | 含义 | 代码位置 | 是否写库 | 现状 |
|---|---|---|---|---|
| **D1** | 保存汇总表草稿（`saveEdits` 后的「确认」） | `POST /api/forecast-submissions/save-matrix` | 写报单明细 | 早在 v318 已**不再**发通知（原 v277 通知曾挂这里） |
| **D2** | 审核台「确认定稿」（逐 SKU 定最终下单量） | `POST /api/forecast-audit/audit-period/adopt` | 写 `forecast_audit_decisions` | **历史流程**。界面自己写着「逐单审批为历史流程，仅用于追溯」 |
| **D3** | **关闭期次 = 定稿**（弹窗原文「关闭 = 定稿」） | `POST /api/forecast/periods/{pid}/close` | 写 `forecast_periods.status='closed'` | **当前唯一定稿出口**（v219 起） |
| **D4** | 自动关单（调度器按品牌节奏到点关） | `scheduler.py::_auto_period_close` | 同上，**但不经端点** | 每天都可能发生 |

**关键点**：D3 与 D4 产生**同一个状态**（`status='closed'`），但走**两条完全不同的代码路径**、行为不一致（见第四节）。而历史页「定稿」列的判据读的是 **D2 的表**（`forecast_audit_decisions`）——一张随着 D2 废弃而**再也没人写**的表。

## 三、「定稿」的触发条件与完整流程

### 3.1 唯一定稿出口：关闭期次（手动 D3）

```
用户点「往期预报 / 当前期次」→「关闭」
  → 前端 Forecast.vue::confirmClose()
     · v318 起先弹「确认定稿 · 关闭期次」，并列出将推送的加单/减单明细
     · 按钮：「取消，继续修改」/「确定定稿」
  → POST /api/forecast/periods/{pid}/close
  → routers/forecast.py::close_period()
     ① transitioned = db.forecast_period_close(pid)      # 返回是否真的 open→closed
     ② _audit_period_op(..., "period_close", ...)        # 写 forecast_config['audit:<pid>']
     ③ if transitioned: notify_extra_allocs_finalized()  # v318：唯一推送出口
  → 返回 {"success": true, "notified": {sent, skipped, people}}
```

**触发条件（后端硬闸门，`erp_db.py::forecast_period_writable`）**
写报单被拒的条件（`pid > 0`）：
1. 期次不存在 → 拒
2. `status != 'open'` → 拒（**"关闭即定稿"就是这一条**）
3. `order_end < 今天` → 拒（报单截止日已过，**即使还没被关单**）
4. **例外**：`allow_closed=True`（v305 授权改单）⇒ 跳过第 2、3 条

**幂等判据**：不是"接口被调一次"，而是**状态跃迁**（`was != 'closed'`）。所以重复点「确定定稿」不会重复推送。

### 3.2 第二条路径：自动关单（D4）

```
scheduler 每 300 秒一轮（_should_run("auto_period", 300)）
  → _check_auto_period()
     · 取 rebate_target_rules 中 auto_period_enabled=1 的那一条为「基准品牌」
     · build_period_plan(..., horizon_days=14) 生成未来排程
     · 对每个计划期次 p：
         if   oa <= now < ca  → 自动开表
         elif now >= ca       → _auto_period_close(p)     # ← 注意：一旦过了 ca，每一轮都会尝试
  → _auto_period_close(p)
     · SELECT id FROM forecast_periods
         WHERE status='open' AND (order_start=? OR order_end=?)   # ? = 该计划期的报单日
     · 命中 → db.forecast_period_close(id)
     · 直接调 db 层，**不经 HTTP 端点** ⇒ 不走 _audit_period_op，也不走 v318 推送
```

**触发条件**：`auto_period_enabled=1` **且** 期次处于 `open` **且** 期次的 `order_start` 或 `order_end` 等于排程算出的「报单日」。

**当前生产配置**：规则 #10（品牌维度）`auto_period_enabled=1`、开放填报 16:00、**自动关单 11:00**、厂家下单截止 12:00。

### 3.3 历史页「定稿」列的真正判据

```
ForecastHistory.vue:33   {{ row.finalized ? '已定稿' : '未定稿' }}
  ← forecastApi.orderBoard()  → GET /api/forecast/order-board
  → erp_db.py::forecast_order_board()
        finalized = db.execute(
            "SELECT 1 FROM forecast_audit_decisions WHERE period_start=? AND period_end=? LIMIT 1",
            (start, end)).fetchone()          # ← 读 D2 的旧表
        ... "finalized": finalized is not None
```

这就是**病根**：`finalized` 读的是 D2 的表，而当前定稿（D3/D4）**从不写这张表**。

## 五、不合理之处逐条分析

### 🔴 #1 历史页「定稿」列判据错位（恒假）

- **现象**：状态列「已关闭」+ 定稿列「未定稿」同屏矛盾。
- **成因**：`finalized` 读 D2 旧表；D2 已被「关闭期次」取代（界面文案亦自述其为历史流程），旧表不再被写。
- **性质**：**恒假判据**。不是"偶尔不准"，是"永远为 false"，任何数据都无法让它变 true。
- **为什么危险**：它看起来像一个"如实反映"的状态列。用户据此判断「这期没定稿」，而实际已定稿并已锁死不可改 —— 会做出错误动作（比如去重开）。
- **附带**：该判据还用「窗口」`(period_start, period_end)` 当键。期次窗口是**可改**的（`period_update` 留痕里就有改名+改窗口记录），窗口一变，即便旧行存在也会失配。这与 v279 把加单归属从「窗口」改为 `period_id` 是同一类病灶，此处漏改。

### 🔴 #2 人工「重开」被自动关单确定性撤销

- **现象**：期次 #19 两次重开、两次在 5 分钟内被关回。
- **成因**：`_auto_period_close` 只查 `status='open' AND 日期匹配`，**没有任何"人工重开过就别管"的豁免**；而 `_check_auto_period` 用的是 `elif now_str >= ca`（过了关单时刻后**每轮都跑**）。
- **后果链**：
  1. v219 把「重开」定义为关闭后**唯一**的补救路径；
  2. 自动化开启时这条路径**实质失效**（重开不是没用，是"用了，几分钟后被系统撤掉"，且**界面上不会告诉你为什么又关了**）；
  3. 前端 `lockHint`（`Forecast.vue` 的锁提示）还在对销售说「如需改动请联系管理员**重开本期**」——一条已经走不通的建议。
- **为什么危险**：这是「用户意图被系统静默覆盖」。用户看到自己刚点的重开"自己变回去了"，只会认为系统坏了。

### 🟠 #3 两条定稿路径行为不一致（零留痕 / 无时间戳）

| 行为 | 手动关闭（D3） | 自动关单（D4） |
|---|---|---|
| 改 `status` | ✅ | ✅ |
| 写 `audit:<pid>` 留痕 | ✅（谁关的） | ❌ **完全不留痕** |
| 记录关闭时刻 | ❌（`forecast_periods` **没有** `closed_at` 列） | ❌ |
| v318 推送 | ✅ | ❌ |

`forecast_periods` 实际列只有：`id / name / order_start_date / order_end_date / arrival_date / status / created_at / order_start / order_end`。

**后果**：想回答"这期什么时候定的稿、谁定的、是人工还是自动"，**数据里查不到**。本次审查是靠服务日志拼出来的——日志会滚掉，这个答案就永久丢失了。

### 🟠 #4 v318 推送在主要路径上未兑现

v318 的规则是「只有真·定稿才通知，推送出口唯一化」。但实际生产的定稿**主要来自自动关单**（今天 #21 就是），而自动关单经 `db.forecast_period_close`，**不经端点** ⇒ 一条通知都不发。

**注意这里有一个真实的设计矛盾**，不能简单"把推送也挂到自动关单上"：
- 自动关单在 **11:00**；
- 厂家下单截止 **12:00**；
- v305「授权改单」允许管理员在关单后**继续改**到 12:00。

⇒ 若在 11:00 自动推送，推出去的是**一个小时后还会被改掉**的版本，且推送不可撤回。这比"不推"更糟。

### 🟠 #5 付款口径读已废弃的旧表

见 4.4。同一张 `forecast_audit_decisions`，两处误用（`payments_compute` / `payments_preview`），且都被 `except` 静默吞。旧前端已可见，显示为绿色「需付款 ¥0」。

### 🟡 #6 次生问题

- **日志失真**：`_auto_period_close` 无条件 `print("已关闭期次#N")`，即使 `db.forecast_period_close` 返回 `False`（未发生跃迁）。#19 在 20:07 和 20:17 各打印一次，第二次其实是 no-op，但日志读起来像"又关了一次"。
- **术语过载**：UI 上「定稿」被用于 D1（保存确认）、D2（审核台）、D3（关单）三个不同动作，同一个词三种后果。
- **`need_to_pay` 字段缺失**：`payments_preview` 不返回该键，而 `payments_compute` 返回；旧前端读前者 ⇒ 恒 falsy。

## 六、优化建议（按优先级）

### P0-1　修正「定稿」列判据（改 1 处，立即可验证）

- **环节**：`erp_db.py::forecast_order_board` 的 `_agg()`（`finalized` 查询）
- **改法**：`finalized` 不再查 `forecast_audit_decisions`，改为读期次自身状态 —— 即 `p.get("status") == "closed"`（合成行 `id<0` 无期次状态 ⇒ 保持 `false`）
- **同时**：把「逐单审批」旧表从"任何定稿判据"中彻底摘除，只留追溯用途（与界面文案"仅用于追溯"一致）
- **验收**：期次 #16/#17/#18/#19/#21 均显示「已定稿」；对任一期次点「重开」后立刻显示「未定稿」

### P0-2　给自动关单加「人工重开豁免」（止血）

- **环节**：`scheduler.py::_auto_period_close` 的 SELECT + `erp_db.py` 期次表 schema
- **改法**：`forecast_periods` 增列 `reopened_at`（`forecast_period_reopen` 写入），自动关单查询加 `AND COALESCE(reopened_at,'')=''`
- **语义**：人工重开 = **人工接管本期，自动化让位**
- **顺带修文案**：`lockHint` 里「请联系管理员重开本期」改为指向 v305 的**「授权改单」**通道（不重开、不恢复销售报单，就能改数）
- **需要你拍板的权衡**：重开之后，销售又能在小程序报单了（v219 已注明的副作用）。若你希望"重开只给经理改数、不让销售再报"，那要改的是重开本身的语义（把重开拆成「解锁编辑」与「恢复报单」两件事），比上面这条改动大。**建议先做"豁免"止血，语义拆分另立一项。**

### P1-1　定稿留痕补齐（消除两路径不一致）

- **改法**：`forecast_periods` 增 `closed_at` / `closed_by` / `closed_mode`（`manual` / `auto`）；`forecast_period_close(pid, by, mode)` 统一写入；端点和调度器分别传 `manual`/`auto`
- **收益**：
  - 历史页「定稿」列可升级为「已定稿 · 09-29 11:18 · 自动」/「已定稿 · 09-22 16:27 · 张俊峰」
  - `audit:<pid>` 留痕改为由同一入口写入 ⇒ 自动关单也不再零留痕
- **验收**：自动关单后 `closed_at` 非空且 `closed_mode='auto'`；手动关单后 `closed_by` 为操作人
- **依赖**：需走启动期补列对账（`[schema-sync]` 已有该机制），**上线顺序：备份 → 上后端 → 重启看补列日志**

### P1-2　加单/减单推送出口修正

三个选项，建议 A：

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 自动关单**不推送**，但在期次上明示「本期明细**尚未推送**」，并提供**手动「推送本期加单/减单明细」按钮**（人核对完、改完再推） | 语义正确：推送 = 人确认后的版本；与 v305 授权改单窗口（11:00–12:00）不冲突 |
| B | 推送下沉进 `db.forecast_period_close`，自动关单也推，`operator="系统自动定稿"` | 违背"出口唯一化"初衷的反面：会把**一小时后还会变**的版本推出去，且撤回不了 |
| C | 维持现状，仅在文档/界面注明「自动关单不推送」 | 最省事，但用户会持续以为"定稿就推送了" |

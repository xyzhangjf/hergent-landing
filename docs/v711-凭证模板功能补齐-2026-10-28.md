# v711 凭证模板功能补齐（2026-10-28）

> 结论先行：**凭证模板整条功能是"空壳"** —— 路由和模板引擎从 v89 Phase 4 上线起就在调
> `db.voucher_template_list/create/update/delete/apply`，而这五个函数在 `erp_db.py` 里
> **从来不存在**。本版补齐 DB 层、修掉两处必崩的 NameError、接进自动记账，并用
> feature flag `voucher_templates`（**默认关**）把风险关住。

---

## 1. 改前是什么样（实测，不是推断）

| 接口 | 改前 | 原因 |
|---|---|---|
| `GET /api/voucher-templates` | 500 | `db.voucher_template_list` 不存在 |
| `POST /api/voucher-templates` | 500 | 同名函数不存在 + `d` 未定义（`body` 读出来却用 `d.get()`） |
| `PUT /api/voucher-templates/{id}` | 500 | 同上，`d` 未定义 ⇒ 100% NameError |
| `DELETE /api/voucher-templates/{id}` | 500 | 函数不存在 |
| `POST /seed` | 500 | 函数不存在 |
| `POST /test` | 500 | `apply_template` 第一行就调不存在的 `voucher_template_list` |

`.bak-v707` 自证：这两处 `d` 未定义**不是本轮引入**的，从 v89 起就是这样。

另外两个"看不见"的事实：

- **模板引擎零调用者**：`apply_template` 全系统只有 `/test` 一个调用点，自动记账
  `auto_journal_for_*` 一直走硬编码科目 ⇒ 模板配了也白配。
- **flag 机制从来没工作过**：`feature_flags` 存量表是**早期 schema**（主库权威 DDL 只有
  6 列，**没有 `updated_at`**），而 `feature_flag_list()` 的 SELECT 与 `feature_flag_set()`
  的 INSERT 都引用 `updated_at` ⇒ 在任何库上都必抛 `OperationalError` ⇒ 永远读到空。
  连带后果：主库里那行 `ai_timeline=1`（2026-06-22 写入）**从没被读到过**。

## 2. 改了什么（4 个文件）

| 文件 | 改动 |
|---|---|
| `erp_db.py` | 追加 DB 层：`_ensure_voucher_template_tables` / `voucher_template_list\|create\|update\|delete\|apply` / `_voucher_entries_for`；`feature_flag_list\|set` 补惰性建表 + **逐列补齐** |
| `erp_db.py` | 4 个 `auto_journal_for_*`（sale / payment / purchase / cogs）改为**模板优先、硬编码兜底** |
| `routers/voucher_templates.py` | 修 2 处 `d.get(...)` → `body.get(...)`；接上已定义却从未调用的 pydantic 校验 `Val1`（类型错给 422）；`ValueError` → 400 |
| `voucher_engine.py` | `db_conn` 真正透传给 `voucher_template_list` / `_apply`；**审计移到平衡校验之后** |

### 2.1 模板分录要过三道闸才准进账

`_voucher_entries_for()` 任一条件不满足就返回 `None`，调用方回落硬编码：

1. flag `voucher_templates` 未开 / 表缺失 / 抛异常 → `None`（**读不到开关 = 关**）
2. 无匹配模板 → `None`
3. 模板算出的分录**借贷不平衡**（`db.precision.money_balanced`，整数分）或全零 → `None` + warning

第 3 条是硬要求：模板由用户手填，默认模板只覆盖 8 个场景，一旦有人填了单边分录就会
直接写进 `journal_entries`，账立刻不平且无从回滚。

### 2.2 审计为什么必须后写

改前 `apply_template` 的顺序是「生成分录 → 写审计 → return」，而平衡校验在返回**之后**
才做 ⇒ 模板被拒、账走硬编码，审计表里却留着一条"命中"记录。A21 实测复现：单边模板被
拒后 `voucher_template_applies` 仍多了 1 行。现在是「先校验平衡，不平衡就跳过并继续试
下一个模板」，审计只记**真正被采用**的。

## 3. 验证

判据不是"没报错"，是**生成的分录科目与金额**。

| 组 | 场景 | 结果 |
|---|---|---|
| A 隔离空库 | DB 层 CRUD 全流程 + 三道闸 + 反向可证伪 | **26/26** |
| B 生产租户库**副本** | 真实未过账单据（销售 18,122 / 采购 83 / 收付款 16 / 成本 22,506 张） | **16/16** |
| C 生产真实 HTTP | 五个接口 + 事件 + 测试 + flag（改前全 500） | **21/21** |

🔴 B 组用**真实单据**不用 mock（v697 教训：mock 全绿 ≠ 生效）。

关键几条：

- **B2/B3** flag 关 ⇒ 科目 `1122/6001`、金额 = 订单金额、借贷平衡（与改前逐分一致）
- **B5** flag 开 + 默认模板 ⇒ 结果不变（默认模板科目与硬编码相同）
- **B7 反向可证伪①** 把模板借方改成 `1123` ⇒ 分录**必须**跟着变成 `1123`（证明模板不是摆设）
- **B8 反向可证伪②** 把模板改单边 ⇒ **必须**回落 `1122/6001`，且回落的分录仍然平衡
- **A20/A21** 不平衡模板被跳过、且不写审计
- **C3** 空名称 → 400（不是 500）；类型错 → 422
- **回滚实证**：副本上 `--revert` 后与 `.bak-v711` 逐字节 0 差异；再重放，结果与生产当前
  **0 差异**（往返无漂移）

## 4. 本次踩到的坑（写下来防复发）

1. **`sqlite3.Row` 没有 `.get()`** —— 我在 purchase 的 context 里写了 `o.get("order_no", "")`，
   B 组直接 `AttributeError` ⇒ 采购过账整条路径挂掉。已就地修。
2. **改 `NEW` 串的文字 = 破坏幂等**：给已应用过的库重跑时，`n_new=0 且 n_old=0` ⇒ 判为
   "锚点不唯一"，而 `patch_file` 遇错**整批回滚**（v711 自己踩了两次：注释文字改了一个字）。
   要改注释就单列一条替换。
3. **"只针对旧形态"的升级项必须标记为可选**：干净副本上旧形态 0 次是**正常的**，按错误处理
   会连带跳过后面的编辑（一次重放差了 39 行）。
4. **写接口要过 CSRF**：cookie `csrf_token` 与头 `X-CSRF-Token` 必须同时给，否则 403
   （C 组第一次 14 项全 403）。

## 5. 状态与遗留

- **flag `voucher_templates` = 0（默认关）**，已显式登记在库里（不是"因为读不到所以正好是关"）。
  开启后自动记账才走模板；不开则与改前**逐分一致**。
- ⚠️ **开启 flag 要写两处**：`/api/feature-flags` 实测读到的是**主库**，而自动记账跑在
  租户上下文 ⇒ 两边各写一行才生效（脚本：`feature_flag_set("voucher_templates", 1)` 分别在
  `erp.db` 与 `tenant_1.db` 上执行一次）。
- **前端没有凭证模板入口**：生产 `dist` 里 `grep voucher-templates` 0 命中 ⇒ 现在只能走 API。
  要不要补 UI 单独立项。
- **8 个默认模板里有 3 个没有调用点**：`expense_paid` / `assembly_confirm` /
  `disassembly_confirm` 目前没有对应的 `auto_journal_for_*` ⇒ 即使 flag 开也不会被触发。
- `_init_default_templates()` 只在**一条都没有**时才播种（B10 就栽在这：删掉一个事件类型后
  还剩 7 条，它什么都不做）。
- 附带修复：`feature_flags` 补上 `updated_at` 列后，`ai_timeline=1` 现在会被读到了。
  已核实**前端 0 处引用**（`grep ai_timeline dist/*` 0 命中）⇒ 无界面变化。
- 测试数据已清理：租户库 `voucher_templates` 0 行、`voucher_template_applies` 0 行
  （表结构保留 —— 那是功能的一部分，删了下次请求又会惰性建回来）。

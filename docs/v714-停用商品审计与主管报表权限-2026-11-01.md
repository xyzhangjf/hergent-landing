## 一、104 条停用商品审计（只读，未改任何数据）

对生产 `tenant_1.db` 的 `products`（总 494 = 启用 390 + 停用 104）逐条关联库存、销售、报单模板：

| 判据 | 条数 |

**停用是批量操作，不是逐条判断**：`updated_at` 聚成 5 簇 —— 10-17 16:33（49 条）、09-10 21:22（26 条）、10-13 21:37（13 条）、10-13 22:40（7 条）、09-10 21:23（6 条），合计 101 条。

⇒ 是一次「只留蒙牛低温在售品」的清理，把**非主营业态 + 促销物料**整批停掉了。

### 1.1 真问题：16 个停用品还压着 12,726 元实物库存

全部是**赠品/促销物料**（凳子、玻璃杯、吸管杯、礼盒外包装、编织袋、促销台……），不是奶品。合计 7,544 件、账面 12,726.31 元，占全表库存额（156,879.69）的 **8.1%**。

库存来源已确认：`inventory_logs` 里这 16 条流水全是 `change_type='opening'`、`ref_type='v728_stock_snapshot'`、时间同为 `2026-10-29 09:28:47` —— 即 10-29 期初盘点导入的真实数量，**不是坏数据**。近 12 个月**没有任何出库/领用流水**（全库 281 条流水，`change_type` 100% 是 `opening`）。

后果：实物在仓、档案停用 ⇒ 发赠品/领用时选不到，只能先改档案；库存金额又挂在「看不见的商品」上 ⇒ 库存报表里这 8% 解释不通。

**建议（二选一，需老板拍板）**
- **A（推荐）**：把这 16 个恢复启用（`is_active=1`）。它们本质是**物料**，继续用就继续管，比留成死账干净。
- **B**：若确实不再发放，做一次「其他出库/报废」把这 7,544 件清零，再保持停用 —— 否则账上永远挂着钱又动不了。

### 1.2 88 条纯遗留：不建议物理删除

零库存、零销售行、不在报单模板。但 `products` 被 20+ 张表引用（批码、渠道价、目标、促销、报单快照……），物理删要逐表核引用，收益只是「表小一点」；而 v713 之后它们**默认就不显示**，且开关一开就是「这 88 个是历史品」的清晰语义。
⇒ 保持 `is_active=0` 即可，不做批量删除。

### 1.3 顺手发现一个判据坑

`inventory_balance` 表 **0 行**（全空）。按它判库存会得到「所有商品账面 0」的假结论。
🔴 **判库存只认 `inventory` 表**（`quantity` + `stock_value`）；`inventory_balance` 目前是死表。

## 二、主管（supervisor）报表权限 —— 已授权并验证

### 2.1 病害确认

v705f 把「数据报表」区放进 `REPORT_VIEWER_ROLES = ['boss','supervisor']`（`src/constants/pages.js:193`，`lock: true`），但**没给 supervisor 补 `reports` 模块**。而后端 `_PATH_MODULE_MAP` 里：

```
"/api/reports": "reports"
```

⇒ 主管**页面进得去、所有数据接口 403**，正是本项目最怕的「静默失效」形态（前端不报错，只是空白）。
生产实测（授权前）：`/api/reports/inventory-aging`、`/gross-profit`、`/avg-order` 三个全 **403**。

### 2.2 变更方式：走 API，不直接改库

`role_permissions` 直接写库会**绕过 `core.reload_perms(tid)` 的缓存失效**，用户看到的是「权限改了没生效」，而且不留审计。
⇒ 用 `POST /api/role-permissions`（内部会 `merge_module_list_into` + `reload_perms` + 写 `audit_logs`）。

🔴 **陷阱**：该端点的 `merge_module_list_into` 语义是「**existing 里被取消的模块 ⇒ 移除**」。
传 `["reports"]` 会把 supervisor 原有 8 个模块**全部删掉**。必须传**完整模块清单**：

```json
{"role_name":"supervisor","permissions":
 ["data","sales","stock","loss","bid","messages","forecast","forecast-audit","reports"]}
```

### 2.3 验证结果

| 项 | 结果 |
|---|---|
| 快照 | `/opt/hergent-erp/_backup/role_permissions.pre-v714-20261101-180054.json`（10 个角色） |
| 逐角色比对 | 只 `supervisor: +['reports'] -[]`；其余 **9 个角色零变化**，意外变化 0 |
| 主管 → `/api/reports/inventory-aging` | 403 → **200** |
| 销售 → 同一接口（负向对照） | **403**（门禁真按模块裁决，不是全局放开） |
| `/api/auth/permissions`（前端菜单数据源） | 主管模块含 `reports` ⇒ 菜单会出现 |
| 审计 | `audit_logs` id=837，`新增 4 项（reports.create/delete/read/update）`，哈希链 `prev_hash` 接得上 |
| 临时会话 | 已全部删除（`delete from sessions where token like 'v714tmp%'`），老板会话未动 |

影响面：4 个 supervisor 账号（`mptestsp` / `15391589030` / `18671037686` / `15671261085`）。他们现在能看 12 张报表页（毛利/均单/账龄/库存周转/促销ROI/销售订单汇总等）。

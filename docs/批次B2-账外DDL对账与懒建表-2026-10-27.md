## 0. 一句话结论

**那 341 处账外 DDL 不需要"收编"**——它们造成的真故障是 **0 处**。
但它们藏着 **9 个"先读表、后建表"的函数**，用户第一次点进那 8 个模块就是 500。
本批把这 9 处补上了，并留下一把能持续回答"代码说的和库里有的，对不对得上"的尺子。

## 2. 做了什么

### 2.1 新增两个只读工具

| 文件 | 作用 |
|---|---|
| `tools/hergent/v706/extract_ddl_schema.py` | 用 AST 从源码里抽出**全部** `CREATE TABLE` / `ALTER TABLE ADD COLUMN`，产出 JSON 清单（含**所在函数名**和行号） |
| `tools/hergent/v706/check_ddl_parity.py` | 拿清单与三个库的 table/column 快照对账，按 6 类定性输出；`--fail-on-fault` 退出码 2 可直接进 CI |
| `tools/hergent/v705/migrations/other_db_modules.txt` | 自己用另一个 SQLite 文件的模块清单（`memory.py` / `bid_radar_collect.py` / `kingdee_connector.py`），对账时排除，避免误报 |

抽取口径的关键一条：**表名要用 SQLite 自己解析**（把建表语句丢进 `:memory:` 库跑一遍读 `PRAGMA table_info`），
而不是自己拆逗号 —— `DEFAULT (...)` 里的括号、`CHECK(...)` 里的逗号会让手写解析器静默错位。

### 2.2 修 9 个"先读后建"的函数（`patch_v706_lazy_init.py`）

这些表是**懒建**的：DDL 在 `_init_qms_tables()` / `_init_wms_tables()` / `_init_bi_tables()` /
`_init_recruitment_tables()` / `_init_tax_tables()` / `_init_gaap_tables()` / `_init_serial_numbers()` /
`init_deferred_tables()` 里，第一次**写**才建表。写路径都调了 ensure，**读/改路径漏了 9 个**：

| 函数 | 缺的 ensure | 撞上会怎样 |
|---|---|---|
| `ncr_disposition` / `ncr_close` | `_init_qms_tables` | `no such table: non_conformances` → 500 |
| `inspection_with_aql` | `_init_qms_tables` | `no such table: inspection_plans` |
| `job_close` / `application_advance` | `_init_recruitment_tables` | `no such table: hr_jobs` |
| `pick_wave_list` / `pick_wave_detail` / `wave_complete` | `_init_wms_tables` | `no such table: pick_waves` |
| `period_close_checklist` | `init_deferred_tables` | `no such table: deferred_revenue` |

修法**不引入新机制**：仓库里 `inspection_plan_create()` 本来就是"第一行调 ensure"，
照抄这个既有写法即可。DDL 仍只有代码里那一份，**不复制第二份**（复制才是漂移之源）。

**为什么不"提前把 24 张表建出来"**：那会改动三台库的 schema，还要同步保证 doctor 的
master↔tenant 一致，动静远大于收益；而那 8 个模块在生产**从未被使用过**（表一张都没建起来
就是证据）。按需建 + 读前 ensure 是与其风险相称的做法。

## 4. 踩到的坑（都写进了判据）

1. **幂等判断越界**：补丁脚本第一版用 `lines[i:insert_at+8]` 找"是否已有 ensure"，
   窗口跨过函数边界、看到**下一个函数**的调用 ⇒ 把没改的函数判成"已有"而静默跳过。
   dry-run 报「改动 7 处（目标 9 个函数）」才暴露。修法：幂等扫描**限制在本函数体**（到下一个 `^def` 为止）。
2. **`ADD COLUMN {变量}` 被反向回溯抓成"列名叫 column"**：`ADD\s+(COLUMN\s+)?(name)`
   在 `… ADD COLUMN ` 这个片段上会让可选组放弃匹配，把 `COLUMN` 当列名。
   ⇒ 列名落在 SQL 关键字集合里的一律归 `dynamic`，不许当作声明。
3. **"判动态"不能看前缀**：原来用 `s[:m.start()]` 里有没有 `%` 判定拼接，
   导致一个大字符串里前面出现过 `%` 就把后面所有真表名误判成动态 —— **少报**比多报危险。改为只看名字本身。
4. **测试自己的正则少了 `re.M`**：`^def` 只匹配文件开头 ⇒ 除第一个函数外全部判空，
   报出 6 个假 FAIL。教训：测试红了先证伪测试。
5. **工具不能把"样本文件里没有全部目标"当失败**：退出码改为只在 `--strict` 时要求 9/9。

## 6. 留给你拍板的（不属于本批）

1. **试算表/资产负债表的"平衡"判据**（`erp_db.py:6718`、`db/queries/finance.py:102`）
   写的是 `abs(差) < 0.01`，与已修的 `gl_post`（`<= 1 分`）**差一分钱**。
   gl_post 允许差 1 分过账，报表却会把这一分报成"不平衡" —— 两处口径要不要统一，是**业务选择**，
   不是纯缺陷，所以我没动。
2. **对账匹配**（`erp_db.py:18675` 银行对账、`finance.py:607/1084` 金额匹配）同样是浮点 `< 0.01`。
   改它会让"差 1 分"从"不匹配"变"匹配"，有业务后果，建议单独一版 + 双算。
3. **89 张 f-string 拼名建的表**目前没有静态清单。要不要把它们改成常量（便于对账），
   属于可读性工程，不是风险项。

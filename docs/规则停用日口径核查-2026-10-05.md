# 「规则停用日」止于 2026-09-30 是否挡掉 10 月目标 —— 核查报告

- 触发：2026-10-04 复核《返利页签整合评估》时发现的现象 —— 页签「目标配置」3 条规则的**规则停用日全部是 2026-09-30**，但月度分解里 10 月（乃至 11、12 月）**仍有金额**。当时标注为「疑似口径错位，未查证」。
- 核查日期：2026-10-05
- 核查方式：**真实源码（md5 已核 == 生产）+ 真实生产库数据 + 真实计算入口**三方对齐，纯只读
  · 判定源码 `domain/rebate_period.py` md5 `c27bc11917faaf65bd2abf1f0702a492` **本地 == 生产**
  · 数据 `tenant_1.db` 规则 3 条（只读导出，md5 `68923e121e59bc935b6958bda1bf1af9`）

---

## 一、结论（三句话）

1. **不是缺陷，不需要动任何数据。** 对「有月度分解」的规则，**规则启停日完全不参与"哪几个月有目标"的判定** —— 适用月份就是月度分解本身。
2. **这条结论已经被修复过（v186）并且有回归测试**；本次复核是**同一现象第二次被发现**，不是新问题。
3. 🔴 **但核查顺带查出一个真问题**：`简爱9月目标` 与 `蒙牛鲜奶到货节奏` 的月度分解**只有 9、10 两个月** ⇒ **2026 年 11 月起这两条规则会自动"消失"**（不是停用，是没有任何月份适用），届时对应品牌**静默无目标**。详见 §五。

## 二、判定实现（唯一源）

`domain/rebate_period.py::covered_months()`：

```python
amounts = parse_monthly(r.get("monthly_amounts"))
if amounts:                                   # ← 有月度分解：直接按分解的键返回
    y = rule_year(r)
    return {"%04d-%s" % (y, mm) for mm in sorted(amounts.keys())}
if r.get("period_type") == "year":            # ← 无分解的年度规则：才按生效期展开
    ...
return months_between(eff_s, eff_e)           # ← 单期规则：按生效期
```

`rule_covers_month()` / `rule_covers_date()` 均**委托**该函数 ⇒ 月粒度与日粒度同一个口径。

**为什么必须这样**：`monthly_view()` 对"分解里没有的月份"会**回退到顶层 `target_value`（年度总额）**，那个月就会拿"全年目标"比"单月达成" ⇒ 达成率恒失真、永不触发。所以"分解里没有的月份"必须在门禁处判为**不适用**，不能交给下游兜底。

> 该函数 docstring 里记着 v186 的原始事故：tenant_1「蒙牛低温2026年目标」12 个月分解齐全（合计 868.4 万），
> 生效期只写了 2026-09 ⇒ **交集后 11 个月的目标柱整根不画**，8 月已填报的达成（32.4 万）与实际返利（13.1 万）**被整个系统丢弃**。

## 五、🔴 核查顺带查出的**真问题**：11 月起两条规则会自动"消失"

同一份复算数据里藏着一个**真正需要行动**的事实：

| 规则 | 月度分解覆盖 | 2026-11 | 2026-12 |
|---|---|---|---|
| 简爱9月目标 | 只有 09、10 | ❌ 无 | ❌ 无 |
| 蒙牛低温2026年目标 | 01~12 齐全 | ✅ 有 | ✅ 有 |
| 蒙牛鲜奶到货节奏 | 只有 09、10 | ❌ 无 | ❌ 无 |

**机制**：`rule_covers_month(r, 2026, 11)` = False ⇒ 前端「达成填报」的月份矩阵
（`rules.value.filter(x => x.is_active && ruleCoversMonth(x, yy, mm))`）**根本不会渲染这两行**；
后端试算同样判"不适用"、返利为 0。

⚠️ **注意它与"停用"不是一回事**：规则 `is_active` 仍然是 **1**（启用状态），
界面上不会显示任何异常 —— **是"静默空白"，不是"报错"**。这正好命中本项目已知的
高危形态（对照：预报「沿用上一期清单得 0 个商品」的静默空白告警）。

**建议**（不需要立刻做，但别等 11 月 1 日才发现）：
- 现在就给这两条规则补上 **11、12 月的分解额**（在「目标配置」里编辑月度分解即可）；
- 或明确"这两条就是 9~10 月的短期目标"，那就不用管 —— 但**要知道 11 月会归零**。

## 七、探针自身的两处错误（如实记录，不当作"一次就查到"）

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| 1 | 我把断言期望写成"新旧口径差异 = 0" | 报 **1 个 FAIL**，且该 FAIL **恰好是反的** —— 真实差异是 3/3 | 改期望为 3，并把 §三 表格补成核心读数 |
| 2 | 直接调 `compute_rebate_unified`，**跳过 `monthly_view()` 投影** | 报 **6 个假 FAIL**（10 月目标读成年度 838.4 万、达成率 5.4%）⇒ 差点误报"10 月被停用日挡掉" | 改走真实入口 `compute_rule_rebate`（它内部第一步就是 `monthly_view`），10/10 PASS |

**教训（已折进技能）**：内核函数只做**门禁 + 算式**，"投影到当月"是**调用方的职责**
（`compute_rule_rebate` 第 539 行）。复算时**必须从 API 真正调用的那个函数进入**，
否则会造出一个"看起来 10 月没目标"的假象。

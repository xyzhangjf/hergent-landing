## 二、前端问题（页面交互 / 性能 / 代码结构）

### 🔴 F1【高】门店选择随 tab 切换被静默重置 → 可能提交到错误门店
- **定位**：`fill.js:13-18` 的 `onShow` 每次都执行 `loadStores()`；后者在 `fill.js:24` 无条件 `setData({ store: stores[0], storeIdx: 0 })`。购物车存于实例属性 `cartMap`（tabBar 页实例常驻），**跨 tab 不丢**，但 `store` 会被重置。
- **后果**：用户选好门店 B → 切到“我的提交” → 切回“填报”，门店被悄悄重置成 `stores[0]`，而车内商品仍在 → 一点提交就报给错误门店。属于数据正确性 bug。
- **改进**：门店列表与“当前选中门店”缓存到 `app.globalData` 或仅在首次 `onLoad` 加载；`onShow` 只做“未登录跳转”，不再重置选择。

### 🔴 F2【高】已登录用户仍停在登录页；401 不跳转登录
- **定位 A**：`login.js` 无任何生命周期鉴权检查。`app.json` 首屏是 `login`，已登录用户（token 在 storage）打开 App 仍看到空登录框，必须重输账号密码。应在 `onLoad` 检测 token → `reLaunch` 到 `fill`。
- **定位 B**：`utils/api.js:20-24` 处理 401 时只清 token，**没有 `wx.reLaunch` 到登录页**。token 过期后页面停留在无权限状态，后续请求持续 401，用户无感知。
- **改进**：401 分支增加 `wx.reLaunch({url:'/pages/login/login'})`；`login.js` 增加 `onLoad` 已登录跳转。

### 🟠 F3【中】搜索无防抖、存在竞态
- **定位**：`fill.js:50-55` `onSearch` 每次 `bindinput` 都同步触发 `loadProducts(kw)`，后者在有关键词时发 **2 个串行请求**（普通 + fuzzy）。快速输入会瞬间打爆后端，且旧请求慢于新请求时 `hot/results` 会被旧结果覆盖。
- **改进**：`onSearch` 做 300ms 防抖；取消/忽略过期请求的响应（用请求序号或 `wx.request` 的 `abort`）。

### 🟠 F4【中】商品/门店加载失败被静默吞掉
- **定位**：`fill.js:25 / 47` 的 `catch(e){}` 注释写明“接口暂缺时静默”。后端真 500 时用户看到空白搜索、无提示，无法区分“无结果”与“出错了”。
- **改进**：区分业务空结果（友好空态）与异常（`wx.showToast` 报错）；至少对 `loadStores` 失败给提示，否则提交按钮长期禁用且无原因。

### 🟠 F5【中】硬编码 `apiBase`
- **定位**：`app.js:3` `apiBase: 'https://hergent.cn'`，无 dev/staging 切换，也无微信后台 request 合法域名配置说明。
- **改进**：抽到独立 config 文件，按 `process.env`/编译变量切换；附域名白名单清单。

### 🟡 F6【低】`api.js` 顶层 `const app = getApp()` 无兜底
- **定位**：模块加载期 `getApp()` 若早于 `App()` 完成（极端顺序）会 `undefined` → `app.globalData.apiBase` 崩溃。
- **改进**：`const app = getApp() || {}`，函数内再 `getApp()` 取最新实例。

### 🟡 F7【低】退出登录未清理 tenantId
- **定位**：`mine.js:18-24` `logout` 只清 `fs_token/fs_user` 与 `globalData.token/user`，未清 `fs_tenant_id` / `globalData.tenantId`。

### 🟡 F8【低】`summary.wxml` 用 `index` 作 `wx:key`；`copyAll` 缺 `fail` 回调
- **定位**：`summary.wxml:21 / 44` 用 `wx:key="index"`（列表静态可接受，但属反模式）；`summary.js:45` `wx.setClipboardData` 无 `fail`。

## 三、后端问题（接口设计 / 数据处理 / 异常处理 / 安全性）

### 🔴 B1【高·安全】提交门店未校验员工可报范围（越权 + 数据污染）
- **定位**：`forecast_submissions.py:74` 直接把客户端传来的 `store:{id,name}` 透传给 `forecast_submission_create` 落库（`erp_db:12866` 原样 `store_id/store_name`）。`create_submission` 完全没校验 `store.id` 是否属于该员工的 `employee_stores_get(emp_id)`（对比同文件 `:318` 的 `/stores` 逻辑）。
- **后果**：员工可把预报报给任意门店，甚至伪造 `store_name`，污染汇总总表与订货决策。
- **改进**：提交时按 `u` 解析 `emp_id`/`role`，校验 `store_id ∈ 允许门店集合`（员工取 `employee_stores_get`，boss/admin 取全部客户），否则 403。

### 🟠 B2【中】`product_id` 类型转换无保护 → 异常直接 500
- **定位**：`forecast_submissions.py:36` 列表推导 `int(it.get("product_id") or 0)` 与 `:59` `int(it.get("product_id") or 0)` 均**不在 try 内**。客户端若传 `"abc"` 或非数字，`int()` 抛 `ValueError` → 整请求 500。同时 `pid<=0` 的非法明细会被照常写入（`:61-69`）。
- **改进**：统一 `try/except` 跳过非法 `product_id`，并对 `pid<=0` 的明细丢弃并给出明确 400；前端只发数字，但后端必须防恶意/异常输入。

### 🟠 B3【中】汇总未按提交状态过滤（被驳回的预报仍计入订货总量）
- **定位**：`erp_db.py:12932-12937` 的汇总 SQL 仅按日期条件聚合，**无 `status` 过滤**。状态 `pending/approved/rejected` 全部计入 `total_qty`。
- **后果**：老板驳回某条错误预报后，其数量仍留在“汇总总表”里，直接误导订货量。
- **改进**：增加 `status` 过滤参数（默认排除 `rejected`；或区分“已审/未审”分别展示）；前端汇总增加状态维度。

### 🟠 B4【中】重复提交无幂等（同人同店同日可多次提交，总量膨胀）
- **定位**：`create_submission` 每次 `INSERT` 一条 `pending`（`erp_db:12874`）。无“同一 user+store+date 已存在预报”的校验/合并。
- **后果**：员工重复点击或重复报同一门店，汇总总量被放大；也增加审批工作量。
- **改进**：提交前检查 `(user_id, store_id, order_date)` 是否已有提交；若存在则提示“今日已报，是否覆盖/追加”，或直接 upsert。

### 🟠 B5【中】汇总逐行同步调用预测引擎 → 大表慢
- **定位**：`erp_db.py:12965-12973` 对每个 distinct SKU 同步调用 `forecast_product(forecast_days=7)`（ML/预测引擎）。SKU 数百时 = 数百次引擎调用，阻塞请求线程。
- **改进**：`ai_suggested_qty` 改为后台定时预计算并落缓存表；或仅在前端显式“算 AI 建议”时按需计算，避免默认全量实时算。

### 🟠 B6【中】`/stores` 角色覆盖不全
- **定位**：`forecast_submissions.py:302-319` 仅 `admin/boss` 回退到全部客户；`supervisor/accountant` 走 `employee_stores_get(emp_id=0)` → 返回空门店 → 无法提交。但同一个 `supervisor` 在 `/summary` 是被允许查看的（`:102`），权限不一致。
- **改进**：`/stores` 的允许角色集合与 `/summary` 对齐；或让 supervisor 同样可看全部客户门店。

### 🟡 B7【低】错误信封 `ok` / `success` 混用
- **定位**：`forecast_submissions` 系列返回 `{ok:...}`，`forecast_audit` 系列返回 `{success:...}`。前端 `api.js` 已同时兼容两者，但后端不一致易埋坑。
- **改进**：统一为单一信封（推荐 `{success, data, error}`）。

### 🟡 B8【低】双写路径并存（`forecast_orders` vs `forecast_submissions`）
- **定位**：`forecast_audit.py:373 /save` 写 `forecast_orders` 表，而小程序实际走 `forecast_submissions`。两条预报写入路径并存，语义重叠、易混淆。
- **改进**：收敛为单一写入入口（保留 `forecast_submissions`），废弃 `forecast_audit/save`，或明确分工。

### 🟡 B9【低】`/my` 健壮性
- **定位**：`forecast_submissions.py:94` `int(u["id"])` 若 `id` 缺失 → `KeyError` 500；`limit` 固定 50 无分页游标。
- **改进**：`u.get("id")` 兜底；支持 `offset` 分页。

## 四、安全专项小结

| 项 | 状态 | 说明 |
|---|---|---|
| 认证 / 密码 | ✅ 良好 | bcrypt + 失败锁定 + 24h 随机 token |
| 价格 / 角色防篡改 | ✅ 已落地 | 后端忽略客户端 price，role 以 token 为准 |
| 门店范围越权 | 🔴 缺陷 | 见 **B1**，需服务端校验可报门店 |
| SQL 注入 | ✅ 安全 | 全部参数化 |
| 输入校验 | 🟠 待补 | 见 **B2**（product_id 转换）、**B4**（幂等） |
| 租户隔离 | ✅ 安全 | `forecast_audit` 的 `_connect()` 也读 `_tenant_db` 上下文，隔离无虞 |

## 五、优先级与改进方向（行动清单）

**P0（必须修，影响数据正确性/鉴权）**
- B1 服务端校验提交门店 ∈ 员工可报范围（防越权污染汇总）。
- F1 门店选择不因 tab 切换重置（购物车与门店选择一致常驻）。
- F2 已登录跳过登录页 + 401 自动跳登录。

**P1（重要，性能/健壮性/业务逻辑）**
- B2 `product_id` 转换包 try + 丢弃非法明细。
- B3 汇总排除 `rejected`（或按状态维度展示）。
- B4 提交幂等（同人同店同日不重复累计）。
- B5 `ai_suggested_qty` 预计算/缓存，避免逐行实时引擎调用。
- F3 搜索防抖 + 过期请求丢弃。
- F4 加载失败给出明确提示，区分空态与异常。

**P2（代码质量 / 一致性）**
- B6 `/stores` 角色与 `/summary` 对齐。
- B7 统一错误信封。
- B8 收敛双写路径。
- B9 `/my` 兜底 + 分页。
- F5 可配置 `apiBase`；F6 `getApp()` 兜底；F7 清理 tenantId；F8 `wx:key`/`fail` 回调。

## 六、关键修复示例（可直接落地）

**F1 — 门店选择常驻（fill.js 片段）**
```js
// app.js globalData 增加 lastStoreIdx
onShow() {
  const token = app.globalData.token || wx.getStorageSync('fs_token')
  if (!token) { wx.reLaunch({ url: '/pages/login/login' }); return }
  if (!this.data.stores.length) {        // 仅首次加载，不再重置选择
    this.loadStores(app.globalData.lastStoreIdx || 0)
  }
}
loadStores(idx = 0) {
  ...
  this.setData({ stores, store: stores[idx] || stores[0] || {}, storeIdx: idx })
  app.globalData.lastStoreIdx = idx
}
onStoreChange(e) {
  const i = +e.detail.value
  this.setData({ store: this.data.stores[i] || {}, storeIdx: i })
  app.globalData.lastStoreIdx = i       // 持久化选择
}
```

**F2 — 401 自动跳登录（utils/api.js 片段）**

if (res.statusCode === 401) {

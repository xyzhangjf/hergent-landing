# 预报订单模块 · 工作机制分析

> 范围：以真实代码为准，描述「预报订货」模块的**职责、组件、数据流、处理步骤与依赖关系**，并给出 Web 端 / 小程序的优化方向。不含实现教程或代码示例。

---

## 一、模块核心职责

预报订单模块是连接「一线业务员/促销员/导购」与「老板/文员」的**订货协作中枢**，把原本依赖个人经验的报单，升级为「采集 → 汇聚 → 审核 → 定稿 → 付款 → 下游下单」的标准化流水线。它的价值不是替代 ERP 的交易系统，而是坐在交易系统之上做**行业垂直的 AI 经营副驾**：

- **采集**：多角色（业务员、促销、导购、分销商）在微信小程序按授权门店填报预报量；文员/老板也可在 Web 交叉表直接导入 Excel 或编辑矩阵。
- **汇聚**：跨角色、跨门店把同一 SKU 不同单位的预报量按报单窗口聚合，附来源明细（谁、什么角色、哪个店、报了多少）。
- **审核**：复用近 30 天真实销量 + 当前库存，按「日均销量 × 覆盖天数 − 当前库存」生成**系统建议量**与缺货/积压判定，并叠加厂家返利冲量提示（护城河算法）。AI 只建议，定稿必须人工点。
- **闭环**：定稿后自动计算「订单金额 − 厂家预存款 = 应付差额」并催付款；一键生成舟谱订单导入 CSV；返利冲档测算。
- **触达**：定时催单（谁还没报）、经营卡简报（货损/工资/返利）推送站内 + 企微/飞书。

## 三、数据输入来源与输出去向

### 输入来源
1. **小程序填报**：员工选门店 + 商品 + 数量 → `POST /api/forecast-submissions`。
2. **Web 交叉表 Excel 导入**：文员/老板上传「行=商品、列=客户、格=数量」表 → `POST /api/import`（category=`forecast_cross`），逐客户生成 `role='导入'` 报单。
3. **Web 交叉表编辑保存**：`POST /api/forecast-submissions/save-matrix`，把编辑后的矩阵重写回 `role='导入'` 报单（幂等先清后写）。
4. **主数据**：`products`、`contacts`（门店）、`users`、`employee_stores`（员工可报门店范围）、`rebate_contracts`、`purchase_orders`（返利/采购额口径）。
5. **实时派生数据**：`sale_orders/sale_order_items` 近 30 天销量、`inventory` 当前库存 → 驱动 AI 建议量与可销天数。

### 输出去向
- **汇总总表**：老板/文员看板（`/summary`，跨角色聚合 + 来源明细）。
- **采购申请单**：单条预报审批通过时聚合生成 `purchase_requisitions`（`pending_approval`）。
- **周期定稿**：`forecast_audit_decisions`（人点定稿），是付款、舟谱模板、返利测算的共同数据源。
- **舟谱订单导入 CSV**：`/zhoupu-template` 确定性生成（utf-8 BOM），供人工粘贴厂家系统。
- **通知触达**：催单、付款提醒、经营卡简报 → 站内 `message_send` + 企微/飞书。
- **AI 留痕**：`log_workflow_advice` 写入 `ai_advice_log`（提交、审批、定稿均留痕，供副驾回溯）。

## 四、关键处理步骤与执行顺序

### 步骤 1 · 身份与权限初始化
- 登录拿 token（`auth.py`）；`role` 决定接口可见范围（汇总/审批仅 `admin/boss/accountant/supervisor`），`employee_code` 决定小程序可报门店范围。
- 小程序 `login.js` 已登录跳过登录；`api.js` 遇 401 清态并 `reLaunch` 登录页。
- 所有业务接口以 `_auth(request)` 校验 token；`role` 与 `price` 一律以服务端为准，不信任客户端传入。

### 步骤 2 · 报单数据采集（两条入口）
- **小程序入口**：`fill` 选门店（持久化到 Storage，避免跨 tab 错配）→ 搜商品（带防抖）→ 加购物车 → 提交。
  - 后端依次做：门店越权校验（门店 id 必须 ∈ 员工可报范围，否则 403）→ 幂等判断（同日同人同店重复提交=覆盖，已审批则 409）→ 明细清洗（`price` 后端按 `product_id` 查权威价、`product_id` 容错跳过非法明细）→ 落库 `status='pending'`。
- **Web 交叉表入口**：`forecast_cross` 导入识别商品列 + 客户列，逐客户生成 `role='导入'` 报单（幂等先清后写，不碰小程序报单）；并从商品名解析下单主体（恒滋/福宝）、从排期文本提取到货提前天数回写 `products`。

### 步骤 3 · 数据汇聚（汇总）
- `GET /summary?date` 或 `?start&end` → `forecast_submission_summary`：按 SKU + 单位跨角色聚合 `total_qty/total_amount`，附 `sources`（user_id、role、store、数量）。
- 口径约束：`role='导入'` 不计入「应报/已报」统计；被驳回（`status='rejected'`）的预报不计入订货总量。
- 对人名批量 `IN` 查询 `users` 主库补 `display_name`（避免 N+1）。

### 步骤 4 · 状态流转（单条审批流）
- 老板看 `GET /pending`（仅管理员）→ `POST /{sid}/approve`：状态置 `approved` 并聚合明细生成 `purchase_requisitions`（`pending_approval`）。
- 或 `POST /{sid}/reject`：状态置 `rejected`（后续不被汇总计入）。
- 这是「单条提交」维度的旧审批流，与步骤 5 的周期定稿流并存。

### 步骤 5 · 周期级 AI 审核（护城河，Web 交叉表）
- `POST /audit-period {start,end}`：取窗口汇总 → `_audit_items` 逐 SKU 计算 `建议量 = max(0, 日均销量×(lead+到货周期)+安全库存 − 当前库存)`，给出缺货/积压/吻合判定，并附厂家返利冲量提示。
- **纯只读**，AI 只建议不下单。
- 人点「定稿」→ `POST /audit-period/adopt {items:[final_qty...]}`：幂等写 `forecast_audit_decisions`（同窗口先清后写，绝不自动触发真实下单）。

### 步骤 6 · 下游闭环
- **余额 & 付款** `POST /payments/compute`：订单金额 = Σ(`decisions.final_qty` × 出厂价) − 厂家余额 → 应付差额；落 `period_payments(pending)` 并推送。
- **到账确认** `POST /payments/confirm`：标记 `paid` 并通知「可生成下游订单/舟谱模板」。
- **舟谱模板** `POST /zhoupu-template`：Σ(`decisions.final_qty>0`) → CSV 下载。
- **返利测算** `POST /rebate-gap`：基于 `rebate_contracts` + `purchase_orders` 当年采购额，算当前档/下一档/缺口/冲档收益。

### 步骤 7 · 定时催单与经营卡（scheduler）
- 每天 9:00 / 16:00 `_push_forecast_reminder`：遍历所有租户 → `_forecast_reminder_state`（当前开放周期 + 应报/已报/未报单元）→ 推送未报者（站内 + 企微/飞书）。
- 每天 8:05 `_push_copilot_cards_brief`：货损/工资/返利三卡简报（与预报同源的 AI 经营副驾推送能力）。

## 五、步骤间调用与依赖关系

```
登录(auth) ──前置依赖──► 所有业务接口
                              │
        ┌─────────────────────┴─────────────────────┐
   小程序提交(fill)                            Web 交叉表(import / save-matrix)
        │ 写入                                      │ 写入(role='导入')
        ▼                                          ▼
   forecast_submissions(status='pending') ────────┘
        │
        ├─► 汇聚 summary ◄── 依赖 products / inventory / sale_orders（近30天销量）
        │        │
        │        ├─► 单条审批流 approve ──► purchase_requisitions(pending_approval)
        │        │            reject ──► status='rejected'（不计入汇总）
        │        │
        │        └─► 周期审核 audit-period ──► adopt ──► forecast_audit_decisions(定稿)
        │                                                  │
        │                          ┌───────────────────────┼──────────────────┐
        │                          ▼                       ▼                  ▼
        │                  payments/compute      zhoupu-template      rebate-gap
        │                  payments/confirm
        │
   scheduler._push_forecast_reminder ──► 依赖 summary 统计「应报/已报/未报」
```

**关键依赖约束（已确认的事实）**
- 权限：汇总/审批/定稿/付款/舟谱/返利均要求 `admin/boss/accountant/supervisor`；提交要求合法员工 + 门店在授权范围。
- 数据权威：`role` 与商品 `price` 一律服务端计算，客户端传入被忽略（防伪造/防厂价泄露）。
- 租户隔离：写操作经 `get_db_tx()` 租户上下文；`forecast_audit` 用 `_connect()` 同为租户感知；`scheduler` 遍历 `tenant_*.db` 逐个 `set_tenant_context`。
- 幂等：提交（同日同人同店覆盖）、Excel 导入（先清 `role='导入'` 后写）、定稿（先清窗口后写）三处均幂等，避免汇总叠加放大。

## 六、Web 端与小程序的优化方案

### Web 端（hergent-cn-v2 / Forecast.vue）
**性能**
- 交叉表「最终下单列」目前依赖前端二次聚合 `forecast_audit_decisions`；建议后端在 `/summary` 直接 `LEFT JOIN decisions` 返回 `final_qty`，减少前端拼装与额外请求。
- AI 审核弹窗一次算整周期全部 SKU（可能数百行），UI 易卡顿；可改为**分页/分批滚动计算**或后台任务，先出已渲染部分。
- Excel 导入预览目前前端只展示前 4 行 × 12 列；建议服务端在 `preview` 阶段就返回**校验摘要**（未匹配商品数、客户列识别数、计算列误识别告警），让文员在确认前就发现脏数据。

**交互 / 流程**
- **两条状态机并存**（单条审批流 vs 周期定稿流）语义重叠，老板易混淆。建议收敛为**单一主流（周期定稿流）** 作为唯一闭环，旧审批流降级为只读历史。
- 定稿后的「付款 → 舟谱模板 → 返利」目前分散在多个弹窗/按钮；建议做成**一屏向导式串联**，减少跳转与遗漏。
- 返利冲档测算依赖 `rebate_contracts` 绑定口径，未绑定时前端**静默算 0** 易误导；应显式提示「该供应商未绑定总指标，请先录入合同」。

### 小程序端（forecast-order-miniprogram）
**性能**
- 商品搜索每次输入发 2 个串行请求（模糊匹配 + 列表）；虽已加防抖，仍可合并为**单接口返回（商品+库存+日均销量）**，减少 RTT 与竞态。
- 购物车存页面实例属性，跨 tab 不丢但依赖 `onShow` 不再重置（已修复）；更稳妥做法是放到 `globalData`/本地 `Storage`，降低页面销毁风险。

**交互 / 流程**
- 提交成功后**无「今日已报」回执**，员工不确定是否成功。建议提交成功显示「今日 XX 店已报 N 件」，并提供「查看/修改」入口。
- 门店选择可加「最近报单门店」快捷入口（从 `my` 历史取），减少每次翻找。
- **弱网/离线无草稿缓存**：断网填报会丢单。建议加本地 `Storage` 草稿，联网后自动补传（与提交幂等天然兼容）。
- 登录页目前无注册/找回（一人公司可接受），但应保证 401 自动跳登录后**回跳原页面**而非强制首页。

## 七、关键风险与边界（事实层面）
- **两条状态机并存**：单条审批流（`forecast_submissions.status` → `purchase_requisitions`）与周期定稿流（`forecast_audit_decisions`）目前都能跑通，但口径与出口不同，需产品层收敛。
- **下游降级为人工**：蒙牛/舟谱无开放 API，最终「粘贴厂家系统下单」是人工粘贴 CSV（战略一致），系统只负责生成模板，不承诺自动直连。
- **统计口径易错点**：`role='导入'` 被排除出应报统计（避免文员导入被当员工报单）；`status='rejected'` 不计入汇总总量——这两处是汇总正确性的关键，改动 SQL 时需同步维护。
- **多租户靠 `tenant_N.db` 文件隔离** + `set_tenant_context`；`scheduler` 与手动催单共享同一状态计算函数，单租户失败不阻断其他租户（fail-closed）。
